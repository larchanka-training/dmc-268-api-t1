# AGENTS.md

Бэкенд агента автоматического ревью кода в пул- и мердж-реквестах: сервис собирает дифф,
достраивает контекст, прогоняет его через языковую модель по нескольким направлениям —
безопасность, корректность, производительность, читаемость — отсеивает ложные срабатывания и
публикует сводку и комментарии к строкам. Конвейер целиком будет описан в
`docs/SYSTEM_DESIGN.md` — документ готовится в PR #6.

Перед тем как писать код, прочитайте [`.agents/rules/backend.md`](.agents/rules/backend.md) —
команды, слои, швы и тесты. Перед работой с ветками, задачами и пул-реквестами —
[`.agents/rules/git-and-pr.md`](.agents/rules/git-and-pr.md).

## Правила, которые нельзя нарушать

Они здесь целиком, а не ссылкой: ссылку агент может не открыть.

- Зависимости ставим и обновляем **только через `uv`**: `uv sync --all-extras`. Ни `pip`, ни
  `poetry`, ни правка `requirements.txt`.
- Python 3.14, версия зафиксирована в `.python-version` и в `requires-python`.
- Проверки перед коммитом: `uv run ruff check .`, `uv run lint-imports`, `uv run pytest`.
  Пропущенный тест приравнивается к упавшему — CI падает, если тест пропустили.
- Схему базы данных меняет **только миграция Alembic**. Приложение не создаёт и не меняет
  объекты схемы ни при старте, ни во время работы. Ревизия должна быть одна:
  `uv run alembic heads`.
- Поведение сервиса меняется **только через OpenSpec-change**. Каталог `openspec/specs/`
  руками не правится: сначала change, потом реализация, потом синхронизация спеки.
- Зависимости направлены внутрь: `app/domain` и `app/application` не знают про SQLAlchemy,
  FastAPI и прочих вендоров. Правило проверяет `uv run lint-imports`, а не ревью.
- Работаем по git flow. Рабочая ветка отводится **от `develop`** и пул-реквестом мёржится
  **в `develop`**. В `main` попадает только то, что уже прошло `develop`; напрямую в `main`
  и в `develop` не коммитим.
- Имена веток: `feat/…`, `fix/…`, `deps-update-YYYY-MM-DD`. Коммиты — conventional commits.
  У пул-реквеста обязательны осмысленный заголовок и описание: это первый контекст,
  который получает ревью-бот.
- Всё, что делается на GitHub — задачи, пул-реквесты, доска, привязки, — делаем **через `gh`**.
  Если у команды нет готовой формы, берём `gh api` или `gh api graphql`: подзадачи и привязка
  пул-реквеста к задаче в другом репозитории делаются именно так. Руками через веб — только
  когда не умеет и API.
- Задача, которую надо делать в обоих репозиториях, заводится **родительским issue и двумя
  sub-issues** — `— backend` и `— frontend`, по одному на стек, каждый со своим пул-реквестом.
  Постановка и DoD живут в родителе, в подзадаче — только её половина. Родитель закрывается
  последним, когда закрыты обе.
- Пул-реквест **всегда привязан к своей задаче**. В том же репозитории — `Closes #N` в описании.
  В другом репозитории ключевое слово не работает: привязываем через панель Development на
  странице пул-реквеста. Без привязки задача не считается взятой в работу.
- Замечание с ревью закрываем **в его треде**, и резолвит тот, чьё требование выполнено:
  - **нужна правка** — правим, пишем в треде одной строкой, что поправлено, и резолвим сами;
  - **вопрос без правки** — отвечаем по существу и **тред не резолвим**: его закрывает
    задавший, когда ответ его устроил;
  - **не согласны** — аргумент в треде, тред остаётся открытым, решает автор замечания.

  Молча резолвить нельзя. Когда правки по всем тредам готовы, **перезапрашиваем ревью** у
  автора замечаний — одним запросом на всю пачку, а не на каждый коммит.
- Пишем **по-русски всё**: документацию, комментарии в коде, тексты задач, заголовки и описания
  пул-реквестов, ответы в тредах ревью, артефакты OpenSpec и промпты продукта, включая строки
  формата вывода. Английскими остаются имена в коде, команды, названия инструментов и термины
  без устоявшегося русского эквивалента: такой термин пишем как есть, кальку не изобретаем.
