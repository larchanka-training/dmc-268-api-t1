# Пользовательские правила

Формат правил, которые задаёт владелец репозитория, и как сервис их читает.
Инструкции модели о том, как применять правила и ссылаться на их пункты, - в
[`output-format.md`](output-format.md): этот файл модели не отправляется.

## Формат правила

Четыре части; обязательны паттерн, имя и проверки, исключение — нет (без него правило действует
на все файлы под паттерном). Схема правила (так его видит агент; в `.review/rules.md` владелец
пишет те же части Markdown'ом — см. ниже):

```yaml
- pattern: "app/**/*.py"        # на какие файлы распространяется
  exclude: "**/tests/**"        # что исключено
  name: "Error Handling Standards"
  checks:                       # нумерованный список конкретных проверок
    - "Отказ возвращается значением Result, а не исключением"
    - "Текст ошибки содержит данные, по которым её можно воспроизвести"
    - "Пойманное исключение либо обработано, либо переброшено с контекстом"
```

Правило без `checks` не принимается: общий призыв («пишите надёжный код») проверкой не является.

## Файл `.review/rules.md`

Владелец кладёт правила в `.review/rules.md` своего репозитория. Те же четыре части пишутся
Markdown'ом: раздел второго уровня — правило, строки `pattern:` и `exclude:` — область действия
(их может быть несколько), нумерованные пункты — проверки.

```markdown
## Error Handling Standards

- pattern: `app/**/*.py`
- exclude: `**/tests/**`

1. Отказ возвращается значением Result, а не исключением
2. Текст ошибки содержит данные, по которым её можно воспроизвести
3. Пойманное исключение либо обработано, либо переброшено с контекстом
```

Как сервис его читает:

- **Только из целевой ветки.** Файл берётся с коммита `base_sha` — того, куда вливается PR.
  Изменение правил внутри PR действует после мерджа: иначе автор PR сам выбирал бы, по каким
  правилам ревьюить его код.
- **Только распознанные поля.** Абзацы, подзаголовки и блоки кода между правилами модели не
  передаются. Правило, у которого не хватает части, отклоняется с причиной — она видна в
  сохранённом контексте прогона.
- **Паттерны — как в `.gitignore`.** Шаблон без `/` (кроме завершающего) совпадает с именем
  файла на любой глубине: `*.py` — это `**/*.py`. Шаблон совпадает и с файлом,
  и с содержимым каталога такого имени: `docs` заденет `docs/a.md`, `app/api` — `app/api/x.py`.
  Завершающий `/` — только каталог: `app/` — каталог `app` на любой глубине со всем
  содержимым. `/` в начале или середине привязывает шаблон к корню репозитория: `/app/*.py`
  и `app/*.py` не заденут `lib/app/x.py`. `*`, `?` и `[!…]` действуют внутри одного сегмента
  и не совпадают со `/`: через каталоги проходит только `**`.
- **Блоки кода — по CommonMark.** Закрывает блок ограда того же символа (``` или `~~~`), не
  короче открывающей, без текста после неё; отступ ограды любой, так что пример кода внутри пункта списка — тоже
  блок. Незакрытый блок
  съедает остаток файла, поэтому разделы правил внутри него отклоняются с причиной
  «незакрытый блок кода».
- **Заголовок — имя правила.** Закрывающие `#` срезаются только после пробела: `## C#` — правило
  `C#`, `## Имя ##` — правило `Имя`.
- **Только применимые правила.** В контекст прогона попадает правило, под паттерн которого
  попал хотя бы один изменённый файл, — вместе со списком этих файлов.
- **Имя правила уникально.** По имени замечание ссылается на правило, поэтому второй раздел с
  тем же именем отклоняется с причиной «имя правила повторяется»; первый остаётся.
- **Пункты нумеруются по порядку.** Номер пункта - его позиция среди проверок правила, с
  единицы; номера, которые написал автор (`1.`, `1.`, `5.`), значения не имеют.
- **Без файла — стандартные критерии.** Нет файла, он больше лимита размера или недоступен —
  ревью идёт по стандартным критериям, прогон не прерывается.

## Атрибуция

Замечание по правилу модель возвращает со ссылкой на пункт: имя правила и номер пункта.
Сервис проверяет ссылку - правило было показано модели, применимо к файлу замечания, пункт существует - и сам начинает комментарий префиксом:
`Согласно пользовательскому правилу «<имя>» (пункт <N>: <текст пункта>): <замечание>`.
Замечание по стандартным критериям префикса не несёт: по комментарию видно, чьё правило сработало - владельца репозитория или сервиса.
Замечание со ссылкой на правило, которого модель не видела, или на чужой файл отклоняется целиком.

Форма префикса взята из разбора реального прогона, где она выглядела как
`According to custom instructions in '[rule name]' ([summary]): [comment]`; переведена, потому
что комментарии ревью пишутся на языке проекта.

## Стартовый набор

Это подсказка владельцу, а не правила по умолчанию: сервис их не подставляет. Нет
`.review/rules.md` — ревью идёт по стандартным критериям, без префикса атрибуции.

| Имя | О чём |
|---|---|
| Naming Consistency | имена соответствуют словарю проекта и одинаковы в слоях |
| Error Handling Standards | отказ — значение, текст ошибки воспроизводим |
| Complex Function Improvement Suggestions | функция с несколькими ответственностями разделяется |
| Meaningful Comments for Complex Logic | комментарий объясняет почему, а не что |
| Test Coverage for Complex Functions | ветвление правила покрыто тестом без инфраструктуры |
