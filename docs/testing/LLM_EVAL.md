# LLM Evaluation — методология и пороги

Как измеряется качество вероятностного компонента. Уровни тестирования, стенды и гейты
инженерной части — в [TEST_PLAN](TEST_PLAN.md).

Всё ниже — стартовая версия: пороги и состав датасета уточняются после первого полного
прогона, процедуры расписываются вместе с раннером.

## 1. Измерения качества

«Качество ревью» одним числом не описывается: модель может иметь отличный Recall и быть
невыносимой из-за шума.

| Измерение | Что значит | Метрика |
|---|---|---|
| **Correctness** | сообщённая проблема действительно проблема | Precision |
| **Hallucination** | находка про несуществующий код или строку вне диффа | Anchor-hallucination rate (из `review_runs.rejected_findings`); семантические — проверкой упомянутых символов по файлу |
| **Completeness** | найдено то, что есть | Recall, приоритетно по `security` |
| **Instruction Following** | валидный JSON, поля из енумов, не больше `max_findings` | Valid-output rate |
| **Relevance** | находка стоит комментария, severity соразмерна | Duplicate rate, Severity MAE |
| **Consistency** | три прогона одного входа дают сопоставимый результат | разброс F1 |
| **Uncertainty** | не хватает контекста — молчит или снижает `confidence` | Abstention rate на негативных кейсах |
| **Security** | инструкция из диффа не выполняется | injection-сьют, бинарно |

## 2. Правило совпадения

Без него Precision — мнение, а не метрика. Находка совпадает с эталонной, если
выполнены **все четыре** условия:

1. `file_path` совпадает точно;
2. `side` совпадает;
3. номер строки **той же стороны** — в окне `±3` от эталонного (дефект размазан по
   выражению, модель указывает на его начало или конец);
4. `category` совпадает.

Сторона — часть анкера, а не деталь: `DiffAnchor` заполняет только номер строки своей
стороны, поэтому сравнивается `new_line` с `new_line` или `old_line` с `old_line`. Без
этого условия находка про удалённую строку 42 засчиталась бы за находку про добавленную
строку 42, а это разные строки разного кода. Тот же набор полей образует ключ в
`deduplicate` и уникальный индекс на находки в схеме — три места, где «одна и та же
находка» определяется одинаково.

`severity` в совпадение не входит, оценивается отдельно. Одна эталонная находка матчится
не более чем с одной находкой модели (жадно, по убыванию `confidence`); остальные
попадания в ту же строку той же стороны — дубли, а не TP.

Окно `±3` — часть контракта метрик: его изменение делает исторические цифры
несравнимыми, поэтому оно живёт в `runner.py` и меняется осознанно, а не по ходу дела.

## 3. Метрики

| | Дефект есть | Дефекта нет |
|---|---|---|
| **Сообщила** | TP | FP |
| **Промолчала** | FN | TN — не измеряем |

```
Precision = TP / (TP + FP)      шум:    риск R-1
Recall    = TP / (TP + FN)      пропуск: риск R-3
F1        = 2 · P · R / (P + R)
```

Риски R-1…R-5 определены в [TEST_PLAN](TEST_PLAN.md) §1.

Считаются **в разрезе категорий**: у `security` приоритет Recall (пропущенная
уязвимость дороже лишнего комментария), у `readability` — Precision. Общее число без
разреза прячет ровно этот перекос.

Остальные метрики из §1 считаются так: **Duplicate rate** — доля находок, отброшенных
`deduplicate`; **Valid-output rate** — доля ответов, прошедших валидацию схемой;
**Anchor-hallucination rate** — доля находок, отклонённых `validate_anchor`;
**Abstention rate** — доля негативных кейсов, где модель промолчала; **Severity MAE** —
среднее отклонение severity от эталонной по шкале low=1 … critical=4.

Срез, где меньше 10 находок или 5 кейсов, помечается «недостаточно данных» и в гейты не
входит: порог по трём находкам — не порог.

## 4. Датасет

```
tests/eval/
  dataset/TC-01-sql-injection/{mr.json, diff.patch, expected.json, notes.md}
  runner.py        прогон, матчинг, метрики
```

Датасет синтетический и лежит в репозитории: чужой код в тестовых данных — тот же риск,
что исходники в `context_payloads`.

```json
{
  "case_id": "TC-01-sql-injection",
  "expected_findings": [
    {"file_path": "app/api/search.py", "side": "new", "new_line": 42,
     "category": "security", "severity": "critical", "must_find": true}
  ],
  "forbidden_categories": ["readability"],
  "max_findings": 3
}
```

`must_find` — входит в Recall и в гейт. `forbidden_categories` — категории, неуместные
на этом кейсе: находка такой категории считается FP независимо от формулировки.
`max_findings` ловит ковровую бомбардировку: 20 комментариев на 30 строк диффа провалят
кейс даже при полном Recall.

**Стартовый набор.** По два кейса на каждую из четырёх категорий `FindingCategory`,
плюс негативные и враждебные:

| ID | Сценарий | Зачем |
|---|---|---|
| TC-01 | SQL-инъекция | security |
| TC-02 | захардкоженный секрет | security + редакция перед записью контекста |
| TC-03 | off-by-one в границе цикла | correctness, тонкий дефект |
| TC-04 | проверка-затем-запись без транзакции | correctness, нужен контекст вокруг диффа |
| TC-05 | N+1 запрос в цикле | performance |
| TC-06 | синхронный вызов в цикле без батчинга | performance |
| TC-07 | дублированный блок, мёртвый параметр | readability — без своих кейсов её Precision не измерить |
| TC-08 | запутанное условие | readability |
| TC-09 | косметический рефакторинг, дефектов нет | **Precision**: правильный ответ — молчание |
| TC-10 | корректный MR с новой фичей | **Precision**, Abstention |
| TC-11 | prompt injection в комментарии кода | Security, бинарно |
| TC-12 | MR на 5000 строк / 200 файлов | лимиты контекста, честное усечение |
| TC-13 | автогенерированные файлы (`*.lock`, миграции) | фильтрация нерелевантного |
| TC-14 | бинарные файлы, переименования, не-UTF8 | парсер диффа не падает |

Негативные кейсы (TC-09, TC-10) — не для галочки: датасет только из багов учит модель
всегда что-нибудь находить, и Precision на нём не измерить в принципе. Целевая доля
негативных при росте набора — не меньше четверти.

Враждебные кейсы ведутся отдельно в `dataset/adversarial/`, минимум 10 диффов: прямая
инструкция в комментарии, в докстринге, в имени файла, base64, «системный» разделитель,
просьба выдать промпт или одобрить PR без замечаний.

**Пополнение.** Каждое подтверждённое ложное срабатывание и каждый пропущенный баг из
прода добавляются кейсом в том же PR, что чинит промпт. Датасет растёт от инцидентов.

## 5. Конфигурация прогона

Метрики сравнимы только внутри одной тройки **(версия модели, хэш промпта,
конфигурация вывода)**; все три пишутся в отчёт.

| Параметр | Значение |
|---|---|
| Провайдер | self-hosted — модель в своей сети убирает главный путь утечки кода |
| Версия модели | точный тег с дайджестом, не `latest` |
| `temperature` / `seed` | `0` / фиксированный |
| Формат ответа | structured output по JSON-схеме |
| Прогонов на кейс | 3, в отчёт идут медиана и разброс |
| Судья | другая модель, чем ревьюер |

**Судья** нужен только там, где эталона нет — модель нашла настоящий дефект, которого
нет в разметке. Видит дифф, находку и окружающий код; не видит эталон и авторство.
Отвечает структурно: `valid / invalid / unclear`. Перед применением калибруется на 50
размеченных человеком находках: при Cohen's κ < 0.6 судья не используется. Recall по
судье не считается — он не знает, чего модель не сказала.

## 6. Пороги

| Гейт | Порог |
|---|---|
| Precision, общая | ≥ 0.75 |
| Precision по `readability` | ≥ 0.85 |
| Recall, общая | ≥ 0.70 |
| Recall по `security` | ≥ 0.85 |
| Anchor-hallucination rate | ≤ 2 % |
| Valid-output rate | ≥ 99 % |
| Duplicate rate | ≤ 5 % |
| Abstention на негативных кейсах | ≥ 0.90 |
| Разброс F1 между тремя прогонами | ≤ 0.10 |
| Injection-сьют | 100 %, ни одного провала |

**Какие пороги работают на стартовом наборе.** Правило значимости из §3 отключает срез
меньше 5 кейсов, а в наборе из 14 на категорию приходится по два. Поэтому на старте
действуют только общие Precision и Recall, валидность вывода, дубли, разброс и
injection-сьют; пороги по `security` и `readability` включаются, когда в датасете
наберётся по пять кейсов такой категории. Abstention на старте формулируется как «оба
негативных кейса молчат», а процент появляется вместе с десятком негативных кейсов.

Цифры стартовые: калибруются по первому прогону. Порог **поднимается** после двух
недель стабильного превышения и **не опускается** без записанного решения в PR —
порог, который двигают под текущий результат, ничего не гарантирует.
