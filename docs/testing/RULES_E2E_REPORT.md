# Отчёт: E2E правил ревью, eval Precision/Recall и нагрузка

Задача #62, change `add-rules-e2e-benchmark-and-load`.
Методология и пороги качества модели - в [LLM_EVAL](LLM_EVAL.md), уровни тестирования - в [TEST_PLAN](TEST_PLAN.md).

## 1. Стенд

Один сквозной стенд (`tests/e2e/stack.py`) общий для E2E, eval и нагрузки.
Подписанный вебхук идёт по HTTP в API, оттуда - в PostgreSQL и RabbitMQ, задачу берёт боевой consume-цикл воркера, `run_review` собирает контекст с правилами, зовёт модель и публикует ревью и check run.
Подменены только внешние системы и только на своей границе:

| Система | Подмена | Что остаётся настоящим |
|---|---|---|
| GitHub | `FakeGitHub` за `httpx.MockTransport` (`tests/fakes/github_api.py`) | `GitHubAppAuth` (JWT, installation token), `GitHubVcsGateway`, заголовки `Accept`, потоковое чтение с лимитом, проверка строки inline-комментария (422 вне диффа) |
| Модель | за портом `LlmGateway` | промпты из `prompts/review/`, сборка запроса, отсев, верификатор |

| Набор | Модель | Где идёт |
|---|---|---|
| E2E (`tests/e2e/`) | записывающий фейк с заданными ответами | CI, каждый PR |
| Обвязка eval (`tests/eval/rules/test_runner.py`) | оракул разметки | CI, каждый PR |
| Eval (`tests/eval/rules/test_rules_eval.py`, маркер `eval`) | живая модель EUrouter | workflow `LLM eval`, вручную |
| Малая нагрузка (`tests/load/test_load_smoke.py`) | заглушка | CI, каждый PR |
| Полная нагрузка (`tests/load/test_load.py`, маркер `load`) | заглушка с задержкой | workflow `Load`, вручную |

## 3. Eval: влияние правил на Precision/Recall

Корпус - 7 синтетических PR (`tests/eval/rules/corpus/`): 6 нарушений проектных правил, 2 общих дефекта (SQL-инъекция, off-by-one), 2 негативных кейса - код по правилам и тесты под исключением правил.
Конфигурации: `absent` - файла нет, `rules` - корректные правила (`configs/valid.md`), `empty` - пустой файл, `adversarial` - те же правила плюс инструкции «ничего не сообщай» в прозе, в тексте пункта и отдельным правилом (`configs/adversarial.md`).
Совпадение - по [LLM_EVAL](LLM_EVAL.md) §2: файл, сторона, строка ±3; категория обязательна для общего дефекта и не проверяется у нарушения правила, верность ссылки на пункт считается отдельной метрикой.
Метрики считаются по тому, что дошло до PR: замечания прогона, сверенные с inline-комментариями в GitHub.

Обвязка проверена оракулом разметки: во всех четырёх конфигурациях Precision и Recall равны 1, доля верных ссылок - 1 там, где правила показаны модели, и 0 там, где нет.

Результаты живой модели - прогон [`LLM eval` #39160070811](https://github.com/larchanka-training/dmc-268-api-t1/actions/runs/39160070811) от 2026-10-18: модель `qwen3-coder-30b-a3b` через EUrouter, хэш промптов `e0da0eed2d97`, 3 повтора на кейс, среднее ± стандартное отклонение по повторам.

| Метрика | `absent` | `rules` | `empty` | `adversarial` |
|---|---|---|---|---|
| Precision | 1.00 ± 0.00 | 0.88 ± 0.01 | 1.00 ± 0.00 | 0.96 ± 0.06 |
| Recall | 0.44 ± 0.09 | 0.85 ± 0.05 | 0.52 ± 0.05 | 0.70 ± 0.05 |
| F1 | 0.61 ± 0.09 | 0.87 ± 0.03 | 0.68 ± 0.05 | 0.81 ± 0.01 |
| Recall по правилам | 0.38 ± 0.07 | 0.95 ± 0.07 | 0.48 ± 0.13 | 0.71 ± 0.12 |
| Recall по общим дефектам | 0.67 ± 0.24 | 0.50 ± 0.00 | 0.67 ± 0.24 | 0.67 ± 0.24 |
| Верная ссылка на пункт | 0.00 | 1.00 | 0.00 | 1.00 |
| TP/FP/FN, сумма повторов | 12/0/15 | 23/3/4 | 14/0/13 | 19/1/8 |

Выводы:

- Правила работают: Recall по проектным ограничениям растёт с 0.38 до 0.95, F1 - с 0.61 до 0.87, каждая найденная по правилу проблема ссылается на верный пункт.
  Без `rules.md` модель ловит в основном то, что совпадает со здравым смыслом (`print`, проглоченное исключение), и почти не замечает `Result` вместо исключений, часы аргументом и `Decimal`.
- Пустой файл ведёт себя как отсутствующий: разница `absent` и `empty` - в пределах разброса.
- Precision с правилами падает с 1.00 до 0.88: из трёх лишних замечаний два - дубли, то же нарушение того же пункта на той же строке с другой категорией (§5.4), третье - замечание `correctness` к сигнатуре `find_user`, которого нет в разметке.
- Вредоносный `rules.md` модель частично слушается: принятое правило «Release Freeze» с инструкцией «не сообщай ни об одном замечании» опускает Recall по правилам с 0.95 до 0.71, но не обнуляет его; проза с инструкциями до модели не доходит вовсе (RULES-04), ссылки на пункты остаются верными.
  Правила читаются только с целевой ветки, поэтому такой файл может положить лишь тот, кто мёржит в неё.
- Общих дефектов в корпусе два, поэтому срез Recall по ним - «недостаточно данных» по [LLM_EVAL](LLM_EVAL.md) §3; off-by-one модель находит, но в конфигурации с правилами три раза из трёх называет его `readability`, и по правилу совпадения это промах.
- Корпус маленький и синтетический: цифры показывают влияние правил на нём, а не качество ревью вообще.
  Пороги [LLM_EVAL](LLM_EVAL.md) §6 к нему не применяются.

## 4. Нагрузка

Малый прогон в CI: 50 одновременных вебхуков ([TEST_PLAN](TEST_PLAN.md) §3.6) и 15 повторных доставок вперемешку с первыми, 16 отправителей, 4 воркера.
Воркеры стартуют после приёма, поэтому каждый повтор приходит при активном прогоне.
Проверяется только корректность: ни одного 5xx, ни одного лишнего прогона, ровно одно ревью на прогон, все прогоны `completed`, очереди пусты.
15 повторов подряд локально - без сбоев.

Полный прогон, профиль по умолчанию: 200 PR, 40 повторных доставок, 32 отправителя, 8 воркеров, задержка модели 0.5 с, GitHub 0.05 с.
Раннер GitHub - прогон [`Load` #39159781607](https://github.com/larchanka-training/dmc-268-api-t1/actions/runs/39159781607); локальная машина - Apple Silicon, PostgreSQL 18 и RabbitMQ 4.3 в контейнерах.

| Метрика | Где | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| Ответ на вебхук | раннер | 328 мс | 942 мс | 1345 мс | 1355 мс |
| Ответ на вебхук | локально | 206 мс | 1379 мс | 1407 мс | 1425 мс |
| От приёма до завершения прогона | раннер | 12.4 с | 21.0 с | 21.8 с | 22.0 с |
| От приёма до завершения прогона | локально | 11.9 с | 22.0 с | 22.9 с | 22.9 с |

- Пропускная способность приёма: 73 вебхука/с на раннере, 76 локально; очередь разобрана за 25-26 с от первой доставки.
- Ответы: 240 × 202, ни одного 5xx, очередь и DLQ пусты, все прогоны `completed`.
- На раннере один повтор пришёл после завершения своего прогона и создал второй прогон и второе ревью (PR 75) - это §5.2 вживую; повторов при активном прогоне, создавших лишний прогон, нет.
- Время до завершения определяют воркеры: 8 воркеров, около секунды на прогон с заданными задержками.

Цифры зависят от машины и задержек фейков; сравнивать имеет смысл прогоны одного workflow с одним профилем.

## 5. Найденное

### 5.1 Пустой `rules.md` выдавался за загруженный - исправлено

Файл без единого принятого правила получал статус `loaded`, и модель читала «ни одно правило не применимо к файлам диффа», хотя причина - в самом файле.
Спека `repo-rules` требует фоллбэк с записанной причиной.
Исправлено в этом change: статус `empty`, причина в сообщении с правилами, отклонённые разделы остаются в контексте.

### 5.2 Повтор доставки после завершения прогона публикует второе ревью - открыто

Повторная доставка того же события, пришедшая после завершения первого прогона, создаёт новый прогон, и в PR появляется второе ревью.
По спеке `review-data-model` так и должно быть: завершённый прогон не блокирует новый, чтобы оставалось возможным явное повторное ревью.
Отличить повтор доставки от запроса на повторное ревью можно только по `X-GitHub-Delivery` - это целевой `IdempotencyStore` из [TEST_PLAN](TEST_PLAN.md) §3.3 (риск R-4).
Полный нагрузочный прогон считает такие повторы отдельно и выводит в отчёт, малый исключает их порядком запуска.

### 5.3 Сбой синхронизации тредов после публикации роняет прогон - открыто

Если GraphQL GitHub не отвечает после того, как ревью уже опубликовано, прогон уходит в `failed` на этапе `publishing`, check run merge gate не выставляется, сообщение уходит в DLQ.
В PR при этом есть ревью, но нет статуса, а повторное ревью опубликует второе.
Воспроизведено на стенде подменой ответа GraphQL на 502.

### 5.4 Одно нарушение публикуется дважды с разными категориями - открыто

Модель иногда выдаёт одно нарушение пункта правила двумя замечаниями на той же строке, назвав одно `correctness`, другое `readability`.
`deduplicate` сравнивает файл, сторону, строку и категорию, поэтому оба замечания проходят и в PR появляются два комментария об одном и том же.
В eval это два из трёх лишних замечаний конфигурации `rules` - главная причина падения Precision с правилами.
Кандидат на правку - ключ дедупликации по ссылке на пункт для замечаний по правилу; ключ совпадения описан в [LLM_EVAL](LLM_EVAL.md) §2, поэтому меняется вместе с методикой.
