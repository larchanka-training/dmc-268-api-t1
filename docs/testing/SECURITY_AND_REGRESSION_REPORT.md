# Отчёт: отказоустойчивость, регрессия инкрементального ревью и security-аудит

Задача #222. Change: `adopt-orphaned-review`, `bounded-rules-glob`, `review-on-base-change`, `queue-delivery-limit` (#223).
Уровни тестирования - в [TEST_PLAN](TEST_PLAN.md), прошлый отчёт по правилам и нагрузке - в [RULES_E2E_REPORT](RULES_E2E_REPORT.md).

## 1. Стенд и где идут наборы

Все сценарии идут на сквозном стенде `tests/e2e/stack.py`: подписанный вебхук по HTTP → API → PostgreSQL → RabbitMQ → боевой consume-цикл воркера → модель → GitHub.
Сбой подаётся там, где он случается в проде, а не подменой порта:

| Сбой | Как подаётся | Что остаётся настоящим |
|---|---|---|
| Модель: таймаут, `429`, обрыв, `5xx` | `FakeLlmProvider` за `httpx.MockTransport` (`tests/fakes/llm_provider.py`) | `OpenAiCompatibleGateway`: ротация ключей, разбор `429`, перевод таймаута в `LLM_TIMEOUT`, очистка ключей из текста ошибки; `FallbackLlmGateway` |
| GitHub: обрыв до запроса и после записи | `FakeGitHub.network_faults` (`NetworkFault`, `stored=True` - запрос выполнен, ответ потерян) | `GitHubVcsGateway`: цикл повторов, поиск ревью по маркеру |
| Смерть воркера | `WorkerDied(BaseException)` в нужной точке: consume-цикл его не ловит, сообщение не подтверждено | RabbitMQ возвращает сообщение при закрытии соединения, как при обрыве TCP умершего процесса |

| Набор | Где | Запуск |
|---|---|---|
| Chaos (`tests/chaos/`, маркер `chaos`) | job `chaos` в `ci.yml` | каждый PR, отдельной галочкой |
| Регрессия инкрементального ревью (`tests/e2e/test_incremental_review_e2e.py`) | job `test` | каждый PR |
| Security (`tests/security/`) | job `test` | каждый PR |
| Юнит-тесты исправлений (`tests/domain`, `tests/application`, `tests/infrastructure`, `tests/db`) | job `test` | каждый PR |

Ограничение стенда: смерть воркера имитируется исключением в потоке, а не `SIGKILL` процесса. Для брокера разница не видна (соединение закрывается без `ack`), но код `finally` consume-цикла выполняется - у настоящего `SIGKILL` его нет.

### 2.2 Сетевые сбои при постинге в GitHub

Ответ на `POST …/reviews` потерян после записи (502, таймаут), отказ лимита `429` с `Retry-After`, потеря списка inline-комментариев - покрыты сквозными тестами #185 (`tests/e2e/test_publish_no_duplicates_e2e.py`): ревью одно, найдено по маркеру. Chaos-сьют добавляет обрыв сети, совпавший со смертью воркера (§2.3).

Наблюдение: обрыв сети на GET (дифф, файлы) и на `POST /check-runs` не повторяется, повторы адаптера - только на `429`/`5xx` и на создании ревью. Сбой check run после публикации - best-effort (warning, прогон `completed`), сбой GET диффа - прогон `failed`.

### 2.3 Смерть воркера посреди обработки - `tests/chaos/test_worker_crash_chaos.py`

По спеке `review-pipeline` прогон захватывает один воркер, поэтому повторная доставка недоведённый прогон не продолжает, а переводит в `failed` (`REVIEW_RUN_STALE`), сообщение - в DLQ. Ревью затем даёт новый прогон (push, повтор вебхука).

| Точка смерти | Ожидание | Итог |
|---|---|---|
| Вызов модели | сообщение вернулось в очередь; повтор - `failed`, модель не вызывается, шаг `analysing` закрыт `REVIEW_RUN_STALE`; новый прогон публикует одно ревью | проходит |
| GitHub записал ревью, ответ не дошёл | повтор не постит второе ревью; новый прогон не дублирует замечание к той же строке | **падал - исправлено (§4.1)** |
| `POST /check-runs` после публикации | gate не выставлен до нового прогона; замечание не дублируется, новый прогон выставляет `failure` | проходит |

## 3. Регрессия инкрементального ревью - `tests/e2e/test_incremental_review_e2e.py`

Несколько push в один PR; каждый меняет код в другом месте, модель на каждом прогоне снова находит старую проблему. GitHub переносит тред на новую строку (`FakeGitHub.moved_threads`).

| Сценарий | Ожидание | Итог |
|---|---|---|
| Коммит сдвинул строку с замечанием (3 → 5), строка не менялась | второго комментария нет, находка связана с тредом, gate `failure` | проходит |
| Третий коммит добавил новую проблему | публикуется только новая, старая - ни разу больше | проходит |
| Модель оценила старую проблему мягче | комментарий не повторяется | проходит |
| Контроль: строку с замечанием изменили (тред устарел) | замечание к новой версии строки публикуется | проходит |

Чувствительность проверена: без переноса треда на новую строку три сценария из четырёх падают дублем.

## 4. Найденное и исправленное

### 4.1 Дубль замечания после смерти воркера на публикации - исправлено

Воркер умер между `POST …/reviews` и записью `published_comments`. Ревью с маркером прогона на GitHub есть, в базе - нет; отсев по треду бота его не видит, и следующий прогон повторял замечание к той же строке.

Исправление (change `adopt-orphaned-review`): перед публикацией прогон находит прогоны своего PR, упавшие на `publishing` без записей (`ReviewRunRepo.list_unpublished_failures`), ищет их ревью по маркеру (`VcsGateway.find_published_review`) и записывает его комментарии упавшему прогону. Поиск best-effort. Покрывает и путь через выметатель зависших прогонов.

### 4.2 Уязвимость: обход merge gate сменой целевой ветки - исправлено

Серьёзность - высокая. Нужно право толкать ветки в репозиторий.

1. Автор толкает ветку `evil-staging` = целевая ветка + бэкдор, без PR.
2. Открывает PR `feat → evil-staging`: в диффе безобидная правка, бот выставляет check run `success` на `head_sha`.
3. Меняет целевую ветку PR на `develop`. GitHub шлёт `pull_request` `edited` с `changes.base`; приём его игнорировал. Check run висит на коммите, а не на паре «коммит, база», - обязательная проверка пройдена, бэкдор уходит в `develop` без ревью.

Исправление (change `review-on-base-change`). Ретаргет - это `edited`, в котором `target_branch` отличается от записанной в PR; `base_sha` не сравнивается, дублем такой вебхук не бывает. Приём одной транзакцией отменяет активный прогон на этот head и записывает новый, затем выставляет на head `failure` «Целевая ветка сменилась — идёт повторное ревью» и только потом ставит задачу. Если GitHub на блокировку отвечает ошибкой, новый прогон уходит в `failed`, PR возвращается на прежнюю ветку, вебхук отвечает 502: повторная доставка снова увидит смену и заблокирует head. Тест атаки - `test_retargeting_a_reviewed_pull_request_onto_another_branch_reviews_the_new_diff`, сквозной тест проверяет `failure` на head сразу после `edited`, до работы воркера.

Отменённый прогон до `POST …/reviews` перечитывает статус и ничего не публикует. Воркер, чей прогон отменили посреди работы, закрывает открытый шаг как брошенный (`REVIEW_RUN_STALE`) и подтверждает сообщение без ошибки: в DLQ оно не уходит. Если последний прогон на head упал, а на head уже было ревью, воркер ставит `failure` «Ревью не удалось», и прежний `success` на head не остаётся.

Гонку записи gate закрывает `settle_merge_gate`. Публикация и пересчёт по треду выставляют gate только через него: check собирается по последнему прогону на head, а после POST тот перечитывается. Если он сменился, gate переписывается по нему: итог завершённого, «Ревью не удалось» упавшего, блокировка ретаргета для идущего или отменённого. Приём, наоборот, блокирует head после коммита нового прогона. При любом порядке POST последним остаётся gate актуального прогона. Отказ GitHub повторяется до `SETTLE_ATTEMPTS` раз, и каждая попытка заново читает последний прогон.

### 4.3 Уязвимость: ReDoS в паттернах `.review/rules.md` - исправлено

Серьёзность - средняя (отказ в обслуживании всей очереди ревью). Нужно право положить `rules.md` на ветку, в которую открыт PR, - в том числе на свою.

`PurePosixPath.full_match` переводит паттерн в регулярное выражение; паттерн `*a*a…*x` на длинном имени файла из PR перебирает варианты экспоненциально. Замер на имени из 40 `a`: `n = 8` - 1,3 с, `n = 10` - 15 с, `n = 24` не завершается. Регулярное выражение не отпускает GIL: таймаут потока не срабатывает, воркер висит до `kill`, при `prefetch=1` встаёт вся очередь. На стенде прогон с таким паттерном не завершился за 400 с.

Исправление (change `bounded-rules-glob`): своя чистая функция `glob_full_match` (`app/domain/glob.py`). Путь и шаблон делятся на сегменты по `/`. Сегменты сопоставляются жадно с откатом только к последнему `**`, поэтому время не больше произведения числа сегментов. Внутри сегмента - `fnmatchcase`, который с Python 3.14 не перебирает варианты экспоненциально (атомарные группы). Дифференциальная сверка с `full_match` на корпусе и офлайн-фаззинг на 30 000 случайных парах: расхождения только на вырожденных путях из `.` и там, где `full_match` пропускал `/` через `[!…]` и `**` внутри сегмента - это отступление от `.gitignore`, теперь закрытое.

### 4.4 Уязвимость: пересчёт gate давал `success` непроверенному коммиту - исправлено

Серьёзность - высокая. Существовала до #222, найдена при разборе §4.2.

Пересчёт merge gate по вебхуку закрытия треда брал прогон через `find_reviewed` и выставлял check run всегда. Автор делает push, ревью нового head ещё идёт (или упало), автор закрывает свой тред - пересчёт не находит прогона на новом head, открытых тредов нет, и на непроверенный коммит выставляется `success`. После смены целевой ветки тот же путь брал прогон на старой базе.

Исправление (change `review-on-base-change`): пересчёт берёт последний прогон на head в любом статусе (`ReviewRunRepo.find_latest`) и выставляет gate, только если он `completed`. Тесты - `tests/application/test_sync_thread_resolution.py`.

### 4.5 Crash-loop на сообщении, убивающем воркер - исправлено

Серьёзность - средняя (доступность), #223. Классическая очередь `review_jobs` не считала доставки: сообщение, на котором процесс воркера умирает (OOM, segfault), возвращалось при обрыве соединения и бесконечно убивало каждый следующий воркер. В DLQ уводит только пойманное исключение, а смерть процесса - не исключение.

Исправление (change `queue-delivery-limit`): основная очередь - quorum `review_jobs.qq` с `x-delivery-limit` = 5 и прежним DLX; штатная остановка возвращает сообщение `nack` (попытку не тратит); старая классическая `review_jobs` при выкате удаляется на брокере. Тесты - §2.5.
