# Test Plan — AI-ревьюер кода

Стратегия и уровни тестирования сервиса автоматического ревью merge/pull-реквестов.
Методология оценки LLM-компонента — в [LLM_EVAL](LLM_EVAL.md).

## 1. Риски, ради которых существует план

| ID | Риск | Проявление в проде | Где защита |
|---|---|---|---|
| R-1 | **Шум**: неверные или бесполезные комментарии | ревью отключают через неделю | Precision, дедупликация |
| R-2 | **Галлюцинация**: находка вне диффа или про несуществующий код | комментарий не публикуется или уходит не туда | `validate_anchor`, Hallucination rate |
| R-3 | **Пропуск дефекта** | ложное чувство защищённости | Recall |
| R-4 | **Дубли и зависшие прогоны**: перепосланный вебхук, упавший воркер | двойные комментарии, заблокированный коммит | инварианты схемы (§3.2), E2E |
| R-5 | **Безопасность**: prompt injection из диффа, секреты в `context_payloads`, подделанный вебхук | выполнение чужой инструкции, утечка кода | injection-сьют, проверка подписи |

Отдельно — **стоимость**: `tokens_used`, `duration_seconds`, `model` лежат колонками в
`review_runs`, поэтому бюджет проверяется SQL-запросом, а не метрик-стеком. Рост
стоимости — такой же дефект, как падение теста.

## 2. Область

**В области:** приём и валидация вебхуков, очередь, жизненный цикл прогона, сборка
контекста, LLM Gateway и промпты, публикация комментариев, персистентность и миграции,
учёт токенов.

**Вне области:** фронтенд и биллинг; Vector DB и semantic search (индексатора нет —
отдельный план, когда появится); нагрузка выше 50 одновременных вебхуков; автоприменение
suggestion'ов — по решению модели угроз патч применяет человек.

### 2.1 Что план берёт из архитектуры

- **Слои `domain ← application ← infrastructure / api`, `import-linter` в CI.** Тест
  доменного правила не поднимает БД; если правило иначе не проверить — оно лежит не в
  том слое.
- **Чистое ядро.** Время и идентификаторы приходят аргументами, поэтому unit-тест
  утверждает точное значение, а не диапазон.
- **Порты — `Protocol`, адаптеры в `infrastructure`.** Тест подменяет **порт, а не
  вендора**: фейк реализует протокол и живёт в `tests/fakes/`. `mock.patch` по пути
  `sqlalchemy.…` или `httpx.…` — дефект теста.
- **Модульный монолит.** `uvicorn app.main:app` и `python -m app.worker` — один образ,
  одна БД, одна очередь. E2E-стенд поднимает два процесса; «контрактов между
  микросервисами» здесь нет, контракты — только с внешним миром.
- **Наблюдаемость — это колонки.** Метрики берутся из `review_runs`, а не из Prometheus.

### 2.2 Раскладка и CI

```
tests/
  domain/            Unit: чистые правила                [есть]
  db/                Integration: адаптеры, схема        [есть]
  test_container.py  связывание портов                   [есть]
  fakes/             фейки портов                        [целевое]
  api/               контрактные                         [целевое]
  e2e/               два процесса + стенд                [целевое]
  eval/              датасет и раннер                     [целевое]
```

К существующим джобам (`syntax → lint → test`, `terraform` отдельно) добавляются `eval`
и `security` — отдельными джобами, а не шагами: совмещённая сообщает один провал на две
несвязанные причины.

Три детали, без которых это не соберётся:

- маркеры `api`, `e2e`, `eval` объявляются в `pyproject.toml` рядом с `integration`;
- eval исключается из основной джобы через `--ignore=tests/eval`, а не через `skipif` —
  правило «пропущенный тест = провал» уже работает и уронит прогон;
- покрытие сегодня нечем считать: ни `pytest-cov`, ни `coverage` нет в зависимостях, шага
  в CI тоже нет. Гейты §5 до этого не выполняются ни в каком виде. Нужен `pytest-cov` в
  dev-зависимостях и прогон с `--cov=app --cov-branch`: без `--cov-branch` требование «100 %
  строк **и веток**» в `domain` проверяется наполовину.

## 3. Уровни

**L0. Статика [действует].** `compileall`, `ruff`, `lint-imports`, `tofu validate`.
Нарушение слоёв — провал сборки, а не замечание ревьюера.

### 3.1 Unit [действует]

Чистые функции `app/domain/`: `next_status`, `validate_anchor`, `deduplicate`,
`find_stale`, `Result`. Без БД, брокера и сети; прогон — секунды.

- каждая ветка решения покрыта явно, включая отказ (у `validate_anchor` их три);
- матрица переходов `next_status` — табличным тестом, терминальные статусы неизменяемы;
- property-based там, где инвариант формулируется без примера: `deduplicate` сохраняет
  порядок, `kept + dropped` — перестановка входа;
- покрытие `app/domain/` — 100 % строк и веток.

### 3.2 Integration [действует частично]

Адаптеры и всё, что разговаривает с внешней системой. Уже есть: `tests/db/` с маркером
`integration`, пропуск без `TEST_DATABASE_URL`, в CI пропуск запрещён.

Инварианты схемы — по тесту на каждый (R-4):

| Инвариант | Проверка |
|---|---|
| `UNIQUE (provider, provider_id)` | дубль на одном хосте — `IntegrityError`, тот же `full_name` на другом — ок |
| `UNIQUE (repository_id, number)` | тот же номер PR в другом репозитории проходит |
| Частичный индекс на активный прогон | второй незавершённый прогон по тому же `head_sha` отвергается; после `completed` новый создаётся |
| `UNIQUE (review_run_id, chunk_index)` | порядок чанков контекста не теряется |
| `UNIQUE NULLS NOT DISTINCT` на находки | дубль с `new_line IS NULL` на старой стороне тоже отвергается |
| `UNIQUE NULLS NOT DISTINCT (review_run_id, finding_id)` | summary публикуется один раз на прогон |
| `ON DELETE RESTRICT` на каждом внешнем ключе | удаление репозитория с merge-реквестами отклоняется; опубликованный комментарий переживает удаление своей находки. Сирот не бывает по построению, а не потому, что потомков вычистили |
| `timestamptz` | утверждение против скомпилированного DDL, а не против аннотации |

Миграции: на каждый PR со схемой `upgrade head → downgrade base → upgrade head` на
одноразовой базе, затем autogenerate не находит отличий.

**Целевое:** очередь (ack после коммита, повторная доставка не создаёт второй прогон,
недоставленное сообщение уходит в отдельную очередь и не крутится в цикле),
GitHub-адаптер на записанных ответах (403 с исчерпанным лимитом, 404, 422), LLM Gateway
против фейкового сервера (таймаут, не-JSON, пустой список находок). Брокер выбран —
RabbitMQ: он назван в таблице портов `BACKEND_ARCHITECTURE.md`, `pika` стоит в
forbidden-контракте import-linter, layout обменов задаёт `SYSTEM_DESIGN.md` §4.2.
Утверждения при этом сформулированы против порта `JobQueue`: адаптер проверяется на
реальном брокере, а верхние уровни получают фейк.

### 3.3 Контрактные [целевое]

| Контракт | Проверка |
|---|---|
| Вебхук → Gateway | схема payload; неизвестное событие — 202, не 500; HMAC обязателен, без подписи — 401 |
| Повторная доставка → `IdempotencyStore` | ключ занимается через `INSERT … ON CONFLICT DO NOTHING`; вторая доставка **переигрывает исход первой и до очереди не доходит** |
| Превышение лимита → `RateLimiter` | fixed-window счётчик на субъект; отказ возвращается вызывающему, а не создаёт прогон |
| Gateway → очередь | обязательные `job_id`, `event_type`, `repository`, `head_sha` |
| LLM → Orchestrator | ответ парсится в структуру: лишние поля, `severity` вне енума, `confidence` вне `[0,1]`, обрезанный JSON. Невалидный ответ = прогон `failed`, а не частичный результат |
| HTTP API | снапшот OpenAPI |

Идемпотентность на входе и частичный уникальный индекс закрывают **разные** отказы, и
путать их нельзя. Отсев в `IdempotencyStore` означает, что повторная доставка не создала
ни прогона, ни сообщения в очереди. Частичный индекс срабатывает позже: прогон уже
создаётся и падает на констрейнте. Первое — штатный путь, второе — последняя линия, и
тест на каждое свой.

### 3.4 E2E [целевое]

Вебхук → Gateway → очередь → воркер → контекст → LLM (застаблена) → публикация.
Качество модели здесь не измеряется.

| ID | Сценарий | Ожидание |
|---|---|---|
| E2E-01 | PR с одним дефектом | 1 inline + summary, статус `completed` |
| E2E-02 | повторная доставка вебхука | второго прогона нет, комментарии не продублированы |
| E2E-03 | новый push во время прогона | старый переходит в `cancelled`, его находки не публикуются, для нового `head_sha` один прогон |
| E2E-04 | воркер убит в `analysing` | прогон подхвачен по `last_progress_at`, коммит не заблокирован |
| E2E-05 | LLM недоступна | `failed` с `failure_reason`, мусорного комментария в PR нет |
| E2E-06 | PR без дефектов | только summary, inline — ноль |
| E2E-07 | ответ на комментарий агента | продолжение диалога, а не повторное ревью |
| E2E-08 | PR выше лимитов | усечение, в summary сказано, что покрыто не всё |

### 3.5 LLM Evaluation [целевое]

Методология и пороги — в [LLM_EVAL](LLM_EVAL.md). Полный прогон запускается при
изменении промпта или версии модели (обязательно), по метке `run-eval` на PR и перед
релизом; на каждом PR — только дешёвая часть, валидация схемы ответа и injection-сьют
на записанных ответах, без вызовов модели.

### 3.6 Нефункциональные

p95 длительности на MR ≈300 строк и деградация на 10× большем; 50 одновременных
вебхуков без потери сообщений и дедлоков; убийство воркера и обрыв брокера не оставляют
опубликованный комментарий без строки в `published_comments` и наоборот.

## 4. Данные и стенды

| Класс | Как порождается |
|---|---|
| Фабрики сущностей | фиксированные UUIDv7 и timestamp'ы аргументами; тест утверждает точное значение |
| Ответы VCS | VCR-фикстуры, снятые один раз и вычищенные от токенов |
| Ответы LLM | JSON рядом с тестом: валидный, пустой, обрезанный, невалидный |
| Golden dataset | [LLM_EVAL](LLM_EVAL.md) |

Секретов в фикстурах нет; ключи в кейсах — заведомо невалидные строки формата. Чужой
код в датасет не попадает. Каждый тест получает чистую схему или транзакцию с откатом.

| Стенд | Состав | Что гоняем |
|---|---|---|
| Локальный | два процесса, Postgres и шина в контейнерах, фейковый VCS | всё, eval вручную |
| CI (PR) | сервисы Postgres и шины, LLM застаблена | всё, кроме полного eval |
| CI (eval) | + модель с зафиксированной версией | eval по триггерам |
| Staging | GitHub App на тестовой организации | E2E против живого хоста, дымовой после деплоя |

## 5. Гейты

**Мёрж PR:** L0 зелёный; Unit и Integration проходят без пропусков; покрытие `domain`
100 %, проекта ≥ 80 % без снижения; миграции реверсируются и не дрейфуют; у нового
публичного пути есть тест на успех и на отказ.

**Релиз, инженерная часть:** E2E-01…E2E-08 проходят; p95 длительности ≤ 5 мин; средняя
стоимость прогона не выросла больше чем на 20 % относительно предыдущего релиза при том
же качестве.

**Релиз, качество модели:** пороги в [LLM_EVAL](LLM_EVAL.md). Релиз блокируется любым из
двух списков.

## 6. Шаблон тест-кейса

```
ID:              <УРОВЕНЬ>-<номер>         INT-014, E2E-03
Уровень:         Unit | Integration | Контрактный | E2E | LLM Eval
Риск:            R-1 … R-5
Предусловия:     состояние БД, содержимое очереди, стабы
Шаги:            1. … 2. …
Ожидание:        наблюдаемый результат — строка в БД, сообщение, HTTP-код, комментарий
Не ожидается:    второй прогон, второй комментарий, 500
Автоматизирован: путь к тесту | нет + причина
```

Ответственность: разработчик — Unit и Integration на свой код; QA — контрактные, E2E,
eval и датасет; DevOps — стенды и прогоны в CI. План правится в том же PR, что меняет
описанное поведение.
