# GitHub App: как сервис получает доступ к репозиториям

Документ для того, кто видит проект впервые: что такое наше приложение в GitHub, кто что
настраивает, как репозиторий попадает на ревью и почему сервис видит не все репозитории
пользователя. Текст описывает код в `develop`; где написано «Планируется» или «после #243», —
это план задачи
[#243](https://github.com/larchanka-training/dmc-268-api-t1/issues/243) (родитель —
[dmc-268-ui-t1#95](https://github.com/larchanka-training/dmc-268-ui-t1/issues/95)).

## Слова

Одно слово — одно понятие, во всём документе:

| Слово | Что это |
|---|---|
| **Приложение** (GitHub App) | Регистрация нашего сервиса в GitHub: имя, id (`5262828`), права, события, Webhook URL, ключи. Одно на весь сервис |
| **Бот** | Аккаунт `<slug приложения>[bot]` (slug — короткое имя из адреса `github.com/apps/<slug>`), который GitHub сам создаёт для приложения. От него в PR пишутся комментарии ревью и ставится проверка `dmc-268-ai-review`. Отдельно не настраивается |
| **Установить** | В GitHub дать приложению доступ к репозиториям аккаунта или организации |
| **Установка** | То, что появляется в GitHub после «установить»: связка «приложение — аккаунт или организация» со списком репозиториев. Одна на владельца |
| **Токен установки** | Ключ на час, который сервис получает от GitHub для одной установки: им воркер читает код и пишет в PR |
| **Подключить** | В нашем сервисе включить ревью у репозитория — запись в нашей базе. В интерфейсе после #243 — переключатель «Ревью» в положении вкл |
| **Прогон** | Одно ревью одного состояния PR: от вебхука до опубликованных комментариев |
| **Ручка** | HTTP-эндпоинт нашего API, например `GET /api/v1/repositories` |
| **Вебхук** | Запрос, которым GitHub сообщает сервису о событии в репозитории (открыли PR, запушили) |
| **Владелец приложения** | Тот, кто создал приложение и меняет его настройки. У нас — организация `larchanka-training` |
| **Владелец установки** | Аккаунт или организация, где лежат репозитории, — первая часть адреса `github.com/<владелец>/<репозиторий>`. Ставит приложение сам владелец, а в организации ещё admin репозитория (см. «Роли») |
| **Интерфейс** | Фронтенд сервиса, репозиторий `dmc-268-ui-t1` |
| **Стенд** | Сервер, где развёрнут сервис: `https://62.169.24.237` |

Аналогия: приложение — фирма с договором в GitHub, бот — её сотрудник с бейджем, установка —
вы выдали фирме пропуск в квартиру, подключение — фирма внесла квартиру в график работ, вебхук —
звонок в фирму «в квартире открыли PR».

## Кто что делает

| Что | Кто | Где | Как часто |
|---|---|---|---|
| Настройки приложения: права, события, Webhook URL и secret, Setup URL, кому можно устанавливать | владелец приложения | настройки GitHub App | один раз на сервис |
| Реквизиты приложения на стенде | admin репозитория `dmc-268-api-t1` (секреты деплоя) | Settings → Secrets and variables → Actions | при смене приложения |
| Установка и выбор репозиториев | владелец установки или admin репозитория (см. «Роли») | экран установки на GitHub | на аккаунт; список репозиториев меняется в любой момент |
| Подключение в сервисе | admin или maintain репозитория в GitHub | сейчас — страница «Подключение репозитория», после #243 — переключатель «Ревью» на «Репозиториях» | на репозиторий |

Приложение нашего сервиса создано в организации `larchanka-training`, его настройки видят
только владелец организации и назначенные ею менеджеры приложений. Установка привязана к
**владельцу установки**, а не к репозиторию и не к пользователю, который открыл сервис. Для репозиториев одного владельца установка одна: при ней выбирают
«All repositories» или отмечают нужные («Only select repositories»), список потом правится
в GitHub без переустановки. Репозитории в личном аккаунте и в организации — две установки.

## Три состояния репозитория

| Состояние | Что делает GitHub | Что делает сервис | `GET /repositories/available` | `GET /repositories` |
|---|---|---|---|---|
| Приложение не установлено | ничего не шлёт, доступа нет | не знает о репозитории | нет | нет |
| Установлено, не подключён | даёт приложению доступ к коду, шлёт вебхуки | отвечает на вебхук `202 ignored`, прогон не создаёт | да, `already_connected: false` | нет |
| Установлено и подключён | то же | создаёт прогон и ревьюит PR | да, `already_connected: true` | да, если пользователь видит репозиторий на GitHub |

Установку владелец может приостановить (suspend): тогда репозиторий выпадает из списка, а
подключение отвечает `404`, как если бы приложение не было установлено.

Как репозиторий оказывается «установлен, но не подключён»:

- при установке выбрали «All repositories»: доступ есть ко всем репозиториям владельца, а
  ревьюить нужно часть;
- приложение поставил кто-то другой, например владелец организации, а включать ревью — решение
  админа репозитория;
- у пользователя нет прав подключить (см. «Роли»);
- после #243: репозиторий отключили в сервисе, а в GitHub приложение осталось.

Сейчас вебхук неподключённого репозитория игнорируется — спека `webhook-intake`, требование
«Незарегистрированный репозиторий игнорируется». Регистрировать репозиторий по вебхуку спека
запрещает: подключение — отдельная операция с проверкой прав.

## Роли GitHub: кто ставит, кто видит и кто подключает

| Роль на репозитории | Поставить приложение на GitHub | Видит в списке | Может подключить |
|---|---|---|---|
| владелец личного аккаунта | да | да | да |
| владелец организации | да, на любые её репозитории | да | да |
| admin | да, только на репозитории, где он admin; если владелец уже поставил приложение — может добавить в установку свои репозитории. Обе возможности владелец организации может запретить | да | да |
| maintain | нет; в организации — Request, запрос уходит её владельцу | да | да |
| write (push), triage | нет; в организации — Request | да | нет: `403 REPOSITORY_MANAGE_REQUIRED` |
| read | нет | только приватный репозиторий | нет: `403` |

Кто может поставить приложение — правило GitHub
([документация](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)):
установка выдаёт стороннему приложению доступ к коду, это решение владельца аккаунта или
организации. В личном аккаунте ставит только сам владелец, запросить некого. Кто может
подключить — наше правило (`app/domain/repository_access.py`): включение ревью меняет то, что
бот пишет во все PR репозитория, это решение того, кто им управляет. Мейнтейнеру нужен тот, кто
поставит приложение; включить ревью он потом может сам.

«Нет прав» здесь — нет прав **управлять** репозиторием; доступ к нему есть. Примеры:
коллега добавил вас коллаборатором с write и поставил приложение — вы видите репозиторий,
но включает ревью он; вы member организации с write — видите её репозитории, подключает админ.
Строка такого репозитория приходит с `can_connect: false`, и интерфейс не показывает кнопку
«Подключить».

Публичный репозиторий, на котором у пользователя только read, в список не попадает: GitHub
отдаёт любой публичный репозиторий любому, и иначе в списке оказались бы все публичные
репозитории всех установок.

## Две ручки списка (сейчас; после #243 — одна)

| | `GET /api/v1/repositories/available` | `GET /api/v1/repositories` |
|---|---|---|
| Что отдаёт | репозитории, где **установлено** приложение и у пользователя есть доступ | **подключённые** репозитории |
| Откуда | из GitHub по токену пользователя: `GET /user/installations` и `GET /user/installations/{id}/repositories` | из нашей базы, но только те, что пользователь видит на GitHub по тому же токену |
| Страница интерфейса | «Подключение репозитория» | «Репозитории» |
| Действие | «Подключить» → `POST /api/v1/repositories` | настройки, правила, PR, история прогонов |

Подключённый репозиторий, к которому пользователь потерял доступ в GitHub, из его списка
«Репозитории» пропадает; если GitHub не ответил — `502 SCM_UNAVAILABLE`.

Фронт не может спросить GitHub сам: токен пользователя хранится только на бэкенде,
зашифрованным (таблица `provider_tokens`, ключ `USER_TOKEN_ENCRYPTION_KEY`), браузер получает
лишь cookie сессии. Токен даёт доступ к приватному коду — в браузере его украл бы любой
скрипт на странице. Бэкенд добавляет к ответу GitHub то, чего тот не знает:
`already_connected` из базы и `can_connect` по правам.

## Почему сервис не видит все репозитории пользователя

Пользователь входит через то же приложение (OAuth GitHub App). Токен
такого входа, по
[документации GitHub](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user),
видит только то, что доступно одновременно пользователю и приложению, и только в аккаунтах,
где приложение установлено. Поэтому и `GET /user/repos` с этим токеном не откроет
репозитории без установки. Список всех репозиториев пользователя показывает сам GitHub — на
экране установки приложения.

Другой путь — вход через OAuth App со scope `repo` — видит всё, но мы его не берём:

- приватные репозитории OAuth App видит только со scope `repo`, а это чтение **и запись**
  всего кода пользователя и его организаций; scope «только список» у GitHub нет;
- токены OAuth App по умолчанию бессрочные, а токены установки GitHub App живут час и
  открывают только выбранные репозитории
  ([сравнение](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps));
- так уже теряли код: в апреле 2022 у Heroku украли из базы OAuth-токены пользователей для
  GitHub и выкачали приватные репозитории десятков организаций, среди них npm
  ([GitHub](https://github.blog/news-insights/company-news/security-alert-stolen-oauth-user-tokens/));
- вебхуки OAuth App ставятся в каждый репозиторий отдельно и не удаляются при отзыве
  доступа, комментарии шли бы от имени человека, а не бота.

Так же устроены [CodeRabbit](https://docs.coderabbit.ai/platforms/github-com) (кнопка Add
Repositories ведёт на экран установки) и
[Vercel](https://vercel.com/kb/guide/unable-to-find-github-repository) (Adjust GitHub App
Permissions); [Codecov](https://about.codecov.io/?p=9049) ушёл с OAuth App на GitHub App.

## Подключение

### Сейчас

1. Пользователь входит через GitHub (`/api/v1/auth/github/login`), сервис сохраняет его
   токен.
2. Страница «Подключение репозитория» показывает `GET /repositories/available`.
3. «Подключить» у строки → `POST /repositories`. Бэкенд по токену пользователя берёт
   репозиторий (`GET /repositories/{id}`), ключом приложения проверяет установку на нём
   (`GET /repos/{owner}/{repo}/installation`), проверяет admin или maintain и записывает
   репозиторий с `auto_review_enabled = true`. Интерфейс уводит на «Репозитории».
4. Установить приложение из сервиса нельзя: кнопки, ведущей на GitHub, нет. Репозитории, где
   приложение не стоит, в списке не появляются, и пользователю, который не может
   поставить приложение на свои репозитории, подключать нечего.

Ошибки подключения: репозиторий не виден, публичный только с read, приложение не установлено
или установка приостановлена — один ответ `404 REPOSITORY_NOT_IN_INSTALLATION`; нет admin или
maintain — `403 REPOSITORY_MANAGE_REQUIRED`; уже подключён — `409`; токен непригоден — `401`,
сессия закрывается; GitHub не ответил — `502`.

### Планируется (#243, dmc-268-ui-t1#96)

Одна страница «Репозитории» вместо двух, одна ручка списка вместо двух, переключатель вместо
кнопок — как вкладка Repositories в CodeRabbit.

```
Репозитории                        [ Добавить репозитории из GitHub ]  Управлять доступом в GitHub

Репозиторий                          Ревью
larchanka-training/dmc-268-api-t1    [●━━] вкл     Настройки
<логин>/repo-2                       [━━○] выкл
<коллега>/repo                  [━━○] нужна роль admin или maintain   (неактивен)
```

1. `GET /api/v1/repositories` отдаёт все репозитории установок, видимые пользователю,
   подключённые и нет: у строки `connected`, `id` (только у подключённых), `can_connect`; у
   ответа — `install_url` для кнопки. `GET /repositories/available` и страница «Подключение
   репозитория» удаляются.
2. **«Добавить репозитории из GitHub»** открывает экран установки: пользователь выбирает
   аккаунт, отмечает репозитории, в том числе приватные, и жмёт **Install**. В организации без
   прав вместо Install — **Request**: запрос уходит владельцу.
3. GitHub возвращает пользователя на Setup URL — ручку бэкенда с `installation_id` и
   `setup_action` в адресе. `installation_id` бэкенд не доверяет — сверяет с установками
   пользователя по его токену.
4. **По умолчанию:** репозитории, отмеченные галочками («Only select repositories»), бэкенд
   подключает сам, если у пользователя admin или maintain. При «All repositories» не подключает
   ничего: иначе бот сразу пошёл бы во все репозитории аккаунта и тратил бюджет модели.
5. Пользователь возвращается на «Репозитории» с итогом: «подключено N» или «запрос отправлен
   владельцу».
6. **Переключатель «Ревью»**: вкл — `POST /repositories`, выкл — `DELETE /repositories/{id}`.
   Репозиторий, отмеченный на GitHub, можно включать и выключать здесь сколько угодно;
   неотмеченного в списке нет — сначала «Добавить» и галочка на GitHub.

Выключение **мягкое**: строка репозитория остаётся в базе с отметкой «выключено», поэтому прогоны
и PR не теряются (их внешние ключи — `ON DELETE RESTRICT`), а повторное включение возвращает
историю. Как именно хранится отметка и как с ней сочетается уникальный ключ ниже — решается в
OpenSpec-change #243.

Подключение одно на репозиторий, а не своё у каждого пользователя: в базе уникальный ключ
«провайдер и id репозитория» (`uq_repositories_provider_id`), вставка — `ON CONFLICT DO
NOTHING`. Двое включают одновременно — запись одна, второй получает «уже подключён», и
интерфейс показывает «вкл»; выключение уже выключенного — тоже успех; включение и выключение в
одну секунду — побеждает последний.

## Отключение

**Сейчас** отключить репозиторий нельзя: ручки удаления нет. Выключить авто-ревью тоже
нельзя: флаг `auto_review_enabled` ставится в `true` при подключении, а ручки настроек
(`GET`/`PUT /repositories/{id}/settings`) пока отвечают `501`. Приём вебхука флаг не
проверяет.

**Планируется:**

- в сервисе — переключатель «Ревью» в выкл, `DELETE /api/v1/repositories/{id}` с теми же
  правами, что на подключение. Прогоны и PR остаются, при повторном включении история
  возвращается. Нужен, когда убрать приложение в GitHub нельзя: например, его поставил
  владелец организации на «All repositories», а admin одного репозитория не хочет туда бота;
- в GitHub — «Управлять доступом в GitHub»: снять репозиторий с установки или удалить её.
  GitHub присылает `installation_repositories` (`removed`) или `installation` (`deleted`,
  `suspend`), и сервис сам выключает ревью у затронутых репозиториев.

Переключатель «Авто-ревью» в настройках репозитория убирается: пока бот запускается только
автоматически, он значит то же, что «Ревью» выкл. Вернётся вместе с запуском по назначению
ревьюером или упоминанию — тогда «Ревью» вкл и «Авто-ревью» выкл будут значить «бот
приходит, только если позвали».

## От PR до ревью

1. В подключённом репозитории открывают PR или пушат в него.
2. GitHub шлёт вебхук `pull_request` (`opened` или `synchronize`) на Webhook URL. Подпись
   `X-Hub-Signature-256` — HMAC тела секретом вебхука; без неё или с неверной — `401`.
3. Бэкенд создаёт прогон и ставит задачу в очередь, воркер читает дифф и `.review/rules.md`
   токеном установки и публикует ревью от имени бота.

Остальные действия `pull_request` (`reopened`, `closed` и прочие) игнорируются. Событие
`pull_request_review_thread` ревью не запускает: по нему бот пересчитывает проверку
`dmc-268-ai-review`, когда закрывают тред (README, «Merge gate»). Запуск по
назначению бота ревьюером или по упоминанию в комментарии — запланированный шов
(`trigger_source` `manual` / `mention` есть в базе; ручной запуск `POST /api/v1/reviews` —
заглушка `501`, запуска по упоминанию нет).

## Настройки приложения

Задаёт владелец приложения, один раз. Что из этого уже стоит у нашего приложения, видно только в
его настройках; по логам стенда (ни одной доставки от GitHub) Webhook URL сейчас не работает.

Настройки — в GitHub → Settings → Developer settings → GitHub Apps → приложение. Меняете
приложение или создаёте своё — выставьте всё из таблицы: пропущенное поле не ломает старт, а
молча отключает часть работы (последний столбец).

| Поле | Значение | Если не так |
|---|---|---|
| Callback URL | `https://62.169.24.237/api/v1/auth/github/callback` (`<PUBLIC_ORIGIN>/api/v1/auth/github/callback`) | вход в сервис падает |
| Webhook → Active | включено | GitHub не шлёт событий — прогонов нет |
| Webhook URL | `https://62.169.24.237/api/v1/webhooks/github` | то же |
| Webhook secret | значение секрета `WEBHOOK_SECRET_DMC268_T1` | каждая доставка — `401`, прогонов нет |
| Permissions → Metadata | Read-only | обязательно, GitHub выставляет само |
| Permissions → Contents | Read-only | ревью без `.review/rules.md` и AST-окружения (`rules.status = unavailable`) |
| Permissions → Pull requests | Read and write | нет диффа и не публикуется ревью |
| Permissions → Checks | Read and write | нет проверки `dmc-268-ai-review`, merge gate не работает |
| Subscribe to events | Pull request; Pull request review thread | без первого — нет прогонов; без второго — проверка не пересчитывается при закрытии треда |
| Setup URL, Redirect on update | после #243 — ручка возврата после установки | после установки GitHub не вернёт пользователя в сервис |
| Where can this GitHub App be installed | «Any account» — ставить на любые аккаунты; «Only on this account» — только в `larchanka-training` | с «Only on this account» пользователи не поставят приложение на свои репозитории |

**«Any account» и деньги.** Со стендом на Eurorouter (#245) каждый прогон платит за модель с
ключа `AI_DMC268_T1`, а
лимитов, баланса и списка разрешённых аккаунтов нет. С «Any account» любой пользователь
GitHub может поставить приложение на свои репозитории, подключить их в сервисе и ревьюить
свои PR за этот счёт. Остановить быстро: вернуть «Only on this account» или выкатить стенд с
`TF_VAR_llm_backend: stub`.

## Реквизиты приложения на стенде

Стенд берёт реквизиты из настроек репозитория `dmc-268-api-t1`, `deploy.yml` передаёт их в
OpenTofu:

| Значение | Где | Переменная OpenTofu |
|---|---|---|
| App ID | переменная `APP_ID_DMC268_T1` | `github_app_id` |
| Client ID | переменная `APP_CLIENT_ID_DMC268_T1` | `github_app_client_id` |
| Client secret | секрет `APP_CLIENT_SECRET_DMC268_T1` | `github_app_client_secret` |
| Private key | секрет `APP_PRIVATE_KEY_DMC268_T1` | `github_app_private_key` |
| Webhook secret | секрет `WEBHOOK_SECRET_DMC268_T1` | `github_webhook_secret` |

Источник правды по реквизитам — `infra/README.md`, таблица «Откуда»; здесь — для обзора.

Сменить приложение — например, на своё с нужными настройками: создать GitHub App с
настройками из таблицы выше, заменить пять значений и перезапустить деплой. После смены:

- все входят заново: токены пользователей выданы старым приложением;
- подключённые репозитории остаются подключёнными (`installation_id` в базе не хранится,
  берётся из вебхука), но новое приложение нужно **установить** на них — иначе вебхуков нет;
- обязательная проверка `dmc-268-ai-review` в rulesets привязана к id приложения
  (`integration_id`) — её источник надо перенастроить, см. README, «Merge gate».
