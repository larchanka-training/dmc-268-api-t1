# GitHub App: как сервис получает доступ к репозиториям

Документ для того, кто видит проект впервые. В нём: что такое наше приложение в GitHub, кто что
настраивает, как репозиторий попадает на ревью и почему сервис видит не все репозитории
пользователя.

Текст описывает код в `develop`. Пометка «после #243» означает план задачи
[dmc-268-api-t1#243](https://github.com/larchanka-training/dmc-268-api-t1/issues/243) и её
фронтовых частей [dmc-268-ui-t1#95](https://github.com/larchanka-training/dmc-268-ui-t1/issues/95)
и [dmc-268-ui-t1#96](https://github.com/larchanka-training/dmc-268-ui-t1/issues/96). Пометка
«после #246» означает неслитый PR
[dmc-268-api-t1#246](https://github.com/larchanka-training/dmc-268-api-t1/pull/246) с моделью
на стенде.

## Слова

Одно слово означает одно понятие во всём документе.

| Слово | Что это |
|---|---|
| **Приложение** (GitHub App) | Регистрация нашего сервиса в GitHub: имя, id, права, события, Webhook URL, ключи. Одно на весь сервис |
| **Бот** | Аккаунт `<slug>[bot]`, который GitHub сам создаёт для приложения (slug: короткое имя из адреса `github.com/apps/<slug>`). От него в PR пишутся комментарии ревью и ставится проверка `dmc-268-ai-review`. Отдельно не настраивается |
| **Установить** | В GitHub дать приложению доступ к репозиториям аккаунта или организации |
| **Установка** (installation, в старых текстах «инсталляция») | То, что появляется в GitHub после «установить»: связка приложения с аккаунтом или организацией и списком репозиториев. Одна на владельца |
| **Подключить** (в README и API: «зарегистрировать») | Включить ревью у репозитория в нашем сервисе: запись в нашей базе. После #243 в интерфейсе это переключатель «Ревью» в положении «вкл» |
| **Прогон** | Одно ревью одного состояния PR: от вебхука до опубликованных комментариев |
| **Ручка** | Эндпоинт нашего API, например `GET /api/v1/repositories` |
| **Вебхук** | Запрос, которым GitHub сообщает сервису о событии в репозитории: открыли PR, запушили |
| **Владелец приложения** | Тот, кто создал приложение и меняет его настройки. У нас это организация `larchanka-training` |
| **Владелец установки** | Аккаунт или организация, где лежат репозитории: первая часть адреса `github.com/<владелец>/<репозиторий>` |
| **Интерфейс** | Фронтенд сервиса, репозиторий `dmc-268-ui-t1` |
| **Стенд** | Сервер, где развёрнут сервис. Его адрес задаёт `PUBLIC_ORIGIN`, сейчас `https://62.169.24.237`; ниже он пишется как `<PUBLIC_ORIGIN>` |

Доступов к GitHub у сервиса три, и их легко спутать:

| Доступ | Что это | Кто и зачем пользуется |
|---|---|---|
| **Токен пользователя** | Выдаётся при входе через приложение (Client ID и Client secret). Хранится зашифрованным в `provider_tokens`, ключ `USER_TOKEN_ENCRYPTION_KEY` | API: какие репозитории видит пользователь и какие у него права |
| **Ключ приложения** | App ID и private key. Из них сервис подписывает JWT и говорит с GitHub от имени приложения | API: установлено ли приложение на репозитории (`GET /repos/{owner}/{repo}/installation`). Воркер: имя бота (`GET /app`), чтобы найти своё ревью, и повтор упавших доставок вебхука; после #243 тот же ответ даёт API slug для ссылки установки |
| **Токен установки** | Ключ на час для одной установки, его сервис получает по ключу приложения | API: метаданные PR при приёме вебхука. Воркер: читает код и пишет ревью в PR |

Аналогия: приложение похоже на фирму с договором, бот на её сотрудника с бейджем. Установка
значит, что вы выдали фирме пропуск в квартиру. Подключение значит, что фирма внесла квартиру в
график работ.

## Как устроен путь от PR до ревью

```
GitHub ──вебхук──▶ nginx (контейнер интерфейса) ──▶ API ──задача──▶ RabbitMQ ──▶ воркер
                                                    │                          │
                                                    └── база (PostgreSQL) ◀────┤
                                                                               ├──▶ модель (LLM_BACKEND)
                                                                               └──▶ GitHub: ревью от имени бота
```

1. В подключённом репозитории открывают PR или пушат в него.
2. GitHub шлёт вебхук `pull_request` с действием `opened` или `synchronize` на Webhook URL. nginx
   передаёт его в API. Подпись `X-Hub-Signature-256` содержит HMAC тела по секрету вебхука: без
   неё или с неверной API отвечает `401`.
3. API берёт метаданные PR токеном установки (если GitHub не ответил, `502`), записывает прогон
   и ставит задачу в RabbitMQ.
4. Воркер берёт задачу, читает дифф и `.review/rules.md` токеном установки, отправляет запрос
   модели и публикует ревью от имени бота.

Остальные действия `pull_request` (`reopened`, `closed` и прочие) сервис игнорирует. Событие
`pull_request_review_thread` ревью не запускает: по нему бот пересчитывает проверку
`dmc-268-ai-review`, когда закрывают тред (README, «Merge gate»). Запуска по назначению бота
ревьюером или по упоминанию в комментарии нет. В базе для такого запуска есть `trigger_source` `manual` и
`mention`, а ручной запуск `POST /api/v1/reviews` пока отвечает `501`.

## Кто что делает

| Что | Кто | Где | Как часто |
|---|---|---|---|
| Настройки приложения: права, события, Webhook URL и secret, Setup URL, кому можно устанавливать | владелец приложения | настройки GitHub App | один раз на сервис |
| Реквизиты приложения на стенде | admin репозитория `dmc-268-api-t1` (секреты деплоя) | Settings → Secrets and variables → Actions | при смене приложения |
| Установка и выбор репозиториев | владелец установки, в организации ещё admin репозитория (см. [«Роли GitHub»](#роли-github-кто-ставит-кто-видит-и-кто-подключает)) | экран установки на GitHub | на аккаунт; список репозиториев меняется в любой момент |
| Подключение в сервисе | admin или maintain репозитория в GitHub | сейчас страница «Подключение репозитория», после #243 переключатель «Ревью» на «Репозиториях» | на репозиторий |

Наше приложение создано в организации `larchanka-training`. Его настройки видят только владелец
организации и назначенные ею менеджеры приложений.

Установка привязана к владельцу установки, а не к репозиторию и не к пользователю, который
открыл сервис. Для репозиториев одного владельца установка одна. При ней выбирают
«All repositories» или отмечают нужные («Only select repositories»), список потом правится в
GitHub без переустановки. Репозитории в личном аккаунте и в организации требуют двух установок.

## Три состояния репозитория

| Состояние | Что делает GitHub | Что делает сервис | `GET /repositories/available` | `GET /repositories` |
|---|---|---|---|---|
| Приложение не установлено | ничего не шлёт, доступа нет | не знает о репозитории | нет | нет |
| Установлено, не подключён | даёт приложению доступ к коду, шлёт вебхуки | на вебхук отвечает `202 ignored`, прогон не создаёт | да, `already_connected: false` | нет |
| Установлено и подключён | то же | создаёт прогон и ревьюит PR | да, `already_connected: true` | да, если пользователь видит репозиторий на GitHub |

Установку владелец может приостановить (suspend). Тогда репозиторий выпадает из списка, а
подключение отвечает `404`, как будто приложение не установлено.

Репозиторий оказывается «установлен, но не подключён», когда:

- при установке выбрали «All repositories»: доступ есть ко всем репозиториям владельца, а
  ревьюить нужно часть;
- приложение поставил кто-то другой, например владелец организации, а включать ревью решает
  админ репозитория;
- у пользователя нет прав подключить (см. [«Роли GitHub»](#роли-github-кто-ставит-кто-видит-и-кто-подключает));
- после #243: ревью выключили в сервисе, а приложение в GitHub осталось (ответ на вебхук тоже
  `202 ignored`, но с зелёной проверкой, см. [«Подключение и выключение»](#подключение-и-выключение)).

Вебхук неподключённого репозитория сервис игнорирует (спека `webhook-intake`, требование
«Незарегистрированный репозиторий игнорируется»). Регистрировать репозиторий по вебхуку спека
запрещает: подключение идёт отдельной операцией с проверкой прав.

## Роли GitHub: кто ставит, кто видит и кто подключает

| Роль на репозитории | Поставить приложение на GitHub | Видит в списке | Может подключить |
|---|---|---|---|
| владелец личного аккаунта | да | да | да |
| владелец организации | да, на любые её репозитории | да | да |
| admin (бывает только в организации) | да, но только на репозитории, где он admin; если владелец уже поставил приложение, может добавить в установку свои репозитории. Обе возможности владелец организации может запретить | да | да |
| maintain | нет; в организации жмёт Request, запрос уходит её владельцу | да | да |
| write (push), triage | нет; в организации Request | да | нет: `403 REPOSITORY_MANAGE_REQUIRED` |
| read | нет | приватный да; публичный, только если роль выдана явно | нет: приватный `403`, публичный `404` |

Кто может поставить приложение, решает GitHub
([документация](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)):
установка выдаёт стороннему приложению доступ к коду, и это решение владельца аккаунта или
организации. В личном аккаунте ставит только сам владелец, запросить некого: коллабораторы
личного репозитория получают роль write, admin у них не бывает.

Кто может подключить, решает наше правило (`app/domain/repository_access.py`): включение ревью
меняет то, что бот пишет во все PR репозитория, поэтому решает тот, кто репозиторием управляет.
Мейнтейнеру нужен человек, который поставит приложение, а включить ревью он потом может сам.

«Нет прав» здесь значит «нет прав управлять репозиторием», доступ к нему при этом есть. Пример:
коллега добавил вас коллаборатором с write и поставил приложение. Вы видите репозиторий, но
включает ревью он. Или вы member организации с write: видите её репозитории, подключает админ.
Строка такого репозитория приходит с `can_connect: false`, и интерфейс не показывает кнопку
«Подключить».

Список репозиториев сервис не фильтрует: это ответ GitHub по токену пользователя как есть.
Правило про публичные репозитории действует при подключении: публичный репозиторий, на котором
у пользователя только read, получает `404`, как невидимый. GitHub отдаёт любой публичный
репозиторий кому угодно, и без этого правила его мог бы подключить посторонний.

## Две ручки списка (сейчас; после #243 одна)

| | `GET /api/v1/repositories/available` | `GET /api/v1/repositories` |
|---|---|---|
| Что отдаёт | репозитории, где **установлено** приложение и у пользователя есть доступ | **подключённые** репозитории |
| Откуда | из GitHub по токену пользователя: `GET /user/installations` и `GET /user/installations/{id}/repositories` | из нашей базы, но только те, что пользователь видит на GitHub по тому же токену |
| Страница интерфейса | «Подключение репозитория» | «Репозитории» |
| Действие | «Подключить» → `POST /api/v1/repositories` | настройки, правила, PR, история прогонов |

Если пользователь потерял доступ к подключённому репозиторию в GitHub, репозиторий пропадает из
его списка «Репозитории». Если GitHub не ответил, ручка отвечает `502 SCM_UNAVAILABLE`. Набор
видимых репозиториев кэшируется на 30 секунд (`visible_repositories_cache_ttl_seconds`), поэтому
изменения в GitHub доходят до списка с такой задержкой.

Фронт не может спросить GitHub сам: токен пользователя хранится только на бэкенде, а браузер
получает лишь cookie сессии. Токен открывает приватный код, и в браузере его украл бы любой
скрипт на странице. Бэкенд добавляет к ответу GitHub то, чего GitHub не знает: `already_connected`
из базы и `can_connect` по правам.

## Почему сервис не видит все репозитории пользователя

Пользователь входит через то же приложение, поэтому токен пользователя, по
[документации GitHub](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user),
видит только то, что доступно и пользователю, и приложению, и только в аккаунтах с установкой.
Даже `GET /user/repos` с этим токеном не откроет репозитории без установки. Список всех
репозиториев пользователя показывает сам GitHub на экране установки приложения.

Вход через OAuth App со scope `repo` видит всё, но мы его не берём:

- приватные репозитории OAuth App видит только со scope `repo`, а он даёт чтение **и запись**
  всего кода пользователя и его организаций; scope «только список» у GitHub нет;
- токены OAuth App по умолчанию бессрочные, а токены установки живут час и открывают только
  выбранные репозитории
  ([сравнение](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)).
  В апреле 2022 у Heroku украли из базы такие OAuth-токены и выкачали приватные репозитории
  десятков организаций
  ([GitHub](https://github.blog/news-insights/company-news/security-alert-stolen-oauth-user-tokens/)).

Так же устроен [CodeRabbit](https://docs.coderabbit.ai/platforms/github-com): кнопка Add
Repositories ведёт на экран установки GitHub. У
[Vercel](https://vercel.com/kb/guide/unable-to-find-github-repository) тот же экран открывается
ссылкой Adjust GitHub App Permissions.

## Подключение и выключение

### Сейчас

1. Пользователь входит через GitHub (`/api/v1/auth/github/login`), сервис сохраняет его токен.
2. Страница «Подключение репозитория» показывает `GET /repositories/available`.
3. «Подключить» у строки отправляет `POST /repositories`. Бэкенд по токену пользователя берёт
   репозиторий (`GET /repositories/{id}`), ключом приложения проверяет установку на нём,
   проверяет admin или maintain и записывает репозиторий с `auto_review_enabled = true`.
   Интерфейс уводит на «Репозитории».
4. Установить приложение из сервиса нельзя: кнопки, ведущей на GitHub, нет. Репозитории без
   приложения в списке не появляются, и тому, кто не может поставить приложение на свои
   репозитории, подключать нечего.

Ошибки подключения:

- репозиторий не виден, публичный только с read, приложение не установлено или установка
  приостановлена: один ответ `404 REPOSITORY_NOT_IN_INSTALLATION`;
- нет admin или maintain: `403 REPOSITORY_MANAGE_REQUIRED`;
- уже подключён: `409`;
- токен непригоден: `401`, сессия закрывается;
- GitHub не ответил: `502`.

Выключить ревью у репозитория нельзя: ручки удаления нет. Выключить авто-ревью тоже нельзя:
флаг `auto_review_enabled` ставится в `true` при подключении, а ручки настроек
`GET`/`PUT /repositories/{id}/settings` и статуса правил `GET /repositories/{id}/rules` пока
отвечают `501`. Приём вебхука флаг не проверяет.

### После #243

Одна страница «Репозитории» вместо двух, одна ручка списка вместо двух и переключатель вместо
кнопок, как во вкладке Repositories у CodeRabbit.

```
Репозитории                        [ Добавить репозитории из GitHub ]  Управлять доступом в GitHub

Репозиторий                          Ревью
larchanka-training/dmc-268-api-t1    [●━━] вкл     Настройки
<логин>/repo-2                       [━━○] выкл
<коллега>/repo                       [━━○] нужна роль admin или maintain   (неактивен)
```

1. `GET /api/v1/repositories` отдаёт все репозитории установок, видимые пользователю,
   подключённые и нет. У строки есть `connected`, `id` и `can_connect`. `id` приходит, если
   запись в сервисе есть, в том числе у выключенного репозитория: по нему открывается история.
   У ответа есть `install_url` для кнопки. Сервис строит его из slug, который узнаёт у GitHub
   (`GET /app`); если ключа приложения нет или GitHub не ответил, `install_url` равен `null`. Что
   при этом показывает интерфейс, решает #96. `GET /repositories/available` и страница «Подключение репозитория»
   удаляются.
2. **«Добавить репозитории из GitHub»** открывает экран установки. Пользователь выбирает
   аккаунт, отмечает репозитории, в том числе приватные, и жмёт **Install**. В организации без
   прав вместо Install будет **Request**: запрос уходит владельцу. `install_url` несёт `state`,
   привязанный к сессии, поэтому ссылка у каждой сессии своя.
3. GitHub возвращает пользователя на Setup URL:
   `GET /api/v1/auth/github/setup?installation_id=…&setup_action=…`. `installation_id` из адреса
   бэкенд не доверяет и сверяет его с установками пользователя по токену. Ручке нужна сессия;
   без неё `302` на вход.
4. Бэкенд сам подключает репозитории только при **первой установке** (`setup_action=install`) с
   «Only select repositories» и `state` этой сессии: отмеченные галочками, где у пользователя
   admin или maintain и которых ещё нет в базе. Выключенные вручную не включаются. Ничего не
   подключается (`?connected=0`), если:
   - «Добавить» нажали при уже стоящей установке: GitHub вернёт `update`, а `update` только
     обновляет список;
   - выбрали «All repositories», иначе бот сразу пошёл бы во все репозитории аккаунта;
   - приложение поставили прямо на GitHub, мимо кнопки сервиса;
   - GitHub не вернул `state`. Возвращает ли он его, на стенде ещё не проверено.

   Тогда репозиторий появляется в списке выключенным и включается переключателем.
5. Пользователь возвращается на «Репозитории» с итогом: «подключено N», «запрос отправлен
   владельцу» или ошибка: установка не найдена (`setup_error=installation_not_found`) или
   GitHub не ответил (`setup_error=provider_unavailable`).
6. **Переключатель «Ревью»**: «вкл» отправляет `POST /repositories`, «выкл» отправляет
   `DELETE /repositories/{id}` с теми же правами, что на подключение. Отмеченный на GitHub
   репозиторий можно включать и выключать здесь сколько угодно. Неотмеченного в списке нет:
   сначала «Добавить» и галочка на GitHub. Переключатель нужен, когда убрать приложение в GitHub
   нельзя: например, его поставил владелец организации на «All repositories», а admin одного
   репозитория не хочет туда бота.

Выключение мягкое: строка остаётся в базе с `connected_at = NULL`. Прогоны и PR не теряются, их
внешние ключи `ON DELETE RESTRICT`, а повторное включение возвращает историю. На вебхук PR
выключенного репозитория (после #246 только от своего автора, см. «Модель и деньги») сервис
отвечает `202 ignored`, но ставит на коммит проверку
`dmc-268-ai-review` `success` «Ревью выключено в сервисе»: иначе обязательная проверка висела бы
в «Waiting for status». Зелёная проверка без ревью здесь не поломка. У незарегистрированного
репозитория проверки нет.

Убрать бота можно и в GitHub: «Управлять доступом в GitHub», снять репозиторий с установки или
удалить её. GitHub перестаёт присылать по нему события, и бот замолкает. Из списка «Репозитории»
репозиторий пропадает сам (с задержкой кэша до 30 секунд), потому что GitHub больше не отдаёт
его по токену пользователя. Запись в базе остаётся включённой и ни на что не влияет; если
приложение вернут, ревью продолжится без лишних действий.

Подключение одно на репозиторий, а не своё у каждого пользователя. Уже сейчас: в базе уникальный ключ
«провайдер и id репозитория» (`uq_repositories_provider_id`). После #243: если двое включают одновременно,
запись будет одна, второй получит «уже подключён», и интерфейс покажет «вкл». Выключение уже
выключенного тоже считается успехом. Если включают и выключают в одну секунду, побеждает
последний запрос.

Вебхуки `installation` и `installation_repositories` сервис намеренно не обрабатывает: GitHub и
так перестаёт слать события и отдавать репозитории снятой установки, обработка
`suspend`/`unsuspend` выключала бы все репозитории владельца без возврата, а сопоставление
владельца по имени молча ломается при переименовании аккаунта.

Переключатель «Авто-ревью» в настройках репозитория по плану #95 убирается: пока бот запускается
только автоматически, он значит то же, что «Ревью» в положении «выкл». Он вернётся вместе с
запуском по назначению ревьюером или по упоминанию. Тогда «Ревью» «вкл» с «Авто-ревью» «выкл»
будет значить «бот приходит, только если позвали».

## Модель и деньги

Ревью пишет языковая модель, а какую, выбирает `LLM_BACKEND` воркера (README, «Модель»). Без
него воркер не стартует: заглушка выбирается только явно.

| `LLM_BACKEND` | Что происходит | Где |
|---|---|---|
| `stub` | заглушка без похода к модели: прогон доходит до `completed` с пустым ревью | локальный запуск; стенд сейчас (`deploy.yml`: `TF_VAR_llm_backend: stub`) |
| `ollama` | локальная модель в нашей сети; Eurorouter только фоллбэком по `LLM_HOSTED_FALLBACK` | локально, если поднята Ollama |
| `eurorouter` | после #246: hosted-провайдер Eurorouter основным и единственным, код проверяемых репозиториев уходит ему на каждом прогоне. В `develop` значение не принимается, воркер не стартует | стенд после #246 (Ollama там нет) |

После #246 за каждый прогон на стенде будет платить ключ `AI_DMC268_T1`, тот же, что у
`eval.yml`; модель задаёт `.github/eurorouter-model`. Лимитов и баланса нет: сколько прогонов,
столько и трат. #246 ревьюит только PR авторов с `author_association` `OWNER`, `MEMBER` или
`COLLABORATOR`, остальные получают `202 ignored` без проверки. Это отсекает PR посторонних,
например из форков, но не чужие установки: в своём репозитории владелец сам `OWNER`. Списка
разрешённых аккаунтов нет. Какой адаптер и модель выбраны, воркер пишет при старте строкой
`модель: …`.

## Настройки приложения

Задаёт владелец приложения, один раз: GitHub → Settings → Developer settings → GitHub Apps →
приложение. Что сейчас стоит у нашего приложения, видно только в его настройках. Меняете
приложение или создаёте своё, выставьте всё из таблицы: пропущенное поле не ломает старт, а
молча отключает часть работы (последний столбец).

| Поле | Значение | Если не так |
|---|---|---|
| Callback URL | `<PUBLIC_ORIGIN>/api/v1/auth/github/callback` | вход в сервис падает |
| Request user authorization (OAuth) during installation | выключено | по документации GitHub при включённой галочке Setup URL не используется, после установки пользователь уходит на Callback URL |
| Webhook → Active | включено | GitHub не шлёт событий, прогонов нет |
| Webhook URL | `<PUBLIC_ORIGIN>/api/v1/webhooks/github` | то же |
| Webhook secret | значение секрета `WEBHOOK_SECRET_DMC268_T1` | каждая доставка получает `401`, прогонов нет |
| Permissions → Metadata | Read-only | обязательно, GitHub выставляет само |
| Permissions → Contents | Read-only | нет диффа (`GET /repos/{r}/compare/…` требует Contents): прогон падает |
| Permissions → Pull requests | Read and write | нет метаданных PR, ревью не публикуется, треды не читаются |
| Permissions → Checks | Read and write | нет проверки `dmc-268-ai-review`, merge gate не работает |
| Subscribe to events | Pull request; Pull request review thread | без первого нет прогонов; без второго проверка не пересчитывается при закрытии треда |
| Setup URL, Redirect on update | после #243: `<PUBLIC_ORIGIN>/api/v1/auth/github/setup`, Redirect on update включён, но только после проверки на стенде, что GitHub возвращает `state` (задача 3.4 change `repositories-one-list`). Сейчас этой ручки нет, поле не заполнять | после установки GitHub не вернёт пользователя в сервис |
| Where can this GitHub App be installed | «Any account» ставит на любые аккаунты; «Only on this account» только в `larchanka-training` | с «Only on this account» пользователи не поставят приложение на свои репозитории |

**«Any account» и деньги.** После #246 каждый прогон будет платить за модель с ключа
`AI_DMC268_T1`, а ограничений нет. С «Any account» любой пользователь GitHub сможет поставить
приложение на свои репозитории, подключить их и ревьюить свои PR за этот счёт: фильтр авторов
из #246 от этого не защищает. Как остановить,
по порядку:

1. Быстрее всего перестать платить: отозвать или сменить ключ `AI_DMC268_T1` у провайдера.
   Траты прекратятся сразу, но прогоны начнут падать, и на новых коммитах проверки
   `dmc-268-ai-review` не будет и в своих репозиториях: там, где она обязательная, мёрж ждёт её
   («Waiting for status») до шага 4. Это ожидаемо, а не новая поломка.
2. Чужие установки найти (`GET /app/installations` с JWT приложения) и удалить
   (`DELETE /app/installations/{installation_id}`). Приостановка (`PUT …/suspended`) сразу
   снимает вебхуки и токены, но установкой остаётся, и для шага 3 её всё равно придётся
   удалить: пока приложение установлено на других аккаунтах, GitHub не даёт переключить его в
   «Only on this account».
3. Потом закрыть новые установки: «Only on this account».
4. Вернуть стенд к заглушке: `TF_VAR_llm_backend: stub` в `deploy.yml` и деплой.

## Реквизиты приложения на стенде

Стенд берёт пять значений (App ID, Client ID, Client secret, Private key, Webhook secret) из переменных и секретов
репозитория `dmc-268-api-t1`. Имена и переменные OpenTofu перечислены в `infra/README.md`, в
двух таблицах «Откуда»: секрет вебхука в первой (без него `apply` не пройдёт), остальные
четыре во второй.

Секрет вебхука берите случайный и длинный: `openssl rand -hex 32`. Он меняется с простоем:
между сменой в настройках App и деплоем каждая доставка получает `401`. Упавшие доставки воркер
переотправляет сам: до 5 раз, с паузой от 5 минут, вдвое длиннее каждый раз (около 2,5 часа).
Когда попытки кончились, переотправляйте вручную из Recent Deliveries.

Private key меняется без простоя: сгенерировать новый в настройках App, положить в секрет,
выкатить стенд, удалить старый ключ в App. Если ключ утёк, старый удаляйте сразу, не дожидаясь
деплоя, и посмотрите журнал аудита организации: с утёкшим ключом выпускают токены установок и
ходят в API, а это не видно ни по установкам, ни по Recent Deliveries.

Сменить приложение, например на своё с нужными настройками: создать GitHub App по таблице выше,
заменить пять значений и перезапустить деплой. После смены:

- все входят заново: токены пользователей выданы старым приложением;
- подключённые репозитории остаются подключёнными (`installation_id` в базе не хранится, он
  приходит в вебхуке), но новое приложение нужно **установить** на них, иначе вебхуков нет;
- обязательная проверка `dmc-268-ai-review` в rulesets привязана к id приложения
  (`integration_id`), её источник надо перенастроить (README, «Merge gate»).

Для локальной разработки со своим приложением нужны те же переменные `GITHUB_APP_*` и
`PUBLIC_ORIGIN` (`.env.example`, README, «Путь без лишних зависимостей»), а чтобы вебхуки
доходили до ноутбука, нужен туннель на локальный API.

## Почему на стенде нет прогонов

Проверяйте по порядку: каждый шаг отсекает свою причину. Всё ниже только читает.

1. **Доходят ли вебхуки.** В настройках приложения → Advanced → Recent Deliveries (видит
   владелец приложения). Доставок нет: не задан Webhook URL или не включён Webhook. Доставки с
   ошибкой: там же код ответа. Со стороны стенда смотрите шаг «Доставки вебхука и сбои воркера с
   прошлого выката» в summary деплоя: число `POST /webhooks` по кодам и запросов GitHub-Hookshot к
   nginx.
2. **Что ответил сервис.**
   - `401`: секрет вебхука в настройках приложения не совпадает с `WEBHOOK_SECRET_DMC268_T1`;
   - `202` `ignored`: репозиторий не подключён (после #243 ещё и выключен, тогда на коммите
     зелёная проверка «Ревью выключено в сервисе»), действие PR не `opened` и не
     `synchronize`, либо, после #246, автор PR не `OWNER`, `MEMBER` или `COLLABORATOR`;
   - `502`: сервис не достучался до GitHub, проверьте реквизиты приложения на стенде.
3. **Подключён ли репозиторий.** Сейчас: есть строка на странице «Репозитории»
   (`GET /api/v1/repositories`), значит подключён. Строки нет: смотрите «Подключение
   репозитория» (`GET /api/v1/repositories/available`). Там нет и его: приложение не установлено
   или у вас нет доступа (см. [«Три состояния репозитория»](#три-состояния-репозитория) и
   [«Роли GitHub»](#роли-github-кто-ставит-кто-видит-и-кто-подключает)). После #243 одна страница, у строки
   `connected: true`.
4. **Настоящая ли модель.** Строка `модель: …` в логе старта воркера. `заглушка` значит, что
   ревью будут пустыми (см. «Модель и деньги»).
5. **Что с прогоном.** Вкладка «Ревью» интерфейса: статус и шаги прогона, у упавшего причина
   (`failure_reason`).
