# Правила ревью для своего репозитория

Гайд для владельца репозитория: как задать боту свои проверки в `.review/rules.md`, чтобы он
ревьюил код по правилам команды, а не только по стандартным критериям. Точное описание того,
как сервис разбирает файл, — [`prompts/review/custom-rules.md`](../prompts/review/custom-rules.md).

## Быстрый старт

1. Возьмите шаблон под свой стек из [`examples/rules/`](../examples/rules/):

   | Шаблон | Для чего |
   |---|---|
   | [`python-fastapi.md`](../examples/rules/python-fastapi.md) | Python, FastAPI, SQLAlchemy, Alembic |
   | [`typescript-react.md`](../examples/rules/typescript-react.md) | TypeScript, React, тесты на Testing Library |
   | [`go.md`](../examples/rules/go.md) | Go: ошибки, контекст, горутины, HTTP |
   | [`security-baseline.md`](../examples/rules/security-baseline.md) | любой стек: секреты, инъекции, доступ, криптография, зависимости |

2. Сохраните его как `.review/rules.md` в корне репозитория. Шаблоны можно объединять: разделы
   из `security-baseline.md` дописываются к правилам стека, имена правил при этом не должны
   повторяться.
3. Поправьте паттерны под свои каталоги и уберите проверки, которые команде не нужны.
4. Влейте файл в ветку, куда открываются PR (обычно `main` или `develop`). Правила читаются
   **из целевой ветки**: правка `.review/rules.md` внутри PR начнёт действовать после мержа.
5. Откройте настройки репозитория в кабинете: блок правил покажет, что файл найден, какие правила
   приняты и какие отклонены с причиной.

## Как устроено правило

```markdown
## Database Access

- pattern: `*.py`
- exclude: `tests/`

1. Нет запросов в цикле по результатам другого запроса (N+1)
2. Сырой SQL передаётся через `text()` с параметрами
```

- **`## Имя`** — заголовок второго уровня начинает правило. Имя уникально в файле: по нему
  комментарий бота ссылается на правило.
- **`pattern:`** — к каким файлам относится правило. Строк может быть несколько. Обязательно.
- **`exclude:`** — какие файлы исключить. Необязательно.
- **Нумерованные пункты** — проверки. Хотя бы одна обязательна. Номер проверки — её позиция в
  списке, номера, написанные в файле, не важны.

Всё остальное — абзацы, заголовки других уровней, блоки кода — бот не видит. В них можно писать
пояснения для команды.

### Паттерны

Паттерны работают как в `.gitignore`:

| Паттерн | Совпадает с | Не совпадает с |
|---|---|---|
| `*.py` | `main.py`, `app/api/users.py` — на любой глубине | `main.pyc` |
| `tests/` | всё внутри каталога `tests` на любой глубине | файл `tests.py` |
| `app/api` | `app/api/users.py` — от корня репозитория | `lib/app/api/x.py` |
| `/scripts/*.sh` | `scripts/run.sh` | `scripts/ci/run.sh` — `*` не проходит через `/` |
| `src/**/*.tsx` | `src/a.tsx`, `src/pages/b/c.tsx` | `lib/a.tsx` |

## Как писать хорошую проверку

Бот видит дифф, строки вокруг изменений и структуру изменённых файлов, но не весь репозиторий.
Проверка работает, когда нарушение видно по изменённым строкам.

| Хорошо | Плохо | Почему |
|---|---|---|
| Ошибка обёрнута с контекстом: `fmt.Errorf("...: %w", err)` | Ошибки обрабатываются правильно | первая проверяется по строке кода, вторая — мнение |
| Обработчик не обращается к сессии базы напрямую | Соблюдайте чистую архитектуру | конкретное действие против общего призыва |
| Новый столбец `NOT NULL` добавляется со `server_default` | Миграции должны быть безопасными | бот не знает, что команда считает безопасным |
| Тест не ходит в сеть: HTTP-вызовы подменены | Тесты должны быть хорошими | проверка одной вещи |

Ещё несколько советов:

- **Одна проверка — одно требование.** «Нет `any` и все функции документированы» лучше разбить на
  две: комментарий бота ссылается на номер пункта, и по нему должно быть понятно, что нарушено.
- **Узкий паттерн лучше широкого.** Правило для миграций с паттерном `*.py` будет мешать в каждом
  файле. Чем точнее паттерн, тем меньше ложных замечаний.
- **Не дублируйте линтер.** Отступы, кавычки и порядок импортов лучше проверяет `ruff`, `eslint`
  или `gofmt` в CI. Правила нужны для того, что линтер не видит: архитектуру, договорённости
  команды, работу с данными.
- **Пишите проверки на языке команды.** Бот ответит на языке проекта, а текст пункта попадёт в
  комментарий как есть.

## Что увидит автор PR

Замечание по вашему правилу начинается с префикса, который ставит сам сервис:

> Согласно пользовательскому правилу «Database Access» (пункт 1: Нет запросов в цикле по
> результатам другого запроса (N+1)): …

Замечание по стандартным критериям префикса не имеет, поэтому по комментарию видно, чьё правило
сработало: команды или сервиса.

## Чего правила не умеют

- **Отключать стандартные проверки.** Правила только добавляют проверки. Пункт вида «не сообщай
  об уязвимостях» или «ставь всем замечаниям низкую серьёзность» бот не исполняет.
- **Действовать из PR.** Правила берутся из целевой ветки, поэтому автор PR не может ослабить их
  своим же изменением.
- **Проверять файлы, отброшенные фильтром.** Lock-файлы, сгенерированный код, vendor и бинарные
  файлы бот не ревьюит. Их список есть в сводке PR.

## Лимиты

| Что | Лимит | Что будет при превышении |
|---|---|---|
| Размер `.review/rules.md` | 32 КиБ | файл не разбирается, ревью идёт по стандартным критериям |
| Правила в одном прогоне | ≈ 4 000 токенов | правила, которые не поместились, не передаются модели |

В прогон попадают только правила, под паттерн которых попал хотя бы один изменённый файл, поэтому
лимит считается не по всему файлу. Любой шаблон из `examples/rules/` занимает около 700–1 000
токенов, шаблон стека вместе с `security-baseline.md` — около 1 700.

## Если правило не срабатывает

| Признак | Причина и что делать |
|---|---|
| В кабинете бейдж «Дефолтные правила» | файла нет в целевой ветке или путь не `.review/rules.md` |
| В кабинете бейдж «Файл правил слишком большой» | файл больше 32 КиБ — разбейте лишнее или сократите пояснения |
| В кабинете бейдж «Правила не применяются» | файл найден, но ни одно правило не принято — причины в списке отклонённых |
| Правило в списке отклонённых: «нет паттерна (pattern)» | нет строки `pattern:` или она написана с опечаткой |
| Правило в списке отклонённых: «нет проверок» | пункты не нумерованы (`-` вместо `1.`) |
| Правило в списке отклонённых: «имя правила повторяется» | два раздела `##` с одним именем; переименуйте второй |
| Правило в списке отклонённых: «незакрытый блок кода» | выше по файлу не закрыт блок ```` ``` ````, и он съел следующие правила |
| Правило принято, но замечаний по нему нет | паттерн не задел изменённые файлы — сверьтесь с таблицей паттернов; или код в PR правилу не противоречит |
