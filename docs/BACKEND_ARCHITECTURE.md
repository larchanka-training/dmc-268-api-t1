# Архитектура бэкенда

Бэкенд агента для автоматического код-ревью: он отслеживает change request'ы,
собирает контекст вокруг диффа, отдаёт его модели на ревью и публикует
результат обратно на хостинг.

Здесь описано, как устроен сервис, какое правило не даёт этой структуре
расползтись и какие точки расширения уже спроектированы, но пока намеренно не
реализованы. Документ правится в том же изменении, которое меняет описанное в
нём.

## Слои

Четыре пакета внутри `app/`, зависимости направлены только внутрь.

```
app/api/             FastAPI routers, request and response schemas, dependencies
app/infrastructure/  adapters, SQLAlchemy models, the composition root
app/application/     use cases and the ports they depend on
app/domain/          entities, enums, and the rules, as pure functions
```

| Слой | Может импортировать | Содержит |
|---|---|---|
| `domain` | ничего снаружи, никаких сторонних пакетов | сущности, enum'ы, чистые функции принятия решений |
| `application` | `domain` | use case'ы, определения портов |
| `infrastructure` | `application`, `domain`, `api` | адаптеры, модели, контейнер |
| `api` | `application`, `domain`, `infrastructure` | транспорт |

`api` и `infrastructure` находятся на одном уровне и могут импортировать друг
друга: composition root живёт в `infrastructure`, а фабрика приложения в `api`
должна его собрать. Важно лишь, чтобы ни один из них не был достижим из
`application` или `domain`.

### Правило проверяется автоматически, а не держится на договорённости

`import-linter` в CI проверяет три контракта из `pyproject.toml`. Первый задаёт
порядок слоёв. Второй не даёт точке входа разрастись: `app.main` не может
обращаться к `domain`, `application` или `infrastructure` напрямую, только
через `app.api`. Третий полностью запрещает `sqlalchemy`, `fastapi`, `httpx`,
`ollama`, `pika`, `alembic`, `psycopg` и пакеты `tree_sitter*` в `domain` и
`application`.

```
$ lint-imports
Dependencies point inward KEPT
The entrypoint stays thin KEPT
Inner layers know no vendor KEPT
```

При нарушении указываются модуль и строка:

```
app.domain is not allowed to import sqlalchemy:
-   app.domain._violation -> sqlalchemy (l.1)
```

Так сделано специально. Слоистость, которая держится на внимательности
ревьюеров, со временем разваливается. Слоистость, нарушение которой ломает
сборку, нет.

## Чистое ядро

Каждое решение принимает функция, которая получает данные и возвращает данные.
Внутри нет I/O, чтения часов и случайности: время и идентификаторы приходят
аргументами, поэтому тест проверяет точный timestamp, а не диапазон.

| Функция | Модуль | Что решает |
|---|---|---|
| `next_status(current, requested)` | `domain/lifecycle.py` | может ли прогон сменить состояние |
| `validate_anchor(anchor, hunks)` | `domain/diff.py` | указывает ли замечание внутрь диффа |
| `deduplicate(findings)` | `domain/dedup.py` | какие замечания дублируют друг друга |
| `find_stale(runs, now, limit)` | `domain/staleness.py` | какие прогоны перестали продвигаться |

Именно благодаря этому unit-уровень тестов вообще возможен. Большая часть
тестов запускается под `pytest` без базы, брокера и сети. Тесты, которым всё же
нужен PostgreSQL, помечены `integration` и пропускаются, если не задан
`TEST_DATABASE_URL`. Актуальное количество тестов и причина, по которой эта
переменная называется не `DATABASE_URL`, описаны в README.

Адаптеры только переводят данные и больше ничего не делают. Если кажется, что
адаптер применяет правило, значит, он вызывает одну из функций выше:
`SqlAlchemyReviewRunRepo.update` сверяется с `next_status` перед записью
статуса, а `SqlAlchemyFindingRepo.add_validated` сверяется с `validate_anchor`
и учитывает отклонённое замечание в прогоне, чтобы от отфильтрованного
замечания оставался след.

## Порты

К внешней системе обращаются через порт, которым владеет внутренний слой, а
адаптер предоставляет `infrastructure`. Порты сделаны через `typing.Protocol`,
поэтому адаптер никогда не импортирует порт, и у слоя инфраструктуры нет
compile-time зависимости от слоя приложения.

адаптером. Тест проверяет, что у каждого объявленного порта есть адаптер и что
ни один модуль в `api`, `application` или `domain` не ссылается на конкретную
реализацию.

### Сессия на ручках

Две проверки, по порядку:

- `OriginMiddleware` (`app/api/origin.py`) — изменяющие запросы (`POST`, `PUT`, `PATCH`,
  `DELETE`) под `/api/v1/`, кроме приёма вебхуков, проходят, только если `Origin` равен
  `PUBLIC_ORIGIN`; иначе `403 ORIGIN_FORBIDDEN`. Middleware, а не зависимость: FastAPI
  разбирает JSON тела раньше зависимостей, а чужой запрос должен получить `403` до
  разбора тела, сессии и базы.
- `current_user` из `app/api/session.py` — зависимость в `SESSION_REQUIRED`, подключённая
  на уровне роутера: какие ручки открыты, видно в объявлении маршрутов. Пользователь
  сессии из cookie `session` через use case `authenticate`; без действительной сессии
  `401 UNAUTHENTICATED`, а пришедшая недействительная cookie удаляется в том же ответе.
  Битый JSON тела FastAPI отклоняет `422` раньше зависимостей, поэтому со своим `Origin`
  и без сессии он получает `422`, а не `401`.

Открыты без сессии: `/webhooks/*` (подпись), `/auth/{provider}/login`,
`/auth/{provider}/callback` и `/health`. `POST /auth/logout` сессии не требует,
только `Origin`: выход идемпотентен и всегда отвечает `204`.

Ручки репозиториев (`/repositories/available`, `POST /repositories`) берут ещё и токен
пользователя у провайдера, сохранённый при сессии (`call_with_user_token`,
`app/application/use_cases/user_token.py`): истёкший — обмен по refresh token под
блокировкой строки токена (сбой обмена при ещё действующем токене — прежний токен),
`401` на токен, заменённый параллельным обменом, — один повтор с новым, непригодный (нет, не
расшифровывается, отвергнут GitHub) — сессия закрывается и `401 UNAUTHENTICATED` с удалением
cookie. Выход отзывает токен у GitHub после ответа. Обоснование — change
`repositories-via-user-token`.

Истёкшие сессии стирает воркер в том же периодическом проходе, что выметает
зависшие прогоны (`purge_expired_sessions`, раз в минуту). Индекса по
`expires_at` нет: таблица мала, а проход не лежит на пути запроса.

Тот же проход, но не чаще `WEBHOOK_REDELIVERY_INTERVAL_SECONDS`, переотправляет
упавшие доставки вебхука (#149): GitHub сам их не повторяет. Порт
`WebhookDeliveries` (адаптер `GitHubWebhookDeliveries`, JWT приложения) отдаёт
попытки за трое суток, чистая `select_redeliveries` выбирает группы `guid` без
успешной попытки — только события приёма, не больше `max_attempts` переотправок
с паузой, растущей вдвое, — и запросы идут по одному, в пределах бюджета
времени прохода. Доставку `pull_request`, чей коммит уже не голова PR
(`fetch_pr_metadata`), проход не переотправляет: повтор откатил бы head
merge_request на старый коммит. Состояния нет: попытки
считаются по самому списку. Дубль переотправки (два воркера) безвреден: приём
отвечает существующим прогоном, в том числе завершённым не-`failed` (#75).

### Спроектированы, но не реализованы

Порт не пишется, пока его никто не вызывает. Интерфейс, написанный на тикет
раньше своего первого адаптера, это догадка о сигнатуре, и выясняется, что она
неверна, ровно тогда, когда появляется адаптер. В этот момент переписываются и
интерфейс, и его фейк, и тесты. Поэтому здесь они только зафиксированы: это
ничего не стоит и не может оказаться неправильным.

| Точка расширения | Первый адаптер | Что нужно для внедрения |
|---|---|---|
| `IdempotencyStore` | PostgreSQL | захватить ключ через `INSERT ... ON CONFLICT DO NOTHING`, воспроизвести результат победившего запроса. Появится вместе с первым эндпоинтом, который принимает повторы. |
| `RateLimiter` | PostgreSQL | счётчик с фиксированным окном на субъект, `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`. |

Таблицы `accounts`, `idempotency_records` и `rate_limit_counters`
спроектированы вместе с этими портами и появятся вместе с ними.

## Процессы

Одна кодовая база, один образ, две точки входа.

```
uvicorn app.main:app        HTTP: request-response, milliseconds
python -m app.worker      review consumer: minutes, bound by model latency
```

`app/worker` — такая же тонкая точка входа, как `app/main.py`
(`app/worker/__main__.py` + `app/worker/factory.py`, по аналогии с
`app/api/factory.py`): собирает и запускает consume-цикл над `review_jobs`,
ack/nack и dead-letter настоящие. Обработчик сообщения — `run_review`
(`app/application/review_pipeline.py`): разбирает `ReviewJob` из сообщения,
проводит прогон через `queued → building_context → analysing → publishing →
completed`/`failed`: контекст собирает `build_review_context` (дифф,
AST-окружение, правила владельца), анализ — `LlmGateway` (пока заглушка).
Начало и исход каждого этапа (`fetching_diff`, `building_context`,
`analysing`, `verifying`, `publishing`) пишет в `review_run_steps`
`StepRecorder` (`app/application/review_run_steps.py`); их отдаёт
`GET /api/v1/reviews/{id}/steps`. Тот же `StepRecorder` открывает на каждый
шаг спан трассировки, а спан обработки сообщения продолжает трейс запроса
вебхука из заголовка AMQP (раздел «Наблюдаемость»).

У них общие домен, репозитории и база данных, а общаются они через очередь, а
не по HTTP. Это модульный монолит, а не набор сервисов.

Микросервисы решают организационную проблему: дают независимым командам
выпускать релизы без согласования. Здесь одна команда, поэтому издержки есть,
а выгоды нет. Сетевые вызовы там, где хватило бы вызова функции, частичные
отказы, версионирование контрактов, трассировка через границы процессов и
локальное окружение, которому нужно несколько контейнеров, прежде чем что-то
заработает. Нагляднее всего это видно на идемпотентности: здесь это одна задача
в одном месте, а так её пришлось бы решать заново на каждой придуманной нами
границе.

Разница в профилях нагрузки двух процессов реальна, но двух процессов для неё
достаточно, потому что они никогда не вызывают друг друга синхронно.

**Когда действительно стоит разделять.** Когда компоненту нужен другой runtime.
Очевидный кандидат это парсинг AST для четвёртого уровня контекста: если
Python-биндинги tree-sitter разочаруют, в отдельный сервис первым стоит
вынести парсинг. Вынести его значит дать одному порту сетевой адаптер, а не
перестраивать код. Это паттерн Strangler Fig, и именно поэтому модульный
монолит обычно служит для него отправной точкой.

Топология развёртывания в зоне ответственности System Design. Здесь
зафиксировано, на что рассчитывает бэкенд.

## Данные

Диаграмма и ограничения описаны в [модели данных](erd.md).

`ReviewRun` это `ReviewJob` из тикета. Название поменяли, потому что "job"
будет называться и сообщение в RabbitMQ, а когда долгоживущая строка в базе и
временное сообщение называются одинаково, люди в итоге отлаживают не то.

Идентификаторы это UUIDv7, которые генерируются в домене и никогда не
берутся из дефолта базы данных. Упорядоченные по времени ключи попадают в
правый край индекса, а не разбрасываются по нему, как `uuid4`, и сущность
полностью собрана в памяти ещё до обращения к PostgreSQL. `uuid.uuid7()` есть
в стандартной библиотеке начиная с 3.14.

Timestamp'ы явно объявлены как `DateTime(timezone=True)`. Голый
`Mapped[datetime]` компилируется в `TIMESTAMP WITHOUT TIME ZONE`, который
выглядит правильно, но работает неправильно: прогон, начавшийся перед
переходом на летнее или зимнее время, мог бы завершиться раньше, чем начался.
Тесты схемы проверяют скомпилированный DDL, а не аннотацию, потому что именно
аннотация выглядит правильно, будучи неправильной.

## Миграции

Изменения схемы попадают в базу только через Alembic-ревизию, прошедшую ревью.
Приложение ничего не создаёт при старте.

- Имена файлов начинаются с префикса, дополненного нулями: `0001_baseline_schema.py`.
- Ровно один head. Две ветки, каждая из которых добавляет миграцию, при rebase выстраиваются в линию.
- Каждая миграция обратима. `upgrade head`, `downgrade base` и снова `upgrade
  head` должны пройти успешно и не оставить мусора.
- Сгенерированные миграции просматриваются перед коммитом. Baseline без этого
  не обошёлся: autogenerate при downgrade удалял таблицы, но оставлял все
  восемь нативных enum-типов, так что откат был неполным, а следующий upgrade
  упал бы на создании уже существующих типов.
- `env.py` читает `DATABASE_URL` через `Settings`, поэтому в `alembic.ini` нет
  строки подключения, и они не могут разойтись. Если вызывающий код уже задал
  эту опцию, она сохраняется: так тесты направляют миграции на
  `TEST_DATABASE_URL`, не трогая то, что читает сервис. Значение экранируется
  при передаче, потому что `configparser` считает `%` интерполяцией и сразу
  отвергает пароль с percent-encoding.
- Деплой применяет миграцию шагом до выката нового кода, поэтому ломающая миграция
  даёт на стенде короткий сбой старого кода во время выката. Пока нет пользователей,
  это допустимо; для прода — expand/contract в два деплоя (скилл `alembic-migration`).

Интеграционный тест мигрирует одноразовую базу до head и проверяет, что
autogenerate не находит изменений, так что модели и схема не могут незаметно
разойтись.

**Добавление значения в enum** требует `ALTER TYPE ... ADD VALUE`, а в старых
версиях PostgreSQL это нельзя выполнить внутри транзакции. Выносите это в
отдельную миграцию:

```python
def upgrade() -> None:
    op.execute("COMMIT")
    op.execute("ALTER TYPE finding_category ADD VALUE 'maintainability'")
```

Удаление значения означает пересоздание типа, поэтому наборы значений
небольшие и меняются редко.

## Конфигурация

Всё берётся из одного провалидированного объекта, который собирается при
старте. Ниже composition root слои получают нужное через аргументы, окружение
читает только `app/config.py`.

Если обязательная настройка не задана, старт явно падает и называет её.
Обязательная для всех процессов сейчас одна, `DATABASE_URL`; воркеру нужна
ещё `LLM_BACKEND` (`stub` или `ollama`): заглушка модели выбирается только
явно, и без переменной (или с пустой, как её передаёт compose) воркер не
стартует. Зависимости между настройками
модели - `OLLAMA_MODEL` при `ollama`, адрес, модель и ключи Eurorouter при
`LLM_HOSTED_FALLBACK=true` - проверяет валидатор настроек, а то, что пакет
контекста на пределе лимита, системный промпт и резерв ответа помещаются в
окно `LLM_CONTEXT_WINDOW_TOKENS`, и что вызов модели в худшем случае
(`LLM_TIMEOUT_SECONDS` × `LLM_MAX_ATTEMPTS` × провайдеры) короче
`STALE_RUN_TIMEOUT_SECONDS`, а порог ждущего в очереди прогона
`QUEUED_RUN_TIMEOUT_SECONDS` (6 ч) - больше `STALE_RUN_TIMEOUT_SECONDS`, - воркер
при старте, до подключения к брокеру.
Настройки `github_app_id`, `github_app_private_key`, `github_webhook_secret`,
`rabbitmq_url`, `github_app_client_id`, `github_app_client_secret`, `public_origin` и
`user_token_encryption_key` опциональны с пустым дефолтом: приложение без GitHub-реквизитов поднимается
и отвечает на запросы, не касающиеся вебхуков, а пустая настройка громко
падает при первом использовании (пустой ключ токенов — отказ входа; битый —
падение старта, без значения в сообщении). Исключение — повтор упавших доставок
вебхука в проходе воркера (`WEBHOOK_REDELIVERY_*`, #149): без `GITHUB_APP_ID` или
ключа шаг не собирается, и об этом одна строка INFO при старте. Новые настройки появляются вместе с кодом,
который их использует.

## Наблюдаемость

Здесь два разных источника для двух разных читателей, и они не смешиваются.

**Данные продукта — из базы.** Всё, что видит пользователь кабинета, —
длительность, токены и модель прогона, шаги «хода прогона», будущие usage и
биллинг — хранится в колонках и таблицах и отдаётся через REST. `review_runs`
хранит в строке `model`, `tokens_used`, `duration_seconds` и `failure_reason`,
шаги — `review_run_steps`. Вопросы «почему ревью заняло четыре минуты», «во что
обошлась прошлая неделя», «какие прогоны падают и где» решает SQL по таблицам,
которые нужны в любом случае, и ответ остаётся привязан к прогону, который
человек смотрит.

**Телеметрия — для команды.** Трассировка и метрики OpenTelemetry отвечают на
эксплуатационные вопросы: где тормозит, что падает, что происходило между
вебхуком и публикацией. Пользователю она не показывается: спаны сэмплируются,
хранятся ограниченно и не разделены по аккаунтам. Спаны этапов повторяют шаги
прогона, но источником шагов для API не становятся; ни один ответ API не
строится из телеметрии, это проверяет `tests/api/test_tracing.py`. Граница
распространяется и на метрики: в Prometheus уходят только сигналы алертов,
любой отчёт по прогонам — SQL по таблицам, описанным выше.

Трассировка нужна, хотя процессов два: запрос вебхука и работа воркера по нему
разделены очередью, и без общего trace id их связывает только `review_run_id`.
Как устроено (`app/infrastructure/telemetry.py`, `app/infrastructure/logging.py`,
стек `infra/observability/`; спека `observability`):

- **Провайдер.** SDK-провайдер ставят `create_app`, `run_worker` и
  `alembic/env.py` — миграции идут с сервисом `dmc-268-migrate` и корневым
  спаном `migrate`, SQL-миграции — его дети: в Tempo видно, сколько они занимают
  при деплое. HTTP-сервер
  трассирует встроенная телеметрия FastAPI — снаружи всех middleware, поэтому
  `X-Trace-ID` и `trace_id` в problem+json, в том числе у `500`, — trace id
  спана запроса. httpx (GitHub, модель) — `opentelemetry-instrumentation-httpx`,
  запросы к базе — `EngineTracer` из `opentelemetry-instrumentation-sqlalchemy`
  на движке контейнера. Класс внутренний: пакеты contrib держит верхняя граница
  серии в `pyproject.toml`, а несовместимый `EngineTracer` выключает спаны SQL с
  предупреждением и не мешает старту.
- **Через очередь.** Контекст — заголовок AMQP `traceparent` (W3C), тело
  сообщения не меняется. Публикацию и приём делает адаптер очереди
  (`_publish`, `consuming_span`), а не автоинструментирование pika: для
  генератора `consume()` оно закрывает спан приёма сразу и держит его контекст
  текущим на простое цикла. Признак повторной доставки попадает в спан обработки
  булевым атрибутом `messaging.rabbitmq.message.redelivered`.
- **Поток событий.** Цикл опроса `GET /api/v1/events` идёт вне трейса: десять
  минут просмотра в кабинете не добавляют в трейс SQL-спанов, а штатное
  отключение клиента закрывает спан потока без ошибки (`untraced`,
  `app/api/events.py`).
- **Доверие.** Глобальный пропагатор пуст: входящий `traceparent` от HTTP-клиента
  не продолжает трейс (каждый запрос начинает новый), и httpx не отдаёт наш
  контекст GitHub и провайдерам модели. Заголовкам своей очереди доверяем —
  писать в неё может только API.
- **Трейс клиента — ссылкой.** Валидный `traceparent` запроса (кабинет шлёт его
  из браузера) серверный спан получает не родителем, а span link с атрибутом
  `link.source = "client"`: в Tempo от трейса API виден переход к спану браузера.
  Ссылку ставит `link_client_trace` из `TraceIdMiddleware`, где спан запроса уже
  текущий: у встроенной телеметрии FastAPI нет ни параметра `links`, ни хука на
  создание спана, а `span.add_link` SDK поддерживает с 1.45. Разбирает
  `TraceContextTextMapPropagator`, и только `traceparent` — `tracestate` и baggage
  ему не передаются; невалидный заголовок — без ссылки и без ошибки. Почему не
  родитель: trace id показывается людям (`X-Trace-ID`, problem+json, логи) и
  должен быть нашим; флаг `sampled` клиента управлял бы записью трейсов (`00` —
  ничего, `01` — всё при частичном сэмплировании), а ссылки сэмплер
  `parentbased_*` не видит — она добавляется после его решения; один `trace_id`
  в тысяче запросов склеил бы их в гигантский трейс; браузер, не выгрузивший свои
  спаны, оставил бы серверный трейс без корня. CORS не нужен: кабинет ходит в API
  с того же origin.
- **Этапы.** Спан `review.<этап>` с атрибутом `review_run_id` открывается и
  закрывается в тех же точках, что шаг `StepRecorder`; повтор этапа — отдельный
  спан. Слой приложения о OpenTelemetry не знает: шаги зовут порт
  `StageTracer`, адаптер — `OtelStageTracer`; `opentelemetry` в запрещённых
  вендорах внутренних слоёв (`lint-imports`).
- **Экспорт включается окружением.** Список экспортёров разбирает
  `parse_exporters`: значение `OTEL_TRACES_EXPORTER` — через запятую,
  поддержаны `console` и `otlp`, пробелы, регистр и дубликаты гасятся, мусорное
  значение выключает только себя с одним предупреждением в лог. По умолчанию
  `none`: спаны никуда не уходят и ошибок экспорта в логе нет. `console`
  печатает их в stdout для отладки, `otlp` шлёт OTLP/HTTP в коллектор
  (`OTEL_EXPORTER_OTLP_ENDPOINT`). Ресурс дополняют `OTEL_RESOURCE_ATTRIBUTES` —
  `service.version` (в инфре — sha образа), `deployment.environment.name` и стабильный
  `service.instance.id` по сервису (`dmc268-api`, `dmc268-worker`, `dmc268-migrate`): случайный
  UUID на процесс растил бы в Prometheus серии `exported_instance`. Таймаут OTLP —
  `OTEL_EXPORTER_OTLP_TIMEOUT=4`, в секундах: Python SDK читает переменную в секундах, вопреки
  спецификации OTel с её миллисекундами (4000 означало бы 66 минут), значение меньше окна
  graceful shutdown (5 с). Лимит длины атрибутов — `OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT`.
  Автонастройка
  экспортёров FastAPI и его OTel-лог исключений выключены явно
  (`telemetry={"auto_configure": False, "logs": False}` в `create_app`).
- **Метрики** — тот же SDK с отдельным гейтом: `configure_telemetry` собирает
  `MeterProvider` с периодическим экспортом, включая его `OTEL_METRICS_EXPORTER`
  — тот же список, `none` по умолчанию. HTTP-метрики даёт встроенная телеметрия
  FastAPI, ручки `/metrics` нет — Prometheus собирает их через коллектор, а
  `resource_to_telemetry_conversion` делает лейбл `job` равным `service.name`.
  Ручные — только сигналы алертов: прогоны по статусам (`review_runs_total{status}`),
  длительность этапов (`review_stage_duration{stage}`) и каждого фактического вызова
  провайдера (`review_llm_call_duration{outcome}` — в `FallbackLlmGateway`; метка
  `provider` стоит всегда, `model` — модель ответа только у `ok`, в гистограмму попадают
  упавшие вызовы и таймауты), пул соединений — снимками состояния (`db.client.connection.*`);
  стоимость — отдельное изменение (#119).
  «Во что обошёлся прогон» остаётся SQL по колонкам `review_runs`: метрики —
  для алертов, не для отчётов.
- **Логи** — два транспорта из одной точки настройки. `configure_logging(service_name)`
  ставит JSON-хендлер в stdout: поля по модели данных OTel — `timestamp`, `severity`,
  `message`, `logger`, `service.name`, атрибуты из `extra` верхним уровнем
  (служебные поля `extra` перетереть не может); trace-поля
  (`trace_id`/`span_id`/`trace_flags`) добавляет `TraceContextFilter` из
  текущего спана, запись вне спана пишется без них и не теряется. `exc_info`
  кладёт стектрейс и `exception.type` (qualname класса) в ту же запись,
  дубль uvicorn «Exception in ASGI application» отсекается: на `500` в логе
  ровно одна запись, и её `trace_id` равен `X-Trace-ID` ответа. Необработанное
  исключение воркера — вплоть до `WorkerConfigError` старта — пишут excepthook'и
  той же JSON-записью: текстовый дамп интерпретатора уходит в stderr и до
  хранилища логов не доходит. stdout остаётся для `docker logs` и локальной
  отладки; в Loki записи уходят вторым транспортом — по OTLP из SDK при
  `OTEL_LOGS_EXPORTER=otlp` (дефолт `none` — только stdout): `configure_telemetry`
  ставит `LoggerProvider` с `BatchLogRecordProcessor` и хендлер на root, resource
  общий с трейсами, тело записи — текст сообщения, `exc_info` — атрибуты
  `exception.*`. Коллектор принимает логи только по OTLP — каталог Docker не
  читает, логов postgres и rabbitmq в Loki нет. От записи лога к трейсу в
  Grafana ведёт переход по `trace_id` (derived field по structured metadata
  OTLP-лога). На пути коллектор редактирует записи с исключениями: стектрейс,
  текст и тело такой записи заменяются маркером `<скрыто>`, `exception.type`
  остаётся диагнозом.
- **Стек** — восемь контейнеров (коллектор, Loki, Tempo, Prometheus, Grafana,
  node_exporter за сервер, cAdvisor за контейнеры и socket-proxy — доступ cAdvisor
  к Docker API по белому списку эндпоинтов вместо маунта `docker.sock`) с
  одними конфигами локально и на стенде: конфиги лежат в
  `infra/observability/`, локально их монтирует профиль `observability` в
  compose, на стенде те же файлы собирает `infra/` (Terraform), весь стек — за
  флагом `observability_enabled` (по умолчанию выключен; потолки памяти и
  объём диска — в `infra/README.md`). Метрики базы
  снимает сам коллектор receiver-ом `postgresql` — отдельного экспортёра нет,
  роль только-чтение `dmc268_monitor` с `pg_monitor` создаёт миграция 0013.
  На входе трейсов и логов коллектор редактирует чувствительные данные — query
  URL, значения `db.*`, тексты и стектрейсы исключений заменяются маркером
  `<скрыто>`, атрибут остаётся; проверка — `tests/infrastructure/test_collector_redaction.py`.
  Разворачивание стенда — по готовности DevOps; для включения экспорта сервису
  нужен только `OTEL_EXPORTER_OTLP_ENDPOINT`, код при этом не меняется.
- **Атрибуты** SQL и httpx — стабильные имена semconv:
  `OTEL_SEMCONV_STABILITY_OPT_IN=database,http` по умолчанию ставит код до первого
  инструментирования (пакеты читают переменную один раз на процесс).

## Расширение

**Добавление GitLab.** Адаптер `VcsGateway` и ещё одно значение в enum
`provider`. Миграция не нужна: каждая запись, отражающая объект хостинга, уже
хранит дискриминатор провайдера рядом с id самого хостинга, и ни один use case
не ссылается на конкретного провайдера.

**Добавление Redis.** По одному классу адаптера на порт и привязка в
контейнере. Места вызова не меняются, потому что вызывающий код с самого
начала будет написан против `IdempotencyStore`, `RateLimiter` и `CacheStore`.
Поводом станет кэш в памяти процесса: он корректен для одного процесса и
бесполезен для нескольких реплик, так что как только появится вторая реплика,
он станет неправильным.

**Смена базы данных.** Сложнее, и мы с этим согласны. Схема использует
нативные enum'ы, JSONB, массивы, частичный уникальный индекс и `ON CONFLICT`,
и ничего из этого не переносится на другой движок. Это осознанный компромисс:
использовать базу данных как базу данных, а не как хранилище строк. В
частности, именно частичный индекс делает правило "один активный прогон на
коммит" атомарным, а не гонкой между `SELECT` и `INSERT`.

## Модель угроз

Агент код-ревью по своей природе читает входные данные, на которые может
влиять атакующий, хранит учётные данные с правом записи в репозитории и хранит
чужой исходный код.

**Prompt injection через проверяемый код.** Дифф контролирует атакующий.
Pull request может содержать `# IGNORE ALL PREVIOUS INSTRUCTIONS` в
комментарии, docstring или тестовой фикстуре. Защита строится на структуре,
потому что фильтрация по фразам проигрывает перефразированию: дифф передаётся
как отделённые разделителями данные и никогда не склеивается с инструкцией,
модель возвращает структурированный вывод, а не прозу, которую потом парсят,
вывод модели никогда не выбирает действие, а у модели ревью нет инструментов.
`validate_anchor` уже является одной из таких защит: замечание, выдуманное про
файл вне диффа, не может быть сохранено.

Сборка контекста (`app/application/context_assembly.py`) добавляет к этому три
структурные меры. Каждый текст из репозитория — hunk'и, сигнатуры, импорты,
проверки правил — лежит внутри блока `<<<untrusted kind=… id=…>>>`, граница
которого — 128 бит sha256 от самого текста: закрыть блок досрочно можно,
только подобрав текст с собственным тегом, — порядка 2^128 хэшей.
Раньше мера держалась на допущении, что модель сверяет `id` закрывающей строки с открывающей: системный промпт этого требует, но это инструкция, а не механизм.
Теперь у поддельной границы нет и формы: `sanitize` заменяет первый символ любой последовательности `<<<` в тексте из репозитория записью `<U+003C>`, поэтому строкой разметки блока может быть только строка, которую поставил сам сервис.
Тем же способом обезвреживаются служебные токены чат-шаблонов (`<|im_start|>`, `[INST]`, `<start_of_turn>`, `<s>` и другие, перечень в `app/domain/untrusted.py`): llama.cpp под Ollama разбирает их и внутри текста реплики, и `<|im_start|>system` в диффе стал бы настоящей сменой роли, от которой блок не защищает.
У меры есть цена: экранируется и законный код, например `<s>` и `</s>` в HTML или JSX модель видит как `<U+003C>s>`.
Системный промпт объясняет, что на месте записи в коде стоит сам символ, но ревью такого кода зависит от того, как модель это учтёт.
Управляющие, bidi- и zero-width-символы до этого заменяются видимой записью `<U+XXXX>` - Trojan Source становится видимым.

Запрос к модели собирает чистая функция (`app/domain/prompt.py`): инструкции сервиса, правила владельца и код идут разными сообщениями, а строка из репозитория попадает в запрос только внутри блока или литералом JSON.
Заголовок, описание PR и сообщения коммитов - тоже текст атакующего: в пакете они лежат блоками недоверенных данных (`pull_request_context`, своя доля бюджета `pr_context_max_tokens`) и попадают только в сообщение с кодом, никогда в системное.
Правила владельца (`.review/rules.md`) читаются только с `base_sha` целевой ветки: автор PR не может переписать критерии собственного ревью, а из файла в контекст попадают только распознанные поля правил, без прозы.
Пункты правил добавляют проверки и ничего не отменяют - это требование системного промпта, проверяемое только на живой модели.
Ссылку замечания на пункт правила проверяет код, а не модель: правило должно быть показано модели и применимо к файлу замечания, иначе замечание отклоняется целиком; префикс атрибуции строит сервис.
Префикс, который модель всё же написала в тексте сама, снимается до последнего повтора и узнаётся по скелету текста - без невидимых символов, после NFKC и замены латинских и греческих букв, похожих на кириллические; разметка Markdown вокруг его частей не мешает.
Замечание, начало которого и после этого читается как префикс, отклоняется: опубликованное, оно выглядело бы как замечание по правилу.
«Правило», подложенное в дифф, поэтому не может дать атрибуцию.

Второй проход модели (верификатор) отсеивает галлюцинации, но сам является мерой, а не гарантией: он видит тот же недоверенный контекст и тексты замечаний первого прохода, которые тоже лежат в блоках.
Его полномочия ограничены кодом: ответ - только вердикты по идентификаторам, сохраняются исходные объекты первого прохода, поэтому добавить или изменить замечание ему нечем.
Сам верификатор - тоже канал инъекции: его единственное полномочие - отбросить, и подавить находку - ровно цель атакующего.
Поэтому замечание `security` уровня `high` или `critical` он отбросить не может: вердикт `drop` по нему пишется в лог с причиной, а замечание публикуется.
Его сбой не роняет прогон (fail-open), а итог `unavailable` хранится в прогоне.
Адаптер модели может повторять запрос и дописывать сообщения об ошибке валидации, но исходных сообщений не меняет.
Фильтр по фразам не вводится - проигрывает перефразированию.

**Секреты в `context_payloads`.** Эта таблица хранит исходный код как есть.
Разработчик, закоммитивший API-ключ, получает его копию в нашей базе, и она
там остаётся. Секреты надо вычищать до вставки, и
`ContextPayloadRepo` это узкое место, где это можно обеспечить для всех, кто
пишет в таблицу. Срок хранения это вопрос защиты данных, а не только хранения.

**Подлинность webhook'ов.** GitHub подписывает доставки HMAC от тела запроса.
Без проверки подписи любой, кто узнал эндпоинт, может заставить сервис ревьюить
что угодно и тратить на это бюджет модели. Проверка реализована вместе с
эндпоинтом: `app/domain/hmac.py` сравнивает подпись за постоянное время
(`hmac.compare_digest`) по сырому телу запроса до разбора payload'а; без
подписи или с неверной вебхук получает 401, и ни одной записи не появляется.
Пустой секрет не принимает ничего: все доставки отклоняются.

**Сессия пользователя.** Значение cookie `session` равносильно паролю. В базе —
только SHA-256 от него, cookie `HttpOnly; Secure; SameSite=Lax`, выход удаляет
сессию сразу. Токен пользователя GitHub (user access token и refresh token) хранится
при сессии только зашифрованным — AES-256-GCM, ключ `USER_TOKEN_ENCRYPTION_KEY` вне
базы, associated data привязывает шифротекст к строке; в логи, ответы и `repr` он не
попадает (`Secret`), удаляется вместе с сессией. Утечка базы без ключа токенов не даёт;
утечка ключа и базы вместе даёт токены живых сессий с правами пользователя в пределах
разрешений приложения. Access-лог uvicorn
пишет путь с query, а там бывают `code` и `state` callback'а входа и поисковые query
кабинета, поэтому `app/api/log_redaction.py` вырезает query на любом пути; в серверном спане
запроса query путей входа скрывает `QueryRedaction` из `app/infrastructure/telemetry.py`. CSRF держат
`SameSite=Lax` и проверка `Origin`. Обоснование — `openspec/changes/archive/2026-10-17-auth-session/design.md`.

**Область действия учётных данных.** Для публикации комментариев нужен доступ
на запись. GitHub App с токенами на каждую установку ограничивает утечку одной
установкой. Personal access token открыл бы доступ ко всем репозиториям,
доступным его владельцу.

**Авторизация при регистрации.** При регистрации репозитория нужно проверять,
что у вызывающего есть к нему доступ, иначе можно подписать чужой репозиторий
и читать его анализ.

**Suggestions пишут в чужие ветки.** Замечание может содержать патч, применяемый в
один клик, то есть написанное моделью изменение, предлагаемое в чью-то ветку.
Оно остаётся предложением, которое принимает человек. Ничего не применяется
автоматически.

**Исчерпание ресурсов.** Change request может быть сколь угодно большим.
Сборщик контекста держит жёсткий лимит `context_max_tokens` (по умолчанию
32 000): оценка токенов (байты / 4, средняя, не верхняя граница)
сериализованного пакета его никогда не превышает. Не поместившееся
перечисляется в `omitted`. Это лимит пакета, а не окна модели: запрос целиком
вместе с резервом ответа (`llm_max_output_tokens`) сверяется с окном
(`llm_context_window_tokens`) той же оценкой до отправки, и не помещающийся
запрос не уходит ни одному провайдеру (`PromptTooLargeError`). Конфигурация, в
которой пакет на пределе лимита заведомо не помещается в окно, не даёт воркеру
стартовать. Дифф прогона ограничен `diff_max_bytes` (больший — прогон `failed`
с `DIFF_TOO_LARGE`, ревью нет; приём вебхука дифф не запрашивает вовсе),
довыборка файлов для AST — `ast_max_files` и `ast_max_file_bytes`, правила —
`rules_max_bytes`; лимит
размера соблюдается во время загрузки (адаптер читает тело потоком и обрывает
его), поэтому большой файл или сжатая «бомба» в память не попадают. Лимита на
длительность прогона пока нет.

**Self-hosted модель это свойство безопасности.** Ollama в нашей собственной
сети убирает главный путь утечки данных, поэтому по умолчанию запрос уходит
только локальной модели. Eurorouter - hosted-провайдер - подключается только
явным решением (`LLM_HOSTED_FALLBACK=true`, в `infra/` - `llm_hosted_fallback`)
и только фоллбэком после сбоя локальной модели: основным он стать не может,
это проверяет тест сборки контейнера. Включённый фоллбэк означает, что код
проверяемых репозиториев может уйти провайдеру, и не только при недоступности
Ollama: сбоем локальной модели считается любой `LlmError`, в том числе ответ
не по схеме, обрезанный ответ и запрос, который Ollama насчитала больше окна, -
то есть просто длинный PR. Какие провайдеры включены,
воркер пишет в лог при старте, а каждый переход на фоллбэк - в лог прогона.
Кто и почему включает фоллбэк на стенде - решение эксплуатации, которое
фиксируется в `infra/` вместе со значением переменной.

Ключи Eurorouter - `SecretStr` и не попадают ни в логи, ни в тексты ошибок, ни
в причину сбоя прогона: в лог пишется номер ключа, а описание ошибки
провайдера очищается от ключей.

Из этого списка изменение, вместе с которым появился этот документ, отвечает за
первые два пункта, потому что они определяют `ContextPayload.body` и указывают
на чувствительную таблицу. Остальные зафиксированы, чтобы тикеты, добавляющие
эндпоинты и пайплайн, начинались со списка, а не с того, что удастся вспомнить.

## Как должен выглядеть код

- **Чистое ядро, эффекты на краях.** Решения это функции над данными. Время,
  идентификаторы и случайность передаются аргументами и никогда не берутся из
  окружения.
- **Тонкие адаптеры.** Перевод между внешним форматом и доменным. Ветвление,
  выражающее бизнес-правило, находится не в том слое.
- **Нет порта без вызывающего кода.** Если результат задачи это сама точка
  расширения, опишите её здесь, а не коммитьте неиспользуемый код.
- **Один источник для того, что может разойтись.** Enum'ы, таблица переходов и
  mixin для timestamp'ов существуют в одном экземпляре. Шесть похожих методов
  репозиториев это совпадение, а не общий смысл, и базового класса для них нет.
- **Предпочитайте скучные решения.** Rate limiting с фиксированным окном, а не
  со скользящим. Словарь, а не библиотека кэширования. Если у простого варианта
  есть потолок, опишите потолок и путь дальше, а не стройте всё заранее.
- **Тестируемость это критерий приёмки.** Если правило можно протестировать,
  только подняв инфраструктуру, оно находится не в том слое.
