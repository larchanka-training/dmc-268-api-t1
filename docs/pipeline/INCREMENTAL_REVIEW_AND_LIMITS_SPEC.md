# Инкрементальное ревью и лимиты

> **Статус: предложение, не утверждено.** Требования — в OpenSpec-change
> [`incremental-review`](../../openspec/changes/incremental-review/) и
> [`review-limits`](../../openspec/changes/review-limits/) (применяется вторым). Всё, что не
> нужно одному VPS с одним воркером, вынесено.

## 1. Термины

| Термин | Что это |
|---|---|
| PR diff | `compare/{base}...{head}` — то, что показывает GitHub и к чему привязываются замечания |
| Hunk | Фрагмент PR diff; hunk нового файла длиннее предела делится на сегменты |
| Журнал | `reviewed_hunks`: `(путь, дайджест hunk'а, дайджест конфигурации) → вхождения, прогон, устарел ли` |
| Область ревью | Hunk'и PR diff после фильтрации, не покрытые действующими записями журнала |
| Покрытие | `complete` / `partial` / `none` области прогона и статус каждого файла |

Дайджест hunk'а — строки с маркерами ` `, `+`, `-` без `@@`-заголовка и номеров строк.
Дайджест конфигурации — версия промпта, правила владельца на `base_sha`, версия схемы пакета, модель.

Алгоритм прогона и решения — в `design.md` обоих change.

## 2. Сценарии

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Первое ревью PR | Область — весь PR diff после фильтрации |
| 2 | Push с правкой одной функции | Модель получает только изменившиеся hunk'и |
| 3 | Сдвиг строк | Сдвинутые hunk'и не в области |
| 4 | Push только lock-файла | Без модели, gate по открытым тредам |
| 4а | Часть hunk'ов ушла в `omitted` | Они не в журнале и входят в область следующего прогона |
| 5 | Смена ветки на том же head | Область из PR diff против новой базы |
| 6 | `eval` → исправили → вернули | Вернувшийся hunk проверяется, находка публикуется снова, запись журнала переактивируется |
| 7 | Копия блока в том же файле | Второе вхождение проверяется |
| 8 | Три push во время анализа | Публикует только последний, вытесненные `cancelled` |
| 9 | Запоздавшая доставка A после B | Прогона на A нет, B не вытеснен |
| 9а | Метаданные отстают от push B | `503`, повтор #149 создаёт прогон на B |
| 10 | Бюджет исчерпан | `partial`, `failure` со списком, остаток — следующим прогоном; новые hunk'и раньше перепроверяемых |
| 11 | 60 файлов при пределе 50 с правкой CI | CI проверен, `partial`, `failure` |
| 12 | Квота исчерпана → восстановилась | `none` и `failure`, остаток — следующим push или повтором доставки |
| 13 | `// @generated` в новом файле | Файл в области |

## 3. Не входит

| Что | Почему |
|---|---|
| Водяной знак, режимы `full/incremental/rebased` | Журнал решает область сам; знак давал дыру при смене ветки |
| Состояния замечаний (`possibly_fixed`, `outdated`, …), fingerprint, L1/L2 | Дубли сдерживает `thread_coverage`; L2 против закрытых тредов подавлял бы новые проблемы |
| Сериализация публикации (D9) | Один воркер с prefetch=1; сессионный `pg_advisory_lock` переживал ROLLBACK в пуле. Для второго воркера — `pg_advisory_xact_lock` |
| Лимиты частоты, backpressure, `defer`, авто-добор по квоте | Один воркер на стенде; отсрочка конфликтует с выметателем `queued` и merge gate |
| `installation_id` в базе и квота на инсталляцию | `review-rest-api` запрещает хранить; квота — по репозиторию |
| Бюджет повторов | Уже ограничен повтором доставок #149 и `x-delivery-limit` #230 |
| `GET …/coverage` | Покрытие отдаёт `ReviewJob` |
| Многочанковое ревью | Отдельный change: меняет пакет контекста и верификатор |

## 4. Открытые вопросы

- Предел сегмента нового файла и правило границы — LLM-команда.

- Числа лимитов — после нагрузочного прогона (`load.yml`).
