# Стек сервера (API на Python 3.14, PostgreSQL 18, RabbitMQ 4.4)

Нужны **Docker Engine** на целевом хосте и OpenTofu >= 1.13 (в CI ставится 1.13.2). Образ API не собирается здесь: он публикуется в ghcr из CI и запускается по digest (`api_image` — `<репозиторий>:<commit sha>@sha256:<digest>`; ссылка без digest не проходит проверку переменной).

## Раскладка файлов

Конфигурация разложена по доменам; OpenTofu читает все `*.tf` каталога как один модуль, так что адреса ресурсов от файла не зависят.

| Файл | Что внутри |
| --- | --- |
| `versions.tf` | версия OpenTofu, провайдер `kreuzwerker/docker` и его настройки (хост Docker) |
| `backend.tf` | хранилище состояния (S3 на сервере) |
| `locals.tf` | общие значения: ротация логов, окружение процессов приложения, грейс-период воркера |
| `network.tf` | три сети: вход `dmc268` (общая со стеком `dmc-268-ui-t1`), данные `dmc268-backend`, исходящая `dmc268-egress` |
| `postgres.tf` | образ, том и контейнер PostgreSQL |
| `rabbitmq.tf` | образ, том и контейнер RabbitMQ |
| `app.tf` | контейнеры `api`, `worker` из образа API по digest |
| `observability.tf` | стек наблюдаемости: образы, тома, сети и восемь контейнеров |
| `replica.tf` | роль репликации, горячая реплика и резервные копии PostgreSQL |
| `postgres/` | то, что загружается в контейнеры PostgreSQL: `pg_hba.conf`, SQL роли, entrypoint реплики, скрипт копий |
| `variables.tf` | входные переменные, по секциям тех же доменов |
| `outputs.tf` | выходы: `migrate_env` — окружение миграций для шага деплоя |
| `tests/*.tftest.hcl` | `tofu test` с mock-провайдером |

## Почему OpenTofu, а не Terraform

Terraform с версии 1.6 распространяется под Business Source License (BUSL) — она не open source, и условия дополнительного разрешения HashiCorp на использование размыты. OpenTofu — форк последней открытой версии под Mozilla Public License 2.0, проект Linux Foundation. Провайдеры у него те же, что у Terraform (своих OpenTofu не пишет), а берутся из собственного реестра `registry.opentofu.org`: `kreuzwerker/docker` работает без изменений. Сверх Terraform OpenTofu умеет шифровать состояние и план на диске и в бэкенде (с 1.7); у нас шифрование пока не включено — состояние лежит в хранилище на петле сервера, доступном только через SSH-туннель.

## Локальный или удалённый Docker

Скопируйте `terraform.tfvars.example` в `terraform.tfvars` и замените плейсхолдеры `CHANGE_ME_*`. Файл `terraform.tfvars` не коммитится (gitignore).

- Локальный демон: `docker_host = "unix:///var/run/docker.sock"` (у Docker Desktop на macOS часто `unix:///Users/<вы>/.docker/run/docker.sock`).
- Удалённый сервер: `docker_host = "ssh://user@server"` (нужны SSH-доступ и Docker на удалённом хосте).

Образ API перед `apply` скачивают на тот же Docker сами: `docker pull <api_image>` (с `DOCKER_HOST`, если демон удалённый; для приватного пакета — после `docker login ghcr.io`). Провайдер создаёт `api` и `worker` из уже скачанного образа, а если его нет — тянет сам, но без учётных данных, и на приватном пакете `apply` падает с `denied`.

API публикуется на `bind_ip`, в деплое это `127.0.0.1`. Другого значения конфигурация не примет: переменная проверяется на адрес петли (`127.0.0.0/8` или `::1`), и ошибка всплывает на `plan`. PostgreSQL, реплика и RabbitMQ портов на хосте не публикуют вовсе — см. «Сети».

## Сети

Контейнеры разнесены по трём docker-сетям, каждый видит только тех, с кем говорит:

| Сеть | Кто в ней | Зачем |
| --- | --- | --- |
| `dmc268` | интерфейс (из `dmc-268-ui-t1`), `api` | публичный вход: nginx интерфейса проксирует `/api/` в API. Имя прежнее — интерфейс подключается к ней по имени |
| `dmc268-backend` (`internal`) | `postgres`, `postgres-replica`, `postgres-backup`, `rabbitmq`, `replication-setup`, `api`, `worker`, миграции шага деплоя | данные. У сети нет шлюза: из неё не выйти в интернет, а интерфейса в ней нет |
| `dmc268-egress` | `worker` | исходящие запросы воркера к GitHub API и провайдеру модели |

API — единственный, кто стоит и во входе, и в данных. С `internal`-сети Docker не публикует порты, поэтому у базы и брокера портов на хосте нет: для отладки — `docker exec -it dmc268-postgres psql -U dmc268 -d dmc268` и `docker exec dmc268-rabbitmq rabbitmq-diagnostics status`. Изоляцию проверяют `tests/test_infra_isolation.py` (по тексту `infra/*.tf`) и `infra/tests/main.tftest.hcl` (по плану).

## Реплика и резервные копии

**Горячая реплика** `dmc268-postgres-replica` — физическая потоковая репликация с основного сервера по слоту `dmc268_replica`, только чтение. Приложение в неё не ходит; с неё снимаются резервные копии.

- **Роль `replicator`** заводит одноразовый контейнер `dmc268-replication-setup` (`postgres/replication-setup.sql`), идемпотентно: init-скрипты образа на уже заведённом томе не выполняются. Контейнер запускается заново, когда сменились пароль или SQL либо пересоздана основная база (её контейнер или том), — не на каждом деплое.
- **Пароль роли** — секрет `PG_REPLICATION_PASSWORD_DMC268_T1`. В каталоге данных реплики его нет: реплика пишет `passfile` на каждом старте и передаёт `primary_conninfo` аргументом. Поэтому смена секрета — обычный деплой: роль получает новый пароль, реплика пересоздаётся с новым `passfile`, том не пересобирается.
- **Слот** заводит сама реплика (`pg_basebackup --create-slot`) при каждой пересборке, удаляя неактивный старый.
- **Пересборка** (`postgres/replica-entrypoint.sh`) происходит сама при старте контейнера, если том пуст или копия не дописана либо слота нет или он потерян: основной сервер тогда тот же кластер, и пересборка ничего не теряет. Копия снимается во временный каталог и переименовывается целиком; на это время на диске нужно место под две копии базы (старый каталог и новый). При постоянной ошибке `pg_basebackup` пауза между попытками растёт до минуты.
- **Другой кластер основного сервера** (его том заведён заново, например потерян) реплика **не стирает**: в ней может быть последняя копия данных, а новый основной сервер — пустым. Контейнер завершается с ошибкой «основной сервер — другой кластер», деплой падает на проверке потока. Дальше решает человек: если данные реплики нужны — поднять из них основной сервер (или снять `pg_dump` с остановленной реплики); если нет — пересобрать реплику, удалив её том: `docker rm -f dmc268-postgres-replica && docker volume rm dmc268-postgres-replica-data`, затем деплой. Решение принимается только по ответу основного сервера: пока он недоступен, реплика ничего не трогает.
- **Потолок WAL.** Слот держит WAL для отставшей реплики, но не больше `postgres_max_slot_wal_keep_size` (2 ГБ): иначе упавшая реплика заполнила бы диск основного сервера. Реплика, перешагнувшая потолок, теряет поток и становится `unhealthy`. Docker unhealthy-контейнеры не перезапускает, поэтому это делает деплой: перед проверкой потока он перезапускает unhealthy-реплику, и она пересобирается. Между деплоями — вручную: `docker restart dmc268-postgres-replica`.
- **Здоровье реплики** — это поток: healthcheck смотрит `pg_stat_wal_receiver.status = streaming`. Отставшая реплика отвечает на запросы, но `unhealthy`.
- **Деплой** (`.github/scripts/deploy/check-replica.sh`) проверяет со стороны основного сервера, что слот держит именно реплика (`application_name = dmc268_replica`, а у `pg_basebackup` первой сборки — `dmc268_basebackup`) и поток в состоянии `streaming`; unhealthy-реплику перед этим перезапускает.
- **Доступ к базе** (`postgres/pg_hba.conf`, вне каталога данных) — только из подсети самого сервера (`samenet`), то есть из `dmc268-backend`.

Реплика на том же сервере: она спасает от сбоя процесса или тома основной базы, но не от падения самого сервера.

**Резервные копии** снимает `dmc268-postgres-backup`: `pg_dump -Fc` при старте и затем раз в сутки, в том `dmc268-postgres-backups`, хранение — `backup_keep_days` (7 суток). Источник — реплика, если она получает поток, иначе основной сервер: копия с отставшей реплики выглядела бы свежей, а содержала бы данные на момент обрыва. Контейнер становится `unhealthy`, если свежей копии нет дольше 26 часов. Источник копии видно только в логе бэкапа, а не в его healthcheck: **unhealthy-реплика означает, что копии идут с основного сервера**. Пока база маленькая, это незаметно; на большой базе ежедневный `pg_dump` с основного сервера держит блокировки и может задержать миграции с `ALTER TABLE` — реплику стоит поднять, не откладывая. Копии лежат на том же диске — от потери сервера не спасают; вынос копий за пределы сервера — отдельная задача.

**Ollama**, если её развернут на сервере, подключается к `dmc268-backend`: воркер ходит к ней оттуда. К `dmc268-egress` — только если Ollama сама скачивает модели.

Восстановление в основную базу (API и воркер на это время остановить):

```bash
docker run --rm --network dmc268-backend -v dmc268-postgres-backups:/backups:ro \
  -e PGPASSWORD=<пароль> pgvector/pgvector:pg18 \
  pg_restore -h dmc268-postgres -U dmc268 -d dmc268 --clean --if-exists /backups/<файл>.dump
```

## Ограничения контейнеров

- `api`, `worker` и миграции работают не от root (`USER` в `Dockerfile`), с файловой системой только для чтения (запись — только в `/tmp`), без capabilities и с `no-new-privileges`. У миграций это флаги `docker run` в `.github/scripts/deploy/migrate.sh`.
- `postgres` и `rabbitmq` — только `no-new-privileges`: их entrypoint стартует от root, чтобы подготовить каталог данных, и сам переходит на служебного пользователя.
- У каждого контейнера потолок памяти без свопа (`postgres` 1 ГБ, `postgres-replica`, `rabbitmq`, `api` и `worker` по 512 МБ, `postgres-backup` и миграции по 256 МБ, `replication-setup` 64 МБ) и ротация логов: три файла по 10 МБ. Постоянно работающие контейнеры — около 3,3 ГБ, на время деплоя добавляются миграции и `replication-setup`; без учёта интерфейса и хранилища состояния.
- `replication-setup` и `postgres-backup` — как миграции и `api`: файловая система только для чтения, без capabilities. `postgres-replica` — как `postgres`: только `no-new-privileges`.
- `postgres`, `postgres-replica` и `rabbitmq` при пересоздании и `docker stop` останавливаются штатно: `stop_timeout` и `destroy_grace_seconds` по 60 с. Без `destroy_grace_seconds` провайдер удаляет контейнер через SIGKILL, и база поднимается с восстановлением после аварии.

Смена любого из этих атрибутов пересоздаёт контейнер. Данные PostgreSQL и RabbitMQ лежат в томах и замену переживают.

## Версия провайдера

Точная версия `kreuzwerker/docker` и её хэши закреплены в `.terraform.lock.hcl`, файл коммитится. После смены `version` в `versions.tf` его пересобирают на все платформы команды, иначе `tofu init` на неперечисленной системе допишет в файл свои хэши и оставит изменение в рабочей копии:

```bash
cd infra && tofu init -backend=false -upgrade && tofu providers lock \
  -platform=linux_amd64 -platform=linux_arm64 \
  -platform=darwin_amd64 -platform=darwin_arm64 \
  -platform=windows_amd64
```

## Деплой

Стенд катится сам при мерже в `develop` (`.github/workflows/deploy.yml`). `main` в деплое не участвует: сервер один, и два источника дрались бы за него.

Порядок такой: образ собирается и публикуется в `ghcr.io/larchanka-training/dmc-268-api-t1` с тегом по commit sha → поднимается хранилище состояния и туннель к нему → `tofu apply -target` для сети, базы и брокера → план полного выката в файл и сторож томов (`plan.sh`) → миграции (`.github/scripts/deploy/migrate.sh`) → `tofu apply` этого плана (`apply.sh`) → проверка `/health` через туннель и проверка воркера → уборка образов → summary (`summary.sh`). Публичной проверки здесь нет: API снаружи не публикуется, а его доступность по `https://62.169.24.237/api/v1/` проверяет деплой интерфейса.

**Снаружи API адресуется через интерфейс, с исходным путём.** Публичный вход — `nginx` в контейнере фронтенда на **https://62.169.24.237** (сертификат Let's Encrypt на IP, HTTP перенаправляется на HTTPS; устройство — в `infra/README.md` репозитория `dmc-268-ui-t1`). Префикс он не трогает: браузерный `GET /api/v1/reviews` приходит сюда как `GET /api/v1/reviews`, поэтому роутеры монтируются на `/api/v1`, как требует контракт API. `/health` через этот вход не публикуется — проверка живости ходит мимо него.

**Тома данных деплой не уничтожает.** У `docker_volume.postgres`, `docker_volume.rabbitmq`, `docker_volume.postgres_replica` и `docker_volume.postgres_backups` — `lifecycle { prevent_destroy = true }`: план, который уничтожает или заменяет том, OpenTofu отклоняет до изменений на сервере с `Error: Resource instance cannot be destroyed`. Это действует и на targeted apply шага «Поднять базу и брокер» — `-target=docker_container.postgres` тянет том зависимостью, и сторож полного плана такую замену уже не увидел бы. Полный выкат идёт планом в файл: `plan.sh` строит `tofu plan -out=tfplan` сразу после targeted apply, и `scripts/deploy_report.py` по `tofu show -json` дублирует проверку для summary — падает, если план уничтожает или заменяет защищённый том, и apply не запускается. Миграции идут между планом и apply: состояние они не трогают, план не устаревает. Применяется ровно проверенный план (`apply.sh`); если до него не дошло, файл плана удаляет `summary.sh`. Сменить том, как при смене сборки PostgreSQL или версии RabbitMQ, — новым ресурсом с новым адресом (с `prevent_destroy`, и его адрес — в `PROTECTED` сторожа; то и другое сверяет тест), а прежний снять с учёта блоком `removed { lifecycle { destroy = false } }`: план выйдет `forget` и `create`, старый том с данными останется на сервере до ручного `docker volume rm`. В плане и его JSON пароли лежат открытым текстом: JSON идёт только трубой, файл плана удаляется после apply и артефактом не загружается, обёртка `setup-opentofu`, копирующая stdout tofu в выходы шага, выключена.

**Summary деплоя** пишет `summary.sh` на любом исходе: шаг падения, простой API с разбивкой (SIGTERM старому → выход → `Created` нового → `State.StartedAt` → событие `health_status: healthy` нового; всё, кроме `Created` и `StartedAt`, — из событий Docker, которые `apply.sh` читает потоком всё время apply. `State.Health.Log` — запасной путь, если событий нового контейнера нет: журнал держит пять последних проверок, и после долгого apply первой успешной в нём уже нет — summary тогда помечает простой как недостоверный), план по типам ресурсов, применённые миграции, свободное место на `/` и в каталоге Docker после уборки и длительность шагов — по засечкам `mark.sh`, без `actions: read` у токена. Подписи значений — ключи OpenTelemetry (`cicd.pipeline.*`, `container.image.*`, `system.filesystem.*`), свои — в `dmc268.deploy.*`.

**Миграции — шаг деплоя до полного `apply`, а не контейнер стека.** Шаг `Применить миграции` запускает `.github/scripts/deploy/migrate.sh`: одноразовый `docker run --rm` того же образа (тот же digest), что сейчас выкатится, с `alembic upgrade head` и шагом роли мониторинга (ALTER ROLE при выключенном `track_utility`, пароль — из окружения; тот же шаг — у сервиса `migrate` в compose) — на сервере через `DOCKER_HOST=ssh://stand`, в сети данных `dmc268-backend`. Окружение — выход `migrate_env` (`outputs.tf`): те же строки `local.app_env`, что у `api` и `worker`, плюс телеметрия (`local.telemetry_env`) и `POSTGRES_MONITOR_PASSWORD`, через env-файл с правами 600, который удаляется после запуска. Упала миграция — шаг падает, полный `apply` не запускается, на стенде остаётся прежняя версия. Проверка `/health` этого не заметила бы: по контракту она отвечает независимо от базы.

Пока идут миграции, работает старый код: ломающая миграция (удаление или переименование колонки, которую он читает) даст на стенде короткий сбой во время выката. Пока нет пользователей, это допустимо; для прода — expand/contract в два деплоя (скилл `.agents/skills/alembic-migration`).

Образ лежит в приватном пакете: перед миграциями job входит в `ghcr.io` на раннере (`docker/login-action`, `GITHUB_TOKEN` с `packages: read`), и docker CLI передаёт учётные данные демону сервера вместе с запросом pull. На сервере токен не остаётся. Этот pull в `migrate.sh` — единственный для образа API: учётных данных реестра у провайдера нет, и `api` с `worker` он создаёт из уже скачанного образа.

**Чистый сервер.** База и брокер должны существовать до миграций, поэтому перед ними каждый деплой выполняет

```bash
tofu apply -target=docker_network.dmc268 -target=docker_container.postgres -target=docker_container.rabbitmq
```

На живом стенде это `No changes` и ожидаемое предупреждение OpenTofu о `-target`; на чистом — создание сети, томов, базы и брокера. У `postgres` `wait = true`: apply возвращается, когда healthcheck зелёный, и миграциям не нужен цикл повторов. Этот же apply обновляет в состоянии выход `migrate_env`: выход зависит от контейнеров базы и брокера (хосты в `local.app_env` — ссылки на них), а выход, не зависящий от целевых ресурсов, targeted apply не записывает. Руками ничего делать не нужно: первый деплой на пустой сервер проходит тем же путём (проверено на чистом локальном Docker 29.9.2).

**Контейнер `dmc268-migrate`** жил в стеке до #159. Блок `removed` в `app.tf` снимает его с учёта без уничтожения, а `migrate.sh` удаляет остановленный контейнер на сервере: его старые логи и код выхода легко принять за текущие, и он держит прежний образ.

**Образ API — без ресурса `docker_image`.** `api` и `worker` ссылаются на образ строкой `<репозиторий>@sha256:<digest>` — `local.api_image_ref` в `app.tf`, тег из `api_image` срезан. Ресурс образа пересоздавался на каждом коммите (тег — commit sha) уже после остановки старого API, и его pull добавлял к простою 6 с (деплой #202). Тег в ссылке контейнера дал бы то же: провайдер сравнивает `image` строкой и пересоздаёт контейнер, даже если digest не изменился. Теперь контейнеры меняются, только когда меняется digest; `docker ps` показывает репозиторий без тега, commit sha — в summary деплоя. Замена API не ждёт воркера и без отдельного ресурса образа: общего ресурса, который ждал бы уничтожения обоих контейнеров, больше нет.

Ресурсы `docker_image.api` и `docker_image.worker` снимаются с учёта блоками `removed` без уничтожения. Первый деплой после перехода пересоздаёт `api` и `worker` один раз, даже при том же digest: в состоянии у них `image` — ID образа, в конфигурации — ссылка. Проверено на Docker 29.9.2: переход — один простой API, следующий `plan` — `No changes`, новый тег при том же digest — `No changes`, контейнеры те же.

**Готовность API ждёт сам `apply`.** У `docker_container.api` `wait = true` и `wait_timeout = 90`: создав контейнер, провайдер опрашивает его состояние и считает выкат завершённым, когда healthcheck (`/health` изнутри контейнера) стал `healthy`; не стал за 90 с — `apply` падает, контейнер помечается tainted и пересоздаётся следующим деплоем, а шаг `Логи API после упавшего apply` печатает хвост лога и историю проверок. `start_interval = "1s"` даёт `healthy` в первую секунду после старта приложения, а не через `interval` 30 с. Длительности healthcheck пишутся в формате Go (`"2s"`, `"30s"`, `"1m0s"`): в нём провайдер читает их обратно, и `"1m"` дал бы вечный diff. Правку healthcheck провайдер планирует обновлением на месте, но к запущенному контейнеру она не применяется, поэтому API пересоздаётся от `terraform_data.api_healthcheck` (`replace_triggered_by`). Проверка `/health` через туннель после `apply` остаётся: она проверяет путь снаружи — публикацию порта и туннель.

**Одно SSH-соединение на job.** Хост `stand` в `~/.ssh/config` (`.github/actions/stand-ssh`) — с `ControlMaster auto`, `ControlPath ~/.ssh/cm-%C` и `ControlPersist 10m`: первый `ssh stand` поднимает фоновое соединение, и через него идут все шаги и каждый запрос docker-провайдера и docker CLI к `ssh://stand`, без нового рукопожатия на запрос. Замер с RTT 80 мс: 10 вызовов `docker -H ssh://stand version` — 12,5 с без мультиплексирования, 3,9 с с ним. `ServerAliveInterval 10` и `ServerAliveCountMax 3`: если TCP мастера пропал без разрыва, master закрывается за 30 с — `ConnectTimeout` через живой master не действует, клиент идёт в сокет. ssh в шагах `always()` (`finish` в `apply.sh`, `summary.sh`) к тому же под `timeout 30`, у шага summary `timeout-minutes: 3`. Сессии сверх `MaxSessions` сервера (по умолчанию 10) ssh открывает своим соединением, вызов не падает. Туннели (`s3-backend`, `check-api.sh`) идут мимо master, с `-o ControlPath=none`: через master проброс открывает сам master, `ExitOnForwardFailure` не срабатывает на занятом порте, а туннель закрывается вместе с master через `ControlPersist` простоя — посреди деплоя это был бы туннель к хранилищу состояния.

**Воркер** `dmc268-worker` разворачивается из того же образа, что и API, с командой `python -m app.worker`. Портов у него нет: с остальным стеком он говорит только через очередь и базу, наружу — исходящими запросами к GitHub API (дифф, `.review/rules.md`, файлы для AST), поэтому получает те же `GITHUB_APP_ID` и `GITHUB_APP_PRIVATE_KEY`, что и API. Стартует, как и API, после миграций. HTTP-проверки у него нет, поэтому деплой считает воркер живым, если контейнер 30 секунд подряд запущен и ни разу не перезапустился.

Адаптер модели воркера задаёт `llm_backend` (`LLM_BACKEND`): `stub` - без похода к модели, `ollama` - локальная модель. Значения по умолчанию нет: заглушка выбирается только явно, и деплой стенда передаёт `TF_VAR_llm_backend: stub` в `.github/workflows/deploy.yml`.
`ollama` требует `ollama_model` и развёрнутой Ollama по `ollama_base_url`.
Eurorouter подключается только фоллбэком после локальной модели и только при `llm_hosted_fallback = true` с `eurorouter_base_url`, `eurorouter_model` и `eurorouter_api_keys`: это решение отправляет код проверяемых репозиториев hosted-провайдеру.

## Стек наблюдаемости

Рядом с API на стенде стоит стек телеметрии из восьми контейнеров: OTel Collector
(`dmc268-otelcol`), Loki (логи), Tempo (трейсы), Prometheus (метрики), Grafana (интерфейс,
`grafana_port` на `bind_ip`), `node-exporter` (сервер: CPU, память, диски), `cAdvisor`
(контейнеры) и socket-proxy (`dmc268-docker-proxy`: Docker API для cAdvisor по белому списку
эндпоинтов вместо маунта `docker.sock`; отдельная сеть, где кроме proxy и cAdvisor никого).
Белый список — свой шаблон haproxy (`observability/docker-socket-proxy.cfg`), а не
env-переменные образа: `CONTAINERS=1` открывал любой GET под `/containers`, вплоть до чтения
файлов контейнеров через `/archive` (замечание ревью PR #130); в compose шаблон монтируется
по пути, который рендерит entrypoint образа, на стенде заливается тем же `upload`, что и
остальные конфиги.
Метрики базы снимает сам коллектор — receiver `postgresql` (решение #89), отдельного экспортёра
Postgres нет. Конфиги лежат в `observability/` и **те же самые** используются локальным
docker compose (профиль `observability`): различия окружений — только переменные и лимиты, не
конфиги. Образы стека зафиксированы дайджестами (`имя@sha256:…`, дайджест манифест-листа) в
`locals.tf` и в `docker-compose.yml` — одинаково; тег в комментарии рядом, обновление образа —
осознанная замена дайджеста в обоих файлах, с чтением breaking changes.

Конфиги заливаются в контейнеры при создании (`upload` в `docker_container`): tofu читает их из
рабочей копии и передаёт через Docker API, поэтому на сервере не нужен чекаут репозитория. Правка
конфига пересоздаёт контейнер следующим `apply`; если провайдер не заметил изменение содержимого,
контейнер пересоздают явно (`tofu apply -replace=docker_container.otelcol`). Из-за `upload`
коллектор стенда живёт без `read_only` (заливка — запись в rootfs, read-only демон отклоняет
её до всякого пути): вместо неё — `cap_drop ALL` и `no-new-privileges`. Локальный коллектор
read_only: конфиг приходит read-only маунтом. Локально тот же
стек поднимается профилем: `OTEL_TRACES_EXPORTER=otlp OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp docker compose --profile observability up -d` (Grafana —
http://127.0.0.1:3000 без логина).

Экспорт телеметрии API, воркера и миграций включён окружением (`local.telemetry_env`): трейсы,
метрики и логи уходят коллектору по OTLP. `service.version` берётся из тега `api_image` (это sha
коммита сборки), окружение задаёт `deployment_environment_name` — `production`, потому что стенд
и есть прод (#97), то же значение шлёт кабинет (#108); `service.instance.id` у каждого сервиса
своё и стабильное (`dmc268-api`, `dmc268-worker`, у миграций — `dmc268-migrations` из выхода
`migrate_env`, локально в compose — `dmc268-migrate`) — вместо случайного UUID на
процесс, который растил бы в Prometheus серии `exported_instance`. Таймаут OTLP — 4 секунды
(`OTEL_EXPORTER_OTLP_TIMEOUT`): Python SDK читает переменную в секундах, вопреки спецификации
OTel с её миллисекундами. Логи коллектор получает только по OTLP от сервисов — каталог Docker
не читает, логов postgres и rabbitmq в Loki нет; чувствительные данные он редактирует до
отправки — правила в `observability/otelcol.yaml`, тест `tests/infrastructure/test_collector_redaction.py`.

### Включение и выключение: observability_enabled

Стек поднимается только по флагу `observability_enabled`, по умолчанию `false`: локальному
`apply` без него хватает памяти, а секреты стека не нужны. Включают переменной окружения
`TF_VAR_observability_enabled=true` — так делает деплой стенда (`deploy.yml`) — или строкой
`observability_enabled = true` в `terraform.tfvars` (пример закомментирован в
`terraform.tfvars.example`); эффект одинаковый.

За флагом идёт всё разом: восемь контейнеров стека и их образы, четыре тома (Loki, Tempo,
Prometheus, Grafana), отдельная сеть socket-proxy (`count = 1 : 0` у каждого ресурса),
`telemetry_env` — `OTEL_*_EXPORTER=otlp`, адрес коллектора и таймаут в env api, воркера и
миграций — и `command` контейнера Postgres: при флаге база стартует с
`shared_preload_libraries=pg_stat_statements`, без флага — с родным `CMD` образа. Смена
`command` пересоздаёт контейнер Postgres (том данные сохраняет), поэтому переключение флага —
осознанное действие. Выключение снимает стек целиком: приложение работает без телеметрии, а
пустой `telemetry_env` SDK молчит — ни отправки, ни ошибок экспорта в логе. Нюанс: шаг
миграций перегенерирует пароль роли `dmc268_monitor` при каждом деплое независимо от флага,
поэтому выключение стека на существующем стенде без секретов вернёт роли локальный
дефолтный пароль — держите секрет выставленным, пока роль существует.

При `observability_enabled = true` валидации переменных требуют секретов: непустой
`grafana_admin_password` (анонимный вход в Grafana на стенде выключен — без учётки в неё не
зайти) и настоящий `postgres_monitor_password`, не локальный дефолт `dmc268_monitor` (роль
становится входом в базу, открытым в docker-сети). Без секретов `apply` падает на проверке
переменной.

Переменные стека: `observability_enabled` (весь стек — за флагом, см. выше), `observability_memory_mb`
(потолки памяти без свопа, восемь контейнеров — таблица ниже), `grafana_port`, `grafana_admin_password`
(секрет; локально Grafana без логина, на стенде — по учётке), `postgres_monitor_password` (секрет, см.
таблицу выше), `deployment_environment_name`.
Метрики базы коллектор снимает receiver-ом `postgresql`: роль только-чтение `dmc268_monitor` с
`pg_monitor` создаёт миграция 0013, и она же создаёт расширение `pg_stat_statements` — коллектор его
не читает (медленные запросы им не собираются), расширение оставлено только для ручной диагностики;
`shared_preload_libraries` включает контейнер Postgres. RabbitMQ отдаёт метрики встроенным
плагином `rabbitmq_prometheus` (порт 15692 в сети, per-object эндпоинт — метрики очередей с
лейблом `queue`); сервер — `node-exporter` (9100), контейнеры — `cAdvisor` (8080); все скреятся
`prometheus.yml`. Дашборд «Обзор dmc-268» провиженится из репозитория
(`observability/grafana/provisioning/dashboards/`). Применение стека на стенд — задача DevOps (#108).

### Память стека

Потолки памяти без свопа (`memory` = `memory_swap`) задаются переменной `observability_memory_mb`,
дефолт — прод-размеры с запасом против замеров ниже:

| Компонент | Потолок, МБ |
| --- | --- |
| коллектор `dmc268-otelcol` | 384 |
| Loki | 768 |
| Tempo | 768 |
| Prometheus | 768 |
| Grafana | 512 |
| node-exporter | 64 |
| cAdvisor | 256 |
| socket-proxy | 64 |
| **Итого стек** | **3584 (~3,5 ГБ)** |

Рядом — лимиты контейнеров приложения (`app.tf`, `postgres.tf`, `rabbitmq.tf`): `postgres` 1024,
`api`, `worker` и `rabbitmq` по 512 — итого 2560 МБ (~2,5 ГБ) постоянно живущих. Миграции —
шаг деплоя (`docker run` в `migrate.sh` с `--memory 256m`), в постоянный лимит стенда не входят.
Суммарный потолок стенда — ~6 ГБ по постоянно живущим контейнерам.

Память стека без нагрузки — по замерам ревью PR #130 (Grafana ~350 МБ, Tempo ~200 МБ, Loki
~90 МБ, коллектор ~85 МБ) и локальному прогону Docker Desktop (2026-10-24: node-exporter
~13 МБ, cAdvisor ~45 МБ, коллектор ~65 МБ, Prometheus сразу после старта ~170 МБ и растёт
по мере накопления). Фактическое потребление — ориентир при пересмотре
`observability_memory_mb`, а не гарантия (под нагрузкой Loki и Tempo растут).

### Диск

Диск на стенде один на всё: тома данных стека и PostgreSQL растут на одной файловой системе,
и его объём в README пока не зафиксирован — снять факт можно `df -h /` на сервере.
У `docker_volume` размера нет — потолок задаёт только само приложение, если умеет:

| Что | Потолок | Откуда |
| --- | --- | --- |
| метрики Prometheus | ≤ 8 ГБ и не дольше 30 дней | `--storage.tsdb.retention.size=8GB` и `--storage.tsdb.retention.time=30d` (`observability.tf`, compose) |
| логи Loki | только 30 дней (`retention_period: 720h`), лимита по размеру нет | `observability/loki.yaml` |
| трейсы Tempo | только 14 дней (`block_retention: 336h`), лимита по размеру нет | `observability/tempo.yaml` |
| логи контейнеров (json-file) | 30 МБ на контейнер (3 файла × 10 МБ) | `local.log_opts` в `locals.tf`, `logging.options` в compose |

Единственный компонент с потолком по размеру — Prometheus (8 ГБ): всплеск кардинальности не
забьёт диск раньше срока хранения. У Loki и Tempo такого лимита нет: записи старше срока
хранения удаляются, но суммарный объём под сроком ничем не ограничен. Теоретический потолок
Loki — скорость приёма 1 МБ/с (`ingestion_rate_mb: 1`) ≈ 86 ГБ в сутки: поток сверх лимита
Loki отбрасывает с 429 и долг не копит, но всё принятое до отбрасывания пишет на диск.
Алертов #100 пока нет (задача открыта), поэтому до #100 защиты от переполнения диска нет
никакой — ни лимита, ни алерта; после #100 заполнение ловят алерты по
`node_filesystem_avail_bytes` от node-exporter.

Ожидаемые объёмы: под ротацию json-file попадает 13 контейнеров этого стека (5 приложения +
8 наблюдаемости) — не больше 390 МБ. В Loki пишут только три сервиса приложения — api, worker
и одноразовый migrate (логи postgres и rabbitmq туда не попадают: приём только OTLP). При
допущении «запись в секунду на сервис по 1 КБ» — 3 КБ/с ≈ 260 МБ в сутки ≈ 7,8 ГБ за 30 дней
на все три; индекс TSDB Loki (период 24 ч) и рабочие файлы compactor в оценку не входят.

## Хранилище состояния

Состояние OpenTofu лежит не рядом с конфигурацией, а в S3-совместимом хранилище (RustFS) на том же сервере (`backend.tf`). Так оно переживает прогон раннера GitHub Actions, который исчезает вместе со своим диском.

Хранилище слушает только `127.0.0.1`, поэтому `tofu` любой командой, которой нужно состояние, работает через SSH-туннель:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
```

Учётные данные хранилища передаются как `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`; в CI они приходят из секретов `S3_USER_DMC268_T1` и `S3_PASSWORD_DMC268_T1`. Состояния API и UI лежат в одном бакете `dmc268-tfstate` под разными ключами.

Состояние блокируется на время каждой команды, которая его меняет (`use_lockfile`): OpenTofu кладёт рядом lock-объект условной записью, и второй запуск получает `Error acquiring the state lock` с ID блокировки. Если запуск упал, не сняв блокировку, её снимают вручную — только убедившись, что никто больше не работает с состоянием:

```bash
cd infra && tofu force-unlock <ID из ошибки>
```

Сам контейнер хранилища **не входит в этот стек**: его поднимает composite action `.github/actions/s3-backend` шагом job'а деплоя перед `tofu apply`, а не OpenTofu, иначе `apply` мог бы снести хранилище собственного состояния. Практическое следствие: `tofu destroy` его не удалит, и полная зачистка сервера состоит из двух шагов — `tofu destroy` со снятой защитой томов (раздел «Развёртывание и удаление»), а затем `docker rm -f dmc268-s3` и `docker volume rm dmc268-s3-data` вручную.

## Развёртывание и удаление

Штатный путь один: **мерж в `develop`**. Дальше всё делает `deploy.yml` — собирает образ, поднимает хранилище состояния, базу и брокер, применяет миграции и конфигурацию, проверяет `/health` и что воркер работает. Руками ничего запускать не нужно и, как правило, не получится.

Локальный запуск перестал быть самодостаточным с появлением `backend.tf`: состояние лежит в хранилище на сервере, поэтому любая команда, которой нужно состояние, требует открытого туннеля и учётных данных хранилища:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
export AWS_ACCESS_KEY_ID=<логин хранилища> AWS_SECRET_ACCESS_KEY=<пароль> AWS_DEFAULT_REGION=us-east-1
cd infra && tofu init && tofu plan
```

Ключ и учётные данные лежат в секретах GitHub и наружу не отдаются, так что у большинства их не будет — и это нормально: чтобы разрабатывать, разворачивать стенд не нужно, достаточно `docker compose up` из корня репозитория.

Проверить конфигурацию без доступа к состоянию можно всегда — то же делает job `opentofu` в `ci.yml`:

```bash
cd infra && tofu fmt -check -recursive && tofu init -backend=false && tofu validate && tofu test
```

`tofu test` гоняет `tests/*.tftest.hcl` с `mock_provider "docker"`: ни Docker, ни сервер не нужны. Тесты проверяют адреса базы и брокера в окружении контейнеров и в `migrate_env`, какие секреты получает какой контейнер, раскладку по сетям и порты, грейс-период воркера и штатную остановку базы, реплики и брокера, образ `api` и `worker` по digest без тега, `wait` у базы, ожидание `healthy` у API и формат длительностей его healthcheck, проверки переменных. Проверки отклоняют на `plan`, пока сервер не тронут: пустые `github_webhook_secret`, `postgres_password`, `rabbitmq_password`, пустой или короткий `postgres_replication_password` (незаданный секрет CI приходит пустой строкой), `llm_backend = "ollama"` без `ollama_model`, `llm_hosted_fallback` без `ollama` и всех `eurorouter_*`, `api_image` без digest.

`tofu destroy` **падает на томах** базы, брокера, реплики и копий: у них `prevent_destroy = true`, и OpenTofu отказывается строить план, который их уничтожает. Удалить стенд осознанно — с данными — можно, только сняв защиту: заменить `prevent_destroy = true` на `false` в `postgres.tf`, `rabbitmq.tf` и `replica.tf` локально (не в коммите), затем `tofu destroy`. Без этого `tofu destroy` не тронет ничего: ошибка — до изменений. Контейнер хранилища состояния `tofu destroy` не удаляет и так — он не входит в этот стек намеренно. Полная зачистка описана выше, в разделе «Хранилище состояния».

Этот стек только для API. UI деплоится отдельно из `dmc-268-ui-t1/infra/`.
