# Стек сервера (API на Python 3.14, PostgreSQL 18, RabbitMQ 4.4)

Нужны **Docker Engine** на целевом хосте и OpenTofu >= 1.13 (в CI ставится 1.13.2). Образ API не собирается здесь: он публикуется в ghcr из CI и запускается по digest (`api_image` — `<репозиторий>:<commit sha>@sha256:<digest>`; ссылка без digest не проходит проверку переменной).

## Раскладка файлов

Конфигурация разложена по доменам; OpenTofu читает все `*.tf` каталога как один модуль, так что адреса ресурсов от файла не зависят.

| Файл | Что внутри |
| --- | --- |
| `versions.tf` | версия OpenTofu, провайдер `kreuzwerker/docker` и его настройки (хост Docker) |
| `backend.tf` | хранилище состояния (S3 на сервере) |
| `locals.tf` | общие значения: ротация логов, драйвер fluentd, окружение процессов приложения, грейс-период воркера |
| `network.tf` | три сети: вход `dmc268` (общая со стеком `dmc-268-ui-t1`), данные `dmc268-backend`, исходящая `dmc268-egress` |
| `postgres.tf` | образ, том и контейнер PostgreSQL |
| `rabbitmq.tf` | образ, том и контейнер RabbitMQ |
| `app.tf` | контейнеры `api`, `worker` из образа API по digest |
| `observability.tf` | стек наблюдаемости: образы, тома, сети и девять контейнеров |
| `replica.tf` | роль репликации, горячая реплика и резервные копии PostgreSQL |
| `postgres/` | то, что загружается в контейнеры PostgreSQL: `pg_hba.conf`, SQL роли, entrypoint реплики, скрипт копий |
| `variables.tf` | входные переменные, по секциям тех же доменов |
| `outputs.tf` | выходы: `migrate_env` — окружение миграций для шага деплоя |
| `tests/*.tftest.hcl` | `tofu test` с mock-провайдером |

## Почему OpenTofu, а не Terraform

Terraform с версии 1.6 распространяется под Business Source License (BUSL) — она не open source, и условия дополнительного разрешения HashiCorp на использование размыты. OpenTofu — форк последней открытой версии под Mozilla Public License 2.0, проект Linux Foundation. Провайдеры у него те же, что у Terraform (своих OpenTofu не пишет), а берутся из собственного реестра `registry.opentofu.org`: `kreuzwerker/docker` работает без изменений. Сверх Terraform OpenTofu умеет шифровать состояние и план на диске и в бэкенде (с 1.7); у нас оно включено (`encryption.tf`, раздел «Шифрование состояния»), а само хранилище лежит на петле сервера и доступно только через SSH-туннель.

## Локальный или удалённый Docker

Скопируйте `terraform.tfvars.example` в `terraform.tfvars` и замените плейсхолдеры `CHANGE_ME_*`. Файл `terraform.tfvars` не коммитится (gitignore).

- Локальный демон: `docker_host = "unix:///var/run/docker.sock"` (у Docker Desktop на macOS часто `unix:///Users/<вы>/.docker/run/docker.sock`).
- Удалённый сервер: `docker_host = "ssh://user@server"` (нужны SSH-доступ и Docker на удалённом хосте).

Образ API перед `apply` скачивают на тот же Docker сами: `docker pull <api_image>` (с `DOCKER_HOST`, если демон удалённый; для приватного пакета — после `docker login ghcr.io`). Провайдер создаёт `api` и `worker` из уже скачанного образа, а если его нет — тянет сам, но без учётных данных, и на приватном пакете `apply` падает с `denied`.

API публикуется на `bind_ip`, в деплое это `127.0.0.1`. Другого значения конфигурация не примет: переменная проверяется на адрес петли (`127.0.0.0/8` или `::1`), и ошибка всплывает на `plan`. PostgreSQL, реплика и RabbitMQ портов на хосте не публикуют вовсе — см. «Сети».

## Сети

Контейнеры приложения разнесены по docker-сетям (сети стека наблюдаемости — в его разделе), каждый видит только тех, с кем говорит:

| Сеть | Кто в ней | Зачем |
| --- | --- | --- |
| `dmc268` | интерфейс (из `dmc-268-ui-t1`), `api` | публичный вход: nginx интерфейса проксирует `/api/` в API. Имя прежнее — интерфейс подключается к ней по имени |
| `dmc268-backend` (`internal`) | `postgres`, `postgres-replica`, `postgres-backup`, `rabbitmq`, `replication-setup`, `api`, `worker`, миграции шага деплоя | данные. У сети нет шлюза: из неё не выйти в интернет, а интерфейса в ней нет |
| `dmc268-egress` | `worker` | исходящие запросы воркера к GitHub API и провайдеру модели |
| `dmc268-otlp` (`internal`) | интерфейс, `otelcol` (при `observability_enabled`) | трейсы браузера: nginx интерфейса проксирует `/otlp/v1/traces` на отдельный приёмник коллектора `dmc268-otelcol:4319`: только трейсы, `service.name` ставит коллектор (`dmc-268-ui`), кабинет шлёт их на свой же origin. По ней же receiver `nginx` коллектора снимает `stub_status` интерфейса (`dmc268-ui:8081`, на хост не публикуется). Сеть создаётся и без стека: интерфейс подключается к ней по имени, и без коллектора `/otlp/v1/traces` отвечает 502, а остальное работает |
| `dmc268-grafana-proxy` (`internal`) | интерфейс, `grafana` (при `observability_enabled`) | публичный вход в Grafana: nginx интерфейса на порту 8443 проксирует `/grafana/` на `dmc268-grafana:3000`, Grafana отдаётся из этого подпути. Из стека в сети только Grafana, шлюза нет. Создаётся и без стека, как `dmc268-otlp`: интерфейс подключается к ней по имени. Откатывают в обратном порядке: сначала фронт (из сети уходит `dmc268-ui`), потом бэкенд — Docker не удаляет сеть с подключённым контейнером, и `tofu apply` бэкенда раньше фронта упадёт |

API — единственный, кто стоит и во входе, и в данных. С `internal`-сети Docker не публикует порты, поэтому у базы и брокера портов на хосте нет: для отладки — `docker exec -it dmc268-postgres psql -U dmc268 -d dmc268` и `docker exec dmc268-rabbitmq rabbitmq-diagnostics status`. Изоляцию проверяют `tests/test_infra_isolation.py` (по тексту `infra/*.tf`) и `infra/tests/main.tftest.hcl` (по плану).

## Реплика и резервные копии

**Горячая реплика** `dmc268-postgres-replica` — физическая потоковая репликация с основного сервера по слоту `dmc268_replica`, только чтение. Приложение в неё не ходит; с неё снимаются резервные копии.

- **Роль `replicator`** заводит одноразовый контейнер `dmc268-replication-setup` (`postgres/replication-setup.sql`), идемпотентно: init-скрипты образа на уже заведённом томе не выполняются. Контейнер запускается заново, когда сменились пароль или SQL либо пересоздана основная база (её контейнер или том), — не на каждом деплое.
- **Пароль роли** — секрет `PG_REPLICATION_PASSWORD_DMC268_T1`. В каталоге данных реплики его нет: реплика пишет `passfile` на каждом старте и передаёт `primary_conninfo` аргументом. Поэтому смена секрета — обычный деплой: роль получает новый пароль, реплика пересоздаётся с новым `passfile`, том не пересобирается.
- **Слот** заводит сама реплика (`pg_basebackup --create-slot`) при каждой пересборке, удаляя неактивный старый.
- **Пересборка** (`postgres/replica-entrypoint.sh`) происходит сама при старте контейнера, если том пуст или копия не дописана либо слота нет или он потерян: основной сервер тогда тот же кластер, и пересборка ничего не теряет. Копия снимается во временный каталог и переименовывается целиком; на это время на диске нужно место под две копии базы (старый каталог и новый). При постоянной ошибке `pg_basebackup` пауза между попытками растёт до минуты.
- **Другой кластер основного сервера** (его том заведён заново, например потерян) реплика **не стирает**: в ней может быть последняя копия данных, а новый основной сервер — пустым. Контейнер завершается с ошибкой «основной сервер — другой кластер», деплой падает на проверке потока. Дальше решает человек: если данные реплики нужны — поднять из них основной сервер (или снять `pg_dump` с остановленной реплики); если нет — пересобрать реплику, удалив её том: `docker rm -f dmc268-postgres-replica && docker volume rm dmc268-postgres-replica-data`, затем деплой. Решение принимается только по ответу основного сервера: пока он недоступен, реплика ничего не трогает.
- **Потолок WAL.** Слот держит WAL для отставшей реплики, но не больше `postgres_max_slot_wal_keep_size` (2 ГБ): иначе упавшая реплика заполнила бы диск основного сервера. Реплика, перешагнувшая потолок, теряет поток и становится `unhealthy`. Docker unhealthy-контейнеры не перезапускает, поэтому это делает деплой: перед проверкой потока он перезапускает unhealthy-реплику, и она пересобирается. Между деплоями — вручную: `docker restart dmc268-postgres-replica`.
- **Здоровье реплики** — это поток: healthcheck смотрит `pg_stat_wal_receiver.status = streaming`. Отставшая реплика отвечает на запросы, но `unhealthy`.
- **Деплой** (`.github/scripts/deploy/check-replica.sh`) проверяет со стороны основного сервера, что слот держит именно реплика (`application_name = dmc268_replica`, а у `pg_basebackup` первой сборки — `dmc268_basebackup`) и поток в состоянии `streaming`; unhealthy-реплику перед этим перезапускает.
- **Доступ к базе** (`postgres/pg_hba.conf`, вне каталога данных) — только из подсети самого сервера (`samenet`), то есть из `dmc268-backend`.

Реплика на том же сервере: она спасает от сбоя процесса или тома основной базы, но не от падения самого сервера.

**Резервные копии** снимает `dmc268-postgres-backup`: `pg_dump -Fc` при старте и затем раз в сутки, в том `dmc268-postgres-backups`, хранение — `backup_keep_days` (7 суток). Источник — реплика, если она получает поток, иначе основной сервер: копия с отставшей реплики выглядела бы свежей, а содержала бы данные на момент обрыва. Контейнер становится `unhealthy`, если свежей копии нет дольше 26 часов. Источник копии видно только в логе бэкапа, а не в его healthcheck: **unhealthy-реплика означает, что копии идут с основного сервера**. Пока база маленькая, это незаметно; на большой базе ежедневный `pg_dump` с основного сервера держит блокировки и может задержать миграции с `ALTER TABLE` — реплику стоит поднять, не откладывая. Копии лежат на том же диске; от потери сервера спасает их вынос — ниже, «Копии вне сервера».

**Брокер копий не имеет, и они ему не нужны.** Если том `dmc268-rabbitmq-v44-data` потерян, деплой поднимает брокер на пустом томе: пользователя заводит `RABBITMQ_DEFAULT_USER`, пароль ставит шаг «Выставить пароли базы и брокера» (`passwords.sh`), очереди, DLX и DLQ объявляют API и воркер при подключении. Сообщения DLQ терять не жалко: перед уходом в DLQ воркер переводит прогон в `failed` с `failure_reason` и кодами ошибок шагов, а если не успел — прогон выметает `sweep_stale_runs`. Всё нужное для разбора лежит в базе, поэтому упавшие прогоны разбирают по `review_runs` и копиям `pg_dump`. Теряются задачи, стоявшие в очереди: их прогоны остаются `queued`, и `sweep_stale_runs` переводит их в `failed` через 6 часов (`queued_run_timeout_seconds`, брошенные в работе — через 30 минут). До этого новый прогон на тот же коммит не создаётся. Потом ревью head запускает следующий push или переотправка доставки из настроек GitHub App.

**Ollama**, если её развернут на сервере, подключается к `dmc268-backend`: воркер ходит к ней оттуда. К `dmc268-egress` — только если Ollama сама скачивает модели.

Восстановление в основную базу (API и воркер на это время остановить):

```bash
docker run --rm --network dmc268-backend -v dmc268-postgres-backups:/backups:ro \
  -e PGPASSWORD=<пароль> pgvector/pgvector:pg18 \
  pg_restore -h dmc268-postgres -U dmc268 -d dmc268 --clean --if-exists /backups/<файл>.dump
```

После восстановления `alembic_version` пересоздана с правами по умолчанию, и роль приложения снова может её писать. Запрет вернёт ближайший деплой (`alembic/role_passwords.py`), до него можно вручную:

```bash
docker run --rm --network dmc268-backend -e PGPASSWORD=<пароль> pgvector/pgvector:pg18 \
  psql -h dmc268-postgres -U dmc268 -d dmc268 -c 'REVOKE ALL ON alembic_version FROM dmc268_app'
```

### Копии вне сервера

Workflow `.github/workflows/db-backup.yml` каждый день в 21:17 UTC (и вручную: `gh workflow run db-backup.yml --ref develop`) берёт со стенда самую новую копию из `dmc268-postgres-backup`, шифрует её и загружает артефактом прогона на 90 суток — дольше публичный репозиторий не хранит. Копия старше 26 часов или отсутствие ключа — красный прогон до загрузки: устаревшую копию workflow не выносит, открытую — никогда (артефакт публичного репозитория скачивает любой). Вторым job'ом та же копия скачивается, расшифровывается и восстанавливается в чистый PostgreSQL 18; проверка — одна ревизия в `alembic_version`, основные таблицы на месте, `repositories` не пуста. Письмо GitHub о красном плановом прогоне получает один человек — тот, кто последним менял строку `cron` в `db-backup.yml` (или включил workflow снова), а если расписание не запустилось (нагрузка GitHub, автоотключение через 60 дней без активности в репозитории), нет ни прогона, ни письма. Поэтому третий job, `mark-success`, после проверки восстановления пишет на стенде отметку `dmc268_offsite_backup_last_success_timestamp_seconds`: файл `offsite-backup.prom` в томе `dmc268-backup-metrics` рядом с отметкой `backup.sh`, через `docker exec` в контейнер копий. Отметки нет дольше 28 часов — алерт `OffsiteBackupStale` в Telegram (раздел «Алерты»). Записи о деплое в environment `stand` вынос не создаёт (`deployment: false`). Сразу после первого деплоя с этим алертом отметки ещё нет, и он горит до первого успешного выноса: запустить вручную `gh workflow run db-backup.yml --ref develop`.

Шифрование — `openssl enc -aes-256-cbc -pbkdf2 -iter 600000`, ключ — секрет репозитория `STATE_BACKUP_KEY_DMC268_T1`, тот же, что у аварийной копии `errored.tfstate` (раздел «Если деплой упал посреди apply»): один ключ открывает и копии базы, и копию состояния. **Копия ключа обязана лежать вне GitHub** — секрет обратно не прочитать, и без копии ключа копии базы бесполезны. Если копии нет (ключ ставили трубой `openssl rand … | gh secret set`), ключ заводится заново, и копия сохраняется до установки секрета:

```bash
key="$(openssl rand -base64 48)"   # сохранить в менеджер паролей до следующей строки
printf '%s' "$key" | gh secret set STATE_BACKUP_KEY_DMC268_T1
```

Новый ключ не открывает копии, снятые старым: при ротации старый ключ хранится вне GitHub, пока не истекут его копии (90 суток).

Восстановление из вынесенной копии (сервер потерян или копии на нём испорчены):

```bash
# прогон с нужной копией; артефакт называется по копии, dmc268-<UTC> (виден в gh run view)
gh run list -w db-backup.yml -s success -L 5
gh run view <id прогона>
gh run download <id прогона> -n dmc268-<UTC> -D backup   # backup/dmc268-<UTC>.dump.enc
read -rs STATE_BACKUP_KEY && export STATE_BACKUP_KEY   # ключ из копии вне GitHub
openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -pass env:STATE_BACKUP_KEY \
  -in backup/dmc268-<UTC>.dump.enc -out dmc268.dump
```

Дальше — `pg_restore` на сервере: файл скопировать туда (`scp dmc268.dump <пользователь>@<сервер>:`) и восстановить со стандартного ввода (API и воркер остановлены). В том копий файл не кладётся: там его приняли бы за свежую копию и healthcheck, и вынос.

```bash
docker run --rm -i --network dmc268-backend -e PGPASSWORD=<пароль> pgvector/pgvector:pg18 \
  pg_restore -h dmc268-postgres -U dmc268 -d dmc268 --clean --if-exists < dmc268.dump
```

На новом сервере сначала деплой (он заводит пустую базу и миграции), потом то же `pg_restore --clean --if-exists`. Затем тот же `REVOKE ALL ON alembic_version FROM dmc268_app`, что после восстановления из тома. Открытый `dmc268.dump` после восстановления удалить: в нём токены и данные пользователей.

**Сменить хранилище** (например, на S3-совместимый R2 или B2) — заменить в `db-backup.yml` два шага, которые о нём знают: «Сохранить копию» — на `aws s3 cp "$FILE" "s3://<бакет>/$NAME.dump.enc"`, «Взять копию» — на `aws s3 cp` обратно в `$RUNNER_TEMP/db-backup/`. Ключи бакета — новыми секретами в env этих шагов, срок хранения — правилом жизненного цикла бакета вместо `retention-days`. Скрипты `.github/scripts/db-backup/` (взять копию со стенда, зашифровать, расшифровать, восстановить) остаются как есть: они работают с файлом `<имя>.dump.enc`, а не с хранилищем. Из runbook выше меняются поиск и скачивание копии (первые три команды).

## Ограничения контейнеров

- `api`, `worker` и миграции работают не от root (`USER` в `Dockerfile`), с файловой системой только для чтения (запись — только в `/tmp`), без capabilities и с `no-new-privileges`. У миграций это флаги `docker run` в `.github/scripts/deploy/migrate.sh`.
- `postgres` и `rabbitmq` — только `no-new-privileges`: их entrypoint стартует от root, чтобы подготовить каталог данных, и сам переходит на служебного пользователя.
- У каждого контейнера потолок памяти без свопа (`postgres` 1 ГБ, `postgres-replica`, `rabbitmq`, `api` и каждый экземпляр `worker` по 512 МБ, `postgres-backup` и миграции по 256 МБ, `replication-setup` 64 МБ) и ротация логов: три файла по 10 МБ. Постоянно работающие контейнеры — около 3,3 ГБ с одним воркером и ещё 0,5 ГБ на каждый следующий («Масштабирование воркеров»), на время деплоя добавляются миграции и `replication-setup`; без учёта интерфейса и хранилища состояния.
- Лимит cgroup RabbitMQ не видит и считал бы пороги от памяти хоста (на стенде вышло 5 ГБ при лимите 512 МБ). Поэтому пороги абсолютные, в `rabbitmq/30-dmc268.conf`: память 300 МиБ (выше брокер блокирует издателей, а не ждёт OOM) и свободный диск 1 ГБ (по умолчанию 50 МБ). Healthcheck брокера — `check_port_connectivity`: `ping` отвечает ещё до листенера AMQP.
- `replication-setup` и `postgres-backup` — как миграции и `api`: файловая система только для чтения, без capabilities. `postgres-replica` — как `postgres`: только `no-new-privileges`.
- `postgres`, `postgres-replica` и `rabbitmq` при пересоздании и `docker stop` останавливаются штатно: `stop_timeout` и `destroy_grace_seconds` по 60 с. Без `destroy_grace_seconds` провайдер удаляет контейнер через SIGKILL, и база поднимается с восстановлением после аварии.

Смена любого из этих атрибутов пересоздаёт контейнер. Данные PostgreSQL и RabbitMQ лежат в томах и замену переживают.

## Версия провайдера

Точная версия `kreuzwerker/docker` и её хэши закреплены в `.terraform.lock.hcl`, файл коммитится. После смены `version` в `versions.tf` его пересобирают на все платформы команды, иначе `tofu init` на неперечисленной системе допишет в файл свои хэши и оставит изменение в рабочей копии:

```bash
cd infra && tofu init -backend=false -upgrade && tofu providers lock \
  -platform=linux_amd64 -platform=linux_arm64 \

```

## Деплой

Стенд катится сам при мерже в `develop` (`.github/workflows/deploy.yml`). `main` в деплое не участвует: сервер один, и два источника дрались бы за него.

Порядок такой: образ собирается и публикуется в `ghcr.io/larchanka-training/dmc-268-api-t1` с тегом по commit sha → сверка, что коммит всё ещё вершина `develop` (`check-tip.sh`) → поднимается хранилище состояния и туннель к нему → targeted-план сети, базы и брокера в файл, сторож и его apply (`infra.sh`) → план полного выката в файл и сторож томов (`plan.sh`) → pull образа API → пароли базы и брокера из секретов (`passwords.sh`, раздел «Смена паролей») → миграции (`.github/scripts/deploy/migrate.sh`) → `tofu apply` этого плана (`apply.sh`) → проверка воркера → уборка образов → summary (`summary.sh`). Если упал шаг, который пишет состояние, между apply и проверками идёт восстановление состояния (раздел «Если деплой упал посреди apply»).

**Устаревший коммит не катится.** `gate` сверяет коммит с вершиной `develop`, но только у `workflow_run` и только при своём запуске, а «Re-run failed jobs» успешный `gate` не перезапускает и берёт его выход `sha` из первой попытки. Поэтому первым шагом после checkout job `deploy` сверяет коммит ещё раз (`check-tip.sh`) — и для ручного запуска тоже: вершина ушла — остальные шаги пропускаются, job зелёный, в summary «пропущен: вершина develop уже …». Перезапуск упавшего деплоя, пока за ним не пришёл новый коммит, катит как обычно. Публичной проверки здесь нет: API снаружи не публикуется, а его доступность по `https://62.169.24.237/api/v1/` проверяет деплой интерфейса.

**Снаружи API адресуется через интерфейс, с исходным путём.** Публичный вход — `nginx` в контейнере фронтенда на **https://62.169.24.237** (сертификат Let's Encrypt на IP, HTTP перенаправляется на HTTPS; устройство — в `infra/README.md` репозитория `dmc-268-ui-t1`). Префикс он не трогает: браузерный `GET /api/v1/reviews` приходит сюда как `GET /api/v1/reviews`, поэтому роутеры монтируются на `/api/v1`, как требует контракт API. `/health` через этот вход не публикуется — проверка живости ходит мимо него.

**Тома данных деплой не уничтожает.** У каждого тома (`docker_volume.postgres`, `docker_volume.rabbitmq`, `docker_volume.postgres_replica`, `docker_volume.postgres_backups`) — `lifecycle { prevent_destroy = true }`: план, который уничтожает или заменяет том, OpenTofu отклоняет до изменений на сервере с `Error: Resource instance cannot be destroyed`. Это действует и на targeted apply шага «Поднять базу и брокер» — `-target=docker_container.postgres` тянет том зависимостью; тот же сторож `scripts/deploy_report.py` смотрит и его план (`infra.sh`). Полный выкат идёт планом в файл: `plan.sh` строит `tofu plan -out=tfplan` сразу после targeted apply, и `scripts/deploy_report.py` по `tofu show -json` дублирует проверку для summary — падает, если план уничтожает или заменяет любой `docker_volume`, и apply не запускается. Списка адресов у сторожа нет: ресурс, переименованный без блока `moved`, уничтожается по старому адресу, и `prevent_destroy` у него уже нет — по списку его бы не поймать. Миграции идут между планом и apply: состояние они не трогают, план не устаревает. Применяется ровно проверенный план (`apply.sh`); если до него не дошло, файл плана удаляет `summary.sh`. Сменить том, как при смене сборки PostgreSQL или версии RabbitMQ, — новым ресурсом с новым адресом (с `prevent_destroy` — его наличие у каждого тома сверяет тест), а прежний снять с учёта блоком `removed { lifecycle { destroy = false } }`: план выйдет `forget` и `create`, старый том с данными останется на сервере до ручного `docker volume rm`. Файл плана зашифрован фразой состояния (раздел «Шифрование состояния»), а в JSON `tofu show -json` пароли открытым текстом: JSON идёт только трубой, файл плана удаляется после apply и артефактом не загружается, обёртка `setup-opentofu`, копирующая stdout tofu в выходы шага, выключена.

**Summary деплоя** пишет `summary.sh` на любом исходе: шаг падения, простой API с разбивкой (SIGTERM старому → выход → `Created` нового → `State.StartedAt` → событие `health_status: healthy` нового; всё, кроме `Created` и `StartedAt`, — из событий Docker, которые `apply.sh` читает потоком всё время apply. `State.Health.Log` — запасной путь, если событий нового контейнера нет: журнал держит пять последних проверок, и после долгого apply первой успешной в нём уже нет — summary тогда помечает простой как недостоверный), оба плана по типам ресурсов (targeted базы и брокера и полный), применённые миграции — а если шаг миграций упал, ревизия, на которой он упал, и ревизия базы по `alembic current`, который `migrate.sh` запускает после сбоя тем же образом под `timeout 60` (по логу alembic не сказать, что откатилось: `autocommit_block` фиксирует всё до себя, а при оборванном ssh код выхода теряется; не ответила база — summary пишет «ревизия базы неизвестна», без «откатено»); упал шаг до alembic (`tofu output`) — так и сказано, свободное место на `/` и в каталоге Docker после уборки и длительность шагов — по засечкам `mark.sh`, без `actions: read` у токена. Подписи значений — ключи OpenTelemetry (`cicd.pipeline.*`, `container.image.*`, `system.filesystem.*`), свои — в `dmc268.deploy.*`.

**Миграции — шаг деплоя до полного `apply`, а не контейнер стека.** Шаг `Применить миграции` запускает `.github/scripts/deploy/migrate.sh`: одноразовый `docker run --rm` того же образа (тот же digest), что сейчас выкатится, с `alembic upgrade head` и шагом роли мониторинга (ALTER ROLE при выключенном `track_utility`, пароль — из окружения; тот же шаг — у сервиса `migrate` в compose) — на сервере через `DOCKER_HOST=ssh://stand`, в сети данных `dmc268-backend`. Окружение — выход `migrate_env` (`outputs.tf`): те же строки `local.app_env`, что у `api` и `worker`, плюс телеметрия (`local.telemetry_env`) и `POSTGRES_MONITOR_PASSWORD`, через env-файл с правами 600, который удаляется после запуска. Упала миграция — шаг падает, полный `apply` не запускается, на стенде остаётся прежняя версия. Проверка `/health` этого не заметила бы: по контракту она отвечает независимо от базы.

Бесконечно ждать миграция не может. Сессии alembic `alembic/env.py` ставит `lock_timeout = '5s'` и `statement_timeout = '2min'` (только онлайн, в SQL `--sql` их нет): `ALTER TABLE`, который ждёт блокировку горячей таблицы за транзакцией старого API или воркера, иначе ставил бы за собой в очередь все её чтения, и API висел бы. Через 5 с миграция падает с `LockNotAvailable`, транзакция откатывается, стенд работает на прежней схеме. `migrate.sh` тогда спрашивает `alembic current` и, если база на ревизии, с которой попытка начала, повторяет upgrade через 15 с — всего до 3 попыток, и новая не начинается позже 5 мин от старта шага; база сдвинулась (`autocommit_block`), не ответила или ошибка другая — шаг падает сразу, решает человек. У шага `timeout-minutes: 10`. Контейнер `dmc268-migrations`, оставшийся от шага, убитого по таймауту (раннер убивает docker CLI, а не контейнер на сервере), `migrate.sh` удаляет перед запуском; удаление рвёт соединение, и PostgreSQL откатывает его транзакцию.

Пока идут миграции, работает старый код: ломающая миграция (удаление или переименование колонки, которую он читает) даст на стенде короткий сбой во время выката. Пока нет пользователей, это допустимо; для прода — expand/contract в два деплоя (скилл `.agents/skills/alembic-migration`).

Образ лежит в приватном пакете: перед миграциями job входит в `ghcr.io` на раннере (`docker/login-action`, `GITHUB_TOKEN` с `packages: read`), и docker CLI передаёт учётные данные демону сервера вместе с запросом pull. На сервере токен не остаётся. Этот pull — единственный для образа API, он идёт своим шагом «Скачать образ API» до шага паролей (окно смены пароля его не включает, раздел «Смена паролей»): учётных данных реестра у провайдера нет, и `api` с `worker` он создаёт из уже скачанного образа.

**Чистый сервер.** База и брокер должны существовать до миграций, поэтому перед ними каждый деплой (`infra.sh`) строит и применяет targeted-план

```bash
tofu plan -out=infra.tfplan -target=docker_network.dmc268 -target=docker_network.backend -target=docker_container.postgres -target=docker_container.rabbitmq
tofu show -json infra.tfplan | python3 scripts/deploy_report.py plan infra
tofu apply infra.tfplan
```

На живом стенде это `No changes` и ожидаемое предупреждение OpenTofu о `-target`; на чистом — создание сети, томов, базы и брокера. У `postgres` и `rabbitmq` `wait = true`: apply возвращается, когда их healthcheck зелёный, и миграциям и смене паролей не нужен цикл повторов. Если контейнер не стал healthy за `wait_timeout`, apply падает, а контейнер остаётся в состоянии tainted, и следующий деплой планирует его замену, которую сторож отклонит. Тогда, выяснив причину, `tofu untaint docker_container.rabbitmq` (или `postgres`), а не повторная замена с `allow_stateful_replace`: она остановит уже поднявшийся узел. Этот же apply обновляет в состоянии выход `migrate_env`: выход зависит от контейнеров базы и брокера (хосты в `local.app_env` — ссылки на них), а выход, не зависящий от целевых ресурсов, targeted apply не записывает. Руками ничего делать не нужно: первый деплой на пустой сервер проходит тем же путём (проверено на чистом локальном Docker 29.9.2).

**Базу и брокер деплой не пересоздаёт.** План, который заменяет или удаляет `docker_container.postgres` или `docker_container.rabbitmq`, сторож отклоняет — и targeted, и полный: apply не запускается, контейнеры те же. Узнаёт он их и по имени контейнера на хосте (`dmc268-postgres`, `dmc268-rabbitmq` в `change.before`/`after` плана): ресурс, переименованный без `moved`, уничтожается по старому адресу, и сверка только по адресу его бы пропустила. Реплику (`docker_container.postgres_replica`) и копии (`docker_container.postgres_backup`) сторож не держит, хотя они тоже на томах данных: API и воркер в них не ходят, данные остаются в защищённых томах, а замена — обычная правка. Реплика при этом останавливается штатно (`destroy_grace_seconds` 60), копия, оборванная на полпути, остаётся `*.partial` и убирается следующим стартом. Так же не держит он и хранилища стека наблюдаемости — Loki, Tempo, Prometheus и Grafana (`observability.tf`): их тома защищены, а правка конфига — замена контейнера с окном штатной остановки 30 с (`stop_timeout`/`destroy_grace_seconds`), чтобы WAL и буферы сбрасывались, а не обрывались SIGKILL. До миграций их не поднимают: targeted-план — только сети, основной сервер и брокер. Повод к замене — правка их `command`, памяти, `log_opts`, образа или конфига брокера `rabbitmq/30-dmc268.conf`. Правку `env` план не видит (`ignore_changes = [env]`): там только переменные инициализации тома, и смена `TF_VAR_postgres_password` раньше давала `postgres must be replaced`, не меняя пароль в существующем томе, — миграции потом падали с `password authentication failed`. Пароль теперь выставляет шаг деплоя (раздел «Смена паролей»). Правку `command`, памяти или образа базы и брокера выкатывает ручной запуск с осознанным обходом сторожа: `gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true`. Флаг доходит до сторожа только из `workflow_dispatch` и только у первой попытки (у автоматического деплоя выражение в env шага даёт `false`; Re-run повторил бы inputs старого запуска, поэтому повтор с флагом — новым `gh workflow run`, а не Re-run), замена тогда — `::warning::` и пометка в summary с тем, кто запустил эту попытку (`github.triggering_actor`); уничтожение или замену томов флаг не разрешает никогда. У обоих контейнеров `destroy_grace_seconds = 60`: при ручной замене провайдер ждёт штатной остановки, а не шлёт SIGKILL сразу после стоп-сигнала (было: `kill 2` → `kill 9`, код 137). У брокера задан `hostname = "dmc268-rabbitmq"`: RabbitMQ хранит данные в каталоге узла `rabbit@<hostname>`, и без постоянного имени каждый новый контейнер стартовал бы на томе пустым узлом, а очереди и DLQ старого остались бы сиротами (#338). Брокер, заведённый до этого, переходит на постоянное имя один раз: проверить, что очереди пусты (`docker exec dmc268-rabbitmq rabbitmqctl -q list_queues name messages`), выкатить ручным запуском с `allow_stateful_replace=true`, убедиться, что узел — `rabbit@dmc268-rabbitmq` (`rabbitmq-diagnostics -q status`), и удалить каталоги прежних узлов `rabbit@<id>*` в `/var/lib/rabbitmq/mnesia`. Их данные не нужны: прогоны по их сообщениям в базе уже `failed`.

**Образ API — без ресурса `docker_image`.** `api` и `worker` ссылаются на образ строкой `<репозиторий>@sha256:<digest>` — `local.api_image_ref` в `app.tf`, тег из `api_image` срезан. Ресурс образа пересоздавался на каждом коммите (тег — commit sha) уже после остановки старого API, и его pull добавлял к простою 6 с (деплой #202). Тег в ссылке контейнера дал бы то же: провайдер сравнивает `image` строкой и пересоздаёт контейнер, даже если digest не изменился. Теперь контейнеры меняются, только когда меняется digest; `docker ps` показывает репозиторий без тега, commit sha — в summary деплоя. Замена API не ждёт воркера и без отдельного ресурса образа: общего ресурса, который ждал бы уничтожения обоих контейнеров, больше нет.

**Готовность API ждёт сам `apply`.** У `docker_container.api` `wait = true` и `wait_timeout = 90`: создав контейнер, провайдер опрашивает его состояние и считает выкат завершённым, когда healthcheck (`/health` изнутри контейнера) стал `healthy`; не стал за 90 с — `apply` падает, контейнер помечается tainted и пересоздаётся следующим деплоем, а шаг `Логи API после упавшего apply` печатает хвост лога и историю проверок. `start_interval = "1s"` даёт `healthy` в первую секунду после старта приложения, а не через `interval` 30 с. Длительности healthcheck пишутся в формате Go (`"2s"`, `"30s"`, `"1m0s"`): в нём провайдер читает их обратно, и `"1m"` дал бы вечный diff. Правку healthcheck провайдер планирует обновлением на месте, но к запущенному контейнеру она не применяется, поэтому API пересоздаётся от `terraform_data.api_healthcheck` (`replace_triggered_by`).

**Одно SSH-соединение на job.** Хост `stand` в `~/.ssh/config` (`.github/actions/stand-ssh`) — с `ControlMaster auto`, `ControlPath ~/.ssh/cm-%C` и `ControlPersist 10m`: первый `ssh stand` поднимает фоновое соединение, и через него идут все шаги и каждый запрос docker-провайдера и docker CLI к `ssh://stand`, без нового рукопожатия на запрос. Замер с RTT 80 мс: 10 вызовов `docker -H ssh://stand version` — 12,5 с без мультиплексирования, 3,9 с с ним. `ServerAliveInterval 10` и `ServerAliveCountMax 3`: если TCP мастера пропал без разрыва, master закрывается за 30 с — `ConnectTimeout` через живой master не действует, клиент идёт в сокет. ssh в шагах `always()` (`finish` в `apply.sh`, `summary.sh`) к тому же под `timeout 30`, у шага summary `timeout-minutes: 3`. Сессии сверх `MaxSessions` сервера (по умолчанию 10) ssh открывает своим соединением, вызов не падает. Туннель к хранилищу (`.github/scripts/s3-tunnel.sh`) идёт мимо master, с `-o ControlPath=none`: через master проброс открывает сам master, `ExitOnForwardFailure` не срабатывает на занятом порте, а туннель закрывается вместе с master через `ControlPersist` простоя — посреди деплоя это был бы туннель к хранилищу состояния. Туннель к хранилищу терпит провал связи дольше master — `ServerAliveCountMax=12`, две минуты: пока он жив, запрос OpenTofu ждёт в нём и доходит, когда связь вернулась, а закрылся — запись состояния падает, и его приходится восстанавливать.

**Воркер** `dmc268-worker` разворачивается из того же образа, что и API, с командой `python -m app.worker`; экземпляров — `worker_replicas` (раздел «Масштабирование воркеров»), следующие называются `dmc268-worker-2` и далее. Портов у него нет: с остальным стеком он говорит только через очередь и базу, наружу — исходящими запросами к GitHub API (дифф, `.review/rules.md`, файлы для AST), поэтому получает те же `GITHUB_APP_ID` и `GITHUB_APP_PRIVATE_KEY`, что и API. Стартует, как и API, после миграций. HTTP-проверки у него нет, поэтому деплой считает воркеры живыми, если каждый экземпляр 30 секунд подряд запущен и ни разу не перезапустился.

Адаптер модели воркера задаёт `llm_backend` (`LLM_BACKEND`): `stub` - без похода к модели, `ollama` - локальная модель, `eurorouter` - hosted-провайдер основным. Значения по умолчанию нет: заглушка выбирается только явно. Деплой стенда передаёт `TF_VAR_llm_backend: eurorouter` в `.github/workflows/deploy.yml` (#245): Ollama на стенде нет, код проверяемых репозиториев уходит Eurorouter. `eurorouter` требует `eurorouter_base_url`, `eurorouter_model` и `eurorouter_api_keys`, без них план падает.
`ollama` требует `ollama_model` и развёрнутой Ollama по `ollama_base_url`.

## Масштабирование воркеров

Число воркеров — одна переменная `worker_replicas` (#99): по умолчанию 1, допустимо от 1 до 4. На стенде её задаёт `TF_VAR_worker_replicas` в `env` job'а `deploy` (`.github/workflows/deploy.yml`), оттуда же её берёт проверка воркеров после выката. Экземпляры — контейнеры `dmc268-worker` (первый, имя то же, что до масштабирования), `dmc268-worker-2`, `dmc268-worker-3`, `dmc268-worker-4`: один образ, команда, сети, окружение и окно остановки, разные только имя и `service.instance.id`. Все потребляют одну очередь `review_jobs.qq` с `prefetch_count = 1`, поэтому две задачи, пришедшие одновременно, идут параллельно на разных воркерах (`tests/queue/test_worker_replicas.py` на живом брокере); прогон захватывает один воркер, и повторная доставка чужой прогон не трогает (спека `job-queue`).

**Как поднять.** Сверить запас по памяти и соединениям ниже, поменять `TF_VAR_worker_replicas` в `deploy.yml` пул-реквестом. Деплой создаст недостающие экземпляры; при уменьшении снимет последние номера, дав каждому доработать сообщение (`destroy_grace_seconds`). Шаг «Проверить, что воркеры работают» (`check-worker.sh`) находит экземпляры на сервере по имени и ждёт, что их ровно `worker_replicas`, все запущены и 30 с не перезапускаются; иначе деплой падает с хвостом лога каждого. Prometheus при смене числа пересоздаётся: меняется его список ожидаемых экземпляров (`/etc/prometheus/workers.yml`).

**Переход на `for_each`.** До #99 воркер был в состоянии по адресу `docker_container.worker`, теперь — `docker_container.worker["dmc268-worker"]`. Адрес переносится без пересоздания контейнера: блок `moved` в `app.tf`, а на стенде — `tofu state mv` в `infra.sh` до targeted-плана базы и брокера. Targeted-план с непроведённым `moved` OpenTofu не строит («Moved resource instances excluded by targeting»), а `-target` воркера пересоздал бы его новым образом раньше миграций. Перенос срабатывает один раз — пока в состоянии старый адрес; локальному `tofu plan` хватает `moved`. Откат перехода реверт-коммитом после деплоя: в состоянии уже `docker_container.worker["dmc268-worker"]`, а прежняя конфигурация ждёт `docker_container.worker`. План удалил бы один и создал другой с тем же именем, а зависимости между ними нет — создание может упасть на конфликте имени, пока старый воркер дорабатывает сообщение. Поэтому до деплоя реверта адрес возвращают руками (туннель и учётные данные — раздел «Развёртывание и удаление»): `cd infra && tofu state mv 'docker_container.worker["dmc268-worker"]' docker_container.worker`. Экземпляры сверх первого перед этим снимают деплоем с `worker_replicas = 1`.

**Память.** Потолок экземпляра — 512 МБ без свопа, как у единственного воркера. Потолки постоянно живущих контейнеров уже 8160 МБ при 7947 МБ памяти VPS (раздел «Память стека»), и каждый экземпляр сверх первого добавляет 512 МБ: перерасход потолков — 725 МБ при двух воркерах, 1237 МБ при трёх, 1749 МБ при четырёх (потолки на 22 % больше памяти). Перерасход потолков — ещё не нехватка: занято было 2,6 ГБ (2026-11-05), опасен одновременный пик всех контейнеров. Сколько воркер занимает в прогоне, на стенде не замерено. Перед подъёмом — `docker stats --no-stream dmc268-worker` во время прогона и `free -m` (колонка `available`): если пик воркера с запасом, умноженный на число новых экземпляров, не помещается в свободную память, не поднимать. Пятый экземпляр отклоняет проверка переменной.

**Соединения базы.** Пул каждого процесса — до `DB_POOL_SIZE + DB_MAX_OVERFLOW` = 15 соединений (дефолты в `app/config.py`). API и четыре воркера — до 75 из 100 `max_connections` PostgreSQL по умолчанию, три из них оставлены суперпользователю; остальное — миграциям, коллектору под ролью мониторинга и копиям. Пятый воркер съел бы почти весь запас — вторая причина потолка 4.

**Остановка и таймаут деплоя.** Окно остановки у всех экземпляров одно — `local.worker_stop_seconds` (1260 с, с фоллбэком 2460 с), и новый образ apply пересоздаёт их параллельно: `parallelism` OpenTofu по умолчанию — 10, больше потолка 4. Деплой ждёт одно окно, а не по окну на экземпляр, поэтому расчёт `timeout-minutes: 60` у job `deploy` от числа воркеров не зависит.

**Алерты и статус.** Сколько экземпляров должно работать, Prometheus сам не знает, поэтому OpenTofu кладёт ему список: правило записи `dmc268:worker_expected` по ряду на имя (`local.worker_rules` → `/etc/prometheus/workers.yml`; в compose и CI — `observability/workers.yml` с одним `dmc268-worker`). `ContainerDown` горит по каждому ожидаемому экземпляру без ряда метрик контейнера, `ContainerRestarting` и `ContainerMemoryNearLimit` — по каждому контейнеру `dmc268-*`, у последнего `service` без номера экземпляра (`worker`, а не `worker-2`). На странице статуса упавший экземпляр — `degraded`: задачи забирают остальные; `outage` — когда у очереди нет потребителей (`WorkerNotConsuming`). `WorkerStalled` и `ReviewJobStuck` смотрят на очередь целиком: зависший экземпляр среди работающих их не зажжёт, такой прогон доводит до `failed` выметатель через 30 минут, а статус остаётся `operational`. Поэтому пул-реквест, который поднимает `worker_replicas` выше 1, сначала добавляет алерт на зависание по экземпляру (например, по спанам `review.*` или по неподтверждённым сообщениям канала в RabbitMQ). Метрики приложения различает `service.instance.id`; на дашборде занятые соединения и предел пула воркера сложены по экземплярам.

**Локально.** `docker compose up -d --scale worker=2` поднимает два воркера, имена им compose даёт сам (`<проект>-worker-1`, `-2`). `service.instance.id` у обоих — `dmc268-worker` из `OTEL_RESOURCE_ATTRIBUTES`: с экспортом метрик задайте каждому свой, иначе их ряды сольются.

- **Ротация паролей без простоя** (две роли или два пароля с переключением): окно — шаг миграций и начало apply, секунды; без внешних клиентов это допустимо, решение — в change `password-rotation` (#161).

## Смена паролей

Пароль базы и брокера меняется **обычным деплоем**: новый секрет → деплой. Ручной запуск с `allow_stateful_replace` не нужен, база и брокер не пересоздаются.

**Пароль — печатный ASCII без пробела** (`0x21`–`0x7E`); совет — `openssl rand -hex 24`, но и `openssl rand -base64 24` годится. Пароль базы и брокера едет в URL подключения (`DATABASE_URL`, `RABBITMQ_URL` в `locals.tf`, они же `migrate_env`): `+`, `/`, `=`, `@`, `:`, `%`, кавычки и `\` `urlencode` кодирует в `%XX`, и SQLAlchemy (`make_url`) и pika (`URLParameters`) декодируют их верно — проверено на dind сквозь деплой: `a+b/c=d`, `p@ss:w%rd`, `x'y"z\$` и base64 для базы, брокера и `replicator` (`\password`, `passfile` реплики, `PGPASSWORD` копий). Ломаются пробельные символы: пробел `urlencode` пишет как `+`, а SQLAlchemy и pika читают `+` буквально; `rabbitmqctl` обрезает пробелы по краям — шаг был бы зелёным, а API не вошёл бы; перевод строки разрезал бы пароль в stdin. Пустой пароль, пробел, таб, перевод строки и не-ASCII шаг паролей отклоняет `::error::` до изменений на сервере. Пароль `replicator` шаг не проверяет — правило то же.

`POSTGRES_PASSWORD` и `RABBITMQ_DEFAULT_PASS` образы читают только на пустом томе. Поэтому:

- у `docker_container.postgres` и `docker_container.rabbitmq` — `lifecycle { ignore_changes = [env] }`: в их `env` только переменные инициализации тома, правку план не видит, контейнер не пересоздаётся. Переменной, которая действует при каждом старте, в этом `env` не место — её правка не дошла бы до контейнера (сверяет `tests/test_deploy_passwords.py`);
- **смену имён** — `postgres_user`, `postgres_db`, `rabbitmq_user` — `ignore_changes` спрятал бы: шаг сменил бы пароль прежней роли, а API и миграции входили бы новой. Её отклоняет `postcondition` контейнера: при `ignore_changes` `self.env` — окружение, с которым контейнер создан, и plan падает `Resource postcondition failed` до изменений на сервере. Новое имя в заведённом томе не появится и после замены контейнера: это новый том. `postcondition` эту замену не поймает: при ручном запуске с `allow_stateful_replace` новый контейнер берёт `env` из конфига, проверка проходит, а в томе остаются старые имена — имена с таким запуском не меняют. `replace_triggered_by` от `terraform_data` не годится — первое создание такого ресурса тоже повод к замене, и переход на эту конфигурацию пересоздал бы базу (проверено на dind);
- шаг деплоя «Выставить пароли базы и брокера» (`.github/scripts/deploy/passwords.sh`) идёт после проверенного плана и pull образа, до миграций. Он входит новым паролем — в базу по сети, как API (`samenet`, scram), в брокер — `rabbitmqctl authenticate_user`. Вошёл — ничего не меняет, это обычный деплой. Не вошёл — меняет пароль изнутри контейнера: `\password` в `psql` по локальному сокету (`trust` в `postgres/pg_hba.conf`, старый пароль не нужен) и `rabbitmqctl change_password`. Затем входит снова; не вошёл — шаг падает, миграции и apply не идут;
- миграции и полный apply получают новый пароль из `TF_VAR_*`: apply пересоздаёт всех, у кого он в окружении.

Пароль не попадает ни в аргументы команд (их видно в `ps` на сервере), ни в лог шага: он идёт первой строкой stdin `docker exec -i`, дальше — встроенным `printf` в stdin `psql` и `rabbitmqctl`. На сервер PostgreSQL открытый пароль не уходит вовсе: `\password` без tty читает его из stdin и шлёт `ALTER USER … PASSWORD 'SCRAM-SHA-256$…'` — в лог запросов (`log_statement`, `log_min_duration_statement`) и в `pg_stat_activity.query`, которую видит `pg_monitor`, попадает только хеш (проверено на pg18 с `log_statement = all` и `log_min_duration_statement = 0`). Так же теперь и `replication-setup`: `\password replicator` последней строкой `postgres/replication-setup.sql`.

| Секрет | Чей пароль | Кто им входит | Что пересоздаёт apply |
| --- | --- | --- | --- |
| `PG_PASSWORD_DMC268_T1` | роль `dmc268`: владелец базы и суперпользователь кластера (`POSTGRES_USER`) | миграции (`DATABASE_URL` в `migrate_env`), `replication-setup`, `postgres-backup` (`PGPASSWORD`) | `replication-setup`, `postgres-backup` |
| `PG_APP_PASSWORD_DMC268_T1` | роль `dmc268_app`: только DML, без прав на схему (миграция 0023) | `api`, `worker` (`DATABASE_URL`) | `api`, `worker` |
| `RABBITMQ_PASSWORD_DMC268_T1` | пользователь `dmc268` брокера | `api`, `worker` (`RABBITMQ_URL`; у миграций он в окружении, но они в брокер не ходят) | `api`, `worker` |
| `PG_REPLICATION_PASSWORD_DMC268_T1` | роль `replicator` | реплика (`passfile`) | `replication-setup` (он и меняет пароль роли), `postgres-replica` |
| `PG_MONITOR_PASSWORD_DMC268_T1` | роль `dmc268_monitor` | коллектор метрик | `otelcol` |

Проверки реплики (`check-replica.sh`, healthcheck реплики) входят по локальному сокету и пароля не знают.

Пароли ролей `dmc268_app` и `dmc268_monitor` ставит не шаг паролей, а шаг миграций: роли создают миграции 0023 и 0013, и на первом деплое до миграций их ещё нет. После `alembic upgrade head` тем же образом запускается `alembic/role_passwords.py` и сводит оба пароля с секретами (`ALTER ROLE` параметром запроса, на сервер уходит только SCRAM-хеш, `track_utility` выключен той же транзакцией) и снова закрывает `alembic_version` от `dmc268_app`: после `pg_restore --clean` таблица открыта ей по DEFAULT PRIVILEGES. Окно то же: от этого шага до замены API в apply. Упал шаг — summary пишет «миграции применены, пароли ролей не обновлены», apply не идёт. Сменился ли пароль `dmc268_app`, скрипт узнаёт входом этой ролью секретом: не вошла — печатает «`dmc268_app`: … — меняю» до `ALTER ROLE`, и `migrate.sh` пишет `postgres-app` в `passwords-changed` (как `passwords.sh` для `postgres` и `rabbitmq`). Пароль `dmc268_monitor` в summary не попадает.

### Окно смены

Открытые соединения смена пароля не рвёт — ни у PostgreSQL, ни у брокера. Новые соединения со старым паролем отклоняются сразу. Значит, от шага паролей до замены API в полном apply старые API и воркер работают на открытых соединениях, а новое соединение открыть не могут. Это окно: **шаг миграций** (с повторами после `LockNotAvailable` — до 5 мин) **и начало apply до остановки старого API**; после — обычная замена API, как на любом деплое. Pull образа в окно не входит: он — свой шаг «Скачать образ API» до шага паролей.

Поставить шаг паролей после миграций, прямо перед apply, нельзя: миграции входят паролем из `migrate_env`, а он из того же секрета — то есть уже новым. Повторы миграций поэтому остаются внутри окна; обычно это одна попытка в пару секунд.

Репетиция на `docker:29-dind` (Docker 29.9.2, OpenTofu 1.13.2, настоящий образ API с новым digest из реестра, локальное состояние): смена пароля базы — контейнеры `postgres`, `rabbitmq`, `postgres-replica` те же; pull — отдельным шагом до окна; окно 2,7 с от смены пароля до SIGTERM старому API (миграции 1,5 с и начало apply), затем 3,2 с замены API. Последовательные запросы к `/api/v1/auth/me` шли по открытому соединению пула и не падали; из 12 параллельных 6 получили `500` (новое соединение старым паролем). Долгая сессия со старым паролем пережила смену. Брокер — окно 2 с, долгое AMQP-соединение старым паролем живо, новый воркер подключился новым. На стенде окно дольше на ssh до сервера.

Худший случай — **упали миграции** после смены: apply не идёт, и старые API и воркер до следующего деплоя не откроют новых соединений. Тогда — сразу чинить вперёд (ниже, «Откат»). Воркер, который в момент смены дорабатывает сообщение (до 41 мин), живёт на открытых соединениях; понадобится ему новое — это сообщение упадёт.

### Плановая смена

```bash
openssl rand -hex 24 | gh secret set PG_PASSWORD_DMC268_T1      # значение не печатается
gh workflow run deploy.yml --ref develop                         # без allow_stateful_replace
gh run watch "$(gh run list --workflow deploy.yml --limit 1 --json databaseId -q '.[0].databaseId')"
```

Новый секрет до деплоя ни на что не действует: окна нет, пока деплой не дошёл до шага паролей. Для брокера — `RABBITMQ_PASSWORD_DMC268_T1`, для роли приложения — `PG_APP_PASSWORD_DMC268_T1`, для реплики — `PG_REPLICATION_PASSWORD_DMC268_T1`. Несколько секретов можно сменить одним деплоем.

**Перед деплоем** (`ssh stand`) — сохранить адреса старого API, ими потом проверяется, что старый пароль не принимается. Файлы с паролями — с правами 600, после проверки удалить:

```bash
(umask 077; docker exec dmc268-api printenv DATABASE_URL > ~/old-db-url; docker exec dmc268-postgres-backup printenv PGPASSWORD > ~/old-owner-password; docker exec dmc268-api printenv RABBITMQ_URL > ~/old-amqp-url)
```

В `~/old-db-url` — пароль роли приложения `dmc268_app`, в `~/old-owner-password` — владельца `dmc268` (у API его больше нет, он у копий). `$POSTGRES_PASSWORD` и `$RABBITMQ_DEFAULT_PASS` в `env` контейнеров базы и брокера для этого не годятся: там навсегда пароль инициализации тома (`ignore_changes`), а не текущий.

**Что должно быть в деплое.** Шаг «Выставить пароли базы и брокера»: `postgres: пароль роли dmc268 сменён` (или `rabbitmq: … сменён`; у роли приложения — шаг миграций: `dmc268_app: пароль не совпадает с секретом — меняю`); у остальных — «совпадает с секретом». В summary: раздел «Пароли» с тем, что сменено, targeted-план без изменений, в полном — замена `docker_container` (`replication-setup`, `postgres-backup`; для роли приложения — `api` и `worker`; для реплики — `replication-setup` и `postgres-replica`), базу и брокер план не пересоздаёт. Зелёные проверки API, воркера и реплики.

**Проверка после** (`ssh stand`):

```bash
# старый пароль роли приложения не принимается: ждём «password authentication failed»
docker exec -i dmc268-api python -c 'import sys, sqlalchemy as s; s.create_engine(sys.stdin.read().strip()).connect()' < ~/old-db-url 2>&1 | grep -o 'password authentication failed'
# старый пароль владельца не принимается — по сети, как миграции (samenet, scram)
docker exec -i dmc268-postgres sh -c 'IFS= read -r PGPASSWORD; export PGPASSWORD; psql -h dmc268-postgres -U dmc268 -d dmc268 -Xtc "select 1"' < ~/old-owner-password 2>&1 | grep -o 'password authentication failed'
# старый пароль брокера не принимается: ждём ACCESS_REFUSED
docker exec -i dmc268-api python -c 'import sys, pika; pika.BlockingConnection(pika.URLParameters(sys.stdin.read().strip()))' < ~/old-amqp-url 2>&1 | grep -o ACCESS_REFUSED
rm -f ~/old-db-url ~/old-owner-password ~/old-amqp-url
# новые принимаются: API входит своими адресами
docker exec dmc268-api python -c 'import os, sqlalchemy as s; s.create_engine(os.environ["DATABASE_URL"]).connect().close(); print("ok")'
docker exec dmc268-api python -c 'import os, pika; pika.BlockingConnection(pika.URLParameters(os.environ["RABBITMQ_URL"])).close(); print("ok")'
# все соединения роли — новые, открыты после смены
docker exec dmc268-postgres psql -U dmc268 -d dmc268 -XtAc "select application_name, client_addr, backend_start from pg_stat_activity where usename in ('dmc268', 'dmc268_app') and client_addr is not null"
# копии идут новым паролем: первая копия снимается при старте контейнера
docker logs --tail 3 dmc268-postgres-backup
# брокер: воркер подключён после деплоя
docker exec dmc268-rabbitmq rabbitmqctl -q list_connections user peer_host connected_at
# реплика: поток идёт (для replicator)
docker exec dmc268-postgres psql -U dmc268 -d dmc268 -XtAc "select application_name, state from pg_stat_replication"
```

### Откат

Секреты GitHub не читаются, и старого значения взять негде — откат идёт **вперёд**:

- деплой упал после шага паролей (миграции, apply) — summary покажет это в разделе «Пароли»: «пароль сменён, а … не заменены» — API и воркер для роли приложения и брокера, `postgres-backup` и `replication-setup` для владельца `dmc268`. Устранить причину и запустить деплой ещё раз: шаг скажет «совпадает», остальное пройдёт как обычно;
- на первом деплое с ролью приложения summary тоже пишет «Сменены: роль приложения» (у роли ещё не было пароля), но старые API и воркер ходят владельцем: откатывать нечего, деплой просто повторить;
- не устраняется быстро, а старый API должен открывать соединения — вернуть роли `dmc268_app` пароль старого API руками. Он в `~/old-db-url` (не сохранили — `(umask 077; docker exec dmc268-api printenv DATABASE_URL > ~/old-db-url)`: API на стенде ещё старый), но закодирован `urlencode`: `a+b/c=d` там — `a%2Bb%2Fc%3Dd`. Раскодирует его `make_url` SQLAlchemy в контейнере API, и дважды — как спрашивает `\password` — он идёт трубой в psql: ни в аргументы, ни на экран, а на сервер PostgreSQL уходит только SCRAM-хеш:

  ```bash
  docker exec -i dmc268-api python -c 'import sys, sqlalchemy as s; p = s.make_url(sys.stdin.read().strip()).password; print(p); print(p)' < ~/old-db-url \
    | docker exec -i dmc268-postgres psql -XqU dmc268 -d dmc268 -v ON_ERROR_STOP=1 -c '\password dmc268_app'
  ```

  Пароль владельца API и воркер не используют: его откатывают, только если старые копии и `replication-setup` должны войти до следующего деплоя, — из `~/old-owner-password` (там пароль как есть, без `urlencode`):

  ```bash
  cat ~/old-owner-password ~/old-owner-password | docker exec -i dmc268-postgres psql -XqU dmc268 -d dmc268 -v ON_ERROR_STOP=1 -c '\password dmc268'
  ```

  У брокера то же — из `~/old-amqp-url`, раскодирует pika, `rabbitmqctl change_password` без пароля в аргументах читает его из stdin:

  ```bash
  docker exec -i dmc268-api python -c 'import sys, pika; print(pika.URLParameters(sys.stdin.read().strip()).credentials.password)' < ~/old-amqp-url \
    | docker exec -i dmc268-rabbitmq rabbitmqctl -q change_password dmc268
  ```

  Секрет остаётся новым, и следующий деплой сам выставит его снова.

**Реверт этого механизма** (#161) после хотя бы одной смены ломает деплой. Без `ignore_changes = [env]` у базы и брокера план видит, что пароль в их `env` (пароль инициализации тома) не совпадает с секретом, и пересоздаёт контейнеры (`postgres must be replaced`, `rabbitmq must be replaced` — проверено на dind); сторож отклоняет каждый такой деплой, а выход — только ручной запуск с `allow_stateful_replace`, то есть перезапуск базы и брокера. Поэтому при реверте `ignore_changes = [env]` в `infra/postgres.tf` и `infra/rabbitmq.tf` оставляют.

### Пароль утёк

База и брокер портов наружу не публикуют (сеть `dmc268-backend` — `internal`), и войти утёкшим паролем можно только с сервера или из контейнера стека. Но смена — сразу:

1. Сменить секрет и запустить деплой — как в плановой смене. Деплой в очереди (`concurrency: deploy`) ждёт текущий; отменять текущий нельзя — отменённый apply оставляет блокировку состояния.
2. Если деплой сейчас не пройдёт (CI или раннер недоступны) — сменить пароль руками на сервере тем же значением, что в новом секрете: `docker exec -it dmc268-postgres psql -U dmc268 -d dmc268 -c '\password dmc268'` (`\password dmc268_app` — для роли приложения) или `docker exec -it dmc268-rabbitmq rabbitmqctl change_password dmc268`. Старые API и воркер до деплоя новых соединений не откроют — это цена; деплой потом скажет «совпадает».
3. **Закрыть открытые соединения**: смена пароля их не рвёт, и вошедший утёкшим паролем остаётся внутри. После деплоя все свои клиенты пересозданы и подключены заново, поэтому всё, что открыто раньше смены, — чужое или старое:

   ```bash
   docker exec dmc268-postgres psql -U dmc268 -d dmc268 -XtAc "select pg_terminate_backend(pid) from pg_stat_activity where usename = '<роль: dmc268 или dmc268_app>' and client_addr is not null and backend_start < '<время смены, UTC>'"
   docker exec dmc268-rabbitmq rabbitmqctl -q list_connections name user peer_host connected_at
   docker exec dmc268-rabbitmq rabbitmqctl close_connection "<name>" "ротация пароля"
   ```

4. Где ещё лежит прежнее значение: в `env` контейнеров `dmc268-postgres` и `dmc268-rabbitmq` — пароль инициализации тома (`ignore_changes`, после смены не действует) и в состоянии OpenTofu (там все секреты стека — утечка состояния равна утечке всех паролей, их меняют все).

## Стек наблюдаемости

Рядом с API на стенде стоит стек телеметрии из двенадцати контейнеров: OTel Collector
(`dmc268-otelcol`: трейсы, логи, метрики приложения и базы), его второй экземпляр
`dmc268-otelcol-docker` (метрики контейнеров), третий `dmc268-otelcol-logs` (логи postgres, его
реплики и rabbitmq, см. «Логи контейнеров»), Loki (логи), Tempo (трейсы), Prometheus
(метрики), Grafana (интерфейс: публичный вход `:8443/grafana/` и `grafana_port` на `bind_ip`), `node-exporter` (сервер: CPU,
память, диски) и socket-proxy (`dmc268-docker-proxy`: Docker API для `dmc268-otelcol-docker` по
белому списку эндпоинтов вместо маунта `docker.sock`; отдельная сеть `dmc268-docker-proxy`, где
кроме proxy и `dmc268-otelcol-docker` никого), а для алертов — Alertmanager
(`dmc268-alertmanager`, доставка в Telegram) и два экземпляра blackbox-exporter
(`dmc268-blackbox` — пробы сервисов, `dmc268-blackbox-public` — публичного входа); подробно —
«Алерты».
Сеть стека `dmc268-observability` — `internal`, как и сеть данных: из неё в интернет не выйти,
а публикуемый порт Grafana живёт в отдельной не-internal сети `dmc268-grafana` — порты на
internal-сети Docker не публикует. Выход наружу через эту сеть есть только у Grafana, и её
собственные походы наружу выключены env: статистика (`GF_ANALYTICS_REPORTING_ENABLED`),
проверки обновлений Grafana и плагинов (`GF_ANALYTICS_CHECK_FOR_UPDATES`,
`GF_ANALYTICS_CHECK_FOR_PLUGIN_UPDATES`). Локальный compose повторяет раскладку: сеть
`observability` — `internal`, порт Grafana — через отдельную сеть `grafana`.

**Вход в Grafana стенда** — через публичный вход на порту 8443: `https://<VPS_DMC268_IP_T1>:8443/grafana/`
(сейчас https://62.169.24.237:8443/grafana/). Хост и сертификат те же, что у кабинета, но
отдельный порт — это свой origin, и XSS в Grafana не прочитает API кабинета. nginx интерфейса
слушает 8443, проксирует подпуть по сети `dmc268-grafana-proxy`, TLS терминирует он же. Вход только по учётке: анонимный вход и
регистрация выключены, у каждого участника — личная учётка, её заводит админ
(Administration → Users and access → Users → New user). Пароль админа
(`grafana_admin_password`) не раздаётся и для работы не используется. **До заведения учёток —
один раз переименовать `admin`** (Administration → Users and access → Users → `admin` → Edit,
поле Username — неочевидное имя): Grafana блокирует логин после пяти неудачных попыток за
5 минут, и по известному имени `admin` кто угодно держит его заблокированным через форму входа.
`GF_SECURITY_ADMIN_USER` для этого не годится — действует только при создании тома, поэтому
после пересоздания тома `dmc268-grafana-data` шаг повторяют. Env Grafana для публичного входа:
`GF_SERVER_ROOT_URL` — `public_origin`, порт `8443` и `/grafana/` (слеш на конце `public_origin`
отбрасывается; без `public_origin` — относительный `/grafana/`; порт — константа
`local.grafana_public_root_url`, его слушает nginx интерфейса, меняется только вместе с фронтом), `GF_SERVER_SERVE_FROM_SUB_PATH=true`, `GF_SECURITY_COOKIE_SECURE=true` — cookie
сессии только по HTTPS, `GF_METRICS_ENABLED=false` — `/grafana/metrics` иначе отдаётся без входа
(версия, коммит, число пользователей; Prometheus стенда Grafana не опрашивает),
`GF_AUTH_BASIC_ENABLED=false` — запрос с `Authorization: Basic` идёт мимо `limit_req` на
`/grafana/login` и засчитывается в блокировку логина; API-клиентов у Grafana нет. `GF_AUTH_ANONYMOUS_HIDE_VERSION=true` — без входа `/grafana/api/health` и `buildInfo` страницы входа иначе отдают версию и коммит, `GF_METRICS_ENABLED=false` этого не закрывает. `GF_PUBLIC_DASHBOARDS_ENABLED=false` — публичные дашборды в 13.x включены по умолчанию, и Admin или Editor кнопкой «Share externally» открыл бы панели с логами и трейсами без входа. `GF_SNAPSHOTS_ENABLED=false` — снимки (Share → Snapshot) по умолчанию включены, открываются без входа любым по ссылке, а внешние уходят на `snapshots.raintank.io`; `GF_SNAPSHOTS_EXTERNAL_ENABLED=false` — отдельная настройка, без неё кнопка публикации на raintank остаётся. Туннель продолжает работать: `ssh -L 3000:127.0.0.1:3000 <сервер>`, но
адрес теперь с подпутём — http://localhost:3000/grafana/. Корень `http://localhost:3000/`
отвечает 301 на публичный адрес: с `serve_from_sub_path` Grafana отдаёт интерфейс только под
`/grafana/`. Secure-cookie по `http://localhost` браузеры принимают (localhost у них — безопасный
контекст). Grafana сверяет `Origin` изменяющих запросов с `Host`, поэтому nginx передаёт ей
`Host` клиента вместе с портом (`proxy_set_header Host $http_host`), а WebSocket Grafana Live (`/grafana/api/live/`)
проксирует с `Upgrade`/`Connection`. Локальный compose подпуть не включает: публичного входа там
нет, Grafana — в корне без логина.
Белый список — свой шаблон haproxy (`observability/docker-socket-proxy.cfg`), а не
env-переменные образа: `CONTAINERS=1` открывал любой GET под `/containers`, вплоть до чтения
файлов контейнеров через `/archive` (замечание ревью PR #130); в compose шаблон монтируется
по пути, который рендерит entrypoint образа, на стенде заливается тем же `upload`, что и
остальные конфиги.
Метрики базы снимает сам коллектор — receiver `postgresql` (решение #89), отдельного экспортёра
Postgres нет. Конфиги лежат в `observability/` и **те же самые** используются локальным
docker compose (профиль `observability`): различия окружений — только переменные и лимиты, не
конфиги. Образы стека зафиксированы дайджестами (`имя@sha256:…`, дайджест манифест-листа) в
`locals.tf` и в `docker-compose.yml` — одинаково; тег в комментарии рядом, обновление образа —
осознанная замена дайджеста в обоих файлах, с чтением breaking changes.

Конфиги заливаются в контейнеры при создании (`upload` в `docker_container`): tofu читает их из
рабочей копии и передаёт через Docker API, поэтому на сервере не нужен чекаут репозитория. Правка
конфига пересоздаёт контейнер следующим `apply`; если провайдер не заметил изменение содержимого,
контейнер пересоздают явно (`tofu apply -replace=docker_container.otelcol`). Из-за `upload`
коллектор стенда живёт без `read_only` (заливка — запись в rootfs, read-only демон отклоняет
её до всякого пути): вместо неё — `cap_drop ALL` и `no-new-privileges`. Локальный коллектор
read_only: конфиг приходит read-only маунтом. Локально тот же
стек поднимается профилем: `OTEL_TRACES_EXPORTER=otlp OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp docker compose -f docker-compose.yml -f infra/observability/compose.logs.yml
--profile observability up -d` (Grafana — http://127.0.0.1:3000 без логина; второй файл
отправляет логи postgres и rabbitmq в Loki, без него стек поднимается и на podman).

Экспорт телеметрии API, воркера и миграций включён окружением (`local.telemetry_env`): трейсы,
метрики и логи уходят коллектору по OTLP. `service.version` берётся из тега `api_image` (это sha
коммита сборки), окружение задаёт `deployment_environment_name` — `production`, потому что стенд
и есть прод (#97), то же значение шлёт кабинет (#108); `service.instance.id` у каждого сервиса
своё и стабильное (`dmc268-api`, `dmc268-worker`, у миграций — `dmc268-migrations` из выхода
`migrate_env`, локально в compose — `dmc268-migrate`) — вместо случайного UUID на
процесс, который растил бы в Prometheus серии `exported_instance`. Таймаут OTLP — 4 секунды
(`OTEL_EXPORTER_OTLP_TIMEOUT`): Python SDK читает переменную в секундах, вопреки спецификации
OTel с её миллисекундами. Логи сервисов коллектор получает только по OTLP, логи postgres, его
реплики и rabbitmq — от `dmc268-otelcol-logs` («Логи контейнеров»); каталог Docker не читает ни один
коллектор. Чувствительные данные основной коллектор редактирует до отправки
(`observability/otelcol.yaml`), коллектор логов — своими правилами (`observability/otelcol-logs.yaml`);
тест `tests/infrastructure/test_collector_redaction.py`.

### Включение и выключение: observability_enabled

Стек поднимается только по флагу `observability_enabled`, по умолчанию `false`: локальному
`apply` без него хватает памяти, а секреты стека не нужны. Включают переменной окружения
`TF_VAR_observability_enabled=true` — так делает деплой стенда (`deploy.yml`) — или строкой
`observability_enabled = true` в `terraform.tfvars` (пример закомментирован в
`terraform.tfvars.example`); эффект одинаковый.

За флагом идёт всё разом: девять контейнеров стека и их образы, сети стека —
`dmc268-observability`, `dmc268-grafana` и `dmc268-logs` — вместе с сетью socket-proxy
(`count = 1 : 0` у каждого ресурса; `dmc268-grafana-proxy`, как и `dmc268-otlp`, — без флага), `telemetry_env` — `OTEL_*_EXPORTER=otlp`, адрес коллектора
и таймаут в env api, воркера и миграций, — `status_env` — `PROMETHEUS_URL` в env api для страницы
статуса (без флага его нет, и `GET /api/v1/status` отвечает `unknown`), — `command` контейнера Postgres (при флаге база
стартует с `shared_preload_libraries=pg_stat_statements`, без флага — с родным `CMD` образа) и
драйвер логов Postgres, его реплики и RabbitMQ (`fluentd` вместо `json-file`, «Логи контейнеров»). Смена
`command` и драйвера пересоздаёт контейнеры (тома данные сохраняют), поэтому переключение флага —
осознанное действие.

Первый деплой после включения флага требует замены базы, и автоматический деплой её не
сделает — он упадёт. Деплой стенда (`deploy.yml`) включает флаг, поэтому targeted-шаг «Поднять
базу и брокер» видит смену `command` и `dmc268-postgres must be replaced`, а сторож плана
(`.github/scripts/deploy/infra.sh`, `stateful_deletes` в `scripts/deploy_report.py`) такую
замену без `allow_stateful_replace` отклоняет: шаг красный, на сервере ничего не меняется. Первый
выкат после мерджа — ручной запуск
`gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true` (повтор — новым
запуском, не Re-run). Он заменяет `dmc268-postgres` с окном остановки 60 с
(`stop_timeout`/`destroy_grace_seconds`), база поднимается на прежнем томе. Пока длится замена,
старые api и воркер отвечают ошибками базы, а реплика теряет поток и переподключается сама,
когда основной сервер вернётся: том тот же, и слот репликации на нём сохраняется. Пересборка
реплики (`infra/postgres/replica-entrypoint.sh`) идёт только при потерянном слоте. Замену базы провайдер
делает до миграций и до замены api, так что короткий сбой видят только запросы в этот
интервал; следующие планы — `No changes`, и автоматический деплой снова проходит.

Выключение флага снимает контейнеры стека: приложение работает без телеметрии, а с пустым
`telemetry_env` SDK молчит — ни отправки, ни ошибок экспорта в логе. Томам с данными
(Loki, Tempo, Prometheus, Grafana) флаг не грозит: они объявлены без `count` и создаются
всегда, поэтому план с выключенным флагом поверх включённого стенда не пытается их уничтожить
(а `prevent_destroy` не встаёт на пути отката) — логи, метрики и трейсы переживают и
выключение, и повторное включение флага. Выключение, как и первое включение, меняет `command`
у `dmc268-postgres` (preload и `track_utility` идут за флагом), поэтому тоже выкатывается
ручным запуском с `allow_stateful_replace=true`: автоматический деплой упрётся в сторожа. Нюанс:
шаг миграций перегенерирует пароль роли `dmc268_monitor` при каждом деплое независимо от флага,
поэтому выключение стека на существующем стенде без секретов вернёт роли локальный
дефолтный пароль — держите секрет выставленным, пока роль существует.

При `observability_enabled = true` валидации переменных требуют секретов: непустой
`grafana_admin_password` (анонимный вход в Grafana на стенде выключен — без учётки в неё не
зайти) и настоящий `postgres_monitor_password`, не локальный дефолт `dmc268_monitor` (роль
становится входом в базу, открытым в docker-сети). Без секретов `apply` падает на проверке
переменной.

Переменные стека: `observability_enabled` (контейнеры, образы и сети стека — за флагом, см.
выше; тома с данными — нет), `observability_memory_mb`
(потолки памяти без свопа, девять контейнеров — таблица ниже), `grafana_port`, `grafana_admin_password`
(секрет; локально Grafana без логина, на стенде — по учётке), `postgres_monitor_password` (секрет, см.
таблицу выше), `deployment_environment_name`.
Метрики базы коллектор снимает receiver-ом `postgresql`: роль только-чтение `dmc268_monitor` с
`pg_monitor` создаёт миграция 0013, и она же создаёт расширение `pg_stat_statements` — коллектор его
не читает (медленные запросы им не собираются), расширение оставлено только для ручной диагностики;
`shared_preload_libraries` включает контейнер Postgres. RabbitMQ отдаёт метрики встроенным
плагином `rabbitmq_prometheus` (порт 15692 в сети, per-object эндпоинт — метрики очередей с
лейблом `queue`); сервер — `node-exporter` (9100), контейнеры — receiver `docker_stats`
экземпляра `dmc268-otelcol-docker` (`collector-docker:8889`, job `docker-stats`); свои метрики
отдают `dmc268-otelcol`, `dmc268-otelcol-docker` и `dmc268-otelcol-logs` (`otelcol_*` на `:8888`, на хосте не публикуется), Loki и Tempo; все скрейпятся
`prometheus.yml`. Дашборд «Обзор dmc-268» провиженится из репозитория
(`observability/grafana/provisioning/dashboards/`). Применение стека на стенд — задача DevOps
(#108).

### Метрики контейнеров

CPU, память, сеть и диск по каждому контейнеру снимает receiver `docker_stats`: он
спрашивает Docker API (`/containers/{id}/stats`) через socket-proxy, ряды различает лейбл
`container_name`. Белый список proxy — список, inspect, статистика и события контейнеров
(`/events`: без них новые контейнеры не находятся), `/info`, `/version`, `/_ping`; события и
статистика отдают имя, образ, метки, цифры и командные строки `docker exec` — без Env и файлов.
Поэтому секреты в командной строке `docker exec` не передаём (ротация пароля Grafana — через
stdin, см. `grafana_admin_password` в «Деплой»).

Receiver живёт в отдельном экземпляре коллектора `dmc268-otelcol-docker` (тот же образ, конфиг
`observability/otelcol-docker.yaml`), а не в основном `dmc268-otelcol`. Inspect через proxy
отдаёт Env всех контейнеров: ключи S3 бэкапа, пароль репликации, пароли Grafana и брокера.
Основной коллектор разбирает OTLP без аутентификации из сети данных и, через nginx интерфейса,
из интернета (`otlp/browser`); с доступом к proxy ошибка в разборе OTLP стала бы утечкой этих
секретов. У `dmc268-otelcol-docker` входящего OTLP нет, он стоит только в
`dmc268-observability` (оттуда его скрейпит Prometheus) и `dmc268-docker-proxy`. Второй довод —
надёжность: receiver на старте читает список контейнеров и без proxy не даёт подняться
процессу. В отдельном экземпляре сбой proxy гасит только метрики контейнеров, трейсы и логи
идут дальше.

**Почему не cAdvisor (#249).** До #249 метрики контейнеров снимал cAdvisor v0.52.1, и на стенде
он не видел ни одного контейнера: панели «CPU контейнеров» и «Память контейнеров» были пустыми,
в логе — `failed to identify the read-write layer ID` на каждый контейнер. Причина — Docker 29 на
стенде хранит образы в containerd (`docker info`: `driver-type io.containerd.snapshotter.v1`), и
каталога `/var/lib/docker/image/overlayfs/layerdb`, откуда cAdvisor берёт слой контейнера, нет.
Поддержка containerd snapshotter есть в cAdvisor с v0.54 (google/cadvisor#3709), но до последней
v0.60.6 включительно без сокета `/run/containerd/containerd.sock` фабрика docker не регистрируется
вовсе — исправление (google/cadvisor#3910) не смёржено. Сокет containerd — полный доступ к хосту,
а cAdvisor на ревью PR #130 сознательно увели от сокетов, корня хоста и root. Отключать
containerd snapshotter в Docker на стенде — перезапуск демона и перекачка всех образов. Поэтому
cAdvisor убран, а `docker_stats` берёт те же сигналы у Docker API: Docker отдаёт статистику
контейнера как бы ни хранил образы. Чего нет по сравнению с cAdvisor: метрик файловой системы
контейнера, PSI и OOM-событий — в дашборде и алертах их не было.

### Логи контейнеров

У Postgres, его реплики и RabbitMQ нет OTel SDK, поэтому со стеком их stdout забирает сам демон Docker:
драйвер логов `fluentd` (`local.fluentd_log_opts` в `locals.tf`, `logging` в
`observability/compose.logs.yml` для compose) шлёт
каждую строку на `tcp://127.0.0.1:24224`. Там слушает третий экземпляр коллектора
`dmc268-otelcol-logs` (тот же образ, конфиг `observability/otelcol-logs.yaml`): receiver
`fluent_forward`, имя сервиса из тега драйвера (имя контейнера), маскирование и отдача основному
коллектору по OTLP (`collector:4318`), а дальше — общий конвейер логов в Loki:
`{service_name="dmc268-postgres"}`, `{service_name="dmc268-postgres-replica"}`,
`{service_name="dmc268-rabbitmq"}`. Коллектор логов заменяет
маркером `<скрыто>` IPv4-адреса (клиент в начале access-лога nginx, `client:` в его error-логе,
адреса соединений брокера), query в URL (коды OAuth в запросе обратного вызова nginx и в
Referer), пароль в `PASSWORD '…'` и `DETAIL` ошибок Postgres со значениями ключей и строк таблиц (`Key (…)=(…)`,
`Failing row contains`). Пароль роли мониторинга `migrate.sh` и миграция 0013 шлют литералом:
если `ALTER ROLE` упадёт, Postgres запишет запрос в `STATEMENT`, и скрывает пароль только это
правило. IPv6 не маскируется: сети Docker стенда только IPv4. Примеры —
`tests/infrastructure/test_collector_redaction.py`.

Маскирование построчное, поэтому в Loki остаются: текст `ERROR` (например, значение, не
прошедшее приведение типа), прочие `DETAIL` (например, `Token "…" is invalid` у jsonb),
`CONTEXT`, `STATEMENT` (значения параметров psycopg привязывает на сервере, в тексте только
`$N`) и продолжения многострочного значения после `DETAIL`. Пароль скрывается до конца строки:
литерал с `\'` скрыт целиком, а у многострочного скрыта только первая строка.

Почему отдельный экземпляр, а не receiver основного коллектора: публикация порта требует
не-internal сети, а основной коллектор, который принимает трейсы браузера из интернета, стоит
только в internal-сетях и выхода наружу не имеет.

Почему не чтение файлов. В `/var/lib/docker/containers` рядом с логами лежит `config.v2.json` с
Env всех контейнеров (пароли базы, брокера, репликации, Grafana, ключи S3), а Docker API отдаёт
тот же Env через inspect. Поэтому ни файлов, ни Docker API у коллекторов за логами нет: строки
приносит демон, и коллектор логов видит только их. Порт `24224` опубликован лишь на `127.0.0.1`
хоста, к нему подключается демон Docker. Протокол без аутентификации, поэтому извне сервера
порт недоступен; из сети стека доступен, как OTLP основного коллектора. С internal-сети Docker порт не публикует, поэтому коллектор
логов, как Grafana, стоит в отдельной не-internal сети `dmc268-logs` (больше там никого) и в сети
стека — для отдачи основному коллектору; сетей данных и socket-proxy у него нет.

`fluentd-async`: контейнер стартует и пишет и без приёмника — драйвер копит записи в памяти
демона и досылает, когда коллектор логов поднимется; база и брокер от него не зависят. Буфер
— 10 000 записей на контейнер (`fluentd-buffer-limit`; по умолчанию 1 048 576, фактически без
потолка). Записи сверх него в Loki не попадают, а уходят ошибкой `Error writing log message` с
текстом строки в журнал dockerd (не больше 333 в секунду). `docker logs` у них работает через кэш dual
logging Docker с теми же потолками, что у `json-file` (`cache-max-size`, `cache-max-file`). Без стека драйвер — прежний `json-file`. В основном
`docker-compose.yml` драйвера `fluentd` нет: podman его не знает, а без приёмника демон зря
копит буфер. Его включает отдельный файл вместе со стеком:
`docker compose -f docker-compose.yml -f infra/observability/compose.logs.yml --profile
observability up -d`; без файла `docker logs` у postgres и rabbitmq работает как обычно, в Loki
записи не уходят. Реплика PostgreSQL (`dmc268-postgres-replica`) есть только на стенде, в compose
её нет; на стенде она тоже пишет через `fluentd`.

Выкат. Смена драйвера пересоздаёт `dmc268-postgres`, `dmc268-rabbitmq` и
`dmc268-postgres-replica` (тома прежние), и сторож
плана такую замену автоматическим деплоем не пропустит — выкат, как и включение флага выше,
ручным запуском `gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true`.
Targeted-шаг пересоздаёт базу и брокер с окном остановки 60 с до миграций; полный `apply` после
них пересоздаёт реплику (она снова проходит `check-replica.sh`) и поднимает
`dmc268-otelcol-logs`, и накопленные записи уходят в Loki. Пока идёт замена, api и
воркер отвечают ошибками базы и брокера.

Тег драйвера становится `service_name`. В infra это `{{.Name}}`, имя контейнера; в compose
`container_name` нет, и тег в `compose.logs.yml` записан тем же именем, что на стенде.

nginx интерфейса подключается так же в `dmc-268-ui-t1`: у `dmc268-ui` драйвер `fluentd` с теми
же опциями. Правила IP и query рассчитаны на его access- и error-лог по умолчанию и от тега не
зависят (задача 4.7 в `openspec/changes/observability-audit-fixes/tasks.md`).

### Алерты

Критические алерты (#100) считает Prometheus по правилам `observability/alerts.yml` раз в
минуту (`evaluation_interval` не задан, умолчание — 1m; 15 секунд — это `scrape_interval`) и
отдаёт сработавшие Alertmanager (`dmc268-alertmanager`), тот шлёт их в Telegram
(`observability/alertmanager.yml`). Конфиги те же локально и на стенде; токен бота и chat id —
не в конфиге, а файлами `/etc/alertmanager/secrets/telegram_{bot_token,chat_id}`: на стенде их
заливает `upload` из секретов `TELEGRAM_BOT_TOKEN_DMC268_T1` и `TELEGRAM_CHAT_ID_DMC268_T1`,
локально — compose (`configs`) из `ALERT_TELEGRAM_BOT_TOKEN` и `ALERT_TELEGRAM_CHAT_ID`. Сам
стек алертов сторожит внешний heartbeat-сервис («Dead man's switch» ниже). Из
контейнеров алертов наружу ходят только Alertmanager (api.telegram.org и heartbeat) и
`dmc268-blackbox-public` (публичный вход стенда) — через свою не-internal сеть `dmc268-alerting`, портов на хосте у них нет.
Пробы сервисов делает другой экземпляр, `dmc268-blackbox`, — только в сети данных, там же его
скрейпит Prometheus: `/probe?target=` принимает любой URL без авторизации, и экземпляр с
выходом наружу или с путём до `dmc268-blackbox-public` (цепочка
`/probe?target=http://blackbox-public:9115/probe?target=…`) был бы прокси в интернет для
любого контейнера сети данных.

Поведение правил закрепляет `observability/alerts.test.yml`: на каждый алерт — синтетические
ряды «горит / молчит», `promtool test rules` в job `observability-configs`; там же
`amtool check-config` и проверка конфига blackbox. Связи между файлами — имена метрик и пути
секретов — держит `tests/infrastructure/test_alerting.py`.

Те же алерты — источник публичной страницы статуса `GET /api/v1/status`: API по
`PROMETHEUS_URL` (`http://dmc268-prometheus:9090`, сеть данных) читает
`ALERTS{alertstate="firing"}` и сводит их к статусам api, worker и queue. Какие алерты что
значат — таблица `ALERT_RULES` в `app/domain/service_status.py`; переименование алерта, метки
`container_name`/`service` или job скрейпа правится и там — расхождение ловит
`tests/domain/test_service_status.py`.

**Бот и чат.** Бот создаётся у @BotFather (`/newbot`), его добавляют в группу или канал
команды. Chat id — из `https://api.telegram.org/bot<токен>/getUpdates` после любого
сообщения в чате (у групп и каналов он отрицательный, `-100…`). Оба значения —
секретами репозитория (таблица переменных выше). Пока их нет, Alertmanager получает заглушки —
токен `unset` и chat id `0`: правила работают, горящие алерты видны через `amtool alert query`
(ниже), а каждая попытка доставки пишет в его лог `Notify attempt failed … 404`.

**Пороги.** `critical` уходит сразу и повторяется раз в 4 часа, пока горит; `warning` — раз в
12 часов. Критический алерт сервиса глушит его же предупреждения (`inhibit_rules`: та же
метка `service`, у дисков — и `mountpoint`). Погасший алерт присылает сообщение «RESOLVED» (`send_resolved`).

Бюджеты токенов и евро — константы в `alerts.yml` (`dmc268:llm_tokens_budget_month`,
`dmc268:llm_cost_budget_eur_month`), а не переменные: конфиги стека одинаковы в обоих
окружениях. Смена бюджета — правка этой строки и таблицы выше. Расход берётся из
`review_runs.tokens_used` и `review_runs.cost_eur` запросом receiver-а `sqlquery` основного
коллектора под ролью `dmc268_monitor`; ревизии 0017 и 0021 дают ей `SELECT` только на
`created_at`, `tokens_used` и `cost_eur`. Ряда стоимости нет — значит, нет и ряда токенов, и
горит `LlmBudgetUnknown`.

Баланс Eurorouter снимает воркер: `GET /credits` первым ключом не чаще раза в 5 минут, остаток —
`data.total_credits − data.total_usage`. Опрос не удался — в лог одно предупреждение, и до
следующего опроса воркер точку не отдаёт. Коллектор держит последнее значение 5 минут, так что
ряд в Prometheus пропадает, только если опросы не удаются дольше; алерты баланса при этом молчат. Без Eurorouter (`LLM_BACKEND` не
`eurorouter` и фоллбэк выключен) ряда нет совсем.

**Чего алерты не видят.** Статуса healthcheck контейнера у receiver `docker_stats` 0.158 нет
(`container.state.health.status` появился в 0.160), поэтому «unhealthy» ловят пробы
blackbox-exporter по тем же проверкам, а свежесть копий — отметка от `backup.sh`. Падение самого
Prometheus или Alertmanager ловит не правило, а внешний сервис («Dead man's switch» ниже):
`ContainerDown` за `dmc268-prometheus` и `dmc268-alertmanager` не следит, а `ScrapeTargetDown` по
Alertmanager отправлял бы сам упавший Alertmanager. Сломанную доставку в Telegram (токен бота
отозван после ротации, бота убрали из чата) heartbeat не видит: пинг идёт мимо Telegram. Её ловит
`AlertDeliveryFailing` и шлёт тоже мимо Telegram — на `/fail` внешнего check («Dead man's switch»
ниже). Счётчик растёт только на попытке отправки: пока в Telegram ничего не уходит, отозванный
токен не виден до первого настоящего алерта, а без секрета heartbeat этот путь молчит совсем. Поэтому
после смены секретов Telegram и после деплоя, пересоздавшего Alertmanager, нужен тестовый алерт
(«Проверка доставки» ниже). Локально часть алертов
горит всегда: реплики, копий и интерфейса там нет, а контейнеры compose называются по проекту
(`<проект>-api-1`), поэтому `ContainerDown` горит по всем именам `dmc268-*`.

**Dead man's switch** (#334). `Watchdog` горит всегда, и Alertmanager отдельным первым маршрутом
шлёт его не в Telegram, а POST-ом на адрес из секрета `ALERT_HEARTBEAT_URL_DMC268_T1` (файл
`/etc/alertmanager/secrets/heartbeat_url`, `url_file`): сразу и раз в 5–6 минут, пока горит.
Внешний сервис ждёт эти пинги и, когда они пропали, сам шумит в канал команды. Пинги пропадают,
когда:

- остановлен или упал `dmc268-prometheus`: Alertmanager держит его алерты ещё 4 минуты и
  перестаёт;
- остановлен или упал `dmc268-alertmanager`, или у него пропал выход наружу.

**Сломанная доставка в Telegram.** Пинг `Watchdog` идёт мимо Telegram, поэтому отозванный
токен бота или бот, удалённый из канала, heartbeat не видит. Это ловит `AlertDeliveryFailing`:
счётчик неудачных отправок Alertmanager в Telegram вырос за 10 минут. Вторым маршрутом, тоже
мимо Telegram, он уходит POST-ом на тот же check с суффиксом `/fail` (файл
`/etc/alertmanager/secrets/heartbeat_fail_url`, адрес строит деплой из того же секрета).
healthchecks.io по `/fail` сразу переводит check в down и оповещает своим каналом. Пока горит
`AlertDeliveryFailing`, пинг `Watchdog` заглушён (`inhibit_rules`), поэтому check остаётся down до
починки доставки, а не возвращается в up через 5–6 минут. `/fail` повторяется раз в час: check,
вручную возвращённый в up, снова уходит в down. Локально адрес `/fail` compose строит из того же
`ALERT_HEARTBEAT_URL` — задавайте его без завершающего `/`.

Страницу статуса `Watchdog` и `AlertDeliveryFailing` не трогают: их нет в `ALERT_RULES`.

Внешний сервис **необязателен**: без учётки в нём и без секрета стенд и алерты в Telegram работают
как раньше, деплой проходит с предупреждением, а `Watchdog` горит в Alertmanager без пингов. Не
будет только одного — сообщения о том, что лёг сам Prometheus или Alertmanager.

Настройка внешнего сервиса, когда он нужен, на примере healthchecks.io (бесплатного тарифа хватает):

1. Новый check: **Period** 5 минут, **Grace** 10 минут. Пинги приходят раз в 5–6 минут, так что
   ложной тревоги нет, а оповещение — не позже чем через 20 минут после падения (4 минуты, пока
   Alertmanager держит алерт упавшего Prometheus, и 15 — период с запасом).
2. Integrations: оповещение в канал команды — Telegram-интеграция healthchecks.io (свой бот
   сервиса, не наш: наш мог сломаться) или почта.
3. Ping URL (`https://hc-ping.com/<uuid>`) — в секрет `ALERT_HEARTBEAT_URL_DMC268_T1`, затем
   деплой. Адрес — секрет: по нему пинг может прислать кто угодно и скрыть падение.

Подойдёт сервис, который принимает POST на HTTPS-адрес и понимает неуспех по суффиксу `/fail`:
healthchecks.io или Better Stack. Dead Man's Snitch и Cronitor неуспех принимают иначе (параметром,
`?state=fail`): POST на `/fail` у них получит ошибку, а неудачи webhook `AlertDeliveryFailing` не
считает — сломанная доставка снова пройдёт молча. Пока секрета нет, Alertmanager получает заглушку `unset`: пинг раз в 5 минут падает в его
логе (`Notify attempt failed … receiver=heartbeat … unsupported protocol scheme`), а деплой
предупреждает аннотацией прогона. Проверка — остановить Alertmanager и дождаться сообщения
внешнего сервиса:

```bash
ssh stand 'docker stop dmc268-alertmanager'   # не позже чем через 20 минут — сообщение в канале
ssh stand 'docker start dmc268-alertmanager'  # следующий пинг снова делает check зелёным
```

**Проверка доставки.** Тестовый алерт напрямую в Alertmanager стенда, минуя правила:

```bash
ssh stand 'docker exec dmc268-alertmanager amtool alert add alertname=ТестДоставки severity=critical service=test --annotation=summary=Тестовый-алерт --annotation=description=Проверка-доставки-в-Telegram --alertmanager.url=http://127.0.0.1:9093'
```

Сообщение приходит через `group_wait` (30 секунд); не пришло — ошибка доставки в логе
Alertmanager (`Notify attempt failed`, 401 — неверный токен, 400 — неверный chat id или бот не
в чате, 404 — заглушка вместо токена). При сетевой ошибке Alertmanager пишет в лог URL
целиком, **с токеном бота** (`…/bot<токен>/sendMessage`): лог смотрим только с маской и сырым
никуда не вставляем —

```bash
ssh stand 'docker logs dmc268-alertmanager 2>&1' | sed -E 's#/bot[^/]+/#/bot***/#g' | grep -i notify
```
 Горящие алерты и тишины —
`docker exec dmc268-alertmanager amtool alert query --alertmanager.url=http://127.0.0.1:9093`;
заглушить на время работ — `amtool silence add alertname=… --duration=2h …` там же.

| коллектор метрик контейнеров `dmc268-otelcol-docker` | 96 |
| коллектор логов контейнеров `dmc268-otelcol-logs` | 96 |
| Loki | 768 |
| Tempo | 768 |
| Prometheus | 768 |
| Grafana | 1024 |
| node-exporter | 64 |
| socket-proxy | 64 |
| Alertmanager | 64 |
| blackbox-exporter, пробы сервисов | 48 |
| blackbox-exporter, публичный вход | 48 |

Рядом — лимиты контейнеров приложения (`app.tf`, `postgres.tf`, `rabbitmq.tf`, `replica.tf`):
`postgres` 1024, `api`, `worker`, `rabbitmq` и реплика (`postgres_replica_memory`) по 512,
резервные копии (`dmc268-postgres-backup`) 256 — итого 3328 МБ (~3,3 ГБ) постоянно живущих.
Миграции (`docker run` в `migrate.sh` с `--memory 256m`) и одноразовый
`dmc268-replication-setup` (64) — шаги деплоя, в постоянный лимит стенда не входят.
Вне Terraform живут хранилище состояния `dmc268-s3` с потолком 512 МБ (его поднимает
`.github/actions/s3-backend`) и интерфейс `dmc268-ui` со 128 МБ (стек `dmc-268-ui-t1`).
Суммарный потолок стенда — 8160 МБ (~8,0 ГБ) по постоянно живущим контейнерам с одним воркером;
каждый следующий экземпляр (`worker_replicas`) — ещё 512 МБ (раздел «Масштабирование воркеров»).

На VPS 7947 МБ (~7,9 ГБ) памяти и нет свопа (`free -m`): потолки превышают память примерно на
210 МБ, запаса под них нет. Потолок не резерв: через 30 минут после первого выката стека было
занято 2,2 ГБ, 2026-11-05 — 2,6 ГБ, и опасен только одновременный пик всех контейнеров. Grafana
в покое занимает 330–413 МБ, а при открытии трейса в Explore её убивал OOM при потолке 512 МБ
(4 раза за час 2026-11-01, `dmesg`), отсюда 1024. Новый потолок в стеке поднимает риск
одновременного пика: прежде чем поднимать, проверить реальное потребление.

Память стека без нагрузки — по замерам ревью PR #130 (Grafana ~350 МБ, Tempo ~200 МБ, Loki
~90 МБ, коллектор ~85 МБ) и локальному прогону Docker Desktop (2026-10-24: node-exporter
~13 МБ, коллектор ~65 МБ, Prometheus сразу после старта ~170 МБ и растёт
по мере накопления; 2026-10-30: `dmc268-otelcol-docker` на 15 контейнерах ~47 МБ).
Фактическое потребление — ориентир при пересмотре `observability_memory_mb`, а не гарантия
(под нагрузкой Loki и Tempo растут).

### Диск

Диск на стенде один на всё: тома данных стека и PostgreSQL растут на одной файловой системе,
и его объём в README пока не зафиксирован — снять факт можно `df -h /` на сервере.
У `docker_volume` размера нет — потолок задаёт только само приложение, если умеет:

| Что | Потолок | Откуда |
| --- | --- | --- |
| метрики Prometheus | ≤ 8 ГБ и не дольше 30 дней | `--storage.tsdb.retention.size=8GB` и `--storage.tsdb.retention.time=30d` (`observability.tf`, compose) |
| логи Loki | только 30 дней (`retention_period: 720h`), лимита по размеру нет | `observability/loki.yaml` |
| трейсы Tempo | только 14 дней (`block_retention: 336h`), лимита по размеру нет | `observability/tempo.yaml` |
| логи контейнеров (json-file; у postgres, реплики и rabbitmq со стеком — кэш `docker logs` драйвера fluentd) | 30 МБ на контейнер (3 файла × 10 МБ) | `local.log_opts` и `local.fluentd_log_opts` в `locals.tf`, `logging.options` в compose и `observability/compose.logs.yml` |

Единственный компонент с потолком по размеру — Prometheus (8 ГБ): всплеск кардинальности не
забьёт диск раньше срока хранения. У Loki и Tempo такого лимита нет: записи старше срока
хранения удаляются, но суммарный объём под сроком ничем не ограничен. Теоретический потолок
Loki — скорость приёма 1 МБ/с (`ingestion_rate_mb: 1`) ≈ 86 ГБ в сутки: поток сверх лимита
Loki отбрасывает с 429 и долг не копит, но всё принятое до отбрасывания пишет на диск.
Лимита нет, но заполнение ловят алерты по `node_filesystem_avail_bytes` от node-exporter:
`DiskSpaceLow`, `DiskSpaceCritical` и прогноз `DiskWillFillIn24h` (раздел «Алерты»).

Ожидаемые объёмы: под ротацию json-file попадает 13 контейнеров этого стека (4 приложения —
api, worker, копии, replication-setup — и 9 наблюдаемости) — не больше 390 МБ, и ещё
до 90 МБ — кэш `docker logs` у postgres, реплики и rabbitmq. В Loki пишут api, worker,
одноразовый migrate, postgres, реплика и rabbitmq. При допущении «запись в секунду на сервис по 1 КБ» — 6 КБ/с ≈
520 МБ в сутки ≈ 15,5 ГБ за 30 дней на все шесть; индекс TSDB Loki (период 24 ч) и рабочие файлы compactor в оценку не входят.

## Хранилище состояния

Состояние OpenTofu лежит не рядом с конфигурацией, а в S3-совместимом хранилище (RustFS) на том же сервере (`backend.tf`). Так оно переживает прогон раннера GitHub Actions, который исчезает вместе со своим диском.

Хранилище слушает только `127.0.0.1`, поэтому `tofu` любой командой, которой нужно состояние, работает через SSH-туннель:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
```

Учётные данные хранилища передаются как `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`; в CI они приходят из секретов `S3_USER_DMC268_T1` и `S3_PASSWORD_DMC268_T1`. Состояния API и UI лежат в одном бакете `dmc268-tfstate` под разными ключами.

Состояние блокируется на время каждой команды, которая его меняет (`use_lockfile`): OpenTofu кладёт рядом lock-объект условной записью, и второй запуск получает `Error acquiring the state lock` с ID блокировки. Шаги деплоя ждут чужую блокировку до двух минут (`-lock-timeout=2m` у targeted apply, плана и apply), а не падают сразу: так короткий ручной `plan` деплой не роняет. Блокировку, оставленную другим деплоем (`Who` — `runner@…`), снимает следующий деплой сам (раздел «Если деплой упал посреди apply»). Блокировку ручного запуска снимают вручную — только убедившись, что никто больше не работает с состоянием:

```bash
cd infra && tofu force-unlock <ID из ошибки>
```

Сам контейнер хранилища **не входит в этот стек**: его поднимает composite action `.github/actions/s3-backend` шагом job'а деплоя перед `tofu apply`, а не OpenTofu, иначе `apply` мог бы снести хранилище собственного состояния. Практическое следствие: `tofu destroy` его не удалит, и полная зачистка сервера состоит из двух шагов — `tofu destroy` со снятой защитой томов (раздел «Развёртывание и удаление»), а затем `docker rm -f dmc268-s3` и `docker volume rm dmc268-s3-data` вручную.

У контейнера хранилища, как у контейнеров стека, потолок памяти 512 МБ без свопа и ротация логов (три файла по 10 МБ); задаёт их `docker run` в `.github/scripts/render-s3-script.sh`. Контейнер без лимита (созданный до них) action пересоздаёт на том же томе тем же путём, что при смене образа: штатный `stop`, `rm` и новый `run`, состояние в томе переживает замену.

### Шифрование состояния

Состояние и сохранённый план OpenTofu шифрует сам (`infra/encryption.tf`, #147): ключ выводит `key_provider "pbkdf2"` из фразы, шифр — `method "aes_gcm"`. В состоянии лежат значения всех секретов стека — пароли базы, брокера и реплики, ключ GitHub App, секрет вебхука, ключ шифрования токенов, — и без шифрования доступ к бакету открывал бы их все. Теперь в бакете лежит конверт `{encrypted_data, encryption_version, lineage, meta, serial}`: serial и lineage читаются, ресурсы и значения — только с фразой. Зашифрован и `infra/errored.tfstate`, который остаётся на раннере после упавшей записи.

Сейчас идёт шаг 1 из двух: у `state` есть `fallback` на `method "unencrypted"`, чтобы первый деплой прочитал прежнее открытое состояние. Любой `apply` (и `apply -refresh-only`) переписывает его зашифрованным, даже без изменений; `plan` — нет. У `plan` `fallback` нет: план создаётся и применяется в одном job'е, старых открытых планов не бывает. Шаг 2 — `enforced = true` без `fallback` у `state` и удаление старых открытых версий объекта в бакете (задачи — `openspec/changes/tfstate-encryption/tasks.md`).

**Где фраза.** Секрет `STATE_PASSPHRASE_DMC268_T1` в environment `stand`; деплой передаёт его как `TF_VAR_state_passphrase` всем шагам `tofu` и восстановлению. Не короче 16 символов (проверка переменной). Копия фразы **обязательно** хранится вне GitHub — секрет GitHub обратно не прочитать, а без фразы состояние не открыть. Поэтому фраза сначала сохраняется вне GitHub, а секрет ставится из той же переменной:

```bash
P=$(openssl rand -base64 48)     # сохранить P вне GitHub, потом:
printf %s "$P" | gh secret set STATE_PASSPHRASE_DMC268_T1 --env stand
```

Копию проверить после первого деплоя с шифрованием (или ротации), когда объект в бакете уже зашифрован. Фразу — отдельным `export`: префикс `VAR=… cmd1 && cmd2` доходит только до первой команды, и `state pull` взял бы фразу, экспортированную раньше в той же оболочке (раздел «Локально»), — проверка прошла бы на неверной копии:

```bash
export TF_VAR_state_passphrase=<копия>
cd infra && tofu init && tofu state pull | jq .serial
```

Раньше проверка ничего не значит — открытое состояние `fallback` читает с любой фразой. Резервную копию состояния (`tofu state pull > backup`) удалять только после этой проверки.

**Локально.** Фраза нужна уже `tofu init` с настоящим бэкендом — без неё он падает: «depends on var.state_passphrase which is not available»:

```bash
export TF_VAR_state_passphrase=<фраза>
cd infra && tofu init && tofu plan
```

Проверке конфигурации без состояния (`tofu init -backend=false`, `tofu validate`) фраза не нужна, `tofu test` берёт фиктивную из `tests/*.tftest.hcl`. Неверная фраза роняет команду с ошибкой расшифровки, состояние при этом не меняется.

**Проверить, что объект в бакете зашифрован** (туннель и учётные данные — как в разделе «Развёртывание и удаление»):

```bash
aws s3 cp s3://dmc268-tfstate/api/terraform.tfstate - --endpoint-url http://127.0.0.1:9000 | jq 'keys'
```

Зашифрованное — в ключах есть `encrypted_data`, а `resources` нет. Видно `resources` — состояние открыто: после шага 1 так бывает только до первого деплоя.

**Ротация фразы.** Существующие `key_provider` и `method` не переименовывать: документация OpenTofu предупреждает, что переименованный провайдер или метод не откроет уже зашифрованное состояние.

1. Добавить в `encryption.tf` новый `key_provider "pbkdf2"` с новым именем и новой переменной фразы и новый `method "aes_gcm"` на нём; у `state` и `plan` основным поставить новый метод, прежний `aes_gcm` — в `fallback`. `fallback` в блоке один и метод в нём один (второй блок — «Duplicate fallback block», список — «Invalid expression»), поэтому, пока идёт шаг 1, `unencrypted` у `state` уходит во вложенный `fallback`; у `plan` — только прежний `aes_gcm`:

   ```hcl
   state {
     method = method.aes_gcm.next
     fallback {
       method = method.aes_gcm.main
       fallback {
         method = method.unencrypted.legacy # только пока идёт шаг 1
       }
     }
   }
   plan {
     method = method.aes_gcm.next
     fallback {
       method = method.aes_gcm.main
     }
   }
   ```

   Проверено на OpenTofu 1.13.8 с локальным бэкендом: состояние, зашифрованное прежней фразой, и открытое — оба читаются, `apply` переписывает их новой; без вложенного `fallback` открытое не читается («encountered unencrypted payload without unencrypted method configured»).
2. Завести новый секрет, передать его в `deploy.yml`, выкатить: `apply` перешифрует состояние новым ключом. Фразу в `deploy.yml` читают три `env`: якорь `&tofu-env`, шаг миграций (`migrate.sh` — `tofu output`) и шаг «Восстановить состояние OpenTofu»; два последних якорем не пользуются. Новая переменная — во все три, иначе миграции и расшифровка при восстановлении упадут на «not available».
3. Проверить объект в бакете (выше) и следующим пул-реквестом убрать прежние провайдер, метод, переменную (из всех трёх `env` `deploy.yml`) и секрет. Копию новой фразы — вне GitHub, как и прежней.

**Откат.** Revert пул-реквеста с шифрованием ломает каждый деплой: состояние в бакете уже зашифровано, и без блока `encryption` `tofu init` и `plan` падают с «This state file is encrypted and can not be read without an encryption configuration». Откатывать — в обратную сторону, с той же фразой в секрете:

1. Пул-реквест, где в `encryption.tf` `state` пишет открыто и читает зашифрованное, а `plan` — открытый:

   ```hcl
   state {
     method = method.unencrypted.legacy
     fallback {
       method = method.aes_gcm.main
     }
   }
   plan {
     method = method.unencrypted.legacy
   }
   ```

   Выкатить: `apply` (и `apply -refresh-only`) переписывает состояние открытым, даже без изменений.
2. Проверить объект в бакете (выше): в `jq 'keys'` есть `resources`, `encrypted_data` нет.
3. Только после этого следующим пул-реквестом удалить `encryption.tf` и `TF_VAR_state_passphrase` из всех трёх `env` `deploy.yml` (якорь `&tofu-env`, шаг миграций, шаг «Восстановить состояние OpenTofu»), затем секрет. Тем же пул-реквестом убрать расшифровку в `.github/scripts/deploy/recover-state.sh` — она безусловно копирует `infra/encryption.tf`, и без файла любой обрыв apply кончится «не скопировать для расшифровки»: вернуть прямой `tofu state push` с `errored.tfstate`, убрать её тесты в `tests/test_deploy_recovery.py` и шаг расшифровки из ручного восстановления ниже.

Проверено на OpenTofu 1.13.8 с локальным бэкендом: зашифрованное состояние после такого `apply` — открытый JSON с `resources`, и `plan` без блока `encryption` проходит.

**Если фраза потеряна,** состояние не восстановить: ключ из него не достать. Остаётся резервная копия, снятая раньше (`tofu state pull > backup` с фразой; файл открытый — хранить вне репозитория и как секрет), либо пересборка состояния: пустое состояние под новой фразой и `tofu import` каждого ресурса стека (`docker_container.*`, `docker_volume.*`, `docker_network.*`, `docker_image.*`). Тома на сервере при этом не трогаются, но это долгая ручная работа — поэтому копия фразы вне GitHub обязательна.

**Восстановление после обрыва.** `errored.tfstate` теперь зашифрован, а `tofu state push` зашифрованный файл не читает («This state file is encrypted and can not be read without an encryption configuration»; `TF_ENCRYPTION` не помогает). Поэтому `recover-state.sh` сначала расшифровывает его во временном каталоге — копии `encryption.tf` и `.terraform.lock.hcl`, файл как локальный `terraform.tfstate`, `tofu init -plugin-dir` с провайдерами из `infra/.terraform/providers` (без скачивания из реестра), `tofu state pull` — в открытый временный файл (`umask 077`, удаляется на выходе), сверяет с хранилищем и записывает его. Push шифрует, в бакет открытое не попадает. Руками — шаг 3 следующего раздела.

### Если деплой упал посреди apply

Самый дорогой сбой деплоя — пропавшая связь с хранилищем, пока OpenTofu пишет состояние. Что делает OpenTofu 1.13.2 (проверено на `docker:29-dind` с RustFS 1.0.3): промежуточная запись состояния падает, и apply останавливается, не трогая оставшиеся ресурсы; несохранённое состояние ложится в `infra/errored.tfstate` на раннере и исчезает вместе с ним; блокировка не снимается — объект `api/terraform.tfstate.tflock` остаётся в бакете, а её ID в выводе apply нет, он есть только в самом объекте. Следующий деплой упирается в блокировку, а после `force-unlock` — в старое состояние: план создаёт заново контейнеры, которые apply уже создал, и падает на `Conflict. The container name "/dmc268-api" is already in use`.

Деплой чинит это сам. Шаг `Восстановить состояние OpenTofu` (`.github/scripts/deploy/recover-state.sh`) идёт, если упал или оборван (отмена, таймаут job'а) шаг, который пишет состояние или держит блокировку (`Поднять базу и брокер`, план, apply): заново открывает туннель, ждёт хранилище до двух минут, сверяет `errored.tfstate` с состоянием в хранилище, записывает его (`tofu state push` под той же блокировкой, без `-force`) и снимает блокировку этого раннера. Оборванная запись оставляет в хранилище ту же линию (lineage) и serial меньше нашего; другую линию или serial не меньше нашего скрипт не перетирает: сам `state push` без `-force` отказывает, только если линия другая или наш serial меньше, а с тем же serial перетёр бы чужую запись. Итог — раздел «Состояние OpenTofu» в summary; если состояние не пострадало и восстанавливать нечего (например, шаг упал на стороже базы в `infra.sh`), раздела нет. После этого достаточно перезапустить деплой («Re-run failed jobs»): он доделает выкат. Исключение — запуск с `allow_stateful_replace`: Re-run флага не получает, и доделывает выкат новый `gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true` — так и пишет summary.

Блокировку другого раннера (`Who` — `runner@…`) восстановление тоже снимает: деплои идут строго по одному (`concurrency: deploy`), и её оставил запуск, который уже кончился, — иначе в неё упирался бы каждый следующий деплой. Так же снимается своя блокировка, если шаг оборвали: убитый tofu `errored.tfstate` не пишет. Записалось ли состояние под такой блокировкой, неизвестно: у блокировки apply в summary — предупреждение, что состояние может быть старше стенда; если план перезапуска создаёт контейнеры, которые на сервере уже есть, — шаг 4 ниже. Блокировку ручного `tofu` (`Who` — `пользователь@хост`) деплой не трогает никогда.

Если восстановление не вышло, а `errored.tfstate` был, его копия, зашифрованная отдельным случайным ключом (секрет `STATE_BACKUP_KEY_DMC268_T1`, `openssl rand -base64 48`; не пароль хранилища — он открывал бы состояние каждому, кто знает пароль; тем же ключом шифруются копии базы вне сервера, раздел «Копии вне сервера»), уходит артефактом `errored-tfstate` прогона на сутки. Открытым текстом состояние не загружается: в нём пароли, а репозиторий публичный.

Зависшее хранилище (соединение живо, ответа нет) ловит сторож туннеля `.github/scripts/s3-watchdog.sh`: таймаута запроса у s3-бэкенда OpenTofu нет, и без него запись состояния висела бы до таймаута job'а. Через две минуты без ответа сторож закрывает туннель, apply падает с `errored.tfstate`, и дальше — то же восстановление.

Если в summary «Состояние не восстановлено», причина — там же. Руками, убедившись, что никто больше не работает с состоянием (нет идущего деплоя, ручного `apply`):

1. Туннель и учётные данные — как в разделе «Развёртывание и удаление».
2. Посмотреть блокировку: `aws --endpoint-url http://127.0.0.1:9000 s3 cp s3://dmc268-tfstate/api/terraform.tfstate.tflock -` — `ID`, кто (`Who`) и когда (`Created`) её взял.
3. Если `errored.tfstate` есть — артефакт `errored-tfstate` прогона (сутки): `gh run download <id прогона> -n errored-tfstate`, затем `STATE_BACKUP_KEY=… openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -pass env:STATE_BACKUP_KEY -in errored.tfstate.enc -out infra/errored.tfstate`. Сверить с хранилищем: `tofu state pull | jq '.lineage, .serial'` — линия та же, serial меньше, чем в файле (`jq '.lineage, .serial' infra/errored.tfstate`: в зашифрованном конверте оба поля открыты), иначе в хранилище запись после нашей, и файл не нужен. Файл зашифрован OpenTofu, и `tofu state push` его не прочитает — сначала расшифровать во временном каталоге (нужна фраза, раздел «Шифрование состояния»):

   ```bash
   export TF_VAR_state_passphrase=<фраза>
   (cd infra && tofu init)   # провайдеры — в infra/.terraform/providers
   tmp="$(mktemp -d)" && cp infra/encryption.tf infra/.terraform.lock.hcl "$tmp/" && cp infra/errored.tfstate "$tmp/terraform.tfstate"
   (umask 077 && tofu -chdir="$tmp" init -plugin-dir="$PWD/infra/.terraform/providers" && tofu -chdir="$tmp" state pull > "$tmp/plain.tfstate")
   ```

   Записать открытый файл, пока блокировка висит; не перетирать `-force`: `cd infra && tofu state push -lock=false "$tmp/plain.tfstate"` — push шифрует, в бакет ляжет зашифрованное. После записи удалить и `errored.tfstate`, и временный каталог с открытым файлом: `rm -rf "$tmp" infra/errored.tfstate`.
4. Если файла нет, состояние в хранилище старше стенда. `tofu plan` покажет, что он хочет создать заново: контейнеры, которые на сервере уже есть, либо удалить с сервера (`ssh <сервер> 'docker rm -f dmc268-api $(docker ps -aq --filter name=dmc268-worker)'` — следующий деплой создаст их, это короткий простой стенда), либо взять в состояние: `tofu state rm docker_container.api` и `tofu import docker_container.api <id контейнера>`. Тома (`docker_volume.postgres`, `docker_volume.rabbitmq`) не трогать: их защищает `prevent_destroy`, и план с их заменой не пройдёт.
5. Снять блокировку: `tofu force-unlock <ID>` и перезапустить деплой.

## Развёртывание и удаление

Штатный путь один: **мерж в `develop`**. Дальше всё делает `deploy.yml` — собирает образ, поднимает хранилище состояния, базу и брокер, применяет миграции и конфигурацию, проверяет `/health` и что воркеры работают. Руками ничего запускать не нужно и, как правило, не получится.

Локальный запуск перестал быть самодостаточным с появлением `backend.tf`: состояние лежит в хранилище на сервере, поэтому любая команда, которой нужно состояние, требует открытого туннеля и учётных данных хранилища:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
export AWS_ACCESS_KEY_ID=<логин хранилища> AWS_SECRET_ACCESS_KEY=<пароль> AWS_DEFAULT_REGION=us-east-1
export TF_VAR_state_passphrase=<фраза шифрования состояния>
cd infra && tofu init && tofu plan
```

Ключ и учётные данные лежат в секретах GitHub и наружу не отдаются, так что у большинства их не будет — и это нормально: чтобы разрабатывать, разворачивать стенд не нужно, достаточно `docker compose up` из корня репозитория.

Проверить конфигурацию без доступа к состоянию можно всегда — то же делает job `opentofu` в `ci.yml`:

```bash
cd infra && tofu fmt -check -recursive && tofu init -backend=false && tofu validate && tofu test
```

`tofu test` гоняет `tests/*.tftest.hcl` с `mock_provider "docker"`: ни Docker, ни сервер не нужны. Тесты проверяют адреса базы и брокера в окружении контейнеров и в `migrate_env` (api и worker — ролью `dmc268_app`, миграции — владельцем), какие секреты получает какой контейнер, раскладку по сетям и порты, грейс-период воркера и штатную остановку базы, реплики и брокера, образ `api` и `worker` по digest без тега, `wait` у базы и брокера, ожидание `healthy` у API и формат длительностей его healthcheck, проверки переменных. Проверки отклоняют на `plan`, пока сервер не тронут: пустые `github_webhook_secret`, `postgres_password`, `rabbitmq_password`, пустой или короткий `postgres_replication_password`, пустой, короткий или с пробелом `postgres_app_password` (незаданный секрет CI приходит пустой строкой), `llm_backend = "ollama"` без `ollama_model`, `llm_hosted_fallback` без `ollama` и всех `eurorouter_*`, `api_image` без digest.

`tofu destroy` **падает на томах** базы, брокера, реплики и копий: у них `prevent_destroy = true`, и OpenTofu отказывается строить план, который их уничтожает. Удалить стенд осознанно — с данными — можно, только сняв защиту: заменить `prevent_destroy = true` на `false` в `postgres.tf`, `rabbitmq.tf` и `replica.tf` локально (не в коммите), затем `tofu destroy`. Без этого `tofu destroy` не тронет ничего: ошибка — до изменений. Контейнер хранилища состояния `tofu destroy` не удаляет и так — он не входит в этот стек намеренно. Полная зачистка описана выше, в разделе «Хранилище состояния».

Этот стек только для API. UI деплоится отдельно из `dmc-268-ui-t1/infra/`.
