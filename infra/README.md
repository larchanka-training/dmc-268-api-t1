# Стек сервера (API на Python 3.14, PostgreSQL 18, RabbitMQ 4.4)

Нужны **Docker Engine** на целевом хосте и OpenTofu >= 1.13 (в CI ставится 1.13.2). Образ API не собирается здесь: он публикуется в ghcr из CI и запускается по digest (`api_image` — `<репозиторий>:<commit sha>@sha256:<digest>`; ссылка без digest не проходит проверку переменной).

## Раскладка файлов

Конфигурация разложена по доменам; OpenTofu читает все `*.tf` каталога как один модуль, так что адреса ресурсов от файла не зависят.

| Файл | Что внутри |
| --- | --- |
| `versions.tf` | версия OpenTofu, провайдер `kreuzwerker/docker` и его настройки (хост Docker) |
| `backend.tf` | хранилище состояния (S3 на сервере) |
| `locals.tf` | общие значения: ротация логов, окружение процессов приложения, грейс-период воркера |
| `network.tf` | сеть `dmc268`, общая со стеком `dmc-268-ui-t1` |
| `postgres.tf` | образ, том и контейнер PostgreSQL |
| `rabbitmq.tf` | образ, том и контейнер RabbitMQ |
| `app.tf` | контейнеры `api`, `worker` из образа API по digest |
| `variables.tf` | входные переменные, по секциям тех же доменов |
| `outputs.tf` | выходы: `migrate_env` — окружение миграций для шага деплоя |
| `tests/*.tftest.hcl` | `tofu test` с mock-провайдером |

## Почему OpenTofu, а не Terraform

Terraform с версии 1.6 распространяется под Business Source License (BUSL) — она не open source, и условия дополнительного разрешения HashiCorp на использование размыты. OpenTofu — форк последней открытой версии под Mozilla Public License 2.0, проект Linux Foundation. Провайдеры у него те же, что у Terraform (своих OpenTofu не пишет), а берутся из собственного реестра `registry.opentofu.org`: `kreuzwerker/docker` работает без изменений. Сверх Terraform OpenTofu умеет шифровать состояние и план на диске и в бэкенде (с 1.7); у нас шифрование пока не включено — состояние лежит в хранилище на петле сервера, доступном только через SSH-туннель.

## Локальный или удалённый Docker

Скопируйте `terraform.tfvars.example` в `terraform.tfvars` и замените плейсхолдеры `CHANGE_ME_*`. Файл `terraform.tfvars` не коммитится (gitignore).

- Локальный демон: `docker_host = "unix:///var/run/docker.sock"` (у Docker Desktop на macOS часто `unix:///Users/<вы>/.docker/run/docker.sock`).
- Удалённый сервер: `docker_host = "ssh://user@server"` (нужны SSH-доступ и Docker на удалённом хосте).

Образ API перед `apply` скачивают на тот же Docker сами: `docker pull <api_image>` (с `DOCKER_HOST`, если демон удалённый; для приватного пакета — после `docker login ghcr.io`). Провайдер создаёт `api` и `worker` из уже скачанного образа, а если его нет — тянет сам, но без учётных данных, и на приватном пакете `apply` падает с `denied`.

PostgreSQL и RabbitMQ публикуются на `internal_bind_ip`, API — на `bind_ip`; в деплое оба равны `127.0.0.1`. Другого значения конфигурация не примет: обе переменные проверяются на адрес петли (`127.0.0.0/8` или `::1`), и ошибка всплывает на `plan`.

## Ограничения контейнеров

- `api`, `worker` и миграции работают не от root (`USER` в `Dockerfile`), с файловой системой только для чтения (запись — только в `/tmp`), без capabilities и с `no-new-privileges`. У миграций это флаги `docker run` в `.github/scripts/deploy/migrate.sh`.
- `postgres` и `rabbitmq` — только `no-new-privileges`: их entrypoint стартует от root, чтобы подготовить каталог данных, и сам переходит на служебного пользователя.
- У каждого контейнера потолок памяти без свопа (`postgres` 1 ГБ, `rabbitmq`, `api` и `worker` по 512 МБ, миграции 256 МБ) и ротация логов: три файла по 10 МБ.

Смена любого из этих атрибутов пересоздаёт контейнер. Данные PostgreSQL и RabbitMQ лежат в томах и замену переживают.

## Версия провайдера

Точная версия `kreuzwerker/docker` и её хэши закреплены в `.terraform.lock.hcl`, файл коммитится. После смены `version` в `versions.tf` его пересобирают на все платформы команды, иначе `tofu init` на неперечисленной системе допишет в файл свои хэши и оставит изменение в рабочей копии:

```bash
cd infra && tofu init -backend=false -upgrade && tofu providers lock \
  -platform=linux_amd64 -platform=linux_arm64 \
  -platform=darwin_amd64 -platform=darwin_arm64 \
  -platform=windows_amd64
```

## Деплой

Стенд катится сам при мерже в `develop` (`.github/workflows/deploy.yml`). `main` в деплое не участвует: сервер один, и два источника дрались бы за него.

Порядок такой: образ собирается и публикуется в `ghcr.io/larchanka-training/dmc-268-api-t1` с тегом по commit sha → сверка, что коммит всё ещё вершина `develop` (`check-tip.sh`) → поднимается хранилище состояния и туннель к нему → `tofu apply -target` для сети, базы и брокера → план полного выката в файл и сторож томов (`plan.sh`) → миграции (`.github/scripts/deploy/migrate.sh`) → `tofu apply` этого плана (`apply.sh`) → проверка `/health` через туннель и проверка воркера → уборка образов → summary (`summary.sh`). Если упал шаг, который пишет состояние, между apply и проверками идёт восстановление состояния (раздел «Если деплой упал посреди apply»).

**Устаревший коммит не катится.** `gate` сверяет коммит с вершиной `develop`, но только у `workflow_run` и только при своём запуске, а «Re-run failed jobs» успешный `gate` не перезапускает и берёт его выход `sha` из первой попытки. Поэтому первым шагом после checkout job `deploy` сверяет коммит ещё раз (`check-tip.sh`) — и для ручного запуска тоже: вершина ушла — остальные шаги пропускаются, job зелёный, в summary «пропущен: вершина develop уже …». Перезапуск упавшего деплоя, пока за ним не пришёл новый коммит, катит как обычно. Публичной проверки здесь нет: API снаружи не публикуется, а его доступность по `https://62.169.24.237/api/v1/` проверяет деплой интерфейса.

**Снаружи API адресуется через интерфейс, с исходным путём.** Публичный вход — `nginx` в контейнере фронтенда на **https://62.169.24.237** (сертификат Let's Encrypt на IP, HTTP перенаправляется на HTTPS; устройство — в `infra/README.md` репозитория `dmc-268-ui-t1`). Префикс он не трогает: браузерный `GET /api/v1/reviews` приходит сюда как `GET /api/v1/reviews`, поэтому роутеры монтируются на `/api/v1`, как требует контракт API. `/health` через этот вход не публикуется — проверка живости ходит мимо него.

**Тома данных деплой не уничтожает.** У `docker_volume.postgres` и `docker_volume.rabbitmq` — `lifecycle { prevent_destroy = true }`: план, который уничтожает или заменяет том, OpenTofu отклоняет до изменений на сервере с `Error: Resource instance cannot be destroyed`. Это действует и на targeted apply шага «Поднять базу и брокер» — `-target=docker_container.postgres` тянет том зависимостью, и сторож полного плана такую замену уже не увидел бы. Полный выкат идёт планом в файл: `plan.sh` строит `tofu plan -out=tfplan` сразу после targeted apply, и `scripts/deploy_report.py` по `tofu show -json` дублирует проверку для summary — падает, если план уничтожает или заменяет защищённый том, и apply не запускается. Миграции идут между планом и apply: состояние они не трогают, план не устаревает. Применяется ровно проверенный план (`apply.sh`); если до него не дошло, файл плана удаляет `summary.sh`. Сменить том, как при смене сборки PostgreSQL или версии RabbitMQ, — новым ресурсом с новым адресом (с `prevent_destroy`, и его адрес — в `PROTECTED` сторожа; то и другое сверяет тест), а прежний снять с учёта блоком `removed { lifecycle { destroy = false } }`: план выйдет `forget` и `create`, старый том с данными останется на сервере до ручного `docker volume rm`. В плане и его JSON пароли лежат открытым текстом: JSON идёт только трубой, файл плана удаляется после apply и артефактом не загружается, обёртка `setup-opentofu`, копирующая stdout tofu в выходы шага, выключена.

**Summary деплоя** пишет `summary.sh` на любом исходе: шаг падения, простой API с разбивкой (SIGTERM старому → выход → `Created` нового → `State.StartedAt` → событие `health_status: healthy` нового; всё, кроме `Created` и `StartedAt`, — из событий Docker, которые `apply.sh` читает потоком всё время apply. `State.Health.Log` — запасной путь, если событий нового контейнера нет: журнал держит пять последних проверок, и после долгого apply первой успешной в нём уже нет — summary тогда помечает простой как недостоверный), план по типам ресурсов, применённые миграции, свободное место на `/` и в каталоге Docker после уборки и длительность шагов — по засечкам `mark.sh`, без `actions: read` у токена. Подписи значений — ключи OpenTelemetry (`cicd.pipeline.*`, `container.image.*`, `system.filesystem.*`), свои — в `dmc268.deploy.*`.

**Миграции — шаг деплоя до полного `apply`, а не контейнер стека.** Шаг `Применить миграции` запускает `.github/scripts/deploy/migrate.sh`: одноразовый `docker run --rm` того же образа (тот же digest), что сейчас выкатится, с `alembic upgrade head` — на сервере через `DOCKER_HOST=ssh://stand`, в сети `dmc268`. Окружение — выход `migrate_env` (`outputs.tf`): те же строки `local.app_env`, что у `api` и `worker`, через env-файл с правами 600, который удаляется после запуска. Упала миграция — шаг падает, полный `apply` не запускается, на стенде остаётся прежняя версия. Проверка `/health` этого не заметила бы: по контракту она отвечает независимо от базы.

Пока идут миграции, работает старый код: ломающая миграция (удаление или переименование колонки, которую он читает) даст на стенде короткий сбой во время выката. Пока нет пользователей, это допустимо; для прода — expand/contract в два деплоя (скилл `.agents/skills/alembic-migration`).

Образ лежит в приватном пакете: перед миграциями job входит в `ghcr.io` на раннере (`docker/login-action`, `GITHUB_TOKEN` с `packages: read`), и docker CLI передаёт учётные данные демону сервера вместе с запросом pull. На сервере токен не остаётся. Этот pull в `migrate.sh` — единственный для образа API: учётных данных реестра у провайдера нет, и `api` с `worker` он создаёт из уже скачанного образа.

**Чистый сервер.** База и брокер должны существовать до миграций, поэтому перед ними каждый деплой выполняет

```bash
tofu apply -target=docker_network.dmc268 -target=docker_container.postgres -target=docker_container.rabbitmq
```

На живом стенде это `No changes` и ожидаемое предупреждение OpenTofu о `-target`; на чистом — создание сети, томов, базы и брокера. У `postgres` `wait = true`: apply возвращается, когда healthcheck зелёный, и миграциям не нужен цикл повторов. Этот же apply обновляет в состоянии выход `migrate_env`: выход зависит от контейнеров базы и брокера (хосты в `local.app_env` — ссылки на них), а выход, не зависящий от целевых ресурсов, targeted apply не записывает. Руками ничего делать не нужно: первый деплой на пустой сервер проходит тем же путём (проверено на чистом локальном Docker 29.9.2).

**Контейнер `dmc268-migrate`** жил в стеке до #159. Блок `removed` в `app.tf` снимает его с учёта без уничтожения, а `migrate.sh` удаляет остановленный контейнер на сервере: его старые логи и код выхода легко принять за текущие, и он держит прежний образ.

**Образ API — без ресурса `docker_image`.** `api` и `worker` ссылаются на образ строкой `<репозиторий>@sha256:<digest>` — `local.api_image_ref` в `app.tf`, тег из `api_image` срезан. Ресурс образа пересоздавался на каждом коммите (тег — commit sha) уже после остановки старого API, и его pull добавлял к простою 6 с (деплой #202). Тег в ссылке контейнера дал бы то же: провайдер сравнивает `image` строкой и пересоздаёт контейнер, даже если digest не изменился. Теперь контейнеры меняются, только когда меняется digest; `docker ps` показывает репозиторий без тега, commit sha — в summary деплоя. Замена API не ждёт воркера и без отдельного ресурса образа: общего ресурса, который ждал бы уничтожения обоих контейнеров, больше нет.

Ресурсы `docker_image.api` и `docker_image.worker` снимаются с учёта блоками `removed` без уничтожения. Первый деплой после перехода пересоздаёт `api` и `worker` один раз, даже при том же digest: в состоянии у них `image` — ID образа, в конфигурации — ссылка. Проверено на Docker 29.9.2: переход — один простой API, следующий `plan` — `No changes`, новый тег при том же digest — `No changes`, контейнеры те же.

**Готовность API ждёт сам `apply`.** У `docker_container.api` `wait = true` и `wait_timeout = 90`: создав контейнер, провайдер опрашивает его состояние и считает выкат завершённым, когда healthcheck (`/health` изнутри контейнера) стал `healthy`; не стал за 90 с — `apply` падает, контейнер помечается tainted и пересоздаётся следующим деплоем, а шаг `Логи API после упавшего apply` печатает хвост лога и историю проверок. `start_interval = "1s"` даёт `healthy` в первую секунду после старта приложения, а не через `interval` 30 с. Длительности healthcheck пишутся в формате Go (`"2s"`, `"30s"`, `"1m0s"`): в нём провайдер читает их обратно, и `"1m"` дал бы вечный diff. Правку healthcheck провайдер планирует обновлением на месте, но к запущенному контейнеру она не применяется, поэтому API пересоздаётся от `terraform_data.api_healthcheck` (`replace_triggered_by`). Проверка `/health` через туннель после `apply` остаётся: она проверяет путь снаружи — публикацию порта и туннель.

**Одно SSH-соединение на job.** Хост `stand` в `~/.ssh/config` (`.github/actions/stand-ssh`) — с `ControlMaster auto`, `ControlPath ~/.ssh/cm-%C` и `ControlPersist 10m`: первый `ssh stand` поднимает фоновое соединение, и через него идут все шаги и каждый запрос docker-провайдера и docker CLI к `ssh://stand`, без нового рукопожатия на запрос. Замер с RTT 80 мс: 10 вызовов `docker -H ssh://stand version` — 12,5 с без мультиплексирования, 3,9 с с ним. `ServerAliveInterval 10` и `ServerAliveCountMax 3`: если TCP мастера пропал без разрыва, master закрывается за 30 с — `ConnectTimeout` через живой master не действует, клиент идёт в сокет. ssh в шагах `always()` (`finish` в `apply.sh`, `summary.sh`) к тому же под `timeout 30`, у шага summary `timeout-minutes: 3`. Сессии сверх `MaxSessions` сервера (по умолчанию 10) ssh открывает своим соединением, вызов не падает. Туннели (`.github/scripts/s3-tunnel.sh`, `check-api.sh`) идут мимо master, с `-o ControlPath=none`: через master проброс открывает сам master, `ExitOnForwardFailure` не срабатывает на занятом порте, а туннель закрывается вместе с master через `ControlPersist` простоя — посреди деплоя это был бы туннель к хранилищу состояния. Туннель к хранилищу терпит провал связи дольше master — `ServerAliveCountMax=12`, две минуты: пока он жив, запрос OpenTofu ждёт в нём и доходит, когда связь вернулась, а закрылся — запись состояния падает, и его приходится восстанавливать.

**Воркер** `dmc268-worker` разворачивается из того же образа, что и API, с командой `python -m app.worker`. Портов у него нет: с остальным стеком он говорит только через очередь и базу, наружу — исходящими запросами к GitHub API (дифф, `.review/rules.md`, файлы для AST), поэтому получает те же `GITHUB_APP_ID` и `GITHUB_APP_PRIVATE_KEY`, что и API. Стартует, как и API, после миграций. HTTP-проверки у него нет, поэтому деплой считает воркер живым, если контейнер 30 секунд подряд запущен и ни разу не перезапустился.

Адаптер модели воркера задаёт `llm_backend` (`LLM_BACKEND`): `stub` - без похода к модели, `ollama` - локальная модель. Значения по умолчанию нет: заглушка выбирается только явно, и деплой стенда передаёт `TF_VAR_llm_backend: stub` в `.github/workflows/deploy.yml`.
`ollama` требует `ollama_model` и развёрнутой Ollama по `ollama_base_url`.
Eurorouter подключается только фоллбэком после локальной модели и только при `llm_hosted_fallback = true` с `eurorouter_base_url`, `eurorouter_model` и `eurorouter_api_keys`: это решение отправляет код проверяемых репозиториев hosted-провайдеру.

Переменные, без которых `apply` не пройдёт (в CI приходят через `TF_VAR_*`):

| Переменная | Откуда |
| --- | --- |
| `api_image` | тег и digest собранного образа (`outputs.digest` у `docker/build-push-action`) |
| `postgres_password`, `rabbitmq_password` | секреты `PG_PASSWORD_DMC268_T1`, `RABBITMQ_PASSWORD_DMC268_T1` |
| `github_webhook_secret` | секрет `WEBHOOK_SECRET_DMC268_T1` |

Без него или с битым значением `apply` падает на проверке переменной: стенд не стартует без шифрования токенов пользователя. Генерация и установка — `README.md`, «Ключ шифрования токенов пользователя» |

## Хранилище состояния

Состояние OpenTofu лежит не рядом с конфигурацией, а в S3-совместимом хранилище (RustFS) на том же сервере (`backend.tf`). Так оно переживает прогон раннера GitHub Actions, который исчезает вместе со своим диском.

Хранилище слушает только `127.0.0.1`, поэтому `tofu` любой командой, которой нужно состояние, работает через SSH-туннель:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
```

Учётные данные хранилища передаются как `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`; в CI они приходят из секретов `S3_USER_DMC268_T1` и `S3_PASSWORD_DMC268_T1`. Состояния API и UI лежат в одном бакете `dmc268-tfstate` под разными ключами.

Состояние блокируется на время каждой команды, которая его меняет (`use_lockfile`): OpenTofu кладёт рядом lock-объект условной записью, и второй запуск получает `Error acquiring the state lock` с ID блокировки. Шаги деплоя ждут чужую блокировку до двух минут (`-lock-timeout=2m` у targeted apply, плана и apply), а не падают сразу: так короткий ручной `plan` деплой не роняет. Если запуск упал, не сняв блокировку, её снимают вручную — только убедившись, что никто больше не работает с состоянием:

```bash
cd infra && tofu force-unlock <ID из ошибки>
```

Сам контейнер хранилища **не входит в этот стек**: его поднимает composite action `.github/actions/s3-backend` шагом job'а деплоя перед `tofu apply`, а не OpenTofu, иначе `apply` мог бы снести хранилище собственного состояния. Практическое следствие: `tofu destroy` его не удалит, и полная зачистка сервера состоит из двух шагов — `tofu destroy` со снятой защитой томов (раздел «Развёртывание и удаление»), а затем `docker rm -f dmc268-s3` и `docker volume rm dmc268-s3-data` вручную.

### Если деплой упал посреди apply

Самый дорогой сбой деплоя — пропавшая связь с хранилищем, пока OpenTofu пишет состояние. Что делает OpenTofu 1.13.2 (проверено на `docker:29-dind` с RustFS 1.0.3): промежуточная запись состояния падает, и apply останавливается, не трогая оставшиеся ресурсы; несохранённое состояние ложится в `infra/errored.tfstate` на раннере и исчезает вместе с ним; блокировка не снимается — объект `api/terraform.tfstate.tflock` остаётся в бакете, а её ID в выводе apply нет, он есть только в самом объекте. Следующий деплой упирается в блокировку, а после `force-unlock` — в старое состояние: план создаёт заново контейнеры, которые apply уже создал, и падает на `Conflict. The container name "/dmc268-api" is already in use`.

Деплой чинит это сам. Шаг `Восстановить состояние OpenTofu` (`.github/scripts/deploy/recover-state.sh`) идёт, если упал шаг, который пишет состояние или держит блокировку (`Поднять базу и брокер`, план, apply): заново открывает туннель, ждёт хранилище до двух минут, записывает `errored.tfstate` (`tofu state push` под той же блокировкой, без `-force`: состояние другой линии или с serial не меньше нашего он не перетрёт) и снимает блокировку — только свою, у которой `Who` — этот раннер. Итог — раздел «Состояние OpenTofu» в summary. После этого достаточно перезапустить деплой («Re-run failed jobs»): он доделает выкат.

Зависшее хранилище (соединение живо, ответа нет) ловит сторож туннеля `.github/scripts/s3-watchdog.sh`: таймаута запроса у s3-бэкенда OpenTofu нет, и без него запись состояния висела бы до таймаута job'а. Через две минуты без ответа сторож закрывает туннель, apply падает с `errored.tfstate`, и дальше — то же восстановление.

Если в summary «Состояние не восстановлено», причина — там же. Руками, убедившись, что никто больше не работает с состоянием (нет идущего деплоя, ручного `apply`):

1. Туннель и учётные данные — как в разделе «Развёртывание и удаление».
2. Посмотреть блокировку: `aws --endpoint-url http://127.0.0.1:9000 s3 cp s3://dmc268-tfstate/api/terraform.tfstate.tflock -` — `ID`, кто (`Who`) и когда (`Created`) её взял.
3. Если `errored.tfstate` есть (раннер жив только до конца job'а, так что обычно его нет): `cd infra && tofu state push -lock=false errored.tfstate`, пока блокировка висит. Отказ про serial или lineage значит, что в хранилище уже более новое состояние, — не перетирать его `-force`.
4. Если файла нет, состояние в хранилище старше стенда. `tofu plan` покажет, что он хочет создать заново: контейнеры, которые на сервере уже есть, либо удалить с сервера (`ssh <сервер> docker rm -f dmc268-api dmc268-worker` — следующий деплой создаст их, это короткий простой стенда), либо взять в состояние: `tofu state rm docker_container.api` и `tofu import docker_container.api <id контейнера>`. Тома (`docker_volume.postgres`, `docker_volume.rabbitmq`) не трогать: их защищает `prevent_destroy`, и план с их заменой не пройдёт.
5. Снять блокировку: `tofu force-unlock <ID>` и перезапустить деплой.

## Развёртывание и удаление

Штатный путь один: **мерж в `develop`**. Дальше всё делает `deploy.yml` — собирает образ, поднимает хранилище состояния, базу и брокер, применяет миграции и конфигурацию, проверяет `/health` и что воркер работает. Руками ничего запускать не нужно и, как правило, не получится.

Локальный запуск перестал быть самодостаточным с появлением `backend.tf`: состояние лежит в хранилище на сервере, поэтому любая команда, которой нужно состояние, требует открытого туннеля и учётных данных хранилища:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
export AWS_ACCESS_KEY_ID=<логин хранилища> AWS_SECRET_ACCESS_KEY=<пароль> AWS_DEFAULT_REGION=us-east-1
cd infra && tofu init && tofu plan
```

Ключ и учётные данные лежат в секретах GitHub и наружу не отдаются, так что у большинства их не будет — и это нормально: чтобы разрабатывать, разворачивать стенд не нужно, достаточно `docker compose up` из корня репозитория.

Проверить конфигурацию без доступа к состоянию можно всегда — то же делает job `opentofu` в `ci.yml`:

```bash
cd infra && tofu fmt -check -recursive && tofu init -backend=false && tofu validate && tofu test
```

`tofu test` гоняет `tests/*.tftest.hcl` с `mock_provider "docker"`: ни Docker, ни сервер не нужны. Тесты проверяют адреса базы и брокера в окружении контейнеров и в `migrate_env`, какие секреты получает какой контейнер, сеть и порты, грейс-период воркера, образ `api` и `worker` по digest без тега, `wait` у базы, ожидание `healthy` у API и формат длительностей его healthcheck, проверки переменных. Проверки отклоняют на `plan`, пока сервер не тронут: пустые `github_webhook_secret`, `postgres_password`, `rabbitmq_password` (незаданный секрет CI приходит пустой строкой), `llm_backend = "ollama"` без `ollama_model`, `llm_hosted_fallback` без `ollama` и всех `eurorouter_*`, `api_image` без digest.

`tofu destroy` **падает на томах** базы и брокера: у них `prevent_destroy = true`, и OpenTofu отказывается строить план, который их уничтожает. Удалить стенд осознанно — с данными — можно, только сняв защиту: заменить `prevent_destroy = true` на `false` в `postgres.tf` и `rabbitmq.tf` локально (не в коммите), затем `tofu destroy`. Без этого `tofu destroy` не тронет ничего: ошибка — до изменений. Контейнер хранилища состояния `tofu destroy` не удаляет и так — он не входит в этот стек намеренно. Полная зачистка описана выше, в разделе «Хранилище состояния».

Этот стек только для API. UI деплоится отдельно из `dmc-268-ui-t1/infra/`.
