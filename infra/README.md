# Стек сервера (API на Python 3.14, PostgreSQL 18, RabbitMQ 4.4)

Нужны **Docker Engine** на целевом хосте и OpenTofu >= 1.13 (в CI ставится 1.13.2). Образ API не собирается здесь: он публикуется в ghcr из CI и запускается по digest (`api_image` — `<репозиторий>:<commit sha>@sha256:<digest>`; ссылка без digest не проходит проверку переменной).

## Раскладка файлов

Конфигурация разложена по доменам; OpenTofu читает все `*.tf` каталога как один модуль, так что адреса ресурсов от файла не зависят.

| Файл | Что внутри |
| --- | --- |
| `versions.tf` | версия OpenTofu, провайдер `kreuzwerker/docker` и его настройки (хост Docker) |
| `backend.tf` | хранилище состояния (S3 на сервере) |
| `locals.tf` | общие значения: ротация логов, драйвер fluentd, окружение процессов приложения, грейс-период воркера |
| `network.tf` | три сети: вход `dmc268` (общая со стеком `dmc-268-ui-t1`), данные `dmc268-backend`, исходящая `dmc268-egress` |
| `postgres.tf` | образ, том и контейнер PostgreSQL |
| `rabbitmq.tf` | образ, том и контейнер RabbitMQ |
| `app.tf` | контейнеры `api`, `worker` из образа API по digest |
| `observability.tf` | стек наблюдаемости: образы, тома, сети и девять контейнеров |
| `replica.tf` | роль репликации, горячая реплика и резервные копии PostgreSQL |
| `postgres/` | то, что загружается в контейнеры PostgreSQL: `pg_hba.conf`, SQL роли, entrypoint реплики, скрипт копий |
| `variables.tf` | входные переменные, по секциям тех же доменов |
| `outputs.tf` | выходы: `migrate_env` — окружение миграций для шага деплоя |
| `tests/*.tftest.hcl` | `tofu test` с mock-провайдером |

## Почему OpenTofu, а не Terraform

Terraform с версии 1.6 распространяется под Business Source License (BUSL) — она не open source, и условия дополнительного разрешения HashiCorp на использование размыты. OpenTofu — форк последней открытой версии под Mozilla Public License 2.0, проект Linux Foundation. Провайдеры у него те же, что у Terraform (своих OpenTofu не пишет), а берутся из собственного реестра `registry.opentofu.org`: `kreuzwerker/docker` работает без изменений. Сверх Terraform OpenTofu умеет шифровать состояние и план на диске и в бэкенде (с 1.7); у нас шифрование пока не включено — состояние лежит в хранилище на петле сервера, доступном только через SSH-туннель.

## Локальный или удалённый Docker

Скопируйте `terraform.tfvars.example` в `terraform.tfvars` и замените плейсхолдеры `CHANGE_ME_*`. Файл `terraform.tfvars` не коммитится (gitignore).

- Локальный демон: `docker_host = "unix:///var/run/docker.sock"` (у Docker Desktop на macOS часто `unix:///Users/<вы>/.docker/run/docker.sock`).
- Удалённый сервер: `docker_host = "ssh://user@server"` (нужны SSH-доступ и Docker на удалённом хосте).

Образ API перед `apply` скачивают на тот же Docker сами: `docker pull <api_image>` (с `DOCKER_HOST`, если демон удалённый; для приватного пакета — после `docker login ghcr.io`). Провайдер создаёт `api` и `worker` из уже скачанного образа, а если его нет — тянет сам, но без учётных данных, и на приватном пакете `apply` падает с `denied`.

API публикуется на `bind_ip`, в деплое это `127.0.0.1`. Другого значения конфигурация не примет: переменная проверяется на адрес петли (`127.0.0.0/8` или `::1`), и ошибка всплывает на `plan`. PostgreSQL, реплика и RabbitMQ портов на хосте не публикуют вовсе — см. «Сети».

## Сети

Контейнеры приложения разнесены по docker-сетям (сети стека наблюдаемости — в его разделе), каждый видит только тех, с кем говорит:

| Сеть | Кто в ней | Зачем |
| --- | --- | --- |
| `dmc268` | интерфейс (из `dmc-268-ui-t1`), `api` | публичный вход: nginx интерфейса проксирует `/api/` в API. Имя прежнее — интерфейс подключается к ней по имени |
| `dmc268-backend` (`internal`) | `postgres`, `postgres-replica`, `postgres-backup`, `rabbitmq`, `replication-setup`, `api`, `worker`, миграции шага деплоя | данные. У сети нет шлюза: из неё не выйти в интернет, а интерфейса в ней нет |
| `dmc268-egress` | `worker` | исходящие запросы воркера к GitHub API и провайдеру модели |
| `dmc268-otlp` (`internal`) | интерфейс, `otelcol` (при `observability_enabled`) | трейсы браузера: nginx интерфейса проксирует `/otlp/v1/traces` на отдельный приёмник коллектора `dmc268-otelcol:4319`: только трейсы, `service.name` ставит коллектор (`dmc-268-ui`), кабинет шлёт их на свой же origin. Сеть создаётся и без стека: интерфейс подключается к ней по имени, и без коллектора `/otlp/v1/traces` отвечает 502, а остальное работает |

API — единственный, кто стоит и во входе, и в данных. С `internal`-сети Docker не публикует порты, поэтому у базы и брокера портов на хосте нет: для отладки — `docker exec -it dmc268-postgres psql -U dmc268 -d dmc268` и `docker exec dmc268-rabbitmq rabbitmq-diagnostics status`. Изоляцию проверяют `tests/test_infra_isolation.py` (по тексту `infra/*.tf`) и `infra/tests/main.tftest.hcl` (по плану).

## Реплика и резервные копии

**Горячая реплика** `dmc268-postgres-replica` — физическая потоковая репликация с основного сервера по слоту `dmc268_replica`, только чтение. Приложение в неё не ходит; с неё снимаются резервные копии.

- **Роль `replicator`** заводит одноразовый контейнер `dmc268-replication-setup` (`postgres/replication-setup.sql`), идемпотентно: init-скрипты образа на уже заведённом томе не выполняются. Контейнер запускается заново, когда сменились пароль или SQL либо пересоздана основная база (её контейнер или том), — не на каждом деплое.
- **Пароль роли** — секрет `PG_REPLICATION_PASSWORD_DMC268_T1`. В каталоге данных реплики его нет: реплика пишет `passfile` на каждом старте и передаёт `primary_conninfo` аргументом. Поэтому смена секрета — обычный деплой: роль получает новый пароль, реплика пересоздаётся с новым `passfile`, том не пересобирается.
- **Слот** заводит сама реплика (`pg_basebackup --create-slot`) при каждой пересборке, удаляя неактивный старый.
- **Пересборка** (`postgres/replica-entrypoint.sh`) происходит сама при старте контейнера, если том пуст или копия не дописана либо слота нет или он потерян: основной сервер тогда тот же кластер, и пересборка ничего не теряет. Копия снимается во временный каталог и переименовывается целиком; на это время на диске нужно место под две копии базы (старый каталог и новый). При постоянной ошибке `pg_basebackup` пауза между попытками растёт до минуты.
- **Другой кластер основного сервера** (его том заведён заново, например потерян) реплика **не стирает**: в ней может быть последняя копия данных, а новый основной сервер — пустым. Контейнер завершается с ошибкой «основной сервер — другой кластер», деплой падает на проверке потока. Дальше решает человек: если данные реплики нужны — поднять из них основной сервер (или снять `pg_dump` с остановленной реплики); если нет — пересобрать реплику, удалив её том: `docker rm -f dmc268-postgres-replica && docker volume rm dmc268-postgres-replica-data`, затем деплой. Решение принимается только по ответу основного сервера: пока он недоступен, реплика ничего не трогает.
- **Потолок WAL.** Слот держит WAL для отставшей реплики, но не больше `postgres_max_slot_wal_keep_size` (2 ГБ): иначе упавшая реплика заполнила бы диск основного сервера. Реплика, перешагнувшая потолок, теряет поток и становится `unhealthy`. Docker unhealthy-контейнеры не перезапускает, поэтому это делает деплой: перед проверкой потока он перезапускает unhealthy-реплику, и она пересобирается. Между деплоями — вручную: `docker restart dmc268-postgres-replica`.
- **Здоровье реплики** — это поток: healthcheck смотрит `pg_stat_wal_receiver.status = streaming`. Отставшая реплика отвечает на запросы, но `unhealthy`.
- **Деплой** (`.github/scripts/deploy/check-replica.sh`) проверяет со стороны основного сервера, что слот держит именно реплика (`application_name = dmc268_replica`, а у `pg_basebackup` первой сборки — `dmc268_basebackup`) и поток в состоянии `streaming`; unhealthy-реплику перед этим перезапускает.
- **Доступ к базе** (`postgres/pg_hba.conf`, вне каталога данных) — только из подсети самого сервера (`samenet`), то есть из `dmc268-backend`.

Реплика на том же сервере: она спасает от сбоя процесса или тома основной базы, но не от падения самого сервера.

**Резервные копии** снимает `dmc268-postgres-backup`: `pg_dump -Fc` при старте и затем раз в сутки, в том `dmc268-postgres-backups`, хранение — `backup_keep_days` (7 суток). Источник — реплика, если она получает поток, иначе основной сервер: копия с отставшей реплики выглядела бы свежей, а содержала бы данные на момент обрыва. Контейнер становится `unhealthy`, если свежей копии нет дольше 26 часов. Источник копии видно только в логе бэкапа, а не в его healthcheck: **unhealthy-реплика означает, что копии идут с основного сервера**. Пока база маленькая, это незаметно; на большой базе ежедневный `pg_dump` с основного сервера держит блокировки и может задержать миграции с `ALTER TABLE` — реплику стоит поднять, не откладывая. Копии лежат на том же диске — от потери сервера не спасают; вынос копий за пределы сервера — отдельная задача.

**Ollama**, если её развернут на сервере, подключается к `dmc268-backend`: воркер ходит к ней оттуда. К `dmc268-egress` — только если Ollama сама скачивает модели.

Восстановление в основную базу (API и воркер на это время остановить):

```bash
docker run --rm --network dmc268-backend -v dmc268-postgres-backups:/backups:ro \
  -e PGPASSWORD=<пароль> pgvector/pgvector:pg18 \
  pg_restore -h dmc268-postgres -U dmc268 -d dmc268 --clean --if-exists /backups/<файл>.dump
```

## Ограничения контейнеров

- `api`, `worker` и миграции работают не от root (`USER` в `Dockerfile`), с файловой системой только для чтения (запись — только в `/tmp`), без capabilities и с `no-new-privileges`. У миграций это флаги `docker run` в `.github/scripts/deploy/migrate.sh`.
- `postgres` и `rabbitmq` — только `no-new-privileges`: их entrypoint стартует от root, чтобы подготовить каталог данных, и сам переходит на служебного пользователя.
- У каждого контейнера потолок памяти без свопа (`postgres` 1 ГБ, `postgres-replica`, `rabbitmq`, `api` и `worker` по 512 МБ, `postgres-backup` и миграции по 256 МБ, `replication-setup` 64 МБ) и ротация логов: три файла по 10 МБ. Постоянно работающие контейнеры — около 3,3 ГБ, на время деплоя добавляются миграции и `replication-setup`; без учёта интерфейса и хранилища состояния.
- `replication-setup` и `postgres-backup` — как миграции и `api`: файловая система только для чтения, без capabilities. `postgres-replica` — как `postgres`: только `no-new-privileges`.
- `postgres`, `postgres-replica` и `rabbitmq` при пересоздании и `docker stop` останавливаются штатно: `stop_timeout` и `destroy_grace_seconds` по 60 с. Без `destroy_grace_seconds` провайдер удаляет контейнер через SIGKILL, и база поднимается с восстановлением после аварии.

Смена любого из этих атрибутов пересоздаёт контейнер. Данные PostgreSQL и RabbitMQ лежат в томах и замену переживают.

## Версия провайдера

Точная версия `kreuzwerker/docker` и её хэши закреплены в `.terraform.lock.hcl`, файл коммитится. После смены `version` в `versions.tf` его пересобирают на все платформы команды, иначе `tofu init` на неперечисленной системе допишет в файл свои хэши и оставит изменение в рабочей копии:

```bash
cd infra && tofu init -backend=false -upgrade && tofu providers lock \
  -platform=linux_amd64 -platform=linux_arm64 \
  -platform=darwin_amd64 -platform=darwin_arm64 \
  -platform=windows_amd64
```

## Деплой

Стенд катится сам при мерже в `develop` (`.github/workflows/deploy.yml`). `main` в деплое не участвует: сервер один, и два источника дрались бы за него.

Порядок такой: образ собирается и публикуется в `ghcr.io/larchanka-training/dmc-268-api-t1` с тегом по commit sha → сверка, что коммит всё ещё вершина `develop` (`check-tip.sh`) → поднимается хранилище состояния и туннель к нему → targeted-план сети, базы и брокера в файл, сторож и его apply (`infra.sh`) → план полного выката в файл и сторож томов (`plan.sh`) → pull образа API → пароли базы и брокера из секретов (`passwords.sh`, раздел «Смена паролей») → миграции (`.github/scripts/deploy/migrate.sh`) → `tofu apply` этого плана (`apply.sh`) → проверка `/health` через туннель и проверка воркера → уборка образов → summary (`summary.sh`). Если упал шаг, который пишет состояние, между apply и проверками идёт восстановление состояния (раздел «Если деплой упал посреди apply»).

**Устаревший коммит не катится.** `gate` сверяет коммит с вершиной `develop`, но только у `workflow_run` и только при своём запуске, а «Re-run failed jobs» успешный `gate` не перезапускает и берёт его выход `sha` из первой попытки. Поэтому первым шагом после checkout job `deploy` сверяет коммит ещё раз (`check-tip.sh`) — и для ручного запуска тоже: вершина ушла — остальные шаги пропускаются, job зелёный, в summary «пропущен: вершина develop уже …». Перезапуск упавшего деплоя, пока за ним не пришёл новый коммит, катит как обычно. Публичной проверки здесь нет: API снаружи не публикуется, а его доступность по `https://62.169.24.237/api/v1/` проверяет деплой интерфейса.

**Снаружи API адресуется через интерфейс, с исходным путём.** Публичный вход — `nginx` в контейнере фронтенда на **https://62.169.24.237** (сертификат Let's Encrypt на IP, HTTP перенаправляется на HTTPS; устройство — в `infra/README.md` репозитория `dmc-268-ui-t1`). Префикс он не трогает: браузерный `GET /api/v1/reviews` приходит сюда как `GET /api/v1/reviews`, поэтому роутеры монтируются на `/api/v1`, как требует контракт API. `/health` через этот вход не публикуется — проверка живости ходит мимо него.

**Тома данных деплой не уничтожает.** У каждого тома (`docker_volume.postgres`, `docker_volume.rabbitmq`, `docker_volume.postgres_replica`, `docker_volume.postgres_backups`) — `lifecycle { prevent_destroy = true }`: план, который уничтожает или заменяет том, OpenTofu отклоняет до изменений на сервере с `Error: Resource instance cannot be destroyed`. Это действует и на targeted apply шага «Поднять базу и брокер» — `-target=docker_container.postgres` тянет том зависимостью; тот же сторож `scripts/deploy_report.py` смотрит и его план (`infra.sh`). Полный выкат идёт планом в файл: `plan.sh` строит `tofu plan -out=tfplan` сразу после targeted apply, и `scripts/deploy_report.py` по `tofu show -json` дублирует проверку для summary — падает, если план уничтожает или заменяет любой `docker_volume`, и apply не запускается. Списка адресов у сторожа нет: ресурс, переименованный без блока `moved`, уничтожается по старому адресу, и `prevent_destroy` у него уже нет — по списку его бы не поймать. Миграции идут между планом и apply: состояние они не трогают, план не устаревает. Применяется ровно проверенный план (`apply.sh`); если до него не дошло, файл плана удаляет `summary.sh`. Сменить том, как при смене сборки PostgreSQL или версии RabbitMQ, — новым ресурсом с новым адресом (с `prevent_destroy` — его наличие у каждого тома сверяет тест), а прежний снять с учёта блоком `removed { lifecycle { destroy = false } }`: план выйдет `forget` и `create`, старый том с данными останется на сервере до ручного `docker volume rm`. В плане и его JSON пароли лежат открытым текстом: JSON идёт только трубой, файл плана удаляется после apply и артефактом не загружается, обёртка `setup-opentofu`, копирующая stdout tofu в выходы шага, выключена.

**Summary деплоя** пишет `summary.sh` на любом исходе: шаг падения, простой API с разбивкой (SIGTERM старому → выход → `Created` нового → `State.StartedAt` → событие `health_status: healthy` нового; всё, кроме `Created` и `StartedAt`, — из событий Docker, которые `apply.sh` читает потоком всё время apply. `State.Health.Log` — запасной путь, если событий нового контейнера нет: журнал держит пять последних проверок, и после долгого apply первой успешной в нём уже нет — summary тогда помечает простой как недостоверный), оба плана по типам ресурсов (targeted базы и брокера и полный), применённые миграции — а если шаг миграций упал, ревизия, на которой он упал, и ревизия базы по `alembic current`, который `migrate.sh` запускает после сбоя тем же образом под `timeout 60` (по логу alembic не сказать, что откатилось: `autocommit_block` фиксирует всё до себя, а при оборванном ssh код выхода теряется; не ответила база — summary пишет «ревизия базы неизвестна», без «откатено»); упал шаг до alembic (`tofu output`) — так и сказано, свободное место на `/` и в каталоге Docker после уборки и длительность шагов — по засечкам `mark.sh`, без `actions: read` у токена. Подписи значений — ключи OpenTelemetry (`cicd.pipeline.*`, `container.image.*`, `system.filesystem.*`), свои — в `dmc268.deploy.*`.

**Миграции — шаг деплоя до полного `apply`, а не контейнер стека.** Шаг `Применить миграции` запускает `.github/scripts/deploy/migrate.sh`: одноразовый `docker run --rm` того же образа (тот же digest), что сейчас выкатится, с `alembic upgrade head` и шагом роли мониторинга (ALTER ROLE при выключенном `track_utility`, пароль — из окружения; тот же шаг — у сервиса `migrate` в compose) — на сервере через `DOCKER_HOST=ssh://stand`, в сети данных `dmc268-backend`. Окружение — выход `migrate_env` (`outputs.tf`): те же строки `local.app_env`, что у `api` и `worker`, плюс телеметрия (`local.telemetry_env`) и `POSTGRES_MONITOR_PASSWORD`, через env-файл с правами 600, который удаляется после запуска. Упала миграция — шаг падает, полный `apply` не запускается, на стенде остаётся прежняя версия. Проверка `/health` этого не заметила бы: по контракту она отвечает независимо от базы.

Бесконечно ждать миграция не может. Сессии alembic `alembic/env.py` ставит `lock_timeout = '5s'` и `statement_timeout = '2min'` (только онлайн, в SQL `--sql` их нет): `ALTER TABLE`, который ждёт блокировку горячей таблицы за транзакцией старого API или воркера, иначе ставил бы за собой в очередь все её чтения, и API висел бы. Через 5 с миграция падает с `LockNotAvailable`, транзакция откатывается, стенд работает на прежней схеме. `migrate.sh` тогда спрашивает `alembic current` и, если база на ревизии, с которой попытка начала, повторяет upgrade через 15 с — всего до 3 попыток, и новая не начинается позже 5 мин от старта шага; база сдвинулась (`autocommit_block`), не ответила или ошибка другая — шаг падает сразу, решает человек. У шага `timeout-minutes: 10`. Контейнер `dmc268-migrations`, оставшийся от шага, убитого по таймауту (раннер убивает docker CLI, а не контейнер на сервере), `migrate.sh` удаляет перед запуском; удаление рвёт соединение, и PostgreSQL откатывает его транзакцию.

Пока идут миграции, работает старый код: ломающая миграция (удаление или переименование колонки, которую он читает) даст на стенде короткий сбой во время выката. Пока нет пользователей, это допустимо; для прода — expand/contract в два деплоя (скилл `.agents/skills/alembic-migration`).

Образ лежит в приватном пакете: перед миграциями job входит в `ghcr.io` на раннере (`docker/login-action`, `GITHUB_TOKEN` с `packages: read`), и docker CLI передаёт учётные данные демону сервера вместе с запросом pull. На сервере токен не остаётся. Этот pull — единственный для образа API, он идёт своим шагом «Скачать образ API» до шага паролей (окно смены пароля его не включает, раздел «Смена паролей»): учётных данных реестра у провайдера нет, и `api` с `worker` он создаёт из уже скачанного образа.

**Чистый сервер.** База и брокер должны существовать до миграций, поэтому перед ними каждый деплой (`infra.sh`) строит и применяет targeted-план

```bash
tofu plan -out=infra.tfplan -target=docker_network.dmc268 -target=docker_network.backend -target=docker_container.postgres -target=docker_container.rabbitmq
tofu show -json infra.tfplan | python3 scripts/deploy_report.py plan infra
tofu apply infra.tfplan
```

На живом стенде это `No changes` и ожидаемое предупреждение OpenTofu о `-target`; на чистом — создание сети, томов, базы и брокера. У `postgres` `wait = true`: apply возвращается, когда healthcheck зелёный, и миграциям не нужен цикл повторов. Этот же apply обновляет в состоянии выход `migrate_env`: выход зависит от контейнеров базы и брокера (хосты в `local.app_env` — ссылки на них), а выход, не зависящий от целевых ресурсов, targeted apply не записывает. Руками ничего делать не нужно: первый деплой на пустой сервер проходит тем же путём (проверено на чистом локальном Docker 29.9.2).

**Базу и брокер деплой не пересоздаёт.** План, который заменяет или удаляет `docker_container.postgres` или `docker_container.rabbitmq`, сторож отклоняет — и targeted, и полный: apply не запускается, контейнеры те же. Узнаёт он их и по имени контейнера на хосте (`dmc268-postgres`, `dmc268-rabbitmq` в `change.before`/`after` плана): ресурс, переименованный без `moved`, уничтожается по старому адресу, и сверка только по адресу его бы пропустила. Реплику (`docker_container.postgres_replica`) и копии (`docker_container.postgres_backup`) сторож не держит, хотя они тоже на томах данных: API и воркер в них не ходят, данные остаются в защищённых томах, а замена — обычная правка. Реплика при этом останавливается штатно (`destroy_grace_seconds` 60), копия, оборванная на полпути, остаётся `*.partial` и убирается следующим стартом. Так же не держит он и хранилища стека наблюдаемости — Loki, Tempo, Prometheus и Grafana (`observability.tf`): их тома защищены, а правка конфига — замена контейнера с окном штатной остановки 30 с (`stop_timeout`/`destroy_grace_seconds`), чтобы WAL и буферы сбрасывались, а не обрывались SIGKILL. До миграций их не поднимают: targeted-план — только сети, основной сервер и брокер. Повод к замене — правка их `command`, памяти, `log_opts` или образа. Правку `env` план не видит (`ignore_changes = [env]`): там только переменные инициализации тома, и смена `TF_VAR_postgres_password` раньше давала `postgres must be replaced`, не меняя пароль в существующем томе, — миграции потом падали с `password authentication failed`. Пароль теперь выставляет шаг деплоя (раздел «Смена паролей»). Правку `command`, памяти или образа базы и брокера выкатывает ручной запуск с осознанным обходом сторожа: `gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true`. Флаг доходит до сторожа только из `workflow_dispatch` и только у первой попытки (у автоматического деплоя выражение в env шага даёт `false`; Re-run повторил бы inputs старого запуска, поэтому повтор с флагом — новым `gh workflow run`, а не Re-run), замена тогда — `::warning::` и пометка в summary с тем, кто запустил эту попытку (`github.triggering_actor`); уничтожение или замену томов флаг не разрешает никогда. У обоих контейнеров `destroy_grace_seconds = 60`: при ручной замене провайдер ждёт штатной остановки, а не шлёт SIGKILL сразу после стоп-сигнала (было: `kill 2` → `kill 9`, код 137).

**Контейнер `dmc268-migrate`** жил в стеке до #159. Блок `removed` в `app.tf` снимает его с учёта без уничтожения, а `migrate.sh` удаляет остановленный контейнер на сервере: его старые логи и код выхода легко принять за текущие, и он держит прежний образ.

**Образ API — без ресурса `docker_image`.** `api` и `worker` ссылаются на образ строкой `<репозиторий>@sha256:<digest>` — `local.api_image_ref` в `app.tf`, тег из `api_image` срезан. Ресурс образа пересоздавался на каждом коммите (тег — commit sha) уже после остановки старого API, и его pull добавлял к простою 6 с (деплой #202). Тег в ссылке контейнера дал бы то же: провайдер сравнивает `image` строкой и пересоздаёт контейнер, даже если digest не изменился. Теперь контейнеры меняются, только когда меняется digest; `docker ps` показывает репозиторий без тега, commit sha — в summary деплоя. Замена API не ждёт воркера и без отдельного ресурса образа: общего ресурса, который ждал бы уничтожения обоих контейнеров, больше нет.

Ресурсы `docker_image.api` и `docker_image.worker` снимаются с учёта блоками `removed` без уничтожения. Первый деплой после перехода пересоздаёт `api` и `worker` один раз, даже при том же digest: в состоянии у них `image` — ID образа, в конфигурации — ссылка. Проверено на Docker 29.9.2: переход — один простой API, следующий `plan` — `No changes`, новый тег при том же digest — `No changes`, контейнеры те же.

**Готовность API ждёт сам `apply`.** У `docker_container.api` `wait = true` и `wait_timeout = 90`: создав контейнер, провайдер опрашивает его состояние и считает выкат завершённым, когда healthcheck (`/health` изнутри контейнера) стал `healthy`; не стал за 90 с — `apply` падает, контейнер помечается tainted и пересоздаётся следующим деплоем, а шаг `Логи API после упавшего apply` печатает хвост лога и историю проверок. `start_interval = "1s"` даёт `healthy` в первую секунду после старта приложения, а не через `interval` 30 с. Длительности healthcheck пишутся в формате Go (`"2s"`, `"30s"`, `"1m0s"`): в нём провайдер читает их обратно, и `"1m"` дал бы вечный diff. Правку healthcheck провайдер планирует обновлением на месте, но к запущенному контейнеру она не применяется, поэтому API пересоздаётся от `terraform_data.api_healthcheck` (`replace_triggered_by`). Проверка `/health` через туннель после `apply` остаётся: она проверяет путь снаружи — публикацию порта и туннель.

**Одно SSH-соединение на job.** Хост `stand` в `~/.ssh/config` (`.github/actions/stand-ssh`) — с `ControlMaster auto`, `ControlPath ~/.ssh/cm-%C` и `ControlPersist 10m`: первый `ssh stand` поднимает фоновое соединение, и через него идут все шаги и каждый запрос docker-провайдера и docker CLI к `ssh://stand`, без нового рукопожатия на запрос. Замер с RTT 80 мс: 10 вызовов `docker -H ssh://stand version` — 12,5 с без мультиплексирования, 3,9 с с ним. `ServerAliveInterval 10` и `ServerAliveCountMax 3`: если TCP мастера пропал без разрыва, master закрывается за 30 с — `ConnectTimeout` через живой master не действует, клиент идёт в сокет. ssh в шагах `always()` (`finish` в `apply.sh`, `summary.sh`) к тому же под `timeout 30`, у шага summary `timeout-minutes: 3`. Сессии сверх `MaxSessions` сервера (по умолчанию 10) ssh открывает своим соединением, вызов не падает. Туннели (`.github/scripts/s3-tunnel.sh`, `check-api.sh`) идут мимо master, с `-o ControlPath=none`: через master проброс открывает сам master, `ExitOnForwardFailure` не срабатывает на занятом порте, а туннель закрывается вместе с master через `ControlPersist` простоя — посреди деплоя это был бы туннель к хранилищу состояния. Туннель к хранилищу терпит провал связи дольше master — `ServerAliveCountMax=12`, две минуты: пока он жив, запрос OpenTofu ждёт в нём и доходит, когда связь вернулась, а закрылся — запись состояния падает, и его приходится восстанавливать.

**Воркер** `dmc268-worker` разворачивается из того же образа, что и API, с командой `python -m app.worker`. Портов у него нет: с остальным стеком он говорит только через очередь и базу, наружу — исходящими запросами к GitHub API (дифф, `.review/rules.md`, файлы для AST), поэтому получает те же `GITHUB_APP_ID` и `GITHUB_APP_PRIVATE_KEY`, что и API. Стартует, как и API, после миграций. HTTP-проверки у него нет, поэтому деплой считает воркер живым, если контейнер 30 секунд подряд запущен и ни разу не перезапустился.

Адаптер модели воркера задаёт `llm_backend` (`LLM_BACKEND`): `stub` - без похода к модели, `ollama` - локальная модель, `eurorouter` - hosted-провайдер основным. Значения по умолчанию нет: заглушка выбирается только явно. Деплой стенда передаёт `TF_VAR_llm_backend: eurorouter` в `.github/workflows/deploy.yml` (#245): Ollama на стенде нет, код проверяемых репозиториев уходит Eurorouter. `eurorouter` требует `eurorouter_base_url`, `eurorouter_model` и `eurorouter_api_keys`, без них план падает.
`ollama` требует `ollama_model` и развёрнутой Ollama по `ollama_base_url`.
Фоллбэком после локальной модели Eurorouter подключается при `llm_hosted_fallback = true` с `eurorouter_base_url`, `eurorouter_model` и `eurorouter_api_keys`: это решение отправляет код проверяемых репозиториев hosted-провайдеру.

## Смена паролей

Пароль базы и брокера меняется **обычным деплоем**: новый секрет → деплой. Ручной запуск с `allow_stateful_replace` не нужен, база и брокер не пересоздаются.

**Пароль — печатный ASCII без пробела** (`0x21`–`0x7E`); совет — `openssl rand -hex 24`, но и `openssl rand -base64 24` годится. Пароль базы и брокера едет в URL подключения (`DATABASE_URL`, `RABBITMQ_URL` в `locals.tf`, они же `migrate_env`): `+`, `/`, `=`, `@`, `:`, `%`, кавычки и `\` `urlencode` кодирует в `%XX`, и SQLAlchemy (`make_url`) и pika (`URLParameters`) декодируют их верно — проверено на dind сквозь деплой: `a+b/c=d`, `p@ss:w%rd`, `x'y"z\$` и base64 для базы, брокера и `replicator` (`\password`, `passfile` реплики, `PGPASSWORD` копий). Ломаются пробельные символы: пробел `urlencode` пишет как `+`, а SQLAlchemy и pika читают `+` буквально; `rabbitmqctl` обрезает пробелы по краям — шаг был бы зелёным, а API не вошёл бы; перевод строки разрезал бы пароль в stdin. Пустой пароль, пробел, таб, перевод строки и не-ASCII шаг паролей отклоняет `::error::` до изменений на сервере. Пароль `replicator` шаг не проверяет — правило то же.

`POSTGRES_PASSWORD` и `RABBITMQ_DEFAULT_PASS` образы читают только на пустом томе. Поэтому:

- у `docker_container.postgres` и `docker_container.rabbitmq` — `lifecycle { ignore_changes = [env] }`: в их `env` только переменные инициализации тома, правку план не видит, контейнер не пересоздаётся. Переменной, которая действует при каждом старте, в этом `env` не место — её правка не дошла бы до контейнера (сверяет `tests/test_deploy_passwords.py`);
- **смену имён** — `postgres_user`, `postgres_db`, `rabbitmq_user` — `ignore_changes` спрятал бы: шаг сменил бы пароль прежней роли, а API и миграции входили бы новой. Её отклоняет `postcondition` контейнера: при `ignore_changes` `self.env` — окружение, с которым контейнер создан, и plan падает `Resource postcondition failed` до изменений на сервере. Новое имя в заведённом томе не появится и после замены контейнера: это новый том. `postcondition` эту замену не поймает: при ручном запуске с `allow_stateful_replace` новый контейнер берёт `env` из конфига, проверка проходит, а в томе остаются старые имена — имена с таким запуском не меняют. `replace_triggered_by` от `terraform_data` не годится — первое создание такого ресурса тоже повод к замене, и переход на эту конфигурацию пересоздал бы базу (проверено на dind);
- шаг деплоя «Выставить пароли базы и брокера» (`.github/scripts/deploy/passwords.sh`) идёт после проверенного плана и pull образа, до миграций. Он входит новым паролем — в базу по сети, как API (`samenet`, scram), в брокер — `rabbitmqctl authenticate_user`. Вошёл — ничего не меняет, это обычный деплой. Не вошёл — меняет пароль изнутри контейнера: `\password` в `psql` по локальному сокету (`trust` в `postgres/pg_hba.conf`, старый пароль не нужен) и `rabbitmqctl change_password`. Затем входит снова; не вошёл — шаг падает, миграции и apply не идут;
- миграции и полный apply получают новый пароль из `TF_VAR_*`: apply пересоздаёт всех, у кого он в окружении.

Пароль не попадает ни в аргументы команд (их видно в `ps` на сервере), ни в лог шага: он идёт первой строкой stdin `docker exec -i`, дальше — встроенным `printf` в stdin `psql` и `rabbitmqctl`. На сервер PostgreSQL открытый пароль не уходит вовсе: `\password` без tty читает его из stdin и шлёт `ALTER USER … PASSWORD 'SCRAM-SHA-256$…'` — в лог запросов (`log_statement`, `log_min_duration_statement`) и в `pg_stat_activity.query`, которую видит `pg_monitor`, попадает только хеш (проверено на pg18 с `log_statement = all` и `log_min_duration_statement = 0`). Так же теперь и `replication-setup`: `\password replicator` последней строкой `postgres/replication-setup.sql`.

| Секрет | Чей пароль | Кто им входит | Что пересоздаёт apply |
| --- | --- | --- | --- |
| `PG_PASSWORD_DMC268_T1` | роль `dmc268`: владелец базы и суперпользователь кластера (`POSTGRES_USER`) | `api`, `worker`, миграции (`DATABASE_URL`), `replication-setup`, `postgres-backup` (`PGPASSWORD`) | `api`, `worker`, `replication-setup`, `postgres-backup` |
| `RABBITMQ_PASSWORD_DMC268_T1` | пользователь `dmc268` брокера | `api`, `worker` (`RABBITMQ_URL`; у миграций он в окружении, но они в брокер не ходят) | `api`, `worker` |
| `PG_REPLICATION_PASSWORD_DMC268_T1` | роль `replicator` | реплика (`passfile`) | `replication-setup` (он и меняет пароль роли), `postgres-replica` |
| `PG_MONITOR_PASSWORD_DMC268_T1` | роль `dmc268_monitor` | коллектор метрик | на `develop` пока не используется: роль и коллектор приходят с PR #130, и там пароль переустанавливает шаг миграций на каждом деплое — порядок тот же, секрет → деплой |

Проверки реплики (`check-replica.sh`, healthcheck реплики) входят по локальному сокету и пароля не знают.

### Окно смены

Открытые соединения смена пароля не рвёт — ни у PostgreSQL, ни у брокера. Новые соединения со старым паролем отклоняются сразу. Значит, от шага паролей до замены API в полном apply старые API и воркер работают на открытых соединениях, а новое соединение открыть не могут. Это окно: **шаг миграций** (с повторами после `LockNotAvailable` — до 5 мин) **и начало apply до остановки старого API**; после — обычная замена API, как на любом деплое. Pull образа в окно не входит: он — свой шаг «Скачать образ API» до шага паролей.

Поставить шаг паролей после миграций, прямо перед apply, нельзя: миграции входят паролем из `migrate_env`, а он из того же секрета — то есть уже новым. Повторы миграций поэтому остаются внутри окна; обычно это одна попытка в пару секунд.

Репетиция на `docker:29-dind` (Docker 29.9.2, OpenTofu 1.13.2, настоящий образ API с новым digest из реестра, локальное состояние): смена пароля базы — контейнеры `postgres`, `rabbitmq`, `postgres-replica` те же; pull — отдельным шагом до окна; окно 2,7 с от смены пароля до SIGTERM старому API (миграции 1,5 с и начало apply), затем 3,2 с замены API. Последовательные запросы к `/api/v1/auth/me` шли по открытому соединению пула и не падали; из 12 параллельных 6 получили `500` (новое соединение старым паролем). Долгая сессия со старым паролем пережила смену. Брокер — окно 2 с, долгое AMQP-соединение старым паролем живо, новый воркер подключился новым. На стенде окно дольше на ssh до сервера.

Худший случай — **упали миграции** после смены: apply не идёт, и старые API и воркер до следующего деплоя не откроют новых соединений. Тогда — сразу чинить вперёд (ниже, «Откат»). Воркер, который в момент смены дорабатывает сообщение (до 41 мин), живёт на открытых соединениях; понадобится ему новое — это сообщение упадёт.

### Плановая смена

```bash
openssl rand -hex 24 | gh secret set PG_PASSWORD_DMC268_T1      # значение не печатается
gh workflow run deploy.yml --ref develop                         # без allow_stateful_replace
gh run watch "$(gh run list --workflow deploy.yml --limit 1 --json databaseId -q '.[0].databaseId')"
```

Новый секрет до деплоя ни на что не действует: окна нет, пока деплой не дошёл до шага паролей. Для брокера — `RABBITMQ_PASSWORD_DMC268_T1`, для реплики — `PG_REPLICATION_PASSWORD_DMC268_T1`. Несколько секретов можно сменить одним деплоем.

**Перед деплоем** (`ssh stand`) — сохранить адреса старого API, ими потом проверяется, что старый пароль не принимается. Файлы с паролями — с правами 600, после проверки удалить:

```bash
(umask 077; docker exec dmc268-api printenv DATABASE_URL > ~/old-db-url; docker exec dmc268-api printenv RABBITMQ_URL > ~/old-amqp-url)
```

`$POSTGRES_PASSWORD` и `$RABBITMQ_DEFAULT_PASS` в `env` контейнеров базы и брокера для этого не годятся: там навсегда пароль инициализации тома (`ignore_changes`), а не текущий.

**Что должно быть в деплое.** Шаг «Выставить пароли базы и брокера»: `postgres: пароль роли dmc268 сменён` (или `rabbitmq: … сменён`); у остальных — «совпадает с секретом». В summary: раздел «Пароли» с тем, что сменено, targeted-план без изменений, в полном — замена `docker_container` (`api`, `worker`, `replication-setup`, `postgres-backup`; для реплики — `replication-setup` и `postgres-replica`), базу и брокер план не пересоздаёт. Зелёные проверки API, воркера и реплики.

**Проверка после** (`ssh stand`):

```bash
# старый пароль базы не принимается: ждём «password authentication failed»
docker exec -i dmc268-api python -c 'import sys, sqlalchemy as s; s.create_engine(sys.stdin.read().strip()).connect()' < ~/old-db-url 2>&1 | grep -o 'password authentication failed'
# старый пароль брокера не принимается: ждём ACCESS_REFUSED
docker exec -i dmc268-api python -c 'import sys, pika; pika.BlockingConnection(pika.URLParameters(sys.stdin.read().strip()))' < ~/old-amqp-url 2>&1 | grep -o ACCESS_REFUSED
rm -f ~/old-db-url ~/old-amqp-url
# новые принимаются: API входит своими адресами
docker exec dmc268-api python -c 'import os, sqlalchemy as s; s.create_engine(os.environ["DATABASE_URL"]).connect().close(); print("ok")'
docker exec dmc268-api python -c 'import os, pika; pika.BlockingConnection(pika.URLParameters(os.environ["RABBITMQ_URL"])).close(); print("ok")'
# все соединения роли — новые, открыты после смены
docker exec dmc268-postgres psql -U dmc268 -d dmc268 -XtAc "select application_name, client_addr, backend_start from pg_stat_activity where usename = 'dmc268' and client_addr is not null"
# копии идут новым паролем: первая копия снимается при старте контейнера
docker logs --tail 3 dmc268-postgres-backup
# брокер: воркер подключён после деплоя
docker exec dmc268-rabbitmq rabbitmqctl -q list_connections user peer_host connected_at
# реплика: поток идёт (для replicator)
docker exec dmc268-postgres psql -U dmc268 -d dmc268 -XtAc "select application_name, state from pg_stat_replication"
```

### Откат

Секреты GitHub не читаются, и старого значения взять негде — откат идёт **вперёд**:

- деплой упал после шага паролей (миграции, apply) — summary покажет это в разделе «Пароли»: «пароль сменён, а API и воркер не заменены». Устранить причину и запустить деплой ещё раз: шаг скажет «совпадает», остальное пройдёт как обычно;
- не устраняется быстро, а старый API должен открывать соединения — вернуть роли пароль старого API руками. Он в `~/old-db-url` (не сохранили — `(umask 077; docker exec dmc268-api printenv DATABASE_URL > ~/old-db-url)`: API на стенде ещё старый), но закодирован `urlencode`: `a+b/c=d` там — `a%2Bb%2Fc%3Dd`. Раскодирует его `make_url` SQLAlchemy в контейнере API, и дважды — как спрашивает `\password` — он идёт трубой в psql: ни в аргументы, ни на экран, а на сервер PostgreSQL уходит только SCRAM-хеш:

  ```bash
  docker exec -i dmc268-api python -c 'import sys, sqlalchemy as s; p = s.make_url(sys.stdin.read().strip()).password; print(p); print(p)' < ~/old-db-url \
    | docker exec -i dmc268-postgres psql -XqU dmc268 -d dmc268 -v ON_ERROR_STOP=1 -c '\password dmc268'
  ```

  У брокера то же — из `~/old-amqp-url`, раскодирует pika, `rabbitmqctl change_password` без пароля в аргументах читает его из stdin:

  ```bash
  docker exec -i dmc268-api python -c 'import sys, pika; print(pika.URLParameters(sys.stdin.read().strip()).credentials.password)' < ~/old-amqp-url \
    | docker exec -i dmc268-rabbitmq rabbitmqctl -q change_password dmc268
  ```

  Секрет остаётся новым, и следующий деплой сам выставит его снова.

**Реверт этого механизма** (#161) после хотя бы одной смены ломает деплой. Без `ignore_changes = [env]` у базы и брокера план видит, что пароль в их `env` (пароль инициализации тома) не совпадает с секретом, и пересоздаёт контейнеры (`postgres must be replaced`, `rabbitmq must be replaced` — проверено на dind); сторож отклоняет каждый такой деплой, а выход — только ручной запуск с `allow_stateful_replace`, то есть перезапуск базы и брокера. Поэтому при реверте `ignore_changes = [env]` в `infra/postgres.tf` и `infra/rabbitmq.tf` оставляют.

### Пароль утёк

База и брокер портов наружу не публикуют (сеть `dmc268-backend` — `internal`), и войти утёкшим паролем можно только с сервера или из контейнера стека. Но смена — сразу:

1. Сменить секрет и запустить деплой — как в плановой смене. Деплой в очереди (`concurrency: deploy`) ждёт текущий; отменять текущий нельзя — отменённый apply оставляет блокировку состояния.
2. Если деплой сейчас не пройдёт (CI или раннер недоступны) — сменить пароль руками на сервере тем же значением, что в новом секрете: `docker exec -it dmc268-postgres psql -U dmc268 -d dmc268 -c '\password dmc268'` или `docker exec -it dmc268-rabbitmq rabbitmqctl change_password dmc268`. Старые API и воркер до деплоя новых соединений не откроют — это цена; деплой потом скажет «совпадает».
3. **Закрыть открытые соединения**: смена пароля их не рвёт, и вошедший утёкшим паролем остаётся внутри. После деплоя все свои клиенты пересозданы и подключены заново, поэтому всё, что открыто раньше смены, — чужое или старое:

   ```bash
   docker exec dmc268-postgres psql -U dmc268 -d dmc268 -XtAc "select pg_terminate_backend(pid) from pg_stat_activity where usename = 'dmc268' and client_addr is not null and backend_start < '<время смены, UTC>'"
   docker exec dmc268-rabbitmq rabbitmqctl -q list_connections name user peer_host connected_at
   docker exec dmc268-rabbitmq rabbitmqctl close_connection "<name>" "ротация пароля"
   ```

4. Где ещё лежит прежнее значение: в `env` контейнеров `dmc268-postgres` и `dmc268-rabbitmq` — пароль инициализации тома (`ignore_changes`, после смены не действует) и в состоянии OpenTofu (там все секреты стека — утечка состояния равна утечке всех паролей, их меняют все).

## Стек наблюдаемости

Рядом с API на стенде стоит стек телеметрии из двенадцати контейнеров: OTel Collector
(`dmc268-otelcol`: трейсы, логи, метрики приложения и базы), его второй экземпляр
`dmc268-otelcol-docker` (метрики контейнеров), третий `dmc268-otelcol-logs` (логи postgres, его
реплики и rabbitmq, см. «Логи контейнеров»), Loki (логи), Tempo (трейсы), Prometheus
(метрики), Grafana (интерфейс, `grafana_port` на `bind_ip`), `node-exporter` (сервер: CPU,
память, диски) и socket-proxy (`dmc268-docker-proxy`: Docker API для `dmc268-otelcol-docker` по
белому списку эндпоинтов вместо маунта `docker.sock`; отдельная сеть `dmc268-docker-proxy`, где
кроме proxy и `dmc268-otelcol-docker` никого), а для алертов — Alertmanager
(`dmc268-alertmanager`, доставка в Telegram) и два экземпляра blackbox-exporter
(`dmc268-blackbox` — пробы сервисов, `dmc268-blackbox-public` — публичного входа); подробно —
«Алерты».
Сеть стека `dmc268-observability` — `internal`, как и сеть данных: из неё в интернет не выйти,
а публикуемый порт Grafana живёт в отдельной не-internal сети `dmc268-grafana` — порты на
internal-сети Docker не публикует. Выход наружу через эту сеть есть только у Grafana, и её
собственные походы наружу выключены env: статистика (`GF_ANALYTICS_REPORTING_ENABLED`),
проверки обновлений Grafana и плагинов (`GF_ANALYTICS_CHECK_FOR_UPDATES`,
`GF_ANALYTICS_CHECK_FOR_PLUGIN_UPDATES`). Локальный compose повторяет раскладку: сеть
`observability` — `internal`, порт Grafana — через отдельную сеть `grafana`.
Белый список — свой шаблон haproxy (`observability/docker-socket-proxy.cfg`), а не
env-переменные образа: `CONTAINERS=1` открывал любой GET под `/containers`, вплоть до чтения
файлов контейнеров через `/archive` (замечание ревью PR #130); в compose шаблон монтируется
по пути, который рендерит entrypoint образа, на стенде заливается тем же `upload`, что и
остальные конфиги.
Метрики базы снимает сам коллектор — receiver `postgresql` (решение #89), отдельного экспортёра
Postgres нет. Конфиги лежат в `observability/` и **те же самые** используются локальным
docker compose (профиль `observability`): различия окружений — только переменные и лимиты, не
конфиги. Образы стека зафиксированы дайджестами (`имя@sha256:…`, дайджест манифест-листа) в
`locals.tf` и в `docker-compose.yml` — одинаково; тег в комментарии рядом, обновление образа —
осознанная замена дайджеста в обоих файлах, с чтением breaking changes.

Конфиги заливаются в контейнеры при создании (`upload` в `docker_container`): tofu читает их из
рабочей копии и передаёт через Docker API, поэтому на сервере не нужен чекаут репозитория. Правка
конфига пересоздаёт контейнер следующим `apply`; если провайдер не заметил изменение содержимого,
контейнер пересоздают явно (`tofu apply -replace=docker_container.otelcol`). Из-за `upload`
коллектор стенда живёт без `read_only` (заливка — запись в rootfs, read-only демон отклоняет
её до всякого пути): вместо неё — `cap_drop ALL` и `no-new-privileges`. Локальный коллектор
read_only: конфиг приходит read-only маунтом. Локально тот же
стек поднимается профилем: `OTEL_TRACES_EXPORTER=otlp OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp docker compose -f docker-compose.yml -f infra/observability/compose.logs.yml
--profile observability up -d` (Grafana — http://127.0.0.1:3000 без логина; второй файл
отправляет логи postgres и rabbitmq в Loki, без него стек поднимается и на podman).

Экспорт телеметрии API, воркера и миграций включён окружением (`local.telemetry_env`): трейсы,
метрики и логи уходят коллектору по OTLP. `service.version` берётся из тега `api_image` (это sha
коммита сборки), окружение задаёт `deployment_environment_name` — `production`, потому что стенд
и есть прод (#97), то же значение шлёт кабинет (#108); `service.instance.id` у каждого сервиса
своё и стабильное (`dmc268-api`, `dmc268-worker`, у миграций — `dmc268-migrations` из выхода
`migrate_env`, локально в compose — `dmc268-migrate`) — вместо случайного UUID на
процесс, который растил бы в Prometheus серии `exported_instance`. Таймаут OTLP — 4 секунды
(`OTEL_EXPORTER_OTLP_TIMEOUT`): Python SDK читает переменную в секундах, вопреки спецификации
OTel с её миллисекундами. Логи сервисов коллектор получает только по OTLP, логи postgres, его
реплики и rabbitmq — от `dmc268-otelcol-logs` («Логи контейнеров»); каталог Docker не читает ни один
коллектор. Чувствительные данные основной коллектор редактирует до отправки
(`observability/otelcol.yaml`), коллектор логов — своими правилами (`observability/otelcol-logs.yaml`);
тест `tests/infrastructure/test_collector_redaction.py`.

### Включение и выключение: observability_enabled

Стек поднимается только по флагу `observability_enabled`, по умолчанию `false`: локальному
`apply` без него хватает памяти, а секреты стека не нужны. Включают переменной окружения
`TF_VAR_observability_enabled=true` — так делает деплой стенда (`deploy.yml`) — или строкой
`observability_enabled = true` в `terraform.tfvars` (пример закомментирован в
`terraform.tfvars.example`); эффект одинаковый.

За флагом идёт всё разом: девять контейнеров стека и их образы, сети стека —
`dmc268-observability`, `dmc268-grafana` и `dmc268-logs` — вместе с сетью socket-proxy
(`count = 1 : 0` у каждого ресурса), `telemetry_env` — `OTEL_*_EXPORTER=otlp`, адрес коллектора
и таймаут в env api, воркера и миграций, — `command` контейнера Postgres (при флаге база
стартует с `shared_preload_libraries=pg_stat_statements`, без флага — с родным `CMD` образа) и
драйвер логов Postgres, его реплики и RabbitMQ (`fluentd` вместо `json-file`, «Логи контейнеров»). Смена
`command` и драйвера пересоздаёт контейнеры (тома данные сохраняют), поэтому переключение флага —
осознанное действие.

Первый деплой после включения флага требует замены базы, и автоматический деплой её не
сделает — он упадёт. Деплой стенда (`deploy.yml`) включает флаг, поэтому targeted-шаг «Поднять
базу и брокер» видит смену `command` и `dmc268-postgres must be replaced`, а сторож плана
(`.github/scripts/deploy/infra.sh`, `stateful_deletes` в `scripts/deploy_report.py`) такую
замену без `allow_stateful_replace` отклоняет: шаг красный, на сервере ничего не меняется. Первый
выкат после мерджа — ручной запуск
`gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true` (повтор — новым
запуском, не Re-run). Он заменяет `dmc268-postgres` с окном остановки 60 с
(`stop_timeout`/`destroy_grace_seconds`), база поднимается на прежнем томе. Пока длится замена,
старые api и воркер отвечают ошибками базы, а реплика теряет поток и переподключается сама,
когда основной сервер вернётся: том тот же, и слот репликации на нём сохраняется. Пересборка
реплики (`infra/postgres/replica-entrypoint.sh`) идёт только при потерянном слоте. Замену базы провайдер
делает до миграций и до замены api, так что короткий сбой видят только запросы в этот
интервал; следующие планы — `No changes`, и автоматический деплой снова проходит.

Выключение флага снимает контейнеры стека: приложение работает без телеметрии, а с пустым
`telemetry_env` SDK молчит — ни отправки, ни ошибок экспорта в логе. Томам с данными
(Loki, Tempo, Prometheus, Grafana) флаг не грозит: они объявлены без `count` и создаются
всегда, поэтому план с выключенным флагом поверх включённого стенда не пытается их уничтожить
(а `prevent_destroy` не встаёт на пути отката) — логи, метрики и трейсы переживают и
выключение, и повторное включение флага. Выключение, как и первое включение, меняет `command`
у `dmc268-postgres` (preload и `track_utility` идут за флагом), поэтому тоже выкатывается
ручным запуском с `allow_stateful_replace=true`: автоматический деплой упрётся в сторожа. Нюанс:
шаг миграций перегенерирует пароль роли `dmc268_monitor` при каждом деплое независимо от флага,
поэтому выключение стека на существующем стенде без секретов вернёт роли локальный
дефолтный пароль — держите секрет выставленным, пока роль существует.

При `observability_enabled = true` валидации переменных требуют секретов: непустой
`grafana_admin_password` (анонимный вход в Grafana на стенде выключен — без учётки в неё не
зайти) и настоящий `postgres_monitor_password`, не локальный дефолт `dmc268_monitor` (роль
становится входом в базу, открытым в docker-сети). Без секретов `apply` падает на проверке
переменной.

Переменные стека: `observability_enabled` (контейнеры, образы и сети стека — за флагом, см.
выше; тома с данными — нет), `observability_memory_mb`
(потолки памяти без свопа, девять контейнеров — таблица ниже), `grafana_port`, `grafana_admin_password`
(секрет; локально Grafana без логина, на стенде — по учётке), `postgres_monitor_password` (секрет, см.
таблицу выше), `deployment_environment_name`.
Метрики базы коллектор снимает receiver-ом `postgresql`: роль только-чтение `dmc268_monitor` с
`pg_monitor` создаёт миграция 0013, и она же создаёт расширение `pg_stat_statements` — коллектор его
не читает (медленные запросы им не собираются), расширение оставлено только для ручной диагностики;
`shared_preload_libraries` включает контейнер Postgres. RabbitMQ отдаёт метрики встроенным
плагином `rabbitmq_prometheus` (порт 15692 в сети, per-object эндпоинт — метрики очередей с
лейблом `queue`); сервер — `node-exporter` (9100), контейнеры — receiver `docker_stats`
экземпляра `dmc268-otelcol-docker` (`collector-docker:8889`, job `docker-stats`); свои метрики
отдают `dmc268-otelcol`, `dmc268-otelcol-docker` и `dmc268-otelcol-logs` (`otelcol_*` на `:8888`, на хосте не публикуется), Loki и Tempo; все скрейпятся
`prometheus.yml`. Дашборд «Обзор dmc-268» провиженится из репозитория
(`observability/grafana/provisioning/dashboards/`). Применение стека на стенд — задача DevOps
(#108).

### Метрики контейнеров

CPU, память, сеть и диск по каждому контейнеру снимает receiver `docker_stats`: он
спрашивает Docker API (`/containers/{id}/stats`) через socket-proxy, ряды различает лейбл
`container_name`. Белый список proxy — список, inspect, статистика и события контейнеров
(`/events`: без них новые контейнеры не находятся), `/info`, `/version`, `/_ping`; события и
статистика отдают имя, образ, метки, цифры и командные строки `docker exec` — без Env и файлов.
Поэтому секреты в командной строке `docker exec` не передаём (ротация пароля Grafana — через
stdin, см. `grafana_admin_password` в «Деплой»).

Receiver живёт в отдельном экземпляре коллектора `dmc268-otelcol-docker` (тот же образ, конфиг
`observability/otelcol-docker.yaml`), а не в основном `dmc268-otelcol`. Inspect через proxy
отдаёт Env всех контейнеров: ключи S3 бэкапа, пароль репликации, пароли Grafana и брокера.
Основной коллектор разбирает OTLP без аутентификации из сети данных и, через nginx интерфейса,
из интернета (`otlp/browser`); с доступом к proxy ошибка в разборе OTLP стала бы утечкой этих
секретов. У `dmc268-otelcol-docker` входящего OTLP нет, он стоит только в
`dmc268-observability` (оттуда его скрейпит Prometheus) и `dmc268-docker-proxy`. Второй довод —
надёжность: receiver на старте читает список контейнеров и без proxy не даёт подняться
процессу. В отдельном экземпляре сбой proxy гасит только метрики контейнеров, трейсы и логи
идут дальше.

**Почему не cAdvisor (#249).** До #249 метрики контейнеров снимал cAdvisor v0.52.1, и на стенде
он не видел ни одного контейнера: панели «CPU контейнеров» и «Память контейнеров» были пустыми,
в логе — `failed to identify the read-write layer ID` на каждый контейнер. Причина — Docker 29 на
стенде хранит образы в containerd (`docker info`: `driver-type io.containerd.snapshotter.v1`), и
каталога `/var/lib/docker/image/overlayfs/layerdb`, откуда cAdvisor берёт слой контейнера, нет.
Поддержка containerd snapshotter есть в cAdvisor с v0.54 (google/cadvisor#3709), но до последней
v0.60.6 включительно без сокета `/run/containerd/containerd.sock` фабрика docker не регистрируется
вовсе — исправление (google/cadvisor#3910) не смёржено. Сокет containerd — полный доступ к хосту,
а cAdvisor на ревью PR #130 сознательно увели от сокетов, корня хоста и root. Отключать
containerd snapshotter в Docker на стенде — перезапуск демона и перекачка всех образов. Поэтому
cAdvisor убран, а `docker_stats` берёт те же сигналы у Docker API: Docker отдаёт статистику
контейнера как бы ни хранил образы. Чего нет по сравнению с cAdvisor: метрик файловой системы
контейнера, PSI и OOM-событий — в дашборде и алертах их не было.

### Логи контейнеров

У Postgres, его реплики и RabbitMQ нет OTel SDK, поэтому со стеком их stdout забирает сам демон Docker:
драйвер логов `fluentd` (`local.fluentd_log_opts` в `locals.tf`, `logging` в
`observability/compose.logs.yml` для compose) шлёт
каждую строку на `tcp://127.0.0.1:24224`. Там слушает третий экземпляр коллектора
`dmc268-otelcol-logs` (тот же образ, конфиг `observability/otelcol-logs.yaml`): receiver
`fluent_forward`, имя сервиса из тега драйвера (имя контейнера), маскирование и отдача основному
коллектору по OTLP (`collector:4318`), а дальше — общий конвейер логов в Loki:
`{service_name="dmc268-postgres"}`, `{service_name="dmc268-postgres-replica"}`,
`{service_name="dmc268-rabbitmq"}`. Коллектор логов заменяет
маркером `<скрыто>` IPv4-адреса (клиент в начале access-лога nginx, `client:` в его error-логе,
адреса соединений брокера), query в URL (коды OAuth в запросе обратного вызова nginx и в
Referer), пароль в `PASSWORD '…'` и `DETAIL` ошибок Postgres со значениями ключей и строк таблиц (`Key (…)=(…)`,
`Failing row contains`). Пароль роли мониторинга `migrate.sh` и миграция 0013 шлют литералом:
если `ALTER ROLE` упадёт, Postgres запишет запрос в `STATEMENT`, и скрывает пароль только это
правило. IPv6 не маскируется: сети Docker стенда только IPv4. Примеры —
`tests/infrastructure/test_collector_redaction.py`.

Маскирование построчное, поэтому в Loki остаются: текст `ERROR` (например, значение, не
прошедшее приведение типа), прочие `DETAIL` (например, `Token "…" is invalid` у jsonb),
`CONTEXT`, `STATEMENT` (значения параметров psycopg привязывает на сервере, в тексте только
`$N`) и продолжения многострочного значения после `DETAIL`. Пароль скрывается до конца строки:
литерал с `\'` скрыт целиком, а у многострочного скрыта только первая строка.

Почему отдельный экземпляр, а не receiver основного коллектора: публикация порта требует
не-internal сети, а основной коллектор, который принимает трейсы браузера из интернета, стоит
только в internal-сетях и выхода наружу не имеет.

Почему не чтение файлов. В `/var/lib/docker/containers` рядом с логами лежит `config.v2.json` с
Env всех контейнеров (пароли базы, брокера, репликации, Grafana, ключи S3), а Docker API отдаёт
тот же Env через inspect. Поэтому ни файлов, ни Docker API у коллекторов за логами нет: строки
приносит демон, и коллектор логов видит только их. Порт `24224` опубликован лишь на `127.0.0.1`
хоста, к нему подключается демон Docker. Протокол без аутентификации, поэтому извне сервера
порт недоступен; из сети стека доступен, как OTLP основного коллектора. С internal-сети Docker порт не публикует, поэтому коллектор
логов, как Grafana, стоит в отдельной не-internal сети `dmc268-logs` (больше там никого) и в сети
стека — для отдачи основному коллектору; сетей данных и socket-proxy у него нет.

`fluentd-async`: контейнер стартует и пишет и без приёмника — драйвер копит записи в памяти
демона и досылает, когда коллектор логов поднимется; база и брокер от него не зависят. Буфер
— 10 000 записей на контейнер (`fluentd-buffer-limit`; по умолчанию 1 048 576, фактически без
потолка). Записи сверх него в Loki не попадают, а уходят ошибкой `Error writing log message` с
текстом строки в журнал dockerd (не больше 333 в секунду). `docker logs` у них работает через кэш dual
logging Docker с теми же потолками, что у `json-file` (`cache-max-size`, `cache-max-file`). Без стека драйвер — прежний `json-file`. В основном
`docker-compose.yml` драйвера `fluentd` нет: podman его не знает, а без приёмника демон зря
копит буфер. Его включает отдельный файл вместе со стеком:
`docker compose -f docker-compose.yml -f infra/observability/compose.logs.yml --profile
observability up -d`; без файла `docker logs` у postgres и rabbitmq работает как обычно, в Loki
записи не уходят. Реплика PostgreSQL (`dmc268-postgres-replica`) есть только на стенде, в compose
её нет; на стенде она тоже пишет через `fluentd`.

Выкат. Смена драйвера пересоздаёт `dmc268-postgres`, `dmc268-rabbitmq` и
`dmc268-postgres-replica` (тома прежние), и сторож
плана такую замену автоматическим деплоем не пропустит — выкат, как и включение флага выше,
ручным запуском `gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true`.
Targeted-шаг пересоздаёт базу и брокер с окном остановки 60 с до миграций; полный `apply` после
них пересоздаёт реплику (она снова проходит `check-replica.sh`) и поднимает
`dmc268-otelcol-logs`, и накопленные записи уходят в Loki. Пока идёт замена, api и
воркер отвечают ошибками базы и брокера.

Тег драйвера становится `service_name`. В infra это `{{.Name}}`, имя контейнера; в compose
`container_name` нет, и тег в `compose.logs.yml` записан тем же именем, что на стенде.

nginx интерфейса подключается так же в `dmc-268-ui-t1`: у `dmc268-ui` драйвер `fluentd` с теми
же опциями. Правила IP и query рассчитаны на его access- и error-лог по умолчанию и от тега не
зависят (задача 4.7 в `openspec/changes/observability-audit-fixes/tasks.md`).

### Алерты

Критические алерты (#100) считает Prometheus по правилам `observability/alerts.yml` и раз в
15 секунд отдаёт сработавшие Alertmanager (`dmc268-alertmanager`), тот шлёт их в Telegram
(`observability/alertmanager.yml`). Конфиги те же локально и на стенде; токен бота и chat id —
не в конфиге, а файлами `/etc/alertmanager/secrets/telegram_{bot_token,chat_id}`: на стенде их
заливает `upload` из секретов `TELEGRAM_BOT_TOKEN_DMC268_T1` и `TELEGRAM_CHAT_ID_DMC268_T1`,
локально — compose (`configs`) из `ALERT_TELEGRAM_BOT_TOKEN` и `ALERT_TELEGRAM_CHAT_ID`. Из
контейнеров алертов наружу ходят только Alertmanager (api.telegram.org) и
`dmc268-blackbox-public` (публичный вход стенда) — через свою не-internal сеть `dmc268-alerting`, портов на хосте у них нет.
Пробы сервисов делает другой экземпляр, `dmc268-blackbox`, — только в сети данных, там же его
скрейпит Prometheus: `/probe?target=` принимает любой URL без авторизации, и экземпляр с
выходом наружу или с путём до `dmc268-blackbox-public` (цепочка
`/probe?target=http://blackbox-public:9115/probe?target=…`) был бы прокси в интернет для
любого контейнера сети данных.

Поведение правил закрепляет `observability/alerts.test.yml`: на каждый алерт — синтетические
ряды «горит / молчит», `promtool test rules` в job `observability-configs`; там же
`amtool check-config` и проверка конфига blackbox. Связи между файлами — имена метрик и пути
секретов — держит `tests/infrastructure/test_alerting.py`.

**Бот и чат.** Бот создаётся у @BotFather (`/newbot`), его добавляют в группу или канал
команды. Chat id — из `https://api.telegram.org/bot<токен>/getUpdates` после любого
сообщения в чате (у групп и каналов он отрицательный, `-100…`). Оба значения —
секретами репозитория (таблица переменных выше). Пока их нет, Alertmanager получает заглушки —
токен `unset` и chat id `0`: правила работают, горящие алерты видны через `amtool alert query`
(ниже), а каждая попытка доставки пишет в его лог `Notify attempt failed … 404`.

**Пороги.** `critical` уходит сразу и повторяется раз в 4 часа, пока горит; `warning` — раз в
12 часов. Критический алерт сервиса глушит его же предупреждения (`inhibit_rules`: та же
метка `service`). Погасший алерт присылает сообщение «RESOLVED» (`send_resolved`).

| --- | --- | --- | --- |

| `ContainerRestarting` | перезапуски контейнера `dmc268-*` | 2 и больше за 15 минут | critical |
| `ServiceProbeFailed` | сервис не отвечает (то же, что видит его healthcheck): `/health` API, TCP базы, реплики, брокера | 2 минуты | critical |
| `PublicEndpointDown` | HTTPS публичного входа (`public_origin`) | 3 минуты | critical |
| `WorkerNotConsuming` | у `review_jobs.qq` нет потребителей или очереди нет совсем (при живом скрейпе брокера) | 5 минут | critical |
| `Api5xxSpike` | доля 5xx у API за 5 минут, при трафике больше 3 запросов в минуту | > 5 % дольше 5 минут | critical |
| `ReviewRunsFailing` | доля прогонов в `failed` за 30 минут, при 3+ прогонах | > 30 % | critical |
| `ReviewDlqNotEmpty` | сообщения в `review_jobs.dlq` | > 0 дольше 5 минут | critical |
| `LlmBudgetNearLimit` | токены модели с начала месяца (UTC) от бюджета `dmc268:llm_tokens_budget_month` — 50 млн | > 80 % | warning |
| `LlmBudgetExceeded` | то же | ≥ 100 % | critical |
| `LlmBudgetUnknown` | ряда расхода токенов нет — алерт бюджета слеп | 15 минут | warning |
| `DiskSpaceLow` | свободно на файловой системе сервера | < 15 % дольше 5 минут | warning |
| `DiskSpaceCritical` | то же | < 5 % дольше 2 минут | critical |
| `DiskWillFillIn24h` | прогноз по 6 часам: место кончится за сутки, при свободных < 40 % | 30 минут | critical |
| `ReplicaNotStreaming` | реплики нет в `pg_stat_replication` основного сервера | 5 минут | critical |
| `ReplicaLagHigh` | отставание реплики (слот держит WAL до `max_slot_wal_keep_size` 2 ГБ) | > 512 МБ дольше 10 минут | warning |
| `BackupStale` | последняя успешная копия (`dmc268_backup_last_success_timestamp_seconds`) | старше 26 часов | critical |
| `BackupStatusUnknown` | отметки о копии нет совсем | 26 часов | critical |
| `TlsCertificateExpiringSoon` | срок сертификата публичного входа (`shortlived`, 160 часов, продлевается на середине) | < 48 часов дольше 10 минут | critical |
| `ScrapeTargetDown` | цель скрейпа Prometheus не отвечает — её алерты слепы | 5 минут | warning |

Бюджет токенов — константа в `alerts.yml` (`dmc268:llm_tokens_budget_month`), а не
переменная: конфиги стека одинаковы в обоих окружениях. Смена бюджета — правка этой строки и
таблицы выше. Расход берётся из `review_runs.tokens_used` запросом receiver-а `sqlquery`
основного коллектора под ролью `dmc268_monitor`; ревизия 0017 даёт ей `SELECT` только на
`created_at` и `tokens_used`. Разбивка по типам токенов, стоимость и баланс провайдера — #119.

**Чего алерты не видят.** Статуса healthcheck контейнера у receiver `docker_stats` 0.158 нет
(`container.state.health.status` появился в 0.160), поэтому «unhealthy» ловят пробы
blackbox-exporter по тем же проверкам, а свежесть копий — отметка от `backup.sh`. Если упал
сам Prometheus или Alertmanager, алертов нет вовсе: внешнего «dead man's switch» у стенда пока
нет. Локально часть алертов горит всегда: реплики, копий и интерфейса там нет, а контейнеры
compose называются по проекту (`<проект>-api-1`), поэтому `ContainerDown` горит по всем
именам `dmc268-*`.

**Проверка доставки.** Тестовый алерт напрямую в Alertmanager стенда, минуя правила:

```bash
ssh stand 'docker exec dmc268-alertmanager amtool alert add alertname=ТестДоставки severity=critical service=test --annotation=summary=Тестовый-алерт --annotation=description=Проверка-доставки-в-Telegram --alertmanager.url=http://127.0.0.1:9093'
```

Сообщение приходит через `group_wait` (30 секунд); не пришло — ошибка доставки в логе
Alertmanager (`Notify attempt failed`, 401 — неверный токен, 400 — неверный chat id или бот не
в чате, 404 — заглушка вместо токена). При сетевой ошибке Alertmanager пишет в лог URL
целиком, **с токеном бота** (`…/bot<токен>/sendMessage`): лог смотрим только с маской и сырым
никуда не вставляем —

```bash
ssh stand 'docker logs dmc268-alertmanager 2>&1' | sed -E 's#/bot[^/]+/#/bot***/#g' | grep -i notify
```
 Горящие алерты и тишины —
`docker exec dmc268-alertmanager amtool alert query --alertmanager.url=http://127.0.0.1:9093`;
заглушить на время работ — `amtool silence add alertname=… --duration=2h …` там же.

### Диск

Диск на стенде один на всё: тома данных стека и PostgreSQL растут на одной файловой системе,
и его объём в README пока не зафиксирован — снять факт можно `df -h /` на сервере.
У `docker_volume` размера нет — потолок задаёт только само приложение, если умеет:

| Что | Потолок | Откуда |
| --- | --- | --- |
| метрики Prometheus | ≤ 8 ГБ и не дольше 30 дней | `--storage.tsdb.retention.size=8GB` и `--storage.tsdb.retention.time=30d` (`observability.tf`, compose) |
| логи Loki | только 30 дней (`retention_period: 720h`), лимита по размеру нет | `observability/loki.yaml` |
| трейсы Tempo | только 14 дней (`block_retention: 336h`), лимита по размеру нет | `observability/tempo.yaml` |
| логи контейнеров (json-file; у postgres, реплики и rabbitmq со стеком — кэш `docker logs` драйвера fluentd) | 30 МБ на контейнер (3 файла × 10 МБ) | `local.log_opts` и `local.fluentd_log_opts` в `locals.tf`, `logging.options` в compose и `observability/compose.logs.yml` |

Единственный компонент с потолком по размеру — Prometheus (8 ГБ): всплеск кардинальности не
забьёт диск раньше срока хранения. У Loki и Tempo такого лимита нет: записи старше срока
хранения удаляются, но суммарный объём под сроком ничем не ограничен. Теоретический потолок
Loki — скорость приёма 1 МБ/с (`ingestion_rate_mb: 1`) ≈ 86 ГБ в сутки: поток сверх лимита
Loki отбрасывает с 429 и долг не копит, но всё принятое до отбрасывания пишет на диск.
Лимита нет, но заполнение ловят алерты по `node_filesystem_avail_bytes` от node-exporter:
`DiskSpaceLow`, `DiskSpaceCritical` и прогноз `DiskWillFillIn24h` (раздел «Алерты»).

Ожидаемые объёмы: под ротацию json-file попадает 13 контейнеров этого стека (4 приложения —
api, worker, копии, replication-setup — и 9 наблюдаемости) — не больше 390 МБ, и ещё
до 90 МБ — кэш `docker logs` у postgres, реплики и rabbitmq. В Loki пишут api, worker,
одноразовый migrate, postgres, реплика и rabbitmq. При допущении «запись в секунду на сервис по 1 КБ» — 6 КБ/с ≈
520 МБ в сутки ≈ 15,5 ГБ за 30 дней на все шесть; индекс TSDB Loki (период 24 ч) и рабочие файлы compactor в оценку не входят.

## Хранилище состояния

Состояние OpenTofu лежит не рядом с конфигурацией, а в S3-совместимом хранилище (RustFS) на том же сервере (`backend.tf`). Так оно переживает прогон раннера GitHub Actions, который исчезает вместе со своим диском.

Хранилище слушает только `127.0.0.1`, поэтому `tofu` любой командой, которой нужно состояние, работает через SSH-туннель:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
```

Учётные данные хранилища передаются как `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`; в CI они приходят из секретов `S3_USER_DMC268_T1` и `S3_PASSWORD_DMC268_T1`. Состояния API и UI лежат в одном бакете `dmc268-tfstate` под разными ключами.

Состояние блокируется на время каждой команды, которая его меняет (`use_lockfile`): OpenTofu кладёт рядом lock-объект условной записью, и второй запуск получает `Error acquiring the state lock` с ID блокировки. Шаги деплоя ждут чужую блокировку до двух минут (`-lock-timeout=2m` у targeted apply, плана и apply), а не падают сразу: так короткий ручной `plan` деплой не роняет. Блокировку, оставленную другим деплоем (`Who` — `runner@…`), снимает следующий деплой сам (раздел «Если деплой упал посреди apply»). Блокировку ручного запуска снимают вручную — только убедившись, что никто больше не работает с состоянием:

```bash
cd infra && tofu force-unlock <ID из ошибки>
```

Сам контейнер хранилища **не входит в этот стек**: его поднимает composite action `.github/actions/s3-backend` шагом job'а деплоя перед `tofu apply`, а не OpenTofu, иначе `apply` мог бы снести хранилище собственного состояния. Практическое следствие: `tofu destroy` его не удалит, и полная зачистка сервера состоит из двух шагов — `tofu destroy` со снятой защитой томов (раздел «Развёртывание и удаление»), а затем `docker rm -f dmc268-s3` и `docker volume rm dmc268-s3-data` вручную.

### Если деплой упал посреди apply

Самый дорогой сбой деплоя — пропавшая связь с хранилищем, пока OpenTofu пишет состояние. Что делает OpenTofu 1.13.2 (проверено на `docker:29-dind` с RustFS 1.0.3): промежуточная запись состояния падает, и apply останавливается, не трогая оставшиеся ресурсы; несохранённое состояние ложится в `infra/errored.tfstate` на раннере и исчезает вместе с ним; блокировка не снимается — объект `api/terraform.tfstate.tflock` остаётся в бакете, а её ID в выводе apply нет, он есть только в самом объекте. Следующий деплой упирается в блокировку, а после `force-unlock` — в старое состояние: план создаёт заново контейнеры, которые apply уже создал, и падает на `Conflict. The container name "/dmc268-api" is already in use`.

Деплой чинит это сам. Шаг `Восстановить состояние OpenTofu` (`.github/scripts/deploy/recover-state.sh`) идёт, если упал или оборван (отмена, таймаут job'а) шаг, который пишет состояние или держит блокировку (`Поднять базу и брокер`, план, apply): заново открывает туннель, ждёт хранилище до двух минут, сверяет `errored.tfstate` с состоянием в хранилище, записывает его (`tofu state push` под той же блокировкой, без `-force`) и снимает блокировку этого раннера. Оборванная запись оставляет в хранилище ту же линию (lineage) и serial меньше нашего; другую линию или serial не меньше нашего скрипт не перетирает: сам `state push` без `-force` отказывает, только если линия другая или наш serial меньше, а с тем же serial перетёр бы чужую запись. Итог — раздел «Состояние OpenTofu» в summary; если состояние не пострадало и восстанавливать нечего (например, шаг упал на стороже базы в `infra.sh`), раздела нет. После этого достаточно перезапустить деплой («Re-run failed jobs»): он доделает выкат. Исключение — запуск с `allow_stateful_replace`: Re-run флага не получает, и доделывает выкат новый `gh workflow run deploy.yml --ref develop -f allow_stateful_replace=true` — так и пишет summary.

Блокировку другого раннера (`Who` — `runner@…`) восстановление тоже снимает: деплои идут строго по одному (`concurrency: deploy`), и её оставил запуск, который уже кончился, — иначе в неё упирался бы каждый следующий деплой. Так же снимается своя блокировка, если шаг оборвали: убитый tofu `errored.tfstate` не пишет. Записалось ли состояние под такой блокировкой, неизвестно: у блокировки apply в summary — предупреждение, что состояние может быть старше стенда; если план перезапуска создаёт контейнеры, которые на сервере уже есть, — шаг 4 ниже. Блокировку ручного `tofu` (`Who` — `пользователь@хост`) деплой не трогает никогда.

Если восстановление не вышло, а `errored.tfstate` был, его копия, зашифрованная отдельным случайным ключом (секрет `STATE_BACKUP_KEY_DMC268_T1`, `openssl rand -base64 48`; не пароль хранилища — он открывал бы состояние каждому, кто знает пароль), уходит артефактом `errored-tfstate` прогона на сутки. Открытым текстом состояние не загружается: в нём пароли, а репозиторий публичный.

Зависшее хранилище (соединение живо, ответа нет) ловит сторож туннеля `.github/scripts/s3-watchdog.sh`: таймаута запроса у s3-бэкенда OpenTofu нет, и без него запись состояния висела бы до таймаута job'а. Через две минуты без ответа сторож закрывает туннель, apply падает с `errored.tfstate`, и дальше — то же восстановление.

Если в summary «Состояние не восстановлено», причина — там же. Руками, убедившись, что никто больше не работает с состоянием (нет идущего деплоя, ручного `apply`):

1. Туннель и учётные данные — как в разделе «Развёртывание и удаление».
2. Посмотреть блокировку: `aws --endpoint-url http://127.0.0.1:9000 s3 cp s3://dmc268-tfstate/api/terraform.tfstate.tflock -` — `ID`, кто (`Who`) и когда (`Created`) её взял.
3. Если `errored.tfstate` есть — артефакт `errored-tfstate` прогона (сутки): `gh run download <id прогона> -n errored-tfstate`, затем `STATE_BACKUP_KEY=… openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -pass env:STATE_BACKUP_KEY -in errored.tfstate.enc -out infra/errored.tfstate`. Сверить с хранилищем: `tofu state pull | jq '.lineage, .serial'` — линия та же, serial меньше, чем в файле, иначе в хранилище запись после нашей, и файл не нужен. Записать: `cd infra && tofu state push -lock=false errored.tfstate`, пока блокировка висит; не перетирать `-force`. Файл после записи удалить.
4. Если файла нет, состояние в хранилище старше стенда. `tofu plan` покажет, что он хочет создать заново: контейнеры, которые на сервере уже есть, либо удалить с сервера (`ssh <сервер> docker rm -f dmc268-api dmc268-worker` — следующий деплой создаст их, это короткий простой стенда), либо взять в состояние: `tofu state rm docker_container.api` и `tofu import docker_container.api <id контейнера>`. Тома (`docker_volume.postgres`, `docker_volume.rabbitmq`) не трогать: их защищает `prevent_destroy`, и план с их заменой не пройдёт.
5. Снять блокировку: `tofu force-unlock <ID>` и перезапустить деплой.

## Развёртывание и удаление

Штатный путь один: **мерж в `develop`**. Дальше всё делает `deploy.yml` — собирает образ, поднимает хранилище состояния, базу и брокер, применяет миграции и конфигурацию, проверяет `/health` и что воркер работает. Руками ничего запускать не нужно и, как правило, не получится.

Локальный запуск перестал быть самодостаточным с появлением `backend.tf`: состояние лежит в хранилище на сервере, поэтому любая команда, которой нужно состояние, требует открытого туннеля и учётных данных хранилища:

```bash
ssh -i <ключ> -o ExitOnForwardFailure=yes -f -N -L 9000:127.0.0.1:9000 <user>@<server>
export AWS_ACCESS_KEY_ID=<логин хранилища> AWS_SECRET_ACCESS_KEY=<пароль> AWS_DEFAULT_REGION=us-east-1
cd infra && tofu init && tofu plan
```

Ключ и учётные данные лежат в секретах GitHub и наружу не отдаются, так что у большинства их не будет — и это нормально: чтобы разрабатывать, разворачивать стенд не нужно, достаточно `docker compose up` из корня репозитория.

Проверить конфигурацию без доступа к состоянию можно всегда — то же делает job `opentofu` в `ci.yml`:

```bash
cd infra && tofu fmt -check -recursive && tofu init -backend=false && tofu validate && tofu test
```

`tofu test` гоняет `tests/*.tftest.hcl` с `mock_provider "docker"`: ни Docker, ни сервер не нужны. Тесты проверяют адреса базы и брокера в окружении контейнеров и в `migrate_env`, какие секреты получает какой контейнер, раскладку по сетям и порты, грейс-период воркера и штатную остановку базы, реплики и брокера, образ `api` и `worker` по digest без тега, `wait` у базы, ожидание `healthy` у API и формат длительностей его healthcheck, проверки переменных. Проверки отклоняют на `plan`, пока сервер не тронут: пустые `github_webhook_secret`, `postgres_password`, `rabbitmq_password`, пустой или короткий `postgres_replication_password` (незаданный секрет CI приходит пустой строкой), `llm_backend = "ollama"` без `ollama_model`, `llm_hosted_fallback` без `ollama` и всех `eurorouter_*`, `api_image` без digest.

`tofu destroy` **падает на томах** базы, брокера, реплики и копий: у них `prevent_destroy = true`, и OpenTofu отказывается строить план, который их уничтожает. Удалить стенд осознанно — с данными — можно, только сняв защиту: заменить `prevent_destroy = true` на `false` в `postgres.tf`, `rabbitmq.tf` и `replica.tf` локально (не в коммите), затем `tofu destroy`. Без этого `tofu destroy` не тронет ничего: ошибка — до изменений. Контейнер хранилища состояния `tofu destroy` не удаляет и так — он не входит в этот стек намеренно. Полная зачистка описана выше, в разделе «Хранилище состояния».

Этот стек только для API. UI деплоится отдельно из `dmc-268-ui-t1/infra/`.
