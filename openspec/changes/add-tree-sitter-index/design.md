# Design: add-tree-sitter-index

## Context

Контур AST-уровня уже в `develop` (change `add-context-engine-and-repo-rules`):
порты `CacheStore` и `DefinitionExtractor` существуют и потребляются,
`InMemoryCacheStore` кэширует правила по ключу «репозиторий, base_sha»,
`TreeSitterDefinitionExtractor` извлекает контуры файлов на пяти грамматиках
(Python, TypeScript, TSX, JavaScript, Go — зависимости tree-sitter уже в
`pyproject.toml`), а `build_review_context` довыбирает изменённые файлы на
`head_sha` через `VcsGateway.fetch_file(..., max_bytes=...)` и кладёт
AST-окружение изменённых строк уровнем `ast` (спека `context-assembly`).
Сигнатуры остальных файлов репозитория в контекст не попадают, хотя §2
`docs/SYSTEM_DESIGN.md` называет «сигнатуры из файлов, на которые ссылаются
импорты» запланированными. Не хватает трёх вещей: списка файлов коммита
(`fetch_tree` — разрешение импортов в пути), кэша определений основной
ветки и потребления его записей.

Правило «контекст без клона» (§2 `docs/SYSTEM_DESIGN.md`) запрещает клонировать
и хранить репозиторий; tree-sitter за портом упомянут в нём как
запланированный шов. Мотивация и состав изменений — в proposal.md, контракты
поведения — в дельтах спек.

Ограничения, определяющие решения: правило `uv sync --all-extras` для
зависимостей (колёса tree-sitter под cp314 уже проверены — отдельный спайк не
нужен), проверка `lint-imports` для направленности зависимостей, одна ревизия
Alembic (миграций в change нет).

## Goals / Non-Goals

**Goals:**

- Ленивая довыборка определений при прогоне ревью: по импортам изменённых
  файлов выбираются соседние файлы; промах по ключу
  «репозиторий, base_sha, путь» → довыборка файла и извлечение; попадание →
  переиспользование без запросов и парсинга.
- Потребление сразу: сигнатуры основной ветки, релевантные диффу, попадают в
  контекст прогона вторым источником уровня `ast`.
- Переиспользование существующих швов: `CacheStore`, `DefinitionExtractor`,
  реестр языков и `fetch_file` — без новых портов, адаптеров и грамматик;
  из инфраструктуры добавляется только `fetch_tree`.

**Non-Goals:**

- Упреждающая переиндексация по push-вебхуку — вернётся вместе с
  durable-хранилищем `CacheStore` (Redis, §4.3) и по измерениям латентности
  первых прогонов.
- Полный словарь сигнатур всего репозитория — довыборка идёт по требованию и
  ограничивается соседями по импортам; обход всего дерева не делается.
- Векторный поиск и хранение содержимого файлов — только определения.
- Новые грамматики: реестр уже покрывает пять языков; расширение — запись в
  реестре и зависимость, спеки не меняются.
- Redis-адаптер `CacheStore` — появляется вместе со второй репликой (§4.3).

## Decisions

**D1. Определения кэшируются на base_sha прогона, а не на head_sha MR.**
`base_sha` из сообщения задачи (§4.2) — коммит основной ветки, от которого
пошёл PR. Ключ «репозиторий, base_sha, путь» неизменяем по построению и общий
для всех прогонов репозитория на этом коммите: записи стабильны и
переиспользуются между MR. MR-специфичные контуры изменённых файлов
по-прежнему довыбираются на `head_sha` прогона существующим AST-уровнем
(спека `context-assembly`, требование «AST-окружение изменённых строк») —
индекс их не вытесняет. Альтернатива — доставать определения на `head_sha`
MR: сосед по импорту меняется от MR к MR, записи почти не переиспользуются
между прогонами. Следствие: правка принципа «контекст без клона» в
`docs/SYSTEM_DESIGN.md` — довыборка файлов по sha через `VcsGateway` остаётся
единственным способом доступа к коду, полного клона нет.

**D2. Триггер — запрос соседа при прогоне ревью, а не push-вебхук.**
Определения довыбираются в момент, когда сборке контекста нужен конкретный
сосед, и результат получает текущий прогон. Индекс живёт в in-process
`CacheStore` воркера и сбрасывается при каждом рестарте; рестарт происходит
на каждом деплое, то есть на каждом мердже в `develop` — тот же push, который
запустил бы переиндексацию, стирал бы только что построенный словарь до
первого чтения. Упреждающая индексация без потребителя — то самое
«абстракция без второго вызова». Ленивая довыборка даёт потребителя немедленно
(сборка контекста прогона), не требует подписки App на событие `push` и
задачи в очереди и не тратит запросы к GitHub API на файлы, которые никто не
спросит: после мерджа в основную ветку `base_sha` новый, и первый прогон по
нему платит один запрос дерева и довыборку только своих соседей, а не до
`index_max_files` файлов всего репозитория. Альтернатива — push-вебхук +
задача переиндексации: упреждающе, но осмысленно только с durable-хранилищем
и потребителем; отложена (Non-Goals). Гонка двух прогонов на одном `base_sha`
безопасна: оба довыбирают те же файлы, каждый пишет то же содержимое в
неизменяемый ключ, последний пишущий сохраняет то же значение.

**D3. Хранение — существующий `CacheStore` в отдельном экземпляре, без миграций.**
Порт и in-process адаптер уже в `develop`; кэш правил — первый потребитель.
Записи индекса живут во втором экземпляре `InMemoryCacheStore` с собственным
лимитом `index_cache_max_entries`: смешивать их с кэшем правил в одном
экземпляре нельзя — адаптер ограничен числом записей, а не байтами, и общие
1024 записи выставили бы записи индекса против килобайтных правил. Отдельный
экземпляр с осознанным лимитом даёт верхнюю границу памяти: записи индекса —
определения одного файла, килобайты, граница — «записей × средний размер
записи»; байтовый лимит в адаптере менял бы контракт для уже работающего
потребителя и приходит вместе с Redis (§4.3). Записи двух видов: дерево путей
коммита по ключу «репозиторий, base_sha» и определения по ключу
«репозиторий, base_sha, путь». Содержимое по sha не меняется (§4.3), поэтому
записи не инвалидируются, а живут до TTL (`index_cache_ttl_seconds`) либо
вытесняются — штатные события: следующий запрос довыберет файл заново.
Отдельный маркер «проиндексированный sha» не нужен: попадание по ключу само
и есть коалесинг повторных запросов. Историю sha в базе не храним.
Альтернатива — таблицы `repository_heads` + `definitions` с миграцией:
durability, которую никто не требует (потребитель переживает промах), плюс
расход лимита миграций на feature без платёжного контракта.

**D4. Из швов добавляется только `fetch_tree`; `fetch_file` используется как есть.**
Парсинг уже спрятан за `DefinitionExtractor` (адаптер
`app/infrastructure/parsing/`, шов Strangler Fig), кэш — за `CacheStore`;
новых портов и адаптеров нет. `VcsGateway` расширяется единственным методом
`fetch_tree(repo_full_name, sha, installation_id)` — рекурсивный список путей
файлов дерева коммита. Он нужен для разрешения импортов: превратить
`app.domain.result` в существующий путь (`app/domain/result.py` или
`app/domain/result/__init__.py`) можно, только сверившись со списком файлов;
дерево кэшируется по ключу «репозиторий, base_sha» и служит многим прогонам.
GitHub trees API — тот же провайдер, те же installation-токены и backoff,
что у `fetch_diff` и `fetch_file`. Содержимое соседей довыбирается
существующим `fetch_file`: его контракт уже отвечает задаче — обязательный
`max_bytes` обрывает загрузку большого файла на лимите
(`VcsFileTooLargeError`), отсутствие файла — `None`. Усечение дерева самим
GitHub (флаг `truncated`) — не сбой, а частичный список: импорт, чей путь не
нашёлся в доступной части, разрешить нельзя — сосед пропускается без сбоя.
Лимиты (число соседей, время) применяет вызывающий сценарий, адаптер только
транспортирует.

**D5. Реестр грамматик переиспользуется, новых языков индекс не добавляет.**
`language_for_path` (домен, `app/domain/code_context.py`) уже отображает
расширения пяти языков на грамматики — общий реестр AST-уровня и индекса
(комментарий в модуле это фиксирует). Запрос соседа фильтруется тем же
реестром: файл без грамматики пропускается. Альтернатива — свой реестр для
индекса: два списка правды на один вопрос «какой у файла язык».

**D6. Лимиты конфигурацией, исчерпание — не сбой.**
`index_max_files`, `index_max_file_bytes`, `index_timeout_seconds`,
`index_cache_ttl_seconds`, `index_cache_max_entries` в `app/config.py`
(значения по умолчанию + override окружением, как остальные настройки).
`index_max_files` — сколько соседей довыбирается за один прогон: между
прогонами выбор не сохраняется, лимит ограничивает разовую работу. Размер
файла проверяется транспортом: `index_max_file_bytes` передаётся в `max_bytes`
вызова `fetch_file`, превышение прилетает `VcsFileTooLargeError` — штатный
пропуск файла. `index_timeout_seconds` ограничивает довыборку и парсинг
соседей одного прогона и обязан быть меньше `stale_run_timeout_seconds`
(1800): довыборка идёт внутри шага `BUILDING_CONTEXT` и отметок прогресса не
пишет, и при `index_timeout_seconds >= stale_run_timeout_seconds` выметатель
зависших прогонов объявит живой прогон мёртвым раньше, чем сработает лимит;
инвариант навязывается валидатором конфигурации при старте. Исчерпание
лимита соседей или времени — прогон получает уже довыбранные записи,
недобранные соседи просто не входят в пакет: частичный набор полезнее
отсутствия, добор произойдёт при следующем запросе. Это тот же принцип
«жёсткие лимиты» из §5 сборки контекста.

**D7. Потребление: один уровень `ast`, два источника, релевантность — дифф и его импорт-окрестность.**
Уровень `ast` уже означает AST-окружение изменённых строк; индекс не вводит
отдельного значения в `tiers`, а становится вторым источником того же уровня —
формат пакета новым тиром не расширяется. Из индекса запрашиваются только
соседи: файлы, разрешимые из импортов изменённых файлов по дереву коммита.
Записи для файлов диффа не добавляются безусловно — независимо от того,
попал ли контур файла на `head_sha` в AST-окружение: базовая версия
изменённого файла устарела, и отсутствие head-контура не делает её верной;
когда контур на `head_sha` есть, он и так побеждает как более свежий. Словарь
без фильтра раздавил бы бюджет токенов нерелевантными сигнатурами. Порядок
бюджета внутри уровня: AST-блоки изменённых файлов, затем записи индекса; не
поместившееся — в `omitted` с файлом и причиной, как у остальных уровней.
Выбор соседей и разрешение импортов в пути — чистые функции домена (по
образцу `select_scopes`), тестируются на литералах без tree-sitter и сети.
Сбой соседа не расширяется на прогон: слишком большой файл и неизвестный
язык — штатный пропуск; прочие `VcsError` и сбои извлечения — сосед не входит
в пакет и запись не сохраняется, следующий запрос повторит довыборку. Промах
или отсутствие записей ничего не меняет в составе остальных уровней.

## Risks / Trade-offs

- [Первый прогон по коммиту платит запрос дерева и довыборку ещё не
  закэшированных соседей — латентность прогона растёт умеренно: соседей
  единицы, а не всё дерево] → лимиты D6 ограничивают работу; если измерения
  покажут проблему — упреждающая переиндексация вернётся вместе с
  durable-хранилищем (D2, §4.3).
- [Память воркера растёт с числом закэшированных записей индекса] →
  отдельный экземпляр кэша с `index_cache_max_entries` (D3): записи
  килобайтные, граница — «записей × средний размер записи»; байтовый лимит —
  вместе с Redis.
- [Гонка одновременных прогонов на одном base_sha — двойная довыборка] →
  результаты идентичны по содержимому, побеждает то же значение; отдельный
  коалесинг не нужен.
- [Разрешение импортов в монорепо может распухнуть (широкие `__init__`,
  реэкспорты) и упереться в лимит соседей] → метрика в логах воркера
  (соседей довыбрано/пропущено, байт), решение о подстройке — по измерениям,
  не догадкам.
- [Импорт-окрестность разрешается по правилам языка и может ошибаться
  (реэкспорты, динамические импорты)] → пропущенный сосед — потеря полноты,
  не корректности: определения не попадают в контекст, но ложных не дают.
- [Словарь сигнатур раздувает контекст прогона] → фильтрация D7 и общий
  жёсткий лимит §5: записи индекса идут после AST-блоков изменённых файлов
  и вытесняются в `omitted`.

## Migration Plan

Схема базы не меняется — ни новых таблиц, ни новых очередей. Развёртывание не
требует изменений окружения: разрешение GitHub App **Contents: read** уже
нужно для `fetch_file` и покрывает trees API; новых подписок на события
вебхуков нет. Откат — реверт-коммит: two-way door, данные не затронуты
(`CacheStore` — эфемерное хранилище, чистить не нужно). База — `develop`:
вебхуки, очередь и контекст-движок смёржены, change опирается на их текущую
форму.

## Open Questions

- Пороговые значения лимитов (`index_max_files`, `index_max_file_bytes`,
  `index_timeout_seconds`, `index_cache_ttl_seconds`,
  `index_cache_max_entries`) фиксируются при реализации по данным первого
  прогона на реальном репозитории; спека требует лишь их наличия, поведения
  при исчерпании и инварианта таймаута (D6).
- Момент возврата упреждающей переиндексации (push-триггер) и Redis-адаптера
  `CacheStore` — по измерениям латентности первых прогонов после рестартов.
