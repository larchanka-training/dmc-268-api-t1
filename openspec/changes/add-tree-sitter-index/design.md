# Design: add-tree-sitter-index

## Context

Контур AST-уровня уже в `develop` (change `add-context-engine-and-repo-rules`):
порты `CacheStore` и `DefinitionExtractor` существуют и потребляются,
`InMemoryCacheStore` кэширует правила по ключу «репозиторий, base_sha»,
`TreeSitterDefinitionExtractor` извлекает контуры файлов на пяти грамматиках
(Python, TypeScript, TSX, JavaScript, Go — зависимости tree-sitter уже в
`pyproject.toml`), а `build_review_context` довыбирает изменённые файлы на
`head_sha` через `VcsGateway.fetch_file(..., max_bytes=...)` и кладёт
AST-окружение изменённых строк уровнем `ast` (спека `context-assembly`).
Сигнатуры остальных файлов репозитория в контекст не попадают, хотя §2
`docs/SYSTEM_DESIGN.md` называет «сигнатуры из файлов, на которые ссылаются
импорты» запланированными. Не хватает трёх вещей: списка файлов коммита
(`fetch_tree`), индекса определений основной ветки и потребления его словаря.

Правило «контекст без клона» (§2 `docs/SYSTEM_DESIGN.md`) запрещает клонировать
и хранить репозиторий; tree-sitter за портом упомянут в нём как
запланированный шов. Мотивация и состав изменений — в proposal.md, контракты
поведения — в дельтах спек.

Ограничения, определяющие решения: правило `uv sync --all-extras` для
зависимостей (колёса tree-sitter под cp314 уже проверены — отдельный спайк не
нужен), проверка `lint-imports` для направленности зависимостей, одна ревизия
Alembic (миграций в change нет).

## Goals / Non-Goals

**Goals:**

- Ленивое построение индекса определений при прогоне ревью: промах по ключу
  «репозиторий, base_sha» → сборка индекса; попадание → переиспользование без
  довыборки и парсинга.
- Потребление сразу: сигнатуры основной ветки, релевантные диффу, попадают в
  контекст прогона вторым источником уровня `ast`.
- Переиспользование существующих швов: `CacheStore`, `DefinitionExtractor`,
  реестр языков и `fetch_file` — без новых портов, адаптеров и грамматик;
  из инфраструктуры добавляется только `fetch_tree`.

**Non-Goals:**

- Упреждающая переиндексация по push-вебхуку — вернётся вместе с
  durable-хранилищем `CacheStore` (Redis, §4.3) и по измерениям латентности
  первых прогонов.
- Инкрементальная переиндексация (дельты коммитов) — полная сборка на промах;
  оптимизация отложена до измерений.
- Векторный поиск и хранение содержимого файлов — только определения.
- Новые грамматики: реестр уже покрывает пять языков; расширение — запись в
  реестре и зависимость, спеки не меняются.
- Redis-адаптер `CacheStore` — появляется вместе со второй репликой (§4.3).

## Decisions

**D1. Индекс строится на base_sha прогона, а не на head_sha MR.**
`base_sha` из сообщения задачи (§4.2) — коммит основной ветки, от которого
пошёл PR. Ключ «репозиторий, base_sha» неизменяем по построению и общий для
всех прогонов репозитория: индекс — стабильный словарь сигнатур.
MR-специфичные контуры изменённых файлов по-прежнему довыбираются на
`head_sha` прогона существующим AST-уровнем (спека `context-assembly`,
требование «AST-окружение изменённых строк») — индекс их не вытесняет.
Альтернатива — индексировать каждый head_sha MR: индекс почти не
переиспользуется между прогонами и вырождается в кэш парсинга. Следствие:
правка принципа «контекст без клона» в `docs/SYSTEM_DESIGN.md` — довыборка
файлов по sha через `VcsGateway` остаётся единственным способом доступа к
коду, полного клона нет.

**D2. Триггер — промах при прогоне ревью, а не push-вебхук.**
Индекс живёт в in-process `CacheStore` воркера и сбрасывается при каждом
рестарте; рестарт происходит на каждом деплое, то есть на каждом мердже в
`develop` — тот же push, который запустил бы переиндексацию, стирал бы только
что построенный индекс до первого чтения. Упреждающая индексация без
потребителя — то самое «абстракция без второго вызова». Ленивая сборка даёт
индексу потребителя немедленно (сборка контекста прогона), не требует подписки
App на событие `push` и задачи в очереди. Альтернатива — push-вебхук + задача
переиндексации: упреждающе, но осмысленно только с durable-хранилищем и
потребителем; отложена (Non-Goals). Гонка двух прогонов на одном `base_sha`
безопасна: оба строят одинаковый словарь, каждый пишет его в неизменяемый
ключ, последний пишущий сохраняет то же содержимое.

**D3. Хранение — существующий `CacheStore`, без миграций.**
Порт и in-process адаптер уже в `develop`; кэш правил — первый потребитель,
индекс — второй по тому же контракту best-effort. Содержимое по sha не
меняется (§4.3), поэтому запись «(репозиторий, base_sha) → определения» не
инвалидируется, а вытеснение — штатное событие. Отдельный маркер
«проиндексированный sha» не нужен: попадание по ключу само и есть коалесинг
повторных прогонов. Историю sha в базе не храним: при вытеснении следующий
прогон по тому же коммиту перестроит индекс — достаточно для best-effort
семантики. Альтернатива — таблицы `repository_heads` + `definitions` с
миграцией: durability, которую никто не требует (потребитель переживает
промах), плюс расход лимита миграций на feature без платёжного контракта.

**D4. Из швов добавляется только `fetch_tree`; `fetch_file` используется как есть.**
Парсинг уже спрятан за `DefinitionExtractor` (адаптер
`app/infrastructure/parsing/`, шов Strangler Fig), кэш — за `CacheStore`;
новых портов и адаптеров нет. `VcsGateway` расширяется единственным методом
`fetch_tree(repo_full_name, sha, installation_id)` — рекурсивный список путей
файлов дерева коммита; GitHub trees API — тот же провайдер, те же
installation-токены и backoff, что у `fetch_diff` и `fetch_file`. Содержимое
файлов довыбирается существующим `fetch_file`: его контракт уже отвечает
задаче индексации — обязательный `max_bytes` обрывает загрузку большого файла
на лимите (`VcsFileTooLargeError`), отсутствие файла — `None`. Усечение
дерева самим GitHub (флаг `truncated`) — не сбой, а частичный список: индекс
по доступной части валиден. Лимиты (число файлов, время) применяет вызывающий
сценарий, адаптер только транспортирует.

**D5. Реестр грамматик переиспользуется, новых языков индекс не добавляет.**
`language_for_path` (домен, `app/domain/code_context.py`) уже отображает
расширения пяти языков на грамматики — общий реестр AST-уровня и индекса
(комментарий в модуле это фиксирует). Индекс фильтрует дерево тем же реестром:
файл без грамматики пропускается. Альтернатива — свой реестр для индекса:
два списка правды на один вопрос «какой у файла язык».

**D6. Лимиты конфигурацией, исчерпание — не сбой.**
`index_max_files`, `index_max_file_bytes`, `index_timeout_seconds` в
`app/config.py` (значения по умолчанию + override окружением, как остальные
настройки). Размер файла проверяется транспортом: `index_max_file_bytes`
передаётся в `max_bytes` вызова `fetch_file`, превышение прилетает
`VcsFileTooLargeError` — штатный пропуск файла. Исчерпание лимита
файлов/времени — частичный индекс, который сохраняется и считается валидным:
частичный словарь сигнатур полезнее отсутствия индекса, добор произойдёт при
следующем промахе. Это тот же принцип «жёсткие лимиты» из §5 сборки контекста.

**D7. Потребление: один уровень `ast`, два источника, релевантность — дифф и его импорт-окрестность.**
Уровень `ast` уже означает AST-окружение изменённых строк; индекс не вводит
отдельного значения в `tiers`, а становится вторым источником того же уровня —
формат пакета новым тиром не расширяется. В пакет из индекса попадают только
определения, релевантные диффу: файлы, разрешимые из импортов изменённых
файлов (соседи). Записи для самих изменённых файлов не дублируются: их контур
на `head_sha` уже в пакете и побеждает как более свежий. Словарь без фильтра
раздавил бы бюджет токенов нерелевантными сигнатурами. Порядок бюджета внутри
уровня: AST-блоки изменённых файлов, затем записи индекса; не поместившееся —
в `omitted` с файлом и причиной, как у остальных уровней. Выбор записей и
разрешение импортов в пути файлов — чистые функции домена (по образцу
`select_scopes`), тестируются на литералах без tree-sitter и сети. Промах
индекса ничего не меняет в составе остальных уровней.

## Risks / Trade-offs

- [Первый прогон по коммиту после рестарта воркера платит полную индексацию —
  латентность прогона растёт] → лимиты D6 ограничивают работу, частичный
  индекс валиден; если измерения покажут проблему — упреждающая переиндексация
  вернётся вместе с durable-хранилищем (D2, §4.3).
- [Гонка одновременных прогонов на одном base_sha — двойная работа] →
  результаты идентичны по содержимому, побеждает тот же словарь; отдельный
  коалесинг не нужен.
- [Индексация монорепо может исчерпать лимит файлов и дать почти пустой
  индекс на первом прогоне] → метрика в логах воркера (файлов обработано/
  пропущено, байт), решение о частичной переиндексации — по измерениям,
  не догадкам.
- [Импорт-окрестность разрешается по правилам языка и может ошибаться
  (реэкспорты, динамические импорты)] → пропущенный сосед — потеря полноты,
  не корректности: определения не попадают в контекст, но ложных не дают.
- [Словарь сигнатур раздувает контекст прогона] → фильтрация D7 и общий
  жёсткий лимит §5: записи индекса идут после AST-блоков изменённых файлов
  и вытесняются в `omitted`.

## Migration Plan

Схема базы не меняется — ни новых таблиц, ни новых очередей. Развёртывание не
требует изменений окружения: разрешение GitHub App **Contents: read** уже
нужно для `fetch_file` и покрывает trees API; новых подписок на события
вебхуков нет. Откат — реверт-коммит: two-way door, данные не затронуты
(`CacheStore` — эфемерное хранилище, чистить не нужно). База — `develop`:
вебхуки, очередь и контекст-движок смёржены, change опирается на их текущую
форму.

## Open Questions

- Пороговые значения лимитов (`index_max_files`, `index_max_file_bytes`,
  `index_timeout_seconds`) фиксируются при реализации по данным первого
  прогона на реальном репозитории; спека требует лишь их наличия и поведения
  при исчерпании.
- Момент возврата упреждающей переиндексации (push-триггер) и Redis-адаптера
  `CacheStore` — по измерениям латентности первых прогонов после рестартов.
