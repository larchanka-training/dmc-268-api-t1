# Design: add-tree-sitter-index

## Context

Приём вебхуков, порт `VcsGateway` и очередь задач пришли в `develop` с PR #37:
гейт событий пропускает только `pull_request`, у `VcsGateway` есть лишь
`fetch_diff` и `fetch_pr_metadata`, воркер обрабатывает единственный тип задачи,
сообщение очереди несёт `base_sha` и `head_sha` прогона (§4.2). Порт
`CacheStore` из раздела 4.3 `docs/SYSTEM_DESIGN.md` спроектирован, но нигде не
реализован — этот change становится его первым потребителем. Правило «контекст
без клона» (раздел 2 `docs/SYSTEM_DESIGN.md`) запрещает клонировать и хранить
репозиторий; инструменты анализа кода (tree-sitter) упомянуты в нём как
запланированный шов. Мотивация и состав изменений — в proposal.md, контракты
поведения — в дельтах спек.

Ограничения, определяющие решения: Python 3.14 (доступность колёс tree-sitter
под свободнопоточную сборку — как у grimp, см. комментарий в `pyproject.toml`),
правило `uv sync --all-extras` для зависимостей, проверка `lint-imports` для
направленности зависимостей, одна ревизия Alembic (миграций в change нет).

## Goals / Non-Goals

**Goals:**

- Ленивое построение индекса определений при прогоне ревью: промах по ключу
  «репозиторий, base_sha» → сборка индекса; попадание → переиспользование без
  парсинга.
- Потребление индекса сразу: словарь сигнатур основной ветки попадает в
  контекст прогона (уровень `ast` в `tiers`).
- Соблюдение слоёв: tree-sitter только в инфраструктуре, решения — в чистых
  функциях домена/приложения.

**Non-Goals:**

- Упреждающая переиндексация по push-вебхуку — вернётся вместе с
  durable-хранилищем `CacheStore` (Redis, §4.3) и по измерениям латентности
  первых прогонов.
- Инкрементальная переиндексация (дельты коммитов) — полная сборка на промах;
  оптимизация отложена до измерений.
- Векторный поиск и хранение содержимого файлов — только определения.
- Грамматики кроме Python — расширение реестра не требует изменений спек.
- Redis-адаптер `CacheStore` — появляется вместе со второй репликой (§4.3).

## Decisions

**D1. Индекс строится на base_sha прогона, а не на head_sha MR.**
`base_sha` из сообщения задачи (§4.2) — коммит основной ветки, от которого
пошёл PR. Ключ «репозиторий, base_sha» неизменяем по построению и общий для
всех прогонов репозитория: индекс — стабильный словарь сигнатур. MR-специфичные
сигнатуры изменённых файлов по-прежнему довыбираются по `head_sha` прогона
(уровень `ast` в §5) — вне этого change. Альтернатива — индексировать каждый
head_sha MR: индекс почти не переиспользуется между прогонами и вырождается в
кэш парсинга. Следствие: правка принципа «контекст без клона» в
`docs/SYSTEM_DESIGN.md` — довыборка файлов по sha через `VcsGateway` остаётся
единственным способом доступа к коду, полного клона нет.

**D2. Триггер — промах при прогоне ревью, а не push-вебхук.**
Индекс живёт в in-process `CacheStore` воркера и сбрасывается при каждом
рестарте; рестарт происходит на каждом деплое, то есть на каждом мердже в
`develop` — тот же push, который запустил бы переиндексацию, стирал бы только
что построенный индекс до первого чтения. Упреждающая индексация без
потребителя — то самое «абстракция без второго вызова». Ленивая сборка даёт
индексу потребителя немедленно (сборка контекста прогона), не требует подписки
App на событие `push` и задачи в очереди. Альтернатива — push-вебхук + задача
переиндексации: упреждающе, но осмысленно только с durable-хранилищем и
потребителем; отложена (Non-Goals). Гонка двух прогонов на одном `base_sha`
безопасна: оба строят одинаковый словарь, каждый пишет его в неизменяемый ключ,
последний пишущий сохраняет то же содержимое.

**D3. Хранение — `CacheStore` по неизменяемым ключам, без миграций.**
Содержимое по sha не меняется (§4.3), поэтому запись
«(репозиторий, base_sha) → определения» не инвалидируется, а вытеснение —
штатное событие. Отдельный маркер «проиндексированный sha» не нужен: попадание
по ключу само и есть коалесинг повторных прогонов. Историю sha в базе не
храним: при вытеснении следующий прогон по тому же коммиту перестроит индекс —
достаточно для best-effort семантики. Альтернатива — таблицы
`repository_heads` + `definitions` с миграцией: durability, которую никто не
требует (потребитель переживает промах), плюс расход лимита миграций на
feature без платёжного контракта.

**D4. Парсинг за портом `DefinitionExtractor`; `VcsGateway` расширяется
методами `fetch_tree` и `fetch_file`.**
tree-sitter — вендор в слое инфраструктуры (адаптер
`app/infrastructure/parsing/`); домен получает чистые типы `Definition` и решение «язык по
расширению» как чистую функцию над реестром грамматик. Порт сохраняет шов
Strangler Fig: если биндинги разочаруют, `DefinitionExtractor` получит
сетевой адаптер без изменения слоёв выше (§5, BACKEND_ARCHITECTURE.md).
Довыборка файлов — через методы того же `VcsGateway`, а не отдельный порт:
GitHub trees/blobs — тот же провайдер, те же installation-токены и backoff;
лимиты (число файлов, байты) применяет вызывающий сценарий, адаптер только
транспортирует. Альтернатива — отдать парсеру сырые пути и позволить ему
ходить в сеть: смешивает чистое извлечение с I/O, тесты парсера требуют
сети.

**D5. Первая грамматика — Python; реестр «расширение → грамматика» — шов
для остальных.**
Репозиторий и первый контур ревью — Python; грамматика подключается как
обычная зависимость tree-sitter. Реестр — словарь в домене, добавление
языка — новая запись и зависимость, спеки не меняются (спека фиксирует
поведение «неизвестный язык пропускается»). Альтернатива — сразу все
популярные грамматики: восемь зависимостей без потребителя против правила
«абстракция без второго вызова».

**D6. Лимиты конфигурацией, исчерпание — не сбой.**
`index_max_files`, `index_max_file_bytes`, `index_timeout_seconds` в
`app/config.py` (значения по
умолчанию + override окружением, как остальные настройки). Превышение размера
файла — пропуск файла; исчерпание лимита файлов/времени — частичный индекс,
который сохраняется и считается валидным: частичный словарь сигнатур полезнее
отсутствия индекса, а добор произойдёт при следующем промахе. Это тот же
принцип «жёсткие лимиты» из §5 сборки контекста.

## Risks / Trade-offs

- [Нет колёс tree-sitter под cp314/свободнопоточную сборку → сборка из
  исходников потребует компилятор в образе] → первый таск — спайк:
  `uv add tree-sitter tree-sitter-python`, сборка образа, в `pyproject.toml`
  комментарий с зафиксированной версией; если провал — откат change без
  кода (ни один другой таск не начат).
- [Первый прогон по коммиту после рестарта воркера платит полную индексацию —
  латентность прогона растёт] → лимиты D6 ограничивают работу, частичный
  индекс валиден; если измерения покажут проблему — упреждающая переиндексация
  вернётся вместе с durable-хранилищем (D2, §4.3).
- [Гонка одновременных прогонов на одном base_sha — двойная работа] →
  результаты идентичны по содержимому, побеждает тот же словарь; отдельный
  коалесинг не нужен.
- [Индексация монорепо может исчерпать лимит файлов и дать почти пустой
  индекс на первом прогоне] → метрика в логах воркера (файлов обработано/
  пропущено, байт), решение о частичной переиндексации — по измерениям,
  не догадкам.
- [Словарь сигнатур раздувает контекст прогона] → тот же принцип «жёсткие
  лимиты» §5: словарь проходит через лимиты токенов сборки контекста наравне
  с другими уровнями.

## Migration Plan

Схема базы не меняется — ни новых таблиц, ни новых очередей. Развёртывание
требует одного изменения окружения: GitHub App нужно разрешение
**Contents: read** — через `VcsGateway` довыбираются git-деревья и блобы;
новых подписок на события вебхуков нет. Откат — реверт-коммит: two-way door,
данные не затронуты (CacheStore — эфемерное хранилище, чистить не нужно).
База — `develop`: PR #37 смёржен, change вливается независимо.

## Open Questions

- Пороговые значения лимитов (`index_max_files`, `index_max_file_bytes`,
  `index_timeout_seconds`)
  фиксируются при реализации по данным спайка на реальном репозитории;
  спека требует лишь их наличия и поведения при исчерпании.
- Момент возврата упреждающей переиндексации (push-триггер) и Redis-адаптера
  `CacheStore` — по измерениям латентности первых прогонов после рестартов.
