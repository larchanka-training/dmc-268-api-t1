# Design: add-tree-sitter-index

## Context

Приём вебхуков, порт `VcsGateway` и очередь задач появляются в PR #37
(`feat/architecture_and_vcs_context_engine`): гейт событий пропускает только
`pull_request`, у `VcsGateway` есть лишь `fetch_diff` и `fetch_pr_metadata`,
воркер обрабатывает единственный тип задачи. Порт `CacheStore` из раздела 4.3
`docs/SYSTEM_DESIGN.md` спроектирован, но нигде не реализован — этот change
становится его первым потребителем. Правило «контекст без клона» (раздел 2
`docs/SYSTEM_DESIGN.md`) запрещает клонировать и хранить репозиторий;
инструменты анализа кода (tree-sitter) упомянуты в нём как запланированный шов.
Мотивация и состав изменений — в proposal.md, контракты поведения — в дельтах
спек.

Ограничения, определяющие решения: Python 3.14 (доступность колёс tree-sitter
под свободнопоточную сборку — как у grimp, см. комментарий в `pyproject.toml`),
правило `uv sync --all-extras` для зависимостей, проверка `lint-imports` для
направленности зависимостей, одна ревизия Alembic (миграций в change нет).

## Goals / Non-Goals

**Goals:**

- Реиндексация репозитория по каждому коммиту в основную ветку: вебхук →
  очередь → воркер → индекс определений.
- Готовый словарь сигнатур по ключу «репозиторий, sha» для будущего
  AST-уровня сборки контекста (потребление индекса — вне этого change).
- Соблюдение слоёв: tree-sitter только в инфраструктуре, решения — в чистых
  функциях домена/приложения.

**Non-Goals:**

- Потребление индекса контекст-билдером (AST-уровень) — следующий change,
  когда у сборки контекста появится реальный источник данных PR.
- Инкрементальная переиндексация (дельты коммитов) — полная переиндексация
  на каждый коммит основной ветки; оптимизация отложена до измерений.
- Векторный поиск и хранение содержимого файлов — только определения.
- Грамматики кроме Python — расширение реестра не требует изменений спек.
- Redis-адаптер `CacheStore` — появляется вместе со второй репликой (§4.3).

## Decisions

**D1. Индекс строится на sha основной ветки, а не на head_sha MR.**
Выбор пользователя. Индекс — стабильный словарь сигнатур, общий для всех
прогонов репозитория; MR-специфичные сигнатуры изменённых файлов по-прежнему
довыбираются по `head_sha` прогона (уровень `ast` в §5). Альтернатива —
индексировать каждый head_sha MR: индекс почти не переиспользуется между
прогонами и вырождается в кэш парсинга. Следствие: правка принципа
«контекст без клона» в `docs/SYSTEM_DESIGN.md` — довыборка файлов по sha
через `VcsGateway` остаётся единственным способом доступа к коду, полного
клона нет.

**D2. Триггер — push-вебхук, а не опрос.**
Быстрее и без расхода квоты API. Подписанная доставка уже проходит HMAC-гейт;
`default_branch` берётся из payload'а, поэтому «основная ветка» — свойство
репозитория GitHub, а не нашей конфигурации. Альтернатива — периодический
опрос head через `VcsGateway`: проще приём, но задержка индекса и постоянный
расход лимитов. Отказ от обработки: `ref` ≠ `refs/heads/<default_branch>`,
нулевой `after` (удаление ветки), незарегистрированный репозиторий — всё это
`202 ignored` по существующим правилам приёма.

**D3. Задача переиндексации идёт в общую очередь без строки в `review_runs`.**
Переиндексация — не ревью: у неё нет прогона, публикации и статусов, поэтому
создавать `ReviewRun` и частичный уникальный индекс «не более одного прогона
на коммит» — чужая семантика.
Тело задачи несёт `event_type: "push"`, инсталляцию, репозиторий и коммит;
воркер маршрутизирует по `event_type`. DLX и приоритет наследуются бесплатно,
повторное потребление идемпотентно само по себе (D4). Альтернатива — вторая
очередь: отдельный consumer, конфигурация и топология против «очередь одна»
(§4.2). Альтернатива — синхронный парсинг в эндпоинте: блокирует доставку
вебхуков на минуты — нарушает контракт приёма.

**D4. Хранение — `CacheStore`, коалесинг по маркеру sha, без миграций.**
Выбор пользователя. Ключи неизменяемы по построению: содержимое по sha не
меняется (§4.3), поэтому запись `(репозиторий, sha)` не инвалидируется, а
вытеснение — штатное событие. Маркер «проиндексированный sha» даёт коалесинг:
задача на уже проиндексированный коммит подтверждается без работы, повторные
доставки push (GitHub шлёт ретраи на таймаут) не создают каскад парсинга.
Гонка двух задач на разные sha безопасна: записи по разным ключам, маркер
устанавливает победивший последним воркер. Не храним историю sha в базе —
при вытеснении маркера следующий push перестроит индекс; этого достаточно
для best-effort семантики. Альтернатива — таблицы `repository_heads` +
`definitions` с миграцией: durability, которую никто не требует (потребитель
переживает промах по спеке), плюс расход лимита миграций на feature без
платёжного контракта.

**D5. Парсинг за портом `DefinitionExtractor`; `VcsGateway` расширяется
методами `fetch_tree` и `fetch_file`.**
tree-sitter — вендор в слое инфраструктуры (адаптер
`app/infrastructure/parsing/`); домен получает чистые типы `Definition` и решение «язык по
расширению» как чистую функцию над реестром грамматик. Порт сохраняет шов
Strangler Fig: если биндинги разочаруют, `DefinitionExtractor` получит
сетевой адаптер без изменения слоёв выше (§5, BACKEND_ARCHITECTURE.md).
Довыборка файлов — через методы того же `VcsGateway`, а не отдельный порт:
GitHub trees/blobs — тот же провайдер, те же installation-токены и backoff;
лимиты (число файлов, байты) применяет вызывающий сценарий, адаптер только
транспортирует. Альтернатива — отдать парсеру сырые пути и позволить ему
ходить в сеть: смешивает чистое извлечение с I/O, тесты парсера требуют
сети.

**D6. Первая грамматика — Python; реестр «расширение → грамматика» — шов
для остальных.**
Репозиторий и первый контур ревью — Python; грамматика подключается как
обычная зависимость tree-sitter. Реестр — словарь в домене, добавление
языка — новая запись и зависимость, спеки не меняются (спека фиксирует
поведение «неизвестный язык пропускается»). Альтернатива — сразу все
популярные грамматики: восемь зависимостей без потребителя против правила
«абстракция без второго вызова».

**D7. Лимиты конфигурацией, исчерпание — не сбой.**
`index_max_files`, `index_max_file_bytes`, `index_timeout_seconds` в
`app/config.py` (значения по
умолчанию + override окружением, как остальные настройки). Превышение размера
файла — пропуск файла; исчерпание лимита файлов/времени — частичный индекс,
который сохраняется и считается валидным: частичный словарь сигнатур полезнее
отсутствия индекса, а добор произойдёт на следующем коммите. Это тот же
принцип «жёсткие лимиты» из §5 сборки контекста.

**D8. Очерёдность: база — ветка PR #37, мёрж после него.**
Изменение затирает те же файлы (`app/api/webhooks.py`, use case приёма,
порт `VcsGateway`, `pyproject.toml`, спеки `webhook-intake` и `job-queue`).
Ветка `feat/tree-sitter` отводится от `feat/architecture_and_vcs_context_engine`
и перенацеливается на `develop` после мёржа #37. Дельты спек используют
ADDED-требования с новыми именами, поэтому синхронизация при архивации не
конфликтует с требованиями из #37.

## Risks / Trade-offs

- [Нет колёс tree-sitter под cp314/свободнопоточную сборку → сборка из
  исходников потребует компилятор в образе] → первый таск — спайк:
  `uv add tree-sitter tree-sitter-python`, сборка образа, в `pyproject.toml`
  комментарий с зафиксированной версией; если провал — откат change без
  кода (ни один другой таск не начат).
- [In-process `CacheStore` разделяет индекс только внутри одного процесса;
  парсер в воркере, потребитель в будущем — тоже воркер, но вторая реплика
  сделает индекс неодинаковым] → допустимо до появления второй реплики по
  §4.3; Redis-адаптер — отдельный change с той же спекой, потребители уже
  живут с «промах — не ошибка».
- [Переиндексация монорепо может исчерпать лимит файлов и дать почти пустой
  индекс на каждом коммите] → метрика в логах воркера (файлов обработано/
  пропущено, байт), решение о частичной переиндексации — по измерениям,
  не догадкам.
- [Пуш-доставки учащаются (CI-роботы), задачи переиндексации теснят задачи
  ревью] → коалесинг по маркеру (D4) убирает повторы; при необходимости
  приоритеты уже в спеке очереди, тарифная модель — шов §4.2.
- [Гейт событий усложняется (`push` рядом с `pull_request`)] → извлечение
  остаётся чистой функцией над payload'ом с таблицей исходов; эндпоинт
  добавляет один тип события, контракт ответов (202/401/502) не меняется.

## Migration Plan

Развёртывание не требует изменений окружения: новые события `push` приходят
таблиц, ни очередей, ни внешних сервисов. Откат — реверт-коммит: two-way door,
данные не затронуты (CacheStore — эфемерное хранилище, чистить не нужно).
Порядок мёржа: PR #37 в `develop`, затем перенацеливание и мёрж этого change.

## Open Questions

- Пороговые значения лимитов (`index_max_files`, `index_max_file_bytes`,
  `index_timeout_seconds`)
  фиксируются при реализации по данным спайка на реальном репозитории;
  спека требует лишь их наличия и поведения при исчерпании.
