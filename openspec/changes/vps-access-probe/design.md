# Design

## Context

Мотивация — в `proposal.md`. Существенные для подхода ограничения:

- Значение `VPS_DMC268_P` неизвестно и непрочитаемо; узнать его форму можно только внутри прогона.
- Секреты организации доступны этому репозиторию (проверено через `repos/.../actions/organization-secrets`), но не подставляются в прогонах по PR из форков.
- `workflow_dispatch` появляется в интерфейсе Actions только для workflow, лежащего в дефолтной ветке; у репозитория это `develop`.
- Раннеры GitHub выходят с общих адресов: неудачные попытки входа бьют не только по нам.

## Goals / Non-Goals

**Goals:**

- Получить три факта за один прогон: форма `VPS_DMC268_P`, проходит ли SSH, доступен ли Docker пользователю `VPS_DMC268_U`.
- Не оставить значение секрета ни в логах, ни в списке процессов раннера, ни в файле на его диске.
- Не менять состояние сервера.

**Non-Goals:**

- Устанавливать ключ CI на сервер — это следующее изменение, и его форма зависит от полученного здесь ответа.
- Выбирать хранилище Terraform state и схему разведения окружений: обе развилки открыты и на диагностику не влияют.
- Что-либо деплоить или трогать `infra/`.

## Decisions

**Тип секрета определяется по форме значения, а не перебором способов входа.** Приватный ключ в любом распространённом формате начинается с `-----BEGIN`; проверка префикса не требует сетевого обращения. Альтернатива — попробовать ключом, при неудаче паролем — отвергнута: это две попытки входа за прогон, ровно то, что провоцирует бан по fail2ban.

**Секрет передаётся скрипту через `env:`, а не интерполяцией `${{ secrets.* }}` в тело шага.** При интерполяции значение попадает в текст скрипта, который раннер пишет на диск, и всплывает в трассировке, если шаг когда-нибудь запустят с `set -x`. Через `env:` оно остаётся переменной процесса.

**Пароль отдаётся `sshpass` через переменную окружения (`-e`), а не аргументом командной строки.** Аргументы видны в `ps` любому процессу на раннере; маскирование GitHub на это не распространяется, оно работает только для лога.

**Ключ хоста принимается по первому подключению (`ssh-keyscan`), отпечаток не пинится.** Для диагностики, которая ничего не разворачивает, цена MITM — ложный ответ на три вопроса, и не более того. В CD, который будет выполнять код на сервере, отпечаток придётся закрепить; это требование переходит в следующее изменение.

**Триггеры: `workflow_dispatch` плюс `push` по пути самого файла.** Один dispatch не годится — до мержа в `develop` кнопки в интерфейсе не будет, а мержить диагностику в дефолтную ветку ради того, чтобы её запустить, странно. Ограничение по `paths` не даёт ей срабатывать на каждый пуш ветки.

**Docker проверяется вызовом `docker version --format '{{.Server.Version}}'`.** Один вызов отвечает сразу на оба вопроса: жив ли демон и имеет ли пользователь доступ к сокету. `docker ps` дал бы то же самое, но вывалил бы в лог чужие контейнеры.

**Прогон не падает на неуспехе диагностики.** Ответ «SSH не проходит» — такой же результат, как «проходит», и он должен быть виден в summary, а не только в красном крестике. Падение остаётся за ошибками самого workflow.

## Risks / Trade-offs

- **Неудачная попытка входа по паролю приближает бан адреса раннера** → ровно одна попытка за прогон, без ретраев и без матрицы; `ConnectTimeout` ограничен, чтобы прогон не висел.
- **`ssh-keyscan` доверяет первому ответу** → принято осознанно, см. решение выше; ограничено тем, что диагностика ничего не выполняет на сервере, кроме одной read-only команды.
- **Диагностика отвечает на момент времени** → если сервер перенастроят, ответ протухнет. Поэтому результат фиксируется в #22 и workflow удаляется, а не остаётся висеть как «проверка».
- **Секрет может оказаться ни ключом, ни рабочим паролем** (например, пароль от панели VPS, а не от SSH) → это тоже валидный результат: workflow сообщит «форма: пароль, SSH: отказ», и следующий шаг будет разговором с Михаилом, а не кодом.
