## Context

Контракт симуляции уже в схеме (`SimulationRequest`, `SimulationResponse`, `429 RATE_LIMITED`, `404 SIMULATION_NOT_FOUND`), ручки отвечают `501`.
Ревью запроса на изменение устроено так: API пишет `ReviewRun` и ставит `ReviewJob` в quorum-очередь `review_jobs.qq`; один воркер с prefetch 1 берёт сообщение, `run_review` проходит этапы с шагами (`review_run_steps`), пакет контекста пишется в `context_payloads`, замечания - в `findings`, затем публикация.
Анализ внутри `run_review` - это три уже отдельные функции: `request_review`, `screen_findings` и закрытая `_verify` (верификатор с fail-open).
`assemble_context` берёт из `ReviewJob` только заголовок пакета: репозиторий, номер PR и пару sha.
Воркер раз в минуту делает проход обслуживания: зависшие прогоны, истёкшие сессии, повтор доставок вебхуков.

## Goals / Non-Goals

**Goals:**

- Симуляция даёт тот же результат, что дало бы ревью того же кода с теми же правилами: общий анализ, а не его копия.
- Расход модели ограничен на пользователя.
- Код и правила пользователя хранятся, только пока их читает анализ; в сохранённом результате секреты скрыты, как в пакетах контекста ревью (#28).
- Ревью запросов на изменение не ждёт симуляций дольше одной симуляции.

**Non-Goals:**

- События симуляции в общем потоке `GET /events`: итог - опросом (D1).
- Список симуляций пользователя и история; общий доступ к симуляции.
- Правила из репозитория по кнопке - когда заработает статус rules.md (#272).
- AST-окружение для входа-диффа: полного текста файла у диффа нет.
- Бизнес-метрики симуляций в Prometheus: хватает логов и спанов, пока нет потребителя.

## Decisions

### D1. Итог - опросом `GET`, без событий потока

Фронт опрашивает `GET /simulations/{simulation_id}` раз в 1-2 секунды, пока статус не `completed` или `failed`.
Симуляция одна у пользователя за раз и идёт 20-90 секунд: это десятки дешёвых запросов по первичному ключу.

Альтернатива - типы `simulation.*` в общем потоке. Отклонена: второй канал `NOTIFY`, свой курсор и чтение симуляций пользователя в цикле потока, а поток при подключении считает видимые репозитории по GitHub и падает вместе с ним - статус симуляции от GitHub зависеть не должен. Типы `simulation.*` из контракта убраны ещё до реализации.

### D2. Та же очередь, вид задачи - в свойстве AMQP `type`, приоритет ниже ревью

Задача симуляции идёт в `review_jobs.qq` с приоритетом `SIMULATION_PRIORITY = 1` (ревью - `DEFAULT_PRIORITY = 5`) и свойством `type = simulation`; у ревью `type = review`, сообщение без `type` - ревью (так публикует API до этого change).
Тело - только `job_id` и `simulation_id`: вход пользователя лежит в базе и через брокер не идёт.
Порт `JobQueue.enqueue` принимает `ReviewJob | SimulationJob`; воркер выбирает обработчик по `type`.

Порядок выдачи по приоритету у quorum-очереди проверяется интеграционным тестом на образе стенда (`rabbitmq:4.4`) до кода обработчика: ревью, поставленное после симуляции, берётся раньше неё.
Проверено на `rabbitmq:4.4.0` с потребителем воркера (prefetch 1): порядок строгий - пока в очереди ждёт хоть одно ревью, симуляция не выдаётся; внутри одного приоритета - FIFO.
Одна уже взятая симуляция задерживает ревью не дольше своего прогона.
Обратная сторона строгого порядка - симуляция ждёт, пока очередь ревью не опустеет; дольше `SIMULATION_STALE_SECONDS` она не ждёт (D8).

Альтернатива - отдельная очередь и отдельный процесс воркера. Отклонена: новый контейнер в `infra/`, второй потребитель, свои проверки деплоя - ради потока, который ограничен лимитами D4.
Ещё альтернатива - второй потребитель в том же процессе: `channel.consume()` pika обслуживает одну очередь, понадобился бы переход на callback-потребление и переписывание цикла `Worker.run`.

### D3. Таблица `simulations`, результат - одним JSONB

```text
simulations
  id            uuid PK
  user_id       uuid FK users ON DELETE CASCADE
  status        simulation_status            queued | building_context | analysing | verifying | completed | failed
  source_kind   simulation_source_kind       code | diff
  file_path     text NULL                    только у code (CHECK)
  source        text NULL                    фрагмент или дифф; есть ровно у незавершённой (CHECK, D10)
  rules         text NULL                    текст rules.md, пустой допустим; есть ровно у незавершённой (CHECK, D10)
  result        jsonb NULL                   замечания, отброшенные, контекст без секретов; есть ровно у completed (CHECK)
  model         text NULL
  tokens_used   bigint NULL                  >= 0, оба вызова модели
  verification  review_verification NULL       тот же тип, что у прогона ревью
  error_code    varchar(64) NULL             есть ровно у failed (CHECK)
  created_at, updated_at, expires_at  timestamptz

  UNIQUE (user_id) WHERE status NOT IN ('completed', 'failed')   -- одна незавершённая на пользователя
  INDEX (user_id, created_at)                                     -- лимит за час
  INDEX (expires_at)                                              -- очистка
```

Результат читается целиком одним документом и ни в каком запросе не разбирается, поэтому JSONB, а не три таблицы с замечаниями, отброшенными и контекстом.
Перевод доменного `SimulationResult` в JSON и обратно - в адаптере.
Пакет контекста симуляции в `context_payloads` не пишется: та таблица - след прогонов ревью с внешним ключом на `review_runs`; что видела модель, симуляция хранит в `result.context` по файлам.

### D4. Лимиты - по строкам самой таблицы

Чистая `admit_simulation(active, recent_created_at, now, max_per_window, window)` решает: допустить или `Limited(retry_after)`.

- Есть незавершённая симуляция - отказ, `Retry-After: 5` (каденс опроса).
- `SIMULATION_MAX_PER_HOUR` запусков за скользящий час (по умолчанию 60) - отказ, `Retry-After` - до выхода самого старого запуска из окна, не меньше секунды.

Гонку двух параллельных `POST` закрывает уникальный частичный индекс: второй `INSERT ... ON CONFLICT DO NOTHING` ждёт коммита первого и ничего не пишет, ручка отвечает тем же `429`.
Счёт за час точен, пока строки живут не меньше окна: `SIMULATION_TTL_SECONDS` не меньше часа проверяет валидация настроек.

Альтернатива - порт `RateLimiter` (fixed-window) над Redis, как он описан в `docs/SYSTEM_DESIGN.md` для вебхуков. Отклонена для симуляций: строки, которые фича и так хранит, дают точный скользящий счёт без новой инфраструктуры и переживают рестарт; так же #239 считает суточную квоту репозитория суммой по прогонам.

### D5. Анализ - общие функции, а не общий оркестратор

Симуляция вызывает те же `request_review` → `screen_findings` → `verify_findings`, что и ревью; закрытая `_verify` из `review_pipeline.py` становится общей `verify_findings` (fail-open, вердикты, токены).
Последовательность из трёх вызовов повторяется в двух оркестраторах: ревью оборачивает её шагами `review_run_steps` и переходами прогона, симуляция - своими статусами.

Две правки доменных функций, которые нужны и ревью:

- `screen_findings` отдаёт отклонённых кандидатов с причиной (`Screening.rejected` - кортеж, ревью считает его длину, как раньше считало число): «привязка вне показанного диффа», «правило не показывали модели», «правило не применимо к файлу», «нет пункта N», «префикс атрибуции не снимается», «повтор замечания».
- `apply_verdicts` отдаёт вердикт и причину по каждому оставленному замечанию - и подтверждённому, и оставленному вопреки `drop`; эти же данные сохранит у замечаний прогона инспектор замечания (тоже #288).

Альтернатива - один оркестратор анализа с хуками этапов. Отклонена: хуки шагов и переходов прогона - широкий интерфейс над тремя вызовами.

### D6. Контекст симуляции

`assemble_context` берёт заголовок пакета из `ContextSubject(repository, pull_request, base_sha, head_sha)` вместо `ReviewJob`; у симуляции все четыре - `null`, промпт их пропускает (метаданные в системном сообщении и так берутся только проверенные).

- Фрагмент кода - `ParsedFile` нового файла с одним hunk'ом `@@ -0,0 +1,N @@`, все строки добавлены; строится чистой функцией, без текста диффа и его разбора.
  AST-окружение - `DefinitionExtractor` по самому фрагменту, если язык поддержан и фрагмент не больше `AST_MAX_FILE_BYTES`; больше - `omitted` с `too_large`.
- Дифф - `parse_diff` и `filter_diff_files`, как у ревью; у файлов поддержанного языка AST - `omitted` с причиной `no_source`.
- Правила - `parse_rules_markdown` текста пользователя: пустой текст - статус `absent`, без принятых правил - `empty`.
- Контекста PR нет: заголовок, описание и коммиты - пустые, а не «недоступны».

Входу, в котором после фильтра нечего ревьюить (дифф без hunk'ов, только `uv.lock`, неразборчивый текст), ручка отвечает `422` до записи симуляции: та же `filter_diff_files`.

### D7. Сбой симуляции - статус, а не DLQ

Ошибка модели, разбора ответа или неожиданное исключение переводит симуляцию в `failed` с кодом (`LLM_TIMEOUT`, `LLM_INVALID_OUTPUT`, `INTERNAL_ERROR` и т.д.) и потраченными токенами; сообщение подтверждается.
DLQ ревью нужна, чтобы разобрать и переиграть прогон по сообщению; у симуляции в сообщении только id, переиграть её пользователь может сам, а исключение - в логе со стектрейсом.
Повторная доставка задачи завершённой симуляции и задачи удалённой по сроку симуляции подтверждается без работы.
Сбой верификатора, как у ревью, не роняет симуляцию: итог `unavailable`, замечания после отсева.

Задача не встала в очередь - симуляция сразу `failed` с `QUEUE_UNAVAILABLE`, ручка всё равно отвечает `202`: ресурс создан, клиент видит итог первым же опросом, а незавершённая симуляция не блокирует следующий запуск.

### D8. Зависшие и истёкшие - в проходе обслуживания

В проход обслуживания воркера добавляются два независимых шага, как у сессий:

- незавершённая симуляция без перехода дольше `SIMULATION_STALE_SECONDS` (по умолчанию 600) - `failed` с `SIMULATION_STALE`: освобождает слот лимита после смерти воркера и закрывает задачи, которые в окне деплоя взял старый воркер.
  Ждущая в очереди за ревью - тоже: столько пользователь ждать не станет, а слот лимита освобождается; воркер, взявший такую задачу позже, видит итоговый статус и не работает;
- симуляция с прошедшим `expires_at` удаляется вместе с результатом.

Порог зависания больше худшего прогона симуляции: два вызова модели с их дедлайнами; это проверяется на старте воркера, как `check_model_deadline`.

### D9. Видимость, данные пользователя, телеметрия

- Симуляцию видит только автор: чужая, несуществующая и удалённая по сроку отвечают одним `404 SIMULATION_NOT_FOUND`.
- Правила в симуляции - правила самого пользователя: подложить их можно только в свою симуляцию. Код и правила в пакете - недоверенные данные в оградах, как у ревью; ссылка замечания на правило проверяется кодом.
- В логах и атрибутах спанов - `simulation_id`, статусы и счётчики, без кода и правил. Спаны этапов - `simulation.<этап>`.
- Расход модели - `tokens_used` симуляции; в суточную квоту токенов репозитория (#239) симуляция не входит: репозитория у неё нет, расход ограничивает D4.

### D10. Вход - до итога, секреты в результате скрыты

Пакеты контекста ревью пишутся в базу с секретами, заменёнными меткой (`redact_secrets`, #28), а модели уходят как есть: ревью должно увидеть зашитый секрет и указать на него.
Симуляция держит то же правило и не хранит лишнего:

- Вход (`source` и `rules`) нужен только анализу: воркер читает его в начале прогона, ответ его не отдаёт, текст остаётся в редакторе фронта.
  Переход в `completed` или `failed` стирает вход - `complete_simulation` и `fail_simulation` отдают итоговую симуляцию без него, CHECK в базе не даёт итоговой строке со входом; массовый перевод зависших (D8) стирает его тем же `UPDATE`.
- Контекст в `result.context` адаптер пишет через `redact_secrets`, как `SqlAlchemyContextPayloadRepo.add`: правило одно, в домене, адаптер его только применяет.
  Замечания и отброшенные пишутся как есть - так же, как замечания прогона в `findings`.

Альтернатива - редактировать вход при записи. Отклонена: воркер берёт вход из базы, и модель не увидела бы секрет, который ревью обязано найти.
Ещё альтернатива - держать вход до `expires_at`. Отклонена: после итога его никто не читает, а сутки хранения кода с возможными секретами - ровно то, что убирал #28.

## Risks / Trade-offs

- [Симуляция занимает единственный воркер, пока ревью ждёт] → приоритет ниже ревью (D2) и одна незавершённая симуляция на пользователя (D4); задержка ревью - не больше одной симуляции на воркер.
- [Приоритет quorum-очереди ведёт себя не так, как ожидается] → интеграционный тест на образе стенда до кода (D2) подтвердил строгий порядок на `rabbitmq:4.4.0`; он же упадёт, если обновление образа брокера поменяет порядок, и тогда вопрос решается отдельным потребителем.
- [В окне деплоя новый API ставит задачу симуляции, а её берёт старый воркер] → старый воркер не разбирает тело, сообщение уходит в DLQ, симуляция закрывается как зависшая (D8). Ревью это окно не задевает.
- [Код пользователя хранится в базе] → вход стирается с итогом, секреты в контексте результата скрыты (D10), результат удаляется по сроку (D8), ничего из входа - в логах и спанах (D9); видит только автор.
- [Секрет, который `redact_secrets` не знает, остаётся в `result.context` до срока хранения] → тот же риск принят для пакетов контекста ревью (#28); список форм секретов один на оба места.
- [Повторяющаяся последовательность анализа в двух оркестраторах] → три вызова без ветвлений; правки отсева и вердиктов - в общих функциях (D5).

## Migration Plan

1. Миграция: enum-типы `simulation_status`, `simulation_source_kind`, таблица `simulations` с ограничениями и индексами. Новые объекты, горячие таблицы не трогает.
2. Деплой API и воркера обычным порядком; окно, когда старый воркер видит задачу симуляции, закрывает D8.
3. Откат: реверт кода и `downgrade` - таблица удаляется вместе с симуляциями; они временные, потеря ожидаема.
