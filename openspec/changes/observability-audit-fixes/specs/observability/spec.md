## MODIFIED Requirements

### Requirement: Стек наблюдаемости одинаков локально и на проде

Наблюдаемость SHALL работать в стеке из девяти контейнеров из официальных образов с зафиксированными
версиями: три экземпляра OTel Collector, Loki, Tempo, Prometheus, Grafana, node_exporter и
socket-proxy.
Конфигурации
SHALL быть одними и теми же локально и на стенде: различаться SHALL только ресурсы, хранение и
доступ — через переменные и оверрайды, не через разные конфиги. По `trace_id` из записи лога SHALL
открываться трейс в Grafana — переход лог ↔ трейс работает в обе стороны.

#### Scenario: Локальный стек поднимается теми же конфигами

- **WHEN** разработчик поднимает локальный стек с профилем наблюдаемости
- **THEN** все три экземпляра коллектора, Loki, Tempo, Prometheus, Grafana, node_exporter и
  socket-proxy подняты теми же
  конфигами, что на стенде, и логи с трейсами локального прогона видны в Grafana

#### Scenario: Из лога в трейс

- **WHEN** в Grafana открыта запись лога с `trace_id`
- **THEN** по этому `trace_id` открывается трейс прогона в Tempo

#### Scenario: Из трейса в логи

- **WHEN** в Grafana открыт спан трейса API или воркера
- **THEN** открываются записи Loki этого сервиса (лейбл `service_name`) с `trace_id` трейса из structured metadata

#### Scenario: Стек выключен флагом

- **WHEN** стенд разворачивается при `observability_enabled = false`
- **THEN** контейнеров стека нет, сервисы работают без экспорта телеметрии, и в логе ошибок
  экспорта нет

## ADDED Requirements

### Requirement: Коллектор телеметрии принимает логи сервисов по OTLP

Между сервисами и хранилищами телеметрии SHALL стоять основной OTel Collector на все сигналы: приём
OTLP (трейсы, метрики, логи), ограничение памяти, редакция и батчинг. Логи сервисов приложения
SHALL поступать в коллектор только по OTLP из SDK. Экспорт логов SHALL включаться переменной
`OTEL_LOGS_EXPORTER`; без неё записи SHALL оставаться только в stdout. Включение экспорта SHALL
NOT требовать правок кода.

#### Scenario: Логи сервисов доходят в хранилище

- **WHEN** сервис с `OTEL_LOGS_EXPORTER=otlp` пишет лог
- **THEN** SDK экспортирует запись по OTLP, и в хранилище логов она попадает с `trace_id` записи

#### Scenario: Экспорт логов выключен по умолчанию

- **WHEN** сервис запущен без `OTEL_LOGS_EXPORTER`
- **THEN** записи выходят только в stdout (docker logs), в коллектор ничего не уходит, и в лог
  ошибок экспорта нет

### Requirement: Логи контейнеров без SDK — через драйвер fluentd

Логи контейнеров без SDK — PostgreSQL, RabbitMQ и nginx интерфейса — при включённом стеке SHALL
доставлять драйвер логов `fluentd` демона Docker в отдельный экземпляр коллектора, который
принимает их только на петле хоста, скрывает в них IP-адреса и секреты и передаёт записи
основному коллектору по OTLP. Читать
лог-файлы контейнеров и каталог Docker и брать логи через Docker API коллекторы SHALL NOT. Без
приёмника такие контейнеры SHALL стартовать и работать.

#### Scenario: Логи контейнеров без SDK доходят в Loki без адресов и секретов

- **WHEN** при включённом стеке контейнер postgres, rabbitmq или nginx интерфейса пишет строку в
  stdout
- **THEN** в Loki есть запись с лейблом `service_name`, равным тегу драйвера (имени контейнера на
  стенде), а IPv4-адреса, query в URL, пароль в `PASSWORD '…'` и
  `DETAIL: Key …` / `DETAIL: Failing row contains …` заменены маркером

#### Scenario: Без коллектора логов база работает

- **WHEN** коллектор логов недоступен
- **THEN** контейнеры postgres и rabbitmq стартуют и работают, а их записи видны в `docker logs`

### Requirement: Свои метрики стека — в Prometheus

Prometheus SHALL скрейпить собственные метрики всех экземпляров коллектора (`otelcol_*`: отказы приёма, сбои экспорта), Loki и Tempo. Порт своих метрик коллектора (`:8888`) SHALL NOT публиковаться на хосте: как `:8889`, он доступен из сетей, к которым подключён контейнер коллектора.

#### Scenario: Сбой экспорта виден

- **WHEN** коллектор не может отправить логи в Loki
- **THEN** в Prometheus растёт `otelcol_exporter_send_failed_log_records` этого коллектора

### Requirement: Health-check не пишется в access-лог

Access-запись uvicorn о запросе health-check'а SHALL NOT попадать в лог: его опрашивает контейнерный healthcheck, и такие записи вытесняли бы из Loki все остальные. Access-записи прочих путей SHALL писаться как раньше.

#### Scenario: Опрос health-check'а

- **WHEN** контейнерный healthcheck опрашивает `GET /health`
- **THEN** access-записи об этом запросе в логе нет, а запрос к другому пути записан

### Requirement: Ошибка шага прохода очистки различима

Запись об исключении шага периодического прохода воркера SHALL нести поле `maintenance_step` с именем шага: `sweep_stale_runs`, `purge_expired_sessions` или `redeliver_webhooks`. Тело такой записи коллектор гасит, и без поля шаги различаются только номером строки.

#### Scenario: Упал повтор доставок

- **WHEN** шаг повтора упавших доставок вебхука завершился исключением
- **THEN** запись лога об ошибке несёт `maintenance_step = redeliver_webhooks`

## REMOVED Requirements

### Requirement: Коллектор телеметрии между сервисами и хранилищами

**Reason**: Сценарий «Логи postgres и rabbitmq в Loki не попадают» противоречит новому пути логов
контейнеров без SDK, а MODIFIED не может убрать сценарий.

**Migration**: Положения о логах сервисов и два их сценария перенесены как есть в «Коллектор
телеметрии принимает логи сервисов по OTLP»; логи контейнеров — в «Логи контейнеров без SDK —
через драйвер fluentd», где запрет читать лог-файлы контейнеров сохранён и дополнен запретом
брать логи через Docker API.
