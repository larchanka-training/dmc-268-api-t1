## Why

Ревью видит только дифф с ±30 строками контекста, и каждый прогон начинается с чистого листа: модель не помнит код этого репозитория, который она уже видела в прошлых прогонах. Полный репозиторий недоступен по дизайну («контекст без клона», SYSTEM_DESIGN.md §2.1), но фрагменты, уже прошедшие через воркер, накапливаются — из них можно собрать профиль репозитория и подмешивать похожий код в контекст новых ревью, не нарушая принцип «не клонируем и не индексируем весь репозиторий».

## What Changes

- Новый уровень контекста `similar`: перед генерацией замечаний прогон находит top-k похожих чанков кода в профиле своего репозитория и добавляет их в контекст как отделённые разделителями данные.
- Профиль строится инкрементально из surrounding-окон (±30 строк) каждого прогона: окно становится чанком с путём, границами, коммитом и дайджестом содержимого.
- Хранение — pgvector в существующем PostgreSQL: таблица чанков с векторным столбцом, обратимая миграция Alembic, без отдельной векторной БД.
- Новый порт `EmbeddingGateway` с первым адаптером Ollama; модель и размерность эмбеддингов — параметры конфигурации.
- Профиль best-effort: сбой эмбеддинга, записи или поиска не роняет прогон ревью — уровень `similar` просто отсутствует.
- Обновление документации: SYSTEM_DESIGN.md (уточнение принципа «контекст без клона»: Vector DB по-прежнему нет, но есть профиль из уже увиденных фрагментов; новый уровень контекста), BACKEND_ARCHITECTURE.md (новый порт и шов интеграции с пайплайном), erd.md (таблица чанков).

Вне рамок: чанки из уровней `whole_file` и `ast`, профиль конвенций (`key_patterns`), векторные индексы HNSW/IVFFlat, применение профиля вне пайплайна ревью, фронтенд.

## Capabilities

### New Capabilities

- `repo-rag-profile`: накопление по прогонам RAG-профиля репозитория (чанки кода с эмбеддингами в pgvector) и retrieval похожего кода как уровень контекста ревью; включает требования по секретам, границам репозитория, совместимости моделей эмбеддингов и best-effort отказоустойчивости.

### Modified Capabilities

Нет. Требования существующих спек не меняются: `database-migrations` покрывает новую миграцию своими общими правилами, `backend-architecture` уже требует актуальности архитектурного документа, уровни контекста в спеках не перечисляются (только в SYSTEM_DESIGN.md, который обновляется задачей).

## Impact

- **Код**: новые `app/domain/profile.py` (чистые функции: чанкинг окон, отбор под лимиты, редакция секретов), `app/application/ports/embedding_gateway.py` и порт репозитория чанков, use case'ы накопления и retrieval, адаптеры `app/infrastructure` (SQLAlchemy-модель, pgvector-поиск, Ollama-эмбеддер), `app/config.py`, `app/infrastructure/container.py`.
- **Схема БД**: одна миграция Alembic — расширение `pgvector`, таблица `repo_code_chunks` c уникальностью `(repository_id, content_digest)`; обратимый downgrade.
- **Зависимости**: `pgvector` (python-пакет с SQLAlchemy-типом), `ollama` (SDK; появится здесь раньше планируемого `LlmGateway`).
- **Развёртывание**: образ PostgreSQL должен содержать pgvector (расширение создаёт миграция).
- **Интеграция с пайплайном**: воркер и сборка контекста ещё не реализованы. Этот change поставляет подсистему профиля целиком (домен, порты, адаптеры, use case'ы с тестами на фейках); вызов use case'ов из пайплайна ревью фиксируется в BACKEND_ARCHITECTURE.md как шов и выполняется в change'ах пайплайна — до них порты не мертвы: их первый вызывающий код — use case'ы этого change.
