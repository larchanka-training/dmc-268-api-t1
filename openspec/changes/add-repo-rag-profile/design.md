## Context

Пайплайн ревью спроектирован, но ещё не реализован: в коде есть домен, порты репозиториев и SQLAlchemy-адаптеры, воркера и сборки контекста нет. SYSTEM_DESIGN.md §2.1 фиксирует принцип «контекст без клона»: репозиторий не клонируется, Vector DB и Repository Indexer исключены. Мотивация change — в proposal.md («Why»). Правила: порты — Protocol во внутреннем слое, адаптеры — в infrastructure; решения — чистые функции; «нет порта без вызывающего кода».

## Goals / Non-Goals

**Goals:**

- Подсистема профиля, целиком реализованная и покрытая тестами на фейках: домен → порты → адаптеры → конфигурация → контейнер.
- Уровень контекста `similar` с жёсткими лимитами и защитой от prompt injection (delimited data).
- Схема — одна обратимая миграция, совместимая с правилом «один head».

**Non-Goals:**

- Сам пайплайн ревью (воркер, сборка контекста, промпт) — отдельные change'ы; здесь только use case'ы профиля, которые они вызовут.
- Векторные индексы (HNSW/IVFFlat), перевложение при смене модели, счётчики стоимости эмбеддингов, любые чанки кроме surrounding-окон.

## Decisions

### D1 — pgvector в существующем PostgreSQL, без векторного индекса

Альтернативы — внешняя векторная БД (ломает «only PostgreSQL», новый сервис в стеке) и полнотекстовый поиск (дешевле, но нет семантики). Потолок: последовательный скан векторов одного репозитория; на десятках тысяч чанков это миллисекунды. Когда станет узко — HNSW-индекс отдельной миграцией; строить сейчас — предварительная оптимизация.

### D2 — Модель и размерность — конфигурация

`EMBEDDING_MODEL` (по умолчанию `nomic-embed-text`), `EMBEDDING_DIMENSION` (должна совпадать с моделью, фиксирует тип столбца `vector(N)`), `OLLAMA_BASE_URL` (настройка появится здесь раньше `LlmGateway` и станет с ним общей). Смена модели не смешивает пространства: у чанка хранится `embedding_model`, поиск фильтрует по ней.

### D3 — Порт `EmbeddingGateway` — Protocol в application, один батчевый метод `embed(texts)`

Адаптер `OllamaEmbeddingGateway` только транспортирует и сверяет размерность ответа с конфигурацией. Первый вызывающий код — use case'ы этого change, поэтому правило «нет порта без вызывающего кода» не нарушено; вызов use case'ов из пайплайна фиксируется швом в BACKEND_ARCHITECTURE.md.

### D4 — Порт `CodeProfileRepo`: `add_many` и `search`

`add_many` — идемпотентная вставка `ON CONFLICT (repository_id, content_digest) DO NOTHING`; `search(repository, embedding, model, k, exclude_digests)` — косинусное расстояние pgvector, фильтры по репозиторию и модели. Редакция секретов — в этом же шве адаптера (единая точка для всех пишущих, как у `ContextPayloadRepo` по threat model).

### D5 — Чистые функции в `app/domain/profile.py`

`build_chunks(windows, limits)` (окно → черновик чанка: путь, границы, коммит, sha256-дайджест; сверхлимитные — пропуск), `pick_similar(scored, limits)` (top-k с бюджетом байтов, дедуп по дайджесту, отсечение самосовпадений), `redact(text)` (минимальный набор паттернов: AWS/GitHub-токены, private keys, высокоэнтропийные строки). `redact` — тот самый механизм, который потом переиспользует сохранение контекста прогона: один источник, расхождение исключено.

### D6 — Порядок шага профиля в прогоне: сначала retrieval, потом ingestion

Запросы — вложения текущих окон одним батчем; исключение по дайджесту защищает от самосовпадений независимо от порядка, но порядок «сначала спросили, потом положили» проще рассуждать и не требует фильтра по текущему прогону. Оба шага best-effort: исключение адаптера гасится на границе use case'а, прогон живёт без уровня `similar`.

### D7 — Таблица `repo_code_chunks`

UUIDv7 PK (генерирует домен), FK `repository_id` и `review_run_id` с `ON DELETE RESTRICT` (история не удаляется неявно — как у остальных сущностей; прогон даёт провенанс), `path`, `start_line`/`end_line`, `commit_sha`, `content_digest`, `body` (отредактированный текст), `embedding vector(N)`, `embedding_model`, временные метки с часовым поясом. Уникальность `(repository_id, content_digest)`: одинаковый код в двух файлах — один чанк, для retrieval этого достаточно.

### D8 — Миграция

`CREATE EXTENSION IF NOT EXISTS vector` + таблица; downgrade — `DROP TABLE` + `DROP EXTENSION IF EXISTS vector`. Требование обратимости («upgrade → downgrade → upgrade») выполняется; допущение — расширение в окружении создаётся этой миграцией.

## Risks / Trade-offs

- [Последовательный скан замедлится на больших профилях] → потолок задокументирован; HNSW-миграция, когда измерим, а не заранее.
- [Regex-редакция пропускает неизвестные паттерны секретов] → механизм один на context_payloads и профиль; расширение набора — в одном месте.
- [Найденные чанки — вектор prompt injection] → тот же контракт, что у диффа: delimited data, никогда не инструкция; модель без инструментов.
- [Смена модели эмбеддингов обесценивает старые чанки] → фильтр по `embedding_model`; перевложение — будущий change, старые чанки просто не участвуют в поиске.
- [В окружении нет pgvector] → миграция падает явно при развёртывании; образ PostgreSQL локального стека должен содержать расширение (задача в infra).
- [Use case'ы без runtime-вызова до появления воркера] → шов зафиксирован в BACKEND_ARCHITECTURE.md; поведение покрыто тестами на фейках, порты связаны в контейнере.

## Migration Plan

Развёртывание: одна ревизия Alembic, `upgrade head` создаёт расширение и таблицу. Откат: `downgrade` уносит таблицу и расширение; данные профиля не нужны для корректности ревью, потеря при откате допустима. Конфликт head'ов с параллельными change'ами решается сведением в одну цепочку до слияния (правило database-migrations).

## Open Questions

- Точные значения лимитов (k, бюджет байтов, максимальный размер чанка) — дефолты в конфигурации, тюнинг после первых живых прогонов.
- Дефолтная модель эмбеддингов: `nomic-embed-text` как рабочая; замена — правкой конфигурации, подход не меняет.
