# Design

## Context

Состояние OpenTofu — объект `api/terraform.tfstate` в бакете `dmc268-tfstate` (RustFS на стенде, `backend "s3"`, `use_lockfile = true`), деплой ходит к нему через SSH-туннель. В состоянии — значения всех секретов стека: провайдер `docker` хранит `env` контейнеров, переменные — тоже. Шифрование встроено в OpenTofu с 1.7: блок `terraform { encryption { … } }` шифрует состояние и сохранённый план, ключ выводит `key_provider "pbkdf2"` из фразы, шифр — `method "aes_gcm"`. `fallback` у `state` даёт прочитать то, что первый метод не открыл, — так читается старое открытое состояние.

Проверено запуском OpenTofu 1.13.8 локально (CI закреплён на 1.13.2, разница — патч-версии одной ветки), backend `local` и `http`:

- `tofu init` с настоящим бэкендом без фразы падает: конфигурация шифрования «depends on var.state_passphrase which is not available». `tofu init -backend=false` и `tofu validate` без фразы проходят — job `opentofu` в `ci.yml` фраза не нужна.
- Открытое состояние при шифровании с `fallback` на `unencrypted`: `plan` его читает и не переписывает; `apply`, в том числе `apply -refresh-only`, переписывает зашифрованным даже без изменений.
- Зашифрованный файл состояния — JSON-конверт с ключами верхнего уровня `encrypted_data`, `encryption_version`, `lineage`, `meta`, `serial`: serial и lineage читаются без фразы, ресурсы и выходы — нет.
- Неверная фраза: команда падает с ошибкой расшифровки, файл состояния не меняется.
- `errored.tfstate`, который OpenTofu пишет после упавшей записи в бэкенд (сымитировано `http`-бэкендом, отвечающим 500), тоже зашифрован: открытых секретов на раннере не остаётся.
- `tofu state push errored.tfstate` зашифрованного файла **падает**: «Unsupported state file format: This state file is encrypted and can not be read without an encryption configuration». Переменная окружения `TF_ENCRYPTION` не помогает. Расшифровка через временный каталог с локальным бэкендом и `tofu state pull`, затем push открытого файла — работает, и в хранилище состояние ложится зашифрованным.
- `tofu show -json <план>` с заданной фразой работает и выводит её значение в `variables` — так же, как уже выводит остальные секреты `TF_VAR_*`.

Не проверено: версионирование объектов в RustFS (`list-object-versions`, `delete-object --version-id`) — нужно шагу 2, проверяется руками на стенде до него.

## Goals / Non-Goals

**Goals:** состояние и план в бакете и `errored.tfstate` на раннере зашифрованы; переход без ручной перезаписи состояния; восстановление после обрыва работает с зашифрованным файлом; ротация и потеря фразы описаны.

**Non-Goals:** шифрование состояния интерфейса (свой ключ в том же бакете, свой репозиторий); внешний KMS — на стенде его нет, `pbkdf2` с фразой из секрета достаточен; удаление старых открытых версий объекта — шаг 2.

## Decisions

- **`pbkdf2` + `aes_gcm`, фраза — секрет `STATE_PASSPHRASE_DMC268_T1` в environment `stand`.** Внешнего KMS на стенде нет, а статический ключ (`key_provider "static"`) пришлось бы генерировать и хранить так же, как фразу, без растяжки ключа. Environment `stand` — там, где уже живут секреты деплоя, job `deploy` к нему привязан. Валидация переменной — не короче 16 символов: короче `pbkdf2` отказывает сам, но позже и непонятнее.
- **Два шага: `fallback` сейчас, `enforced = true` потом.** Без `fallback` первый деплой не прочитал бы открытое состояние из бакета. С `fallback` любой `apply` переписывает его зашифрованным — первый же деплой после мёржа. `enforced = true` и удаление `unencrypted.legacy` — шаг 2, после того как деплой прошёл и объект проверен: иначе откат на открытое чтение невозможен, а он нужен, пока не убедились, что фраза в секрете та, что надо.
- **Переменная — в `encryption.tf`, а не в `variables.tf`.** Восстановлению нужна конфигурация шифрования без остального стека (провайдеров, ресурсов): оно копирует один файл во временный каталог. Файл с переменной внутри самодостаточен.
- **План шифруется тем же методом.** Сохранённый план содержит значения переменных и `env` контейнеров; деплой пишет его на раннер (`plan.sh`) — открытым он лежал бы рядом с зашифрованным состоянием.
- **Восстановление расшифровывает `errored.tfstate` перед записью.** `tofu state push` зашифрованный файл не читает (проверено, `TF_ENCRYPTION` не помогает). Временный каталог: копия `infra/encryption.tf`, файл как `terraform.tfstate` локального бэкенда, `tofu init`, `tofu state pull` → открытый файл. Он создаётся с `umask 077` во временном каталоге и удаляется на выходе скрипта (`trap`); сверка serial, lineage, ресурсов и выходов и `state push` идут с ним. Push шифрует, в бакет открытое не попадает. Зашифрованная копия для артефакта (`STATE_BACKUP_KEY_DMC268_T1`) по-прежнему делается из `errored.tfstate` как есть — теперь это двойное шифрование, расшифровка в README.
- **Фраза — на весь job, не только на шаги `tofu apply`.** Уже `tofu init` с бэкендом без неё падает. В общем якоре окружения шагов `tofu` и отдельно в шаге восстановления.
- **Ротация — новыми именами, без переименования существующих.** Новый `key_provider` и `method` с новой фразой, прежние — в `fallback`, `apply`, потом прежние убрать. Документация OpenTofu предупреждает: переименованный провайдер ключей или метод не откроет уже зашифрованное состояние.

## Risks / Trade-offs

- **Потеря фразы — потеря состояния.** Восстановить нечем: остаётся резервная копия, снятая раньше (`tofu state pull` с фразой), или пересборка через `tofu import`. Поэтому копия фразы вне GitHub обязательна — секрет GitHub прочитать обратно нельзя.
- **Старые открытые версии объекта.** Если в бакете включено версионирование, открытые версии состояния остаются после первой зашифрованной записи. Их удаление — шаг 2, и поведение RustFS тут не проверено.
- **Фраза в `tofu show -json`.** Значение видно в выводе плана, как и остальные секреты `TF_VAR_*`; `deploy_report.py` берёт из него только счётчики и ничего не сохраняет.
- **Окно до первого деплоя.** Между мёржем и первым `apply` состояние в бакете открыто — как и сейчас; первый деплой идёт сразу после мёржа.
- **Локальная работа сложнее.** Тот, у кого есть доступ к бакету, без фразы `tofu init` не сделает. Это и есть цель: доступа к бакету больше недостаточно.
- **Проверено на 1.13.8, CI — 1.13.2.** На 1.13.2 поведение отдельно не проверяли — это допущение; его подтвердит первый деплой и проверка объекта в бакете (задача 2.3).
