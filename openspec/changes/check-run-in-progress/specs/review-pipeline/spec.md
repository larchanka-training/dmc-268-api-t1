## ADDED Requirements

### Requirement: Прогон в работе отмечается на head

Воркер, захватив прогон, SHALL выставить на head-коммит check run `in_progress` «Идёт ревью» по прогону, который отвечает за head, а на паузе ревью check run паузы. Сбой GitHub SHALL попадать в лог и SHALL NOT прерывать прогон. Любой исход захваченного прогона (ревью записано, упал, выметен очисткой, отменён) SHALL сменять `in_progress` на head итогом по находкам, `failure` или check run паузы.

#### Scenario: Воркер взял прогон

- **WHEN** воркер захватил прогон нового head-коммита
- **THEN** на head выставлен check run `in_progress` «Идёт ревью», после записи ревью его сменяет итог по находкам

#### Scenario: Прогон ещё в очереди

- **WHEN** прогон по `synchronize` создан, а воркер его ещё не захватил
- **THEN** приём check run не выставляет: на новом head-коммите обязательная проверка ждёт «Expected»

#### Scenario: Повторное ревью проверенного коммита

- **WHEN** на head `success` прежнего прогона, и воркер захватил ручной прогон того же коммита
- **THEN** на head `in_progress`, пока новый прогон не запишет ревью

#### Scenario: GitHub недоступен при захвате

- **WHEN** check run `in_progress` GitHub не принял
- **THEN** прогон идёт дальше, сбой пишется в лог, итог выставляется как обычно

### Requirement: Check run ведёт на прогон в кабинете

Check run, выставленный по прогону, SHALL нести `details_url` на экран этого прогона в кабинете: `{PUBLIC_ORIGIN}/reviews/{id прогона}`. Check run паузы и любой check run при пустом `PUBLIC_ORIGIN` SHALL NOT нести ссылку: GitHub тогда ведёт на страницу приложения.

#### Scenario: Ссылка из итога ревью

- **WHEN** прогон записал ревью, и на head выставлен итог по находкам
- **THEN** «Details» у check run открывает `/reviews/{id}` этого прогона в кабинете

#### Scenario: Ссылка из упавшего прогона

- **WHEN** прогон упал, и на head выставлен `failure` «Ревью не удалось»
- **THEN** ссылка ведёт на упавший прогон, откуда ревью запускается заново

#### Scenario: Пауза без ссылки

- **WHEN** на head выставлен check run паузы
- **THEN** `details_url` у него нет

## MODIFIED Requirements

### Requirement: Упавший прогон блокирует merge gate

Прогон, упавший в воркере, выметенный очисткой или не поставленный в очередь, SHALL выставить на свой head-коммит check run `failure` «Ревью не удалось», если он там последний, и первое ревью коммита тоже: иначе висел бы `in_progress`. Прогон, за которым на head есть более поздний, check run SHALL NOT выставлять. На паузе ревью действует «Прогон при паузе ревью не блокирует merge gate». Сбой GitHub SHALL попадать в лог и SHALL NOT подменять ошибку прогона и прерывать очистку.

#### Scenario: Ревью после смены ветки упало, поправка не дошла

- **WHEN** на head `success` прежнего прогона по старой ветке, а прогон нового диффа упал
- **THEN** на head выставляется `failure` «Ревью не удалось»

#### Scenario: Первое ревью коммита упало

- **WHEN** ревью не на паузе, прогон упал, а других прогонов на этот head-коммит нет
- **THEN** `in_progress` на head сменяется `failure` «Ревью не удалось»

#### Scenario: За head отвечает более поздний прогон

- **WHEN** прогон упал, а на этот head-коммит уже создан более поздний прогон
- **THEN** упавший прогон check run не выставляет

#### Scenario: Очистка вымела прогон

- **WHEN** воркер умер посреди прогона, и очистка перевела прогон в `failed`
- **THEN** очистка узнаёт у GitHub номер установки по репозиторию прогона и ставит на head `failure` «Ревью не удалось»

#### Scenario: Очистка вымела прогон живого воркера

- **WHEN** вызов модели длиннее порога, очистка перевела прогон в `failed`, и на этот head-коммит уже было ревью
- **THEN** следующая запись воркера падает, ревью не публикуется, на head ставится `failure` «Ревью не удалось»

#### Scenario: GitHub недоступен во время очистки

- **WHEN** очистка вымела два прогона, а номер установки или check run GitHub не отдал
- **THEN** сбой пишется в лог, оба прогона остаются `failed`, и счётчик выметенных равен двум

#### Scenario: Временный сбой GitHub в проходе очистки

- **WHEN** на первом выметенном прогоне GitHub отвечает временным сбоем (сеть, лимит)
- **THEN** до конца прохода очистка в GitHub не ходит: остальные прогоны выметаются без gate

### Requirement: Пересчёт merge gate только по завершённому ревью head

Пересчёт merge gate по вебхуку закрытия треда SHALL выставлять check run, только если последний прогон на head-коммите PR - `completed`. Если прогона на head нет, или последний идёт, упал или отменён, check run по тредам SHALL NOT выставляться: `success` непроверенному коммиту не даётся, gate выставит прогон, который его проверит. Если после этого последний прогон на head сменился, пересчёт SHALL поправить check run, как прогон.

#### Scenario: Тред закрыт, пока ревью нового head идёт

- **WHEN** после push ревью нового head-коммита ещё идёт, и приходит вебхук закрытия треда
- **THEN** check run на новый head не выставляется

#### Scenario: Ревью после смены целевой ветки упало

- **WHEN** последний прогон на head - `failed` (ревью нового диффа), а прежний `completed` был на старой базе, и закрыт тред
- **THEN** check run не выставляется: остаётся `failure` «Ревью не удалось» упавшего прогона

#### Scenario: Ветку сменили во время пересчёта

- **WHEN** пересчёт выставил check run по `completed` прогону, а приём к этому моменту закоммитил смену ветки и новый прогон
- **THEN** пересчёт выставляет блокировку смены ветки, а если новый прогон уже `completed`, то его итог
