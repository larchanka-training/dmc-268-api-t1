# Design

## Context

Check run `dmc-268-ai-review` создаётся POST на каждое изменение; GitHub показывает и проверяет
по правилам ветки последний созданный check run с этим именем на коммите. Гонки задержанных POST
закрывает `settle_merge_gate`: собрать check по прогону за head (`head_run_in_charge`), POST,
перечитать, повторить, пока check не перестанет меняться (#325, #330, #360).

Рядом с ним решают сами и шлют POST в обход цикла:

| Где | Что решает |
|---|---|
| `start_review_run`, смена ветки | `build_retarget_check()`, всегда `failure` |
| `_block_head_of_failed_run` | `failure`, только если на head уже было ревью (`find_reviewed`) |
| очистка (#356) | то же, что упавший прогон |

`settle_merge_gate` упавшему прогону за head ставит `failure` всегда: правило уже расходится.

Обязательная проверка с `in_progress` не пройдена, как и с `failure`; пройдены `success`,
`neutral`, `skipped` (документация GitHub, «Troubleshooting required status checks»). Без check
run на коммите проверка висит в «Expected» и тоже не пускает мердж.

## Goals / Non-Goals

**Goals:**
- Любой check run `in_progress`, выставленный нами, сменяется итогом на каждом исходе прогона.
- Одно правило gate по состоянию head вместо четырёх.

**Non-Goals:**
- Кнопка «Re-run» на check run (`check_run.rerequested`): отдельная задача.
- Пересчёт gate при закрытии треда (`sync_thread_resolution`) не меняется: его условие «только по
  `completed`» остаётся.
- Хранение id check run и PATCH, см. D5.

## Decisions

### D1. Одно правило по прогону за head

Решение остаётся в `settle_merge_gate`, где ветвление уже было, и становится единственным: по
прогону за head (`head_run_in_charge`), check паузы и признаку «ревью записано».

| Прогон за head | Check |
|---|---|
| нет | `None`, check не выставляется |
| пауза (`pause_check`) | check паузы |
| `completed` или `publishing` с записанным ревью | итог по находкам (`build_merge_gate_check`) |
| `queued` … `publishing` без ревью | `in_progress` «Идёт ревью» |
| `failed`, `cancelled` | `failure` «Ревью не удалось» |

`cancelled` за head бывает, когда фильтр веток отменил прогон, а фильтр потом вернули: `in_progress`
там висел бы. Сейчас этот случай даёт `failure` блокировки смены ветки, теперь `failure` «Ревью не удалось»: мердж так же закрыт.

Альтернатива: оставить решения по местам и добавить `in_progress` в каждое. Отклонена: правило
уже расходится в двух местах, а пятый вход умножил бы расхождения.

Альтернатива: вынести таблицу в чистую функцию домена. Отклонена: у неё один вызывающий, а находки
нужны только одной строке таблицы. Функции пришлось бы либо читать их заранее на каждой попытке,
либо возвращать вид check отдельным перечислением ради одного `if`.

### D2. Один пересчёт с перечитыванием

`settle_merge_gate` читает состояние, решает по D1, шлёт POST, перечитывает. Его
зовут: воркер при захвате и после записи ревью, упавший прогон, очистка, приём при смене ветки,
компенсация несостоявшейся постановки. `build_retarget_check` удаляется, а
`block_head_of_failed_run` сводится к проверке «прогон на head последний» и вызову пересчёта.

Параметр `run_id` уходит. Ветка «свой прогон» (`latest.id == run_id`) нужна была потому, что
`publishing` не отличался от «ревью ещё не записано»; признак «ревью записано» из #360 это
различает, а воркер зовёт пересчёт уже после записи ревью.

### D3. `in_progress` ставит воркер при захвате, а не приём

- В пути вебхука не появляется вызов GitHub с повторами адаптера; GitHub ждёт ответ 10 с.
- Пока задача в очереди, на новом коммите «Expected», и мердж и так закрыт.
- Пути без захвата (не поставлен в очередь, выметен из `queued`, DLQ без строки прогона)
  `in_progress` не оставляют.

Исключение составляет смена целевой ветки: там надо перекрыть прежний `success` сразу, приём зовёт тот же
пересчёт, и функция даёт `in_progress`. Сбой POST там по-прежнему 502 с откатом. При захвате сбой
только в лог: до него на head пусто или итог того же диффа.

### D4. Ссылка строится в адаптере

В `MergeGateCheck` `conclusion` становится `str | None` (`None` означает `in_progress`), а
`set_merge_gate_check` получает `run_id: UUID | None`: прогон, по которому выставлен check, а у
check паузы `None`. Ссылка относится к прогону, а не к содержимому check, поэтому в
`MergeGateCheck` её нет, и check одного содержания сравниваются как раньше. Пересчёт сравнивает
пару «check, прогон»: сменился прогон за head, значит, check выставляется заново со своей ссылкой.

Адаптер GitHub получает `public_origin` при сборке и ставит
`details_url = f"{public_origin}/reviews/{run_id}"`, если оба заданы. Маршрут кабинета знает только
инфраструктура; приложение не читает настройки.

### D5. Без хранения id check run

Вариант: создать check run при захвате, хранить его id и обновлять PATCH, тогда поздний POST старого
прогона менял бы только свой объект. Отклонён: check паузы, пересчёт по треду и смена ветки
всё равно создают новые объекты, и PATCH прогона в старый объект был бы не виден. Получилась бы
миграция и второй механизм рядом с перечитыванием, а не замена ему.

## Risks / Trade-offs

- [Итоговый POST не принят все три попытки] → `in_progress` висит до следующего события; сейчас в
  том же случае висит устаревший итог. Через 14 дней GitHub помечает его `stale`. Выход: ручной
  запуск по `details_url`.
- [Сбой модели на первом ревью] → на PR красное «Ревью не удалось» вместо «Expected». Мердж закрыт
  так же, как сейчас, но причина видна и есть ссылка на прогон.
- [Лишний POST на прогон] → один вызов GitHub при захвате; на потоке прогонов это вдвое больше
  check run на коммит.

## Migration Plan

Миграций и настроек нет: `PUBLIC_ORIGIN` уже задан на стенде. Откат: реверт коммита; check run,
выставленные до отката, сменит следующий прогон.
