# Design

## Context

После вливания #36 в `develop` в дереве спек остались два противоречия между
`review-pipeline` (написана до разведения скоупов) и `webhook-intake`
(написана позже и определяет принятое поведение приёма): регистрация
репозитория по вебхуку и обновление состояния запроса при `closed`. Код
приёма (#37) реализует `webhook-intake`; противоречит только текст
`review-pipeline` (треды финального ревью #37 от @Grinv).

## Goals / Non-Goals

**Goals:**

- Спеки в объединённом дереве не противоречат друг другу: `review-pipeline`
  повторяет решение `webhook-intake` — репозиторий не регистрируется по
  вебхуку, `closed` игнорируется.
- Зафиксировать переходный путь регистрации репозитория до появления
  отдельной ручки.

**Non-Goals:**

- Сама ручка регистрации (REST или CLI) — отдельный тикет, в этот PR не
  входит.
- Изменение кода, схемы базы, REST-контракта и топологии очереди.

## Decisions

- **D1 — поведение задаёт `webhook-intake`, `review-pipeline` выравнивается
  под него.** Альтернатива (вернуть авто-регистрацию `_upsert_repository` из
  `develop`) отвергнута: противоречит принятому в `webhook-intake`
  консервативному поведению (чужой вебхук ничего не создаёт) и направлению
  ревью.
- **D2 — сценарий про `closed` удаляется, а не реализуется.** Приём запускает
  ревью только `opened`/`synchronize`; состояние запроса обновляется из
  свежих метаданных VCS при обработке вебхука, отдельная ветка для `closed`
  не нужна. Сценарий «Закрытие запроса на изменение отражается в хранилище»
  не имеет реализующего кода в объединённом дереве — оставленный сценарий
  описывал бы несуществующее поведение.
- **D3 — до появления ручки регистрации репозиторий вносится вручную.**
  Раздел в README фиксирует переходный путь (SQL-вставка на стенде) и ссылку
  на тикет с будущей ручкой. Альтернативы (CLI-команда или REST-ручка в этом
  PR) отвергнуты: PR #37 уже большой, регистрация — отдельное поведение со
  своей авторизацией и контрактом.

## Risks / Trade-offs

- До ручки регистрации репозитории вносятся вручную — операция на стенде
  выполняется человеком; риск опечатки закрывается проверкой уникального
  индекса по `(provider, provider_id)`.
