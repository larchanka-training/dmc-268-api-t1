## Context

`JobQueue` сегодня — только строка в таблице «Спроектированы, но не
реализованы» `docs/BACKEND_ARCHITECTURE.md`, с единственным методом
`enqueue`. `app/worker` описан в `docs/SYSTEM_DESIGN.md` как второй процесс
модульного монолита, но кода нет. Это первое изменение из трёх
последовательных (очередь → пайплайн → REST API) на одной ветке; следующее
изменение (`add-review-pipeline`) подключит к воркеру реальный обработчик
доменного пайплайна — здесь воркер получает только универсальный
consume-цикл.

## Goals / Non-Goals

**Goals:**
- Порт `JobQueue` с адаптером на RabbitMQ, соответствующим топологии
  `SYSTEM_DESIGN.md` §4.2 (одна очередь, `x-max-priority`).
- Dead-letter queue: необработанное сообщение не крутится в цикле вечно.
- Процесс `app/worker` как тонкая точка входа, симметричная `app/main.py`.
- CI и локальный docker-compose поднимают RabbitMQ по-настоящему, не только
  описывают его в документе.

**Non-Goals:**
- Приоритет сообщения по тарифу аккаунта — `accounts`/биллинг не
  реализованы, приоритет фиксированный.
- Retry с backoff перед DLQ — сразу nack без requeue.
- Доменный обработчик сообщения (парсинг job, LLM, сохранение результата) —
  предмет `add-review-pipeline`.

## Decisions

**RabbitMQ, не Redis.** Уже выбран архитектурой (`BACKEND_ARCHITECTURE.md`,
`SYSTEM_DESIGN.md`, `infra/main.tf`); Redis по `backend-base-setup` не должен
обрастать кодом до своего настоящего вызывающего кода (cache/idempotency).
Альтернатива (переопределить на Redis) обсуждалась и отклонена пользователем.

**Одна очередь с `x-max-priority`, без exchange-роутинга.** Соответствует
буквально §4.2 SYSTEM_DESIGN.md: «Очередь одна, с x-max-priority». DLQ —
отдельный fanout-exchange `review_jobs.dlx` + очередь `review_jobs.dlq`,
подключённые через `x-dead-letter-exchange` аргумент основной очереди —
стандартный RabbitMQ-паттерн, не альтернативная архитектура.

**Фиксированный приоритет вместо расчёта по тарифу.** `enqueue` пока не может
узнать тариф аккаунта — такого понятия в хранимой модели нет. Публикуем с
дефолтным приоритетом (5 из диапазона 0–9); когда появится `accounts`,
вычисление приоритета — это правка адаптера, не порта (сигнатура `enqueue(job)`
не меняется).

**`app/worker/__main__.py` — тонкая точка входа, как `app/main.py`; сам пакет
`app.worker` — на уровне `app.api`/`app.infrastructure`.** Только файл
`__main__.py` добавлен в forbidden-контракт "точка входа тонкая" (не весь
пакет): `app/worker/factory.py` играет ту же роль, что `app/api/factory.py` —
собирает зависимости, включая адаптеры инфраструктуры, — поэтому он не может
быть заперт тем же запретом, что и сам `__main__.py`. В layers-контракте
`app.worker` становится третьим сиблингом рядом с `app.api : app.infrastructure`:
`app/worker` и `app/api` документированы как равноправные процессы одного
монолита с общим доступом к `infrastructure`/`application`/`domain`; именно
поэтому `app.api` уже разрешено импортировать `app.infrastructure`.

**Консьюмер в этом change — универсальный, без домена.** Принимает
`Callable[[bytes], None]` как обработчик; ack/nack-решение — чистая функция
`should_ack(exc)`, тестируемая без брокера. Разделение по границе «есть
исключение или нет» — минимально достаточная логика для этого change;
подключение реального пайплайна откладывается на `add-review-pipeline`,
чтобы не смешивать в одном коммите инфраструктуру очереди и бизнес-логику
ревью.

**`JobQueue` не входит в `ports.__all__`.** Этот список используется тестом
`tests/test_container.py::test_every_declared_port_has_an_adapter_and_a_caller`
как источник имён для проверки `SqlAlchemy{Port}` в `db/repositories.py` —
специфично для портов хранения. `JobQueue` живёt в отдельном модуле
`app/application/ports/job_queue.py`; тест обобщается явной картой
"порт → adapter → файл", а не регэкспом по одному файлу.

## Risks / Trade-offs

[Сообщение теряется, если воркер падает между `basic_consume`-callback и
`ack`] → RabbitMQ переставит недоставленное сообщение другому консьюмеру при
разрыве соединения (auto-ack выключен); двойная обработка одного и того же
`ReviewRun` безопасна по требованию `review-data-model` «Повторная доставка
той же задачи безвредна» (partial unique index уже это гарантирует на уровне
следующего change).

[DLQ без ретраев может отправить туда сообщение из-за временного сбоя, а не
системной ошибки] → осознанный trade-off для этого тикета (см. Non-Goals);
DLQ — ручной разбор, а не автоматический retry. Зафиксировано в
`docs/SYSTEM_DESIGN.md` как то, что стоит пересмотреть, когда появится
наблюдаемость по DLQ.

[Новый обязательный `Settings.rabbitmq_url` ломает все места, где тесты
строят `Settings(database_url=...)` напрямую] → механическая правка всех
таких мест в рамках этого же change; альтернатива (сделать поле опциональным)
отклонена — противоречит требованию `backend-architecture`: «Запуск SHALL
завершаться явной ошибкой, если обязательный параметр отсутствует».

## Migration Plan

Новый код, новая инфраструктура, миграций БД нет. Откат — two-way door: PR
ревертится обычным коммитом, RabbitMQ-контейнер и очередь не хранят ничего,
что нужно было бы откатывать отдельно.
