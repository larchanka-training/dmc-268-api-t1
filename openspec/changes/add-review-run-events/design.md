# Design

## Context

Мотивация — в `proposal.md`. Здесь только то, что определяет подход.

- Статус прогона пишет **воркер** (`app/worker`, `run_review`), читает **API**
  (`app/api`) — это разные процессы одного образа. Общего у них только
  PostgreSQL и RabbitMQ; сообщений о прогрессе между ними нет.
- Каждый переход — отдельный коммит (`_transition` в
  `app/application/review_pipeline.py`), поэтому свежий статус виден в базе
  сразу после перехода.
- Все нынешние обработчики API — синхронные `def` поверх синхронного
  SQLAlchemy; зависимость `get_unit_of_work` держит транзакцию и соединение на
  всё время запроса.
- Redis поднят в `docker compose`, но спека `backend-base-setup` запрещает
  клиент Redis в коде до первого вызывающего.
- Контракт событий уже зафиксирован потребителем: `design.md` change'а
  `review-run-live-status` в `dmc-268-ui-t1` (PR #23). Клиент — нативный
  `EventSource`, таймаут тишины 45 секунд, транспорт через `nginx` фронтенда
  проверен на заглушке (HTTP/1.1, HTTP/2, HTTP/3).
- Авторизации в API нет (#46 в планировке); REST открыт целиком.

## Goals / Non-Goals

**Goals:**

- Контракт потока совпадает с тем, на котором протестирован фронтенд, —
  подмена mock-источника не требует правок экрана.
- Никакой новой инфраструктуры и зависимостей.
- Логика «какое событие отправить» проверяется тестом без HTTP, базы и
  настоящего времени.

**Non-Goals:**

- Доставка каждого промежуточного перехода: поток отражает состояние, а не
  журнал (спека `review-run-events`).
- `Last-Event-ID` и повтор истории — снимок при подключении их заменяет.
- Авторизация и проверка `Origin` — приходят с #46 одной зависимостью на REST
  и SSE.
- Масштабирование на тысячи одновременных потоков.

## Decisions

### D1. API узнаёт о переходах опросом базы внутри обработчика

Обработчик раз в секунду читает прогон и сравнивает статус с последним
отправленным. Требование спеки — «не позже 2 секунд после записи» — закрыто с
запасом.

Альтернативы:

- **Redis pub/sub.** Нужны клиент, порт, адаптер и публикация из воркера —
  новая точка отказа и правка `backend-base-setup` ради экрана, который смотрит
  один человек. Не окупается.
- **PostgreSQL `LISTEN/NOTIFY`.** Требует выделенного соединения на слушателя
  вне пула и `NOTIFY` в коде записи статуса. Выигрыш — секунда задержки,
  которую пользователь не заметит.
- **События через RabbitMQ.** Fanout-обмен и очередь на каждый поток; сложнее
  обоих вариантов выше.

Опрос — «скучная конструкция»: один `SELECT` по первичному ключу в секунду на
открытый поток. Если потоков станет много, замена на `LISTEN/NOTIFY` меняет
только источник чтения, контракт и генератор событий остаются.

### D2. Решение о событии — чистая функция, цикл — генератор с внедрёнными часами

Разделение по правилу «решение — функция над данными»:

- **Чистая функция** в `app/domain`: по прогону, последнему отправленному
  статусу и времени с последнего события возвращает, что отправить — `status`,
  `ping` или ничего — и нужно ли закрыть поток. Тест сверяет точные значения.
- **Асинхронный генератор** в `app/application`: крутит цикл, зовёт чистую
  функцию. Чтение прогона и ожидание приходят аргументами, поэтому тест
  прокручивает «15 секунд тишины» без настоящего сна.
- **Роутер** в `app/api`: отдаёт 404 до начала потока, сериализует события в
  формат SSE и ставит заголовки. Сериализация — отдельная чистая функция.

Порта нет: внешней системы, которую подменял бы адаптер, здесь не появляется —
прогон читается существующим `ReviewRunRepo.get`.

### D3. Обработчик асинхронный, чтение базы — в пуле потоков, короткими транзакциями

Поток живёт минуты; синхронный обработчик занял бы поток пула Starlette на всё
это время. Поэтому обработчик — `async def`, а каждое чтение прогона уходит в
пул потоков и открывает **свой короткий** `UnitOfWork` из контейнера.
Зависимость `get_unit_of_work` здесь не используется: она удержала бы
соединение с базой на всю жизнь потока, и пяти открытых вкладок хватило бы,
чтобы исчерпать пул.

Отключение клиента обрабатывает Starlette: при `http.disconnect` генератор
отменяется на ближайшем ожидании, отдельная проверка не нужна.

### D4. Этап сбоя выставляет `advance`, а не вызывающие

`advance(run, FAILED, now)` — единственное место, через которое прогон
попадает в `failed`: им пользуются и `_mark_failed` в пайплайне, и
`sweep_stale_runs`, и приём вебхука при сбое постановки в очередь. Там же
`failed_stage` получает прежний статус, если это один из трёх этапов
обработки, и `None`, если прогон упал из `queued`.

Альтернатива — выставлять поле в каждом вызывающем — повторила бы правило в
трёх местах и разошлась бы на четвёртом.

`None` для сбоя из `queued` — выбор в пользу контракта фронтенда: его схема
ждёт один из трёх этапов или `null`, и значение вне схемы отбросило бы событие
целиком. Сам факт «упал, не начав» виден по `failure_reason`.

### D5. Колонка `failed_stage` — существующий enum `review_run_status`

Nullable-колонка типа `review_run_status`: новый enum повторил бы список
статусов во втором месте. Ограничение `CHECK` запрещает непустой этап у
прогона не в `failed` и значения вне трёх этапов — инвариант из D4 держит не
только код.

Прежние упавшие прогоны остаются с `NULL`; фронтенд для них уже показывает
«Этап сбоя неизвестен». Заполнять их задним числом нечем.

### D6. Поля событий и ответа — в `snake_case`

Так отдаёт нынешний `GET /api/v1/reviews/{id}` и так написан контракт
фронтенда. `docs/openapi/openapi.yaml` описывает `camelCase` и расходится с
реализацией целиком — это известный долг вне этого change. Данные события
потока описываются в нём отдельной схемой в том виде, в каком реально уходят
по сети; в существующую схему `ReviewJob` этап сбоя добавляется в её же
`camelCase` (`failedStage`), рядом с уже описанным там `lastProgressAt`, —
иначе одна схема смешала бы два стиля.

### D7. Без авторизации, как остальной REST

Поток доступен так же, как `GET /api/v1/reviews/{id}`, который отдаёт те же
данные. Отдельная защита одного эндпоинта ничего не закрыла бы; #46 добавляет
`current_user` на REST и SSE разом.

## Risks / Trade-offs

- **[Промежуточные этапы пролетают]** На заглушке LLM прогон проходит
  `building_context → completed` за миллисекунды, и клиент увидит только
  `queued` и `completed`. → Это следствие D1 и зафиксировано в спеке; с
  настоящей моделью этап `analysing` длится секунды и десятки секунд.
- **[Нагрузка на базу растёт с числом потоков]** Один запрос в секунду на
  открытый поток. → Фронтенд закрывает поток в скрытой вкладке и после
  терминального статуса; запрос — по первичному ключу. Путь отхода — D1.
- **[Пул потоков Starlette]** Чтение занимает поток на миллисекунды раз в
  секунду, но при сотнях потоков конкурирует с синхронными обработчиками. →
  Для стенда и демо запас большой; признак проблемы — рост времени ответа REST.
- **[Деплой рвёт открытые потоки]** При замене контейнера соединения
  обрываются. → `retry: 3000` и снимок при подключении: клиент переподключается
  и получает актуальный статус.
- **[Буферизация в прокси]** `nginx` может придержать события. →
  `X-Accel-Buffering: no`; на стенде проверяется, что событие доходит сразу
  (задача в `tasks.md`).
- **[Две головы Alembic]** PR #51 тоже добавляет ревизию поверх `0002`. →
  `down_revision` выставляется по `develop` на момент мерджа; `alembic heads`
  — в проверках перед коммитом и в CI.
- **[Поток без авторизации]** Любой, кто знает id прогона, видит его статус. →
  Тот же уровень, что у существующего REST; закрывается #46.

## Migration Plan

1. Миграция добавляет nullable-колонку и `CHECK` — существующие строки ей
   удовлетворяют, блокировка таблицы короткая.
2. Порядок выкладки штатный: контейнер миграций, затем API и воркер из одного
   образа. Старый воркер с новой схемой совместим (колонку он не пишет), новый
   со старой схемой не встречается — миграция идёт первой.
3. Откат: `alembic downgrade -1` удаляет ограничение и колонку; реверт коммита
   убирает эндпоинт. Фронтенд на mock-источнике от бэкенда не зависит.

## Open Questions

- Порог предупреждения о зависшем прогоне на фронтенде: на бэкенде это
  `stale_run_timeout_seconds`, по умолчанию 1800 секунд, а фронтенд пока берёт
  10 минут. Сообщить значение автору `dmc-268-ui-t1#20`; на реализацию не
  влияет.
- Нужно ли фронтенду отличать сбой из `queued` от прочих отдельным значением
  `failed_stage`. Сейчас — `null` (D4); расширение обратно совместимо.
