# Design

## Context

`review_runs_total{status}` пишет тот, кто перевёл прогон в терминальный статус (порт
`RunOutcomeRecorder`). Прогон без денег завершается `completed` с `coverage_reason = balance`, и
сейчас ветка отказа в `run_review` счётчик не трогает.

## Decisions

### D1. Отказ — значение метки, а не статус прогона

`refused` есть только в метрике: в базе прогон остаётся `completed` с причиной покрытия, контракт
API не меняется. Значение — константа порта `RUN_REFUSED`, рядом с `completed` и `failed`,
которые берутся из `ReviewRunStatus`.

### D2. `ReviewRunsFailing` по `status=~"completed|failed"`

Иначе десять отказов на три падения опустили бы долю упавших ниже 30 %. Порог «хотя бы три
прогона» тоже без отказов: три отказа и одно падение не должны давать 100 % из одного ревью.

### D3. Порог `ReviewRunsRefused`: больше половины за час и хотя бы три

Отдельный отказ — нормальная ситуация (у плательщика кончились деньги), алерт на каждый отказ
шумел бы. Больше половины исходов за час — признак массовой причины: ошибка оценки, снятый
плательщик популярного репозитория, `BILLING_ENABLED` при пустых балансах. Окно час, а не
30 минут, как у падений: отказ не теряет работу, его можно разобрать позже. Уровень warning:
сервис работает, не хватает денег. Пока биллинг выключен, отказов нет и алерт не горит.

### D4. Страница статуса не меняется

`ReviewRunsRefused` не входит в `ALERT_RULES`: страница статуса говорит о сбоях сервиса, а отказ
по балансу касается одного плательщика.

## Risks / Trade-offs

- Отказ повторной доставки уже завершённого прогона — дубль и счётчик не трогает, как и раньше.
- Счётчик не различает плательщиков: один плательщик без денег с серией пушей или перезапусков
  при малом трафике поднимет `ReviewRunsRefused`, как массовая причина. Метка плательщика
  дала бы кардинальность; разбор — по базе, `coverage_reason = balance` с плательщиком.
- Ряд `refused` появится у всех процессов с нулём, даже при выключенном биллинге: это три ряда
  вместо двух, кардинальность не меняется.
