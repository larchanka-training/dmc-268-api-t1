# Design: доводка хранения и использования токена пользователя

## Context

Уточняет change `repositories-via-user-token` (D3, D4, D5) по итогам ревью безопасности PR #111.

## Decisions

### D1. `401` после параллельного refresh

Запрос A взял access token, запрос B той же сессии в это время обменял refresh token. Если GitHub отзывает прежний access token при выдаче нового, A получает `401` на уже заменённый токен. Поэтому на `ProviderTokenRejected` токен перечитывается: сменился — вызов повторяется один раз с новым; не сменился или повтор тоже `401` — сессия закрывается. Повтор один: бесконечного цикла нет.

### D2. Сбой обмена при ещё действующем токене

Refresh начинается за 5 минут до истечения. Если обмен не удался по причине провайдера (`OAuthProviderUnavailable`: сеть, `5xx`, ошибка настройки) или чужая блокировка не отпущена за 15 секунд (`ProviderTokenBusy`, наследник `OAuthProviderUnavailable`), а `now < access_expires_at` (`is_usable`), используется прежний access token, в лог — предупреждение без значений. Истёк — `502`, как раньше. Отказ GitHub в refresh token (`bad_refresh_token`) — по-прежнему закрытие сессии: refresh token мёртв, сессия всё равно умрёт через минуты.

### D3. Ответ GitHub на refresh потерян или коммит упал

GitHub принял refresh token и выдал новую пару, но ответ не дошёл (обрыв, таймаут чтения) или наш коммит не прошёл. Старый refresh token израсходован, новый не сохранён. Следующий refresh получит `bad_refresh_token` → сессия закрывается → пользователь входит заново и получает новую пару. Пока прежний access token действует, запросы идут им (D2). Состояния «сессия навсегда без рабочего токена» не бывает: худший исход — один перелогин.

### D4. Таймауты и ожидание блокировки

HTTP к GitHub от имени пользователя (вход, refresh, отзыв, список) — `httpx.Timeout(10.0, connect=5.0)`. Это таймаут на каждую фазу (подключение 5 с, запись, чтение и ожидание пула по 10 с), а не на запрос целиком: держатель блокировки при refresh в худшем случае ждёт GitHub дольше 10 секунд. Поэтому ожидающий берёт блокировку с `SET LOCAL lock_timeout = '15s'` (только эта транзакция): дольше — `ProviderTokenBusy`, затем D2. Типичный refresh — доли секунды; 15 секунд не держат соединение пула бесконечно.

### D5. Список: `403`, лимит, пагинация

- `403` на `GET /user/installations/{id}/repositories` без признаков лимита — установка недоступна этому токену (например, организация требует SAML SSO, а токен не авторизован), пропускается, как `404`. На `GET /user/installations` такой `403` — `502`: пропускать там нечего.
- `403` с `x-ratelimit-remaining: 0` или `retry-after` — лимит GitHub («Rate limits for the REST API»), это сбой, а не отсутствие доступа: `VcsUnavailableError`, `502`.
- Пагинация — до `total_count` (без лишнего запроса пустой страницы), короткой страницы или 50 страниц (5000 элементов). На пределе список усекается с предупреждением в логе: неполный список ничего не раскрывает, а бесконечный ответ не держит запрос. `total_count` не целое — неожиданное тело, `502`.

### D6. Токен через `httpx.Auth`

`BearerAuth(Secret)` раскрывает токен только в `auth_flow` при отправке: в локальных переменных адаптера (и в трейсбеке с ними) открытого значения нет. Внутри httpx заголовок запроса, разумеется, есть — поэтому исключения транспорта по-прежнему гасятся `from None`.

### D7. Отзыв токена при выходе

`logout` возвращает access token удалённой сессии; ручка ставит `revoke_quietly` фоновой задачей FastAPI — после ответа `204`, поэтому выход не ждёт GitHub. Адаптер: `DELETE /applications/{client_id}/token`, basic auth `client_id:client_secret`, тело `{"access_token": …}` («Delete an app token» — один токен, не вся авторизация приложения). `204`, `404`, `422` — токена у GitHub больше нет; прочее и сеть — `OAuthProviderUnavailable`, которую `revoke_quietly` пишет в лог без токена и глушит. Сложность небольшая (метод порта, фоновая задача), поэтому сделано, а не записано риском.

Не отзываются: refresh token отдельно (у GitHub нет отдельного отзыва; удалён из базы), токен сессии, заменённой новым входом, и токены сессий, удалённых уборкой. Они перестают существовать у нас и истекают у GitHub сами (8 часов access, 6 месяцев refresh, если включено истечение) — принятый риск: без базы и ключа ими не воспользоваться.
