# Proposal

## Why

**Блокировки состояния нет.** `backend "s3"` в `infra/backend.tf` работает без `use_lockfile`. `concurrency: deploy` не даёт столкнуться двум прогонам деплоя, но ручной `tofu apply` по README (доступ к стенду у части команды есть) идёт мимо этой очереди. Два одновременных `apply` пишут состояние поверх друг друга, и расхождение состояния с сервером узнаётся уже на следующем деплое.

**RabbitMQ 3.13 устарел.** Ветка 3.13 больше не получает бесплатных исправлений, актуальная — 4.3. Сейчас обновиться дешевле всего: приложение на `develop` брокер ещё не использует, очередь приходит только в PR #36.

## What Changes

- В `backend "s3"` включается `use_lockfile = true`: OpenTofu кладёт рядом с состоянием lock-объект условной записью (`If-None-Match`), второй запуск получает отказ.
- Образ брокера — `rabbitmq:4.3-alpine`.
- Том брокера заводится заново (`dmc268-rabbitmq-v4-data`), старый удаляется деплоем.

**Не входит:** `docker-compose.yml` и сервис RabbitMQ в `ci.yml` — они появляются в PR #36 с `3.13-alpine` и должны перейти на 4.3 там же, иначе описания стека разойдутся. Шифрование состояния — отдельное изменение.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `backend-delivery`: требование «Состояние развёртывания переживает исполнителя» дополняется запретом на одновременную запись состояния двумя запусками.

## Impact

- `infra/backend.tf`, `infra/main.tf`, `infra/README.md`.
- **Данные брокера на стенде теряются.** Сейчас их нет: на `develop` брокер не используется. Если PR #36 окажется в `develop` раньше этого изменения и в очередях появятся сообщения, их нужно будет вычитать до деплоя.
- Упавший посреди `apply` запуск оставит lock-объект; снимается он `tofu force-unlock <ID>`, ID печатается в ошибке второго запуска.
