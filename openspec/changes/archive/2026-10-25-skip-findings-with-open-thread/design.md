## Context

`publish_review` публиковал все находки прогона. Тред бота и находка повторного прогона ничем не связаны, поэтому на каждом push то же замечание появлялось новым inline-комментарием. Сопоставление по ключу (путь, сторона, строка, категория) уже было в `_publish_thread_follow_ups`: ответ модели находил тред по строке из прошлого прогона (`_line_for_anchor`). Текущей строки треда на GitHub в коде не было. Закрытие тред получал из трёх мест — бот после ответа, вебхук `pull_request_review_thread`, сверка `sync_open_threads_from_host` после публикации — и все они писали один флаг `thread_resolved`: кто закрыл, система не различала.

## Goals / Non-Goals

**Goals:** повторный прогон не повторяет замечание, о котором уже говорит тред бота; тред, закрытый человеком, не воскрешается; одна проблема не даёт и нового inline, и ответа в тред; подавленная находка не снимает блокировку мерджа.

**Non-Goals:** передача открытых тредов в промпт модели (модель сейчас их не видит, `threadFollowUps` по ним приходят только «вслепую»); закрытие старого треда, когда вместо него опубликован более серьёзный; сверка закрытого в базе, но открытого заново на GitHub треда без вебхука.

## Decisions

- **Текущая строка — из `reviewThreads` GraphQL, тем же запросом.** У `PullRequestReviewThread` есть `line` (строка в текущем диффе), `originalLine` и `isOutdated` (документация GitHub GraphQL, объект `PullRequestReviewThread`). На живом PR проверено: у устаревшего треда `isOutdated: true` и `line: null`, у живого `line` уже отличается от `originalLine`, когда над строкой дописали код; REST `GET /pulls/comments/{id}` даёт те же `line`/`original_line`. Запрос `reviewThreads` уже был в адаптере (сверка закрытия), поэтому новый вызов не нужен: порт `fetch_review_threads_state` отдаёт по корню и `resolved`, и `line` (`None`, если тред устарел). `_line_for_anchor` для находок не годится: это строка прошлого head.
- **Одна сверка на прогон — до публикации.** Чтобы решить, публиковать ли находку, состояние тредов нужно до `POST …/reviews`. Повторная сверка после публикации лишняя: новые треды прогона открыты, свои закрытия бот записывает сам, ручные закрытия во время публикации догонит вебхук. Поэтому сверка перенесена, а не добавлена: один GraphQL-запрос с пагинацией на прогон; на первом прогоне PR, где тредов бота нет, запроса нет вовсе.
- **Решение — чистая функция `thread_coverage`.** Совпадение: тот же путь, сторона, категория и текущая строка треда. Открытый тред покрывает находку, если её серьёзность не выше его (`low < medium < high < critical`). Тред, закрытый человеком, покрывает любую, кроме `critical` при замечании треда ниже `critical` (#169, п. 3а). Тред, закрытый ботом, не покрывает ничего. Открытые треды на том же месте, которые не покрыли находку (серьёзность выросла), возвращаются как вытесненные.
- **Закрыл бот или человек — отметка при закрытии ботом.** Флаг `published_comments.thread_resolved_by_bot` ставит только `_publish_thread_follow_ups` после успешного `resolveReviewThread`; любое другое закрытие (вебхук, сверка) — человеком. `resolvedBy` из GraphQL не взят: поле типа `User`, а бот GitHub App — `Bot`, и что придёт для закрытия токеном инсталляции, без живого App не проверить. Гонка с вебхуком о собственном закрытии бота безопасна: вебхук до записи бота затирается ею, после — видит тот же `thread_resolved` и ничего не меняет. Открытие треда заново (`unresolved`) снимает отметку. Треды, закрытые до миграции, считаются закрытыми ботом (`thread_resolved_by_bot = thread_resolved`): кто закрыл, неизвестно, а «человек» навсегда заглушил бы вернувшийся `critical`, который бот раньше сам закрыл как исправленный, и пропустил бы его мимо merge gate. «Бот» оставляет для старых тредов поведение до правки — замечание публикуется заново: шум, но не потерянный `critical`.
- **Почему тред, закрытый ботом, ничего не покрывает.** Бот закрывает тред, когда модель сочла замечание исправленным или неактуальным (для `critical` — только при подтверждённом изменении строки). Если та же проблема снова находится на той же строке, она вернулась: молчать значит потерять её, а закрытый тред мердж уже не блокирует.
- **Связь находки с тредом — ссылка на находку треда.** `findings.covered_by_finding_id` → `findings.id`: у inline-треда ровно одна находка (`published_comments.finding_id`), так что ссылка однозначно указывает тред и не создаёт циклического внешнего ключа `findings ↔ published_comments`. Без миграции выразить связь нельзя: запись в `published_comments` означала бы публикацию, которой не было, и упала бы на `uq_published_comments_provider_comment_id`. API прогона отдаёт поле как есть.
- **Ответы в треды не дублируют находки и не ломают gate.** Тред, вместо которого опубликован новый inline, в этом прогоне ответа не получает: иначе одна проблема — два комментария. Тред, покрывающий находку прогона, бот не закрывает, даже если модель ответила «исправлено»: проблема на месте, и закрытие сняло бы блокировку критичного треда. Gate по-прежнему считается по открытым тредам в базе; подавленная находка покрыта тредом не ниже её серьёзности или тредом, закрытым человеком, — блокировка остаётся ровно там, где была.
- **Сбой сверки — публикуем всё.** Без ответа GitHub строка треда неизвестна: подавить находку по строке прошлого прогона значит рискнуть спрятать замечание под устаревшим тредом. Повтор комментария при недоступном GraphQL дешевле потерянного `critical`. Gate — по базе, как и раньше.

## Risks / Trade-offs

- Модель называет одну проблему то `correctness`, то `readability` → разная категория не совпадёт, замечание повторится. Ключ тот же, что у ответов в треды; расширять его без данных не стали.
- Если PR ушёл вперёд между постановкой прогона и публикацией, `line` треда — по новейшему head, а находка — по head прогона → в редком случае повтор или пропуск совпадения. Тот же сдвиг уже есть у публикации inline.
- Пропущенный вебхук `unresolved` для треда, закрытого ботом, оставляет отметку бота → находка опубликуется снова: повтор, а не потеря.
