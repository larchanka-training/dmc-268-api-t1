## Context

Мотивация — `proposal.md`, требования — дельты `specs/review-rest-api/spec.md` и
`specs/webhook-intake/spec.md`. Что есть сейчас:

- `load_run_diff` (`app/application/use_cases/run_diff.py`) на промахе кэша зовёт
  `vcs.fetch_diff(..., max_bytes=run_diff_max_bytes)`, пишет сырой дифф в кэш диффов и строит
  представление (`parse_diff` → `build_diff_view`). `VcsFileTooLargeError` превращается в
  `DiffTooLargeError`, ручка отвечает `422 DIFF_TOO_LARGE`.
- Адаптер (`GitHubVcsGateway._request`) отказывает рано по объявленному `content-length` и
  обрывает поток на лимите. Ответ `4xx`, кроме `404` и отказов лимита, — `VcsError`, у ручки —
  `502 SCM_UNAVAILABLE`.
- Кэш диффов — `InMemoryCacheStore(max_entries=24)` в контейнере API, запись не больше
  `RUN_DIFF_MAX_BYTES` (2 МиБ). Контейнер API — 512 МБ, один процесс uvicorn.
- Воркер получает дифф тем же `fetch_diff` с `DIFF_MAX_BYTES` (5 МиБ); `fetch_review_diff`
  переводит `VcsFileTooLargeError` в `DiffTooLargeError`, прогон — `failed` с `DIFF_TOO_LARGE`.

## Goals / Non-Goals

**Goals:**

- Один запрос диффа не выводит память API за предел контейнера, сколько бы строк ни было в диффе.
- Отказ GitHub строить дифф показывается как «дифф слишком большой», а не как сбой GitHub.
- Оценка памяти кэша в коде и документации — честная для любого текста.

**Non-Goals:**

- Лимит строк в воркере: `DIFF_MAX_BYTES` 5 МиБ ≈ 2,5 млн односимвольных строк и тот же
  `parse_diff` — та же проблема, но другой процесс и другой путь; отдельная задача.
- Учёт байтов в `InMemoryCacheStore` и смена числа записей кэша.
- Постраничная выдача или свёртка больших диффов.

## Decisions

### D1. Замер GitHub: compare отвечает `422`, а дифф на миллион строк доходит до нас

Запросы только на чтение к GitHub API, 2026-10-31, `Accept: application/vnd.github.diff`:

| Запрос | Ответ |
|---|---|
| `GET /repos/torvalds/linux/compare/v6.0...v6.10` | `422` `{"message":"The diff is taking too long to generate."}`, `x-github-request-id: A91E:2876BA:AADBC:FDAFC:6AE6312B` |
| `GET /repos/torvalds/linux/compare/v6.9...v6.10` | `200`, `content-length` ≈ 41 МБ |
| `GET /repos/python/cpython/compare/v3.12.0...v3.13.0` | `200`, `content-length` ≈ 40 МБ |

Выводы:

- Предел GitHub на compare — `422`, а не `406`, как у диффа PR. Адаптер переводит `422` на compare
  в `VcsFileTooLargeError`, дальше путь уже есть: ручка — `422 DIFF_TOO_LARGE`, воркер —
  `failed` с `DIFF_TOO_LARGE`.
- `406` на compare не наблюдался. Это непроверено, и в код его не добавляем: догадку о статусе
  в коде не держим.
- Дифф в десятки мегабайт GitHub отдаёт с `200`, значит дифф на миллион коротких строк в пределах
  наших 2 МиБ до нас доходит. Ранний отказ по `content-length` его не ловит: по байтам он в
  лимите.

### D2. Лимит строк — 50 000, проверка до разбора

Замер AndrewKonst на ревью PR #308: 2 МиБ строк по одному символу (≈ 1 млн строк) — пик около
800 МиБ по `tracemalloc`, 33 тыс. строк — около 30 МиБ. Пик растёт с числом строк, а не с
байтами: на каждую строку — объекты `ParsedFile`, `DiffLine`, модели ответа и JSON. 50 000 строк
дают пик ≈ 40 МиБ — с запасом под несколько параллельных запросов в 512 МБ.

`load_run_diff` после `fetch_diff` и **до** `parse_diff` считает переводы строк
(`raw.count("\n")`); больше `RUN_DIFF_MAX_LINES` — `DiffTooLargeError`, запись в кэш не делается.
Подсчёт — один проход по уже прочитанной строке без новых объектов.

Альтернатива — проверять и на попадании кэша, как предлагал AndrewKonst. Не нужна: в кэш пишется
только дифф, прошедший оба лимита, а кэш живёт в памяти процесса и пропадает при рестарте — вместе
со сменой константы при выкате. Дифф больше лимита в кэше оказаться не может.

### D3. `RUN_DIFF_MAX_LINES` — константа, а не настройка

Как TTL кэша (`_CACHE_TTL_SECONDS`, по ревью Grinv): значение определяет память процесса, а не
окружение стенда, и подбирать его на стенде незачем. Константа живёт в модуле use case рядом с
проверкой; смена — правкой кода с тестом границы.

### D4. Кэш остаётся на 24 записях, оценка — честная

`str` в CPython по PEP 393 хранит символ в 1, 2 или 4 байтах — по самому широкому символу строки.
Запись кэша не больше 2 МиБ в UTF-8, отсюда для 24 записей:

- ASCII — ≈ 48 МиБ;
- кириллица (2 байта UTF-8 → 2 байта на символ) — ≈ 96 МиБ;
- один символ вне BMP переводит всю строку на 4 байта на символ — до ≈ 192 МиБ.

Худший случай в 512 МБ помещается, но без большого запаса. Число записей не меняем (решение по
ревью): худший случай требует целого кэша из диффов с символами вне BMP. Комментарий
`shortcut:` в контейнере и документация называют все три числа; если лимит или число записей
поднимут — считать байты в хранилище.

## Risks / Trade-offs

- [Дифф с длинными строками в пределах 50 000 строк и 2 МиБ] → пик ограничен байтовым лимитом,
  как и раньше; 50 000 строк — верхняя граница по числу объектов.
- [Несколько параллельных диффов в лимите] → ≈ 40 МиБ на запрос по замеру, плюс кэш до 192 МиБ в
  худшем случае; запас в 512 МБ есть, но не бесконечный. Числа пика — замер `tracemalloc`, не RSS.
- [Воркер без лимита строк] → тот же `parse_diff` на диффе до 5 МиБ; отдельная задача.
- [GitHub сменит статус отказа] → ответ станет `502 SCM_UNAVAILABLE`, как до этого change; новый
  статус добавляется после наблюдения.

## Migration Plan

Миграций и новых настроек нет. Выкат — обычный деплой, откат — откат коммита: кэш в памяти,
состояния не остаётся.

## Open Questions

- Пик RSS на стенде для диффа в 50 000 строк — уточнить замером; `tracemalloc` не видит
  фрагментации кучи.
