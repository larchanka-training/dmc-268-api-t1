## MODIFIED Requirements

### Requirement: Merge gate по открытым тредам не ниже порога

До публикации находок система SHALL сверить треды бота с GitHub одним запросом с пагинацией на прогон и SHALL выставить check run `dmc-268-ai-review` на `head_sha` с `conclusion=failure`, если остаётся незакрытый тред с замечанием не ниже порога `min_severity` репозитория. Сверка и check run — best-effort: сбой хостинга SHALL логироваться и SHALL NOT переводить прогон в `failed`. Check run SHALL выставляться по базе после публикации ревью; при сбое сверки находки SHALL публиковаться без неё.

#### Scenario: Ручное закрытие треда снимает блокировку

- **WHEN** тред с critical был закрыт на GitHub вручную до merge gate
- **THEN** `thread_resolved` обновляется при сверке и check run получает `success`

#### Scenario: GraphQL недоступен после публикации

- **WHEN** ревью с замечанием `critical` опубликовано, а на следующем прогоне GraphQL GitHub на сверке тредов отвечает 502 и после повторов адаптера
- **THEN** прогон завершается `completed`, находка опубликована, check run выставлен с `failure` по треду из базы, и сообщение не уходит в DLQ

#### Scenario: Check run не выставился

- **WHEN** ревью опубликовано, а создание check run завершилось сбоем хостинга
- **THEN** прогон завершается `completed`, в лог пишется warning с id прогона, второго ревью нет

#### Scenario: Порог ниже critical блокирует high

- **WHEN** у репозитория `min_severity = high`, и после публикации остаётся незакрытый тред с замечанием `high`
- **THEN** check run — `failure`, в заголовке и тексте назван порог `high`

#### Scenario: Замечание ниже порога не блокирует

- **WHEN** у репозитория `min_severity = critical` (по умолчанию), и открыт только тред с замечанием `high`
- **THEN** check run — `success`

#### Scenario: Пересчёт по вебхуку закрытия треда — по текущему порогу

- **WHEN** порог репозитория сменили с `critical` на `medium`, а затем человек закрыл один из тредов, и остаётся открытый тред `medium`
- **THEN** пересчёт по вебхуку `pull_request_review_thread` ставит `failure`

#### Scenario: Смена порога сама не пересчитывает проверку

- **WHEN** `PUT …/settings` меняет `min_severity`, а новых прогонов и закрытий тредов нет
- **THEN** уже стоящий check run не меняется до следующего прогона или вебхука закрытия треда

#### Scenario: Итог изменился, пока шёл POST check run

- **WHEN** пока GitHub принимает check run публикации или пересчёта по треду, меняется порог репозитория, состав незакрытых тредов или пауза ревью
- **THEN** после POST система перечитывает состояние и выставляет check run заново, на head остаётся итог по новому состоянию

#### Scenario: Ответ на check run потерян

- **WHEN** POST check run публикации или пересчёта по треду завершился сбоем, а итог, собранный для повтора, совпадает с прошлым выставленным
- **THEN** check run отправляется снова: при сбое POST мог дойти и перекрыть прошлый итог

### Requirement: Упавший прогон после ревью head блокирует merge gate

Прогон, упавший последним на своём head-коммите, SHALL выставить check run `failure`, если до него на этот head-коммит уже был прогон `completed` или `cancelled` по вебхуку: прежний прогон мог оставить `success` по старому диффу. Без прежнего прогона на head упавший прогон SHALL NOT выставлять check run. На паузе ревью вместо этого действует требование «Прогон при паузе ревью не блокирует merge gate». Сбой GitHub SHALL попадать в лог и SHALL NOT подменять ошибку прогона.

#### Scenario: Ревью после смены ветки упало, поправка не дошла

- **WHEN** на head `success` прежнего прогона по старой ветке, а прогон нового диффа упал
- **THEN** на head выставляется `failure` «Ревью не удалось»

#### Scenario: Первое ревью коммита упало

- **WHEN** ревью не на паузе, прогон упал, а других прогонов на этот head-коммит нет
- **THEN** check run не выставляется, на PR ничего не появляется

#### Scenario: За head отвечает более поздний прогон

- **WHEN** прогон упал, а на этот head-коммит уже создан более поздний прогон
- **THEN** упавший прогон check run не выставляет

### Requirement: Отменённый прогон не выставляет merge gate

Прогон, отменённый (`cancelled`) сменой целевой ветки, SHALL NOT публиковать ни ревью, ни check run, а его сообщение SHALL NOT попадать в DLQ. Check run прогон SHALL собирать по последнему прогону на head: свой итог, если за head отвечает он, иначе итог того, кто отвечает; на паузе ревью — check run паузы. После выставления прогон SHALL перечитать состояние и, если итог изменился, поправить check run. Check run, который GitHub не принял, SHALL повторять до трёх раз.

#### Scenario: Ветку сменили во время публикации

- **WHEN** прогон дошёл до POST ревью, а в базе он уже `cancelled`
- **THEN** ни ревью, ни check run этим прогоном не публикуются, а шаг `publishing` закрывается как брошенный (`REVIEW_RUN_STALE`), а не `completed`

#### Scenario: Ветку сменили во время ревью

- **WHEN** прогон отменили, пока он работал, и его следующий переход отвергнут как переход из терминального состояния
- **THEN** воркер пишет в лог info, закрывает открытый шаг и прочие незакрытые шаги как брошенные (`REVIEW_RUN_STALE`) и подтверждает сообщение, в DLQ оно не уходит

#### Scenario: Ветку сменили между проверкой статуса и check run

- **WHEN** прогон выставил `success`, а приём к этому моменту уже закоммитил отмену и новый прогон
- **THEN** прогон выставляет блокировку смены ветки, а если новый прогон уже `completed`, то его итог

#### Scenario: Ревью нового диффа уже упало

- **WHEN** прогон выставил `success`, а новый прогон после смены ветки уже `failed`
- **THEN** поправка — `failure` «Ревью не удалось», а не «идёт повторное ревью»

#### Scenario: GitHub не принял поправку

- **WHEN** прогон выставил `success`, увидел, что за head отвечает новый прогон, а POST поправки GitHub отверг
- **THEN** поправка отправляется снова, до трёх попыток, и каждый раз собирается по прогону, который отвечает за head в момент попытки

## ADDED Requirements

### Requirement: Прогон при паузе ревью не блокирует merge gate

Если при выставлении check run ревью репозитория на паузе (репозиторий выключен или `auto_review_enabled = false`), система SHALL ставить check run паузы вместо итога прогона, в том числе упавшего.

#### Scenario: Прогон завершился после включения паузы

- **WHEN** прогон начался до паузы, у него есть незакрытый тред не ниже порога, и он завершается, когда у репозитория уже `auto_review_enabled = false`
- **THEN** ревью публикуется, на head ставится check run `success` «Авторевью выключено в настройках»

#### Scenario: Прогон упал после выключения репозитория

- **WHEN** на head уже было ревью, репозиторий выключен `DELETE /api/v1/repositories/{repository_id}`, и начатый до этого прогон падает
- **THEN** на head ставится check run `success` «Ревью выключено в сервисе», а не `failure`

#### Scenario: Первый прогон упал на паузе

- **WHEN** других прогонов на head нет, у репозитория уже `auto_review_enabled = false`, и начатый до этого прогон падает
- **THEN** на head ставится check run `success` «Авторевью выключено в настройках»: обязательная проверка не держит PR
