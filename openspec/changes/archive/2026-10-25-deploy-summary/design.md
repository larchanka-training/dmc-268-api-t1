## Context

Job `deploy` делал полный выкат одной командой `tofu apply -auto-approve`: план строился и применялся сразу. Простой API виден только по строкам `Destroying` и `Creation complete` в логе apply — с часов раннера и без того, что внутри «создания». Проверено на демоне `docker:29-dind` (Docker 29.9.2) и OpenTofu 1.13.2 репетицией выката: старый `infra/` (до #204) с образом v1, затем текущий с v2 — `plan.sh`, `apply.sh`, `summary.sh` с подложным `ssh` в демон.

## Decisions

- **План в файл, а не `plan` и `apply` по отдельности.** Сторож обязан смотреть ровно тот план, который применится. `tofu apply tfplan` с теми же `TF_VAR_*` в окружении (якорь `*tofu-env`) проходит, `-input=false -no-color` сохранены; `replace_triggered_by` и `removed` в JSON плана — `["delete","create"]` с `replace_by_triggers` и `["forget"]` (проверено). Удаление тома — `["delete"]`, замена — `["delete","create"]`: сторож ловит `delete` в любом сочетании.
- **Секреты плана.** В JSON и в файле плана пароли открытым текстом (проверено: значение `postgres_password` есть в `tofu show -json`). JSON только трубой; файл удаляется в `apply.sh` после apply и в `plan.sh`, если план отклонён; артефактом не грузится. Обёртка `setup-opentofu` выключена: она пишет stdout каждого вызова tofu в выходы шага (`wrapper/tofu.js`, `setOutput('stdout', …)`). Исходы шагов в summary — списком, а не `toJSON(steps)`: тот несёт выходы, а env шага печатается в лог. В отчёт из `docker inspect` берутся только `Id`, `Created`, `State`: в полном inspect окружение с паролями.
- **Остановка старого — потоком `docker events`, а не `--since` после apply.** Демон держит 256 последних событий, а каждая проверка здоровья — три события (`exec_create`, `exec_start`, `exec_die`, проверено). Пока воркер дорабатывает сообщение (до 41 мин), остановку API вытеснили бы проверки postgres и rabbitmq. Поток с `--since` на минуту раньше переживает и расхождение часов, и задержку подключения. Начало простоя — `kill` с сигналом 15: uvicorn по SIGTERM первым закрывает слушающий сокет.
- **Новый контейнер — `docker inspect` сразу после apply.** `Created`, `State.StartedAt`, первая запись `State.Health.Log` с `ExitCode == 0` (её `End`). Журнал держит пять записей; после первой успешной проверки они идут раз в 30 с, так что сразу после apply она ещё там. Число неуспешных до неё в полном журнале — нижняя граница. Все отметки — с часов сервера; время в журнале проверок Docker пишет в зоне демона, разбор учитывает смещение.
- **Python, а не jq.** Разбор времени RFC 3339 с наносекундами и зоной, группировка плана и сборка markdown на jq читались бы хуже; GNU `date -d` нет на macOS, где гоняются тесты. Стандартная библиотека, системный `python3` раннера (3.12), как `check_openspec_archived.py`; сбор по SSH — bash.
- **Длительность шагов — засечки, а не API прогона.** `gh api …/actions/runs/{id}/jobs` дал бы точное время всех шагов, но нужен `actions: read` у токена job'а с секретами стенда. Засечка `<id> <время>` первой строкой каждого шага с `run` прав не требует; длительность — до следующей засечки, шаги с `uses` входят в предыдущую. Поэтому вход в ghcr перенесён к остальным `uses` в начале — «Подготовка» одной строкой. `cicd.pipeline.run.duration` (весь прогон: gate, image, deploy) без API не посчитать — в отчёте длительность job'а `dmc268.deploy.duration`.
- **Имена.** Соглашения OpenTelemetry: `cicd.pipeline.name`, `cicd.pipeline.run.id`, `cicd.pipeline.task.name`, `cicd.pipeline.task.type` (`deploy`), `cicd.pipeline.task.run.result` (`success`, `failure`, `cancellation`, `skip`), `error.type` — id шага падения, `vcs.ref.head.revision`, `container.image.name`/`tags`/`repo_digests`, `deployment.environment.name`, `system.filesystem.usage` (`state=free`), `system.filesystem.utilization`, `system.filesystem.mountpoint`. Чего в соглашениях нет — в `dmc268.deploy.*` (`api.downtime` и этапы, `api.health.failed_checks`, `plan.changes` с `plan.action` и `plan.resource.type`, `plan.protected_deletes`, `migrations.*`): соглашения велят своим атрибутам своё пространство имён, не занимая `cicd.*`.
- **Как сменить том при стороже.** Новый ресурс с новым адресом и `removed { lifecycle { destroy = false } }` для прежнего: план — `forget` и `create`, сторож пропускает (проверено), данные старого тома остаются на сервере. Адрес нового тома — в `PROTECTED`, это сверяет тест.

## Risks / Trade-offs

- Засечка ставится в начале шага; время между шагами (подготовка раннером) входит в предыдущий. Порядок секунд не меняет.
- Поток событий через ControlMaster репетирован с подложным `ssh` (`docker exec` в dind): что `kill` mux-клиента закрывает удалённый `docker events`, проверит первый деплой; в худшем случае процесс на сервере доживает до следующего события и падает на записи в закрытый канал.
- `df -Pk` на сервере — GNU; в dind — busybox, вывод тот же по POSIX.
