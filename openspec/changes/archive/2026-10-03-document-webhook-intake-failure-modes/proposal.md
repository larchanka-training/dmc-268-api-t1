## Why

Правки по итогам ревью PR #37 добавили в приём поведение, которого нет в
спеке `webhook-intake`: код опережает спеку. Замечание ревью — «нужен change
или хотя бы сценарии в спеке». Пока требования не зафиксированы, поведение
не защищено от случайной регрессии, а ревьюеры не могут сверять код с
источником правды.

## What Changes

Только спека: поведение уже реализовано и покрыто тестами в PR #37, change
фиксирует его требования задним числом.

- Повторная доставка и проигравшая гонку доставка отвечают HTTP 202 с
  проекцией существующего прогона (сейчас спека требует лишь «не 5xx»);
  гонка первых доставок с разными коммитами — проигравший создаёт новый
  прогон поверх записей победителя.
- Сбой постановки задачи в брокер после коммита переводит прогон в `failed`
  с причиной; вебхук отвечает 5xx, хостинг повторяет доставку, повтор
  создаёт новый прогон.
- Неподдержанный провайдер вебхуков (нет адаптера) получает HTTP 501.
- Публикация в очередь переживает простоявшее соединение: переоткрытие и
  один повтор публикации при отказе, второй отказ уходит вызывающему.

## Capabilities

### Modified Capabilities

- `webhook-intake`: уточнение требования о повторной доставке (202 с
  проекцией, исходы гонок) и требования о постановке задачи (сценарий
  переоткрытия простоявшего соединения).

### New Requirements в `webhook-intake`

- «Сбой постановки задачи переводит прогон в failed».
- «Неподдержанный провайдер получает 501».
- «Публикация переживает простой соединения».

## Impact

**Код** — не меняется: каждое требование уже покрыто тестами
(`test_broker_failure_fails_the_run_and_next_delivery_starts_a_new_one`,
501-тесты неподдержанного провайдера, `test_duplicate_delivery_...`,
liveness-тесты `tests/queue/test_channel_liveness.py`).

**Спеки** — синхронизация дельты в `openspec/specs/webhook-intake/spec.md`
и архивация change'а. Миграций и зависимостей нет.

**Замечание для ребейза #36**: транспортное требование «Публикация
переживает простой соединения» при ребейзе #36 переезжает в их спеку
`job-queue` — рядом с уже имеющимся там «Адаптер очереди переживает
закрытый канал»; приёмное требование о сбое постановки остаётся в
`webhook-intake`.
