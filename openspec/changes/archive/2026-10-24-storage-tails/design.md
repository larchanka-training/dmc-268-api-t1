## Context

`published_comments.provider_comment_id` - `String(255) NOT NULL`. Комментарии ищут по id у провайдера (тред, фидбек, правка), индекса по колонке нет. `list_page` делает `COUNT` и страницу двумя запросами одной сессии; у unit of work уровень изоляции по умолчанию - READ COMMITTED.

## Decisions

### D1. Уникальность - ограничение `(provider_comment_id, kind)`, а не обычный индекс

Дубль id у провайдера означает ошибку записи (повторная публикация или перепутанный ответ), поэтому нужен `UNIQUE`, а не `INDEX`. `provider_comment_id` стоит первым, так что индекс ограничения обслуживает и поиск по id. Колонки `NOT NULL`, значит, вопроса о поведении NULL нет.

`kind` в ключе, потому что id из разных счётчиков GitHub: у сводки - id ревью (`POST /pulls/{n}/reviews`), у `inline` и `thread_reply` - id комментария к строке. Их совпадение - не ошибка; с одним столбцом публикация упала бы после поста на GitHub, и повтор задвоил бы ревью. Провайдера в ключе нет: колонки провайдера у таблицы нет, хостинг один. Если появится второй, ключ придётся расширить.

### D2. Копия `body` - `copy.deepcopy`

`body` - вложенные `dict`/`list` (JSONB). Поверхностная копия оставила бы общими вложенные структуры, поэтому `deepcopy`. Альтернатива «сериализовать и разобрать JSON» дороже и меняет типы.

### D3. Согласованный список - REPEATABLE READ, а не `count(*) over ()`

Оконный `count(*) over ()` дал бы один запрос, но при `offset` за концом выборки страница пуста, и `total` потерялся бы (ответ API показал бы `total=0` при непустом списке). Поэтому два запроса в снимке: `Session.connection(execution_options={"isolation_level": "REPEATABLE READ"})` первым действием в `list_page`. Это уровень транзакции, он действует до её конца и сбрасывается при возврате соединения в пул; общий unit of work не меняется. Если транзакция сессии уже началась, SQLAlchemy откажет с `InvalidRequestError` - такой вызов шумно ломается, а не молча читает без снимка. Поведение проверено на живом PostgreSQL: тест коммитит прогон между `COUNT` и страницей.

## Risks / Trade-offs

- Накат на базу с дублями `(provider_comment_id, kind)` падает - осознанно, разбор данных вручную.
- `list_page` нельзя вызывать после других запросов в той же транзакции; единственный вызов - начало `with uow` в роуте.
