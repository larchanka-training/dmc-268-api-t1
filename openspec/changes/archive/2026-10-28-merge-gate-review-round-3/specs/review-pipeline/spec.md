## ADDED Requirements

### Requirement: Упавший прогон после ревью head блокирует merge gate

Прогон, упавший последним на своём head-коммите, SHALL выставить check run `failure`, если до него на этот head-коммит уже был прогон `completed` или `cancelled` по вебхуку: прежний прогон мог оставить `success` по старому диффу. Без прежнего прогона на head упавший прогон SHALL NOT выставлять check run. Сбой GitHub SHALL попадать в лог и SHALL NOT подменять ошибку прогона.

#### Scenario: Ревью после смены ветки упало, поправка не дошла

- **WHEN** на head `success` прежнего прогона по старой ветке, а прогон нового диффа упал
- **THEN** на head выставляется `failure` «Ревью не удалось»

#### Scenario: Первое ревью коммита упало

- **WHEN** прогон упал, а других прогонов на этот head-коммит нет
- **THEN** check run не выставляется, на PR ничего не появляется

#### Scenario: За head отвечает более поздний прогон

- **WHEN** прогон упал, а на этот head-коммит уже создан более поздний прогон
- **THEN** упавший прогон check run не выставляет

## MODIFIED Requirements

### Requirement: Ревью упавшего прогона не дублируется следующим

Перед публикацией находок прогон SHALL искать на GitHub ревью своего бота с маркером каждого прогона своего PR, упавшего на `publishing` без записей в `published_comments` позже последней записи PR, и SHALL записывать найденное этому прогону, сопоставляя inline по файлу, стороне, строке и тексту. Поиск SHALL быть best-effort: сбой хостинга и параллельный подбор SHALL NOT останавливать публикацию.

#### Scenario: Воркер умер после записи ревью на GitHub

- **WHEN** GitHub записал ревью прогона, воркер умер до записи `published_comments`, повторная доставка перевела прогон в `failed`, и новый прогон того же PR снова нашёл замечание к той же строке
- **THEN** новый прогон записывает ревью упавшего в `published_comments`, своего inline-комментария к этой строке не публикует, а находку связывает с находкой треда

#### Scenario: Упавший прогон ничего не опубликовал

- **WHEN** прогон упал на `publishing`, а ревью с его маркером на GitHub нет
- **THEN** записей для него не появляется, новый прогон публикует замечание как обычно

#### Scenario: Поиск ревью упавшего прогона не удался

- **WHEN** GitHub отвечает ошибкой на поиск ревью упавшего прогона
- **THEN** сбой попадает в лог, новый прогон публикует ревью и завершается `completed`

#### Scenario: Две находки упавшего прогона на одной строке

- **WHEN** у упавшего прогона две находки на одной строке, а опубликована была одна (другую покрыл тред)
- **THEN** id комментария записывается находке с тем же текстом

#### Scenario: Упавший прогон старше опубликованного

- **WHEN** после падения прогона другой прогон PR опубликовал ревью
- **THEN** следующие прогоны ревью упавшего на GitHub не ищут

#### Scenario: Выметатель перевёл прогон в failed после чужой публикации

- **WHEN** прогон записал ревью на GitHub и умер на `publishing`, следующий прогон PR опубликовал своё, не видя его упавшим, и только потом выметатель перевёл первый в `failed`
- **THEN** следующий прогон находит ревью первого и записывает его, а не публикует замечание второй раз

#### Scenario: Два прогона подбирают одно ревью

- **WHEN** два прогона PR одновременно нашли ревью одного упавшего прогона, и второй получил отказ уникального индекса
- **THEN** второй откатывает подбор и публикует своё ревью

### Requirement: Отменённый прогон не выставляет merge gate

Прогон перед выставлением check run SHALL перечитать свой статус; если его отменили (`cancelled`) сменой целевой ветки во время работы, check run SHALL NOT выставляться. После выставления check run прогон SHALL перечитать последний прогон на head и поправить check run, если отвечает за head уже не он. Поправку SHALL повторять до трёх раз, если GitHub её не принял.

#### Scenario: Ветку сменили во время публикации

- **WHEN** прогон опубликовал ревью, а в базе он уже `cancelled`
- **THEN** check run этим прогоном не выставляется

#### Scenario: Ветку сменили между проверкой статуса и check run

- **WHEN** прогон выставил `success`, а приём к этому моменту уже закоммитил отмену и новый прогон
- **THEN** прогон выставляет блокировку смены ветки, а если новый прогон уже `completed`, то его итог

#### Scenario: GitHub не принял поправку

- **WHEN** прогон выставил `success`, увидел, что за head отвечает новый прогон, а POST поправки GitHub отверг
- **THEN** поправка отправляется снова, до трёх попыток

### Requirement: Пересчёт merge gate только по завершённому ревью head

Пересчёт merge gate по вебхуку закрытия треда SHALL выставлять check run, только если последний прогон на head-коммите PR - `completed`. Если прогона на head нет, или последний идёт, упал или отменён, check run по тредам SHALL NOT выставляться: `success` непроверенному коммиту не даётся, gate выставит прогон, который его проверит. Если после этого последний прогон на head сменился, пересчёт SHALL поправить check run, как прогон.

#### Scenario: Тред закрыт, пока ревью нового head идёт

- **WHEN** после push ревью нового head-коммита ещё идёт, и приходит вебхук закрытия треда
- **THEN** check run на новый head не выставляется

#### Scenario: Ревью после смены целевой ветки упало

- **WHEN** последний прогон на head - `failed` (ревью нового диффа), а прежний `completed` был на старой базе, и закрыт тред
- **THEN** check run не выставляется: блокировка смены ветки остаётся

#### Scenario: Ветку сменили во время пересчёта

- **WHEN** пересчёт выставил check run по `completed` прогону, а приём к этому моменту закоммитил смену ветки и новый прогон
- **THEN** пересчёт выставляет блокировку смены ветки, а если новый прогон уже `completed`, то его итог
