## Context

Продолжение `retarget-gate-race`: gate на head выставляют приём, воркер и пересчёт по треду, общей блокировки у них нет. Ревью #225 на `a39affa` нашло пути, где итогом всё же остаётся `success` старого прогона.

## Decisions

### D1. Граница подбора — время падения

Прогон, умерший на `publishing`, становится `failed` позже, чем создаётся следующий прогон. Сравнивается `last_progress_at` упавшего прогона (его ставит переход в `failed`) с `max(published_at)` записей PR. Прогон, упавший до последней публикации, тот её прогон уже проверял. Убрать границу совсем — значит листать ревью PR ради каждой «сироты» на каждом прогоне.

### D2. Повтор поправки и `failure` упавшего прогона

Адаптер GitHub сам повторяет 5xx и лимит, но обрыв сети POST не повторяет, а после исчерпания попыток поправка терялась. `settle_merge_gate` повторяет её до трёх раз и перед каждой попыткой заново читает последний прогон: за время сбоя за head мог начать отвечать другой прогон, и повтор старого check вернул бы чужой итог. После успешного POST — та же проверка, что у всех, кто выставляет gate. Выставленный check помнится парой «прогон, статус»: если блокировка по идущему прогону дошла уже после его завершения, следующий проход видит `completed` и возвращает его итог. Если не дошла и она, head закрывает новый прогон: своим gate или, если упал, `failure`. Упавший прогон выставляет `failure` только когда до него на этот head было ревью (`find_reviewed`): без прежнего check run на head нет, обязательная проверка и так держит мердж, и поведение «упавшее ревью ничего не оставляет на PR» (E2E-05) сохраняется.

### D3. Запоздавшее `edited` — не здесь

Ревью предлагало не ретаргетить по событию, у которого ветка в payload'е не совпадает со свежими метаданными. Это не закрывает исходный сценарий: у запоздавшего D1 ветка в payload'е и в метаданных, полученных до второй смены, одна. Зато открывает путь fail-open: если свежее событие потеряется, смена ветки останется без ревью и с `success` по старому диффу. Гонку закрыла бы только сериализация приёма по PR (блокировка строки PR на время запроса к GitHub или повторное чтение метаданных после коммита) — отдельная задача.

### D4. Время прогона — с часов API, а не базы

Ревью предлагало `created_at` из `now()` базы против рассинхрона часов реплик API. API на стенде одна, все контейнеры на одном хосте, а время прогона намеренно выдаёт `now` use case'а (оно же в проекции `ReviewJob`). Не меняем, пока API одна.
