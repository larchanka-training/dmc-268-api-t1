## Context

Продолжение `retarget-gate-race`: gate на head выставляют приём, воркер и пересчёт по треду, общей блокировки у них нет. Ревью #225 на `a39affa` нашло пути, где итогом всё же остаётся `success` старого прогона.

## Decisions

### D1. Граница подбора — время падения

Прогон, умерший на `publishing`, становится `failed` позже, чем создаётся следующий прогон. Сравнивается `last_progress_at` упавшего прогона (его ставит переход в `failed`) с `max(published_at)` записей PR. Прогон, упавший до последней публикации, тот её прогон уже проверял. Убрать границу совсем — значит листать ревью PR ради каждой «сироты» на каждом прогоне.

### D2. Повтор поправки и `failure` упавшего прогона

Адаптер GitHub сам повторяет 5xx и лимит, но обрыв сети POST не повторяет, а после исчерпания попыток поправка терялась. `settle_merge_gate` повторяет её до трёх раз. Если не дошла и она, head закрывает новый прогон: своим gate или, если упал, `failure`. Упавший прогон выставляет `failure` только когда до него на этот head было ревью (`find_reviewed`): без прежнего check run на head нет, обязательная проверка и так держит мердж, и поведение «упавшее ревью ничего не оставляет на PR» (E2E-05) сохраняется.

### D3. Запоздавшее `edited`

Событие, у которого ветка в payload'е не совпадает с веткой в свежих метаданных, устарело: ветку с тех пор сменили снова, свежее событие придёт или уже пришло. Остаётся окно, когда метаданные получены до второй смены, а транзакция — после обработки второго события; его закрыла бы только блокировка строки PR на время запроса к GitHub. Записано в рисках PR.

### D4. Время прогона — с часов API, а не базы

Ревью предлагало `created_at` из `now()` базы против рассинхрона часов реплик API. API на стенде одна, все контейнеры на одном хосте, а время прогона намеренно выдаёт `now` use case'а (оно же в проекции `ReviewJob`). Не меняем, пока API одна.
