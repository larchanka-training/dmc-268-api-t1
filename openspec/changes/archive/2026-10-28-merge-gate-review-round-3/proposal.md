## Why

Третий круг ревью #225 нашёл в исправлении merge gate при смене целевой ветки (#222) ещё два пути, которыми на head остаётся `success` по старому диффу:

- Подбор ревью упавшего прогона смотрел только прогоны, *созданные* позже последнего прогона с записями. Прогон, который записал ревью на GitHub и умер на `publishing`, выметатель переводит в `failed` позже: следующий прогон его не видел, а после — граница его отсекала, и ревью дублировалось.
- Поправку gate после смены ветки (`settle_merge_gate`) отправляет только тот, кто увидел смену, и один раз. Сбой POST оставлял на head `success`, а если ревью нового диффа падало — навсегда.
- Сценарий пересчёта по треду запрещал выставлять check run, хотя пересчёт после своего POST выставляет поправку.

## What Changes

- Граница подбора — время падения прогона (`last_progress_at` перехода в `failed`) против последнего `published_at` PR.
- `settle_merge_gate` повторяет поправку до трёх раз, каждый раз перечитывая последний прогон и собирая check заново.
- Упавший прогон, последний на head, выставляет `failure`, если до него на этот head было ревью. Первое упавшее ревью коммита по-прежнему ничего на PR не оставляет.
- Пересчёт по треду: поправка после собственного POST описана в требовании.

## Capabilities

### Modified Capabilities

- `review-pipeline`: ADDED «Упавший прогон после ревью head блокирует merge gate», MODIFIED «Ревью упавшего прогона не дублируется следующим», «Отменённый прогон не выставляет merge gate», «Пересчёт merge gate только по завершённому ревью head».

## Impact

- Код: `list_unpublished_failures` (SQL и фейк), `merge_gate_publish.py` (`settle_merge_gate`, `build_failed_review_check`), `review_pipeline.py` (`_block_head_of_failed_run`).
- Схема базы, контракт API и настройки не меняются.
