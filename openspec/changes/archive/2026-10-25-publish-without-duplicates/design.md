## Context

`publish_review` создаёт одно ревью (`POST /repos/{o}/{r}/pulls/{n}/reviews`), читает id inline-комментариев (`GET …/reviews/{id}/comments`), отвечает в треды (`POST …/comments/{id}/replies`) и выставляет check run. Адаптер `GitHubVcsGateway` повторял любой запрос на 429/5xx паузой 0,5 и 1 с (`_get` и `_request_json` — два одинаковых цикла), обрыв сети не повторял. Сбой публикации переводит прогон в `failed`; сообщение уходит в DLQ, а повтор вебхука после `failed` создаёт новый прогон (`webhook-intake`) — с новым id и новым ревью. Один и тот же прогон второй раз до публикации не доходит: переход `publishing → building_context` запрещён (`app/domain/lifecycle.py`).

## Goals / Non-Goals

**Goals:** в PR не появляется второе ревью из-за повтора; `critical`, опубликованный на GitHub, не проходит мимо merge gate; лимиты GitHub пережидаются так, как велит документация, и не дольше бюджета.

**Non-Goals:** поиск по маркеру ответа в тред; переотправка check run, который не выставился; новые таблицы и колонки.

## Сверено с GitHub

- Тело ревью в `GET /repos/{o}/{r}/pulls/{n}/reviews` — raw markdown, HTML-комментарии сохраняются: на живых публичных PR ревью `coderabbitai[bot]` (`type: Bot`) начинается с `<!-- coderabbit-ai-generated:v1 -->` (проверено `gh api`, только чтение). Список — в хронологическом порядке, `per_page` до 100 («REST API endpoints for pull request reviews»).
- `performed_via_github_app` у ревью нет (на живых PR — `null` и у ревью Copilot), поэтому своё ревью узнаётся по `user.login` и `user.type`. Логин бота App — `<slug>[bot]` (пример `copilot-pull-request-reviewer[bot]`); `slug` отдаёт `GET /app`, и только с JWT приложения («REST API endpoints for GitHub Apps»).
- «Rate limits for the REST API»: и первичный, и вторичный лимит — `403` или `429`. Есть `retry-after` — ждать столько секунд; `x-ratelimit-remaining: 0` — до `x-ratelimit-reset` (эпоха UTC); иначе не меньше минуты, при повторных отказах — экспоненциально дольше. Выполнен ли запрос, получивший отказ лимита, документация не говорит.
- «Rate limits and query limits for the GraphQL API»: первичный лимит — HTTP `200` с ошибкой, вторичный — `200` или `403` с сообщением о лимите; заголовки и паузы — как у REST. Тип `RATE_LIMITED` в `errors[].type` на этой странице не описан, поэтому признак лимита при 200 — этот тип или «rate limit» в `message`.
- Создание ревью «may result in secondary rate limiting» и шлёт уведомления: повтор — это и второе ревью, и второе уведомление.

## Decisions

1. **Маркер прогона и поиск вместо повтора.** Адаптер дописывает к телу сводки `<!-- dmc-268-review-run:<id прогона> -->` (без слов — переводить нечего) и шлёт `POST …/reviews` с `repeatable=False` и проверкой `already_done`. На обрыв, таймаут, 5xx и отказ лимита тот же цикл `_request`, что у повторяемых запросов, делает паузу (лимит — по заголовкам в пределах бюджета, иначе backoff), затем зовёт `already_done` — поиск маркера у ревью с `user.login == <slug>[bot]` и `user.type == "Bot"`. Нашлось — проверка возвращает `{"id": …}` как ответ `POST`, и id с комментариями берутся как у созданного; нет — следующий `POST`. Попытки или бюджет кончились — последняя проверка и `VcsUnavailableError`. Ответ в тред идёт без `already_done`: на первом сбое — `VcsUnconfirmedError`, прогон `failed`. Повтор безопасен, пока поиск перед ним надёжен: второе ревью возможно только если GitHub допишет первое уже после поиска, а пауза перед поиском это окно сужает. Поиска до публикации нет: тот же прогон второй раз до `POST` не доходит (lifecycle), а новый прогон на тот же коммит — новый id и новый анализ, его ревью — не дубль, а следующий результат. Почему не только `type: Bot` — маркер видят все, кто читает PR, и другой App мог бы повторить тело; проверка логина стоит один `GET /app` на процесс и только на пути сбоя.
2. **Отказ лимита: ревью — повтор после поиска, ответ в тред — без повтора.** Не повторять `POST …/reviews` на лимите нельзя: вебхук уже принят, #149 его не переотправит, и PR остался бы без ревью и check run. Поиск перед повтором делает повтор безопасным независимо от того, выполнен ли отклонённый запрос. У ответа в тред поиска нет, поэтому повтор допустим, только если документация гарантирует, что запрос с отказом лимита не выполнен. «Rate limits for the REST API» пишет лишь: «If you exceed a secondary rate limit, you will receive a `403` or `429` response and an error message that indicates that you exceeded a secondary rate limit» и «You should not retry your request until after the time specified by the `x-ratelimit-reset` header» — про то, отклонён ли запрос, ни слова. Ответ в тред не повторяется и на лимите: сбой — warning, как в #184.
3. **id сводки не теряется.** Сводка — это само ревью (`summary_provider_comment_id` = id ревью), он известен сразу после `POST` или поиска. Упал `GET …/comments` (после своих повторов) — адаптер пишет warning и возвращает inline `None`; `publish_review` одной транзакцией записывает сводку и сопоставленные inline, как раньше, и прогон доходит до `completed` и check run.
4. **Как merge gate узнаёт о `critical` без id.** Чистая `untracked_findings(findings, comments)`: у прогона есть сводка, а у его находки нет ни inline-записи, ни `covered_by_finding_id` — находка для gate открыта. `collect_open_findings` добавляет такие находки прогона на текущем head: в `publish_review` — текущего прогона, в пересчёте по вебхуку закрытия треда — `find_reviewed(merge_request, head_sha)`. Без этого закрытие соседнего треда выставило бы `success` при `critical` в PR. Снимает блокировку следующий прогон на новом коммите: его модель увидит проблему снова и опубликует новый inline, который уже будет в базе. Новых колонок не нужно: факт «опубликовано, а id нет» выводится из существующих записей.
5. **Сбой check run после публикации — best-effort.** `set_merge_gate_check` в `try/except VcsError`, warning с id прогона, прогон `completed`. Повтор сообщения того же прогона невозможен (lifecycle), а `failed` открывает путь новому прогону и второму ревью. Сам `POST /check-runs` по-прежнему повторяется на 5xx и лимит: сервис и так создаёт новый check run на каждый пересчёт gate (публикация, вебхук закрытия треда), и лишний с тем же исходом безвреден. Документация («REST API endpoints for check runs») говорит только о пределе в 1000 check run с одним именем в наборе; что статус PR берёт последний, она не утверждает — допущение унаследовано от текущей схемы, а не введено здесь. Без check run обязательная проверка не даёт мерджа, пока следующий прогон или вебхук закрытия треда её не выставит, — отказ в безопасную сторону.
6. **Пересчёт gate по вебхуку закрытия треда остаётся без best-effort.** Сбой сверки или check run там — ответ 5xx, доставку переотправит воркер (#149) с паузой от пяти минут; это и есть повтор, и он идемпотентен (`apply_review_thread_webhook` сравнивает состояние). Best-effort здесь выставил бы gate по базе и потерял бы повтор. Отказ лимита в API не пережидается (бюджет 0): ответ вебхуку должен уйти за 10 секунд.
7. **Один цикл повторов.** `_request(method, url, …, repeatable, graphql, already_done)` заменяет `_get` и `_request_json`: 401 — один раз новый токен; лимит — пауза по заголовкам; 5xx — backoff 0,5 и 1 с; прочее — сразу ошибка (404 на GET — `VcsNotFoundError`). Пауза лимита суммируется на запрос; превышение бюджета — `VcsUnavailableError` сразу, без сна. Признак лимита — одна `is_rate_limited` в `github_installations.py` (429, 403 лимита, у GraphQL — ошибка лимита при 200); её же зовут каталог установок и доставки вебхука. Часы (`clock`) и сон (`sleep`) — аргументы конструктора, тесты не ждут.
8. **Таймауты и бюджет — у процесса.** `VcsClientLimits` в composition root: API — `Timeout(5)` (прежнее умолчание httpx) и бюджет 0, воркер — `Timeout(30, connect=5)` и 60 с. 60 с — пауза GitHub без заголовков; второй отказ подряд (120 с) уже сверх бюджета. Публикация — единицы запросов; при 60 с ожидания на запрос и 30 с таймауте этап укладывается в `STALE_RUN_TIMEOUT_SECONDS` (30 минут по умолчанию) с большим запасом. Сброс первичного часового лимита (до часа) воркер не ждёт — прогон `failed` сразу. Проход повтора доставок (#149) в воркере берёт свой шлюз с лимитами API (`Container.redelivery_vcs_gateway`): отказ лимита завершает проход (`webhook-intake`), и минута ожидания общего шлюза держала бы consume-цикл дольше бюджета прохода (30 с).

## Risks / Trade-offs

- **GitHub допишет ревью позже поиска.** После 502 бэкенд GitHub может дописать ревью уже после нашего `GET …/reviews`; тогда следующий `POST` даст второе ревью. Окно — пауза перед поиском (0,5–1 с backoff, на лимите — по заголовкам); прежде адаптер повторял `POST` вслепую.
- **Повторный ответ в тред.** Ответ ушёл, а клиент получил 502 или таймаут: ответа в базе нет, и следующий прогон ответит в тот же тред ещё раз. Поиск по маркеру для ответов — `GET …/pulls/{n}/comments` по всем комментариям PR и маркер в каждом ответе; отложено, пока дубль ответа не замечен на практике.
- **Ответ ушёл, запись в базу упала из-за базы.** Запись ответа — сразу после `POST` своей транзакцией (#184); если упала сама база, следующий прогон ответит повторно. Чинится только поиском ответа на GitHub (см. выше) — не дёшево, остаётся.
- **Блокировка по находке без id снимается только новым коммитом.** Человек закрыл тред на GitHub — вебхук приходит с id комментария, которого нет в базе, и игнорируется; gate остаётся `failure` до следующего прогона. Сознательно: ложная блокировка лучше пропущенного `critical`.
- **Нет check run после сбоя.** Если проверка не обязательна в защите ветки, PR до следующего события выглядит без статуса ревью.
