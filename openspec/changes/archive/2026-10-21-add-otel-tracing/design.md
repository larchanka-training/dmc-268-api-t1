## Context

`TraceIdMiddleware` был рассчитан на то, что `trace_id` станет trace id спана OTel без смены формата. FastAPI 0.146 сам открывает серверный спан на запрос, если глобальный провайдер трейсов настроен, — снаружи всех middleware, включая `ServerErrorMiddleware`. Воркер потребляет `review_jobs` генератором `channel.consume()` на `BlockingConnection`; шаги прогона пишет `StepRecorder` (change `add-review-run-steps`).

## Decisions

### D1. HTTP-сервер — встроенная телеметрия FastAPI, а не `opentelemetry-instrumentation-fastapi`

FastAPI с 0.143 трассирует запросы сам и уступает место contrib-пакету, только если тот подключён. Два источника серверных спанов не нужны. Автонастройку экспортёров FastAPI (`FASTAPI_OTEL_AUTO_CONFIGURE`) не включаем: провайдер ставит `configure_tracing`.

### D2. Контекст через очередь — вручную, в адаптере очереди

`opentelemetry-instrumentation-pika` для генератора `consume()` закрывает спан приёма сразу при выдаче сообщения, а его контекст держит текущим до следующего сообщения — то есть и на простое цикла, и на проходе выметателя. Работа воркера ложилась бы в трейс сообщения случайно, а не по построению. Поэтому `inject`/`extract` — в `app/infrastructure/queue/rabbitmq.py`: `_publish` открывает спан `PRODUCER` и кладёт `traceparent` в `BasicProperties.headers`, `consuming_span` воркера открывает спан `CONSUMER` от извлечённого контекста на время обработчика. Пропагатор W3C — явный экземпляр, а не глобальный (D3).

### D3. Глобальный пропагатор пуст

FastAPI берёт родителя запроса из глобального пропагатора, httpx — кладёт через него контекст в исходящие запросы. Пустой пропагатор (свой класс: `extract` отдаёт пустой контекст, `inject` ничего не делает) даёт сразу оба правила: входящий `traceparent` HTTP-клиента не продолжает трейс, а trace id не уходит GitHub и провайдерам модели. Ставится всегда, поверх `OTEL_PROPAGATORS`: доверие к входящим заголовкам — правило сервиса, а не настройка окружения.

### D4. Спаны этапов — через порт `StageTracer`, в точках `StepRecorder`

Слой приложения не знает вендоров (`lint-imports`, `opentelemetry` добавлен в запрещённые). `StepRecorder` получает `StageTracer` (по умолчанию — без трассировки) и открывает спан в `_open` до записи шага, а закрывает при закрытии этапа до записи исхода — так повтор этапа сам становится отдельным спаном, а сбой записи шага (журнал вторичен, #90) не влияет на спан: этап виден в трейсе, даже если его шаг не записался. Пайплайн только передаёт трассировщик из воркера (`run_review(..., stage_tracer=...)`); тела этапов не тронуты. Адаптер `OtelStageTracer` делает спан этапа текущим, чтобы запросы httpx и SQLAlchemy этапа были его детьми; шаги идут строго по одному, порядок снятия контекста не нарушается.

Альтернатива — `opentelemetry-api` как исключение для слоя приложения: правок меньше на одну-две строки, но граница слоя держалась бы на исключении в контракте, а тест шага пришлось бы писать через SDK.

### D5. SQLAlchemy — `EngineTracer` на движок контейнера

`SQLAlchemyInstrumentor` 0.66b0 и 0.66b1 объявляет `sqlalchemy < 2.1` и на 2.1.1 ничего не делает, а с пропуском проверки подменяет `create_async_engine`, которому нужен `greenlet`. `EngineTracer` того же пакета вешает обычные события движка на один движок; что они работают на 2.1, проверяет сквозной тест трейса.

### D6. Провайдер есть всегда, экспорта нет

SDK-провайдер ставится и без экспорта: без него у спана нет trace id, а `X-Trace-ID` — trace id спана. Процессор добавляется, только если `OTEL_TRACES_EXPORTER=console`; другие значения пишут одно предупреждение при старте и не экспортируют. Если провайдер выключен (`OTEL_SDK_DISABLED=true`), `X-Trace-ID` по-прежнему выдаёт `secrets.token_hex(16)`.

## Risks

- `EngineTracer` — класс пакета, а не его публичная точка входа; при обновлении пакета сигнатура может поменяться. Ловит сквозной тест трейса.
- Спан этапа, открытый на прогоне, который убил сбой процесса, не закроется — как и шаг; трейс останется без этого спана.
