## Context

Мотивация - `proposal.md`, поведение - дельта `specs/context-assembly/spec.md`. Что есть сейчас:

- `build_review_context` (`app/application/use_cases/build_review_context.py`) скачивает текст
  изменённого файла на `head_sha` через `VcsGateway.fetch_file` только для языков с AST и сразу
  отдаёт его парсеру.
- `assemble_context` (`app/application/context_assembly.py`) кладёт в пакет каждый hunk как
  элемент `{"path", "hunk": fence("diff", …)}` в порядке: контекст PR, резерв правил, hunk'и,
  правила, AST. Hunk несёт три строки контекста от GitHub.
- `validate_anchor` (`app/domain/diff.py`) принимает якорь находки, только если строка входит в
  `changed_new_lines`/`changed_old_lines` исходного hunk'а: контекстные строки якорем не бывают.
- Открытый PR #239 (incremental review) считает дайджест журнала по исходному `Hunk`, поэтому
  `Hunk` и список показанных hunk'ов не меняются.

## Goals / Non-Goals

**Goals:**

- Модель видит до 30 строк вокруг каждого изменения, а небольшой файл - целиком, в пределах
  `context_max_tokens`.
- Улучшения не вытесняют изменения: hunk'и всех файлов входят в пакет раньше любого окна.

**Non-Goals:**

- Окна по границам функций (по AST) вместо фиксированных строк.
- Кэш файлов между прогонами.
- Настройки радиуса и порога целого файла.

## Decisions

### D1. Один формат: расширенный hunk вместо отдельного блока

Окно и файл целиком - это тот же unified diff с большим контекстом, как `git diff -U30` и
`git diff -U<весь файл>`. Элемент пакета остаётся `{"path", "hunk": fence("diff", …)}`, рендер
промпта не меняется, модель читает привычный формат, а изменённые строки остаются на месте с
`+`/`-`. Отдельный блок «окружение» дублировал бы строки hunk'а и требовал бы от модели
сопоставлять два текста.

Чистая функция `expand_hunks` (`app/domain/hunk_context.py`) по hunk'ам файла, тексту на
`head_sha` и радиусу добавляет к hunk'у контекстные строки из текста файла с обеих сторон,
склеивает hunk'и, чьи окна пересекаются или смыкаются (между ними не больше двух радиусов строк,
как у git), пересчитывает заголовок `@@ -a,b +c,d @@` и сохраняет строки
`\ No newline at end of file`. Заголовок без подписи функции: git берёт её из строки над началом
hunk'а, а начало сдвинулось.

Если хоть одна контекстная или добавленная строка hunk'а не совпала со строкой файла (файл
изменился после диффа) или hunk выходит за конец файла, функция возвращает `None`: лучше три
строки контекста, чем окно из другого файла. Виды, равные исходным hunk'ам, - не несовпадение:
так бывает у нового файла, hunk которого уже покрывает файл целиком. Для уровня `whole_file` это
успех (бюджет не меняется, AST не нужен), а флаг `surrounding` ставится, только если вид отличается
от исходного.

### D2. Бюджет в два прохода

Первый проход прежний: все hunk'и с тремя строками контекста. Второй идёт по остатку, по
файлам в порядке диффа, тремя ступенями: файлы до порога - целиком, затем AST остальных (как
раньше), затем окна ±30 строк для остальных. Улучшение файла - замена его элементов `diff` на
расширенные, только если разница стоимостей целиком помещается в остаток; иначе файл остаётся
как есть, без записи в `omitted` (ничего не потеряно). Файл, у которого вошли не все hunk'и, не
улучшается: окно не должно стоять там, где модель не видит самого изменения.

Если бы окна входили вместе с hunk'ами за один проход, контекст первых файлов съедал бы бюджет
изменений последних. Файл целиком идёт раньше AST, потому что он дешёвый (порог 8 КБ) и
содержит всё, что дал бы AST: для такого файла AST в пакет не кладётся. Окна - последними: они
дороже AST и при нехватке бюджета AST полезнее.

### D3. Константы, а не настройки

Радиус 30 строк (`SURROUNDING_LINES`) и порог целого файла 8 КБ (`WHOLE_FILE_MAX_BYTES`) -
константы `app/domain/hunk_context.py`. Значения из §5 `docs/SYSTEM_DESIGN.md`, от стенда они не
зависят, а общий размер всё равно держит `context_max_tokens`.

### D4. Довыборка для всех текстовых файлов, лимиты прежние

Окна нужны и файлам без AST (Markdown, YAML, SQL), поэтому текст на `head_sha` скачивается для
каждого изменённого текстового файла с hunk'ами, один раз: из того же текста строится AST.
Лимиты `ast_max_files` и `ast_max_file_bytes` действуют на эту общую довыборку. Причина пропуска
(`file_limit`, `too_large`, `unavailable`, `missing`) попадает в `omitted` как раньше и только
для файлов с AST-языком: у остальных AST не было, а окно - необязательное улучшение.

### D5. Окна фиксированные, а не по функциям

Окно по охватывающей функции точнее, но нужен AST, которого у части языков нет, а у длинной
функции окно стало бы неограниченным. Фиксированный радиус работает для любого текста и
предсказуем по стоимости; охватывающие определения модель и так получает в AST.

### D6. Секреты в неизменённых строках вида заменяются меткой

Три строки контекста от GitHub модель видела и раньше, а окно и файл целиком приносят строки,
которых PR не касался: конфиг с токеном или ключ рядом с правкой ушли бы внешней модели, хотя
ревью о них ничего сказать не должно. Поэтому `expand_hunks` прогоняет через `redact_secrets`
контекстные строки вида (с пробелом в начале), а строки `+`/`-` и заголовок не трогает: секрет,
который PR добавил или удалил, модель должна увидеть и назвать. Строки редактируются блоками
подряд идущих контекстных строк (с префиксом-пробелом), чтобы многострочный ключ PEM узнавался
целиком. Число и порядок строк сохраняет сама `redact_secrets`: совпадение на несколько строк
(ключ, хвост ключа без BEGIN, `authorization` и значение через перевод строки) заменяется меткой
на каждой своей строке, а не одной меткой, и префикс строки диффа (`+`, `-`, пробел) остаётся.
Иначе строки между ключом и изменением съезжали бы, номера строк для модели были бы неверны, а
заголовок `@@` - ложным. Это меняет и редакцию сохраняемого пакета: многострочный секрет там тоже
теперь метки построчно; требование `review-data-model` («заменяться меткой») это не меняет.
Бюджет считается по виду после редакции. Исходные hunk'и без расширения не меняются, как раньше.

`redact_secrets` ловит только формы с узнаваемым префиксом, именем или рамкой, а
`DB_PASSWORD=hunter2` и голый токен проходят. Поэтому файлы, которые по имени похожи на
хранилище секретов (`.env*`, `*.pem`, `*.key`, `credentials*` или `secret` в пути, регистр не
важен), второй проход не расширяет вовсе (`may_hold_secrets`): они идут hunk'ами, как до этого
change. Код с языком AST (`secret_redaction.py`) расширяется: его ревью окно нужнее.

## Risks / Trade-offs

- Больше запросов к GitHub: файлы без AST-языка теперь тоже скачиваются, в пределах
  `ast_max_files`.
- Пакет при свободном бюджете растёт, а с ним стоимость вызова модели. Верхнюю границу держит
  `context_max_tokens`.
- Замечание по контекстной строке `validate_anchor` отсеивает, как и раньше: системный промпт
  напоминает, что замечания ставятся к изменённым строкам.
- Обычные конфиги (`*.yaml`, `*.toml`, `docker-compose.yml`) расширяются: секрет в них без
  узнаваемого префикса уйдёт модели в окне или в файле целиком.
