## Context

`tasks/plan.md` — источник решений этого change; его Open Questions закрыты
владельцем продукта 2026-09-29 и здесь зафиксированы как состоявшиеся.
Что сформировало подход:

- Слои, модель персистентности и composition root уже построены
  (`backend-architecture`); хранимая модель и инварианты зафиксированы
  (`review-data-model`): таблицы `repositories`, `merge_requests`,
  `review_runs` существуют, частичный уникальный индекс «один нетерминальный
  прогон на коммит» уже в схеме (миграция `0002`).
- `docs/BACKEND_ARCHITECTURE.md` описывает `VcsGateway` и `JobQueue` как
  «спроектированы, но не реализованы»; threat model требует GitHub App
  installation tokens и проверку HMAC-подписи вебхуков.
- `docs/SYSTEM_DESIGN.md` §4.2 фиксирует формат сообщения очереди: тело —
  только доменные данные, `priority` — свойство AMQP, очередь одна, с
  `x-max-priority`.
- `docs/testing/TEST_PLAN.md` требует: «неизвестное событие — 202, не 500;
  HMAC обязателен, без подписи — 401».
- Сущность `Hunk` уже существует в `app/domain/entities.py` и
  переиспользуется парсером диффа.

## Goals / Non-Goals

**Goals:**

- Приёмная часть конвейера (Context Level 1): вебхук → проверка подписи →
  дифф (fail-fast, без разбора) → `MergeRequest` + `ReviewRun` → задача в
  очереди; разбор и фильтрация диффа — у воркера (D3).
- Мульти-репозиторий по конструкции: подключение нового репозитория не
  требует изменения настроек сервиса.
- Чистые функции домена для всего решающего: HMAC, разбор диффа, фильтрация,
  извлечение события — тестируемые без базы, брокера и сети.
- Воркер получает в задаче идентификаторы, а не содержимое: контракт
  `docs/SYSTEM_DESIGN.md` §4.2 соблюдён дословно.

**Non-Goals:**

- Воркер, сборка RAG-контекста, вызов LLM — ветка `feat/system_design_rag`.
- Публикация комментариев и статусов на VCS.
- Регистрация репозиториев (отдельный эндпоинт с авторизацией).
- GitLab-адаптер: provider-нейтральная модель уже есть, GitLab — будущий
  адаптер без миграции схемы.
- `IdempotencyStore` и персистенция разобранного диффа.

## Decisions

### D1 — GitHub-first, GitLab-ready

GitHub-специфичны только адаптер `VcsGateway` (`GitHubVcsGateway`) и
экстрактор payload'а вебхука (`extract_github_event`). Домен и application
работают с provider-нейтральной моделью (`Provider` enum, `provider_id`),
которая уже существует. Добавление GitLab позже — новый адаптер и новая
функция разбора payload'а, без миграции схемы
(`docs/BACKEND_ARCHITECTURE.md`, раздел «Расширение»).

### D2 — Аутентификация GitHub App: installation tokens, мульти-репозиторий по конструкции

Адаптер авторизуется как GitHub App: JWT RS256, подписанный PEM private key
по `github_app_id`, обменивается на installation token через
`POST /app/installations/{id}/access_tokens`. `installation_id` берётся из
`payload["installation"]["id"]` каждого вебхука, и каждый метод
`VcsGateway` (`fetch_diff`, `fetch_pr_metadata`) принимает его параметром.
Настройка `github_installation_id` НЕ вводится: добавление репозиториев не
требует изменения конфигурации. Метода `request_reviewer` у порта нет —
бот никогда не назначается нашей системой (см. D4). Exponential backoff на
429/5xx — внутри адаптера, per `docs/BACKEND_ARCHITECTURE.md`.

### D3 — Дифф не персистится

Дифф не разбирается и не хранится в вебхуке: сохраняются только
`MergeRequest` и `ReviewRun`. Сообщение очереди несёт идентификаторы
(`head_sha`, `base_sha`, номер PR); воркер повторно достаёт дифф через
`VcsGateway`, разбирает той же чистой функцией `parse_diff` и фильтрует
`filter_diff_files` — разобранный дифф транзиентен в обработке задачи.
`context_payloads` — территория воркера (уровни контекста 2+), вебхук их
не трогает.

### D4 — `reopened` и прочие действия — ignored (202); бот не переназначается автоматически

Система не назначает бота ревьюером и не переназначает его при reopen:
`reopened` → HTTP 202 (ignored), пользователь переназначает бота вручную, и
тогда событие обрабатывается как обычный запуск. `closed` и любые иные
действия — тоже 202 (ignored). Единый код 202 для «принято» и «принято, но
проигнорировано» — решение владельца продукта от 2026-09-29, соответствует
`docs/testing/TEST_PLAN.md` («неизвестное событие — 202, не 500») и
фиксируется в delta spec. Замечание: чекпойнт 3 в `tasks/plan.md` упоминает
для `reopened` код 200 — расхождение решено в пользу 202 тем же решением
владельца продукта; спека change'а — источник правды.

### D5 — Незарегистрированный репозиторий — игнор (202), без записи

Вебхук для репозитория, которого нет в базе, получает 202 (ignored) без
записей и без задачи. Регистрации на лету нет и не будет: авто-регистрация
позволила бы «подписать чужой репозиторий» — противоречит threat model.
Регистрацию выполняет отдельный эндпоинт с авторизацией (будущий change).

### D6 — `base_sha` всегда из `fetch_pr_metadata`

Use case для любого запускающего действия (`opened`, `synchronize`) вызывает
`fetch_pr_metadata` и берёт `base_sha` из свежих метаданных — единый поток,
без ветвления по действию. Поле `base_sha` из payload'я не используется:
у GitHub оно может быть stale (ветка-цель успела уехать).

### D7 — Кэш installation tokens внутри адаптера, без порта CacheStore

Токены кэшируются в dict с expiry per `installation_id` внутри
`GitHubVcsGateway`; просроченный токен обновляется автоматически. Порт
`CacheStore` не вводится — тот же паттерн «in-process dict first», что
описан в `docs/BACKEND_ARCHITECTURE.md` / `docs/SYSTEM_DESIGN.md` §4.3:
поводом для порта станет вторая реплика, а не этот тикет. per threat model
installation tokens краткосрочные, поэтому потери от отсутствия общего кэша
минимальны.

### D8 — Новые зависимости и настройки — только через uv, только с кодом-потребителем

Runtime-зависимости: `httpx` переводится из dev-зависимости в runtime
(вызовы VCS API), добавляются `pyjwt` (JWT RS256 для GitHub App),
`cryptography` (backend RS256), `pika` (адаптер RabbitMQ). Всё через
`uv sync --all-extras` с обновлением `uv.lock`; `pip` и `poetry` не
используются. `httpx` и `pika` попадают в forbidden-список import-linter
для `domain`/`application` — импорт только в infrastructure.

Настройки (в `Settings`, из окружения): `github_app_id`,
`github_app_private_key` (PEM), `github_webhook_secret`, `rabbitmq_url`.
Они опциональны с дефолтом `""`, а не обязательны: решение осознанное,
чтобы приложение без GitHub-реквизитов поднималось и отвечало на
`/health`, поэтому громкое падение происходит при первом использовании,
а не на старте. Пустой секрет вебхука не принимает ничего: эндпоинт
отклоняет все доставки (401). Настройка `github_bot_username` в этом
change'е не вводится — потребителя у неё нет (публикация комментариев —
non-goal), появится на тикете воркера вместе с кодом, который её читает.
`github_installation_id` не вводится (см. D2).

### D9 — Миграций нет

Таблицы `repositories`, `merge_requests`, `review_runs` уже хранят всё, что
записывает вебхук; разобранный дифф транзиентен (D3); `context_payloads` —
воркер. `uv run alembic heads` остаётся на единственной голове `0002`.
Защита от второго активного прогона на тот же коммит — уже существующий
частичный уникальный индекс; use case обязан пережить конфликт не падая
(см. delta spec — сценарий «Повторная доставка безвредна»).

## Risks / Trade-offs

- **GitHub App auth сложен (JWT + installation token)** → изолирован в
  `github_auth.py`; JWT тестируется отдельным тестовым PEM-ключом; обмен и
  кэш — на `httpx.MockTransport`.
- **RabbitMQ недоступен в тестовом окружении** → порт позволяет фейк;
  интеграционные тесты идут на фейке порта, не на живом брокере.
- **`httpx` и `pika` становятся runtime-зависимостями** → forbidden-список
  import-linter держит их в infrastructure; слойная граница проверяется
  `uv run lint-imports`, а не ревью.
- **Edge cases парсера диффа (rename, mode change, no newline)** → парсер —
  чистая функция, тесты на записанных GitHub-диффах, итерации дёшевы.
- **Вебхук должен отвечать быстро, но ходит в VCS** → два HTTP-вызова VCS
  API (дифф + метаданные, оба fail-fast до создания записей); разбор и
  фильтрация в вебхуке не выполняются — тяжёлая работа целиком у воркера.
- **`reopened` не запускает ревью — пользователь может этого ожидать** →
  поведение зафиксировано в delta spec и README; игнор — осознанное решение,
  не пропуск.

## Migration Plan

1. Чистые функции домена (парсер, фильтр, HMAC, экстрактор события) — без
   новых зависимостей (Phase 1).
2. Порт `VcsGateway` + адаптер GitHub App с кэшем токенов; wiring в
   composition root; зависимости `httpx`/`pyjwt`/`cryptography` (Phase 2).
3. Порт `JobQueue` + адаптер `PikaJobQueue`; настройка `rabbitmq_url`;
   зависимость `pika`; wiring (Phase 3).
4. Use case `HandleWebhookEvent` и эндпоинт `POST /webhooks/github` с
   настройками GitHub App (Phase 4).
5. E2E на записанных fixture'ах, обновление документации, синхронизация
   delta spec в `openspec/specs/webhook-intake/`, архивация change (Phase 5).

**Rollback:** каждая фаза независимо откатываема; порты вводятся вместе с
адаптерами и первым потребителем, неиспользуемого кода не остаётся.
