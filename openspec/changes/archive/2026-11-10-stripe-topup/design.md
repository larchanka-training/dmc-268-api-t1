## Context

Баланс аккаунта — журнал `balance_credits` минус расход прогонов (`review-billing`). Зачисляет пока только администратор скриптом `python -m app.worker.credit_balance`. Решения родительской задачи #411: Stripe в тестовом режиме, ссылка Stripe Payment Link из Dashboard с параметром `client_reference_id` = id пользователя сервиса (Buy Button требует домен сайта, а стенд открывается по IP), зачисление только по вебхуку.

## Goals / Non-Goals

**Goals:** зачислять оплату Checkout на баланс по подписанному событию Stripe ровно один раз на сессию оплаты.

**Non-Goals:** создание сессий оплаты на бэкенде и секретный ключ `sk_…`; возвраты и споры; учёт платежей помимо журнала зачислений.

## Decisions

### D1. Только событие, сессию создаёт Payment Link

Сессию создаёт Payment Link, бэкенд получает только событие. Зачисление не зависит от возврата браузера на `/app/?topup=success`: адрес возврата может нести `{CHECKOUT_SESSION_ID}`, но это только подсказка интерфейсу.

### D2. Thin-события, а не snapshot

Назначение событий в Workbench — формат thin, типы `v1.checkout.session.completed` и `v1.checkout.session.async_payment_succeeded`. Решение пользователя: Stripe рекомендует thin для новых интеграций; форма уведомления не зависит от версии API, а сессия читается свежей, а не снимком на момент события.

Цена: сервису нужен ключ API и лишний запрос на каждое событие оплаты. Ключ — restricted `rk_…` только с **Checkout Sessions: Read**: он не создаёт и не меняет ничего. Приём включён, только когда заданы и `STRIPE_WEBHOOK_SECRET`, и `STRIPE_API_KEY`.

### D3. Проверка подписи и запрос сессии — SDK

`StripeClient(api_key).parse_event_notification(body, sig_header, secret)` проверяет `Stripe-Signature` по сырому телу с допуском 300 с (умолчание SDK) и строит типизированное уведомление; события, кроме двух типов оплаты, отвечают `200` без запроса к Stripe. Сессию отдаёт `fetch_related_object()` — `GET` по `related_object.url` уведомления.

- SDK синхронный: запрос идёт в threadpool и не держит event loop.
- Stripe ждёт ответа доставки около 10 с, поэтому HTTP-клиент SDK — `RequestsClient(timeout=5)` и `max_network_retries=0`: повторять доставку — дело Stripe.
- Роут перекладывает поля сессии SDK в `CheckoutSession` — frozen dataclass слоя приложения: правило зачисления SDK не знает, порта нет, потому что приложение Stripe не вызывает.
- Из сессии читаются только стабильные поля `id`, `mode`, `payment_status`, `currency`, `amount_total`, `client_reference_id`: сессию SDK запрашивает с версией API, зашитой в него, а SDK зафиксирован серией `stripe~=16.1` (`>=16.1,<17`): мажорный релиз меняет версию API Stripe — серия 16.x зафиксирована, точную версию держит `uv.lock`.

### D4. Коды ответа

- Подпись не прошла или тело не thin-событие (snapshot-событие, не JSON, нет `related_object`) — `400 WEBHOOK_SIGNATURE_INVALID`, как велит документация Stripe. Код тот же, что у GitHub (`401`): смысл один, статус у кода теперь `400 | 401`, как у `PROVIDER_NOT_SUPPORTED` (`404 | 501`).
- Секрет или ключ не задан — `503 PAYMENTS_DISABLED`, тело не читается, ничего не зачисляется. Не `400`: ошибка не в запросе, а в настройке стенда, и Stripe повторит доставку, когда настройка появится. Не `404`: маршрут в контракте есть.
- Stripe не отдал сессию (сеть, тайм-аут, отказ ключа, `404`) — `502 PAYMENT_PROVIDER_UNAVAILABLE`, в лог — id события, тип ошибки и HTTP-статус без текста: в тексте ошибки Stripe бывает маска ключа. Сбой базы — `500 INTERNAL_ERROR`. На любой 5xx Stripe повторяет доставку: в sandbox 3 раза за несколько часов, в live — до 3 суток.
- Остальное — `200` с `status`: `credited`, `duplicate` или `ignored`. Сессия не `mode = payment` (`setup`, `subscription`), `payment_status` не `paid` (`unpaid`, `no_payment_required`; на `status = complete` не смотрим — оплата может ещё идти), валюта не `eur`, неизвестный пользователь, суммы нет или она не положительна — `ignored` и одна строка лога с id события и сессии; повтор этому не поможет, поэтому не 4xx. Сумма — `Decimal(amount_total) / 100`, без float. `livemode` не проверяем: у тестового и боевого назначения разные секреты подписи.

### D5. Маршрут

`/api/v1/webhooks/stripe` лежит под префиксом вебхуков: `OriginMiddleware` его не проверяет, `RequestBodyLimitMiddleware` даёт лимит вебхука (2 МиБ). Роутер Stripe подключается раньше роутера `/webhooks/{provider}`, поэтому `stripe` не попадает в параметр провайдера VCS. Отдельный модуль `app/api/stripe_webhook.py`: у VCS-приёма свой порядок и свои коды. Клиент Stripe собирает контейнер (`stripe_client()`, `None` — приём выключен); SDK в `app/domain` и `app/application` запрещён контрактом `lint-imports`.

### D6. Одно зачисление на сессию Checkout

Ключ идемпотентности — id сессии Checkout, а не id события: Stripe может прислать одно событие дважды и даже два разных события об одном объекте, а асинхронная оплата приходит вторым событием (`async_payment_succeeded`) той же сессии. Колонка `balance_credits.stripe_checkout_session_id` nullable, частичный уникальный индекс `WHERE stripe_checkout_session_id IS NOT NULL`; ручные зачисления её не заполняют. Вставка — `INSERT … ON CONFLICT DO NOTHING RETURNING id`: проверка до вставки гонку двух доставок не закрывает, а уникальный индекс закрывает — вторая транзакция ждёт первую и ничего не вставляет.

### D7. Повторное использование ручного пути

Зачисление идёт через тот же порт `BillingRepo.add_credit` и сущность `BalanceCredit`: `credited_by = "stripe"`, заметка `Stripe <id сессии>`. Получатель ищется по id пользователя сервиса (`client_reference_id`), а не по id GitHub: его и отдаёт `GET /api/v1/auth/me`. Подмена значения не угроза: чужой id не узнать (`/auth/me` отдаёт только свой), а потолок общий на аккаунт.

Зачисляется любая оплаченная сессия Checkout аккаунта Stripe в евро, а не только сессия Payment Link пополнения: других продуктов у аккаунта нет. Появится другой продукт — сессии фильтровать по `payment_link`.

### D8. Алерт на отказы вебхука

Stripe о падениях нашего эндпоинта не сообщает, а после исчерпанных повторов оплата остаётся незачисленной. `StripeWebhookFailing` (warning, `service: stripe`) горит, когда за 6 часов больше половины ответов `/api/v1/webhooks/stripe` — 4xx или 5xx. 4xx считаются: `400` на стенде — секрет не того назначения. Только `POST`: `GET` на ту же ручку получает `405` с тем же `http_route`. Окно шире соседей (час): событий мало, одно-два на пополнение.

Свой `service`, а не `api`: `inhibit_rules` с `equal: [service, mountpoint]` дали бы любому критическому алерту api (например, `Api5xxSpike`) заглушить этот.

Порога по числу отказов нет. Ряд кода появляется в Prometheus сразу с 1, и `increase()` первый отказ с кодом, ряда которого в окне ещё не было, не видит — в долю входит только второй (та же ловушка, что у `prime_run_outcomes`, #324). Отказ с кодом, ряд которого уже есть, виден сразу, и один такой без принятых доставок за 6 часов зажигает алерт. Это допустимо: оплата не зачислена, алерт — warning, Stripe повторит доставку, а следующий `200` при уже заведённом ряде `200` опустит долю до половины и погасит его.

### D9. Потолок пополнений на пользователя

Stripe в тестовом режиме, а ссылка оплаты публичная: любой вошедший пополнит баланс тестовой картой `4242…` и потратит настоящие токены Eurorouter. Поэтому всё зачисленное пользователю через Stripe ограничено `STRIPE_TOPUP_LIMIT_EUR` (20 € по умолчанию); сверх него — исход `over_limit`, `200 ignored` и предупреждение в логе. Сумма — по зачислениям с `stripe_checkout_session_id`, ручные не в счёт.

Проверка — в транзакции вставки под `pg_advisory_xact_lock` плательщика (`BillingRepo.lock_payer`, тот же, что у резерва прогона): иначе две сессии одного пользователя видят сумму без друг друга и обе проходят. Сумма считается после `INSERT … ON CONFLICT DO NOTHING`, а сверх потолка транзакция откатывается: повтор уже зачисленной сессии остаётся `duplicate`, а не `over_limit`. Схема не меняется.

## Risks / Trade-offs

- **Тестовый режим — бесплатный баланс.** Тестовая карта пополняет баланс без денег, а ревью тратит настоящие токены Eurorouter. Ограничено потолком на пользователя (D9): потеря не больше `STRIPE_TOPUP_LIMIT_EUR` на аккаунт GitHub, но каждый новый аккаунт получает свой потолок.
- **Возвраты и споры не обрабатываются.** `charge.refunded` и `charge.dispute.created` баланс не списывают: тестовый режим, настоящих денег нет. Корректировку при необходимости делает администратор отрицательным зачислением.
- **Лишний запрос к Stripe на каждое событие оплаты** и ключ на стенде. Ключ restricted, только чтение сессий; утечка открывает чтение сессий Checkout аккаунта, но не платежи.
- **Доставку из Stripe на стенд тестами не проверить**: тесты подписывают thin-события тем же HMAC-алгоритмом, а API Stripe подменяют HTTP-клиентом SDK. Проверка — тестовая оплата на стенде (DoD #411).
- **Секрет или ключ не задан** — оплата пройдёт, а зачисления не будет, пока настройка не появится и Stripe не повторит доставку; иначе — повтор из Workbench. Видно по `503` и алерту.
