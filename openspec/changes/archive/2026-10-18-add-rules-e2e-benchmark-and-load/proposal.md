# Proposal: E2E правил ревью, бенчмарк Precision/Recall и нагрузочный прогон

## Why

Задача #62: путь «вебхук → правила владельца → анализ → публикация в VCS» нигде не проверяется целиком.
Сквозной тест `tests/api/test_webhooks_e2e.py` заканчивается на очереди, а загрузка правил, сборка промпта и публикация проверяются по отдельности на фейках портов.
Поэтому нет доказательства, что правила с коммита целевой ветки доходят до модели, а её замечание по правилу публикуется в PR, и что вредоносный `rules.md` не меняет поведение прогона.
Влияние правил на качество ревью не измерено: неизвестно, ловит ли модель проектные ограничения из `rules.md` и не теряет ли при этом общие дефекты.
Поведение под нагрузкой тоже не проверено: параллельные доставки вебхуков, повторные доставки одного события и несколько воркеров на одной очереди.

Разбор сценариев нашёл расхождение со спекой `repo-rules`: файл без единого принятого правила (пустой, только проза или все разделы отклонены) получает статус `loaded`.
Модель тогда читает «ни одно правило не применимо к файлам диффа», хотя причина в самом файле, и причина фоллбэка в контексте не фиксируется.

## What Changes

- Новый статус загрузки правил `empty`: файл есть, но в нём нет ни одного принятого правила.
  Отклонённые разделы по-прежнему перечисляются в контексте с причиной, сообщение с правилами называет причину фоллбэка.
- Сквозной тест в CI: подписанный вебхук через настоящие API, PostgreSQL, RabbitMQ и воркер, настоящий адаптер GitHub поверх подменённого HTTP-транспорта, подменённая модель.
  Четыре конфигурации `.review/rules.md`: файла нет, корректные правила, пустой файл, вредоносный промпт внутри.
- Бенчмарк Precision/Recall на живой модели: синтетический корпус PR с размеченными нарушениями, прогон через тот же сквозной стенд в конфигурациях `absent`, `rules`, `empty`, `adversarial`.
  Запуск вручную отдельным workflow, отчёт - артефакт прогона и сводка job.
- Нагрузочный прогон: живой HTTP-сервер API, несколько воркеров, поток вебхуков с повторными доставками.
  Малый прогон идёт в CI и проверяет корректность под конкуренцией; полный запускается вручную и пишет отчёт с латентностью и пропускной способностью.
- Отчёт о тестировании сценариев с разными конфигурациями `rules.md` в `docs/testing/`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `repo-rules`: требование «Дефолтный фоллбэк не прерывает прогон» получает статус `empty` для файла без принятых правил.
- `backend-base-setup`: новое требование - сквозной тест конвейера с конфигурациями правил входит в обязательный прогон CI.

## Impact

- Код: `app/domain/enums.py`, `app/application/repo_config_loader.py`, `app/domain/prompt.py`, `app/domain/entities.py`.
- Тесты: новые `tests/e2e/`, `tests/eval/`, `tests/load/`, фейк GitHub API на уровне HTTP в `tests/fakes/`.
- CI: новые workflow `eval.yml` и `load.yml`; маркеры pytest `eval` и `load` исключены из обычного прогона, как `live`.
- Документация: `docs/testing/RULES_E2E_REPORT.md`, `docs/testing/TEST_PLAN.md`, `README.md`.
- Схема базы, REST и формат сообщения очереди не меняются.
