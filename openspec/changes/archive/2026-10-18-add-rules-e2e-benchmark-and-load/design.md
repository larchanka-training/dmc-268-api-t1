# Design: add-rules-e2e-benchmark-and-load

## Context

Мотивация - в proposal.md.
`tests/api/test_webhooks_e2e.py` проверяет приём вебхука до `FakeQueue`; воркер, сборка контекста, модель и публикация проверяются юнит-тестами на фейках портов (`FakeVcs`, `RecordingVcsGateway`, `ScriptedLlmGateway`).
Адаптер `GitHubVcsGateway` принимает `httpx.Client` снаружи, `Container` - frozen dataclass с ленивыми полями, которые можно заполнить при конструировании.
CI уже поднимает PostgreSQL и RabbitMQ и роняет сборку на любом пропущенном тесте.
Живые вызовы модели идут только через `llm-live.yml` с секретом `AI_DMC268_T1`; синтетические запросы - условие из `add-llm-gateway`, D11.

## Goals / Non-Goals

**Goals:**

- Один сквозной стенд, общий для E2E в CI, бенчмарка и нагрузочного прогона: отличаются только модель и объём.
- Внешние системы подменяются на их границе, всё внутри - боевой код: эндпоинт, use case, SQLAlchemy, RabbitMQ, consume-цикл воркера, `run_review`, адаптер GitHub, промпты из `prompts/review/`.
- Метрики бенчмарка считаются по тому, что опубликовано в PR, а не по сырому ответу модели.

**Non-Goals:**

- Нагрузка на настоящий GitHub или на модель: их латентность внешняя и моделируется задержкой фейка.
- Пороги качества как гейт CI: ответ живой модели недетерминирован, бенчмарк измеряет, а не блокирует.
- Нагрузка на REST для фронтенда и на вход OAuth: в задаче речь о конвейере ревью.

## Decisions

**D1. Статус `empty` вычисляется после разбора, кэш не меняется.**
Кэш хранит статус довыборки и текст файла (`loaded` + текст), а разбор идёт после кэша при каждом прогоне.
`empty` - итог разбора, поэтому он выводится из того же кэшированного текста, и формат записи кэша `repo-rules:v1` остаётся прежним.
`RepoRules.rejected` при `empty` не пуст: владелец видит в контексте, почему разделы отклонены.
Альтернатива - оставить `loaded` и различать «нет правил» и «нет применимых» по пустому `rejected` - отвергнута: модель и отчёт видят только статус, и причина фоллбэка терялась бы.

**D2. GitHub подменяется на уровне HTTP, а не порта.**
`FakeGitHub` в `tests/fakes/github_api.py` - in-memory состояние репозитория (PR, файлы на коммитах, опубликованные ревью, check runs), отданное через `httpx.MockTransport` настоящим `GitHubAppAuth` и `GitHubVcsGateway`.
Так в тест попадают JWT приложения, выдача installation token, заголовки `Accept`, потоковое чтение с лимитом и разбор ответов - всё, что фейк порта обходит.
Неизвестный маршрут отвечает 404 и записывается: тест видит запрос, которого не ждал.
Альтернатива - HTTP-сервер фейка на порту - добавляет сеть и гонки за портом без выигрыша: транспорт httpx - и есть граница адаптера.

**D3. Стенд собирает `Container` явно, а не через `build_container`.**
`tests/e2e/stack.py` заполняет поля контейнера готовыми объектами: настоящий engine, `RabbitMQJobQueue`, адаптер GitHub поверх `FakeGitHub`, переданная тестом модель, `InMemoryCacheStore`, `TreeSitterDefinitionExtractor`.
Воркер - настоящий `build_worker(settings).run(handler, limit=n)` с обработчиком `build_review_handler` и текстами промптов из `load_checked_prompt_texts`.
Новый шов в `app/` не нужен: боевой контейнер уже принимает адаптеры полями.

**D4. Модель в E2E - записывающий фейк порта.**
`ScriptedLlmGateway` отдаёт заданные ответы и хранит запросы, поэтому тест сверяет, какие правила и в каком виде дошли до модели.
Для вредоносного файла проверяется отсутствие прозы и правила из блока кода в любом сообщении, обезвреженные служебные токены и имя правила литералом JSON; без файла правил ссылка модели на правило отклоняется отсевом, а остальные замечания публикуются.

**D5. Eval правил - тот же стенд с живой моделью и корпусом.**
Корпус - YAML-кейсы в `tests/eval/rules/corpus/` (раскладка `tests/eval/` - из `docs/testing/LLM_EVAL.md` §4): файлы PR (новые файлы, из них стенд строит дифф) и ожидаемые замечания.
Строка ожидаемого замечания задаётся подстрокой кода, а не номером: так кейс не ломается при правке файла, а в код не нужно вписывать подсказку для модели.
Конфигурации правил: `absent`, `rules`, `empty`, `adversarial` (те же правила плюс инструкции в прозе и в тексте пункта).
Сопоставление - чистые функции в `tests/eval/scoring.py` по правилу `LLM_EVAL.md` §2: один к одному, тот же файл и сторона, строка в окне ±3; категория обязательна для общего дефекта и не проверяется у нарушения правила - у пункта `rules.md` нет своей категории.
Метрики по конфигурации: Precision, Recall, F1 по всем размеченным нарушениям, Recall отдельно по проектным правилам и по общим дефектам, доля верных ссылок на пункт правила.
Модель - `OpenAiCompatibleGateway` на Eurorouter, собранный напрямую, как в живых тестах: без фоллбэка контейнера на локальную модель, метрики снимаются с одной модели; запросы синтетические, код проверяемых репозиториев наружу не уходит.
Обвязка проверяется в каждом CI моделью-оракулом, отвечающей разметкой: метрики обязаны выйти идеальными, иначе сломан корпус или стенд.
Workflow `eval.yml` запускается вручную и на PR, меняющих сам бенчмарк: новый workflow с одним `workflow_dispatch` нельзя запустить до мерджа в ветку по умолчанию, а первый замер нужен в этом PR.

**D6. Нагрузка - живой uvicorn и потоки воркеров.**
API поднимается `uvicorn.Server` в отдельном потоке на свободном порту, вебхуки шлёт пул потоков через `httpx` по настоящему HTTP.
Каждый воркер - свой поток со своим соединением с брокером, как отдельный процесс в проде.
Модель - заглушка с задержкой, GitHub - `FakeGitHub` с задержкой; оба потокобезопасны.
Повторные доставки одного события идут параллельно с первыми: проверяется идемпотентность приёма под конкуренцией.
Метрики: латентность ответа на вебхук (p50, p95, p99), доля ответов 2xx, пропускная способность приёма, время от приёма до `completed` по записям прогонов, время разбора очереди.
Малый прогон (`tests/load/test_load_smoke.py`) идёт в CI без порогов по времени: только корректность - ни одного 5xx, ровно один прогон и одно опубликованное ревью на PR, все прогоны `completed`.
Воркеры в нём стартуют после приёма, чтобы каждый повтор приходил при активном прогоне: повтор после завершения по спеке `review-data-model` создаёт новый прогон, и с ним проверка зависела бы от скорости машины.
Полный прогон такие повторы считает отдельно и выводит в отчёт.
Полный прогон (маркер `load`, workflow `load.yml`) параметризуется окружением и проверяет пороги, заданные входами workflow.
Альтернатива - locust - даёт латентность HTTP, но не время до публикации, ради которого прогон и нужен; собственный сценарий короче обвязки над locust.

**D7. Маркеры `eval` и `load` исключены из обычного прогона.**
Как `live`: `addopts` в `pyproject.toml` их не собирает, поэтому правило «пропуск - провал» в `ci.yml` не задевается.
Чистые функции бенчмарка и сценария нагрузки тестируются в обычном прогоне.

## Risks / Trade-offs

- [Живая модель недетерминирована] → число повторов задаётся входом workflow, в отчёте - среднее и разброс; порогов качества нет.
- [Корпус синтетический и маленький] → метрики показывают влияние правил на этом корпусе, а не качество ревью вообще; корпус расширяется добавлением YAML-файла.
- [Время в нагрузочном прогоне на раннере GitHub шумит] → пороги по времени только в ручном прогоне и задаются входами; в CI - только корректность.
- [Общий брокер в CI] → стенд чистит очереди до и после теста, как `tests/queue/`.

## Migration Plan

Миграций и новых настроек нет.
Откат - revert PR; статус `empty` в старых пакетах контекста не встречается, новые пакеты со статусом `empty` старый код читает как неизвестный статус с общей причиной.
