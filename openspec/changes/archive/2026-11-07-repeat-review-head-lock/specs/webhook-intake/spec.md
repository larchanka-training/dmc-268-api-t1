## MODIFIED Requirements

### Requirement: Повторный прогон по вебхуку блокирует merge gate до нового ревью

Приём вебхука SHALL выставлять на head check run `in_progress` «Идёт ревью» после коммита нового прогона и до задачи, когда сменилась целевая ветка или последний прогон на этом head — `failed` или `cancelled`: прежний check описывает чужой дифф или упавшее ревью. Повтор вебхука на дубль в `queued` SHALL получать ту же блокировку best-effort. Сбой GitHub на блокировке SHALL давать HTTP 502 без задачи и прогон `failed`; целевая ветка SHALL оставаться новой.

#### Scenario: Окно между сменой ветки и новым ревью закрыто

- **WHEN** на head-коммите check run `success` по старой ветке, и приходит `edited` со сменой целевой ветки
- **THEN** до постановки нового прогона на head-коммит выставлен check run `in_progress` «Идёт ревью»; если новое ревью упадёт, его сменит `failure` «Ревью не удалось»

#### Scenario: Воркер старого прогона выставил gate после блокировки

- **WHEN** прогон на старой ветке прочитал свой статус до отмены и выставил `success` уже после блокировки приёма
- **THEN** перечитав последний прогон на head, он выставляет `in_progress` снова (требование «Отменённый прогон не выставляет merge gate», `review-pipeline`)

#### Scenario: GitHub недоступен на блокировке

- **WHEN** выставить блокирующий check run не удалось
- **THEN** ответ — HTTP 502, задача не ставится, новый прогон — `failed`, у PR новая ветка; повтор доставки снова блокирует head и создаёт прогон

#### Scenario: Задачу после блокировки не поставили

- **WHEN** блокировка смены ветки выставлена, а публикация задачи в брокер упала
- **THEN** прогон переходит в `failed`, и на head вместо `in_progress` выставляется `failure` «Ревью не удалось»

#### Scenario: Блокировка не встала и повтор доставки пришёл на ту же ветку

- **WHEN** блокировка смены ветки получила отказ GitHub, а повтор доставки пришёл, когда целевая ветка PR уже записана новой
- **THEN** повтор видит упавший прогон на head, выставляет `in_progress` «Идёт ревью» до задачи и создаёт прогон; ревью не идёт под прежним `success`

#### Scenario: Повтор после упавшего прогона на том же head

- **WHEN** на head-коммите последний прогон по вебхуку `failed`, и приходит повтор доставки `synchronize` того же head
- **THEN** до постановки нового прогона на head выставлен `in_progress` «Идёт ревью» вместо `failure` «Ревью не удалось»

#### Scenario: Первый прогон на head не блокирует

- **WHEN** на head-коммите прогонов ещё не было, и приходит `opened` или `synchronize`
- **THEN** приём check run не выставляет: его выставит воркер при захвате прогона; повтор доставки, пока прогон `queued`, — дубль и один `in_progress` «Идёт ревью»

#### Scenario: Повтор на head, проверенном вручную, не блокирует

- **WHEN** последний прогон на head-коммите — завершённый ручной, и приходит вебхук на тот же head
- **THEN** создаётся прогон по вебхуку, а приём check run не выставляет

#### Scenario: Двойной сбой: повтор застрявшего прогона переставляет блокировку

- **WHEN** блокировка получила отказ GitHub и перевод прогона в `failed` тоже не прошёл, прогон остался `queued`, на head — `success` прежнего ревью, фильтра веток или паузы, и приходит повтор доставки
- **THEN** ответ — дубль этого прогона, а приём best-effort выставляет по нему `in_progress` «Идёт ревью»; сбой GitHub на этом шаге ответ не меняет

### Requirement: Фильтр целевых веток

Вебхук `pull_request` своего PR SHALL сверять целевую ветку из свежих метаданных PR с `branch_filter` репозитория (glob, как у файлов правил); пустой фильтр SHALL означать все ветки. PR вне фильтра SHALL получать HTTP 202 (ignored) без прогона и задачи, а на head SHALL ставиться проверка `success` «Ветка не в фильтре ревью» (best-effort). Уход PR из фильтра SHALL отменять его активный прогон, возврат в фильтр SHALL обрабатываться как смена целевой ветки.

#### Scenario: PR в ветку вне фильтра

- **WHEN** у репозитория `branch_filter = ["release/*"]`, а приходит `pull_request.opened` или `synchronize` своего PR в `main`
- **THEN** ответ — HTTP 202 (ignored), прогон не создаётся, задача не ставится, на `head_sha` ставится check run `success` «Ветка не в фильтре ревью», в лог пишутся id репозитория и номер PR атрибутами записи, без имени ветки

#### Scenario: Совпадение паттерна

- **WHEN** у репозитория `branch_filter = ["release/*"]`
- **THEN** ветка `release/1.2` подходит, а `release/1.2/hotfix` и `Release/1.2` нет; `release/**` подходит и к `release/1.2/hotfix`

#### Scenario: PR в ветку фильтра

- **WHEN** у репозитория `branch_filter = ["release/*"]`, а приходит `pull_request.opened` своего PR в `release/1.2`
- **THEN** создаётся прогон и ставится задача, как без фильтра

#### Scenario: PR увели из ветки фильтра

- **WHEN** у PR в `main` идёт прогон, `branch_filter = ["main"]`, и приходит `pull_request.edited` со сменой целевой ветки на `develop`
- **THEN** прогон отменяется, новый не создаётся, на head ставится check run `success` «Ветка не в фильтре ревью»

#### Scenario: PR вернули в ветку фильтра

- **WHEN** PR, уведённый из ветки фильтра, возвращают `edited` в ветку, подходящую под `branch_filter`, а на head есть завершённый или отменённый прогон
- **THEN** на head ставится блокировка `in_progress` «Идёт ревью» и создаётся прогон на текущий head: завершённый прогон дублем его не делает

#### Scenario: Тред у PR вне фильтра

- **WHEN** у PR в `main` при `branch_filter = ["release/*"]` человек закрывает тред бота и приходит `pull_request_review_thread` с `action=resolved`
- **THEN** ответ HTTP 202 (acknowledged), состояние треда записывается, на head ставится проверка `success` «Ветка не в фильтре ревью», gate по тредам не пересчитывается

#### Scenario: Ручной прогон вне фильтра

- **WHEN** целевая ветка PR вне `branch_filter`, а за head отвечает ручной прогон, который не упал и не отменён
- **THEN** на head остаётся его gate, а не проверка фильтра (требование «Прогон при паузе ревью не блокирует merge gate» спеки `review-pipeline`)
