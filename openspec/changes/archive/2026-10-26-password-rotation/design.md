## Context

Проверено на `docker:29-dind` (Docker 29.9.2), OpenTofu 1.13.2, провайдер kreuzwerker/docker 4.6.0: настоящий `infra/` с локальным состоянием, настоящий образ API (собран в dind, отдан локальным реестром по digest), шаги `infra.sh`, `plan.sh`, `passwords.sh`, `migrate.sh`, `apply.sh`, `check-worker.sh`, `check-replica.sh` по порядку `deploy.yml`; ssh — подложный, «стенд» — сам dind.

Потребители паролей (grep по `infra/` и workflow):

- `PG_PASSWORD_DMC268_T1` — роль `dmc268`, она же `POSTGRES_USER` (суперпользователь кластера): `DATABASE_URL` у `api`, `worker` и миграций (`local.app_env`), `PGPASSWORD` у `replication-setup` и `postgres-backup`. Healthcheck реплики и `check-replica.sh` входят по локальному сокету (`trust`).
- `RABBITMQ_PASSWORD_DMC268_T1` — `RABBITMQ_URL` у `api` и `worker` (у миграций в окружении, но в брокер они не ходят).
- `PG_REPLICATION_PASSWORD_DMC268_T1` — `replication-setup` (`ALTER ROLE replicator`) и `passfile` реплики. Уже меняется обычным деплоем (#102): от пароля пересоздаются оба, сторож их не держит.
- `PG_MONITOR_PASSWORD_DMC268_T1` — секрет заведён, но на `develop` его никто не читает: роль `dmc268_monitor` и коллектор приходят с PR #130, и там шаг миграций переустанавливает пароль на каждом деплое.

## Goals / Non-Goals

- Цель: смена пароля базы и брокера — обычный деплой, простой не больше одного деплоя, без замены базы и брокера.
- Не цель: две роли с переключением (blue/green паролей), чтобы окно было нулевым; ротация по расписанию.

## Decisions

- **Шаг деплоя, а не runbook руками.** Ручной путь (б) — `ALTER ROLE` на сервере → новый секрет → деплой с `allow_stateful_replace` — открывает окно в момент `ALTER ROLE` и держит его, пока человек меняет секрет и ждёт сборку и деплой (минуты), а деплой ещё и пересоздаёт базу: все соединения рвутся, 60 с штатной остановки плюс старт. И замена ничего не даёт — пароль всё равно в томе. Шаг (а) открывает окно только внутри деплоя и не трогает контейнер базы.
- **`ignore_changes = [env]` у базы и брокера.** В `env` у них только `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` и `RABBITMQ_DEFAULT_USER`/`RABBITMQ_DEFAULT_PASS`: образы читают их только на пустом томе (entrypoint postgres проверяет `POSTGRES_PASSWORD` лишь перед initdb, брокер заводит пользователя по умолчанию только на пустой базе). Правка этих значений на живом томе ничего не меняет — её незачем и видеть. Риск — будущая переменная, действующая при каждом старте (`TZ`, `RABBITMQ_SERVER_ADDITIONAL_ERL_ARGS`): её правка молча не дошла бы. Закрыт тестом: состав `env` должен быть ровно этими ключами, новая переменная роняет тест и требует решения. На чистом сервере `POSTGRES_PASSWORD` нужен initdb — он в `env` и остаётся; при ручной замене контейнера (`allow_stateful_replace`) новый получает текущие значения, на заведённом томе безвредные. `POSTGRES_PASSWORD_FILE` и `upload` не взяли: у провайдера `upload` — тоже атрибут с заменой контейнера.
- **Вход новым паролем, потом смена.** Шаг входит новым паролем: в базу — по сети изнутри контейнера (`-h dmc268-postgres`, правило `samenet` scram, как у API и миграций, а не петля с `trust`), в брокер — `rabbitmqctl authenticate_user`. Вошёл — ничего не меняет: на обычном деплое шаг — no-op, в логе «совпадает с секретом». Не вошёл — `ALTER ROLE` по локальному сокету (`trust`, старый пароль не нужен) и `rabbitmqctl change_password`, потом вход снова: не вошёл — шаг падает до миграций. Роль и пользователь — из окружения контейнера (`POSTGRES_USER`, `RABBITMQ_DEFAULT_USER`): это те, кого завёл том.
- **Пароль — первой строкой stdin.** `docker exec -i … sh -c '<скрипт>'`: скрипт секретов не содержит, пароль читает `IFS= read -r` оболочки контейнера, дальше — `PGPASSWORD` и `\getenv` у psql, stdin у `rabbitmqctl` (он читает пароль со stdin, проверено на 4.4). В argv на раннере, в ssh и в `ps` сервера пароля нет. `-e VAR` у `docker exec` тоже не светил бы его в argv, но положил бы в конфиг exec у демона. Перевод строки в пароле шаг отклоняет до сервера. Упавший `ALTER ROLE … PASSWORD '…'` PostgreSQL пишет в лог строкой `STATEMENT`, psql выводит строкой `LINE` (проверено на pg18), поэтому сессия ставит `log_min_error_statement = panic`, `log_statement = none` и `VERBOSITY terse`; `pg_stat_statements.track_utility = off` — на случай расширения из #130, без него `SET` безвреден.
- **После плана, до миграций.** Миграции и новый API входят уже новым паролем: `migrate_env` targeted apply шага «Поднять базу и брокер» обновляет и без изменений ресурсов (`Changes to Outputs: ~ migrate_env`, проверено). После плана — чтобы отклонённый план пароль не менял: окно открывается, только когда до apply остались миграции.
- **Окно.** `ALTER ROLE` и `change_password` открытые соединения не рвут (проверено: долгая сессия psql и AMQP-соединение со старым паролем живы после смены), новые со старым — отклоняются. От шага паролей до SIGTERM старому API в полном apply старые API и воркер работают на открытых соединениях пула и не открывают новых. Замер на dind: база — 3,9 с до SIGTERM старому API и 3,4 с замены API; последовательные запросы по открытому соединению не падали, из 12 параллельных 1 и 6 получили `500`; брокер — 2 с. На стенде окно — шаг миграций (pull образа и alembic по ssh) и начало apply; при повторной сборке того же коммита pull мгновенный.

## Risks / Trade-offs

- Миграции упали после смены — apply не идёт, и старые API и воркер до следующего деплоя без новых соединений. Откат — вперёд: повторный деплой («совпадает» и дальше как обычно) или руками вернуть роли пароль старого API (`\password`, `infra/README.md`, «Откат»). Секрет старым значением не вернуть: GitHub его не отдаёт.
- Воркер, дорабатывающий сообщение во время смены (до 41 мин), живёт на открытых соединениях; понадобится новое — это сообщение упадёт.
- В `env` контейнеров базы и брокера и в состоянии остаётся пароль инициализации тома. Он больше не действует, но `docker inspect` его показывает — не принимать за текущий; README использует его для проверки, что старый пароль отклоняется.
- Смена `postgres_user` или `rabbitmq_user` по-прежнему ничего не меняет в томе и под `ignore_changes` плана не даёт — как и раньше, это новый том.
