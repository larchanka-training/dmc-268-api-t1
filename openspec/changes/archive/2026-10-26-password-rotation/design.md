## Context

Проверено на `docker:29-dind` (Docker 29.9.2), OpenTofu 1.13.2, провайдер kreuzwerker/docker 4.6.0: настоящий `infra/` с локальным состоянием, настоящий образ API (собран в dind, отдан локальным реестром по digest), шаги `infra.sh`, `plan.sh`, `passwords.sh`, `migrate.sh`, `apply.sh`, `check-worker.sh`, `check-replica.sh` по порядку `deploy.yml`; ssh — подложный, «стенд» — сам dind.

Потребители паролей (grep по `infra/` и workflow):

- `PG_PASSWORD_DMC268_T1` — роль `dmc268`, она же `POSTGRES_USER` (суперпользователь кластера): `DATABASE_URL` у `api`, `worker` и миграций (`local.app_env`), `PGPASSWORD` у `replication-setup` и `postgres-backup`. Healthcheck реплики и `check-replica.sh` входят по локальному сокету (`trust`).
- `RABBITMQ_PASSWORD_DMC268_T1` — `RABBITMQ_URL` у `api` и `worker` (у миграций в окружении, но в брокер они не ходят).
- `PG_REPLICATION_PASSWORD_DMC268_T1` — `replication-setup` (`ALTER ROLE replicator`) и `passfile` реплики. Уже меняется обычным деплоем (#102): от пароля пересоздаются оба, сторож их не держит.
- `PG_MONITOR_PASSWORD_DMC268_T1` — секрет заведён, но на `develop` его никто не читает: роль `dmc268_monitor` и коллектор приходят с PR #130, и там шаг миграций переустанавливает пароль на каждом деплое.

## Goals / Non-Goals

- Цель: смена пароля базы и брокера — обычный деплой, простой не больше одного деплоя, без замены базы и брокера.
- Не цель: две роли с переключением (blue/green паролей), чтобы окно было нулевым; ротация по расписанию.

## Decisions

- **Шаг деплоя, а не runbook руками.** Ручной путь (б) — `ALTER ROLE` на сервере → новый секрет → деплой с `allow_stateful_replace` — открывает окно в момент `ALTER ROLE` и держит его, пока человек меняет секрет и ждёт сборку и деплой (минуты), а деплой ещё и пересоздаёт базу: все соединения рвутся, 60 с штатной остановки плюс старт. И замена ничего не даёт — пароль всё равно в томе. Шаг (а) открывает окно только внутри деплоя и не трогает контейнер базы.
- **`ignore_changes = [env]` у базы и брокера.** В `env` у них только `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` и `RABBITMQ_DEFAULT_USER`/`RABBITMQ_DEFAULT_PASS`: образы читают их только на пустом томе (entrypoint postgres проверяет `POSTGRES_PASSWORD` лишь перед initdb, брокер заводит пользователя по умолчанию только на пустой базе). Правка этих значений на живом томе ничего не меняет — её незачем и видеть. Риск — будущая переменная, действующая при каждом старте (`TZ`, `RABBITMQ_SERVER_ADDITIONAL_ERL_ARGS`): её правка молча не дошла бы. Закрыт тестом: состав `env` должен быть ровно этими ключами, новая переменная роняет тест и требует решения. На чистом сервере `POSTGRES_PASSWORD` нужен initdb — он в `env` и остаётся; при ручной замене контейнера (`allow_stateful_replace`) новый получает текущие значения, на заведённом томе безвредные. `POSTGRES_PASSWORD_FILE` и `upload` не взяли: у провайдера `upload` — тоже атрибут с заменой контейнера.
- **Вход новым паролем, потом смена.** Шаг входит новым паролем: в базу — по сети изнутри контейнера (`-h dmc268-postgres`, правило `samenet` scram, как у API и миграций, а не петля с `trust`), в брокер — `rabbitmqctl authenticate_user`. Вошёл — ничего не меняет: на обычном деплое шаг — no-op, в логе «совпадает с секретом». Не вошёл — `\password` в psql по локальному сокету (`trust`, старый пароль не нужен) и `rabbitmqctl change_password`, потом вход снова: не вошёл — шаг падает до миграций. Роль и пользователь — из окружения контейнера (`POSTGRES_USER`, `RABBITMQ_DEFAULT_USER`): это те, кого завёл том.
- **Смена имён — `postcondition`, а не `replace_triggered_by`.** `ignore_changes = [env]` спрятал бы и смену `postgres_user`, `postgres_db`, `rabbitmq_user`: шаг сменил бы пароль прежней роли, а API и миграции входили бы новой (ревью). Первый вариант — `terraform_data` с именами и `replace_triggered_by` у контейнера — на dind при переходе с ветки #220 дал `postgres must be replaced` и `rabbitmq must be replaced`: создание нового `terraform_data` — тоже повод к замене, и деплой встал бы на стороже. `postcondition` с `contains(self.env, "POSTGRES_USER=${var.postgres_user}")`: при `ignore_changes` `self.env` в плане — окружение из состояния, и смена имени роняет plan (`Resource postcondition failed`, проверено на dind для роли, базы и пользователя брокера), а переход — `No changes`. Замена с `allow_stateful_replace` тут не нужна и не помогла бы: новое имя в заведённом томе не появится, это новый том. `tofu test` такой случай не проверит: ему нужно состояние, а `run` с `command = apply` не убирается — тома держит `prevent_destroy`; проверяют текст `infra/*.tf` и dind.
- **Пароль — печатный ASCII без пробела, `^[!-~]+$`.** Пароль базы и брокера едет в URL (`local.app_env`, `urlencode`), а `urlencode` кодирует пробел как `+`, который SQLAlchemy и pika читают буквально; `rabbitmqctl` обрезает пробелы по краям stdin и при смене, и при проверке входа — шаг был бы зелёным, а API не вошёл бы (ревью). Первое правило — только `[A-Za-z0-9._~-]` — было строже нужного: base64-секрет стенда (`+`, `/`, `=`) уронил бы первый деплой после мёржа. `+`, `/`, `=`, `@`, `:`, `%`, кавычки и `\` `urlencode` кодирует в `%XX`, и `make_url` и `URLParameters` декодируют их верно — проверено на dind сквозь деплой (`a+b/c=d`, `p@ss:w%rd`, `x'y"z\$`, base64) для базы, брокера и `replicator`, вместе с `\password`, `passfile` реплики и `PGPASSWORD` копий. Не-ASCII не проверялся и отклоняется; диапазон сверяется в `LC_ALL=C` — по байтам, независимо от локали раннера. Совет — `openssl rand -hex 24`. Правило проверяет шаг до изменений; в `variables.tf` его не перенесли: проверки переменных там нарочно со спецсимволами — ловят пропущенный `urlencode`.
- **Pull образа — своим шагом до паролей.** Окно смены — от шага паролей до замены API. Холодный pull (около минуты) шёл внутри `migrate.sh`; теперь он — шаг «Скачать образ API» перед паролями. Повторы миграций после `LockNotAvailable` (до 300 с) остаются внутри окна: поставить пароли после миграций нельзя — миграции входят паролем из `migrate_env`, а он из того же секрета.
- **Пароль — первой строкой stdin.** `docker exec -i … sh -c '<скрипт>'`: скрипт секретов не содержит, пароль читает `IFS= read -r` оболочки контейнера, дальше — `PGPASSWORD` у psql для входа, встроенным `printf` — в stdin `psql` и `rabbitmqctl` (он читает пароль со stdin, проверено на 4.4). В argv на раннере, в ssh и в `ps` сервера пароля нет. `-e VAR` у `docker exec` тоже не светил бы его в argv, но положил бы в конфиг exec у демона. Первый вариант слал `ALTER ROLE … PASSWORD :'new'` — открытый текст попадал в `log_min_duration_statement`, выборку запросов и `pg_stat_activity.query`, её видит `pg_monitor` из #130 (ревью). Теперь — `\password <роль>` и две строки пароля в stdin psql: без tty psql читает их оттуда и шлёт `ALTER USER … PASSWORD 'SCRAM-SHA-256$…'`. Проверено на pgvector:pg18 с `log_statement = all` и `log_min_duration_statement = 0`: открытого пароля в логе нет, только хеш. Так же переделан `replication-setup` (`\password replicator` последней строкой SQL; SQL — через `chomp`, иначе пустая строка стала бы первым ответом и psql отказал бы «Passwords didn't match» — поймано на dind).
- **После плана, до миграций.** Миграции и новый API входят уже новым паролем: `migrate_env` targeted apply шага «Поднять базу и брокер» обновляет и без изменений ресурсов (`Changes to Outputs: ~ migrate_env`, проверено). После плана — чтобы отклонённый план пароль не менял: окно открывается, только когда до apply остались миграции.
- **Окно.** Смена пароля в PostgreSQL и `change_password` открытые соединения не рвут (проверено: долгая сессия psql и AMQP-соединение со старым паролем живы после смены), новые со старым — отклоняются. От шага паролей до SIGTERM старому API в полном apply старые API и воркер работают на открытых соединениях пула и не открывают новых. Замер на dind после ревью, с новым digest образа (pull настоящий, 0,2 с из локального реестра, до окна): база — 2,7 с от смены до SIGTERM старому API (миграции 1,5 с и начало apply) и 3,2 с замены API; последовательные запросы по открытому соединению не падали, из 12 параллельных 6 получили `500`; брокер — 2 с. На стенде окно — шаг миграций по ssh (с повторами — до 5 мин) и начало apply.

## Risks / Trade-offs

- Миграции упали после смены — apply не идёт, и старые API и воркер до следующего деплоя без новых соединений. Откат — вперёд: повторный деплой («совпадает» и дальше как обычно) или руками вернуть роли пароль старого API (`\password`, `infra/README.md`, «Откат»). Секрет старым значением не вернуть: GitHub его не отдаёт.
- Воркер, дорабатывающий сообщение во время смены (до 41 мин), живёт на открытых соединениях; понадобится новое — это сообщение упадёт.
- В `env` контейнеров базы и брокера и в состоянии остаётся пароль инициализации тома. Он больше не действует, но `docker inspect` его показывает — не принимать за текущий; проверку «старый не принимается» README делает адресами старого API, сохранёнными до деплоя.
- Текущий секрет на стенде с пробелом или не-ASCII уронит первый деплой после мёржа на шаге паролей, до изменений; тогда пароль меняют по runbook. Такой секрет и сейчас не работал бы: пробел ломает URL.
