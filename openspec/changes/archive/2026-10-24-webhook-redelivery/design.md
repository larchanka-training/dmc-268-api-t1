## Context

Приём (`handle_webhook_event`) отсекает повтор только по активному прогону (`find_active`). Прогон, дошедший до `completed`, повтор не видит, и тот же коммит ревьюится второй раз (#75). GitHub ждёт ответа на доставку 10 секунд, неудачные доставки сам не повторяет; переотправка через API доступна три дня и сохраняет `X-GitHub-Delivery` (`guid`). Запуск ревью — только `opened` и `synchronize`, поэтому тот же `head_sha` ещё раз — это повтор доставки или force-push обратно на уже отревьюенный коммит. Ручного повторного ревью (`trigger = manual`) в коде пока нет.

Воркер раз в минуту делает проход обслуживания (`build_maintenance`): зависшие прогоны, истёкшие сессии. Реквизиты GitHub App уже в настройках, JWT подписывает `GitHubAppAuth.app_jwt`.

## Goals / Non-Goals

**Goals:**

- Ни одно событие, запускающее ревью или синхронизацию треда, не теряется из-за нашего временного не-2xx.
- Повтор доставки, в каком бы статусе ни был прогон первой (кроме `failed`), не даёт второго ревью.
- Повтор не нагружает API GitHub и не требует новой таблицы.

**Non-Goals:**

- Таблица ключей идемпотентности `X-GitHub-Delivery`: повтор после нашего сбоя постановки пришёл бы с тем же ключом и был бы отброшен — ревью не было бы никогда.
- Блокировка «один воркер на проход повтора»: несколько воркеров появятся позже, дубль переотправки безвреден (D4).
- Отсев устаревших доставок в приёме: свежая доставка проверку головы PR не проходит (D5).

## Decisions

### D1. Дубль — завершённый не-`failed` прогон по вебхуку на тот же коммит

`ReviewRunRepository.find_reviewed(merge_request_id, head_sha)` — самый поздний прогон с источником `webhook` в терминальном статусе, кроме `failed` (`REVIEWED_STATUSES` в `app/domain/enums.py`, рядом с `TERMINAL_STATUSES`). Проверяется в той же транзакции и там же, где `find_active`, — до upsert'а merge_request, исход `duplicate`, 202 с проекцией найденного прогона. `failed` не блокирует: прогон после сбоя постановки, сбоя модели или выметенный — повтор должен дать новый. Источник `webhook` в фильтре — чтобы будущее явное повторное ревью (`manual`) не делало дублем доставку нового события. Частичные уникальные индексы и `ActiveRunConflict` не меняются: хранилище по-прежнему разрешает прогон после терминального, решение — в приёме. Альтернатива — ключ по `X-GitHub-Delivery` — отвергнута (Non-Goals).

### D2. Что переотправлять — чистая `select_redeliveries`

Вход — список доставок (`WebhookDelivery`: `id`, `guid`, `delivered_at`, `redelivery`, `status`, `status_code`, `event`, `action`), `now` и `RedeliveryPolicy` (`max_attempts`, `backoff`, `limit`, `window`). Решение:

- доставки группируются по `guid` («constant across redeliveries of the same delivery» — документация GitHub, пример скрипта переотправки);
- группа с успешной попыткой пропускается. Успех — `status == "OK"` (так определяет пример GitHub) или код 2xx;
- только события приёма: `pull_request` `opened`/`synchronize`, `pull_request_review_thread` `resolved`/`unresolved`;
- только моложе `window` (3 дня минус час запаса: доставку старше трёх дней GitHub не переотправит, а проход идёт не мгновенно);
- число попыток — число доставок группы с `redelivery = true`; не больше `max_attempts`;
- пауза: последняя попытка группы + `backoff × 2^попыток` ≤ `now`;
- переотправляется последняя попытка группы, самые старые группы первыми; функция отдаёт всех подходящих, а `limit` считает сценарий по настоящим переотправкам (D5) — иначе отсеянные после выбора кандидаты занимали бы места.

Самые старые первыми — чтобы после простоя доставки одного PR приходили в порядке push'ей и merge_request заканчивал на последнем коммите. Состояния нет: всё выводится из списка доставок, поэтому новая таблица не нужна, а рестарт воркера ничего не сбрасывает.

### D3. Порт `WebhookDeliveries` и адаптер `GitHubWebhookDeliveries`

Чужая внешняя система — порт (правило «Швы и порты»): `list_recent(since) -> list[WebhookDelivery]` и `redeliver(delivery_id)`. Адаптер — `GET /app/hook/deliveries?per_page=100` с JWT приложения, следующая страница — по `Link: rel="next"` (курсор `cursor`), стоп — последняя доставка страницы старше `since` или 10 страниц. Без фильтра `status=failure`: успешные попытки нужны, чтобы не повторять уже доставленное, а `failure` у GitHub — только коды 400–599, без тайм-аутов. Переотправка — `POST /app/hook/deliveries/{id}/attempts`, успех — 202. Отказы — как у `GitHubInstallationCatalog`: сеть, 429, 5xx, 403 лимита — `VcsUnavailableError`; 401 — `VcsAuthError`; прочее — `VcsError`. Тело — строгие модели pydantic, лишние поля игнорируются.

Третий метод порта — `delivery_payload(id)`: `GET /app/hook/deliveries/{id}`, из тела читается только `request.payload` (объект или `null`).

Сценарий `redeliver_failed_webhooks` (слой приложения): список, решение, сверка устаревания (D5), переотправки по одной. Временный сбой любого запроса (`VcsTransientError` в домене, его наследник — `VcsUnavailableError`: лимит, сеть, 5xx) завершает проход: вторичные лимиты GitHub считаются на токен, долбить дальше нельзя. Прочий `VcsError` (например, 422 — доставка уже слишком старая, 404 — PR исчез) — предупреждение в лог и пропуск кандидата.

### D4. Проводка и настройки

Шаг повтора — третий в `build_maintenance`, со своим интервалом (`WEBHOOK_REDELIVERY_INTERVAL_SECONDS`, 300 с): проход обслуживания идёт раз в минуту, повтор — реже. Сбой шага логируется и отмечается на спане `review.sweep`, как у соседних шагов. По умолчанию `max_attempts = 5`, `backoff = 300 с` (5, 10, 20, 40, 80 минут — переживает простой около 2,5 часов), не больше 10 переотправок и 10 страниц за проход. На кандидата `pull_request` — до трёх запросов (payload, голова PR, переотправка), поэтому проход ещё ограничен бюджетом времени по монотонным часам (`WEBHOOK_REDELIVERY_PASS_BUDGET_SECONDS`, 30 с): он проверяется перед каждым кандидатом, истёк — INFO в лог, остальные ждут следующего прохода. Проход идёт внутри consume-цикла, и бюджет не даёт ему надолго остановить обработку сообщений; запрос, начатый до истечения, дорабатывает (худший случай — бюджет плюс таймауты одного кандидата). Повтор включён по умолчанию (`WEBHOOK_REDELIVERY_ENABLED=true`), но без `GITHUB_APP_ID` или ключа шаг не собирается, и при старте — одна строка INFO.

Несколько воркеров могут переотправить один `guid` в одном окне: приём ответит существующим прогоном (D1), а лишняя попытка лишь быстрее исчерпает `max_attempts`.

### D5. Устаревшая доставка не переотправляется

Push A упал 5xx, push B прошёл: повтор A не нашёл бы ни активного, ни завершённого прогона на A, приём откатил бы head merge_request на A, и модель отревьюила бы старый коммит. Поэтому у кандидата `pull_request` проход читает payload доставки (`pull_request.head.sha`, номер, `repository.full_name`, `installation.id` — той же `extract_github_event`, что и приём) и свежую голову PR через `VcsGateway.fetch_pr_metadata` (installation token). Голова другая — не переотправляется, INFO «доставка устарела: голова PR уже другая». Payload без PR — не переотправляется. `pull_request_review_thread` — без сверки: головы у него нет, а закрытие треда от коммита не зависит.

Признанные устаревшими (и «payload без PR») `guid` запоминаются во множестве в памяти процесса — в замыкании шага `build_redelivery` — и в следующих проходах пропускаются без запросов: доставка не перестаёт быть устаревшей, а без памяти она трое суток раз в пять минут стоила бы два запроса и, будучи старой, стояла бы в начале списка. Лимит `max_per_pass` считает только переотправки, поэтому десяток устаревших не вытесняет свежую доставку. Туда же попадает кандидат с постоянным отказом (404 метаданных, 422 переотправки), а в начале прохода множество урезается до `guid` текущих кандидатов, так что не растёт. После перезапуска воркера множество пусто, и каждая устаревшая доставка проверяется заново один раз — это дешевле таблицы. У нескольких воркеров память своя у каждого.

Проверка — в проходе повтора, а не в приёме: сразу после push'а GitHub может ещё отдавать прежнюю голову, и свежая доставка потерялась бы молча; повтор идёт через минуты после сбоя (пауза ≥ 5 минут), когда метаданные уже сошлись.

## Risks / Trade-offs

- [Force-push обратно на отревьюенный коммит не ревьюится повторно] → код этого коммита уже отревьюен; merge_request при дубле не обновляется и до следующего push'а показывает прошлый head.
- [Устаревшая доставка] Закрыта сверкой головы PR в проходе повтора (D5). Остаётся окно между сверкой и обработкой переотправки приёмом: push в эти секунды — устаревший прогон, как и при обычной гонке доставок.
- [Свежая доставка, упавшая до сверки] Если упал и push B, после восстановления переотправляются обе: A отсеивается как устаревшая, B проходит.
- [Проверено на настоящем GitHub 2026-10-24, репозиторный API доставок с той же схемой `hook-delivery-item`] Порядок — новые первыми; `Link` с одним `rel="next"` и `cursor=v1_<id>`; `request.payload` у детали — объект; переотправка — `202` с `{}`, сохраняет `guid` и ставит `redelivery: true`; отказ соединения — `502` и `status` «failed to connect to host»; id ~3,85·10¹⁸ читаются точно. Настоящие ответы прогнаны через адаптер. Не проверено: авторизация JWT App на `/app/hook/deliveries` и `status` «OK» у успешной доставки.
