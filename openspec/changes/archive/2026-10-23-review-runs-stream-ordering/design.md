## Context

Продолжение `review-runs-list-contract` и `review-runs-stream-row-events`. Ручки остаются заглушками `501`. Правки касаются контракта и заметок для реализации задачи #103.

## Decisions

### D1. Равные `updated_at` — побеждает пришедшая позже версия

Нового поля версии в контракте нет. Клиенту хватает правила «больший `updated_at`, при равном — пришедшая позже», если сервер гарантирует строгий рост `updated_at` (см. заметки для реализации).

### D2. Имена событий — компонент-enum

`ReviewRunsStreamEventType` — `RootModel` над `Literal` с именами событий. Он попадает в `components/schemas` через `extra_models`, как модели данных потоков. `x-sse-events` остаётся: он связывает имя события с моделью данных, а enum даёт фронтенду тип имени.

### D3. Вход времени — только ISO 8601

В lax-режиме pydantic принимает unix-время числом в строке. `strict` здесь не подходит: в query всё приходит строками, а strict ждёт экземпляр `datetime`. Поэтому `UtcDatetimeParam` проверяет начало строки по форме ISO 8601 (`BeforeValidator`) и только потом передаёт её pydantic.

### D4. Страж времени исключает ровно параметры операций

`test_every_date_time_in_the_schema_is_utc_datetime` пропускает узлы под `/paths/<путь>/<метод>/parameters/`. Префиксы он собирает из самой схемы. Шаблон вида `^/paths/[^/]+/…` не подошёл бы: путь операции сам содержит слеши, а `_walk` склеивает ключи через `/`.

## Заметки для реализации (#103)

- **`updated_at` строго растёт.** Метод `ReviewRunRepo.update` (адаптер `SqlAlchemyReviewRunRepo`) при каждой записи ставит `updated_at = GREATEST(:now, updated_at + interval '1 microsecond')`. Так рост сохраняется, даже если часы API и воркера расходятся.
- **Имя события выводится в одном месте.** Имя (`run.status_changed` или `run.finished`) выводится из нового статуса там же, в адаптере, рядом с `pg_notify`. Тогда правило «при итоговом статусе — только `run.finished`» держится при любом числе мест, где пишется статус.
- **`LISTEN` раньше заголовков.** Подписка на уведомления оформляется до отправки заголовков ответа потока. Клиент запрашивает снимок после события `open`, то есть после заголовков, — значит, подписка к этому моменту уже действует, и событие между снимком и подпиской не потеряется.
