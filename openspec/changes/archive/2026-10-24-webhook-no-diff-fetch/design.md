## Context

Приём вебхука (`handle_webhook_event`) вызывал `fetch_pr_metadata`, затем `fetch_diff` той же парой SHA, что уходит в задачу, — только чтобы сбой VCS дал 502 до создания записей. Воркер на шаге `fetching_diff` достаёт тот же дифф заново (`fetch_review_diff`). У `GitHubVcsGateway.fetch_diff` нет лимита размера, хотя у `fetch_file` он есть: `_get(..., max_bytes=…)` читает тело потоком и обрывает его на лимите (`VcsFileTooLargeError`), с проверкой объявленной длины и распакованного потока.

GitHub ждёт ответа на доставку 10 секунд и неудачные доставки сам не повторяет; ручная или API-переотправка в пределах трёх дней сохраняет `X-GitHub-Delivery`. Автоматическую переотправку делает задача #149.

## Goals / Non-Goals

**Goals:**

- Ответ на доставку не зависит от размера PR: приём делает один запрос к VCS — метаданные.
- Ни один дифф не читается в память без предела.
- Слишком большой дифф — понятный терминальный исход прогона, а не обрезанное ревью.

**Non-Goals:**

- Переотправка неудачных доставок (#149).
- Ревью большого PR по частям или по файлам.
- Хранение кода сбоя в самом прогоне: код остаётся у шага (`review_run_steps.error_code`), у прогона — текст `failure_reason`.

## Decisions

### D1. Приём не качает дифф

Метаданные остаются: из них берётся `base_sha` задачи, и их сбой даёт 502, как раньше. Сбой получения диффа (force-push убрал коммит, 5xx GitHub) теперь проявляется в воркере: шаг `fetching_diff` — `failed` с кодом из `VcsError.code`, прогон — `failed`. Альтернатива — HEAD-запрос или compare без тела ради «раннего 502» — отвергнута: compare GitHub считает дифф целиком и на большом PR медленный при любом формате ответа, а раннее 502 не спасает доставку — GitHub её всё равно не повторит.

### D2. Лимит — у вызова порта, значение — из настроек

`VcsGateway.fetch_diff(..., *, max_bytes: int)` — обязательный аргумент, как у `fetch_file`: у порта нет вызова без лимита. Адаптер передаёт его в существующий `_get(..., max_bytes=…)` — тот же потоковый обрыв, что у файлов. Значение — `Settings.diff_max_bytes` (`DIFF_MAX_BYTES`, 5 МиБ по умолчанию: десятки тысяч строк диффа, на порядок больше, чем помещается в пакет контекста при `CONTEXT_MAX_TOKENS=32000`), в слой приложения приходит через `ContextLimits.diff_max_bytes`, как остальные лимиты воркера.

### D3. Превышение — `DiffTooLargeError` с кодом `DIFF_TOO_LARGE`

`fetch_review_diff` переводит `VcsFileTooLargeError` адаптера в `DiffTooLargeError` (наследник `VcsFileTooLargeError`, домен) с кодом `DIFF_TOO_LARGE` и сообщением «дифф PR больше лимита N байт: ревью не выполняется». Дальше работает общий путь сбоя прогона: шаг `fetching_diff` закрывается `failed` с этим кодом (`error_code` читает `code` у `VcsError`), прогон — `failed` с `failure_reason` из сообщения, сообщение очереди — в DLQ (`nack` без `requeue`). Повторная доставка того же сообщения находит терминальный прогон и ничего не делает, так что повтора нет. Код свой, а не `SCM_UNAVAILABLE`: VCS ответила исправно, и повтор не поможет — как `PROMPT_TOO_LARGE` у модели. Код добавляется в каталог §8 и в `ReviewErrorCode` (тест контракта требует, чтобы каждый код шага был в каталоге).

### D4. Инкрементальный дифф тредов — с тем же лимитом, без сбоя

Публикация сравнивает прошлый head с текущим, чтобы подтвердить, что строка якоря критичного замечания изменилась (`_hunks_between_commits`). Этот запрос тоже ограничивается `diff_max_bytes`. Превышение не роняет уже готовое ревью: hunk'ов нет — изменение строки не подтверждено, и тред критичного замечания со статусом `fixed` не закрывается автоматически (его закроет человек); остальные исходы не зависят от этих hunk'ов.

## Risks / Trade-offs

- [Сбой получения диффа больше не даёт 502 доставке] → он виден в прогоне (`failed`, шаг `fetching_diff` с кодом) и в кабинете; 502 доставки GitHub всё равно бы не повторил.
- [PR больше 5 МиБ диффа не ревьюится вовсе] → лимит настраивается; ревью по частям — вне этого изменения.
- [Не проверено запуском] Как GitHub отвечает compare-диффом на очень большой PR (собственные пределы, 406 или усечение), здесь не проверялось: на любом не-2xx ответе адаптер даёт `VcsError`, как раньше.
