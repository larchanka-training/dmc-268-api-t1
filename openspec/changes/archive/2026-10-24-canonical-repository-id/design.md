## Context

Подключение берёт репозиторий запросом `GET /repositories/{provider_id}` токеном пользователя. GitHub разбирает id как число: ведущие нули и знак `+` дают тот же репозиторий, а в ответе `id` — каноническое число. Вебхук и видимость сравнивают `provider_id` со строкой `str(id)` из ответов GitHub.

## Goals / Non-Goals

**Goals:**

- В `repositories.provider_id` попадает только канонический id GitHub.
- Неканонический ввод не уходит к GitHub.

**Non-Goals:**

- Исправление уже записанных неканонических id миграцией: на стенде проверяем запросом, правим по результату.

## Decisions

### D1. Отказ на входе и id из ответа — оба

Шаблон `^[1-9][0-9]*$` на поле запроса отсекает неканоническую запись до GitHub и описывает формат клиенту в схеме. Нормализация на входе (`str(int(...))`) отвергнута: она молча принимает то, что клиент не должен присылать, — список доступных отдаёт id уже каноническими. Запись `found.provider_id` из ответа нужна сверх шаблона: источник правды об id — GitHub, и use case не зависит от проверки слоя API.

### D2. ASCII-цифры в адаптере

`str.isdigit()` принимает `"²"` и `"١٢٣"`; адаптер проверяет `isascii() and isdigit()`. Ведущие нули адаптер не отсекает: их отсекает API, а use case берёт id из ответа.

### D3. Фейк каталога ищет по числу

Фейк сравнивал id строкой и не воспроизводил поведение GitHub, поэтому тест с `"0101"` не мог быть красным. Теперь он находит репозиторий по числовому значению ASCII-цифр, как GitHub.

## Risks / Trade-offs

- Клиент, который присылал id с ведущими нулями, получит `422` — так и задумано; фронтенд берёт id из списка доступных.
