# Design: доступ к репозиториям по роли пользователя

## Context

Мотивация — в `proposal.md`. Решения change `implement-repository-connect` остаются в силе, кроме D3 (список не фильтруется), порядка проверок в D4 и правила «admin — `permission == "admin"`» в D2: их заменяют решения ниже.

## Goals / Non-Goals

**Goals:**

- Список не раскрывает пользователю репозитории, которых он не видит в GitHub.
- Отказ подключения не раскрывает пользователю без прав, подключён ли репозиторий.

**Non-Goals:**

- Кэш ролей и списка установок — см. D2.
- Ограничение входа организацией.
- Поле «можно подключить» в ответе списка: схема ответа не меняется.

## Decisions

### D1. Список — по доступу, подключение — admin или maintain

Это уточнение решения 3A из larchanka-training/dmc-268-ui-t1#37, где подключать мог только admin, а список не фильтровался.

- **Видеть в списке** может пользователь с любым доступом к репозиторию в GitHub, в том числе read: он видит только то, что и так видит в GitHub. Нет доступа — репозитория в ответе нет, без ошибки.
- **Подключать** может роль admin или maintain. Maintain по замыслу GitHub — управление репозиторием без опасных настроек (удаление, видимость, передача, доступы), подключение к ревью именно такое действие. Пользовательские роли организации подключать не могут: что они разрешают, по имени не сказать.

Порт отдаёт роль, а не решение: `InstallationCatalog.user_role(repository, login) -> RepositoryRole | None`, `None` — доступа нет. Тип `RepositoryRole` — в `app/domain/enums.py`, решения — чистые функции `can_see` и `can_connect` в `app/domain/repository_access.py`. Адаптер только переводит ответ GitHub в роль.

Пользователь с доступом ниже maintain видит репозиторий в списке, а подключение отвечает ему `403`: кабинет не может заранее отличить его от того, кто подключить может, — в схеме ответа такого поля нет, и добавлять его здесь не стали.

### D2. Стоимость: запрос роли на каждый репозиторий

Use case спрашивает роль для каждого репозитория установок, последовательно, без потоков. Стоимость показа экрана — `1 + I` запросов на список (I — число установок, плюс страницы) и `N` запросов ролей (N — число репозиториев установок). Лимит GitHub для installation token — 5000 запросов в час на установку: экран, открытый для установки со 100 репозиториями, съедает 2% часового лимита, которым делятся вебхуки и публикация ревью. Сбой любого запроса (`VcsError`) — `502 SCM_UNAVAILABLE`: частичный список выдал бы сбой GitHub за отсутствие доступа.

Кэш ролей пока не вводим. Роли меняются в GitHub без уведомления сервиса, и устаревший кэш показывал бы репозиторий тому, у кого доступ уже отозван, — ровно то, что эта правка закрывает. Ему нужен TTL и инвалидация, а `CacheStore` сейчас один на процесс в памяти. Вводим, когда реальные установки упрутся в лимит или во время ответа.

### D3. Роль из ответа GitHub

`GET /repos/{owner}/{repo}/collaborators/{login}/permission`, по документации GitHub «Get repository permissions for a user»: `permission` несёт устаревшие базовые роли admin, write, read, none — maintain в нём отдаётся как write, triage — как read; полное имя роли, включая пользовательские, — в `role_name`. Адаптер берёт `role_name`, а если его нет — `permission`. `none` и `404` — доступа нет (`None`); незнакомое имя — `RepositoryRole.CUSTOM`. Без `role_name` maintain не отличить от write, и подключение такому пользователю будет отказано: лишних прав лучше не дать.

### D4. Порядок проверок подключения

`connect_repository`: провайдер не `github` или репозитория нет в установках — `404 REPOSITORY_NOT_IN_INSTALLATION`; роль не admin и не maintain — `403 REPOSITORY_MANAGE_REQUIRED`; уже зарегистрирован, в том числе параллельным запросом, — `409 REPOSITORY_ALREADY_CONNECTED`; иначе `201`. Пользователь без прав получает `403` и не узнаёт, подключён ли репозиторий. Цена — запрос роли и на повторное подключение, которое всё равно кончится `409`. После запроса роли проверка «уже подключён» и запись — одна транзакция; гонку закрывает `RepositoryRepo.add` с `ON CONFLICT DO NOTHING`.

`404` на репозиторий не из установки по-прежнему раньше прав: роль на репозиторий вне установки спросить нечем, а установлено ли приложение на репозиторий, видно в GitHub любому, кто видит репозиторий.

Код отказа назван по праву, а не по роли: `REPOSITORY_MANAGE_REQUIRED` вместо `REPOSITORY_ADMIN_REQUIRED`.

## Risks / Trade-offs

- Время ответа списка растёт линейно с числом репозиториев установок (запрос роли — десятки миллисекунд). Для одной организации с десятками репозиториев — до секунды-двух.
- Пользователь с ролью ниже maintain видит репозиторий, но подключить не может, и узнаёт об этом только из `403`.
