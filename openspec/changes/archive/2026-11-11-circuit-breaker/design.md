## Context

Backoff на отдельный запрос уже есть: GitHub — три попытки на 5xx с паузой 0,5 и 1 с и ожидание
лимита по заголовкам (`GitHubVcsGateway._request`), модель — ротация ключей на `401/403/429` и
фоллбэк Ollama → Eurorouter. Чего нет — памяти между прогонами: каждый прогон при лежащем
провайдере снова ждёт таймауты (у модели — до `LLM_TIMEOUT_SECONDS` на вызов) и падает в DLQ.

У воркера есть решение по сообщению `decide` (ACK / RETRY / DEAD_LETTER, #157). RETRY возвращает
сообщение `basic.reject` с тратой попытки доставки (лимит 5): для долгого сбоя он не годится.

## Decisions

**D1. Что считается отказом.** Отказ — провайдер не ответил: обрыв сети, таймаут, 5xx (у GitHub —
5xx или сеть до конца попыток адаптера). Любой ответ — даже с ошибкой — значит, что провайдер жив,
и breaker замыкает:

| Провайдер | Отказ | Ответ (не отказ) |
|---|---|---|
| GitHub | `httpx.RequestError`, 5xx после 3 попыток, сеть или 5xx при выдаче installation token | 2xx, 3xx, 4xx (включая 401, 404, 422), `429`/`403` лимита — и исчерпанный бюджет ожидания лимита |
| Ollama, Eurorouter | таймаут, обрыв, 5xx | 2xx, 4xx, `401/403/429` на всех ключах (`LLM_RATE_LIMITED`), ответ не по схеме, битое тело |

Лимит — не отказ: провайдер отвечает, а ждать его — дело backoff'а по заголовкам; разомкнутый на
лимит breaker отложил бы прогоны на минуты там, где GitHub просит секунды. Адаптер переводит
отказ в свой класс — `VcsOutageError` (наследник `VcsUnavailableError`) и `LlmUnavailableError`
(предок `LlmTimeoutError`, код `LLM_UNAVAILABLE`), — а исход в breaker пишет одно место:
`GitHubVcsGateway._request` и `FallbackLlmGateway`. Коды шагов прогона не меняются, кроме одного:
5xx на выдаче installation token — теперь `SCM_UNAVAILABLE`, а не `SCM_AUTH_ERROR`. Иначе в долгом
сбое GitHub с истёкшим кэшем токенов каждый прогон замыкал бы breaker ответом «auth» и падал, а
не откладывался (замечание ревью).

**D2. Машина состояний — в домене, часы — инъекцией.** `app/domain/circuit_breaker.py` — запись
`Breaker` и чистые `failed`, `state`, `retry_after` от монотонного времени; ответ провайдера
возвращает `CLOSED`.
`app/application/circuit_breaker.py` — `CircuitBreaker` с блокировкой и часами: один на провайдера
в процессе, общий для потоков (обработчик и проход очистки зовут один GitHub). Ни домен, ни
приложение не знают httpx — проверяет `lint-imports`.

**D3. Параметры.** Порог — 3 отказа подряд: моргнувший провайдер прогоны не откладывает. Пауза —
60 с, после неудачной пробы удваивается до 10 минут: при часовом отказе проб около 8, а не 60.
Half-open не ограничивает вызовы одним: в воркере прогон идёт по одному, а лишний флаг «проба в
полёте» мог бы залипнуть, если исход не дошёл. Отказ вызова, начатого до размыкания, паузу не
продлевает. Константы — в `container.py` (`BREAKER_POLICY`), не в окружении: менять их на стенде
пока незачем.

**D4. Отложить — до захвата.** `run_review` после чтения прогона и проверки, что он `queued`,
спрашивает `paused_for()` (`deferral`): GitHub на паузе или на паузе все провайдеры модели —
`ReviewDeferred(retry_after)`, прогон не захвачен и остаётся `queued`, шаги не пишутся. Один
провайдер модели из двух на паузе — прогон идёт, фоллбэк пропускает лежащего без таймаута.
Терминальный или чужой прогон подтверждается, как раньше.

**D5. Возврат без траты попытки.** `decide` даёт `DEFER`: воркер ждёт до пробы, но не дольше
`MAX_DEFER_SECONDS` (60 с, циклом соединения — heartbeat идёт, сигнал остановки прерывает), и
возвращает сообщение `basic.nack` с requeue. С RabbitMQ 4.3 quorum-очередь не увеличивает за него
`delivery-count` (`basic.reject` — увеличивает); у нас 4.4 на стенде, в compose и в CI. Chaos-тест
проверяет это на брокере: отложенное сообщение возвращается больше `DELIVERY_LIMIT` раз и не
уходит в DLQ. Потолок 60 с — чтобы проход очистки и остановка не ждали всю 10-минутную паузу.

**D6. Наблюдаемость.** Gauge `review_circuit_breaker_state{provider}` (0 замкнут, 1 ждёт пробы,
2 разомкнут) читает состояние на сборе. Алерты горят 15 минут **и** при задачах в `review_jobs.qq`:
без второго условия ночной сбой без трафика горел бы до утра — пробовать нечем. Условие
«прогоны откладываются» для `ProviderCircuitOpen` — не замкнут breaker GitHub или всех
провайдеров модели (`min` по ним). Тогда — `ProviderCircuitOpen` (critical): ревью стоят. Один
провайдер модели лежит, другой отвечает — `LlmProviderCircuitOpen` (warning, service
`llm-provider`): сервис жив, но для Ollama это ещё и код, ушедший Eurorouter. `WorkerStalled` и
`ReviewJobStuck` глушатся только условием откладывания, как в `deferral`: breaker разомкнут (2)
за последние 15 минут — `max_over_time` держит паузу между пробами 2 → 1 → 2. Застрявшее «ждёт
пробы» (1) их не глушит: пробный вызов уже можно делать, и если его нет, а задачи лежат, воркер
завис. Отложенные сообщения не подтверждаются, но при живом фоллбэке зависание воркера должно
быть видно. Breaker у каждого экземпляра воркера свой (#99, лейбл `instance`): глушит, только
когда откладывают все экземпляры, иначе разомкнутый breaker одного прятал бы зависание остальных.

**D7. Только воркер.** API собирает контейнер без breaker'ов: отказ вебхука GitHub переотправляет
сам, кабинет отвечает 502 — откладывать там нечего, а пауза в API глушила бы вебхуки после сбоя
одного чтения кабинета.

## Risks / Trade-offs

- **Первые прогоны и пробы падают.** Пока breaker не разомкнулся, прогоны падают как раньше (у
  модели — три подряд). Проба — настоящий прогон: если провайдер всё ещё лежит, он падает, и
  breaker размыкается на удвоенную паузу. Отдельный health-probe у провайдеров (`/api/version`,
  `/models`) проверял бы не тот путь, что `/chat/completions`; остаёмся на живом трафике.
- **Breaker — на процесс.** Несколько воркеров (#99) размыкаются каждый своим трафиком; gauge —
  по процессу, алерт берёт худший (`max by (provider)`).
- **Ряды gauge экземпляра истекли.** Алерты зависания сравнивают откладывающие экземпляры с
  теми, у кого есть ряды gauge за 15 минут. Если у экземпляра ряды пропали (коллектор перестал их
  получать), а остальные откладывают, `WorkerStalled` и `ReviewJobStuck` молчат. Случай редкий:
  такой экземпляр не шлёт и остальные метрики, и это видно по `ContainerDown` и дашборду.
  Сравнение с числом потребителей очереди закрыло бы и его, но не проверено.
- **Долгий отказ дольше `QUEUED_RUN_TIMEOUT_SECONDS` (6 ч)** — отложенный прогон выметается в
  `failed`, как любой ждущий.
- **Прогон, захваченный до размыкания**, на паузе падает быстро (`SCM_UNAVAILABLE`,
  `LLM_UNAVAILABLE`) вместо ожидания таймаутов. Вернуть захваченный прогон в `queued` машина
  состояний не умеет; менять её ради этого не стали.
