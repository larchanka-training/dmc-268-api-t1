## Why

Общий поток событий `GET /api/v1/events` (#115) узнавал об изменениях прогонов опросом базы раз в секунду: каждое открытое соединение — свой запрос в секунду, даже когда ничего не меняется. Нагрузка на базу росла с числом открытых кабинетов без пользы. Задача #124.

## What Changes

- Адаптер `review_runs.add/update` отправляет `pg_notify('review_runs', id)` через соединение сессии единицы работы: уведомление уходит только при коммите, после `rollback` его нет. Места записи статуса (`handle_webhook`, `review_pipeline`, `stale_sweep`) не меняются.
- API слушает `LISTEN review_runs` одним соединением на процесс (`PostgresRunChanges`), открывает его при первой подписке и будит подписанные потоки.
- Поток читает изменённые прогоны прежним курсором (`list_changed`, `advance_feed`) только по сигналу; опроса раз в секунду больше нет. Сессия по-прежнему проверяется каждые 5 секунд, `ping` — в тишине раз в 15 секунд.
- Обрыв `LISTEN` закрывает открытые потоки; источник недоступен при подключении — поток из одной строки `retry: 3000`.
- События, их данные и контракт не меняются; меняется только описание источника.

## Capabilities

### Modified Capabilities

- `review-rest-api`: источник событий общего потока — NOTIFY вместо опроса.

## Impact

- Код: порт `RunChanges` (`app/application/ports/run_changes.py`), адаптер `app/infrastructure/db/run_changes.py`, `pg_notify` в `SqlAlchemyReviewRunRepo`, цикл `run_feed_events`, `app/api/events.py`, `Container.run_changes`/`aclose`, зависимость `get_run_changes` вместо `get_sleep`.
- Контракт: описание `GET /api/v1/events` (источник событий); схемы не меняются. Фронтенду правок не нужно.
- База: одно постоянное соединение на процесс API; чтения прогонов — по числу изменений, а не по времени.
