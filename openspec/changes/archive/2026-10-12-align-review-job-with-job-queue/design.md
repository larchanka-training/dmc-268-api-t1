# Design

## Context

После вливания #36 в `develop` в репозитории две реализации wire-формата
сообщения очереди: `develop` (`job_id` + `review_run_id`, спека `job-queue`)
и ветка #37 (`id` = идентификатор прогона + `installation_id`, спека
`webhook-intake`). Повторное объявление очереди адаптером с другими
аргументами дало бы `PRECONDITION_FAILED`; два формата тела — сообщения,
которые потребитель не разберёт. Договорённость по скоупу (лид, тред #37):
#37 владеет приёмом, #36 — обработкой, коннектор RabbitMQ берётся из
`develop`.

## Goals / Non-Goals

**Goals:**

- Один формат сообщения для приёма (#37) и обработки (#36): `job_id` — новый
  на каждую постановку, `review_run_id` — идентификатор прогона,
  `installation_id` — инсталляция для авторизации воркера.
- Спеки `webhook-intake` и `job-queue` в объединённом дереве не противоречат
  друг другу.

**Non-Goals:**

- Хранение `installation_id` в базе (change `add-installation-id-to-review-job`,
  D1: актуальное значение приезжает в каждом вебхуке).
- Изменения REST-контракта (`openapi.yaml`) и топологии очереди (DLX/DLQ —
  владелец #36).

## Decisions

- **D1 — коннектор из `develop`, формат `develop` + `installation_id`.**
  Альтернатива (дословно коннектор `develop`, без поля) отвергнута: теряется
  закрытый P1 ревью #37 — воркер не сможет авторизоваться installation-токеном
  за диффом, и спека `webhook-intake` разойдётся с кодом. Альтернатива
  (формат #37 целиком) отвергнута: ломает спеку `job-queue` и воркер
  `develop`, который различает постановки одного прогона по `job_id`.
  Цена: одна правка в wire-адаптере `develop` — перенос `installation_id`
  на верхнем уровне тела — и уточнение его wire-теста.
- **D2 — `job_id` генерирует use case приёма, а не адаптер.** Идентификатор
  сообщения — доменное данное (`new_id` приходит аргументом, тест сверяет
  точное значение); адаптер очереди содержимое не интерпретирует.
- **D3 — `review_run_id` несёт прогон, созданный в этой же доставке.**
  В `duplicate`/`conflict` задача не ставится вовсе, поэтому у уходящего
  сообщения всегда есть свежесозданный прогон.

## Risks / Trade-offs

- [Несовместимость формата с уже опубликованными сообщениями при деплое]
  → очередь опустошается деплоем; источник истины — `review_runs`, повторная
  доставка вебхука пересоздаёт задачу. Потребителей вне репозитория нет.
- [Две постановки одного прогона ставят два сообщения с разными `job_id`]
  → приемлемо и задумано: повторная доставка до постановки завершается
  `duplicate` без постановки; две постановки возможны только из гонки, где
  проигравшее сообщение воркер отбрасывает по отсутствию прогона (тикет
  воркера #36).

## Migration Plan

Деплой опустошает очередь; формат меняется атомарно с кодом приёма и
воркера. Откат — реверт-коммит (two-way door).
