# Proposal

## Why

Деплой бэкенда запускается по пушу в `develop` и не зависит от CI: оба workflow стартуют одновременно, и деплой не ждёт результата проверок. Защиты ветки `develop` нет, поэтому пул-реквест с красным CI можно влить, и он сразу уедет на стенд.

## What Changes

- Автоматический деплой запускается по завершении CI (`workflow_run`) и только если CI прошёл успешно на пуше в `develop`. Прогон CI по пул-реквесту из ветки с именем `develop` деплой не запускает.
- Отдельный job `gate` выбирает коммит для деплоя: `head_sha` прогона CI, а не `GITHUB_SHA` (у `workflow_run` это вершина ветки по умолчанию на момент запуска). Сборка образа и `tofu apply` берут код этого коммита.
- Деплой катит только вершину `develop`. Прогоны CI по `develop` не отменяют друг друга и могут закончиться не по порядку; без проверки поздно завершившийся CI старого коммита откатил бы стенд назад.
- Ручной запуск (`workflow_dispatch`) остаётся и CI не ждёт: это осознанное действие.

## Capabilities

### Modified Capabilities

- `backend-delivery`: новое требование — на стенд попадает только коммит, прошедший CI, и стенд не откатывается на более старый коммит.

## Impact

- `.github/workflows/deploy.yml` — триггер, job `gate`, коммит для checkout и тега образа.
- `workflow_run` срабатывает, только когда файл workflow лежит в ветке по умолчанию. Ветка по умолчанию — `develop`, поэтому новый триггер начнёт работать после мержа этого пул-реквеста.
