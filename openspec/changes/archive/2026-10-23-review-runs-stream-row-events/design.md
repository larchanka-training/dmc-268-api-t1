## Context

Продолжение change `review-runs-list-contract`: обе ручки остаются заглушками `501`. Здесь — правки контракта по ревью PR #105 и заметки для реализации задачи #103.

## Decisions

### D1. Данные любого события прогона — строка списка

`run.created`, `run.status_changed` и `run.finished` несут `ReviewRunListItem`. Фронтенду не нужно сливать частичные события со строкой: он делает upsert по `id`, а из двух версий строки оставляет ту, у которой больше `updated_at`. Тип события — только подсказка для интерфейса (подсветить новую строку, показать уведомление о завершении). При переходе в итоговый статус приходит одно событие `run.finished`, а не `run.status_changed` и `run.finished` подряд.

Порядок клиента — сначала поток, потом снимок: событие, которое придёт раньше ответа `GET /reviews`, не потеряется, а строка снимка, которая старше события, проиграет по `updated_at`.

Отдельные модели событий не нужны: `ReviewRunListItem` уже в `components/schemas`, его использует ответ списка. Связь события с моделью — расширение `x-sse-events` у `text/event-stream` в ответе потока, ссылками `$ref`. Генератор типов расширение пропускает, а тест контракта и читатель схемы его видят.

### D2. Время во входных параметрах — любая зона

`UtcDatetime` описывает форму ответа: UTC с `Z`, и `pattern` в схеме требует `Z`. Для входа он слишком строгий: сервер принимает и `+03:00`. Параметры дат — `UtcDatetimeParam` (время с зоной, приводится к UTC) без `pattern`. Страж `test_every_date_time_in_the_schema_is_utc_datetime` не проверяет параметры запроса: правило `Z` — про ответы.

### D3. Пустая строка в текстовом фильтре — без фильтра

У `q` и `author` одно правило: пустая строка — то же, что отсутствие параметра. Форма фильтров на фронтенде держит состояние в URL, и пустое поле не должно давать `422`. `min_length=1` пришлось бы обходить на клиенте.

### D4. Параметры списка — одна модель запроса

Обратный диапазон дат проверяет `field_validator` поля `created_to` в `ReviewRunListQuery` (`Annotated[ReviewRunListQuery, Query()]`). Ошибка приходит вместе с остальными ошибками схемы, в `query.created_to`, с причиной «начало диапазона позже его конца». В модель вошли и `limit` / `offset`: FastAPI раскладывает модель на параметры только тогда, когда других параметров запроса у операции нет. Если оставить их отдельными, модель стала бы одним параметром-объектом. `Limit` и `Offset` из `app/api/pagination.py` работают и как поля модели.

## Заметки для реализации (#103)

- **Видимость и точный `total`.** Правило видимости (решение А в dmc-268-ui-t1#43) и точный `total` требуют фильтра по множеству видимых репозиториев прямо в SQL: `repository_id IN (…)`. Отфильтровать страницу после запроса нельзя, иначе `total` и размер страницы врут. Множество видимых репозиториев считается на сессию и кэшируется с TTL. Без кэша на каждый запрос списка и на каждое событие потока уходило бы по N запросов к GitHub.
- **Откуда берётся множество.** Видимость считается по токену пользователя через `GET /user/installations` и репозитории установок (задача larchanka-training/dmc-268-api-t1#107, в работе), а не поштучными запросами роли на каждый репозиторий.
- **`repository_id` невидимого или несуществующего репозитория** — пустой список с `total = 0`, а не `404`: ответ не должен раскрывать, существует ли чужой репозиторий.
- **`id`, а не `review_run_id`.** В строке и в событиях общего потока прогон называется `id`, а в потоке одного прогона (`ReviewRunStatusEvent`) — `review_run_id`. Если экран прогона переведут на общий поток, старую модель не копировать: события общего потока — `ReviewRunListItem`.
