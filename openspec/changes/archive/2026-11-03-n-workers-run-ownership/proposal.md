# Proposal

## Why

Повторно доставленное сообщение для прогона в работе переводит живой прогон соседа в `failed`.
Два воркера на сообщении в `queued` оба начинают ревью: второй пишет тот же статус, и проверка
переходов его не останавливает. Очистка по устаревшему чтению роняет прогон, который уже
продвинулся, а две очистки роняют друг другу весь проход. Шаг закрывают воркер и очистка,
побеждает последний. Решение команды: #169, пункт 1, вариант (а).

## What Changes

- Первое действие обработчика: захват `queued → building_context` условной записью. Проиграл или
  прогон уже в работе: warning и ack, прогон не трогаем.
- `ReviewRunRepo.update` получает необязательный `previous`: статус и прогресс строки не как в нём
  дают `RunStateConflict`. Условны захват и очистка. Остальным записям хватает блокировки строки
  и запрета писать поверх терминального статуса: чужие записи после захвата делают только очистка,
  отмена и `_fail_unenqueued`, все терминальные.
- Очистка: чтение, затем условная запись каждого прогона своей транзакцией, конфликт пропускается.
- Шаг закрывается только поверх `running`: первый исход остаётся.
- `updated_at`: `clock_timestamp()` вместо `now()`, иначе запись после ожидания блокировки получает
  метку раньше коммита соседа.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `job-queue`: захват прогона, очистка без гонок.
- `review-pipeline`: повторная доставка прогона в работе, исход шага пишется один раз, очистка не
  меняет merge gate.

## Impact

- `app/application/review_pipeline.py`, `app/application/stale_sweep.py`, порт и адаптер прогонов и
  шагов, `app/infrastructure/db/base.py`, тесты, chaos-сценарии смерти воркера.
- Известные риски, цена варианта (а), все при смерти воркера посреди прогона (OOM, крэш, `SIGKILL`;
  обычный деплой сообщение дорабатывает):
  - коммит занят до очистки (порог `stale_run_timeout_seconds`, 30 минут), новый прогон сам не
    запускается. Раньше повторная доставка освобождала коммит сразу;
  - смерть не видна в DLQ, остаются warning и `review_runs_total{status="failed"}`;
  - очистка не трогает check run (живой воркер выставляет его сам): на head может остаться прежний итог до следующего push, на паузе
    PR без check. Требование сужено, исправление: #331.
- `pool_size` воркера не меняется: на корректность не влияет, отдельная настройка окружения.
- Закрывает #156 и #91.
