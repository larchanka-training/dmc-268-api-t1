## MODIFIED Requirements

### Requirement: У упавшего прогона нет шагов в работе

Перевод прогона в `failed` сбоем в воркере и очисткой зависших SHALL закрывать шаги, оставшиеся `running`: шаг, чей исход воркер знает, но не записал, — этим исходом, прочие — `failed` с `REVIEW_RUN_STALE`, длительностью от начала шага по стенным часам, без токенов. Закрытие SHALL идти своим коммитом после перевода, его сбой SHALL логироваться и SHALL NOT отменять перевод.

#### Scenario: Очистка зависшего прогона

- **WHEN** воркер умер посреди этапа `analysing`, и очистка переводит прогон в `failed` через час после начала шага
- **THEN** шаг `analysing` — `failed` с `error_code = REVIEW_RUN_STALE` и длительностью 3600 секунд, прочие шаги не меняются

#### Scenario: Повторная доставка незавершённого прогона

- **WHEN** воркер умер посреди этапа `analysing`, брокер доставил сообщение снова, а затем сработала очистка
- **THEN** повторная доставка прогон не меняет, очистка переводит его в `failed`, шаг прошлой попытки — `failed` с `error_code = REVIEW_RUN_STALE`

#### Scenario: Исход упавшего шага не записался

- **WHEN** вызов модели на ревью упал с `LLM_UNAVAILABLE`, а запись исхода шага `analysing` не удалась
- **THEN** прогон — `failed`, шаг `analysing` — `failed` с `error_code = LLM_UNAVAILABLE`

#### Scenario: Сбой закрытия шагов

- **WHEN** очистка переводит прогон в `failed`, а запись его брошенных шагов не удалась
- **THEN** сбой попадает в лог, прогон — `failed`

### Requirement: Упавший прогон после ревью head блокирует merge gate

Прогон, упавший в воркере последним на своём head-коммите, SHALL выставить check run `failure`, если до него на этот head-коммит уже был прогон `completed` или `cancelled` по вебхуку: прежний прогон мог оставить `success` по старому диффу. Без прежнего прогона на head упавший прогон SHALL NOT выставлять check run. На паузе ревью вместо этого действует требование «Прогон при паузе ревью не блокирует merge gate». Сбой GitHub SHALL попадать в лог и SHALL NOT подменять ошибку прогона.

#### Scenario: Ревью после смены ветки упало, поправка не дошла

- **WHEN** на head `success` прежнего прогона по старой ветке, а прогон нового диффа упал
- **THEN** на head выставляется `failure` «Ревью не удалось»

#### Scenario: Первое ревью коммита упало

- **WHEN** ревью не на паузе, прогон упал, а других прогонов на этот head-коммит нет
- **THEN** check run не выставляется, на PR ничего не появляется

#### Scenario: За head отвечает более поздний прогон

- **WHEN** прогон упал, а на этот head-коммит уже создан более поздний прогон
- **THEN** упавший прогон check run не выставляет

### Requirement: Ревью упавшего прогона не дублируется следующим

Перед публикацией находок прогон SHALL искать на GitHub ревью своего бота с маркером каждого прогона своего PR, упавшего на `publishing` без записей в `published_comments` позже последней записи PR, и SHALL записывать найденное этому прогону, сопоставляя inline по файлу, стороне, строке и тексту. Поиск SHALL быть best-effort: сбой хостинга и параллельный подбор SHALL NOT останавливать публикацию.

#### Scenario: Воркер умер после записи ревью на GitHub

- **WHEN** GitHub записал ревью прогона, воркер умер до записи `published_comments`, очистка перевела прогон в `failed`, и новый прогон того же PR снова нашёл замечание к той же строке
- **THEN** новый прогон записывает ревью упавшего в `published_comments`, своего inline-комментария к этой строке не публикует, а находку связывает с находкой треда

#### Scenario: Упавший прогон ничего не опубликовал

- **WHEN** прогон упал на `publishing`, а ревью с его маркером на GitHub нет
- **THEN** записей для него не появляется, новый прогон публикует замечание как обычно

#### Scenario: Поиск ревью упавшего прогона не удался

- **WHEN** GitHub отвечает ошибкой на поиск ревью упавшего прогона
- **THEN** сбой попадает в лог, новый прогон публикует ревью и завершается `completed`

#### Scenario: Две находки упавшего прогона на одной строке

- **WHEN** у упавшего прогона две находки на одной строке, а опубликована была одна (другую покрыл тред)
- **THEN** id комментария записывается находке с тем же текстом

#### Scenario: Упавший прогон старше опубликованного

- **WHEN** после падения прогона другой прогон PR опубликовал ревью
- **THEN** следующие прогоны ревью упавшего на GitHub не ищут

#### Scenario: Выметатель перевёл прогон в failed после чужой публикации

- **WHEN** прогон записал ревью на GitHub и умер на `publishing`, следующий прогон PR опубликовал своё, не видя его упавшим, и только потом выметатель перевёл первый в `failed`
- **THEN** следующий прогон находит ревью первого и записывает его, а не публикует замечание второй раз

#### Scenario: Два прогона подбирают одно ревью

- **WHEN** два прогона PR одновременно нашли ревью одного упавшего прогона, и второй получил отказ уникального индекса
- **THEN** второй откатывает подбор и публикует своё ревью

## ADDED Requirements

### Requirement: Очистка не меняет merge gate

Очистка, переводя прогон в `failed`, SHALL NOT менять check run. Если воркер этого прогона жив, он SHALL получить ошибку следующей записи и выставить gate по правилам упавшего прогона.

#### Scenario: Очистка вымела прогон

- **WHEN** воркер умер посреди прогона на коммите, где уже было ревью, и очистка перевела прогон в `failed`
- **THEN** check run на head не меняется

#### Scenario: Очистка вымела прогон живого воркера

- **WHEN** вызов модели длиннее порога, очистка перевела прогон в `failed`, и на этот head-коммит уже было ревью
- **THEN** следующая запись воркера падает, ревью не публикуется, на head ставится `failure` «Ревью не удалось»

### Requirement: Исход шага пишется один раз

Исход шага SHALL записываться только поверх статуса `running`. Запись поверх закрытого шага SHALL NOT менять его.

#### Scenario: Воркер и очистка закрывают один шаг

- **WHEN** воркер записал шаг `completed`, а очистка следом закрывает его с `REVIEW_RUN_STALE`
- **THEN** шаг остаётся `completed`
