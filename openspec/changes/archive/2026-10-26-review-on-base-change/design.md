## Context

Merge gate — check run `dmc-268-ai-review` на head-коммите PR. GitHub привязывает его к коммиту, а не к паре «коммит, база»: после смены целевой ветки обязательная проверка видит прежний `success`. Gate ставят приём (блокировка при смене ветки), воркер (итог прогона и `failure` упавшего) и пересчёт по закрытию треда. Общей блокировки у них нет, только база и порядок вызовов.

## Decisions

### D1. Смена ветки — по имени ветки на `edited`

Признак — `edited` с `changes.base` и `merge_request.target_branch != metadata.target_branch`. `base_sha` двигается при каждом мердже в целевую ветку и как признак не годится: повтор `synchronize` после чужого мерджа ставил бы ложный `failure`. `edited` без `changes.base` (заголовок, описание) дифф не меняет.

### D2. Блокировка — `failure`, а не `in_progress`

`in_progress` тоже держит мердж, но упавшее новое ревью оставило бы его навсегда. `failure` — fail closed: снимает его только завершённое ревью нового диффа.

### D3. Порядок приёма: коммит → блокировка → задача

Частичный индекс допускает один нетерминальный прогон на коммит, поэтому отмена коммитится до вставки нового. Блокировка идёт после коммита: воркер старого прогона и пересчёт после своего POST перечитывают последний прогон (D4) — прочитали до коммита, и блокировка приёма придёт позже; после — они сами видят смену. Задача ставится после блокировки, и новый прогон не выставит gate раньше неё. Приём ставит check прямым POST без повторов `settle`: GitHub ждёт ответа на доставку 10 секунд.

### D4. Один путь выставления gate — `settle_merge_gate`

Вызывающий передаёт свой check. `settle` собирает check по последнему прогону на head: свой, если за head отвечает вызывающий; `completed` — gate его находок; `failed` — «Ревью не удалось»; идёт или отменён — блокировка смены ветки. После POST — перечитать; выставленный check помнится парой «прогон, статус», так что завершение прогона после нашей блокировки возвращает его итог. Отказ GitHub — до трёх попыток, каждая перечитывает прогон: за время сбоя мог смениться тот, кто отвечает за head.

### D5. Пересчёт по треду — только по `completed`

`find_latest` — последний прогон на коммит в любом статусе. Ревью идёт — gate выставит прогон; упал или отменён — остаётся то, что выставлено. Иначе пересчёт ставил `success` непроверенному head.

### D6. Отменённый прогон

Перед POST ревью прогон перечитывает статус и при `cancelled` бросает `RunCancelledError`: ревью по старой ветке стало бы тредами в gate нового прогона. Отмена посреди ревью всплывает исключением на следующем переходе. В обоих случаях `run_review` перечитывает статус, закрывает открытый шаг кодом `REVIEW_RUN_STALE` (исхода у шага нет, отдельного кода в контракте API нет) и подтверждает сообщение: в DLQ оно не уходит.

### D7. `failure` упавшего прогона

Если поправку после смены ветки GitHub так и не принял, на head мог остаться `success` старого диффа. Упавший прогон, последний на head, ставит `failure`, только если до него head уже ревьюили (`find_reviewed`): без прежнего ревью check run нет, обязательная проверка и так держит мердж, и упавшее ревью ничего не оставляет на PR (E2E-05).

## Risks

- Ручной или mention-прогон на тот же head после вебхукового: пересчёт по треду поставит блокировку с заголовком про смену ветки, пока тот не завершится. Мердж блокируется, а не открывается.
- Запоздавшее `edited` (две смены ветки подряд) не закрывается: нужна сериализация приёма по PR — отдельная задача.
- `edited` с правкой заголовка переотправляется проходом #149 и тратит лимит переотправок, приём его отбрасывает.
