## Context

Merge gate - check run `dmc-268-ai-review` на head-коммите PR. GitHub привязывает check run к коммиту, а не к паре «коммит, база»: после смены целевой ветки обязательная проверка видит прежний `success`. Приём запускал ревью только по `opened` и `synchronize`; дубль определялся по head-коммиту.

## Goals / Non-Goals

**Goals:** после смены целевой ветки check run на head-коммите отражает ревью нового диффа.

**Non-Goals:** снимать прежний check run до окончания нового прогона - новый прогон его перезапишет; `reopened` - по-прежнему ручной перезапуск.

## Decisions

### D1. `edited` только с `changes.base`

GitHub шлёт `edited` и на правку заголовка или описания; дифф они не меняют, и прогон на каждую правку был бы лишним вызовом модели. Признак смены целевой ветки - `changes.base` в payload ([документация GitHub](https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request)).

### D2. Дубль - тот же head и та же база

`find_active`/`find_reviewed` по-прежнему ищут по head-коммиту; сравнение базы - в use case (`_same_base`), чистое. Прогон без записанной базы (поле необязательное) считается ревью любой базы: иначе каждый повтор доставки для такого прогона давал бы новый прогон.

### D3. Активный прогон на старой базе - `cancelled` своим коммитом

Частичный уникальный индекс допускает один нетерминальный прогон на коммит, поэтому отмена коммитится до вставки нового. Переход в `cancelled` разрешён из любого нетерминального статуса; если воркер успел завершить прогон, переход отклонён, и отменять нечего. Сообщение отменённого прогона воркер подтверждает без работы, если ещё не начал; начатый прогон упадёт на следующем переходе статуса и уйдёт в DLQ.

## Risks / Trade-offs

- [Начатый прогон на старой базе уже на этапе `publishing` выставит check run после отмены] → его перезапишет новый прогон, который стоит в очереди позже; окно - время публикации против полного прогона модели. Отмечено в отчёте #222.
- [Сообщение отменённого во время работы прогона - в DLQ] → редкий случай, причина видна в `failure_reason` шага; отдельная обработка - когда понадобится.
