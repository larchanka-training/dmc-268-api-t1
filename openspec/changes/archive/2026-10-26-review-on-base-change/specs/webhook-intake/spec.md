## ADDED Requirements

### Requirement: Смена целевой ветки запускает ревью

Событие `pull_request` с действием `edited`, в котором есть `changes.base`, SHALL запускать прогон ревью так же, как `synchronize`: тот же head-коммит с другой базой - другой дифф, а check run merge gate висит на head-коммите и о базе не знает. Базовый коммит SHALL браться из свежих метаданных PR. Если у запроса на изменение есть активный прогон на этот head-коммит с другой базой, он SHALL переводиться в `cancelled` своим коммитом до создания нового прогона.

#### Scenario: Смена целевой ветки после завершённого ревью

- **WHEN** прогон на head-коммит завершился `completed` с check run `success`, а затем приходит `edited` с `changes.base` и в свежих метаданных другая база
- **THEN** создаётся новый прогон в `queued` с новой базой, задача ставится в очередь, и check run на head-коммите выставляет уже он

#### Scenario: Смена целевой ветки во время ревью

- **WHEN** прогон на head-коммит со старой базой ещё не завершён, и приходит `edited` с `changes.base`
- **THEN** этот прогон переводится в `cancelled`, создаётся новый прогон в `queued` с новой базой

## MODIFIED Requirements

### Requirement: Прочие действия pull request игнорируются

Действия `pull_request` `reopened`, `closed`, `edited` без `changes.base` и любые иные, кроме `opened`, `synchronize` и `edited` со сменой целевой ветки, SHALL получать HTTP 202 (ignored): записей не создаётся, очередь не трогается, ответ — не 5xx. При `reopened` система SHALL NOT переназначать бота ревьюером автоматически: пользователь переназначает его вручную, и следующее событие обрабатывается как обычный запуск.

#### Scenario: Reopened игнорируется

- **WHEN** приходит `pull_request` с действием `reopened`
- **THEN** ответ — HTTP 202 (ignored), записей не создаётся и в очередь ничего не уходит, а бот не переназначается ревьюером автоматически

#### Scenario: Неизвестное действие игнорируется без сбоя

- **WHEN** приходит `pull_request` с действием, отличным от `opened`, `synchronize`, `edited` и `reopened` (например, `closed`)
- **THEN** ответ — HTTP 202 (ignored), а не 5xx, записей нет и очередь не трогается

#### Scenario: Правка заголовка или описания игнорируется

- **WHEN** приходит `pull_request` `edited`, в `changes` которого нет `base`
- **THEN** ответ — HTTP 202 (ignored), записей нет и очередь не трогается

### Requirement: Повторная доставка отвечает существующим прогоном

Вебхук для запроса на изменение и head-коммита, у которых уже есть прогон в нетерминальном состоянии или завершённый не-`failed` прогон с источником `webhook` на ту же базу (из свежих метаданных PR), SHALL NOT создавать новый прогон и ставить задачу. Ответ SHALL быть HTTP 202 с проекцией найденного прогона. Прогон `failed` дублем не делает. Дубль SHALL NOT переписывать записи: он проверяется до обновления merge_request.

#### Scenario: Повторная доставка безвредна

- **WHEN** приходит вебхук для head-коммита, у которого уже есть прогон в нетерминальном состоянии на ту же базу
- **THEN** второй активный прогон не создаётся, и ответ — не 5xx

#### Scenario: Повторная доставка отвечает 202 с проекцией существующего прогона

- **WHEN** приходит вебхук для head-коммита, у которого уже есть активный прогон на ту же базу
- **THEN** ответ — HTTP 202 с проекцией `ReviewJob` существующего прогона, новых записей нет и очередь не трогается

#### Scenario: Повтор после завершения прогона — один прогон и одно ревью

- **WHEN** приходит вебхук для head-коммита, прогон по вебхуку для которого на ту же базу уже завершился в `completed`, в том числе с тем же `X-GitHub-Delivery`
- **THEN** ответ — HTTP 202 с проекцией завершённого прогона, новый прогон не создаётся, задача не ставится, и второе ревью не публикуется

#### Scenario: Прогон без записанной базы

- **WHEN** приходит вебхук для head-коммита, завершённый прогон которого не хранит базу
- **THEN** он считается прогоном на любую базу: ответ — дубль, новый прогон не создаётся

#### Scenario: Повтор после failed создаёт новый прогон

- **WHEN** приходит вебхук для head-коммита, единственный прогон которого завершился в `failed`
- **THEN** создаётся новый прогон в `queued` и задача ставится в очередь

#### Scenario: Новый коммит после активного прогона запускает новый прогон

- **WHEN** приходит вебхук с новым head-коммитом для запроса на изменение, у которого есть активный прогон на предыдущем коммите
- **THEN** создаётся новый прогон ревью для нового коммита, а предыдущий прогон по-прежнему указывает свой коммит

### Requirement: Упавшие доставки повторяются

GitHub неудачные доставки сам не повторяет, поэтому воркер SHALL периодически запрашивать доставки вебхука приложения GitHub App за последние трое суток с аутентификацией JWT приложения и SHALL переотправлять доставку, у которой ни одна попытка с тем же `guid` не была успешной. Переотправляются только события приёма: `pull_request` `opened`/`synchronize`/`edited`, если её коммит — всё ещё голова PR, и `pull_request_review_thread` `resolved`/`unresolved`.

#### Scenario: Упавшая доставка переотправляется

- **WHEN** в списке доставок есть `pull_request` `synchronize` с ответом 5xx и без успешной попытки с тем же `guid`
- **THEN** воркер вызывает переотправку этой доставки

#### Scenario: Успешно переотправленная доставка больше не трогается

- **WHEN** у доставки с ответом 5xx есть более поздняя успешная попытка с тем же `guid`
- **THEN** переотправка не вызывается

#### Scenario: Устаревшая доставка не повторяется

- **WHEN** упала доставка `pull_request`, а голова PR по свежим метаданным уже другой коммит, чем `pull_request.head.sha` в её payload
- **THEN** переотправка не вызывается, и в лог пишется, что доставка устарела

#### Scenario: Чужие события не переотправляются

- **WHEN** упала доставка события, которое приём не обрабатывает (например, `push` или `pull_request` `closed`)
- **THEN** переотправка не вызывается

#### Scenario: Без реквизитов GitHub App повтор выключен

- **WHEN** у сервиса не задан идентификатор или приватный ключ GitHub App, или повтор выключен настройкой
- **THEN** воркер не обращается к API доставок и один раз пишет об этом в лог при старте
