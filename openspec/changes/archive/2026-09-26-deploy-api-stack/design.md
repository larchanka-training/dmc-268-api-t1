# Design

## Context

Мотивация — в `proposal.md`. Что уже готово и на что опираемся:

- Docker `29.8.1` на сервере, вход по ключу `VPS_DMC268_KEY_T1` с `BatchMode=yes`.
- Состояние Terraform — в бакете `dmc268-tfstate`, нативная блокировка работает (условная запись поддерживается).
- `tfstate-backend.yml` идемпотентно поднимает хранилище и открывает туннель; задумывался как первый job деплоя, здесь им и становится.
- `infra/main.tf` уже описывает postgres, rabbitmq и api; `bind_ip` и `internal_bind_ip` по умолчанию `127.0.0.1`.
- Эндпоинт `/health` есть (`app/api/factory.py:35`) и отвечает независимо от БД — годится как smoke-проверка живости процесса, но не как проверка миграций.

## Goals / Non-Goals

**Goals:**

- Мерж в `develop` выкатывает бэкенд без участия человека.
- Миграции применяются до того, как API начинает отвечать.
- Неудачный деплой виден как красный прогон, а не как тихо работающий старый контейнер.

**Non-Goals:**

- Воркер, выбор брокера, TLS и домен — см. `proposal.md`.
- Откат на предыдущую версию одной кнопкой. Тег по sha даёт возможность выкатить любой коммит повторным запуском, но отдельной механики отката не делаем, пока её никто не просил.
- Бэкапы БД. Бакет для них есть, задача — отдельная.

## Decisions

**Образ собирается в CI и тянется на сервер, а не собирается на сервере.** Текущая схема — `docker_image` с блоком `build` и тегом по хешу исходников — требует, чтобы рядом с демоном лежал исходный код. При удалённом `docker_host` это означало бы сборку на сервере, без кеша слоёв и с исходниками на проде. Тег по commit sha вместо хеша файлов заодно делает очевидным, какой коммит сейчас на стенде.

**Аутентификация в ghcr — через `registry_auth` провайдера, а не `docker login` на сервере.** Альтернатива заставила бы хранить на сервере долгоживущий токен и помнить про его ротацию. `GITHUB_TOKEN` живёт один прогон, а `packages: write` для публикации и `read` для скачивания у него уже есть. Пакет при этом может остаться приватным.

**Миграции — отдельный контейнер в Terraform, а не команда внутри API.** Рассмотрены три варианта:

1. Скопировать подход compose: `command = ["sh","-c","alembic upgrade head && uvicorn ..."]`. Просто, но упавшая миграция уходит в рестарт-луп контейнера, и причина тонет в логах перезапусков.
2. Отдельный шаг в CI через `ssh docker run --rm`. Работает, но порядок «после postgres, до api» оказывается записан в workflow, тогда как всё остальное про порядок записано в Terraform.
3. `docker_container` с `must_run = false` и `attach = true`: контейнер отрабатывает и завершается, Terraform ждёт и падает на ненулевом коде. Зависимость `api` от него выражается штатным `depends_on`.

Выбран третий: порядок живёт там же, где остальной порядок, а падение миграции останавливает деплой до старта API. Контейнер пересоздаётся при каждой смене тега образа, то есть миграции применяются на каждом деплое, а на неизменном теге — нет.

**`bind_ip` становится `0.0.0.0` для API и остаётся `127.0.0.1` для postgres и rabbitmq.** Публиковать наружу базу и брокер незачем: к ним ходит только API изнутри docker-сети. Это же делает ненужным TLS для них.

**Smoke-проверка идёт по туннелю, а не по публичному адресу.** Туннель уже открыт для состояния, и проверка через него подтверждает, что сервис жив, даже если снаружи что-то режет файрвол. Публичная доступность проверяется отдельно и явно — иначе мы бы узнали о закрытом порте от теммейта, а не от прогона.

**`/health` не доказывает, что миграции применились.** Он отвечает независимо от БД — это его контракт, записанный в `backend-base-setup`. Поэтому доказательством миграций служит успешное завершение контейнера миграций, а не smoke-проверка. Смешивать их нельзя.

## Risks / Trade-offs

- **Стенд открыт в интернет по HTTP без аутентификации** → осознанно: показывать нечего, если закрыто, а сертификат на голый IP не выпустить. Наружу смотрит только API; база и брокер остаются на петле. Как только появится домен, поверх встаёт TLS-терминатор — это отдельная задача.
- **Пароли БД и брокера меняются с плейсхолдеров на секреты** → при смене пароля уже существующий том PostgreSQL сохранит старый: переменная окружения действует только при инициализации кластера. Первый деплой на пустом сервере этого не заметит, а вот ротация потребует отдельной процедуры. Записано, чтобы не выяснять это в момент ротации.
- **Миграции применяются автоматически и без ревью** → на стенде приемлемо; необратимые миграции (удаление колонки) на боевой базе так катить нельзя. Граница проходит по тому, что `develop` — это стенд.
- **Откат только повторным деплоем нужного коммита** → тег по sha делает это возможным, но ручным; отдельной кнопки нет и не планируется, пока не попросят.
- **Первый `apply` создаёт всё сразу** → если он упадёт на середине, часть контейнеров останется. Состояние в бакете это переживёт, повторный прогон доведёт до конца; версионирование бакета страхует от порчи состояния.
