## Context

Второе из трёх последовательных изменений на одной ветке
(`feat/review-pipeline-and-api`): очередь → **пайплайн** → REST API.
`add-rabbitmq-job-queue` уже дал `JobQueue`/`RabbitMQJobQueue` и процесс
`app/worker` с общим consume-циклом и временным обработчиком-заглушкой. Это
изменение подключает к нему реальную бизнес-логику и добавляет точку входа —
вебхук, — с которой всё начинается.

Согласовано с пользователем: реальный `VcsGateway` (поход в GitHub) и
реальный `LlmGateway` (поход в Ollama) в этой задаче не реализуются — только
заготовки, вызываемые по месту. HMAC-подпись вебхука делается по-настоящему.

## Goals / Non-Goals

**Goals:**
- Рабочий сквозной путь: вебхук → `JobQueue` → воркер → `ReviewRun`
  доходит до терминального состояния в БД.
- Подлинность вебхука проверяется HMAC-подписью до какой-либо записи в БД.
- Повторная доставка того же коммита не создаёт второй прогон.
- Пайплайн реально проходит через `validate_anchor`/`add_validated` (пусть
  и с синтетическим hunk'ом из заготовки), а не обходит его.

**Non-Goals:**
- Реальный `VcsGateway` (GitHub REST, GitHub App auth) — заготовка вместо
  него, без сетевых вызовов.
- Реальный `LlmGateway` (Ollama) — адаптер-заглушка с фиксированным
  ответом.
- `IdempotencyStore`, `RateLimiter`, `accounts` — не реализуются; повторная
  доставка отсекается уже существующим частичным уникальным индексом на
  `review_runs`, этого достаточно для DoD этой задачи.
- Публикация в VCS (`VcsGateway.publish`) — раз нет реального VcsGateway,
  раздел «Публикация» из `review_pipeline`, описанный в SYSTEM_DESIGN,
  здесь не реализуется; прогон доходит до `completed` без похода наружу.

## Decisions

**`ReviewRun.id` = `ReviewJob.id` = `job_id`.** Вебхук создаёт `ReviewRun`
синхронно (в состоянии `queued`), берёт его id и кладёт в очередь именно его,
не изобретая отдельный идентификатор сообщения. Соответствует замыслу
`BACKEND_ARCHITECTURE.md`: "`job_id` — идентификатор сообщения... устойчивая
строка — `ReviewRun`".

**Защита от дублей — только партиал-индекс, без `IdempotencyStore`.**
`uq_review_runs_one_active_per_commit` уже не позволяет второму
незавершённому прогону для того же `head_sha` появиться. Вебхук ловит
конфликт (либо предварительной проверкой через `find_active`, либо через
исключение целостности при `add`) и отвечает 202 идемпотентно, не создавая
второй прогон и не публикуя вторую задачу. Требование R-4 теста-плана
(«повторная доставка не создаёт второй прогон») закрыто на этом уровне;
дедупликация именно на входе HTTP (`IdempotencyStore`) — отдельный,
незапрошенный в этом тикете шов.

**Заготовка контекста — чистая функция, без портов.** `assemble_context_stub`
не порт и не адаптер: она не обращается ни к чему внешнему, только пакует
данные, уже присутствующие в `ReviewJob`, в `ContextPayload` с
`tiers=("diff",)`. Поэтому у неё нет соответствующей строки в таблице портов
`BACKEND_ARCHITECTURE.md` — это чистая функция уровня `application`, как
`next_status` или `validate_anchor`, а не спроектированная точка расширения.
Настоящая сборка контекста (уровни `surrounding`/`whole_file`/`ast` через
`VcsGateway`) заменит её вызов внутри `review_pipeline.py`, не меняя форму
пайплайна.

**`LlmGateway` — порт с одним методом, `StubLlmGateway` — первый (временный)
адаптер.** В отличие от заготовки контекста, здесь порт оправдан: это ровно
та спроектированная точка расширения из `BACKEND_ARCHITECTURE.md`, у которой
уже есть назначенный первый адаптер (Ollama) и назначенный вызывающий код
(оркестрация прогона). Адаптер-заглушка временно занимает его место и
возвращает фиксированный результат (`model="stub-llm"`, `tokens_used=0`,
без находок) — реальный транспорт к Ollama меняет только адаптер, контракт
порта не затрагивает.

**Синтетический hunk у заглушки контекста.** Чтобы `validate_anchor`/
`add_validated` были упражнены по-настоящему, а не обойдены, заглушка
возвращает контекст с одним предсказуемым hunk'ом (фиксированный файл и
диапазон строк). `StubLlmGateway` сама сегодня не формирует находок
(фиксированный пустой результат), но контракт `run_review` на находки от
любого `LlmGateway` проверен тестом с подменным шлюзом, отдающим находку
именно на этом hunk'е — путь `add_validated` реально пройден в этом change,
не отложен на первый настоящий ответ модели. Альтернатива (не давать
заглушке ни одного hunk'а) была отклонена: тогда этот путь остался бы
недостижим до реального `LlmGateway`.

**Отдельный эндпоинт, не расширение существующего.** `POST
/api/v1/webhooks/github` — новый роутер `app/api/webhooks.py`, а не часть
уже спланированных в change 3 read-эндпоинтов: разная природа (запись vs
чтение), разная модель авторизации (HMAC vs без авторизации).

**Идентификатор репозитория провайдера — строка, приведение на границе
транспорта.** GitHub присылает `repository.id` числом (`"id": 987654`), но
в домене он `str`: `Repository.provider_id`, `ReviewJob.repository_provider_id`,
поле `repository.id` в сообщении очереди (`"id": "987654"`, `SYSTEM_DESIGN.md`
§4.2) и колонка `repositories.provider_id`. Приведение — единственное:
`str(repo_payload["id"])` в `_to_review_request` (`app/api/webhooks.py`);
дальше число нигде не встречается, и передавать его как есть нельзя.
Причины: идентификатор — ключ поиска (`find_by_provider(provider,
provider_id)`), а не число для вычислений; у других хостингов он бывает
строкой или UUID, и `int` пришлось бы менять с каждым провайдером; числа
выше 2^53 теряют точность в JSON на стороне TypeScript-фронта. Альтернатива
(`int`) отклонена: совпадает с payload одного провайдера, но требует
миграции колонки и правки `docs/erd.md`, а выигрыша не даёт. Тот же тип
должны использовать остальные реализации вебхуков (в #37 поле пока `int`).

## Risks / Trade-offs

[HMAC-секрет — новое обязательное поле `Settings`, ломает прямые
конструкторы `Settings(...)` в тестах] → механическая правка, тем же
способом, что `rabbitmq_url` в предыдущем change.

[Синтетический контекст без реального диффа означает, что находок в этой
задаче не будет никогда] → осознанно: `StubLlmGateway` возвращает пустой
список находок; ReviewRun всё равно доходит до `completed` с
`model`/`tokens_used`/`duration_seconds` — DoD («сохраняет результат ревью в
БД») не требует находок, требует результата прогона.

[Отсутствие `VcsGateway.publish` означает, что раздел «Публикация»
жизненного цикла из SYSTEM_DESIGN не реализован] → задокументировано как
Non-Goal; следующий тикет, добавляющий `VcsGateway`, естественно берёт и
публикацию.

[Дедуп повторной доставки в вебхуке реализован предварительной проверкой
`find_active`, а не перехватом ошибки целостности от партиал-индекса
`uq_review_runs_one_active_per_commit`] → закрывает ровно тот случай,
который описывает спека этого change (последовательная повторная доставка).
Гонка двух одновременно обрабатываемых доставок всё ещё упирается в
партиал-индекс на уровне базы (второй прогон не создастся), но сегодня это
всплывёт как необработанное исключение — 500 клиенту, а не идемпотентный
202. Не покрыто тестом. Настоящая защита от гонки (перехват
`IntegrityError`) — там же, где решается вопрос `IdempotencyStore`: тоже
Non-Goal этой задачи.

[Триггер прогона в этом change — сам факт валидного вебхука `pull_request`,
а не «бота добавили в ревьюеры / упомянули», как описывает
`SYSTEM_DESIGN.md` §3.1] → сознательное упрощение ради DoD тикета (сквозной
путь webhook → воркер → БД); различать `review_requested` и упоминания в
комментариях — отдельная, более тонкая логика триггера, не требуемая этим
тикетом и не покрытая его спекой.

## Migration Plan

Новый код поверх уже существующей схемы, миграций нет. Откат — two-way door:
ревёрт коммита; воркер без этого change просто продолжит крутиться с
заглушкой из `add-rabbitmq-job-queue` (сообщений в очереди при этом не
будет, потому что публиковать их тоже будет некому — эндпоинт вебхука
уходит вместе с ревёртом).
