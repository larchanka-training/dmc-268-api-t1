# Design: подключение репозитория

## Context

Мотивация — в `proposal.md`. Форма ручек зафиксирована заглушками, фронтенд сгенерирован по ней. Токен пользователя после входа через OAuth не сохраняется, у сервиса есть только `login` пользователя и реквизиты GitHub App (`GitHubAppAuth`: JWT приложения и installation tokens с кэшем). `installation_id` не хранится нигде, кроме события вебхука и сообщения очереди.

## Goals / Non-Goals

**Goals:**

- Список репозиториев, доступных для подключения, и подключение с проверкой прав admin у провайдера.
- Решить, откуда брать `installation_id`, — один раз для #41 и #87.

**Non-Goals:**

- Задача #87 (операции с репозиторием вне вебхука): она в следующем спринте, здесь только общее решение про `installation_id`.
- Фильтр списка по правам пользователя — см. D3.
- Провайдеры кроме GitHub.

## Decisions

### D1. `installation_id` не хранится, миграции нет

Его определяем через JWT приложения: `GET /app/installations` (все установки, постранично), для каждой — installation token и `GET /installation/repositories` (`per_page=100`, постранично). Хранить его в `repositories` значило бы держать копию, которая устаревает при переустановке приложения, и писать миграцию ради одного поля. Решение общее для #41 и #87: где нужен `installation_id` вне вебхука, его даёт список установок, а не база.

Альтернатива — `GET /repos/{owner}/{repo}/installation` с JWT. Она не даёт списка, а списку нужны все установки, поэтому одного способа хватает обоим случаям.

### D2. Новый порт `InstallationCatalog`, а не методы `VcsGateway`

Операции провайдера уровня приложения (какие репозитории в установках, есть ли у пользователя admin) — не операции над PR. Отдельный порт с двумя методами не трогает `VcsGateway` и его фейки. Адаптер GitHub — `app/infrastructure/vcs/github_installations.py`: переиспользует `GitHubAppAuth` (публичный `app_jwt()`) и HTTP-клиент шлюза; запросы с installation token идут через `_get` шлюза — тот же backoff, сброс отозванного токена и перевод ошибок в `VcsError`, как у `GitHubReviewClient`. Права: `GET /repos/{full_name}/collaborators/{login}/permission` с installation token, admin — `permission == "admin"`, `404` — не admin. Разрешения App достаточно **Metadata: read**.

### D3. Список не фильтруется по правам пользователя

Фильтр стоил бы запроса прав на каждый репозиторий при каждом показе экрана. Права проверяет подключение, список показывает все репозитории установок. Это сказано в описании ручки.

### D4. Порядок проверок подключения

Use case `connect_repository` (время и id приходят аргументами):

1. провайдер не `github` или репозитория нет среди репозиториев установок — `404 REPOSITORY_NOT_IN_INSTALLATION`;
2. репозиторий уже в `repositories` — `409 REPOSITORY_ALREADY_CONNECTED`; проверка раньше прав экономит запрос к GitHub и ничего не раскрывает: список отдаёт `already_connected` всем;
3. пользователь не admin — `403 REPOSITORY_ADMIN_REQUIRED`;
4. запись с `auto_review_enabled = true`, `full_name` и `default_branch` из данных установки — `201`.

Запросы к GitHub идут вне транзакции: проверка «уже подключён» и запись — две короткие единицы работы, между ними — запрос прав. Гонка двух подключений: `RepositoryRepo.add` вставляет с `ON CONFLICT DO NOTHING` по `uq_repositories_provider_id` и возвращает `False` — проигравший получает `409`, как `UserRepo.add` при первом входе. Сбой GitHub — `502 SCM_UNAVAILABLE` на обеих ручках; описание ответа своё (`ERRORS_502_SCM_REPOSITORIES`): у `ERRORS_502_SCM` вебхука в описании «прогон не создан».

### D5. Два ответа `403` у `POST /repositories`

`403 ORIGIN_FORBIDDEN` (middleware) и `403 REPOSITORY_ADMIN_REQUIRED` (ручка) описаны одним ответом: модель — объединение двух моделей ошибки с discriminator по `code` (`oneOf` в схеме). `{**ERRORS_403_ORIGIN, **…}` не годится: ключ статуса один, второй словарь затёр бы первый. Сверка схемы (`tests/test_docs.py`) принимает у ответа ошибки либо `$ref` на модель ошибки, либо `oneOf` из таких ссылок.

## Risks / Trade-offs

- Список и подключение делают `1 + N` запросов к GitHub (N — число установок) и ещё один на права. Для одной организации это единицы запросов; installation tokens кэшируются.
- Запрос с JWT приложения (`/app/installations`) не повторяется на `429/5xx`: сбой — сразу `502`, пользователь повторит.
