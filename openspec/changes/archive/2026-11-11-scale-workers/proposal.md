## Why

#99. На стенде один воркер `dmc268-worker`: пока он ждёт модель (прогон — до полутора минут, с
таймаутами — до 21 минуты), остальные задачи стоят в очереди. Несколько потребителей одной очереди
теперь безопасны: прогон захватывает один воркер условной записью (#156), heartbeat не рвёт
соединение посреди прогона и решение по сообщению — ACK, RETRY или DLQ (#157), миграции идут
отдельным шагом до выката (#159), деплой ждёт здоровья API через провайдер (#160). Не хватает
самих экземпляров: числа, которое задаётся одним местом, деплоя, который поднимает и проверяет
каждый, и наблюдаемости, которая видит каждый, а не одно имя контейнера.

## What Changes

- Переменная `worker_replicas` (по умолчанию 1, от 1 до 4): контейнеры воркера через `for_each`,
  первый сохраняет имя `dmc268-worker`, следующие — `dmc268-worker-2` и далее. Адрес первого в
  состоянии переносится без пересоздания: `moved` в `infra/app.tf`, а на стенде — `tofu state mv`
  в `infra.sh` до targeted-плана, который с непроведённым переносом не строится.
- `deploy.yml` задаёт `TF_VAR_worker_replicas` одним значением на job (`1`, как сейчас), и
  проверка после выката (`check-worker.sh`) ждёт устойчивой работы каждого экземпляра и их точного
  числа.
- Prometheus получает список ожидаемых экземпляров (`dmc268:worker_expected`, файл
  `workers.yml`), и `ContainerDown` горит по каждому пропавшему. У `ContainerMemoryNearLimit`
  `service` — без номера экземпляра. Предел пула на дашборде сложен по экземплярам.
- Страница статуса: не запущен или перезапускается экземпляр воркера — `degraded`, задачи
  забирают остальные; `outage` — у очереди нет потребителей (`WorkerNotConsuming`), он и с одним
  экземпляром горит раньше `ContainerDown`.
- `infra/README.md`, «Масштабирование воркеров»: запас памяти и соединений базы, окно остановки
  против таймаута job'а, алерты, проверка локально.

Модуль app-контейнера (предложение в #99) не заводится: ресурса `docker_image` у образа API нет
с #204, и модуль только перенёс бы атрибуты контейнера, а тесты `infra/tests` пришлось бы
переписать на выходы модуля. `for_each` на самом ресурсе даёт то же без нового слоя.

### Modified Capabilities

- `backend-delivery`: число воркеров — одна переменная; деплой проверяет каждый экземпляр.
- `job-queue`: несколько воркеров делят очередь, каждый держит не больше одного сообщения.
- `observability`: алерты видят каждый экземпляр воркера.
- `service-status`: упавший экземпляр воркера — `degraded`, `outage` — когда нет потребителей.

## Impact

- `infra/variables.tf`, `infra/app.tf`, `infra/locals.tf`, `infra/observability.tf`,
  `infra/observability/{alerts.yml,alerts.test.yml,workers.yml,prometheus.yml}`, дашборд,
  `infra/tests/*.tftest.hcl`, `docker-compose.yml`, `.github/workflows/{ci.yml,deploy.yml}`,
  `.github/scripts/deploy/{check-worker.sh,infra.sh}`, `scripts/deploy_report.py`,
  `app/domain/service_status.py`, тесты, `infra/README.md`, `docs/`.
- Стенд остаётся с одним воркером: `TF_VAR_worker_replicas` — `"1"`. Первый деплой после мёржа
  один раз переносит адрес воркера в состоянии (`state mv`) и пересоздаёт Prometheus (новый файл
  правил); воркер пересоздаётся, только если сменился образ, как при любом деплое.
- Поднять число — отдельным пул-реквестом после замера памяти воркера на стенде.
