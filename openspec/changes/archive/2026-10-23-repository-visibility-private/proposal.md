# Proposal

## Why

После мержа #96 на стенде `GET /repositories/available` показал вошедшему пользователю девять чужих приватных репозиториев из установки приложения на личном аккаунте — к ним у пользователя доступа нет (GitHub отвечает ему `404`). Видимость решалась по ответу `GET /repos/{owner}/{repo}/collaborators/{login}/permission` с installation token: для постороннего на приватном репозитории он не даёт ни `404`, ни `none`, и код считал это доступом. Тесты адаптера были на записанных ответах с предположением о форме ответа, против настоящего GitHub не проверялись.

## What Changes

- Репозиторий установки несёт флаг `private` из `GET /installation/repositories`.
- Для приватного репозитория доступ сначала проверяется прямо: `GET /repos/{owner}/{repo}/collaborators/{login}` — `204` есть, `404` нет. Без доступа роль не запрашивается, репозиторий не виден и не подключается (`404 REPOSITORY_NOT_IN_INSTALLATION`, как и раньше для невидимого).
- Публичный репозиторий проверяется как раньше: его и так видит любой.
- Ответ, отличный от `204`/`404`, и `private` не булево — сбой провайдера (`502`), а не «доступ есть».

## Capabilities

### Modified Capabilities

- `review-rest-api`: «Список репозиториев, доступных для подключения» — приватный репозиторий виден только пользователю с доступом, проверка прямая.

## Impact

- `app/domain/entities.py` (`InstallationRepository.private`), `app/infrastructure/vcs/github_installations.py`, тесты адаптера.
- Схема API не меняется.
