## Why

Входящему `traceparent` от HTTP-клиента сервис не доверяет (`_NoPropagation`, change `add-otel-tracing`): каждый запрос начинает новый трейс. Это правильно, но трейс браузера (кабинет, larchanka-training/dmc-268-ui-t1#49) и трейс API в Tempo тогда никак не связаны — от медленного действия в кабинете не перейти к спанам сервера. Задача larchanka-training/dmc-268-api-t1#110, родитель #89.

## What Changes

- Валидный `traceparent` запроса даёт серверному спану **span link** на контекст клиента с атрибутом `link.source = "client"`. Родителем контекст клиента не становится.
- Разбор — стандартным `TraceContextTextMapPropagator`, только `traceparent`: `tracestate` и baggage не читаются. Невалидный заголовок — без ссылки и без ошибки.
- Новое требование в спеке `observability` с обоснованием, почему ссылка, а не родитель.

Почему не родитель:

- trace id показывается людям (`X-Trace-ID`, `trace_id` в problem+json, логи) — он должен быть нашим, клиент не должен его подменять;
- флаг `sampled` клиента управлял бы записью: `00` — запросы не пишутся, `01` — пишутся все при частичном сэмплировании. Ссылки сэмплер `parentbased_*` не учитывает;
- один `trace_id` в тысяче запросов склеил бы их в один гигантский трейс;
- браузер, не выгрузивший свои спаны, оставил бы серверные трейсы без корня.

## Impact

- Код: `app/infrastructure/telemetry.py` (`link_client_trace`), `app/api/trace_id.py` (вызов на серверном спане).
- Контракт API не меняется: `X-Trace-ID` и тело ошибок прежние; требование «Каждый ответ несёт trace id» в `review-rest-api` остаётся верным — `traceparent` не принимается ни родителем, ни trace id.
- CORS не нужен: кабинет ходит в API с того же origin, `CORSMiddleware` в API нет.
- Документация: раздел «Наблюдаемость» в `docs/BACKEND_ARCHITECTURE.md`, правило доверия в `.agents/rules/backend.md`.
