## Context

Видимость — ответ GitHub по токену пользователя (`InstallationCatalog.list_repositories`): обход `/user/installations` и репозиториев каждой установки. Его зовут восемь ручек через `user_repositories` / `visible_provider_ids` / `visible_repository` (`app/api/repositories.py`). В процессе API уже есть `CacheStore` (`InMemoryCacheStore`, один на composition root) — порт best-effort кэша с TTL; Redis в `docker-compose.yml` поднят «под первого потребителя», кодом не используется, на стенде его нет. API на стенде — один контейнер, один процесс uvicorn.

## Goals / Non-Goals

**Goals:** повторный запрос в пределах TTL не ходит в GitHub; подключённый репозиторий виден сразу; ответы видимости не меняются.

**Non-Goals:** общий кэш между репликами; кэш проверок подключения (`user_repository`, `app_installed`); rate limiting запросов к GitHub.

## Decisions

### D1. Кэш в памяти процесса API за `CacheStore`, не Redis

Кэшируется только ответ GitHub, а подключённые репозитории читаются из базы на каждый запрос. Поэтому кэш процесса остаётся корректным и при нескольких репликах: у каждой свой, запросов к GitHub больше (раз в TTL на реплику), ответы те же. Redis дал бы меньше запросов при многих репликах и кэш, переживающий деплой, но стоит контейнера на стенде, где память в дефиците (#108), пароля, сетевого перехода на каждом запросе и решения, что делать, когда Redis недоступен. Переход — замена адаптера `CacheStore` в контейнере, места вызова не меняются (`docs/BACKEND_ARCHITECTURE.md`, «Добавление Redis»). Повод — вторая реплика API или первый потребитель, которому общее состояние нужно по-настоящему (rate limiting, идемпотентность вебхуков).

### D2. Декоратор порта, ключ — sha256 токена

`CachedInstallationCatalog` оборачивает `InstallationCatalog` и кэширует только `list_repositories`. Места вызова не меняются: ручки видимости берут каталог зависимостью `get_visibility_catalog`, страница подключения и подключение — прежнюю `get_installation_catalog`. Ключ — хэш токена, а не `session_id`: обновлённый токен или выход дают новый ключ, старая запись недостижима и уходит по TTL — сброс не нужен ни при выходе, ни при обновлении токена. Сам токен в кэше и в логе не появляется. Обход токена и его обновление (`call_with_user_token`) остаются прежними: кэш — внутри вызова провайдера.

### D3. Подключение кэш не сбрасывает

Подключение меняет базу, а не то, что GitHub отдаёт пользователю; «подключён ли» читается из базы. Страница подключения идёт мимо кэша: после установки приложения на GitHub новый репозиторий там виден сразу, без ожидания TTL.

### D4. TTL 30 с

Верхняя граница задержки, с которой кабинет замечает отзыв доступа на GitHub. Кабинет перезапрашивает список не чаще раза в секунду — 30 с сокращают запросы к GitHub до ~120 в час на пользователя и процесс. Настройка `VISIBLE_REPOSITORIES_CACHE_TTL_SECONDS`.

## Risks / Trade-offs

- Отзыв доступа на GitHub виден с задержкой до TTL — принято, граница настраивается.
- Отзыв токена на GitHub (`401`) в пределах TTL не замечается: ответ берётся из кэша, сессия закроется на первом промахе.
- После рестарта процесса первый запрос каждого пользователя — полный обход GitHub.
- `InMemoryCacheStore` ограничен 1024 записями на процесс: при большем числе активных токенов старые вытесняются — больше промахов, не ошибки.
