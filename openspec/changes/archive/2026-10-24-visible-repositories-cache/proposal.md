## Why

Видимость прогонов и репозиториев считается токеном пользователя заново на каждый запрос: `GET /reviews`, `GET /events`, ручки прогона (`/reviews/{id}`, `/steps`, `/diff`) и зарегистрированных репозиториев (`/repositories`, `/repositories/{id}`, `/pull-requests`) обходят все установки пользователя у GitHub постранично. Кабинет перезапрашивает список прогонов на события потока, не чаще раза в секунду. Пользователь в 5 организациях с ~300 репозиториями при идущих прогонах — порядка 20 000 запросов к GitHub в час при лимите токена 5000; когда лимит кончится, всё это отвечает `502`. Задача #126.

## What Changes

- Ответ GitHub «какие репозитории видит пользователь» кэшируется на `VISIBLE_REPOSITORIES_CACHE_TTL_SECONDS` (по умолчанию 30 с) по ключу sha256 токена пользователя в `CacheStore` процесса API.
- Кэш — у ручек видимости. Страница подключения (`GET /repositories/available`) и само подключение идут мимо кэша: только что поставленное приложение видно сразу.
- Подключён ли репозиторий, по-прежнему читается из базы на каждый запрос: подключённый репозиторий виден сразу, кэш сбрасывать не нужно.
- Сбои GitHub и отвергнутый токен не кэшируются. Сбой хранилища кэша — промах, а не ошибка.
- Цена: отзыв доступа на GitHub виден в кабинете с задержкой до TTL.

## Capabilities

### Modified Capabilities

- `review-rest-api`: набор видимых репозиториев берётся из кэша в пределах TTL; требования «Ответы GitHub не выдают, есть ли прогон/репозиторий» — про проверку видимости, а не про обязательный запрос к GitHub.

## Impact

- Код: `app/infrastructure/vcs/cached_installations.py` (декоратор `InstallationCatalog`), `Container.visibility_catalog`, зависимость `get_visibility_catalog` в `app/api/dependencies.py` — у ручек видимости вместо `get_installation_catalog`; настройка `visible_repositories_cache_ttl_seconds`.
- Контракт API не меняется.
- Нагрузка: запрос к GitHub — раз в TTL на токен пользователя и процесс API.
