## Context

Все ручки данных кабинета видят пользователя через `current_session` (`app/api/session.py`), а видимость репозиториев — через одну функцию `user_repositories` (`app/api/repositories.py`). Её вызывают списки и карточка прогона (`app/api/reviews.py`), аналитика (`app/api/analytics.py`) и поток событий (`app/api/events.py`). `user_repositories` идёт в GitHub с токеном пользователя (`InstallationCatalog`, `OAuthProvider`). Прецедент «работы без внешнего сервиса» уже есть: `LLM_BACKEND=stub` собирает `StubLlmGateway` в `app/infrastructure/container.py`.

## Goals / Non-Goals

**Goals:**
- `docker compose up` с чистого клона показывает наполненный кабинет без GitHub App.
- Вход через GitHub, если App настроен, работает как сейчас и видит только настоящие данные.
- Ноль изменений поведения при выключенном `DEMO_MODE` и на стенде.

**Non-Goals:**
- Не мокаем GitHub для изменяющих операций (подключение репозитория, повторный прогон, оплата).
- Не запускаем воркер на демо-данных: прогоны записаны готовыми.
- Не включаем демо на стенде: у проверяющих есть вход через GitHub.

## Decisions

- **D1. «Мок» — это демо-пользователь в базе, а не второй набор ответов.** Анонимный `GET` получает `SignedIn` демо-пользователя, и дальше работают те же use cases, репозитории и модели ответа. Альтернатива — фикстуры ответов в каждой ручке — расходилась бы со схемой и удваивала бы код.
- **D2. Решение — в `current_session`.** Демо-пользователь подставляется, только когда действительной сессии нет, демо-режим включён и запрос — `GET` (`HEAD` до `GET`-роута не доходит: `405`). Условие из одной строки живёт прямо в `current_session`, отдельной функции не заводим: ветки покрыты API-тестами. Use case `demo_sign_in` (`app/application/use_cases/auth.py`) читает демо-пользователя существующим `users.find_by_provider(github, "demo")` и отдаёт `SignedIn` с постоянным `DEMO_SESSION_ID`, которого в базе нет. Нет строки — прежний `401`, то есть демо-режим без seed ведёт себя как выключенный. Недействительная cookie удаляется и при демо-ответе: `current_session` получает `Response` и пишет в него `Set-Cookie`.
- **D3. Видимость демо — по базе.** Ветка демо — в use case `list_user_repositories` (`app/application/use_cases/connect_repository.py`), через который идут и `user_repositories`, и список `GET /repositories` (`list_with_connections`): `UserContext.demo` ставит `as_user` по `is_demo_user`. Демо-пользователю видны демо-репозитории, за которые он записан плательщиком, — существующий `repositories.list_paid_by`, новых методов адаптеров нет. Провайдер не спрашивается. У демо-репозиториев `provider = github` и `provider_id` вида `demo-<n>`: GitHub никогда не вернёт такой id настоящему пользователю, поэтому `is_visible` прячет их от вошедших без дополнительного кода. Новой колонки нет (YAGNI): признак демо — `provider_user_id = "demo"` у пользователя, `provider_id` с префиксом `demo-` у репозитория; константы и проверки — `app/domain/demo.py`. Другие походы в GitHub на чтение для демо тоже не идут: `GET /repositories/{id}/rules` демо-репозитория отвечает `absent`, у демо-прогонов нет `base_sha`, и дифф отвечает `409 DIFF_UNAVAILABLE`; `install_url` в списке репозиториев демо-пользователя — `null`.
- **D4. Seed — use case поверх unit of work.** Набор — чистая функция `demo_dataset(now)`, запись — `seed_demo(uow, dataset)` в `app/application/use_cases/seed_demo.py`, через доменные сущности и порты, а не сырым SQL: схема меняется миграциями, и seed ломается на тесте, а не молча. Те же данные берут тесты ручек на фейковом unit of work. Идемпотентность — пропуск строк, что уже есть по постоянным id (и по `(provider, provider_user_id)` у пользователя); зачисление стартового баланса — только вместе с новым пользователем, журнал баланса идемпотентен лишь по сессии Stripe. Id постоянные, время — от `now` аргументом: аналитика кабинета смотрит последние дни, константы из прошлого она бы не показала. Запись — по транзакции на уровень внешних ключей: у моделей нет связей ORM, и в одном flush порядок вставки разных таблиц не гарантирован (проверено на живой базе: находки ушли раньше прогона).
- **D5. Compose.** CLI — `app/worker/seed_demo.py`, как `app.worker.credit_balance`: `scripts/` в образ не копируется, правка `Dockerfile` не нужна. Сервис `seed` из того же образа, `command: python -m app.worker.seed_demo`, роль приложения, `depends_on: migrate: service_completed_successfully`. Seed сам выходит с кодом 0 при `DEMO_MODE` не `true`, поэтому отдельный профиль не нужен, и `docker compose up` остаётся одной командой.
- **D6. Стенд защищён тем, что `infra/` не передаёт `DEMO_MODE`.** Окружение приложения стенда `infra/app.tf` задаёт явным списком, а `.env` в образ не попадает (`.dockerignore`), так что переменной репозитория `DEMO_MODE` до приложения не дойти. Отсутствие переменной в `infra/` сверяет `tests/test_demo_mode_deploy.py`. Отдельный шаг в `deploy.yml` не нужен: он проверял бы переменную, которая приложению не передаётся.
- **D7. `is_demo` в `/auth/me`.** Поле в модели ответа (`AllFieldsResponse`, обязательное), выводится из пользователя той же функцией, что в D3. Кабинет по нему показывает плашку и прячет кнопки изменений — это подзадача фронтенда.

## Risks / Trade-offs

- [Анонимное чтение случайно включится на стенде] → `DEMO_MODE` нет в `infra/` (D6), сценарий в спеке `backend-delivery`.
- [Демо-данные просочатся вошедшему пользователю] → `provider_id` с префиксом `demo-` невидим через GitHub (D3). Тест: в демо-режиме вошедший пользователь демо-прогонов не видит.
- [Поток событий без сессии закрывался бы каждые 5 с и переподключался] → демо-пользователя нечем отозвать: проверка сессии в потоке для него всегда «жива», поток живёт, пока открыта вкладка. Недействительная cookie на потоке не удаляется: ответ потока — свой `StreamingResponse`, заголовки зависимости в него не попадают; её удалит первый же обычный `GET`.
- [Прогон `analysing` из seed устареет] → очистка воркера (`review.sweep`) переведёт его в `failed`; повторный seed его не восстанавливает — строки уже есть.
- [Seed отстанет от схемы] → интеграционный тест прогоняет seed на мигрированной базе в CI, `compose-smoke` проверяет демо-прогон через кабинет.
