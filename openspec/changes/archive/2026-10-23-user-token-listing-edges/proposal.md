# Proposal

## Why

Повторное ревью PR #111 (задача #107) после change `user-token-hardening` нашло крайние случаи:

- прежний токен, взятый при сбое refresh, мог истечь посреди обхода страниц: `401` на него закрывал сессию, хотя refresh token был жив;
- вторичный лимит GitHub бывает `403` только с «rate limit» в `message` — такую установку список молча пропускал;
- `POST /repositories` искал репозиторий в полном списке установок: репозиторий за пределом 50 страниц получал ложный `404`, а подключение стоило обхода всех установок. По решению пользователя подключение больше не обходит список: два прямых запроса.
- пропуск установок не был виден в логе; выход и повтор после `401` читали токен без блокировки и могли не увидеть параллельный refresh.

## What Changes

- `401` на токен, который не сменился, — refresh под блокировкой, если refresh token жив, и один повтор; закрытие сессии — только после этого.
- Прежний токен при сбое refresh берётся, только если до истечения больше 60 секунд.
- `403` с «rate limit» в `message` (без учёта регистра) — лимит, `502`.
- `POST /repositories`: `GET /repositories/{id}` токеном пользователя, затем `GET /repos/{owner}/{repo}/installation` с JWT приложения; не виден, не установлено, установка приостановлена — один `404`; затем `403` → `409` → `201`.
- Пропущенные установки — одно предупреждение в логе; выход и повтор после `401` читают токен под блокировкой.

## Capabilities

### Modified Capabilities

- `review-rest-api`: «Список репозиториев, доступных для подключения», «Подключение репозитория», «Отказы подключения репозитория», «Истёкший токен пользователя обновляется», «Непригодный токен пользователя закрывает сессию».

## Impact

`app/application/use_cases/user_token.py`, `connect_repository.py`, `auth.py` (`logout`), порт `InstallationCatalog` (`user_repository`, `app_installed`), `app/infrastructure/vcs/github_installations.py` (JWT приложения для проверки установки), `app/infrastructure/container.py`, `app/domain/provider_token.py`. Схема ответов не меняется.
