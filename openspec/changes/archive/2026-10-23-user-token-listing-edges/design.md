# Design: крайние случаи токена и подключение двумя запросами

## Context

Уточняет changes `repositories-via-user-token` и `user-token-hardening` по повторному ревью PR #111.

## Decisions

### D1. `401` на неизменившийся токен — refresh и повтор

На `ProviderTokenRejected` `call_with_user_token` берёт запись токена под блокировкой (`get_for_update`, тот же путь, что refresh): так виден результат параллельного refresh после его коммита. Токен в записи уже другой — повтор с ним. Тот же, refresh token жив — обмен, сохранение, повтор. Обновить нечем (токен без истечения, refresh token истёк или отвергнут) — сессия закрывается. Повтор один; повтор тоже `401` — сессия закрывается. Сбой GitHub при этом обмене — `502`, сессия остаётся.

Это закрывает случай из `user-token-hardening` D2: прежний токен, взятый при сбое refresh, истёк посреди обхода — следующий `401` приводит к refresh, а не к закрытию сессии. Дополнительно прежний токен берётся, только если до истечения больше 60 секунд (`is_usable` с запасом `USABLE_MARGIN`).

### D2. Вторичный лимит без заголовков

`403` считается лимитом, если `x-ratelimit-remaining: 0`, есть `retry-after` или в `message` тела есть «rate limit» без учёта регистра: вторичный лимит GitHub бывает и без заголовков. Остальные `403` на репозиториях установки — пропуск установки, как раньше.

### D3. Подключение — два прямых запроса

Решение пользователя: `POST /repositories` больше не обходит список установок.

1. `GET /repositories/{id}` токеном пользователя (через `call_with_user_token`: refresh, `401`). `404` или `403` не из-за лимита — пользователь репозитория не видит. Из ответа — `full_name`, `default_branch`, `permissions`. Нечисловой `provider_id` в путь не отправляется — сразу «не виден».
2. `GET /repos/{owner}/{repo}/installation` с JWT приложения: `404` — приложение не установлено, `suspended_at` не `null` — установка приостановлена; оба — «не установлено». У каталога свой `GitHubAppAuth` — только для JWT, кэш installation tokens шлюза ему не нужен.

Порядок важен: сначала доступ пользователя, потом установка. На чужой репозиторий второй запрос не делается, и ответ не зависит от того, стоит ли там приложение. Не виден, не установлено, приостановлено — один `404 REPOSITORY_NOT_IN_INSTALLATION` с одинаковым телом. Дальше — `403` без admin/maintain, `409`, `201`. Решения остаются в use case над данными порта: адаптер только переводит ответы.

Итог: подключение стоит ровно два запроса к GitHub вместо обхода всех установок; предел 50 страниц и остановка по `total_count` остаются только у списка, и ложного `404` из-за усечения у подключения нет. Признак усечения списка не вводится.

### D4. Видимость пропусков

Пропущенные установки (приостановлена, `403`, `404`) — одно предупреждение `WARNING` на обход с их id и причинами, без токена.

### D5. Выход под блокировкой

`logout` читает токен через `get_for_update`: параллельный refresh не подменит токен между чтением и удалением сессии, отзывается последний живой. Чужая блокировка дольше 15 секунд (`ProviderTokenBusy`) — сессия удаляется во второй транзакции, отзыва нет (токен в этот момент меняется и будет удалён каскадом).
