## Context

`dmc268-postgres-backup` (`infra/postgres/backup.sh`) раз в сутки пишет `pg_dump -Fc` в
`/backups/dmc268-<UTC>.dump` (около 1,2 МБ), хранит 7 суток; контейнер `unhealthy`, если копии
моложе 26 часов нет. Сутки отсчитываются от старта контейнера: сейчас копия снимается около
20:01 UTC, после пересоздания контейнера время сдвигается. Репозиторий публичный — артефакты
прогонов скачивает любой пользователь GitHub. Прецедент шифрования — `recover-state.sh`:
`openssl enc -aes-256-cbc -pbkdf2 -iter 600000`, ключ `STATE_BACKUP_KEY_DMC268_T1`
(`openssl rand -base64 48`).

## Goals / Non-Goals

- Цель: копия базы переживает потерю сервера; восстановимость каждой вынесенной копии проверена.
- Цель: хранилище меняется без переписывания workflow.
- Не цель: точка восстановления точнее суток (WAL-архив, PITR), отдельный алерт — хватает письма
  GitHub о красном прогоне.

## Decisions

- **Хранилище — артефакты GitHub Actions, 90 суток.** Ничего нового заводить не надо, 90 суток —
  потолок для публичного репозитория. Артефакт называется по копии (`dmc268-<UTC>`), внутри —
  `dmc268-<UTC>.dump.enc`.
- **Про хранилище знают два шага.** «Сохранить копию» (`upload-artifact`) и «Взять копию»
  (`download-artifact`). Взять копию со стенда, зашифровать — `pull.sh`; расшифровать,
  восстановить, проверить — `verify.sh`; они работают с файлом и хранилища не знают. Переезд на
  R2/B2 — эти два шага заменяются на `aws s3 cp` с ключами бакета в env шагов, срок хранения —
  правилом жизненного цикла бакета. Слоя абстракции сверх этого нет: второго хранилища сегодня
  нет.
- **Ключ — существующий `STATE_BACKUP_KEY_DMC268_T1`**, решение пользователя: один секрет вместо
  двух. Параметры `openssl` — те же, что в `recover-state.sh`, их совпадение сверяет тест: один
  ключ открывает обе копии. Секрет уровня репозитория, а не environment `stand`. Следствие: ключ
  теперь открывает базу за 90 суток, а не только копию состояния за сутки, — копия ключа вне
  GitHub обязательна, при ротации старый ключ хранится, пока живут его копии.
- **Нет ключа — отказ до чтения копии.** `pull.sh` проверяет ключ первым делом и выходит с
  `::error::`; шаг загрузки после упавшего шага не идёт. Открытая копия на диск раннера не пишется:
  `ssh stand "docker exec dmc268-postgres-backup cat …" | openssl enc … -out`. В `verify.sh` —
  так же: `openssl enc -d | docker exec -i … pg_restore`.
- **Свежесть — тот же порог, что у healthcheck контейнера копий: 1560 минут.** Копию ищет
  `find /backups -name '*.dump' -mmin -1560` внутри контейнера — по часам сервера, без сверки
  часов раннера. Нет такой — красный прогон, старая не выносится: вынос устаревшей копии прятал бы
  поломку. Время запуска (21:17 UTC) — после нынешней копии в 20:01, но корректность от него не
  зависит: любая копия моложе 26 часов годится. Имя копии сверяется с `^[A-Za-z0-9._-]+\.dump$`
  до подстановки в команду ssh.
- **Проверка восстановлением.** Сервис-контейнер `postgres:18` (та же мажорная версия, что
  `pgvector/pgvector:pg18` стенда; расширение `vector` миграции не создают), образ закреплён
  digest. `pg_restore` и `psql` — изнутри контейнера: клиент на раннере младше 18-го и дамп 18-го
  не читает. `--no-owner --no-acl`: роли кластера (`dmc268_monitor`) в дамп базы не входят.
  `--exit-on-error`. Проверка: ровно одна ревизия в `alembic_version`, таблицы `repositories`,
  `merge_requests`, `review_runs`, `findings`, `users` есть, `repositories` не пуста — пустая
  значит, что копируется пустая база.
- **Скрипты, а не inline.** Ради теста `pull.sh` с подложным `ssh` и ради локального прогона
  ровно тех команд, что в workflow.

Проверено локально (podman, `postgres:18` того же digest): база с миграциями до `0020` и строкой
в `repositories`, `pg_dump -Fc` в `/backups` контейнера `dmc268-postgres-backup`; `pull.sh` с
подложным `ssh` (команда исполняется локально, `docker` → `podman`) выбрал свежую копию из двух,
файл начинается с `Salted__`; `verify.sh` восстановил его во вторую чистую базу и прошёл проверку
(ревизия `0020`, `repositories 1`); с неверным ключом — `bad decrypt`, код 1; с одной копией
двухсуточной давности `pull.sh` — `::error::` и код 1.

## Risks / Trade-offs

- Утёк ключ — открыты все копии базы за 90 суток (и копия состояния за сутки). Ротация — новое
  значение секрета; старые копии остаются под старым ключом.
- Копии ключа вне GitHub может не быть, если его ставили трубой в `gh secret set`: тогда копии
  нерасшифруемы — ключ надо перевыпустить с сохранением копии (`infra/README.md`, «Копии вне
  сервера»).
- Вынесенная копия отстаёт от базы до суток плюс время до запуска workflow.
- Плановый запуск GitHub может задержать или пропустить при нагрузке; пропуск одного дня не
  страшен — на сервере копии за 7 суток.
- Не проверено на GitHub: настоящий плановый прогон и SSH к стенду. Первый ручной запуск после
  мёржа — `gh workflow run db-backup.yml --ref develop`.
