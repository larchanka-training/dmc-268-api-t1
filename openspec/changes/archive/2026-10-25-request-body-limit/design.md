## Context

Порядок приёма вебхука по спеке — сырое тело до любого разбора, затем подпись. Тело читает `request.body()` целиком, без лимита; ручка без сессии. Ручки с JSON-телом читает FastAPI до зависимостей, то есть до сессии. У uvicorn (h11) лимита тела нет. Перед API стоит nginx фронта (`dmc-268-ui-t1`, `nginx/site.conf`): порт API опубликован только на петлю, внешний трафик идёт через него. В `location /api/` у него `client_max_body_size 25m` — большее тело получает `413 text/html` от nginx, без Problem Details и `X-Trace-ID`, — а `proxy_request_buffering` включён по умолчанию: тело буферизуется целиком и до API доходит уже с `Content-Length`, chunked и медленное тело до API не доходят. Лимит в API — второй эшелон: для запроса в обход nginx (из сети стека, при смене прокси или его настроек) и для ручек с JSON-телом, которым nginx оставляет те же 25 МБ.

## Goals / Non-Goals

**Goals:** тело больше лимита не читается целиком ни на одной ручке; отказ — до подписи и сессии; отказ — Problem Details с `trace_id`; законная доставка GitHub никогда не отклоняется.

**Non-Goals:** медленное тело (slowloris) — у uvicorn нет таймаута чтения тела, лимит размера его не останавливает; это решает буферизация тела в nginx фронта.

## Decisions

### Два лимита: 2 МиБ у вебхука, 1 МиБ у остальных

Принимаются только `pull_request` и `pull_request_review_thread`: доставка — десятки КиБ, тело PR и комментария — до 65 536 символов. Потолок доставки GitHub («Payloads are capped at 25 MB», docs.github.com, Webhook events and payloads) нужен `push` и `release` с вложениями, которые приём всё равно игнорирует. Тело читается до подписи, и 25 МиБ давали OOM API без подписи с дюжины параллельных доставок (замер на ревью: 50 МиБ кучи на доставку в момент склейки). Поэтому `WEBHOOK_BODY_MAX_BYTES = 2 097 152` (2 МиБ): законная доставка с запасом проходит, а одна доставка без подписи стоит до 4 МиБ. `413` на чужое большое событие безвреден: чужие события повторная доставка не переотправляет. Ручкам с JSON-телом хватает килобайтов, их лимит `REQUEST_BODY_MAX_BYTES = 1 048 576` (1 МиБ). Лимит выбирается по префиксу пути `/api/v1/webhooks/` до роутинга, префикс — та же константа, что у `OriginMiddleware`: путь, лишь похожий на вебхук, роутер не найдёт, а без префикса действует меньший лимит. Оба переопределяются переменными окружения. `client_max_body_size` nginx фронта не меньше `WEBHOOK_BODY_MAX_BYTES`: при меньшем законная доставка получит его `413`, при большем лишнее тело буферизует nginx, а API отказывает по `Content-Length`, не читая его.

Тело запроса к несуществующему пути читается до лимита, и только потом роутер отвечает `404`: раньше `404` приходил, не трогая тела. Это принятая цена отказа до роутинга: такой запрос стоит не больше доставки вебхука по тому же префиксу.

### Своё middleware вместо `max_body_size` Starlette

Встроенный `RequestBodyLimitMiddleware` Starlette 1.9 стоит снаружи пользовательских middleware и при `Content-Length` больше лимита подменяет любой ответ приложения на `PlainTextResponse` «Content Too Large»: ни Problem Details, ни `X-Trace-ID`. Перехватить его ответ по `Content-Length`, как предлагалось в обсуждении задачи, можно, но тогда поток без длины отказывает встроенным `HTTPException` — общим `HTTP_ERROR`, а не своим кодом. Своё middleware на чистом ASGI (~60 строк, как `OriginMiddleware`) даёт оба пути одним ответом через `problem_response`.

### Тело читается в middleware, а не исключением из `receive`

Альтернатива — считать байты в обёртке `receive` и бросить исключение на превышении. Ручка с JSON-телом читает его внутри FastAPI, а тот превращает любое исключение чтения тела, кроме `HTTPException`, в `400 There was an error parsing the body`: код `413` потерялся бы. Поэтому middleware само читает тело с подсчётом, на превышении отвечает `413` и приложение не вызывает; дочитанное в пределах лимита отдаёт приложению одним сообщением `http.request`, дальнейшие `receive` (`http.disconnect` для SSE) — от сервера как есть. Память — та же, что раньше тратил `request.body()`, но не больше лимита: пока работает ручка, тело лежит одной копией, в кадре middleware ссылок на него не остаётся — куски отпускаются сразу после склейки, а склейку держит только очередь `replay`, которая отдаёт её приложению. На склейке кратко лежат две копии: куски и результат. Держат это тесты на `tracemalloc`: в `verify_hmac` вебхука занято не больше 1,2 тела, а пик восьми параллельных доставок без подписи — не больше 1,5 тела на доставку.

Запрос без `Content-Length` и без `Transfer-Encoding` по HTTP/1.1 (RFC 9112, 6.3) тела не имеет — он идёт мимо middleware, не дожидаясь тела: `GET` и поток SSE не меняются. `Content-Length`, который длиной не разбирается, мимо не пускает: такое тело считается, как chunked, — защита не зависит от того, отклонит ли заголовок HTTP-парсер сервера. Uvicorn у нас только с h11 (HTTP/1.1); на HTTP/2 без этих заголовков тело возможно — тогда условие пересматривается.

### Порядок middleware

`TraceIdMiddleware` → `OriginMiddleware` → `RequestBodyLimitMiddleware` → приложение. `trace_id` нужен ответу `413`; чужой `Origin` отказывает `403`, не читая тела; лимит — до роутинга, разбора тела, сессии и подписи.

### `Connection: close` и `Expect: 100-continue`

При отказе по `Content-Length` тело у сервера не запрашивается: uvicorn не отвечает `100 Continue`, и клиент с `Expect` тело не шлёт вовсе. Недочитанное тело осталось бы в соединении, поэтому ответ несёт `Connection: close`. Проверено на uvicorn 0.54 (h11) с curl: 30 МиБ с `Content-Length` — `413 application/problem+json` с `X-Trace-ID`, отправлено 0 байт; chunked 30 МиБ — `413` после ~27,5 МиБ (лимит плюс буферы сокета); подписанная маленькая доставка — `202` как раньше.

### Сжатое тело

Приложение не распаковывает тело запроса (`Content-Encoding` не обрабатывается, `GZipMiddleware` сжимает только ответы). Лимит считает байты, которые лежат в памяти, и сжатая «бомба» его не обходит. Подпись GitHub считается по телу как оно пришло.

## Risks / Trade-offs

- Тело доставки до 2 МиБ без аутентификации всё ещё читается в память, до 4 МиБ в момент склейки. Лимит контейнера API — 512 МБ, сам процесс — около 130 МиБ, остаётся около 380 МиБ: под сотню одновременных доставок без подписи. Ограничение числа соединений к вебхуку (`limit_conn` в nginx) — у прокси перед API, пока не настроено.
- Доставка `pull_request_review_thread` с длинной веткой из десятков комментариев максимальной длины может перейти 2 МиБ — тогда она получит `413`, и статус треда не синхронизируется. Лимит поднимается переменной окружения.
