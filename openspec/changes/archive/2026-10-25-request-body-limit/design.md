## Context

Порядок приёма вебхука по спеке — сырое тело до любого разбора, затем подпись. Тело читает `request.body()` целиком, без лимита; ручка без сессии. Ручки с JSON-телом читает FastAPI до зависимостей, то есть до сессии. У uvicorn (h11) лимита тела нет. Перед API стоит nginx фронта (`dmc-268-ui-t1`, `nginx/site.conf`): порт API опубликован только на петлю, внешний трафик идёт через него. В `location /api/` у него `client_max_body_size 25m` — большее тело получает `413 text/html` от nginx, без Problem Details и `X-Trace-ID`, — а `proxy_request_buffering` включён по умолчанию: тело буферизуется целиком и до API доходит уже с `Content-Length`, chunked и медленное тело до API не доходят. Лимит в API — второй эшелон: для запроса в обход nginx (из сети стека, при смене прокси или его настроек) и для ручек с JSON-телом, которым nginx оставляет те же 25 МБ.

## Goals / Non-Goals

**Goals:** тело больше лимита не читается целиком ни на одной ручке; отказ — до подписи и сессии; отказ — Problem Details с `trace_id`; законная доставка GitHub никогда не отклоняется.

**Non-Goals:** медленное тело (slowloris) — у uvicorn нет таймаута чтения тела, лимит размера его не останавливает; это решает буферизация тела в nginx фронта.

## Decisions

### Два лимита: 25 МиБ у вебхука, 1 МиБ у остальных

GitHub: «Payloads are capped at 25 MB. If an event generates a larger payload, GitHub will not deliver a payload for that webhook event» (docs.github.com, Webhook events and payloads). Умолчание `WEBHOOK_BODY_MAX_BYTES = 26 214 400` (25 МиБ) не меньше 25 MB в любом прочтении единицы: законная доставка не отклоняется, а запас над потолком — меньше 5 %. Ручкам с JSON-телом хватает килобайтов, их лимит `REQUEST_BODY_MAX_BYTES = 1 048 576` (1 МиБ). Общий 25 МиБ на всё отдал бы 512 МБ памяти API двадцати запросам без сессии на любую ручку. Лимит выбирается по префиксу пути `/api/v1/webhooks/` до роутинга: путь, лишь похожий на вебхук, роутер не найдёт, а без префикса действует меньший лимит. Оба переопределяются переменными окружения. `WEBHOOK_BODY_MAX_BYTES` равен `client_max_body_size 25m` nginx фронта, и менять их надо вместе: при меньшем nginx законная доставка получит его `413`, при большем — `413` от API уже после буферизации тела в nginx.

### Своё middleware вместо `max_body_size` Starlette

Встроенный `RequestBodyLimitMiddleware` Starlette 1.9 стоит снаружи пользовательских middleware и при `Content-Length` больше лимита подменяет любой ответ приложения на `PlainTextResponse` «Content Too Large»: ни Problem Details, ни `X-Trace-ID`. Перехватить его ответ по `Content-Length`, как предлагалось в обсуждении задачи, можно, но тогда поток без длины отказывает встроенным `HTTPException` — общим `HTTP_ERROR`, а не своим кодом. Своё middleware на чистом ASGI (~60 строк, как `OriginMiddleware`) даёт оба пути одним ответом через `problem_response`.

### Тело читается в middleware, а не исключением из `receive`

Альтернатива — считать байты в обёртке `receive` и бросить исключение на превышении. Ручка с JSON-телом читает его внутри FastAPI, а тот превращает любое исключение чтения тела, кроме `HTTPException`, в `400 There was an error parsing the body`: код `413` потерялся бы. Поэтому middleware само читает тело с подсчётом, на превышении отвечает `413` и приложение не вызывает; дочитанное в пределах лимита отдаёт приложению одним сообщением `http.request`, дальнейшие `receive` (`http.disconnect` для SSE) — от сервера как есть. Память — та же, что раньше тратил `request.body()`, но не больше лимита: пока работает ручка, тело лежит одной копией, в кадре middleware ссылок на него не остаётся — куски отпускаются сразу после склейки, а склейку держит только очередь `replay`, которая отдаёт её приложению. На склейке кратко лежат две копии: куски и результат. Держит это тест на `tracemalloc`: в `verify_hmac` вебхука в 25 МиБ занято не больше 1,2 тела.

Запрос без `Content-Length` и без `Transfer-Encoding` по HTTP/1.1 (RFC 9112, 6.3) тела не имеет — он идёт мимо middleware, не дожидаясь тела: `GET` и поток SSE не меняются. Uvicorn у нас только с h11 (HTTP/1.1); на HTTP/2 без этих заголовков тело возможно — тогда условие пересматривается.

### Порядок middleware

`TraceIdMiddleware` → `OriginMiddleware` → `RequestBodyLimitMiddleware` → приложение. `trace_id` нужен ответу `413`; чужой `Origin` отказывает `403`, не читая тела; лимит — до роутинга, разбора тела, сессии и подписи.

### `Connection: close` и `Expect: 100-continue`

При отказе по `Content-Length` тело у сервера не запрашивается: uvicorn не отвечает `100 Continue`, и клиент с `Expect` тело не шлёт вовсе. Недочитанное тело осталось бы в соединении, поэтому ответ несёт `Connection: close`. Проверено на uvicorn 0.54 (h11) с curl: 30 МиБ с `Content-Length` — `413 application/problem+json` с `X-Trace-ID`, отправлено 0 байт; chunked 30 МиБ — `413` после ~27,5 МиБ (лимит плюс буферы сокета); подписанная маленькая доставка — `202` как раньше.

### Сжатое тело

Приложение не распаковывает тело запроса (`Content-Encoding` не обрабатывается, `GZipMiddleware` сжимает только ответы). Лимит считает байты, которые лежат в памяти, и сжатая «бомба» его не обходит. Подпись GitHub считается по телу как оно пришло.

## Risks / Trade-offs

- Тело доставки до 25 МиБ без аутентификации всё ещё читается в память. Лимит контейнера API — 512 МБ, сам процесс — около 130 МиБ, остаётся около 380 МиБ: семь доставок по 25 МиБ, пришедших одновременно (по 50 МиБ на склейке), или пятнадцать уже прочитанных; разбор JSON доставки добавляет объекты сверх этого. Ограничение числа соединений к вебхуку (`limit_conn` в nginx) — у прокси перед API, пока не настроено.
- `Content-Length` не из цифр ASCII middleware длиной не считает (`isascii() and isdigit()`: голый `isdigit()` принимает «²», и `int()` дал бы `500`). Без `Transfer-Encoding` такой запрос идёт мимо подсчёта, как запрос без тела. Под uvicorn это недостижимо — h11 отвечает `400` сам; на другом сервере, который такой заголовок пропустит, тело ничем не ограничено.
