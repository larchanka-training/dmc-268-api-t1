## Context

Последнее из трёх последовательных изменений на ветке
`feat/review-pipeline-and-api`: очередь → пайплайн → **REST API**. Технически
не зависит от первых двух (читает то, что уже давно умеют писать
существующие адаптеры), но логически завершает DoD тикета — без него
результат пайплайна виден только через прямой SQL.

## Goals / Non-Goals

**Goals:**
- Три read-эндпоинта, отражающие уже существующую модель данных без
  изменения её контракта.
- Пагинация с предсказуемым, скучным поведением (`limit`/`offset`, дефолт и
  потолок).
- 404 на несуществующий `repository_id`/`review_run_id`, а не пустой ответ
  или 500.

**Non-Goals:**
- Авторизация/аутентификация запросов — нет ни JWT, ни `accounts` в
  кодовой базе; изобретать их мимо запланированного шва не входит в эту
  задачу.
- Запись (создание/изменение репозиториев, ревью по запросу) — только
  чтение того, что уже пишут вебхук и воркер.
- Курсорная пагинация, сортировка по нескольким полям, фильтры — `limit`/
  `offset` и сортировка по одному полю достаточны для текущего фронтенда;
  усложнять раньше первого реального запроса нет смысла.

## Decisions

**Пагинация — `limit`/`offset`, не курсор.** Скучный, предсказуемый вариант;
у него есть потолок (глубокий `OFFSET` дорог на больших таблицах), но
таблицы, о которых речь, сегодня не настолько велики, чтобы это иметь
значение, а курсорная пагинация — сложность, окупающаяся только при реальной
проблеме с производительностью. Дефолт `limit=50`, потолок `limit=200`;
превышение потолка — тихо обрезается до него, а не 400: постраничный
навигатор фронтенда не должен знать точное число раньше, чем получит первую
ошибку.

**Список PR — вложен в репозиторий, не отдельный плоский эндпоинт.**
`GET /api/v1/repositories/{repository_id}/pull-requests`, а не
`GET /api/v1/pull-requests?repository_id=...`: соответствует тому, как
`MergeRequestRepo.find_by_number` уже требует `repository_id`, и как
фронтенд реально листает — от репозитория к его PR, а не по всем PR разом.

**`GET /api/v1/reviews/{review_run_id}` включает находки в теле, не как
отдельный эндпоинт.** Прогон без находок бессмысленно смотреть отдельно от
них; `FindingRepo.list_for_run` уже даёт ровно то, что нужно — фронтенду
нужен один связный ответ, а не второй поход за находками отдельным запросом.

**Новые методы портов, не новые порты.** `RepositoryRepo.list_all` и
`MergeRequestRepo.list_for_repository` — это тот же порт хранения с ещё
одним методом чтения, а не новая точка расширения; никакого нового вызывающего
кода за пределами этих трёх роутеров они не заводят.

**Без авторизации.** REST сегодня открыт для любого, кто достучится до
API — согласуется с тем, что в кодовой базе нет ни одного механизма
аутентификации вообще (JWT — только упомянут в `openspec/config.yaml` как
намерение, не начат ни одним портом). Добавлять её здесь означало бы
изобретать половину незапланированного шва ради трёх GET.

## Risks / Trade-offs

[`OFFSET`-пагинация деградирует на большом смещении] → таблицы сегодня
малы (без реального продакшена); переход на курсорную пагинацию — локальная
правка трёх роутеров и двух методов портов, не архитектурное изменение.

[Эндпоинты без авторизации читают чужие данные, если сервис когда-либо
получит более одного клиента] → задокументированный Non-Goal; тот же
тикет, что добавит `accounts`/JWT, естественно оборачивает эти три
роутера проверкой доступа.

## Migration Plan

Только чтение существующих таблиц, миграций нет. Откат — two-way door:
ревёрт коммита убирает эндпоинты, ничего не оставляя позади.
