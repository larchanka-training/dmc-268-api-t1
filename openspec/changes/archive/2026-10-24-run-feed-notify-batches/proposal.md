## Why

Ревью смёрженного PR #137 (NOTIFY вместо опроса) нашло регрессию: поток читает изменения только по сигналу, а одно чтение берёт не больше `BATCH_LIMIT` (200) прогонов за курсором. Когда один коммит меняет больше — массовый `stale_sweep` переводит все зависшие прогоны в `failed` разом, — уведомления склеиваются в один сигнал, и остаток ждёт следующего постороннего изменения сколько угодно. Опрос дочитывал его через секунду. Воспроизведено: из 250 изменений за 100 секунд тишины пришло 200.

Там же — две доработки надёжности слушателя.

## What Changes

- Чтение, упёршееся в `BATCH_LIMIT` строк за курсором, сразу повторяется без ожидания сигнала. Окно перепроверки под курсором в счёт не идёт — иначе полное окно гоняло бы чтения по кругу.
- Соединение `LISTEN`: `tcp_user_timeout = 60 с` — пульс `SELECT 1` в мёртвое соединение без RST не висит ~15 минут ретрансляций TCP.
- Подписки слушателя — в `weakref.WeakSet`: подписка, брошенная без `close()`, не копится до обрыва `LISTEN`.

## Capabilities

### Modified Capabilities

- `review-rest-api`: все изменения одного коммита доходят до потока, даже больше одной пачки.
