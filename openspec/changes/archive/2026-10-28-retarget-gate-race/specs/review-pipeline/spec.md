## MODIFIED Requirements

### Requirement: Ревью упавшего прогона не дублируется следующим

Перед публикацией находок прогон SHALL искать на GitHub ревью своего бота с маркером каждого прогона своего PR, упавшего на `publishing` без записей в `published_comments` и созданного позже последнего прогона PR с записями, и SHALL записывать найденное этому прогону, сопоставляя inline с его находками по файлу, стороне, строке и тексту. Поиск SHALL быть best-effort: сбой хостинга и параллельный подбор того же ревью SHALL NOT останавливать публикацию.

#### Scenario: Воркер умер после записи ревью на GitHub

- **WHEN** GitHub записал ревью прогона, воркер умер до записи `published_comments`, повторная доставка перевела прогон в `failed`, и новый прогон того же PR снова нашёл замечание к той же строке
- **THEN** новый прогон записывает ревью упавшего в `published_comments`, своего inline-комментария к этой строке не публикует, а находку связывает с находкой треда

#### Scenario: Упавший прогон ничего не опубликовал

- **WHEN** прогон упал на `publishing`, а ревью с его маркером на GitHub нет
- **THEN** записей для него не появляется, новый прогон публикует замечание как обычно

#### Scenario: Поиск ревью упавшего прогона не удался

- **WHEN** GitHub отвечает ошибкой на поиск ревью упавшего прогона
- **THEN** сбой попадает в лог, новый прогон публикует ревью и завершается `completed`

#### Scenario: Две находки упавшего прогона на одной строке

- **WHEN** у упавшего прогона две находки на одной строке, а опубликована была одна (другую покрыл тред)
- **THEN** id комментария записывается находке с тем же текстом

#### Scenario: Упавший прогон старше опубликованного

- **WHEN** после упавшего прогона другой прогон PR опубликовал ревью
- **THEN** следующие прогоны ревью упавшего на GitHub не ищут

#### Scenario: Два прогона подбирают одно ревью

- **WHEN** два прогона PR одновременно нашли ревью одного упавшего прогона, и второй получил отказ уникального индекса
- **THEN** второй откатывает подбор и публикует своё ревью

### Requirement: Отменённый прогон не выставляет merge gate

Прогон перед выставлением check run SHALL перечитать свой статус; если его отменили (`cancelled`) сменой целевой ветки во время работы, check run SHALL NOT выставляться. После выставления check run прогон SHALL перечитать последний прогон на head и поправить check run, если отвечает за head уже не он.

#### Scenario: Ветку сменили во время публикации

- **WHEN** прогон опубликовал ревью, а в базе он уже `cancelled`
- **THEN** check run этим прогоном не выставляется

#### Scenario: Ветку сменили между проверкой статуса и check run

- **WHEN** прогон выставил `success`, а приём к этому моменту уже закоммитил отмену и новый прогон
- **THEN** прогон выставляет блокировку смены ветки, а если новый прогон уже `completed`, то его итог
