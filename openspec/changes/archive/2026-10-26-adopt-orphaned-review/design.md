## Context

Публикация (`publish_review`) отсеивает находку, о которой уже говорит тред бота (`thread_coverage`); треды берутся из `published_comments` всех прогонов PR. Запись `published_comments` идёт отдельной транзакцией после `POST …/reviews`. Смерть воркера между ними оставляет на GitHub ревью с маркером прогона и ни одной записи в базе. Повторная доставка такой прогон не доводит (`review-pipeline`, «Повторная доставка незавершённого прогона»), а переводит в `failed` с `failed_stage = publishing`.

## Goals / Non-Goals

**Goals:** следующий прогон PR не дублирует замечания ревью, которое упавший прогон успел опубликовать; merge gate видит его `critical`.

**Non-Goals:** доводить упавший прогон до `completed`; перезапускать ревью после смерти воркера автоматически; лимит повторных доставок в очереди - отдельные задачи из отчёта #222.

## Decisions

### D1. Подбирать сироту в следующем прогоне, а не на повторной доставке

Повторная доставка - не единственный путь в `failed`: выметатель зависших прогонов (`stale_sweep`) переводит туда же, и без сообщения в очереди. Следующий прогон PR публикует всегда через `publish_review`, поэтому поиск там закрывает оба пути одной точкой. Альтернатива - поиск на повторной доставке перед `failed` - не покрыла бы выметатель.

### D2. Кандидаты - только `failed` на `publishing` без `published_comments`

Прогон, упавший раньше `publishing`, ревью не постил. Прогон с записями уже виден отсеву. Так поиск по GitHub идёт только после смерти на публикации, а не в каждом прогоне. Выборка - метод хранилища `list_unpublished_failures` (запрос с `NOT EXISTS`).

### D3. Сопоставление inline - по находкам упавшего прогона

Находки упавшего прогона записаны до публикации (`findings`). Черновики строятся из них той же функцией, что и при публикации, и сопоставляются с комментариями найденного ревью существующим `_map_fetched_inline_comments` - по файлу и тексту: `GET …/reviews/{id}/comments` отдаёт `line` и `side` пустыми (#265), а текст комментария сервис пишет сам, поэтому две находки на одной строке различаются. Находка, которую упавший прогон не постил (покрыта тредом), просто не сопоставится. Новый метод порта `find_published_review` переиспользует `_find_review_by_marker` и чтение комментариев ревью.

### D3a. Кандидаты - упавшие после последней публикации PR

Сравнивается `last_progress_at` упавшего прогона (его ставит переход в `failed`) с `max(published_at)` записей PR: прогон, упавший до последней публикации, тот её прогон уже проверял. Время создания не годится: прогон, умерший на `publishing`, выметатель переводит в `failed` позже, чем создаётся следующий. Два прогона, подбирающие одно ревью одновременно, упираются в `uq_published_comments_provider_comment_id`; ограничение входит в `_RACE_CONSTRAINTS`, отказ приходит как `ActiveRunConflict`, подбор откатывается, публикация идёт дальше.

### D4. Best-effort

Поиск ходит в GitHub перед публикацией. Его сбой не должен ронять прогон: `failed` после него привёл бы к ещё одному прогону. `VcsError` - warning в лог, публикация идёт без подбора.

## Risks / Trade-offs

- [Лишний запрос `GET …/reviews` в прогоне после сироты] → только при наличии кандидатов; после записи прогон кандидатом быть перестаёт.
- [Человек удалил ревью сироты] → не найдено, замечание публикуется заново - так и должно быть.
