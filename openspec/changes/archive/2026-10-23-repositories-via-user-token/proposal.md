# Proposal

## Why

`GET /repositories/available` и `POST /repositories` (#41, #96, хотфикс #104) сами решали, кто что видит и может подключить: обходили все установки приложения токеном установки и на каждый репозиторий спрашивали роль пользователя (`collaborators/{login}` и `.../permission`). Независимое ревью по итогам #104 (larchanka-training/dmc-268-api-t1#107) нашло у этого подхода целый класс проблем:

- утечка имён чужих приватных репозиториев — уже случилась на стенде, закрыта хотфиксом обходным путём, причина не установлена;
- `POST` отличал «нет в установке» (`404`) от «есть, но не виден» (`403`) — оракул существования репозитория;
- 1–2 запроса к GitHub на каждый репозиторий всех установок при каждом показе, из лимита **установки** (тот же, которым живут ревью), без кэша; вход открыт любому аккаунту GitHub — любой мог выжечь лимит и сломать ревью установки;
- одна приостановленная установка роняла список всем в `502`;
- права проверялись по логину, сохранённому при входе, а не по id.

У GitHub для этого есть готовое: `GET /user/installations` и `GET /user/installations/{installation_id}/repositories` с токеном пользователя GitHub App возвращают ровно пересечение «доступно приложению» ∩ «доступно пользователю», с `permissions` пользователя на каждом репозитории. Доступ решает GitHub, лимит — пользовательский. Токен мы и так получаем при входе — и выбрасывали.

## What Changes

- Токен пользователя (user access token GitHub App, а при включённом истечении — и refresh token со сроками) сохраняется при сессии, только зашифрованным (AES-256-GCM, ключ — новая настройка `USER_TOKEN_ENCRYPTION_KEY`, на стенде — секрет `USER_TOKEN_KEY_DMC268_T1`). Таблица `provider_tokens`, миграция `0007`.
- Истёкший токен обменивается по refresh token; отказ GitHub в токене или refresh token, отсутствие токена (сессия открыта до этой правки) — `401 UNAUTHENTICATED`, сессия закрывается.
- Выход, вход поверх сессии и уборка истёкших сессий удаляют токен вместе с сессией.
- `GET /repositories/available` — через `/user/installations…` по токену пользователя; `POST /repositories` ищет репозиторий в том же списке: нет его — `404` (без различия «нет в установке» и «не виден»), без `permissions.admin`/`maintain` — `403`.
- **BREAKING (поведение, не схема)**: удалён старый механизм — обход установок токеном установки для этих ручек, проверки `collaborators`, роль `RepositoryRole`. Схема ответов не меняется, фронтенд без правок.

## Capabilities

### Modified Capabilities

- `review-rest-api`: «Список репозиториев, доступных для подключения», «Подключение репозитория», «Отказы подключения репозитория» — по токену пользователя; новое требование «Непригодный токен пользователя закрывает сессию».
- `user-auth`: вместо «Токены провайдера не хранятся» — «Токен провайдера хранится при сессии зашифрованным»; «Выход» и «Истёкшие сессии удаляются» удаляют и токен.

## Impact

- Домен: `Secret`, `ProviderGrant`, `ProviderToken`, `RepositoryPermissions`, `app/domain/provider_token.py`, `app/domain/repository_access.py` (переписан), удалён `RepositoryRole`.
- Приложение: порт `ProviderTokenRepo`, порты `OAuthProvider` (`exchange_code` → `OAuthLogin`, `refresh`) и `InstallationCatalog` (`list_repositories(access_token)`), use case `user_token.py`.
- Инфраструктура: `token_cipher.py`, `SqlAlchemyProviderTokenRepo`, миграция `0007_add_provider_tokens.py`, адаптеры GitHub OAuth и каталога.
- Деплой: `infra/` (переменная `user_token_encryption_key` с проверкой формата), `deploy.yml`, `docker-compose.yml`, `.env.example`, README.
- Пользователи с сессией, открытой до деплоя, на экране репозиториев войдут заново.
