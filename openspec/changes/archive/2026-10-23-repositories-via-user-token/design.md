# Design: список и подключение репозиториев по токену пользователя

## Context

Мотивация — в `proposal.md`. Решения change `repository-access-roles` (D1–D4) и `repository-visibility-private` заменяются этим: роль и видимость больше не вычисляет сервис, их отдаёт GitHub по токену пользователя.

## Goals / Non-Goals

**Goals:**

- Кто что видит и может подключить, решает GitHub; ответ сервиса не раскрывает репозитории, которых пользователь не видит, и не отличает «не виден» от «нет».
- Токен пользователя хранится только зашифрованным, не попадает в логи, ответы, браузер, `repr` и исключения.
- Один механизм для этих ручек — старый удалён.

**Non-Goals:**

- Ограничение входа членами организации; перевод других ручек на токен пользователя.
- Поле `can_connect` в ответе списка (#106) — отдельно; `permissions` для него уже есть.
- Ротация ключа шифрования без перелогина.

## Decisions

### D1. Отдельная таблица `provider_tokens`, ключ — `session_id`

Токен привязан к сессии, а не к пользователю: у пользователя может быть несколько сессий, и выход из одной не должен отзывать другие. Таблица, а не колонки `sessions`:

- строку сессии читает каждый запрос (`authenticate`), токен — только две ручки; шифротекст не ездит лишний раз;
- блокировка на время refresh (D4) берётся на строку токена, а не на сессию;
- «токена нет» — отсутствие строки, а не четыре nullable-колонки с правилом «все или ничего».

`session_id` — первичный ключ и внешний ключ на `sessions` с `ON DELETE CASCADE`: выход, вход поверх сессии (удаляет прежнюю), уборка истёкших (`delete_expired`) и удаление пользователя удаляют токен без отдельного кода. Колонки: `access_token_encrypted`, `access_expires_at`, `refresh_token_encrypted`, `refresh_expires_at`; сроки `NULL` — токены без истечения (у App выключено истечение user access token). Оба режима поддержаны: `expires_in` и `refresh_token_expires_in` из ответа GitHub переводятся в абсолютные моменты чистой функцией `token_from_grant(grant, now)`.

### D2. Шифрование: AES-256-GCM в адаптере хранения

- Ключ — `USER_TOKEN_ENCRYPTION_KEY`, 32 байта в base64 (`openssl rand -base64 32`), `SecretStr`. Формат проверяет валидатор настроек: битый ключ роняет старт, сообщение называет настройку и не печатает значение (`hide_input_in_errors`).
- Пустой ключ: репозиторий токенов не пишет и не читает (`ProviderTokenUnavailable`), вход отвечает `provider_unavailable` и пишет причину в лог, контейнер предупреждает при старте. Токен открытым не пишется никогда. На стенде пустой ключ невозможен: переменная Terraform без значения по умолчанию с проверкой формата роняет `apply`, а секрет без значения GitHub Actions передаёт пустой строкой.
- Шифротекст: байт версии, 12 байт случайного nonce, шифротекст с тегом. Associated data — id сессии и имя поля: шифротекст, скопированный в другую строку или в другое поле, не расшифровывается.
- Шифрует адаптер (`SqlAlchemyProviderTokenRepo` с `TokenCipher`), а не use case: это свойство хранения, домен и приложение работают с `Secret` — обёрткой, чей `repr`/`str` не раскрывает значение. AES-GCM, а не Fernet: 256-битный ключ и associated data, которых у Fernet нет.
- Чужой ключ или повреждённая запись — `ProviderTokenUnavailable`, use case закрывает сессию (D5).

### D3. Список и подключение через `/user/installations…`

Порт `InstallationCatalog.list_repositories(access_token)`: `GET /user/installations`, затем для каждой установки `GET /user/installations/{id}/repositories`, оба постранично `per_page=100` до короткой страницы. Каждый репозиторий — `provider_id`, `full_name`, `default_branch`, `permissions` (`admin`, `maintain`). Адаптер только переводит ответ:

- приостановленная установка (`suspended_at` не `null`) пропускается — ревью в ней не работают, и её отказ не должен ронять список;
- `404` на репозиториях установки (удалена между запросами) — установка пропускается;
- `401` — `ProviderTokenRejected`; сеть, `429`, `5xx` — `VcsUnavailableError`; прочие статусы и неожиданное тело, включая `null` в полях и `bool` вместо id, — `VcsError`. Всё, кроме `401`, — `502 SCM_UNAVAILABLE`, а не `500`;
- `maintain` отсутствует в примере ответа документации (там `admin`, `push`, `pull`), но есть в настоящем ответе; нет поля — права maintain нет.

`POST /repositories` ищет `provider_id` в том же списке. Порядок: не `github` или нет в списке — `404 REPOSITORY_NOT_IN_INSTALLATION` (нет в установках и не виден пользователю — один ответ, без оракула); `can_connect(permissions)` (`admin or maintain`, чистая функция в домене) — иначе `403`; уже подключён — `409`; иначе `201`. `installation_id` не нужен ни списку, ни записи и не хранится.

### D4. Refresh и гонка двух запросов одной сессии

`call_with_user_token(uow, oauth, session_id, now, call)`:

1. Прочитать токен; не нужен refresh (`needs_refresh`: срок есть и до него меньше 5 минут — запас на несколько страниц подряд) — использовать.
2. Нужен — в новой транзакции `SELECT … FOR UPDATE` строки токена. Перечитать: если другой запрос уже обновил токен, использовать его. Иначе, если refresh token жив (`can_refresh`), обменять его (`POST /login/oauth/access_token`, `grant_type=refresh_token`), сохранить новую пару и закоммитить — блокировка снимается коммитом.

Refresh token у GitHub одноразовый: без блокировки два параллельных запроса одной сессии (две вкладки, список и подключение подряд) потратили бы его оба, второй получил бы `bad_refresh_token`, и сессию закрыло бы зря. Со строковой блокировкой второй ждёт первого и видит уже свежий токен. Блокировка держится на время одного HTTP-запроса к GitHub (таймаут клиента 10 секунд) и касается только строки этой сессии; refresh случается раз в 8 часов на сессию. Это осознанное исключение из правила «соединение не ждёт GitHub». Проверено интеграционным тестом на PostgreSQL: два потока, один обмен.

Если обмен прошёл, а коммит упал, новый refresh token потерян, и следующий refresh закроет сессию — пользователь войдёт заново; цена редкая и безопасная.

Исходы обмена: `bad_refresh_token` — `ProviderTokenRejected` (закрыть сессию); прочие коды ошибки (`incorrect_client_credentials` и другие — это неверная настройка приложения, а не сессии), сеть, `5xx`, неожиданное тело — `OAuthProviderUnavailable`, `502`, сессия и токен остаются.

### D5. Непригодный токен закрывает сессию; старые сессии

Сессия закрывается (`sessions.delete`, каскадом токен), а ручка отвечает `401 UNAUTHENTICATED` и удаляет cookie (`Unauthenticated(had_cookie=True)`), когда токена нет, он не расшифровывается, refresh token истёк или отвергнут, или GitHub ответил `401` на токен. Просто `401` без закрытия завёл бы кабинет в петлю: `/auth/me` с той же cookie отвечал бы `200`, страница входа вернула бы на экран репозиториев.

Сессии, открытые до этой правки, строки в `provider_tokens` не имеют — для них это тот же путь: первый заход на экран репозиториев закрывает сессию, пользователь входит заново и получает токен. Остальные ручки старых сессий работают как раньше до перелогина или истечения 30 дней. Миграции данных нет: восстановить токен нечем.

### D6. Что удалено

- Обход установок для этих ручек: `GET /app/installations` с JWT, `GET /installation/repositories` installation-токеном, `GitHubInstallationCatalog` больше не зависит от `GitHubAppAuth` и `GitHubVcsGateway`.
- Поштучные проверки: `user_role`, `_is_collaborator`, `_translate_role`, `collaborators/{login}` и `.../permission`.
- `RepositoryRole`, `can_see`, `InstallationRepository.installation_id` и `.private`. `repository_access.py` переписан: в нём одна функция `can_connect(permissions)`.
- `GitHubAppAuth`, `GitHubVcsGateway` и всё, чем живут вебхуки и воркер, не тронуто.

### D7. Утечки

Токен — `Secret` от выхода из адаптера OAuth до заголовка `Authorization`; `repr`/`str` — `Secret('<скрыто>')`, у `TokenCipher` и `GitHubOAuthProvider` свои `repr` без ключа и секрета. Сообщения ошибок адаптеров называют URL и статус, исключения транспорта гасятся `from None` (в них запрос с заголовком). Логи use case — причина закрытия сессии без значений. Access-лог uvicorn токена не видит: он ходит только в заголовке исходящих запросов. Тесты проверяют отсутствие токенов в логах, ответах (тело и заголовки), `repr`, в сообщениях ошибок и в таблице (только шифротекст).

## Risks / Trade-offs

- Утечка ключа вместе с базой даёт токены живых сессий: права пользователя в пределах разрешений приложения (Metadata: read и то, что выдано App), до 8 часов для access token и до 6 месяцев для refresh token. Ключ живёт только в секрете стенда и окружении контейнера API.
- Смена ключа = перелогин всех (D5). Ротация с двумя ключами — когда понадобится.
- Формы ответов GitHub в тестах — из документации; против настоящего GitHub проверяется на стенде.
