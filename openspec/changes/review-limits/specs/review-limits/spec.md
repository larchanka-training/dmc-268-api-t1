# Spec Delta

## Purpose

Ограничение расхода модели на прогон и на репозиторий так, чтобы непроверенный код никогда не
проходил merge gate: покрытие прогона, бюджет токенов, размер области, суточная квота и
фильтрация шума.

## ADDED Requirements

### Requirement: Прогон хранит покрытие области ревью

Прогон SHALL определять покрытие: `complete` — проверена вся область, `partial` — часть, `none` — ничего, с причиной неполноты (`context_budget`, `token_budget`, `size_limit`, `quota`). Каждый файл области SHALL получать статус `reviewed`, `filtered`, `skipped_limit`, `skipped_budget` или `skipped_quota`. Непроверенные hunk'и SHALL NOT записываться в журнал.

#### Scenario: Часть не поместилась в бюджет

- **WHEN** прогон проверил 3 файла из 5, а 2 не вошли в бюджет токенов
- **THEN** покрытие `partial` с причиной `token_budget`, у файлов 3 статуса `reviewed` и 2 `skipped_budget`, в журнале только проверенные hunk'и

### Requirement: Отложенное сборкой контекста делает покрытие неполным

Hunk, который сборка контекста отложила в `omitted` по `context_max_tokens`, SHALL делать свой файл `skipped_budget`, а покрытие прогона — `partial` с причиной `context_budget`. Для файла, часть hunk'ов которого модель проверила, check run SHALL называть число непроверенных hunk'ов, а не весь файл. Правило SHALL действовать всегда, независимо от того, включены ли лимиты.

#### Scenario: Часть hunk'ов ушла в `omitted` при выключенных лимитах

- **WHEN** лимиты выключены, PR укладывается в их пределы, а сборка контекста отложила 10 hunk'ов в `omitted` по `context_max_tokens`, и открытых `critical` тредов нет
- **THEN** покрытие `partial` с причиной `context_budget`, файлы отложенных hunk'ов — `skipped_budget`, check run на head — `failure` «Ревью неполное» со списком этих файлов и числом непроверенных hunk'ов у частично проверенных

### Requirement: Неполное покрытие не проходит merge gate

Если у прогона, по которому строится check run на head, покрытие не `complete`, check run SHALL быть `failure` с перечнем непроверенных файлов и причиной, независимо от тредов. Правило SHALL действовать везде, где выставляется check run: после публикации, при пересчёте по треду и при поправке по последнему прогону. Conclusion `neutral` SHALL NOT использоваться.

#### Scenario: Конфигурация не поместилась

- **WHEN** PR меняет 60 файлов при пределе 50, и открытых `critical` тредов нет
- **THEN** check run на head — `failure` «Ревью неполное» со списком непроверенных файлов

#### Scenario: Закрыт тред у неполного прогона

- **WHEN** последний прогон на head `completed` с покрытием `partial`, и человек закрывает последний `critical` тред
- **THEN** пересчёт по треду выставляет `failure` по покрытию, а не `success`

### Requirement: Бюджет токенов прогона

Прогон SHALL иметь бюджет токенов на все вызовы модели — ревью, верификатор и повторы. Вызов, чья оценка вместе с израсходованным превышает бюджет, SHALL NOT отправляться. Область, не проверенная из-за бюджета, SHALL давать покрытие `partial` с причиной `token_budget`.

#### Scenario: Бюджет исчерпан до верификатора

- **WHEN** после ответа ревью в бюджете нет места на вызов верификатора
- **THEN** верификатор не вызывается, итог верификации — `unavailable`, находки публикуются после детерминированного отсева

### Requirement: Размер области ревью ограничен

Область ревью SHALL ограничиваться числом файлов и изменённых строк. Сверх предела SHALL проверяться часть: сначала hunk'и без записи журнала, затем перепроверяемые — с записью журнала с признаком находок; внутри — CI и инфраструктура (`.github/`, `Dockerfile*`, `infra/`, `*.tf`, скрипты деплоя), затем код, тесты, документация, по пути. Остальное SHALL получать статус `skipped_limit`.

#### Scenario: Большой PR с изменением CI

- **WHEN** PR меняет 120 файлов кода и `.github/workflows/deploy.yml` при пределе 50 файлов
- **THEN** `deploy.yml` входит в проверенные, покрытие `partial` с причиной `size_limit`

#### Scenario: Перепроверяемые hunk'и не вытесняют новые

- **WHEN** предел — 3 hunk'а, у трёх hunk'ов CI открытые находки прошлого прогона, и новый коммит добавляет hunk кода
- **THEN** новый hunk кода входит в проверенные раньше перепроверяемых

### Requirement: Суточная квота токенов репозитория

Расход токенов прогонов одного репозитория за скользящие сутки SHALL ограничиваться квотой. Прогон, взятый при исчерпанной квоте, SHALL завершаться `completed` без вызова модели с покрытием `none` и причиной `quota`. Остаток SHALL проверять следующий прогон — по новому push или повтору доставки; автоматически прогоны по восстановлению квоты SHALL NOT создаваться.

#### Scenario: Квота исчерпана

- **WHEN** у репозитория исчерпана квота, и приходит push в PR
- **THEN** модель не вызывается, check run на head — `failure` «квота исчерпана, ревью не было»

#### Scenario: Квота восстановилась

- **WHEN** квота репозитория снова позволяет прогон, и приходит push в PR, чей последний прогон завершён по квоте
- **THEN** новый прогон проверяет область по журналу, включая то, что не проверено по квоте

### Requirement: Шум отфильтровывается только по разметке целевой ветки

Кроме правил `webhook-intake`, из области ревью SHALL исключаться файлы, помеченные `linguist-generated` или `linguist-vendored` в `.gitattributes` на `base_sha`. Маркеры в самих файлах и `.gitattributes` из PR SHALL NOT исключать файлы. Исключённые файлы SHALL получать статус `filtered` и SHALL NOT делать покрытие неполным.

#### Scenario: Сгенерированный файл по разметке base

- **WHEN** `.gitattributes` на `base_sha` помечает `api/client.ts` как `linguist-generated`, и PR его меняет
- **THEN** файл `filtered`, покрытие прогона может быть `complete`

#### Scenario: Маркер `@generated` от автора PR

- **WHEN** PR добавляет новый файл с `// @generated` в первой строке
- **THEN** файл входит в область ревью
