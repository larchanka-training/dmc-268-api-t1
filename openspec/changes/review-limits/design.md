# Design

> Предложение, не утверждено. Применяется после `incremental-review`.

## Context

- Gate строят три места: публикация (`build_merge_gate_check`), пересчёт по закрытию треда и
  `settle_merge_gate` (#225). Все три берут последний `completed` прогон на head и умеют только
  `success`/`failure` по открытым `critical` тредам.
- `context_max_tokens` (32 000) отправляет не поместившееся в `omitted`, а прогон `completed`.
- Дубль доставки — последний прогон на коммит не `failed` и не `cancelled` (#225).
- `installation_id` приходит в каждом вебхуке и в `ReviewJob`, в базе его нет: `review-rest-api`
  запрещает его хранить, а API берёт его поиском `GET /repos/{full_name}/installation` с кэшем (#87).

## Goals / Non-Goals

**Goals:** расход ограничен на прогон и на репозиторий; ни одно превышение лимита не даёт
`success` на непроверенный код; добор непроверенного не требует ручных действий там, где это
возможно.

**Non-Goals:** лимиты частоты вебхуков и прогонов, backpressure, отсрочка (`defer`), бюджет
повторов — вынесены (см. сводный документ, «Не входит»); тарифы.

## Decisions

### D1. Покрытие не `complete` — `failure`, никогда `neutral`

`neutral` GitHub засчитывает обязательной проверке как пройденную, а на новом head он же снял
бы блокировку открытых `critical`. Покрытие входит в `build_merge_gate_check`: `partial`/`none`
→ `failure` «Ревью неполное: не проверено N файлов» с перечнем и причиной. Поскольку функция
одна на три места, пересчёт по треду и `settle_merge_gate` получают то же правило без
отдельного кода.

### D2. Кто добирает непроверенное

| Причина | Добор |
|---|---|
| `context_budget`, `token_budget`, `size_limit` | Новый push или повтор доставки: журнал помнит проверенное, следующий прогон берёт остаток. PR больше лимитов целиком не проверится никогда — gate остаётся `failure`, решает человек (разбить PR, поднять лимит, обход обязательной проверки администратором). |
| `quota` | Тоже новый push или повтор доставки. Автоматического прохода добора нет: он разом создавал бы прогоны всех открытых PR, и квота кончалась бы снова — это та же отсрочка (`defer`), которую вынесли. |

Неполный прогон не дубль (MODIFIED в `webhook-intake`), иначе повтор доставки отвечал бы
существующим прогоном, и остаток не проверился бы.

### D3. Приоритет при `size_limit`

Путь выбирает автор PR, поэтому правило «код раньше конфигурации» отрезало бы первыми
`.github/workflows`, `Dockerfile`, `infra/*.tf` — то, через что проще всего пронести бэкдор.
Порядок: CI и инфраструктура → код → тесты → документация; внутри класса — по пути.

Hunk'и с находками журнал не покрывает (D5 `incremental-review`), и они идут модели на каждом
push. Их отличает запись журнала с `has_findings = true`: у нового hunk'а записи нет совсем.
Поэтому `plan_scope` и при `size_limit`, и при `token_budget` берёт сначала hunk'и без записи
журнала, и только потом перепроверяемые; порядок классов — внутри каждой группы.
Иначе при бюджете на 3 hunk'а CI с открытыми находками остальной код не добирался бы никогда.

### D4. Квота — сумма `tokens_used` прогонов репозитория за сутки

Отдельной таблицы счётчиков нет: сумма по `review_runs` репозитория за скользящие 24 ч. Квота на
инсталляцию потребовала бы хранить `installation_id`, а действующее требование `review-rest-api`
его хранение запрещает, и change `repositories-one-list` выносит хранение из скоупа. Цена —
инсталляция с многими репозиториями получает квоту на каждый; для стенда это приемлемо.

### D5. Шум — только из того, что автор PR не контролирует

`.gitattributes` читается с `base_sha` (`linguist-generated`, `linguist-vendored`). Маркер
`@generated` в первых строках файла и `.gitattributes` из PR не учитываются: `// @generated` в
новом файле с бэкдором давал бы `filtered`, покрытие `complete` и `success`.

### D6. `omitted` — неполное покрытие без флага

Сборка контекста откладывает в `omitted` всё, что не влезло в `context_max_tokens`, а лимиты
этого change по умолчанию выключены. Если бы неполноту давали только лимиты, PR в их пределах с
отложенными hunk'ами получал бы `complete` и `success` по коду, которого модель не видела, —
ровно дыра из Why. Поэтому отложенный hunk всегда делает файл `skipped_budget`, а покрытие —
`partial` с причиной `context_budget`, при любых флагах. Отдельная причина, а не
`token_budget`: тот — бюджет на вызовы модели, его можно выключить, а этот предел действует
сегодня.

## Risks / Trade-offs

- Большой PR блокирован навсегда при включённом `size_limit` — осознанно, fail-closed.
- PR, который сегодня не влезает в `context_max_tokens`, после выкладки получает `failure`
  вместо молчаливого `success` (D6). С включённым `incremental-review` остаток добирает следующий
  прогон по журналу; без него повтор упрётся в тот же предел, и решает человек.
- Квота блокирует мердж всех PR репозитория до восстановления — осознанно; значение квоты
  конфигурируемо.

## Migration Plan

1. Миграция: `review_runs.coverage`, `coverage_reason`, `review_run_files` — nullable. `NULL` покрытия у старых прогонов читается как
   `complete`: так вели себя прогоны до этого change.
2. Лимиты со значением «выключено» по умолчанию; включение конфигурацией стенда. Покрытие по
   `omitted` (D6) флагом не выключается.

## Open Questions

- Числовые значения: бюджет токенов прогона, пределы файлов и строк, суточная квота —
  требуют нагрузочного прогона (`load.yml`).
