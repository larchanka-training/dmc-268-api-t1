## Context

Схема согласована в dmc-268-ui-t1#95 и `docs/GITHUB_APP.md` (PR #244): одна страница
«Репозитории» со всеми репозиториями установок, переключатель «Ревью», кнопка «Добавить
репозитории из GitHub», возврат с GitHub на Setup URL, мягкое выключение. Здесь — то, что
постановка оставила на change, и решения, принятые сверх неё.

Контракт первым: фронт (dmc-268-ui-t1#96) начинает после него. В первом шаге реализован
список, `DELETE` и Setup URL — заглушки `501` с полной схемой и описанием поведения;
миграция и реализация заглушек — следующий шаг (`tasks.md`, 2–4).

## Goals / Non-Goals

**Goals:** один список вместо двух; `install_url`; контракт выключения, повторного
включения и Setup URL; схема хранения мягкого выключения.

**Non-Goals:** свитчер «Авто-ревью» и ручки настроек (`GET`/`PUT …/settings` остаются
заглушками как есть); запуск ревью по вызову; `installation_id` в базе; обработка вебхуков
`installation` и `installation_repositories` (D10).

## Decisions

### D1. Список: из чего, в каком порядке, какие поля

Источник строк — ответ GitHub по токену пользователя, тот же, что у прежней
`/repositories/available` (`list_user_repositories`). Подключён ли репозиторий — из базы
одним запросом (`list_by_provider_ids`). Строки, которой нет в ответе GitHub, нет и в списке,
даже если репозиторий подключён: правило видимости прежнее.

`full_name` и `default_branch` берутся из ответа GitHub, а не из записи: репозиторий могли
переименовать, список показывает текущее имя. `connected_at` до миграции — `created_at`
записи: пока выключения нет, запись есть только у включённых. Use case —
`list_with_connections`, строка — `ListedRepository` с `record` (запись сервиса или `None`);
имя ручки и operationId `list_repositories` не меняются.

Порядок — только `full_name` без учёта регистра (`casefold`): у GitHub имя уникально без
учёта регистра, второй ключ не нужен, а сортировка устойчива. Прежний порядок «по времени
регистрации» не подходит: у неподключённых времени нет. Страница — срез в памяти,
как и раньше: строк не больше, чем GitHub отдаёт пользователю (до 50 страниц по 100).
`limit`/`offset`, потолок 200 и «конец — страница короче limit» не меняются.

Тип строки — новая модель `RepositoryListItem`; `RepositoryListResponse` сохраняет имя
(operationId `list_repositories` держат типы фронта). `GET /repositories/{id}` и `POST` по-
прежнему отдают `RepositoryResponse`: форма записи сервиса, а не строки списка. Сценарий
«тело совпадает со строкой списка» заменён на «тот же `id`».

Альтернатива — оставить две ручки и склеивать на фронте — отклонена постановкой.

### D2. `install_url` — slug из `GET /app`

Slug берётся у GitHub тем же запросом `GET /app` с JWT приложения, что уже даёт логин бота
(`GitHubVcsGateway.app_slug`, через него — `bot_login`): ответ запоминается в шлюзе, шлюз —
один на процесс в контейнере, так что запрос один на процесс API и общий с поиском своего
ревью. Отдельной настройки нет: slug нельзя рассинхронизировать с приложением, чьим ключом
сервис ходит в GitHub. Ключ у API-контейнера есть (`infra/app.tf`, `GITHUB_APP_ID` и
`GITHUB_APP_PRIVATE_KEY` — для приёма вебхуков).

`Container.app_slug` отдаёт `None`, если ключа нет (`github_app_configured`, GitHub не
спрашиваем) или `GET /app` не удался — сеть, HTTP-ошибка, ключ не подписывает, тело без
`slug`; тогда `install_url: null`, а список отвечает как обычно: он от ключа приложения не
зависит. Сбой запоминается в контейнере на 60 с (константа, не настройка): фронт грузит
страницы списка подряд, и без этого каждая ждала бы `GET /app` до таймаута (5 с на фазу
запроса) и писала бы своё предупреждение. В эти 60 с `install_url: null` без запроса к
GitHub, потом следующий список спросит снова. Удачный ответ запоминается в шлюзе навсегда. Ручка получает `get_app_slug` — вызываемое, а вызывает его в теле: при `422`
параметров к GitHub никто не идёт.

### D3. Кэш видимости: список читает кэш, Setup URL пишет свежий ответ

Прежде страница подключения (`/available`) всегда спрашивала GitHub и писала ответ в кэш,
поэтому только что поставленное приложение было видно сразу. Теперь страница одна, и
постановка оставляет кэш 30 с: список читает его, а свежий ответ в кэш пишет возврат с
GitHub (Setup URL, `CachedInstallationCatalog(read=False)`). Зависимость
`get_refreshing_catalog` возвращена вместе с Setup URL.
`docs/BACKEND_ARCHITECTURE.md` говорит то же: список читает кэш, свежий ответ пишет возврат с
установки (Setup URL).

Цена: установка мимо Setup URL (прямо на GitHub) появляется в списке с задержкой до TTL. Подключение кэш по-прежнему не трогает:
подключён ли — из базы.

### D4. Мягкое выключение — колонка `repositories.connected_at`

Одна колонка `connected_at timestamptz NULL`: значение — когда ревью включено последний раз,
`NULL` — выключено. Она же даёт `connected_at` строки списка, отдельный флаг не нужен.

- Миграция: `ADD COLUMN connected_at timestamptz NULL`, затем `UPDATE … SET connected_at =
  created_at` — сейчас все записи включены. Таблица маленькая, одним `UPDATE`.
- Уникальный ключ `uq_repositories_provider_id` остаётся: запись на репозиторий одна,
  выключенная тоже. Так повторное включение возвращает прежний `id` и историю.
- `POST /repositories` после проверок прав: `UPDATE repositories SET connected_at = :now,
  full_name, default_branch, updated_at WHERE provider = :p AND provider_id = :id AND
  connected_at IS NULL RETURNING …` — нашлась выключенная запись, `201` с ней; иначе
  `INSERT … ON CONFLICT DO NOTHING` — вставилась, `201`; иначе `409`
  `REPOSITORY_ALREADY_CONNECTED`. Два параллельных включения выключенного: второй `UPDATE`
  после блокировки строки уже не совпадёт, вставка упрётся в ключ — `409`, интерфейс считает
  его успехом.
- `DELETE`: `UPDATE repositories SET connected_at = NULL, updated_at = :now WHERE id = :id`.
  Уже выключен — та же операция, `204`. Включение и выключение одновременно — их сериализует
  блокировка строки, побеждает последнее.
- `auto_review_enabled` для этого не годится: у него другой смысл (D8).

Альтернативы: физическое удаление невозможно — `merge_requests.repository_id … ON DELETE
RESTRICT`, и история должна остаться; булев флаг рядом с `created_at` — две колонки на одно
состояние; отдельная таблица подключений — без второго вызывающего.

### D5. Что видно у выключенного репозитория

В списке — `connected = false` и `connected_at = null`, а `id` остаётся: он отдаётся, если
запись есть, включённость решает `connected_at`. Интерфейс по `id` ведёт к настройкам и
истории выключенного репозитория. `GET /repositories/{id}`, его `/pull-requests` и прогоны в
`GET /reviews` и `GET /events` остаются по прежнему правилу видимости GitHub — история не
пропадает. `RepositoryResponse` в этом change не меняется. Адаптер `list_by_provider_ids`
отдаёт и выключенные записи; включённость решает use case списка по `connected_at`.

### D6. `DELETE /repositories/{id}`

`204` без тела. Порядок проверок: видимость по кэшу (как у `GET /repositories/{id}`) —
нет или не видит — `404 REPOSITORY_NOT_FOUND`, ответ один; права — запросом к GitHub
токеном пользователя мимо кэша (`user_repository`, как у `POST`): нет admin или maintain —
`403 REPOSITORY_MANAGE_REQUIRED`. `401` и `502` — как у остальных ручек репозиториев.
Прогон, уже поставленный в очередь до выключения, доводится до конца: воркер включённость
не проверяет (проще, и прогон уже оплачен).

Вебхук `pull_request` `opened`/`synchronize` выключенного прогона не создаёт и задачи не
ставит, ответ — `202 ignored`. Но на `head_sha` токеном установки ставится check run
`dmc-268-ai-review` `success` «Ревью выключено в сервисе» (`DISABLED_REVIEW_CHECK`, тот же
`set_merge_gate_check`, что у merge gate). README советует сделать проверку обязательной, а
выключить ревью может и maintain, тогда как ruleset правит только admin. Без check run каждый
новый push и PR висели бы в «Expected — Waiting for status». `success`, а не `neutral`: бот
ставит только `success` и `failure`. Проверка best-effort: сбой GitHub пишется в лог, ответ
остаётся `202 ignored`, без `502` и переотправки доставки; следующий push поставит её снова.
У незарегистрированного репозитория к GitHub не ходим.

Решено при реализации. Видимость по кэшу прошла, а свежий ответ GitHub
(`user_repository`) репозиторий уже не отдаёт (доступ отозван в пределах TTL) — тот же
`404 REPOSITORY_NOT_FOUND`, что у невидимого. Вебхук `pull_request_review_thread`
выключенного по-прежнему обрабатывается: он не создаёт прогонов и задач, отмечает закрытый
человеком тред и ставит на head `DISABLED_REVIEW_CHECK`, а не пересчёт по тредам. Пересчёт
поставил бы `failure` на head, где уже стоит «Ревью выключено», если открыт ещё один
`critical` тред, или `success` «Ревью пройдено» на непроверенный head. Без проверки вовсе
check run последнего прогона остался бы красным, и выключение ревью заблокировало бы мёрж.
Сбой GitHub здесь, как у включённого, — `502`, и GitHub переотправит доставку.

### D7. Setup URL `GET /api/v1/auth/github/setup`

Путь — в роутере `auth`: сюда GitHub возвращает браузер, как на callback входа; провайдер в
пути — литерал `github`, других установок нет. Требует сессию. Без сессии или с
недействительной cookie — `302` на `/login?redirect=/app/repositories`, cookie удаляется:
браузер пришёл с GitHub, JSON `401` показать некому, а после входа пользователь попадает на
«Репозитории» и повторяет «Добавить» (установка на GitHub уже сделана, подключить можно
переключателем). Сессия проверяется в теле ручки (`authenticate`), а не зависимостью,
которая ответила бы `401`. Параметры: `setup_action` — `install`, `update` или `request`,
обязателен; `installation_id` — целое больше нуля, при `request` его нет. Ошибка
параметров — `422` раньше проверки сессии и похода к GitHub.

Поведение:

1. `installation_id` ищется среди `GET /user/installations` по токену пользователя; нет —
   редирект с `setup_error=installation_not_found`. Свежий ответ GitHub пишется в кэш
   видимости (D3) по принципу best-effort: обход всех установок нужен только кэшу, и его сбой
   (`VcsError` на любой другой установке) пишется в лог, а подключение по найденной установке
   идёт дальше.
2. Подключает только `setup_action=install` при `repository_selection = selected` («Only
   select repositories»): репозитории установки, где у пользователя admin или maintain и
   которых ещё нет в базе. Выключенные (`connected_at IS NULL`) не включаются: выключение —
   явное решение пользователя. `setup_action=update` не подключает ничего, только обновляет
   кэш: `update` приходит и при правке чужого списка установки, и после «Добавить
   репозитории» к установке, где пользователь часть репозиториев намеренно оставил
   выключенными. Записи у тех нет, и подключение «всех без записи» незаметно включило бы им
   ревью. Новый репозиторий после `update` включается переключателем. `all` — не
   подключается ничего.
3. Редирект `302` на `/app/repositories`: `?connected=<N>`; `setup_action=request` —
   `?requested=true`; GitHub не ответил или отказал — `?setup_error=provider_unavailable`,
   а в лог пишется текст ошибки с HTTP-статусом GitHub: `403` (SSO организации не авторизован
   для токена) так отличим от недоступного GitHub. Отдельного итога для `403` нет. Токен
   непригоден — сессия закрывается, и тот же редирект на вход, что без сессии.

Риск: это `GET` с побочным действием, cookie сессии `SameSite=lax` уходит при переходе по
ссылке с чужого сайта. Подделанный переход может включить ревью у репозиториев, где у жертвы
admin или maintain, в установке, которую она видит, и только у ещё не подключённых — то же,
что жертва сделала бы сама, но без её решения. Защита — `state`, привязанный к сессии, в
`install_url` и сверка на Setup URL; поле `install_url` зависит от сессии, форма ответа не
меняется. Сверяется `state` только у `setup_action=install`: `update` ничего не подключает, и
защищать в нём нечего, а с «Redirect on update» GitHub возвращает на Setup URL и после
правки установки в её настройках, где `state` нет.

Решено при реализации (шаг 3). Документация GitHub, «Sharing your GitHub App»
(https://docs.github.com/en/apps/sharing-github-apps/sharing-your-github-app): `state` в адресе
`installations/new?state=…` нужен, чтобы «return people back to that state after they install,
authenticate, or accept updates». «About the setup URL» про `state` молчит и говорит только про
`installation_id`: ему не доверять. Запуском на настоящем GitHub это **не проверено**: в этом
шаге стенда с установкой нет. Сделано так, что ошибка в предположении безопасна:

- `state` — HMAC-SHA256 с ключом-значением cookie `session` (`setup_state`,
  `app/domain/session.py`). Новых ключей и хранения нет; cookie `HttpOnly`, чужой сайт её не
  знает, а сам `state` cookie не раскрывает. `install_url` в `GET /repositories` несёт его.
- `install` без `state` этой сессии ничего не подключает и к GitHub не идёт: `?connected=0`.
  Итог тот же, что «нечего подключать», а в лог пишется предупреждение «state не совпал»
  (нет или чужой, без значения): по нему на стенде видно, вернул ли GitHub `state`.
  Если GitHub `state` не вернёт, Setup URL просто ничего не подключит, а репозитории
  включаются переключателем. Установка в обход `install_url` (прямо на GitHub) тоже даёт
  `?connected=0`.
- `setup_action=request` и `update` `state` не проверяют: ничего не подключают; `update`
  только обновляет кэш видимости.
- Редирект — только на свою константу `/app/repositories?<итог>`, итог — из констант и числа.

Проверить на стенде, приходит ли `state` (задача 3.3), — до того как прописывать Setup URL в
настройках GitHub App.

### D8. `auto_review_enabled` и свитчер «Авто-ревью»

В строке нового списка флага нет. Колонка, поле `RepositoryResponse` и ручки настроек
остаются как есть: правка ручек настроек — не этот change. Вебхук флаг по-прежнему не
проверяет. Флаг вернётся в интерфейс с запуском ревью по назначению ревьюером или
упоминанию: тогда «Ревью» вкл и «Авто-ревью» выкл будут значить «бот приходит, только если
позвали».

### D9. `409` на уже включённый остаётся

Код ответа не меняется, меняется только описание: интерфейс считает `409` успехом —
ревью уже включено, в том числе параллельным запросом.

### D10. Вебхуки `installation*` не обрабатываем

Не делаем: GitHub сам перестаёт слать события и отдавать репозиторий снятой установки (он
пропадает из списка и не ревьюится), обработка `suspend`/`unsuspend` выключала бы всё
владельца без возврата, а сопоставление владельца по имени (`installation_id` не хранится)
хрупкое — переименование ломает его молча. Эти события по-прежнему получают `202 ignored`.

## Risks / Trade-offs

- Установка мимо Setup URL (прямо на GitHub) видна в списке с задержкой до 30 с (D3).
- Приход `state` на Setup URL не проверен запуском (D7): не придёт — Setup URL ничего не
  подключает, репозитории включаются переключателем.
- Окно на стенде. Этот PR меняет форму `GET /repositories` (`id` бывает `null`, в строке нет
  `auto_review_enabled`, `created_at` и `updated_at`) и убирает `/available`. Фронт на
  `develop` такой ответ не разберёт: его схема ждёт строковый `id` и эти поля. Сломается не
  только страница «Репозитории», но и всё, что берёт список через `useConnectedRepositories`:
  счётчик на «Обзоре» и фильтр «Репозиторий» в прогонах. Фронт этого change,
  dmc-268-ui-t1#98, можно мёржить только после всех трёх PR бэкенда: ему нужен `DELETE` (в
  api#247 он отвечает `501`) и Setup URL, без которого кнопка установки не возвращает в
  «Репозитории». Порядок: api#247 → api#248 → api#252 подряд, затем ui#98 с `pnpm api:sync` на
  голову `develop` бэкенда, затем ui#99 (страница «Помощь» описывает интерфейс из ui#98). Окно
  поломки — от мёржа api#247 до мёржа ui#98: три мёржа бэкенда, синхронизация контракта и
  мёрж фронта. Чтобы окно было коротким, ui#98 заранее готовится на sha ветки api#252
  (`pnpm api:sync <sha>`), а мёржи идут друг за другом без перерыва.
- Setup URL прописывать в настройках GitHub App после проверки `state` на стенде (D7).
- После повторного включения head, запушенный в выключенный период, остаётся с проверкой «Ревью выключено» до следующего push; так же в окне гонки чтения (D6).
- Пока GitHub не отвечает на `GET /app`, список раз в 60 с ждёт его до таймаута (5 с на фазу
  запроса), даже когда сам список отдан из кэша видимости (D2).

## Migration Plan

Шаг 1 (этот PR): контракт, список, удаление `/available`, `install_url` из `GET /app`. Шаг 2:
миграция `connected_at` с откатом (`DROP COLUMN`), реализация `DELETE`, повторного включения,
приёма вебхука выключенного (без прогона, с проверкой `success`) и Setup URL, приведение `docs/GITHUB_APP.md` к
сделанному, архив change.

Откат миграции `connected_at` снова включает выключенные репозитории (старый код считает
включённой любую запись, повторный upgrade заполнит колонку из `created_at`): состояние
выключения хранить негде.
