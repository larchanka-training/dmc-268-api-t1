## Context

Схема согласована в dmc-268-ui-t1#95 и `docs/GITHUB_APP.md` (PR #244): одна страница
«Репозитории» со всеми репозиториями установок, переключатель «Ревью», кнопка «Добавить
репозитории из GitHub», возврат с GitHub на Setup URL, мягкое выключение. Здесь — то, что
постановка оставила на change, и решения, принятые сверх неё.

Контракт первым: фронт (dmc-268-ui-t1#96) начинает после него. В первом шаге реализован
список, `DELETE` и Setup URL — заглушки `501` с полной схемой и описанием поведения;
миграция, реализация заглушек и вебхуки `installation*` — следующий шаг (`tasks.md`, 2–5).

## Goals / Non-Goals

**Goals:** один список вместо двух; `install_url`; контракт выключения, повторного
включения и Setup URL; схема хранения мягкого выключения.

**Non-Goals:** свитчер «Авто-ревью» и ручки настроек (`GET`/`PUT …/settings` остаются
заглушками как есть); запуск ревью по вызову; `installation_id` в базе.

## Decisions

### D1. Список: из чего, в каком порядке, какие поля

Источник строк — ответ GitHub по токену пользователя, тот же, что у прежней
`/repositories/available` (`list_user_repositories`). Подключён ли репозиторий — из базы
одним запросом (`list_by_provider_ids`). Строки, которой нет в ответе GitHub, нет и в списке,
даже если репозиторий подключён: правило видимости прежнее.

`full_name` и `default_branch` берутся из ответа GitHub, а не из записи: репозиторий могли
переименовать, список показывает текущее имя. `connected_at` до миграции — `created_at`
записи: пока выключения нет, запись есть только у включённых.

Порядок — `full_name` без учёта регистра (`casefold`), затем `provider_id`. Прежний порядок
«по времени регистрации» не подходит: у неподключённых времени нет. Страница — срез в памяти,
как и раньше: строк не больше, чем GitHub отдаёт пользователю (до 50 страниц по 100).
`limit`/`offset`, потолок 200 и «конец — страница короче limit» не меняются.

Тип строки — новая модель `RepositoryListItem`; `RepositoryListResponse` сохраняет имя
(operationId `list_repositories` держат типы фронта). `GET /repositories/{id}` и `POST` по-
прежнему отдают `RepositoryResponse`: форма записи сервиса, а не строки списка. Сценарий
«тело совпадает со строкой списка» заменён на «тот же `id`».

Альтернатива — оставить две ручки и склеивать на фронте — отклонена постановкой.

### D2. `install_url` — из настройки `GITHUB_APP_SLUG`

Slug уже известен VCS-шлюзу (`GET /app` с JWT приложения, логин бота), но список за ним к
GitHub не ходит: лишний запрос ключом приложения на каждую страницу, а сбой `GET /app`
сломал бы список, который от ключа приложения не зависит. Настройка — строка, пустая
означает `install_url: null`: кнопку интерфейс не показывает, остальное работает (так же
устроены прочие реквизиты App). Формат проверяется на старте: `^([a-z0-9][a-z0-9-]*)?$` —
slug идёт в путь URL. На стенде — переменная репозитория `APP_SLUG_DMC268_T1` →
`TF_VAR_github_app_slug` → `GITHUB_APP_SLUG`.

### D3. Кэш видимости: список читает кэш, Setup URL пишет свежий ответ

Прежде страница подключения (`/available`) всегда спрашивала GitHub и писала ответ в кэш,
поэтому только что поставленное приложение было видно сразу. Теперь страница одна, и
постановка оставляет кэш 30 с: список читает его, а свежий ответ в кэш пишет возврат с
GitHub (Setup URL, `CachedInstallationCatalog(read=False)`). Зависимость
`get_refreshing_catalog` без вызывающего удалена; Setup URL вернёт её.

Цена: пока Setup URL — заглушка, новый репозиторий появляется в списке с задержкой до TTL;
установка мимо Setup URL (прямо на GitHub) — тоже. Подключение кэш по-прежнему не трогает:
подключён ли — из базы.

### D4. Мягкое выключение — колонка `repositories.connected_at`

Одна колонка `connected_at timestamptz NULL`: значение — когда ревью включено последний раз,
`NULL` — выключено. Она же даёт `connected_at` строки списка, отдельный флаг не нужен.

- Миграция: `ADD COLUMN connected_at timestamptz NULL`, затем `UPDATE … SET connected_at =
  created_at` — сейчас все записи включены. Таблица маленькая, одним `UPDATE`.
- Уникальный ключ `uq_repositories_provider_id` остаётся: запись на репозиторий одна,
  выключенная тоже. Так повторное включение возвращает прежний `id` и историю.
- `POST /repositories` после проверок прав: `UPDATE repositories SET connected_at = :now,
  full_name, default_branch, updated_at WHERE provider = :p AND provider_id = :id AND
  connected_at IS NULL RETURNING …` — нашлась выключенная запись, `201` с ней; иначе
  `INSERT … ON CONFLICT DO NOTHING` — вставилась, `201`; иначе `409`
  `REPOSITORY_ALREADY_CONNECTED`. Два параллельных включения выключенного: второй `UPDATE`
  после блокировки строки уже не совпадёт, вставка упрётся в ключ — `409`, интерфейс считает
  его успехом.
- `DELETE`: `UPDATE repositories SET connected_at = NULL, updated_at = :now WHERE id = :id`.
  Уже выключен — та же операция, `204`. Включение и выключение одновременно — их сериализует
  блокировка строки, побеждает последнее.
- `auto_review_enabled` для этого не годится: у него другой смысл (D8).

Альтернативы: физическое удаление невозможно — `merge_requests.repository_id … ON DELETE
RESTRICT`, и история должна остаться; булев флаг рядом с `created_at` — две колонки на одно
состояние; отдельная таблица подключений — без второго вызывающего.

### D5. Что видно у выключенного репозитория

В списке — `connected = false`, `id = null`, `connected_at = null`, как у неподключённого:
переключатель «выкл». `GET /repositories/{id}`, его `/pull-requests` и прогоны в
`GET /reviews` и `GET /events` остаются по прежнему правилу видимости GitHub — история не
пропадает. `RepositoryResponse` в этом change не меняется. Адаптер `list_by_provider_ids`
отдаёт и выключенные записи; включённость решает use case списка по `connected_at`.

### D6. `DELETE /repositories/{id}`

`204` без тела. Порядок проверок: видимость по кэшу (как у `GET /repositories/{id}`) —
нет или не видит — `404 REPOSITORY_NOT_FOUND`, ответ один; права — запросом к GitHub
токеном пользователя мимо кэша (`user_repository`, как у `POST`): нет admin или maintain —
`403 REPOSITORY_MANAGE_REQUIRED`. `401` и `502` — как у остальных ручек репозиториев.
Прогон, уже поставленный в очередь до выключения, доводится до конца: воркер включённость
не проверяет (проще, и прогон уже оплачен).

### D7. Setup URL `GET /api/v1/auth/github/setup`

Путь — в роутере `auth`: сюда GitHub возвращает браузер, как на callback входа; провайдер в
пути — литерал `github`, других установок нет. Требует сессию; нет сессии — `401` JSON, как у
ручек кабинета: установку пользователь начинает из кабинета с живой сессией, отдельный
редирект на вход не нужен. Параметры: `setup_action` — `install`, `update` или `request`,
обязателен; `installation_id` — целое больше нуля, при `request` его нет. Ошибка
параметров — `422` раньше похода к GitHub.

Поведение (следующий шаг):

1. `installation_id` ищется среди `GET /user/installations` по токену пользователя; нет —
   редирект с `setup_error=installation_not_found`. Свежий ответ GitHub пишется в кэш
   видимости (D3).
2. `repository_selection = selected` («Only select repositories») — подключаются её
   репозитории, где у пользователя admin или maintain и которых ещё нет в базе. Выключенные
   (`connected_at IS NULL`) не включаются: выключение — явное решение пользователя, а `update`
   приходит и при правке чужого списка. `all` — не подключается ничего.
3. Редирект `302` на `/app/repositories`: `?connected=<N>`; `setup_action=request` —
   `?requested=true`; GitHub не ответил — `?setup_error=provider_unavailable`. Токен
   непригоден — `401` с закрытием сессии, как везде.

Риск: это `GET` с побочным действием, cookie сессии `SameSite=lax` уходит при переходе по
ссылке с чужого сайта. Подделанный переход может включить ревью у репозиториев, где у жертвы
admin или maintain, в установке, которую она видит, и только у ещё не подключённых — то же,
что жертва сделала бы сама, но без её решения. Защита — `state`, привязанный к сессии, в
`install_url` и сверка на Setup URL; GitHub, по документации, передаёт `state` на Setup URL —
проверить запуском на следующем шаге и, если работает, добавить (поле `install_url` станет
зависеть от сессии, форма ответа не меняется).

### D8. `auto_review_enabled` и свитчер «Авто-ревью»

В строке нового списка флага нет. Колонка, поле `RepositoryResponse` и ручки настроек
остаются как есть: правка ручек настроек — не этот change. Вебхук флаг по-прежнему не
проверяет. Флаг вернётся в интерфейс с запуском ревью по назначению ревьюером или
упоминанию: тогда «Ревью» вкл и «Авто-ревью» выкл будут значить «бот приходит, только если
позвали».

### D9. `409` на уже включённый остаётся

Код ответа не меняется, меняется только описание: интерфейс считает `409` успехом —
ревью уже включено, в том числе параллельным запросом.

### D10. Вебхуки снятия приложения

Подпись — как у остальных вебхуков. `installation_repositories` с `action = removed` —
выключаются репозитории из `repositories_removed` по `id`. `installation` с `action` `deleted`
или `suspend` — выключаются подключённые репозитории владельца установки: `installation_id` в
базе не хранится, но у приложения на аккаунт одна установка, поэтому владелец — это
`installation.account.login`, сверка с частью `full_name` до `/` без учёта регистра.
`unsuspend` и `added` ничего не включают: включает пользователь (переключатель или Setup URL).
Остальные действия — `202 ignored`. Риск: владельца переименовали, а `full_name` в записи
старый — такие репозитории не выключатся; вебхуки `pull_request` по ним тоже перестанут
приходить, так что бот всё равно молчит.

## Risks / Trade-offs

- Новая установка видна в списке с задержкой до 30 с, пока не реализован Setup URL (D3).
- `GET` Setup URL с побочным действием без `state` (D7) — до проверки `state` на GitHub.
- Ломающее изменение контракта: фронт переходит на новый список одновременно с удалением
  страницы подключения (dmc-268-ui-t1#96).

## Migration Plan

Шаг 1 (этот PR): контракт, список, удаление `/available`, `GITHUB_APP_SLUG`. Шаг 2:
миграция `connected_at` с откатом (`DROP COLUMN`), реализация `DELETE`, повторного включения,
игнорирования выключенного вебхуком, Setup URL и вебхуков `installation*`, приведение
`docs/GITHUB_APP.md` к сделанному, архив change.
