# Design

## Context

Мотивация - в `proposal.md`.
Здесь только то, что определяет подход.

- Контракт уже задан change `add-prompt-guard-and-reflection-pass` (#61, PR #63, design D1 и D10): порт `LlmGateway.complete(LlmRequest[T]) -> LlmResponse[T]`, запрос - собранные сообщения и Pydantic-модель ответа, ответ - её проверенный экземпляр, фактически ответившая модель и токены.
  Сбой транспорта - `LlmError`, ответ не по модели - `LlmOutputError`; пайплайн переводит первый проход в `failed`, верификатор - в `unavailable`.
- Адаптер может дописывать сообщения после исходных, но не менять и не удалять их (требование `review-prompt-assembly` из #61).
- Единственный адаптер - `StubLlmGateway`; `Container.llm_gateway()` возвращает его безусловно.
- `httpx` уже используется адаптером GitHub; `ollama`, `openai`, `instructor` в зависимостях нет.
- Пакет контекста ограничен `context_max_tokens` (32 000 по умолчанию) по оценке «байты / 4» (`app/domain/context_budget.py`); окно модели нигде не учитывается.
- Модель угроз (`docs/BACKEND_ARCHITECTURE.md`) называет self-hosted модель свойством безопасности, а переход на hosted - решением в области безопасности.
- Ollama по умолчанию работает с небольшим окном (`num_ctx`) и при переполнении обрезает запрос, а не отвергает его; через OpenAI-совместимую ручку Ollama окно не задаётся.
- `fetch_pr_metadata` возвращает заголовок, но не описание PR; сообщения коммитов шлюз VCS не достаёт.

Решения, принятые с владельцем задачи до design: Eurorouter - OpenAI-совместимый протокол; локальная модель основная, hosted - явный фоллбэк; структурированный ответ без Instructor.

## Goals / Non-Goals

**Goals:**

- Политика «код не покидает сеть без явного решения» обеспечена конфигурацией и проверена тестом, а не договорённостью.
- Свойства из #61 (исходные сообщения неизменны, ответ проверен моделью из запроса) держатся в любом адаптере, потому что цикл повторов один.
- Запрос, который модель обрезала бы, не уходит; конфигурация, при которой это неизбежно, не стартует.

**Non-Goals:**

- Точный подсчёт токенов токенизатором модели: оценка та же, что у бюджета пакета, плюс защита на стороне адаптера (D5).
- Разное окно для разных провайдеров, потоковый ответ, кэширование ответов, асинхронный транспорт.
- Развёртывание Ollama на стенде и выбор модели для него - DevOps; здесь только профиль `docker-compose` для локального прогона.

## Decisions

### D1. Два тонких адаптера на `httpx`, без SDK

- `OllamaGateway` - нативная ручка `POST /api/chat`: `format` - JSON Schema ответа, `options.num_ctx` - окно, `options.num_predict` - предел ответа, `options.temperature = 0`, `stream = false`.
  Токены - `prompt_eval_count + eval_count`, модель - поле `model` ответа.
- `OpenAiCompatibleGateway` (Eurorouter) - `POST {base}/chat/completions`: `response_format = {"type": "json_schema", "json_schema": {"name", "schema", "strict": false}}`, `max_tokens`, `temperature = 0`, ключ в `Authorization: Bearer`.
  Токены - `usage.total_tokens`, модель - поле `model` ответа.

Почему нативная ручка для Ollama, а не один OpenAI-адаптер на оба провайдера: через `/v1/chat/completions` Ollama не принимает `num_ctx`, и запрос длиннее окна по умолчанию обрезается с начала - вместе с системным сообщением, на котором держится защита из #61.

`strict: false`, потому что строгий режим OpenAI требует, чтобы каждое поле было обязательным, а у `ReviewOutput` есть поля со значением по умолчанию; проверку всё равно выполняет наша модель (D2).

`temperature = 0` - воспроизводимость ответа для eval (#57, #62).

Альтернативы:

- **SDK `ollama` и `openai`.** Две зависимости ради двух POST-запросов; ни один SDK не даёт того, чего нет в `httpx`, а повторы и ротация у нас свои.
- **Один OpenAI-совместимый адаптер.** Отвергнут из-за молчаливой обрезки окна в Ollama (выше).

### D2. Структурированный ответ - один цикл повторов для всех адаптеров

`app/infrastructure/llm/structured.py`: функция `complete_structured(send, request, max_attempts)`.
Адаптер отдаёт ей только `send(messages) -> RawReply(text, model, tokens)` - перевод в протокол провайдера и обратно.
Цикл:

1. `send` с исходными сообщениями;
2. `request.response_model.model_validate_json(text)`; успех - `LlmResponse` с суммой токенов всех попыток;
3. ошибка - к исходным сообщениям дописывается одно `user`-сообщение: «Предыдущий ответ не прошёл проверку схемы» и список `путь: вид нарушения` из `ValidationError.errors(include_input=False, include_url=False)` (только `loc` и `type`); невалидный JSON - «ответ не JSON»;
4. после `max_attempts` (по умолчанию 2) - `LlmOutputError` с тем же списком.

Отвергнутый ответ модели обратно не передаётся: он написан моделью, читавшей код автора PR, и как реплика `assistant` прошёл бы мимо экранирования маркеров (`sanitize`), а значение поля в ошибке Pydantic - тот же канал.
Цена - модель исправляет ответ без своего черновика; для JSON по схеме и списка нарушений этого достаточно.

Альтернатива - **Instructor**: re-ask из коробки, но новая зависимость, повтор с эхом ответа (ровно то, от чего отказались выше) и поведение, которое пришлось бы проверять в каждой версии библиотеки.

### D3. Фоллбэк - составной адаптер над упорядоченным списком

`FallbackLlmGateway(providers)` за тем же портом: вызывает провайдеров по порядку, возвращает первый успех, при `LlmError` (включая `LlmOutputError`) пишет предупреждение с именем провайдера и классом сбоя и переходит к следующему; после последнего пробрасывает его сбой.

Порядок собирает composition root из конфигурации, и выбора там нет: `[ollama]` или `[ollama, eurorouter]`.
Hosted-провайдер включается только флагом `LLM_HOSTED_FALLBACK=true` вместе с адресом, моделью и ключами (D7); основным он стать не может.
Так требование «код не покидает сеть без явного решения» проверяется тестом сборки контейнера, а не ревью конфигурации.

Альтернатива - фоллбэк внутри каждого адаптера: каждый знал бы о других и повторял бы одну логику.

### D4. Ротация ключей - внутри OpenAI-совместимого адаптера

Ключи - `SecretStr` со списком через запятую.
Каждый вызов начинает со следующего ключа по кругу (счётчик под `threading.Lock`), чтобы нагрузка расходилась по ключам.
`401`, `403`, `429` - следующий ключ в том же вызове; отказали все - `LlmError("все ключи провайдера отвергнуты")`.
`5xx`, таймаут, обрыв соединения - сбой провайдера сразу: ключ тут ни при чём, а перебор ключей лишь умножил бы ожидание.

Текст ошибки строится из кода ответа и имени провайдера, а не из запроса: заголовок `Authorization` не попадает ни в исключение, ни в лог.

### D5. Окно модели: проверка до отправки и защита в адаптере

- Чистая функция `check_window(messages, *, window_tokens, max_output_tokens) -> Result[int]` в `app/domain/prompt.py`: оценка - байты UTF-8 содержимого всех сообщений / `BYTES_PER_TOKEN` с округлением вверх плюс постоянная накладка на сообщение под разметку чат-шаблона; не помещается - неудача с оценкой и окном.
- `request_review` и `request_verification` вызывают её до порта; неудача - `PromptTooLargeError(LlmError)` из `app/domain/llm_errors.py`.
  Ревью - `failed` на `analysing`, верификатор - `unavailable`: пайплайн из #61 уже так обрабатывает `LlmError`, нового пути нет.
- `LlmRequest.max_output_tokens` - резерв под ответ; адаптеры передают его как `num_predict` и `max_tokens`.
- Оценка «байты / 4» - средняя, а не верхняя граница.
  Поэтому `OllamaGateway` сверяет `prompt_eval_count` ответа с `window - max_output_tokens`: больше - модель могла обрезать запрос, вызов завершается `LlmError`, а не возвращает ответ на неполный запрос.
- При старте воркера чистая функция `check_window_config(context_max_tokens, review_system_tokens, max_output_tokens, window_tokens)` сверяет конфигурацию с загруженными текстами промптов; не помещается - воркер не стартует (`backend-architecture`: некорректная конфигурация останавливает запуск).

Окно одно на все провайдеры - минимальное из окон настроенных моделей.
Окна по провайдерам потребовали бы пропускать провайдера с узким окном в составном адаптере; второго окна сегодня никто не читает.

Альтернатива - **токенизатор модели** (`tokenizers` и файлы словаря): точный счёт, но тяжёлая зависимость на каждую модель фоллбэка и своя версия словаря; оценка плюс сверка `prompt_eval_count` закрывает то же самое для нашей цели - не отправить обрезанный запрос.

### D6. Контекст PR - новая доля пакета, недоверенные данные

- `PRMetadata.description` (тело PR, `null` - пустая строка); новый метод шлюза `fetch_pr_commit_messages(repo, number, installation_id) -> tuple[str, ...]` - от нового к старому, не больше 250 (предел GitHub для `/pulls/{n}/commits`, до трёх страниц по 100).
- `build_review_context` достаёт оба best-effort, как правила: `VcsError` - контекст PR пуст, причина в `omitted` (`part: "pr_context"`, `reason: "unavailable"`).
- `assemble_context` кладёт в тело поле `pull_request_context` - `title`, `description` (если не пусты) и `commits`, каждый текст через `fence` с видами `pr_title`, `pr_description`, `commit_message`.
  Доля бюджета - `min(pr_context_max_tokens, нужно)`, берётся первой, тем же механизмом `Budget.split`, что и доля правил; не поместившееся - в `omitted` с `reason: "budget"`.
- Сборщик запроса выводит раздел «Контекст PR» в сообщении кода перед изменениями; в системное сообщение текст автора PR не попадает (требование `review-prompt-assembly` из #61 уже это требует).
- Схема пакета остаётся `context-payload/v1`: поле добавочное, старые пакеты без него сборщик запроса читает как пустой контекст PR.

Почему первой долей: заголовок и описание - короткое объяснение намерения автора, ради которого модель правильно читает дифф; верхняя граница доли не даёт им вытеснить дифф.

### D7. Конфигурация

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_BACKEND` | нет | `stub` или `ollama`; не задана - воркер не стартует |
| `OLLAMA_BASE_URL` | `http://ollama:11434` | адрес локальной модели |
| `OLLAMA_MODEL` | нет | обязательна при `ollama` |
| `LLM_HOSTED_FALLBACK` | `false` | явное включение Eurorouter фоллбэком |
| `EUROROUTER_BASE_URL`, `EUROROUTER_MODEL`, `EUROROUTER_API_KEYS` | нет | обязательны при включённом фоллбэке; ключи - `SecretStr` через запятую |
| `LLM_CONTEXT_WINDOW_TOKENS` | 65 536 | окно модели (D5) |
| `LLM_MAX_OUTPUT_TOKENS` | 4 096 | резерв и предел ответа |
| `LLM_MAX_ATTEMPTS` | 2 | попытки получить ответ по схеме у одного провайдера |
| `LLM_TIMEOUT_SECONDS` | 300 | таймаут одного HTTP-запроса к модели |
| `PR_CONTEXT_MAX_TOKENS` | 1 000 | доля пакета под контекст PR |

`LLM_BACKEND` не обязателен в `Settings`, а проверяется в `run_worker`: `Settings` общий с процессом API, которому модель не нужна.
Остальные зависимости между полями - валидатор `Settings`, ошибка называет параметр.

### D8. Few-shot - файл промпта, проверяемый схемой

`prompts/review/few-shot.md` добавляется в конец `REVIEW_SYSTEM_PARTS` (после `output-format.md`: сначала описание формата, потом примеры).
Примеры - блоки ` ```json ` с полным ответом на синтетический дифф, описанный словами рядом: замечание по стандартным критериям, замечание со ссылкой на правило без префикса в тексте, ответ без замечаний.
Тест извлекает каждый блок из тела файла и проверяет `ReviewOutput.model_validate_json`: пример не может разойтись со схемой молча.

### D9. Модель угроз

Абзац «Self-hosted модель это свойство безопасности» в `docs/BACKEND_ARCHITECTURE.md` получает решение: по умолчанию запрос уходит только локальной модели; Eurorouter - явный opt-in фоллбэк, при котором код проверяемого репозитория уходит провайдеру; кто и почему включает фоллбэк на стенде - решение эксплуатации, записанное в `infra/`.

## Risks / Trade-offs

- [Оценка «байты / 4» недооценивает запрос с кириллицей или минифицированным кодом] → сверка `prompt_eval_count` в адаптере Ollama отвергает ответ на возможно обрезанный запрос; у hosted-провайдера переполнение окна - ответ `400`, то есть `LlmError`.
- [Eurorouter не поддерживает `json_schema` в `response_format`] → проверяется живым вызовом в задаче сквозной проверки; запасной вариант - `{"type": "json_object"}` в том же адаптере, проверку и так выполняет наша модель.
- [Фоллбэк на hosted при ответе локальной модели не по схеме отправляет код наружу чаще, чем при недоступности] → фоллбэк включается только явно; каждый переход пишется в лог с именем провайдера, задачей (`review` или `verify`) и классом сбоя; порт о прогоне не знает, прогон виден по соседним записям воркера.
- [Повтор без эха ответа исправляется хуже re-ask'а Instructor'а] → число попыток настраивается; частоту `LlmOutputError` покажет eval (#57).
- [Медленная локальная модель и два вызова на прогон упираются в `stale_run_timeout_seconds`] → таймаут HTTP-запроса меньше порога зависания; отметка прогресса между ревью и верификацией - в #63.
- [Контекст PR - ещё одна поверхность инъекции] → только блоками недоверенных данных и только в сообщении кода; adversarial-кейс в `test_prompt_injection.py`.

## Migration Plan

1. Развёртывание задаёт `LLM_BACKEND` (на стенде - `stub`, пока Ollama не развёрнута); без переменной воркер не стартует, и проверка развёртывания (`backend-delivery`) это ловит.
2. Схема базы не меняется; пакеты контекста без `pull_request_context` читаются как раньше.
3. Откат - реверт: заглушка и пакет без контекста PR остаются рабочими.
