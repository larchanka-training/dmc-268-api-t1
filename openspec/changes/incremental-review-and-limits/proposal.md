# Proposal

> **Статус: черновик архитектурного предложения, не утверждён.** Решения ниже — предложение
> Tech Lead для review командой (Backend, Queue, LLM, Frontend, DevOps, QA). Реализация
> начинается только после согласования; до него `openspec/specs/` не меняется.
> Сводный документ с алгоритмами и диаграммами —
> [`docs/pipeline/INCREMENTAL_REVIEW_AND_LIMITS_SPEC.md`](../../../docs/pipeline/INCREMENTAL_REVIEW_AND_LIMITS_SPEC.md).

## Why

Сегодня каждый `pull_request.synchronize` создаёт прогон, который заново ревьюит весь дифф PR
(`compare/{base_sha}...{head_sha}`): модель повторно получает уже проверенный код, серия push
даёт серию параллельных полных прогонов, а дубли сдерживает только сверка с тредами GitHub по
текущей строке — при её сбое находки публикуются без сверки. Лимитов на частоту, токены
прогона и квоты репозитория нет, а «исправленность» замечания система не отслеживает вовсе.
Прежде чем система пойдёт на реальные репозитории, нужен согласованный контракт повторного
ревью, жизненного цикла замечаний и ограничений расхода.

## What Changes

- **Инкрементальное ревью.** Вводятся понятия *PR diff* (base…head, что видит GitHub),
  *incremental diff* (последний полностью проверенный head…новый head) и *область ревью*
  (hunk'и PR diff, содержимое которых ещё не проверялось). Модель получает только область
  ревью; повторный push без новых hunk'ов не вызывает модель.
- **Водяной знак проверенного состояния** запроса на изменение (`last_reviewed_head_sha`) и
  **журнал проверенных hunk'ов** по содержимому: знак сдвигается только прогоном `completed` с
  полным покрытием, журнал пополняется только проверенными hunk'ами — непроверенный код не
  теряется при частичном ревью, сбое, отмене и force-push.
- **Конкурентная обработка без новых статусов.** Новый head вытесняет активный прогон
  предыдущего head: тот переходит в уже существующий `cancelled` с причиной `superseded` на
  ближайшей границе этапа и ничего не публикует. Публикация в один PR сериализуется. Устаревшая
  (более старая) доставка не откатывает head.
- **Отслеживание замечаний между прогонами.** Устойчивый fingerprint замечания (категория,
  пункт правила, идентичность файла с учётом переименования, нормализованный текст строки
  якоря, охватывающее определение), многоуровневое сопоставление старых и новых находок,
  внутренние состояния замечания и их соответствие GitHub Outdated / Resolved. Отсутствие
  находки в ограниченном ревью не считается исправлением.
- **Многоуровневые лимиты и квоты**: частота вебхуков и прогонов на PR/репозиторий, размер
  области ревью (файлы, строки), бюджет токенов прогона, суточная квота токенов инсталляции,
  бюджет повторов, backpressure очереди, расширенная фильтрация шума. Для каждого превышения
  определено поведение: reject, defer, skip или partial.
- **Безопасность**: защита от устаревших и повторных доставок, правило «на GitHub отказ
  политики — всегда 202», изоляция репозиториев, ограничения недоверенного кода и логов —
  в дополнение к уже построенным мерам threat model.
- Контракты: новые поля прогона и находки в API (аддитивно), причины отмены и покрытия, коды
  ошибок `TOKEN_BUDGET_EXCEEDED`, `QUOTA_EXCEEDED`; **сообщение очереди не меняется**. Схема
  БД меняется миграциями на этапе реализации (в этом change миграций нет).
- **Не BREAKING для API**: все поля добавляются; статусы прогона не меняются. Поведенчески
  меняется ответ на `synchronize` — помечено в дельте `webhook-intake` (MODIFIED).

## Capabilities

### New Capabilities

- `incremental-review`: область повторного ревью, водяной знак и журнал проверенных hunk'ов,
  режимы прогона (full / incremental / rebased / noop), force-push и смена base, вытеснение
  прогонов и сериализация публикации.
- `finding-tracking`: fingerprint замечания, сопоставление находок между прогонами,
  внутренние состояния замечания, соответствие GitHub Outdated / Resolved.
- `review-limits`: лимиты частоты, размера, токенов, квот и повторов, backpressure,
  фильтрация шума и поведение при превышении (reject / defer / skip / partial).

### Modified Capabilities

- `webhook-intake`: `synchronize` вытесняет активный прогон и подчиняется лимитам; устаревшая
  доставка не откатывает head; отказ политики отвечает 202 с исходом.
- `review-data-model`: водяной знак запроса на изменение, режим и покрытие прогона, причина
  отмены, fingerprint и состояние замечания.
- `review-rest-api`: прогон и находка отдают новые поля (аддитивно).

## Impact

- **Код (на этапе реализации)**: `app/domain` (новые чистые функции области ревью,
  fingerprint, сопоставления, решения по лимитам), `app/application/review_pipeline.py`,
  `handle_webhook.py`, `build_review_context.py`, `publish_review.py`,
  `sync_thread_resolution.py`; порт `VcsGateway` (статус compare, переименования); порт
  `RateLimiter` из «Designed, not built»; `app/config.py` (новые лимиты).
- **БД**: колонки `merge_requests`, `review_runs`, `findings`, новые таблицы журнала hunk'ов и
  покрытия файлов, `rate_limit_counters` — отдельными миграциями.
- **API / Frontend**: аддитивные поля `ReviewJob` и находки; экран прогона показывает режим,
  покрытие и причину отмены (`cancelled` клиент уже поддерживает).
- **Queue**: тело сообщения без изменений; возможна задержанная доставка (defer) — решение
  DevOps/Queue, см. открытые вопросы.
- **LLM**: ответ модели без изменений; пакет контекста получает разметку «изменено с прошлого
  ревью» — версия пакета `context-payload/v2` (решение LLM-команды).
- **Документация**: `docs/pipeline/INCREMENTAL_REVIEW_AND_LIMITS_SPEC.md` (создан);
  `SYSTEM_DESIGN.md`, `BACKEND_ARCHITECTURE.md`, `erd.md`, `PIPELINE_SPEC.md` обновляются в
  задачах реализации.
