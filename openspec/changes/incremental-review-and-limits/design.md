# Design

> Черновик, не утверждён. Алгоритмы в псевдокоде, диаграммы, таблицы лимитов и матрица
> тестовых сценариев — в [`docs/pipeline/INCREMENTAL_REVIEW_AND_LIMITS_SPEC.md`](../../../docs/pipeline/INCREMENTAL_REVIEW_AND_LIMITS_SPEC.md).
> Этот файл фиксирует решения, альтернативы и риски; требования — в `specs/` этого change.

## Context

Что есть сегодня (проверено по коду и спекам):

- `synchronize` сдвигает `merge_requests.head_sha` на доставленный коммит и создаёт новый
  прогон; воркер берёт дифф `compare/{base_sha}...{head_sha}` из сообщения и ревьюит **весь PR
  diff** (`fetch_review_diff`, лимит `DIFF_MAX_BYTES`). Водяного знака проверенного состояния нет.
- Машина состояний (`app/domain/lifecycle.py`): `queued → building_context → analysing →
  publishing → completed`, из каждого нетерминального — `failed` и `cancelled`. **В `cancelled`
  сегодня не переводит ни один путь кода**, но клиент и API его уже знают.
- Один нетерминальный прогон на `(merge_request_id, head_sha)` — частичный уникальный индекс;
  параллельные прогоны разных head одного PR ничем не ограничены.
- Дубли: `deduplicate` внутри прогона; между прогонами — `thread_coverage` по пути, стороне,
  категории и **текущей строке треда на GitHub**; outdated-тред не покрывает; закрытый
  человеком — покрывает (кроме эскалации до `critical`). При сбое сверки находки публикуются
  без неё. `threadFollowUps` модели принимаются схемой и игнорируются: бот не закрывает треды.
- Публикация защищена маркером прогона в теле ревью; check run `dmc-268-ai-review` на
  `head_sha` — merge gate по открытым `critical`.
- Лимиты: `DIFF_MAX_BYTES` (5 МиБ → `failed`), `context_max_tokens` 32 000 (не поместившееся —
  в `omitted`, прогон всё равно `completed`), `llm_max_attempts` 2, `llm_timeout_seconds` 300,
  тело вебхука 2 МиБ, повтор упавших доставок ≤ 5. `RateLimiter`, `IdempotencyStore`,
  `rate_limit_counters` — «Designed, not built» в BACKEND_ARCHITECTURE.md.
- Сообщение очереди несёт `head_sha`/`base_sha`; сбой обработки → `nack` без requeue → DLQ.

Ограничения проекта: гексагональные слои, решения — чистые функции без I/O и часов, порт не
пишется раньше вызывающего, контракт API — из кода, схема БД — только миграциями, всё по-русски.

## Goals / Non-Goals

**Goals:**

- Ни один hunk PR diff не остаётся непроверенным молча: либо он в журнале, либо отражён в
  покрытии прогона как непроверенный.
- Модель не получает повторно hunk с уже проверенным содержимым при той же конфигурации.
- Повторная проблема не публикуется повторно ни при каком исходе сверки с GitHub.
- Расход ограничен на каждом уровне, а отказ политики не превращается в шторм повторов.
- Совместимость: статусы прогона и тело сообщения очереди не меняются; поля API — аддитивно.

**Non-Goals:**

- Автоматическое закрытие тредов ботом (запрещено спекой `review-pipeline`).
- Клонирование репозитория, сборка, запуск тестов из PR.
- Многочанковое ревью одного прогона (остаётся один пакет; см. решение 9).
- Тарифы и биллинг — квоты ключуются по инсталляции до появления `accounts`.
- Семантический кэш ответов модели.

## Decisions

### 1. Область ревью = PR diff минус журнал проверенных hunk'ов

Область ревью — hunk'и PR diff на head, чей `hunk_digest = sha256(path_at_head ‖ строки hunk'а с
маркерами ' ', '+', '-', без @@-заголовка, trailing whitespace снят)` отсутствует в журнале
`(merge_request_id, hunk_digest, config_digest)`. `config_digest` = версия промпта + дайджест
правил на `base_sha` + версия сборки контекста.

*Почему так, а не «ревьюить incremental diff `L…H`»:* incremental diff (1) после merge базы в
PR тащит чужие изменения, (2) неприменим после force-push/rebase, (3) не помнит частично
проверенные прогоны. Журнал по содержимому решает все три одним правилом и переживает rebase
без конфликтов (содержимое hunk'ов то же → модель не вызывается). Incremental diff остаётся
нужен для режима, разметки изменённых строк в пакете и для `possibly_fixed`.

*Альтернативы:* (а) только водяной знак + `compare(L…H)` ∩ PR diff — проще, но force-push и
partial требуют полного повтора; (б) кэш по файлу (blob sha) — грубее: одна строка в большом
файле отправляет весь файл; (в) кэш ответов модели по hunk'у — экономнее при отменах, но
находки модели зависят от соседних hunk'ов запроса, кэш дал бы неверную атрибуцию. Выбран
журнал без кэша находок: находки прошлых прогонов и так лежат в базе и сопоставляются по
fingerprint (решение 5).

*Цена:* hunk GitHub несёт 3 строки контекста — правка рядом со старым hunk'ом меняет его
дайджест и отправляет его целиком. Это консервативно (лишние токены, а не пропуск).

### 2. Водяной знак — сводка, а не источник истины

`merge_requests.last_reviewed_head_sha/base_sha/run_id` сдвигается только в транзакции перехода
прогона в `completed` с `coverage=complete`, CAS по значению на начало прогона
(`WHERE last_reviewed_head_sha IS NOT DISTINCT FROM :since_sha`). Используется для режима
(`full`/`incremental`/`rebased`), для `compare(L…H)` и для UI («проверено до коммита X»).
Пропуск кода невозможен даже при ошибке в знаке: область считает журнал.

Режим: нет знака → `full`; `compare(L…H).status = ahead` → `incremental`; `identical` или пустая
область → `noop`; `diverged`/`behind`/404 (force-push, сборка мусора коммита) → `rebased`.

### 3. Вытеснение через существующий `cancelled`, без новых статусов

Новых значений `ReviewRunStatus` нет — клиент, SSE и фильтры `active` уже знают `cancelled`.
Добавляются `cancel_reason` и `superseded_by_run_id`. Проверка «я ещё актуален?» —
`merge_request.head_sha == run.head_sha` — в трёх точках: взятие задачи, перед каждым вызовом
модели, перед публикацией (под правом публикации). Токены уже сделанного вызова пишутся в
прогон и шаги, как у упавшего.

*Альтернатива — дать устаревшему прогону опубликоваться:* экономит токены, но публикует
комментарии на коммит, который уже не head, и усложняет сопоставление. Отклонено.

*Альтернатива — debounce (задержка задачи на N секунд):* требует отложенной доставки в
RabbitMQ (TTL-очередь + DLX). Вытеснение при взятии из очереди даёт тот же эффект для задач в
хвосте очереди бесплатно; debounce оставлен открытым вопросом для DevOps.

### 4. Право публикации — аренда на строке запроса на изменение

`merge_requests.publish_lease_run_id` + `publish_lease_until`, захват CAS-ом
(`UPDATE … WHERE lease IS NULL OR lease_until < now`). Под арендой: проверка актуальности,
сопоставление находок, `POST` ревью, запись `published_comments`, журнала и знака. Аренда, а не
advisory lock: публикация включает сетевые вызовы GitHub, держать транзакцию на них нельзя.
Срок аренды > суммарного бюджета ожидания адаптера GitHub на публикацию (предложение 180 с).
Не взял аренду → ждёт с паузой в пределах `publish_lease_wait_seconds`, затем `nack` без
requeue запрещён (ушло бы в DLQ) — поэтому прогон возвращается в очередь новой постановкой
задачи с тем же `review_run_id` (новый `job_id`). Решение требует подтверждения Queue.

### 5. Fingerprint и сопоставление — чистые функции, уровни от строгого к мягкому

`fingerprint = sha256(category ‖ rule_name#check ‖ file_identity ‖ norm(anchor_line_text) ‖ enclosing_symbol)`,
где `file_identity` — путь на head с прослеживанием переименований из `compare.files[].previous_filename`,
`enclosing_symbol` — имя определения из AST-окружения или пусто, `norm` — схлопывание
пробелов. Сохраняется также `fingerprint_loose` — без текста строки.

Уровни `match_findings` (взаимно-однозначно, жадно по уровню, затем по расстоянию строк):

- `L0 host_line` — текущая строка треда на GitHub (действующее правило `thread_coverage`);
- `L1 exact` — тот же `fingerprint`;
- `L2 loose` — тот же `fingerprint_loose` в том же `enclosing_symbol`, расстояние ≤ окна;
- нет пары → новая находка.

Совпадение дальше подчиняется действующим правилам покрытия (открытый тред не ниже по
серьёзности покрывает; закрытый человеком покрывает, кроме эскалации до `critical`;
outdated не покрывает). Текст модели не входит в ключ: модель формулирует одну проблему
по-разному от прогона к прогону. Поле `issue_type` из закрытого словаря в ответе модели
сделало бы ключ точнее — открытый вопрос LLM-команде.

### 6. Состояние замечания живёт на корневой находке треда

`findings.lifecycle_state` заполняется только у находки с корневым inline-комментарием:
`open → possibly_fixed | outdated | obsolete | resolved`, `resolved ↔ open` по вебхуку треда,
`possibly_fixed/outdated → open` при повторном обнаружении и не устаревшем треде. Состояния —
внутренние, бот тредов не закрывает и (по умолчанию) в них не пишет. Merge gate по-прежнему
считает открытые треды, а не `lifecycle_state`: снять блокировку может только человек.

`possibly_fixed` требует трёх фактов: строки якоря изменены incremental diff; hunk якоря
полностью в области завершённого прогона; пары у прогона нет. В `rebased` первый факт
недоступен → `possibly_fixed` не выставляется.

### 7. Лимиты: одна чистая функция решения + порт `RateLimiter`

`decide_admission(counters, policy, now) -> Admit | Defer(reason) | Reject(reason)` для приёма и
`plan_scope(hunks, budget, limits) -> (selected, skipped_by_reason)` для воркера — чистые.
Счётчики — порт `RateLimiter` из «Designed, not built» (PostgreSQL, фиксированное окно,
`INSERT … ON CONFLICT DO UPDATE … RETURNING`). Суточная квота токенов считается суммой
`review_runs.tokens_used` инсталляции за сутки — отдельной таблицы не нужно, пока нет тарифов.
Отложенные прогоны ставит в очередь периодический проход воркера рядом со `stale_sweep`.

На GitHub отказ политики — всегда 202 с `intake_outcome`: 4xx/5xx подхватил бы повтор упавших
доставок (#149) и умножил бы нагрузку.

### 8. Покрытие — по файлам, неполнота — явная

`omitted` пакета контекста сегодня тих: прогон `completed`, а часть кода не проверена. Теперь
каждый файл области получает статус покрытия; `skipped_*` делает покрытие `partial`, знак не
сдвигается, hunk'и не попадают в журнал, сводка ревью перечисляет непроверенные файлы.

### 9. Один пакет на прогон сохраняется

Многочанковое ревью — отдельный change: оно меняет `context_payloads.chunk_index`, верификатор
и бюджет. Здесь область, не влезшая в пакет, — `partial`, следующий push или ручной перезапуск
доберёт остаток (журнал помнит проверенное).

### 10. Сообщение очереди не меняется

`since_sha`, режим и область вычисляет воркер в момент обработки: между постановкой и
обработкой знак и head могут сдвинуться, значения в сообщении были бы устаревшими.

## Risks / Trade-offs

- [Публикующий воркер упал после `POST` ревью, до записи в базу] → следующий прогон не видит
  этих комментариев и может продублировать их. Митигация: перед публикацией искать ревью бота
  с маркерами прогонов этого PR в статусе `failed`/выметенных и импортировать их комментарии
  (расширение существующего поиска по маркеру).
- [Контекст изменился, hunk нет — сигнатура функции поменялась в другом файле] → hunk
  вызывающего кода не перепроверяется. Митигация: изменённая сигнатура сама в области ревью;
  индекс определений (`add-tree-sitter-index`) позже может инвалидировать зависимые hunk'и.
- [Ложное совпадение `L2 loose` подавит новую проблему] → только в пределах одного
  определения и окна строк, серьёзность выше — публикуется; уровень сохраняется для аудита.
- [Смена правил владельца инвалидирует журнал → полный повтор по всем открытым PR] →
  открытый вопрос: включать ли дайджест правил в `config_digest`.
- [Аренда публикации задерживает прогоны при зависшем GitHub] → срок аренды ограничен, ожидание
  ограничено, сверх — повторная постановка.
- [Квота по инсталляции несправедлива к крупным организациям] → ключ квоты станет `account`
  вместе с тарифами; значения конфигурируемые.
- [`stale_event` по `updated_at` PR: `updated_at` меняется и от правки описания] → сравнение
  только для `synchronize` и только «строго раньше»; при равенстве доставка обрабатывается.
- [Секреты в `context_payloads` (задача #28 не сделана)] → инкрементальность не меняет риск,
  но журнал хранит только дайджесты, не код.

## Migration Plan

Каждый шаг — отдельный PR с миграцией Alembic и откатом:

1. Аддитивные колонки и таблицы (`merge_requests` знак и аренда, `review_runs` режим/покрытие/
   причины, `findings` fingerprint/состояние, `reviewed_hunks`, `review_run_files`,
   `rate_limit_counters`) — nullable, без бэкфилла. Старый код их не читает.
2. Запись fingerprint и покрытия без изменения поведения (теневой режим): метрики «сколько
   hunk'ов было бы пропущено», «сколько находок совпало бы по L1/L2».
3. Включение области ревью по журналу и вытеснения за флагом `INCREMENTAL_REVIEW_ENABLED`
   (по умолчанию выключен); откат — выключение флага, поведение «весь PR diff» возвращается.
4. Лимиты — каждый со значением «выключено» по умолчанию, включение конфигурацией стенда.
5. Существующие PR: пустой журнал → первый прогон после включения — `full`, это ожидаемо.

## Open Questions

Вопросы, на которые нужен ответ команды до начала реализации; дельты спек написаны под
рекомендуемый ответ (в скобках) и правятся, если команда решит иначе. Полный список с
владельцами — в разделе 12 сводного документа.

- Включать ли дайджест правил владельца и id модели в `config_digest`? (правила — да, модель — нет)
- Писать ли боту ответ в тред при `possibly_fixed` детерминированным текстом? (нет)
- Нужен ли debounce отложенной доставкой RabbitMQ? (нет на MVP)
- Обрабатывать ли `pull_request.edited` со сменой base как триггер? (да, отдельной задачей)
- Числовые значения лимитов — раздел 7 сводного документа (все требуют согласования).
