# Design

> Предложение, не утверждено. Алгоритм и сценарии — в
> [`docs/pipeline/INCREMENTAL_REVIEW_AND_LIMITS_SPEC.md`](../../../docs/pipeline/INCREMENTAL_REVIEW_AND_LIMITS_SPEC.md).

## Context

После #225 и #230:

- Дубль доставки — только если последний прогон на коммит не `failed` и не `cancelled`
  (`_duplicate_of` по `find_latest`).
- Смена целевой ветки отменяет активный прогон на head (`_supersede`) своим коммитом до нового
  прогона, ставит блокировку и задачу. Все, кто выставляет gate, после POST перечитывают
  последний прогон на head (`settle_merge_gate`).
- Воркер перечитывает свой статус перед gate; отменённый прогон gate не ставит.
- `SqlAlchemyReviewRunRepo.update` читает строку `FOR UPDATE` и сверяет переход через
  `next_status` от статуса в базе: переход воркера не перезаписывает отмену приёма, а сам воркер
  уходит в ack (#225).
- Очередь `review_jobs.qq` с `x-delivery-limit` 5, один воркер на стенде, prefetch=1.
- Дубли между прогонами сдерживает `thread_coverage`: открытый тред не ниже серьёзности
  покрывает, закрытый человеком покрывает (кроме эскалации до `critical`), outdated — нет.

## Goals / Non-Goals

**Goals:**

- Модель не получает повторно hunk, чьё содержимое уже проверено при той же конфигурации.
- Ни один путь — откат и возврат, копия блока, смена ветки, отмена, сбой — не оставляет код
  без ревью при `success` на head.
- На один PR публикует один прогон за раз, и прогон прежнего head не публикует.

**Non-Goals:** водяной знак и режимы прогона; состояния замечаний; fingerprint и L1/L2;
лимиты (change `review-limits`); многочанковое ревью; кэш ответов модели.

## Decisions

### D1. Только журнал, без водяного знака

Знак `last_reviewed_head_sha` в первом круге давал `noop` по `H == L`, а после смены целевой
ветки head тот же, а дифф другой — дыра #222 возвращалась. Область считается всегда из PR diff
на (head, base) прогона минус журнал, ранних выходов по head нет. Режимы `full/incremental/
rebased` были нужны знаку и состояниям замечаний — обоих нет, режимов тоже.

### D2. Дайджест hunk'а и конфигурации

`hunk_digest = sha256(строки hunk'а с маркерами ' ', '+', '-', без @@-заголовка, trailing
whitespace снят)`; путь хранится отдельной колонкой. `config_digest = sha256(версия промпта ‖
дайджест правил владельца на base_sha ‖ версия схемы пакета ‖ id модели)` — в первом круге модели
не было.

### D3. Запись действует, пока hunk непрерывно в PR diff

Каждый прогон, получивший PR diff, помечает `stale_at` у записей журнала, чьих `(path,
hunk_digest)` в этом диффе нет. Устаревшая запись hunk не исключает и не удаляется (история).
Откат hunk'а, затем «revert the revert» → между ними прогон увидел PR diff без hunk'а → запись
устарела → вернувшийся hunk снова в области. Если между откатом и возвратом прогона не было,
hunk непрерывно присутствует для системы — его содержимое и правда уже проверено.

### D4. Вхождения считаются

Запись хранит `occurrences` — сколько раз hunk с этим `(path, hunk_digest)` был в проверенном
PR diff. В область входят hunk'и сверх записанного числа. Блок, скопированный с контекстом в
другое место того же файла, даёт второе вхождение и проверяется. В другом файле — другой путь,
другая запись.

### D5. Hunk с находками в журнал не попадает

Предложение Grinv: по hunk'у с находкой прогона записи нет, он идёт модели на каждом push, пока
находки на нём есть. Дубль комментария не появляется — его сдерживает `thread_coverage`, как
сегодня. Цена — токены на hunk'и с незакрытыми замечаниями; выигрыш — откат исправления
(тред outdated, человек закрыл) не прячет вернувшуюся уязвимость.

### D6. Сегменты нового файла

Новый файл в PR diff — один hunk `@@ -0,0 +1,N @@`, и любая правка в нём меняет дайджест
целиком. hunk из одних `+` длиннее `SEGMENT_MAX_LINES` (предложение 80) режется на сегменты по
строкам без отступа после пустой строки, не длиннее предела. Правило текстовое, без AST: AST
ограничен `ast_max_files` и пропадает при сбое tree-sitter (#227), граница сегмента должна быть
одинаковой во всех прогонах. Сегмент — единица области и журнала.

### D7. Вытеснение — расширение `_supersede` из #225

На `synchronize` приём в той же транзакции, что и новый прогон, переводит активные прогоны этого
PR на других head в `cancelled` с `cancel_reason=superseded` и `superseded_by_run_id`; при смене
ветки — `base_changed` (#225 причину не хранил). Задача ставится после коммита. Воркер
перечитывает статус при взятии задачи, перед каждым вызовом модели и под блокировкой публикации
перед переходом в `publishing`. Окно между последней проверкой и POST остаётся — требование
поэтому «не начинает публикацию после проверки, показавшей отмену», а gate закрывает
`settle_merge_gate`.

### D8. Снят

Условный переход статуса уже есть в develop — см. Context.

### D9. Сериализация публикации — сессионная advisory-блокировка

Аренда с повторной постановкой из первого круга ломала машину состояний (`publishing →
building_context` запрещён) и обходила `x-delivery-limit`. Вместо неё — `pg_advisory_lock(ключ
запроса на изменение)` на отдельном соединении, без транзакции, на время от проверки статуса до
записи `published_comments`. Падение воркера снимает блокировку с соединением, срок не нужен.
Ожидание ограничено `PUBLISH_LOCK_WAIT_SECONDS` (`lock_timeout`) и входит в худший прогон
`check_consumer_timeout`. Не дождался — прогон `failed` на `publishing`, находки сохранены, gate
закрывает `_block_head_of_failed_run` (#225). На стенде один воркер, так что ожидания на деле нет.

*Альтернатива Grinv* — `SELECT … FOR UPDATE` на `merge_requests` на проверку и переход в
`publishing`: короче, но публикацию двух прогонов одного PR не исключает, если первый уже в
`publishing`. Для одного воркера равноценны; выбрана блокировка, потому что она переживает
масштабирование до нескольких воркеров без новой колонки.

### D10. Устаревшая доставка

`opened`/`synchronize` с `event.head_sha != metadata.head_sha` — устарела: прогон не создаётся,
ответ 202 `ignored`. Иначе запоздавшая доставка A после B (последний прогон на A — `cancelled`,
значит не дубль) создала бы прогон на A и вытеснила B. То же правило у повторов #149; колонка
`head_updated_at` из первого круга не нужна.

## Risks / Trade-offs

- Hunk с находкой уходит модели на каждом push (D5) — расход растёт с числом незакрытых замечаний.
- Откат и возврат без прогона между ними не перепроверяется (D3): содержимое то же, что проверено.
- Изменилась сигнатура в другом файле — hunk вызывающего кода не перепроверяется. Изменённая
  сигнатура сама в области; индекс определений (`add-tree-sitter-index`) позже может
  инвалидировать зависимые hunk'и.
- Смена правил владельца меняет `config_digest` и отправляет модели все открытые PR целиком.

## Migration Plan

1. Миграция: `reviewed_hunks`, `review_runs.cancel_reason`, `superseded_by_run_id` — nullable,
   старый код их не читает. Новые значения нативных enum откатом не удаляются: downgrade
   оставляет тип, удаляет колонки.
2. Теневой режим: прогон считает область и пишет журнал, но модели уходит весь PR diff;
   метрика «сколько hunk'ов было бы пропущено».
3. Флаг `INCREMENTAL_REVIEW_ENABLED` (по умолчанию выключен) включает область по журналу и
   вытеснение. Откат — выключить флаг.
4. Существующие PR: журнал пуст, первый прогон после включения отправляет весь PR diff.
