# Design

> Предложение, не утверждено. Сценарии — в дельтах `specs/`.

## Context

После #225 и #230:

- Дубль доставки — только если последний прогон на коммит не `failed` и не `cancelled`
  (`_duplicate_of` по `find_latest`).
- Смена целевой ветки отменяет активный прогон на head (`_supersede`) своим коммитом до нового
  прогона, ставит блокировку и задачу. Все, кто выставляет gate, после POST перечитывают
  последний прогон на head (`settle_merge_gate`).
- Воркер перечитывает свой статус перед gate; отменённый прогон gate не ставит.
- `SqlAlchemyReviewRunRepo.update` читает строку `FOR UPDATE` и сверяет переход через
  `next_status` от статуса в базе: переход воркера не перезаписывает отмену приёма, а сам воркер
  уходит в ack (#225).
- Очередь `review_jobs.qq` с `x-delivery-limit` 5, один воркер на стенде, prefetch=1.
- Дубли между прогонами сдерживает `thread_coverage`: открытый тред не ниже серьёзности
  покрывает, закрытый человеком покрывает (кроме эскалации до `critical`), outdated — нет.

## Goals / Non-Goals

**Goals:**

- Модель не получает повторно hunk, чьё содержимое уже проверено при той же конфигурации.
- Ни один путь — откат и возврат, копия блока, смена ветки, отмена, сбой — не оставляет код
  без ревью при `success` на head.
- Прогон прежнего head не начинает вызов модели и публикацию, когда head PR уже другой.

**Non-Goals:** водяной знак и режимы прогона; состояния замечаний; fingerprint и L1/L2;
лимиты (change `review-limits`); сериализация публикации (proposal, «Не входит»); многочанковое ревью; кэш
ответов модели.

## Decisions

### D1. Только журнал, без водяного знака

Знак `last_reviewed_head_sha` в первом круге давал `noop` по `H == L`, а после смены целевой
ветки head тот же, а дифф другой — дыра #222 возвращалась. Область считается всегда из PR diff
на (head, base) прогона минус журнал, ранних выходов по head нет. Режимы `full/incremental/
rebased` были нужны знаку и состояниям замечаний — обоих нет, режимов тоже.

### D2. Дайджест hunk'а и конфигурации

`hunk_digest = sha256(строки hunk'а с маркерами ' ', '+', '-', без @@-заголовка, trailing
whitespace снят)`; путь хранится отдельной колонкой. `config_digest = sha256(версия промпта ‖
дайджест правил владельца на base_sha ‖ версия схемы пакета ‖ id модели)` — в первом круге модели
не было.

### D3. Запись действует, пока hunk непрерывно в PR diff

Каждый прогон, получивший PR diff, помечает `stale_at` у записей журнала, чьих `(path,
hunk_digest)` в этом диффе нет, — если после получения диффа его head совпал со свежим head PR
(та же сверка, что в D7). Иначе прогон прежнего head, получивший дифф до вытеснения, устарил бы
записи hunk'ов, которые в диффе актуального head есть, и следующий прогон перепроверил бы уже
проверенный код. Устаревшая запись hunk не исключает и не удаляется. Откат
hunk'а, затем «revert the revert» → между ними прогон увидел PR diff без hunk'а → запись
устарела → вернувшийся hunk снова в области. Когда его снова проверят, запись с тем же ключом
переактивируется: `stale_at = NULL`, новые `occurrences` и `review_run_id` — простой INSERT
упал бы на уникальном ключе и уронил бы транзакцию `completed`. Истории проверок журнал не
хранит, она в прогонах. Если между откатом и возвратом прогона не было, hunk непрерывно
присутствует для системы — его содержимое и правда уже проверено.

### D4. Вхождения считаются

Запись хранит `occurrences` — сколько раз hunk с этим `(path, hunk_digest)` был в проверенном
PR diff. В область входят hunk'и сверх записанного числа. Блок, скопированный с контекстом в
другое место того же файла, даёт второе вхождение и проверяется. В другом файле — другой путь,
другая запись.

### D5. Hunk с находками журнал не покрывает

Предложение Grinv: hunk с находкой прогона идёт модели на каждом push, пока находки на нём есть.
Запись о нём в журнале есть — с `has_findings = true`: такая запись hunk из области не
исключает, но отмечает его как уже побывавший в прогоне. Без неё `plan_scope` из `review-limits`
не отличил бы перепроверяемый hunk от нового: находка хранит якорь строки, а не дайджест hunk'а.
Повторная проверка переписывает признак: без находок — `false`, и запись начинает покрывать hunk. Дубль комментария не появляется — его сдерживает `thread_coverage`, как
сегодня. Выигрыш — откат исправления (тред outdated, человек закрыл) не прячет вернувшуюся
уязвимость.

Находка, которую `thread_coverage` подавил тредом, закрытым человеком и не outdated, для D5 не
считается: человек уже решил, что это не проблема. Иначе ложное срабатывание, которое модель
повторяет на каждом push, держало бы hunk вне журнала всю жизнь PR, и мы платили бы за
закрытые замечания, а не только за открытые. Outdated-тред находку не подавляет, поэтому
вернувшаяся уязвимость под это правило не попадает. Цена — токены на hunk'и с открытыми
замечаниями.

В журнал пишутся только hunk'и, фактически вошедшие в запрос к модели. Что `context_assembly`
отложил в `omitted` (не влезло в `context_max_tokens`), модель не видела: такие hunk'и не
пишутся и входят в область следующего прогона, даже если прогон `completed` без находок.

### D6. Сегменты нового файла

Новый файл в PR diff — один hunk `@@ -0,0 +1,N @@`, и любая правка в нём меняет дайджест
целиком. hunk из одних `+` длиннее `SEGMENT_MAX_LINES` (предложение 80) режется на сегменты по
строкам без отступа после пустой строки, не длиннее предела. Если такой строки в участке до
предела нет — как в Python-классе, где все методы с отступом, — граница ставится на пустой
строке перед строкой с минимальным отступом в участке, и только при отсутствии пустых строк —
ровно по пределу. Иначе принудительная нарезка по 80 строк сдвигала бы все следующие сегменты
от одной вставленной в начало строки, и правка одной функции отправляла бы модели почти весь
файл. Правило текстовое, без AST: AST
ограничен `ast_max_files` и пропадает при сбое tree-sitter (#227), граница сегмента должна быть
одинаковой во всех прогонах. Сегмент — единица области и журнала.

### D7. Вытеснение на `synchronize` — в воркере, по свежему head PR

Приём на `synchronize` прогоны прежних head не отменяет. Метаданные PR приём запрашивает до
транзакции записи, поэтому отмена на приёме зависела бы от порядка доставок: доставка B со
свежими для неё метаданными, вошедшая в транзакцию после закоммиченного прогона C, отменила бы
C, и коммит C остался бы без ревью и без check run, а #149 успешную доставку C не переотправит.
Частичный индекс `uq_review_runs_one_active_per_commit` допускает по активному прогону на
коммит, поэтому прогон нового head вставляется рядом с активными прогонами прежних.

Воркер там, где уже перечитывает статус — при взятии задачи, перед каждым вызовом модели и перед
переходом в `publishing`, — запрашивает head PR (`GET pulls/{n}`) и сверяет его с
`run.head_sha`. При расхождении прогон сам уходит в `cancelled` с `cancel_reason=superseded` и
`superseded_by_head_sha` из этого ответа, без вызова модели и публикации. Правило верно при
любом порядке доставок: прогон публикует, только если его коммит — head PR на момент проверки.
Отставание метаданных сразу после push здесь прогон не отменяет: прогон создаётся, только когда
метаданные приёма уже показали его head (D8), и расхождение после этого значит новый push.
`merge_requests.head_sha` для сверки не годится: в той же гонке доставка B вернула бы в него B.

Смена целевой ветки по-прежнему отменяет прогон на приёме (`_supersede` из #225) и пишет
`cancel_reason=base_changed` — #225 причину не хранил. Там отменяется прогон того же head,
который доставка и пересоздаёт, порядок доставок на это не влияет.

Окно между последней проверкой и POST остаётся — требование поэтому «не начинает публикацию
после проверки, показавшей отмену», а gate закрывает `settle_merge_gate`.

### D8. Устаревшая доставка

`opened`/`synchronize` с `event.head_sha != metadata.head_sha` прогон не создаёт и head не
сдвигает. Если на `event.head_sha` уже есть прогон, это запоздавший повтор вытесненного коммита:
ответ 202 `ignored`. Иначе запоздавшая доставка A после B (последний прогон на A — `cancelled`,
значит не дубль) создала бы прогон на A и вернула бы head запроса на изменение на A.

Если прогона на `event.head_sha` нет, расхождение может значить, что `GET pulls/{n}` сразу после
push ещё отдаёт прежний head, и `ignored` потерял бы свежий коммит: для GitHub это успешная
доставка, и #149 её не переотправит. Поэтому ответ `503`: доставку через минуты переотправит
повтор #149, который сам сверяет head со свежими метаданными и устаревшую не переотправляет
(`webhook_redelivery.py`). Колонка `head_updated_at` из первого круга не нужна.

## Risks / Trade-offs

- Hunk с находкой уходит модели на каждом push (D5) — расход растёт с числом открытых замечаний.
- Каждая проверка статуса в воркере — ещё запрос `GET pulls/{n}` (D7): до трёх на прогон плюс
  по одному на вызов модели.
- Откат и возврат без прогона между ними не перепроверяется (D3): содержимое то же, что проверено.
- Изменилась сигнатура в другом файле — hunk вызывающего кода не перепроверяется. Изменённая
  сигнатура сама в области; индекс определений (`add-tree-sitter-index`) позже может
  инвалидировать зависимые hunk'и.
- Смена правил владельца меняет `config_digest` и отправляет модели все открытые PR целиком.

## Migration Plan

1. Миграция: `reviewed_hunks`, `review_runs.cancel_reason`, `superseded_by_head_sha` — nullable,
   старый код их не читает. Новые значения нативных enum откатом не удаляются: downgrade
   оставляет тип, удаляет колонки.
2. Флаг `INCREMENTAL_REVIEW_ENABLED` (по умолчанию выключен) включает область по журналу и
   вытеснение. Откат — выключить флаг.
3. Существующие PR: журнал пуст, первый прогон после включения отправляет весь PR diff.
