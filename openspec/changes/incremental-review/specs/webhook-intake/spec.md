# Spec Delta

## MODIFIED Requirements

### Requirement: Действия opened и synchronize запускают ревью

Система SHALL запускать прогон ревью по событиям `pull_request` с действиями `opened` и `synchronize` своего PR (требование «Ревьюится только свой PR»). Для них SHALL создаваться или обновляться запись запроса на изменение — при `synchronize` head-коммит существующей записи сдвигается на новый — и создаваться прогон ревью в состоянии `queued` с источником прогона `webhook`, после чего задача ревью SHALL ставиться в очередь. Прогоны прежних head SHALL вытесняться (`incremental-review`). Успешный ответ — HTTP 202.

#### Scenario: Открытие PR запускает ревью

- **WHEN** приходит `pull_request` с действием `opened` и валидной подписью для зарегистрированного репозитория, ветка PR в самом репозитории
- **THEN** ответ — HTTP 202, существует запись запроса на изменение и прогон ревью в состоянии `queued` с источником `webhook`, и в очереди появляется задача ревью

#### Scenario: Новый коммит в PR запускает новый прогон

- **WHEN** приходит `pull_request` с действием `synchronize` с валидной подписью для зарегистрированного репозитория, ветка PR в самом репозитории
- **THEN** ответ — HTTP 202, head-коммит существующего запроса на изменение сдвигается на новый, создаётся новый прогон ревью в состоянии `queued`, и задача ставится в очередь

#### Scenario: Новый коммит во время ревью прежнего

- **WHEN** приходит `synchronize`, а прогон прежнего head ещё не завершён
- **THEN** прежний прогон `cancelled` с причиной `superseded` и head нового коммита, и отмена закоммичена до вставки нового прогона

## ADDED Requirements

### Requirement: Устаревшая доставка не создаёт прогон

Доставка `opened` или `synchronize`, чей `head_sha` не совпадает с head в свежих метаданных PR, SHALL NOT создавать прогон и сдвигать head запроса на изменение. Если на `head_sha` доставки уже есть прогон, ответ SHALL быть HTTP 202 с исходом `ignored`. Иначе ответ SHALL быть HTTP 503, чтобы доставку переотправил повтор упавших доставок со своей сверкой head.

#### Scenario: Запоздавшая доставка прежнего push

- **WHEN** после push B приходит запоздавшая доставка `synchronize` коммита A, а метаданные PR уже показывают head B
- **THEN** прогон на A не создаётся, прогон B не вытесняется, head запроса на изменение — B

#### Scenario: Метаданные отстают от push

- **WHEN** приходит `synchronize` коммита B, прогонов на B нет, а метаданные PR ещё показывают head A
- **THEN** прогон не создаётся, ответ — HTTP 503, и повтор доставки с head B создаёт прогон на B
