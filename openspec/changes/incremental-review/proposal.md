# Proposal

> **Статус: предложение, не утверждено.** Кода, миграций и правок `openspec/specs/` нет.
> Второй круг после ревью #239: ядро урезано, лимиты вынесены в change `review-limits`.

## Why

Каждый `synchronize` создаёт прогон, который заново ревьюит весь дифф PR
(`compare/{base_sha}...{head_sha}`): модель повторно получает уже проверенный код, а серия push
даёт серию параллельных полных прогонов одного PR, каждый из которых публикует ревью и
выставляет gate. Повторную проверку и гонку прогонов нужно убрать, не открыв пути, которым код
мерджится без ревью.

## What Changes

- **Область ревью — hunk'и PR diff минус журнал проверенных** по содержимому hunk'а и
  конфигурации ревью (design, D2). Водяного знака и режимов прогона нет.
- **Журнал не пропускает вернувшийся код.** Запись действует, пока hunk непрерывно есть в PR
  diff: исчезнувший hunk помечается устаревшим, и «revert the revert» проверяется заново.
  Журнал считает вхождения: копия того же блока в том же файле не покрыта записью оригинала.
  Hunk, по которому у прогона есть находки, журнал не покрывает: запись с `has_findings`
  только отмечает его перепроверяемым. Не попадает в журнал отложенное
  сборкой контекста в `omitted`: модель его не видела.
- **Новый файл дробится на сегменты**, чтобы правка в нём не отправляла модели файл целиком.
- **Пустая область — прогон без модели.** Gate на новый head ставится как у любого
  завершённого прогона, включая поправку `settle_merge_gate` (#225).
- **Новый push вытесняет активные прогоны прежних head в воркере.** Приём на `synchronize`
  ничего не отменяет: метаданные он берёт до транзакции, и отмена зависела бы от порядка
  доставок. Воркер при взятии задачи, перед вызовом модели и перед публикацией сверяет head
  прогона со свежим head PR и при расхождении сам уходит в `cancelled(superseded)`. Смена
  целевой ветки отменяет прогон на приёме, как в #225.
- **Устаревшая доставка** (`head_sha` события не равен head в свежих метаданных) прогона не
  создаёт. Если прогона на коммит события ещё нет, ответ `503`: доставку переотправит повтор
  #149 со своей сверкой head.
- **Сводка ревью называет охват** прогона и не пишет «критичных проблем нет» при открытых
  `critical` тредах.

Поведение действует при включённом флаге `INCREMENTAL_REVIEW_ENABLED`; при выключенном прогон
ревьюит весь PR diff, как сегодня.

## Не входит

Для обоих change — этого и `review-limits`.

| Что | Почему |
|---|---|
| Водяной знак, режимы `full/incremental/rebased` | Журнал решает область сам; знак давал дыру при смене ветки |
| Состояния замечаний (`possibly_fixed`, `outdated`, …), fingerprint, L1/L2 | Дубли сдерживает `thread_coverage`; L2 против закрытых тредов подавлял бы новые проблемы |
| Сериализация публикации | Один воркер с prefetch=1. Сессионный `pg_advisory_lock` переживает ROLLBACK в пуле и не работает через pgbouncer; для второго воркера — `pg_advisory_xact_lock` в транзакции публикации |
| Теневой режим | Один воркер, откат — выключить флаг |
| Лимиты частоты, backpressure, `defer`, авто-добор по квоте | Один воркер на стенде; отсрочка конфликтует с выметателем `queued` и merge gate |
| `installation_id` в базе и квота на инсталляцию | `review-rest-api` запрещает хранить; квота — по репозиторию |
| Бюджет повторов | Уже ограничен повтором доставок #149 и `x-delivery-limit` #230 |
| `GET …/coverage` | Покрытие отдаёт `ReviewJob` |
| Многочанковое ревью | Отдельный change: меняет пакет контекста и верификатор |

## Capabilities

### New Capabilities

- `incremental-review`: область ревью по журналу, срок действия и подсчёт записей, сегменты
  новых файлов, пустая область, вытеснение.

### Modified Capabilities

- `webhook-intake`: MODIFIED «Действия opened и synchronize запускают ревью» — вытеснение;
  ADDED «Устаревшая доставка не создаёт прогон».
- `review-data-model`: ADDED журнал проверенных hunk'ов, причина отмены прогона.
- `review-pipeline`: ADDED «Сводка ревью называет охват прогона».

## Impact

- Код (на этапе реализации): `app/domain` (чистые `hunk_digest`, `split_segments`,
  `review_scope`), `review_pipeline.py`, `context_assembly.py`, `publish_review.py`,
  `handle_webhook.py` (причина отмены в `_supersede` из #225).
- БД: таблица `reviewed_hunks`, колонки `review_runs.cancel_reason`, `superseded_by_head_sha` —
  миграциями на этапе реализации.
- API: `cancel_reason` и `superseded_by` в `ReviewJob` — аддитивно. Тело сообщения очереди и
  статусы прогона не меняются.
- Зависит от #225 (`_supersede`, `settle_merge_gate`, правило дубля по последнему прогону) и
  #230 (`x-delivery-limit`, `check_consumer_timeout`).
