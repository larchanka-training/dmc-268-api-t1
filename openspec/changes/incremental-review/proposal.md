# Proposal

> **Статус: предложение, не утверждено.** Кода, миграций и правок `openspec/specs/` нет.
> Второй круг после ревью #239: ядро урезано, лимиты вынесены в change `review-limits`.

## Why

Каждый `synchronize` создаёт прогон, который заново ревьюит весь дифф PR
(`compare/{base_sha}...{head_sha}`): модель повторно получает уже проверенный код, а серия push
даёт серию параллельных полных прогонов одного PR, каждый из которых публикует ревью и
выставляет gate. Повторную проверку и гонку прогонов нужно убрать, не открыв пути, которым код
мерджится без ревью.

## What Changes

- **Область ревью — hunk'и PR diff минус журнал проверенных** по содержимому hunk'а и
  конфигурации ревью (design, D2). Водяного знака и режимов прогона нет.
- **Исчезнувший hunk возвращает файл в область.** Если у файла есть запись журнала, чьего hunk'а
  в PR diff нет, весь файл идёт модели, а прогон переписывает все записи файла: push, удаливший
  проверку доступа, без ревью не проходит. Удаление от правки по дайджесту не отличить, поэтому
  правка в проверенном файле тоже отправляет модели весь файл — гранулярность области файл, а не
  hunk. Последствия удаления в других файлах change не ловит (design, Risks).
  Hunk, чей дайджест повторяется в файле, журнал не покрывает. Перепроверяемый hunk — с находкой,
  с отсеянным кандидатом в его файле или без правил владельца — журнал тоже не покрывает: запись
  с `needs_recheck` только отмечает его показанным модели, и подавленный закрытым тредом
  `critical` признак сохраняет. Не попадает в журнал отложенное сборкой контекста в `omitted`:
  модель его не видела.
- **Новый файл дробится на сегменты**, чтобы файл больше бюджета проверялся по частям.
- **Пустая область — прогон без модели.** Gate на новый head ставится как у любого
  завершённого прогона, включая поправку `settle_merge_gate` (#225).
- **Новый push вытесняет активные прогоны прежних head в воркере.** Приём на `synchronize`
  ничего не отменяет: метаданные он берёт до транзакции, и отмена зависела бы от порядка
  доставок. Воркер при взятии задачи и перед публикацией сверяет head прогона со свежим head PR
  и уходит в `cancelled`, если коммит прогона — предок свежего head; разошедшуюся историю
  (force-push) отменяет только сверка перед публикацией, когда отставание чтений уже прошло. Сбой
  сверки прогон не отменяет и не роняет. Смена целевой ветки отменяет прогон на приёме, как в #225.
- **Устаревшая доставка** (`head_sha` события не равен head в свежих метаданных) прогона не
  создаёт. Если прогона на коммит события ещё нет, ответ `502`, как при сбое метаданных:
  доставку переотправит повтор #149 со своей сверкой head — ревью свежего push в этом случае
  начинается на 5–10 минут позже.
- **Сводка ревью называет охват** прогона и не пишет «блокирующих проблем нет» при открытых
  тредах не ниже порога `min_severity`.

Поведение действует при включённом флаге `INCREMENTAL_REVIEW_ENABLED`; при выключенном прогон
ревьюит весь PR diff, как сегодня.

## Не входит

Для обоих change — этого и `review-limits`.

| Что | Почему |
|---|---|
| Водяной знак, режимы `full/incremental/rebased` | Журнал решает область сам; знак давал дыру при смене ветки |
| Состояния замечаний (`possibly_fixed`, `outdated`, …), fingerprint, L1/L2 | Дубли сдерживает `thread_coverage`; L2 против закрытых тредов подавлял бы новые проблемы |
| Сериализация публикации | Один воркер с prefetch=1. Сессионный `pg_advisory_lock` переживает ROLLBACK в пуле и не работает через pgbouncer; для второго воркера — `pg_advisory_xact_lock` в транзакции публикации |
| Теневой режим | Один воркер, откат — выключить флаг |
| Лимиты частоты, backpressure, `defer`, авто-добор по квоте | Один воркер на стенде; отсрочка конфликтует с выметателем `queued` и merge gate |
| `installation_id` в базе и квота на инсталляцию | `review-rest-api` запрещает хранить; квота — по репозиторию |
| Бюджет повторов | Уже ограничен повтором доставок #149 и `x-delivery-limit` #230 |
| Бюджет токенов прогона | Прогон уже ограничен `context_max_tokens` и `LlmLimits`, сутки — квотой |
| Предел числа файлов и строк области, приоритет CI | Дублирует `context_max_tokens`; `omitted` и так даёт неполное покрытие и `failure` |
| Шум по `.gitattributes` | К лимитам не относится, добавляет чтение файла, кэш и разбор шаблонов |
| Причина отмены и head вытеснившего коммита в базе | Потребителя нет: gate их не читает; свежий head пишется в лог отмены |
| `GET …/coverage` | Покрытие отдаёт `ReviewJob` |
| Многочанковое ревью | Отдельный change: меняет пакет контекста и верификатор |

## Capabilities

### New Capabilities

- `incremental-review`: область ревью по журналу, удаление кода и повторяющиеся hunk'и, сегменты
  новых файлов, пустая область, вытеснение.

### Modified Capabilities

- `webhook-intake`: MODIFIED «Действия opened и synchronize запускают ревью» — приём не
  отменяет прогоны прежних head; ADDED «Устаревшая доставка не создаёт прогон» — под флагом.
- `review-data-model`: ADDED журнал проверенных hunk'ов.
- `review-pipeline`: ADDED «Сводка ревью называет охват прогона».

## Impact

- Код (на этапе реализации): `app/domain` (чистые `hunk_digest`, `split_segments`,
  `review_scope`), `review_pipeline.py`, `context_assembly.py`, `publish_review.py`,
  `handle_webhook.py` (устаревшая доставка).
- БД: таблица `reviewed_hunks` — миграцией на этапе реализации.
- API: не меняется. Тело сообщения очереди и статусы прогона не меняются.
- Зависит от #225 (`_supersede`, `settle_merge_gate`, правило дубля по последнему прогону) и
  #230 (`x-delivery-limit`, `check_consumer_timeout`).
