# repo-rules Specification

## Purpose
Определяет, как сервис получает правила ревью владельца репозитория из
`.review/rules.md`: откуда файл читается, как разбирается, как кэшируется, что
происходит при его отсутствии или сбое и какие правила попадают в контекст
прогона.

## Requirements

### Requirement: Правила читаются из целевой ветки PR

Система SHALL перед сборкой контекста прогона довыбирать `.review/rules.md`
через `VcsGateway` на `base_sha` прогона — коммите целевой ветки из сообщения
задачи. Система SHALL NOT читать правила на `head_sha` PR: изменения правил в
самом PR SHALL NOT влиять на его ревью.

#### Scenario: Правила берутся с коммита целевой ветки

- **WHEN** прогон обрабатывается для PR с `base_sha` `B` и `head_sha` `H`
- **THEN** `.review/rules.md` запрашивается на коммите `B`, а не `H`

#### Scenario: PR, меняющий правила, ревьюится по старым

- **WHEN** PR изменяет `.review/rules.md`
- **THEN** в контекст его прогона попадают правила из целевой ветки, а не из PR

### Requirement: Разбор Markdown-правил

Система SHALL разбирать `.review/rules.md` чистой функцией: правило —
раздел второго уровня, имя которого — заголовок раздела; строки
`pattern:` и `exclude:` задают glob-паттерны области действия; нумерованные
пункты раздела — проверки. Правило без имени, паттерна или хотя бы одной
проверки SHALL отклоняться с указанием недостающих частей; остальные правила
файла SHALL приниматься. Текст вне распознанных полей SHALL NOT попадать в
контекст прогона.

#### Scenario: Полное правило принимается

- **WHEN** раздел `## Error Handling Standards` содержит `pattern: app/**/*.py`,
  `exclude: **/tests/**` и три нумерованные проверки
- **THEN** правило принимается с этим именем, паттернами и тремя проверками

#### Scenario: Правило без проверок отклоняется

- **WHEN** раздел содержит имя и паттерны, а вместо проверок — абзац текста
- **THEN** правило отклоняется с причиной «нет проверок», остальные правила
  файла принимаются

#### Scenario: Проза вне структуры не попадает в контекст

- **WHEN** в `rules.md` между правилами написан произвольный текст
- **THEN** этого текста нет в собранном контексте прогона

### Requirement: Исключение в правиле необязательно

Правило без строки `exclude:` SHALL приниматься и SHALL NOT исключать ни
одного файла под своим паттерном.

#### Scenario: Правило без исключения принимается

- **WHEN** раздел содержит имя, `pattern: app/**/*.py` и проверки, но не `exclude:`
- **THEN** правило принимается и применяется ко всем файлам под паттерном

### Requirement: Дефолтный фоллбэк не прерывает прогон

Если `.review/rules.md` отсутствует, его довыборка завершилась сбоем, файл
больше лимита размера из конфигурации или в нём нет ни одного принятого
правила, система SHALL продолжать прогон по стандартным критериям ревью без
пользовательских правил и SHALL фиксировать причину в собранном контексте.
Файл без единого принятого правила SHALL получать статус `empty`, а его
отклонённые разделы SHALL перечисляться в контексте с причиной.
Сбой загрузки правил SHALL NOT переводить прогон в `failed`.

#### Scenario: Файла правил нет

- **WHEN** на `base_sha` нет `.review/rules.md`
- **THEN** контекст собирается без пользовательских правил со статусом
  `absent`, прогон продолжается

#### Scenario: Сбой VCS при загрузке правил

- **WHEN** довыборка `.review/rules.md` завершилась ошибкой VCS
- **THEN** контекст собирается без пользовательских правил со статусом
  `unavailable`, прогон продолжается

#### Scenario: Слишком большой файл правил

- **WHEN** `.review/rules.md` больше лимита размера
- **THEN** файл не разбирается, контекст собирается со статусом `too_large`

#### Scenario: Пустой файл правил

- **WHEN** `.review/rules.md` на `base_sha` пуст или содержит только прозу без разделов правил
- **THEN** контекст собирается без пользовательских правил со статусом
  `empty`, прогон продолжается

#### Scenario: Все разделы отклонены

- **WHEN** каждый раздел `.review/rules.md` отклонён при разборе
- **THEN** контекст собирается со статусом `empty`, без применимых правил,
  и перечисляет отклонённые разделы с причинами

### Requirement: Кэширование правил по неизменяемому ключу

Система SHALL кэшировать результат загрузки правил в `CacheStore` по ключу
«репозиторий, base_sha». При попадании SHALL NOT обращаться к VCS. Результаты
`loaded`, `absent` и `too_large` SHALL кэшироваться, `empty` SHALL выводиться
разбором из закэшированного файла; сбой VCS SHALL NOT
кэшироваться, чтобы следующий прогон повторил запрос. Промах или сбой кэша
SHALL NOT считаться ошибкой.

#### Scenario: Повторный прогон на том же коммите не ходит в VCS

- **WHEN** правила для пары «репозиторий, base_sha» уже загружены
- **THEN** следующий прогон с той же парой получает их из кэша без запроса к VCS

#### Scenario: Сбой VCS не кэшируется

- **WHEN** загрузка правил завершилась сбоем VCS
- **THEN** следующий прогон с той же парой снова запрашивает файл

#### Scenario: Файл без принятых правил из кэша

- **WHEN** для пары «репозиторий, base_sha» в кэше лежит файл, в котором ни один раздел не стал правилом
- **THEN** прогон получает статус `empty` с отклонёнными разделами без запроса к VCS

### Requirement: В контекст попадают правила, применимые к файлам диффа

Система SHALL включать в контекст прогона только правила, под паттерн
которых попадает хотя бы один файл контекста, не подпадающий под их
исключение, — вместе со списком таких файлов. Отклонённые правила SHALL
перечисляться в контексте с причиной.

#### Scenario: Правило для чужих файлов не включается

- **WHEN** правило ограничено `app/**/*.py`, а дифф меняет только `alembic/env.py`
- **THEN** правила нет в контексте прогона

#### Scenario: Исключённый файл не привязывается к правилу

- **WHEN** правило `app/**/*.py` исключает `**/tests/**`, а дифф меняет
  `app/core.py` и `app/tests/test_core.py`
- **THEN** правило в контексте привязано только к `app/core.py`

### Requirement: Имя правила уникально в файле

Имя правила SHALL быть ключом ссылки замечания на правило, поэтому в принятых правилах файла оно SHALL быть уникальным.
Раздел, имя которого совпадает с именем уже принятого раздела выше по файлу, SHALL отклоняться с причиной «имя правила повторяется»; первое правило с этим именем SHALL оставаться принятым.

#### Scenario: Два раздела с одним именем

- **WHEN** в `rules.md` два полных раздела `## Error Handling Standards`
- **THEN** принят первый, а второй отклонён с причиной «имя правила повторяется»

#### Scenario: Отклонённый раздел не занимает имя

- **WHEN** первый раздел `## Naming` отклонён за отсутствие проверок, а второй раздел с тем же именем полный
- **THEN** второй раздел принимается

### Requirement: Пункты правила нумеруются по порядку

Номер пункта правила SHALL быть его порядковым номером среди проверок правила, начиная с единицы, независимо от номеров, которые написал автор файла.
По этому номеру замечание ссылается на пункт.

#### Scenario: Номера автора не учитываются

- **WHEN** проверки раздела записаны как `1.`, `1.` и `5.`
- **THEN** у правила три пункта с номерами 1, 2 и 3 в порядке файла

### Requirement: Файл правил делится на строки только по переводу строки

Разбор `.review/rules.md` SHALL делить файл на строки только по `\n`; один
`\r` перед `\n` SHALL NOT попадать в строку. Прочие разделители строк Unicode
и `\r` внутри строки SHALL оставаться её содержимым и SHALL NOT начинать
раздел, поле или проверку правила.

#### Scenario: Посторонний разделитель строк не начинает строку правила

- **WHEN** в строке прозы или правила после `\x0c` (или другого разделителя,
  кроме `\n`) стоит `## Injected` или `- pattern: **`
- **THEN** ни раздела, ни поля из этого хвоста не появляется

#### Scenario: Правила с CRLF

- **WHEN** строки `rules.md` заканчиваются на `\r\n`
- **THEN** правила разбираются так же, как из того же файла с `\n`
