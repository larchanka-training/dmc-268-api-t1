# webhook-intake Specification

## Purpose

Определяет приёмную часть конвейера автоматического ревью (Context Level 1): как система принимает вебхуки GitHub, проверяет их подлинность, решает, какие события pull request запускают ревью, а какие игнорируются, достаёт дифф и метаданные через VCS-шлюз и ставит задачу ревью в очередь, передавая воркеру идентификаторы, а не содержимое; разбор диффа на файлы и hunk'и с фильтрацией шума выполняет воркер конвейера ревью той же чистой функцией домена.

## Requirements

### Requirement: Проверка подлинности вебхука

Система SHALL проверять подпись каждого вебхука до любой обработки payload'а. Подпись — HMAC-SHA256, вычисленный по сырому телу запроса с секретом вебхука, передаётся в заголовке `X-Hub-Signature-256` в формате `sha256=<hex>`. Сравнение SHALL выполняться за постоянное время (constant-time), без раннего выхода по длине или первым различающимся байтам.

Вебхук без заголовка подписи, с подписью не в формате `sha256=<hex>`, с подписью, вычисленной по другому ключу или другому телу, SHALL получать HTTP 401. При отклонении SHALL NOT создаваться ни одной записи в базе и SHALL NOT публиковаться ни одного сообщения в очередь.

#### Scenario: Валидная подпись пропускает вебхук

- **WHEN** приходит вебхук с корректной подписью `sha256=<hex>` в заголовке `X-Hub-Signature-256`
- **THEN** запрос продолжает обрабатываться по правилам событий pull request

#### Scenario: Отсутствующая подпись отклоняется

- **WHEN** приходит вебхук без заголовка `X-Hub-Signature-256`
- **THEN** ответ — HTTP 401, записей не создаётся и очередь не трогается

#### Scenario: Неверная подпись отклоняется

- **WHEN** подпись в заголовке не соответствует HMAC-SHA256 тела с секретом вебхука, включая подпись без префикса `sha256=<hex>` и подпись по другому телу
- **THEN** ответ — HTTP 401, записей не создаётся и очередь не трогается

#### Scenario: Подпись проверяется до разбора payload'а

- **WHEN** приходит вебхук с неверной подписью и телом, не являющимся корректным JSON
- **THEN** ответ — HTTP 401, а не ошибка разбора JSON

### Requirement: Неподдержанный провайдер получает 501

Маршрут приёма провайдер-нейтральный (`/api/v1/webhooks/{provider}`), но приём SHALL поддерживаться только для провайдеров с реализованным адаптером (GitHub). Вебхук провайдера без адаптера SHALL получать HTTP 501: записей не создаётся, очередь не трогается. Добавление провайдера — новый адаптер без изменения маршрута.

#### Scenario: Вебхук неподдержанного провайдера получает 501

- **WHEN** приходит вебхук на провайдере без адаптера (например, `gitlab`)
- **THEN** ответ — HTTP 501, записей нет и очередь не трогается

#### Scenario: Маршрут не меняется с появлением провайдера

- **WHEN** добавляется адаптер нового провайдера
- **THEN** маршрут остаётся `/api/v1/webhooks/{provider}`, и обработка подчиняется общим требованиям этой спеки

### Requirement: Запуск ревью событиями pull request

Система SHALL запускать прогон ревью по событиям `pull_request` с действиями `opened` и `synchronize`. Для этих действий SHALL создаваться или обновляться запись запроса на изменение — при `synchronize` head-коммит существующей записи сдвигается на новый — и создаваться прогон ревью в состоянии `queued` с источником прогона `webhook`, после чего задача ревью SHALL ставиться в очередь. Успешный ответ — HTTP 202.

Действия `reopened`, `closed` и любые иные SHALL получать HTTP 202 (ignored): записей не создаётся, очередь не трогается, ответ — не 5xx. При `reopened` система SHALL NOT переназначать бота ревьюером автоматически: пользователь переназначает его вручную, и следующее событие обрабатывается как обычный запуск.

#### Scenario: Открытие PR запускает ревью

- **WHEN** приходит `pull_request` с действием `opened` и валидной подписью для зарегистрированного репозитория
- **THEN** ответ — HTTP 202, существует запись запроса на изменение и прогон ревью в состоянии `queued` с источником `webhook`, и в очереди появляется задача ревью

#### Scenario: Новый коммит в PR запускает новый прогон

- **WHEN** приходит `pull_request` с действием `synchronize` с валидной подписью для зарегистрированного репозитория
- **THEN** ответ — HTTP 202, head-коммит существующего запроса на изменение сдвигается на новый, создаётся новый прогон ревью в состоянии `queued`, и задача ставится в очередь

#### Scenario: Reopened игнорируется

- **WHEN** приходит `pull_request` с действием `reopened`
- **THEN** ответ — HTTP 202 (ignored), записей не создаётся и в очередь ничего не уходит, а бот не переназначается ревьюером автоматически

#### Scenario: Неизвестное действие игнорируется без сбоя

- **WHEN** приходит `pull_request` с действием, отличным от `opened`, `synchronize` и `reopened` (например, `closed`)
- **THEN** ответ — HTTP 202 (ignored), а не 5xx, записей нет и очередь не трогается

### Requirement: Незарегистрированный репозиторий игнорируется

Вебхук для репозитория, которого нет в системе, SHALL получать HTTP 202 (ignored) без создания записей и без постановки задач. Регистрация репозитория на лету по вебхуку SHALL NOT выполняться: регистрацию выполняет отдельная операция с авторизацией.

#### Scenario: Вебхук незарегистрированного репозитория не создаёт записей

- **WHEN** приходит валидный вебхук `pull_request.opened` для репозитория, не зарегистрированного в системе
- **THEN** ответ — HTTP 202 (ignored), записей не создаётся и задача не ставится

#### Scenario: Репозиторий не регистрируется автоматически

- **WHEN** валидный вебхук для незарегистрированного репозитория приходит повторно
- **THEN** репозиторий по-прежнему не зарегистрирован, а реакция системы не изменилась

### Requirement: Повторная доставка на тот же коммит не создаёт второй активный прогон

Повторный вебхук для того же запроса на изменение и того же head-коммита, у которого уже есть прогон в нетерминальном состоянии, SHALL NOT создавать второй активный прогон — ограничение уже обеспечивает частичный уникальный индекс схемы. Обработка SHALL завершаться без сбоя: ответ — HTTP 202 с проекцией найденного прогона, той же, что и ответ на его собственную доставку (контракт: «ReviewJob создан или найден существующий»; не-2xx хостинг считает доставку неудавшейся и повторяет её). Повторная доставка SHALL NOT переписывать существующие записи: дубль проверяется до обновления merge_request.

Гонку параллельных доставок страхуют частичные уникальные индексы. Доставка, вставку которой индекс отклонил, после отката SHALL искать записи победителя по естественному ключу (репозиторий, номер): у победителя с тем же коммитом есть активный прогон — проигравший отвечает его проекцией; у победителя с другим коммитом есть только merge_request — проигравший создаёт новый прогон на доставленный коммит поверх записей победителя. Второй отказ индекса SHALL пробрасываться наверх: ответ 5xx, хостинг повторит доставку.

#### Scenario: Повторная доставка безвредна

- **WHEN** приходит вебхук для head-коммита, у которого уже есть прогон в нетерминальном состоянии
- **THEN** второй активный прогон не создаётся, и ответ — не 5xx

#### Scenario: Повторная доставка отвечает 202 с проекцией существующего прогона

- **WHEN** приходит вебхук для head-коммита, у которого уже есть активный прогон
- **THEN** ответ — HTTP 202 с проекцией `ReviewJob` существующего прогона, новых записей нет и очередь не трогается

#### Scenario: Проигравший гонку на тот же коммит отвечает прогоном победителя

- **WHEN** две параллельные доставки создают прогон на один и тот же коммит, и уникальный индекс отклоняет вторую вставку
- **THEN** проигравший после отката отвечает HTTP 202 с проекцией активного прогона победителя

#### Scenario: Победитель гонки с другим коммитом получает новый прогон

- **WHEN** в гонке первых доставок победитель нёс другой head-коммит, и активного прогона на доставленный коммит у него нет
- **THEN** проигравший после отката обновляет merge_request победителя и создаёт новый прогон на доставленный коммит, а второй отказ индекса даёт 5xx

#### Scenario: Новый коммит после активного прогона запускает новый прогон

- **WHEN** приходит вебхук с новым head-коммитом для запроса на изменение, у которого есть активный прогон на предыдущем коммите
- **THEN** создаётся новый прогон ревью для нового коммита, а предыдущий прогон по-прежнему указывает свой коммит

### Requirement: Получение диффа через VCS-шлюз

Для запускаемого прогона система SHALL получать дифф и метаданные PR через порт `VcsGateway`, авторизуясь installation-токеном GitHub App по `installation_id` из payload'а вебхука: один и тот же сервис работает с любым числом репозиториев без изменения настроек. Базовый коммит SHALL всегда браться из свежих метаданных PR — единый поток для `opened` и `synchronize`.

Ошибка VCS при получении диффа или метаданных SHALL приводить к ответу HTTP 502; прогон ревью SHALL NOT создаваться, и задача SHALL NOT ставиться в очередь.

#### Scenario: Дифф достаётся по installation_id из payload'а

- **WHEN** обрабатывается вебхук зарегистрированного репозитория
- **THEN** дифф и метаданные PR запрашиваются с авторизацией по installation-токену для `installation_id` из payload'а этого вебхука, без настройки инсталляции в конфигурации сервиса

#### Scenario: Базовый коммит — из метаданных PR

- **WHEN** создаётся задача ревью для любого действия, запускающего ревью
- **THEN** базовый коммит задачи совпадает с базовым коммитом из свежих метаданных PR, а не берётся из поля payload'а

#### Scenario: Ошибка VCS — 502

- **WHEN** VCS API недоступен или отвечает ошибкой на запрос диффа или метаданных
- **THEN** ответ — HTTP 502, прогон ревью не создаётся и задача не ставится

### Requirement: Разбор диффа на файлы и hunk'и

Вебхук SHALL NOT разбирать дифф: приёмная часть достаёт дифф через VCS-шлюз (fail-fast — ошибка VCS даёт 502 до создания записей), но не разбирает его. Разбор unified diff на файлы и hunk'и SHALL выполнять воркер конвейера ревью при обработке задачи, повторно достав дифф по идентификаторам из сообщения очереди, — чистой функцией `parse_diff`: для каждого файла — путь, старый путь при переименовании, признак бинарности и hunk'и с точными номерами строк из заголовков `@@ -a,b +c,d @@`. Строки контекста (пробел в начале) SHALL NOT попадать в множества изменённых строк, но SHALL сдвигать счётчики строк; маркер `\ No newline at end of file` SHALL NOT ломать разбор; пустой дифф SHALL давать пустой список файлов.

Дифф SHALL NOT сохраняться в базе ни вебхуком, ни воркером: он транзиентен в обработке задачи, а сообщение очереди несёт идентификаторы (`head_sha`, `base_sha`, номер PR), по которым воркер достаёт и разбирает дифф повторно той же чистой функцией.

#### Scenario: Multi-file дифф разбирается на файлы и hunk'и

- **WHEN** воркер разбирает дифф, затрагивающий несколько файлов
- **THEN** каждый файл разобран на hunk'и, и изменённые строки несут точные номера строк новой и старой версии

#### Scenario: Бинарный файл распознаётся

- **WHEN** дифф содержит бинарный файл
- **THEN** файл помечается бинарным, его hunk'и пусты, и разбор остальных файлов продолжается

#### Scenario: Переименование даёт оба пути

- **WHEN** дифф содержит переименованный файл
- **THEN** разобранный файл несёт и старый, и новый путь

#### Scenario: Дифф не персистится

- **WHEN** приём вебхука завершился созданием прогона и постановкой задачи
- **THEN** в базе появляются только записи запроса на изменение и прогона ревью, сообщение очереди содержит идентификаторы, а не содержимое диффа, а разбор диффа выполняет воркер при обработке задачи

### Requirement: Фильтрация шума в диффе

Перед ревью из разобранного воркером диффа SHALL отфильтровываться файлы, не подлежащие ревью: lock-файлы (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `composer.lock`, `Cargo.lock`, `Gemfile.lock`, `go.sum` и другие lock-файлы), минифицированные (`*.min.js`, `*.min.css`), сгенерированные (`*.generated.*`, `*.pb.go`), бинарные файлы и файлы вендорных директорий (`vendor/`, `node_modules/`). Обычные исходники SHALL проходить фильтр неизменёнными. Фильтрация — чистая функция `filter_diff_files` в домене; правила фильтрации SHALL быть определены в одном месте, без дублирования в адаптерах.

#### Scenario: Lock-файл отфильтрован

- **WHEN** дифф содержит `package-lock.json` или иной lock-файл
- **THEN** этот файл исключается из результата фильтрации

#### Scenario: Минифицированный и сгенерированный код отфильтрован

- **WHEN** дифф содержит `*.min.js`, `*.min.css`, `*.generated.*` или `*.pb.go`
- **THEN** эти файлы исключаются из результата фильтрации

#### Scenario: Бинарные и вендорные пути отфильтрованы

- **WHEN** дифф содержит бинарный файл или файл внутри `vendor/` либо `node_modules/`
- **THEN** эти файлы исключаются из результата фильтрации

#### Scenario: Обычные исходники проходят фильтр

- **WHEN** дифф содержит обычные файлы исходного кода
- **THEN** они остаются в результате фильтрации с нетронутыми hunk'ами

### Requirement: Постановка задачи ревью в очередь

Задача ревью SHALL ставиться в очередь через порт `JobQueue` единственным методом `enqueue`. Тело сообщения — JSON только с доменными данными по формату `docs/SYSTEM_DESIGN.md` §4.2: `job_id`, `event_type`, `action`, `repository` и `pull_request` с номером, `head_sha` и `base_sha`. Приоритет SHALL передаваться свойством AMQP, а не полем тела; очередь SHALL объявляться с аргументом `x-max-priority`. Для игнорируемых событий и отклонённых вебхуков SHALL NOT публиковаться ни одного сообщения.

#### Scenario: Сообщение несёт только доменные данные

- **WHEN** прогон ревью успешно создан и задача поставлена в очередь
- **THEN** тело сообщения соответствует формату `docs/SYSTEM_DESIGN.md` §4.2 и не содержит ни диффа, ни метаданных доставки

#### Scenario: Приоритет живёт в свойствах AMQP

- **WHEN** задача публикуется в очередь
- **THEN** приоритет передан свойством AMQP-сообщения, а в теле сообщения поля приоритета нет

#### Scenario: Очередь объявляется с x-max-priority

- **WHEN** адаптер очереди публикует первое сообщение
- **THEN** очередь объявлена с аргументом `x-max-priority`, так что приоритеты сообщений учитываются при выдаче

#### Scenario: Игнорируемое событие ничего не публикует

- **WHEN** вебхук завершается как ignored или отклонён по подписи
- **THEN** в очереди не появляется нового сообщения

### Requirement: Сбой постановки задачи переводит прогон в failed

Сбой публикации задачи в брокер после закоммиченного прогона SHALL переводить прогон в терминальное состояние `failed` с причиной сбоя, а вебхук SHALL получать ответ 5xx: не-2xx хостинг считает доставку неудавшейся и повторяет её, и повторная доставка создаёт новый прогон — `failed` не блокирует повтор. Компенсация SHALL NOT маскировать исходную ошибку: прогон, уже переведённый в терминальное состояние, не переписывается; если компенсация не удалась (база недоступна), ответ остаётся 5xx, а зависший прогон выметает sweep обработки.

#### Scenario: Сбой брокера переводит прогон в failed

- **WHEN** публикация задачи в очередь завершается исключением после закоммиченного прогона
- **THEN** прогон переводится в `failed` с причиной сбоя, и вебхук отвечает 5xx

#### Scenario: Повторная доставка после сбоя создаёт новый прогон

- **WHEN** после сбоя постановки приходит повторная доставка того же коммита
- **THEN** создаётся новый прогон в `queued` и задача ставится в очередь — `failed` повтор не блокирует

#### Scenario: Ответ остаётся 5xx, даже если компенсация не удалась

- **WHEN** публикация упала и компенсация не смогла записать `failed`
- **THEN** вебхук всё равно отвечает 5xx

### Requirement: Публикация переживает простой соединения

Адаптер очереди SHALL публиковать задачу, даже если брокер закрыл соединение, простоявшее без трафика, а клиент ещё считает его открытым (`is_closed` остаётся `False`): при отказе публикации из-за соединения или закрытого канала адаптер переоткрывает обе стороны, объявляет топологию и повторяет публикацию один раз. Повторный отказ SHALL пробрасываться вызывающему — его обрабатывает компенсация приёма (прогон в `failed`, ответ 5xx). Отказы публикации (nack, unroutable) повторяться SHALL NOT: повтор не устраняет их причину.

#### Scenario: Проявившееся соединение переоткрывается, задача публикуется

- **WHEN** публикация падает из-за соединения, закрытого брокером после простоя, а `is_closed` ещё `False`
- **THEN** адаптер открывает новое соединение, публикует задачу, и вызывающий исключения не получает

#### Scenario: Повторный отказ уходит вызывающему

- **WHEN** публикация падает и после переоткрытия
- **THEN** исключение пробрасывается вызывающему
