# webhook-intake Specification

## Purpose

Определяет приёмную часть конвейера автоматического ревью (Context Level 1): как система принимает вебхуки GitHub, проверяет их подлинность, решает, какие события pull request запускают ревью, а какие игнорируются, достаёт метаданные PR через VCS-шлюз и ставит задачу ревью в очередь, передавая воркеру идентификаторы, а не содержимое, и как повторяются доставки, которые приём не принял; дифф с лимитом размера достаёт и разбирает на файлы и hunk'и воркер конвейера ревью.

## Requirements

### Requirement: Проверка подлинности вебхука

Система SHALL проверять подпись вебхука до любой обработки payload'а: HMAC-SHA256 сырого тела с секретом вебхука, заголовок `X-Hub-Signature-256`, формат `sha256=<hex>`. Сравнение SHALL идти за постоянное время, без раннего выхода по длине или первым различающимся байтам. Вебхук без подписи или с подписью не того формата, ключа или тела SHALL получать HTTP 401, и SHALL NOT создаваться записей в базе и публиковаться сообщений в очередь.

#### Scenario: Валидная подпись пропускает вебхук

- **WHEN** приходит вебхук с корректной подписью `sha256=<hex>` в заголовке `X-Hub-Signature-256`
- **THEN** запрос продолжает обрабатываться по правилам событий pull request

#### Scenario: Отсутствующая подпись отклоняется

- **WHEN** приходит вебхук без заголовка `X-Hub-Signature-256`
- **THEN** ответ — HTTP 401, записей не создаётся и очередь не трогается

#### Scenario: Неверная подпись отклоняется

- **WHEN** подпись в заголовке не соответствует HMAC-SHA256 тела с секретом вебхука, включая подпись без префикса `sha256=<hex>` и подпись по другому телу
- **THEN** ответ — HTTP 401, записей не создаётся и очередь не трогается

#### Scenario: Подпись проверяется до разбора payload'а

- **WHEN** приходит вебхук с неверной подписью и телом, не являющимся корректным JSON
- **THEN** ответ — HTTP 401, а не ошибка разбора JSON

### Requirement: Неподдержанный провайдер получает 501

Маршрут приёма провайдер-нейтральный (`/api/v1/webhooks/{provider}`), но приём SHALL поддерживаться только для провайдеров с реализованным адаптером (GitHub). Вебхук провайдера без адаптера SHALL получать HTTP 501: записей не создаётся, очередь не трогается. Добавление провайдера — новый адаптер без изменения маршрута.

#### Scenario: Вебхук неподдержанного провайдера получает 501

- **WHEN** приходит вебхук на провайдере без адаптера (например, `gitlab`)
- **THEN** ответ — HTTP 501, записей нет и очередь не трогается

#### Scenario: Маршрут не меняется с появлением провайдера

- **WHEN** добавляется адаптер нового провайдера
- **THEN** маршрут остаётся `/api/v1/webhooks/{provider}`, и обработка подчиняется общим требованиям этой спеки

### Requirement: Незарегистрированный репозиторий игнорируется

Вебхук для репозитория, которого нет в системе, SHALL получать HTTP 202 (ignored) без создания записей и без постановки задач. Регистрация репозитория на лету по вебхуку SHALL NOT выполняться: регистрацию выполняет отдельная операция с авторизацией.

#### Scenario: Вебхук незарегистрированного репозитория не создаёт записей

- **WHEN** приходит валидный вебхук `pull_request.opened` для репозитория, не зарегистрированного в системе
- **THEN** ответ — HTTP 202 (ignored), записей не создаётся и задача не ставится

#### Scenario: Репозиторий не регистрируется автоматически

- **WHEN** валидный вебхук для незарегистрированного репозитория приходит повторно
- **THEN** репозиторий по-прежнему не зарегистрирован, а реакция системы не изменилась

### Requirement: Получение диффа через VCS-шлюз

Приём вебхука SHALL получать через порт `VcsGateway` только метаданные PR, installation-токеном GitHub App по `installation_id` из payload'а; дифф приём SHALL NOT запрашивать. Базовый коммит SHALL браться из свежих метаданных PR, одинаково для `opened` и `synchronize`. Ошибка VCS на метаданных SHALL давать HTTP 502; прогон SHALL NOT создаваться, задача SHALL NOT ставиться. Дифф SHALL получать воркер тем же портом по `installation_id` и паре SHA из сообщения очереди.

#### Scenario: Дифф достаётся по installation_id из payload'а

- **WHEN** обрабатывается вебхук зарегистрированного репозитория и задача ревью по нему
- **THEN** метаданные PR при приёме и дифф в воркере запрашиваются с авторизацией по installation-токену для `installation_id` из payload'а этого вебхука, без настройки инсталляции в конфигурации сервиса

#### Scenario: Базовый коммит — из метаданных PR

- **WHEN** создаётся задача ревью для любого действия, запускающего ревью
- **THEN** базовый коммит задачи совпадает с базовым коммитом из свежих метаданных PR, а не берётся из поля payload'а

#### Scenario: Ошибка VCS — 502

- **WHEN** VCS API недоступен или отвечает ошибкой на запрос метаданных
- **THEN** ответ — HTTP 502, прогон ревью не создаётся и задача не ставится

#### Scenario: Приём не запрашивает дифф

- **WHEN** вебхук запускаемого действия создаёт прогон и ставит задачу
- **THEN** через `VcsGateway` запрошены только метаданные PR, дифф не запрашивается

### Requirement: Фильтрация шума в диффе

Перед ревью из разобранного воркером диффа SHALL отфильтровываться файлы, не подлежащие ревью: lock-файлы (перечень — в сценарии «Перечень lock-файлов»), минифицированные (`*.min.js`, `*.min.css`), сгенерированные (`*.generated.*`, `*.pb.go`), бинарные и из `vendor/` и `node_modules/`. Обычные исходники SHALL проходить фильтр неизменёнными. Правила SHALL жить в одном месте — чистой функции домена `filter_diff_files`, без дублирования в адаптерах.

#### Scenario: Перечень lock-файлов

- **WHEN** дифф содержит любой из файлов `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `composer.lock`, `Cargo.lock`, `Gemfile.lock`, `go.sum` или другой lock-файл
- **THEN** этот файл исключается из результата фильтрации

#### Scenario: Lock-файл отфильтрован

- **WHEN** дифф содержит `package-lock.json` или иной lock-файл
- **THEN** этот файл исключается из результата фильтрации

#### Scenario: Минифицированный и сгенерированный код отфильтрован

- **WHEN** дифф содержит `*.min.js`, `*.min.css`, `*.generated.*` или `*.pb.go`
- **THEN** эти файлы исключаются из результата фильтрации

#### Scenario: Бинарные и вендорные пути отфильтрованы

- **WHEN** дифф содержит бинарный файл или файл внутри `vendor/` либо `node_modules/`
- **THEN** эти файлы исключаются из результата фильтрации

#### Scenario: Обычные исходники проходят фильтр

- **WHEN** дифф содержит обычные файлы исходного кода
- **THEN** они остаются в результате фильтрации с нетронутыми hunk'ами

### Requirement: Сбой постановки задачи переводит прогон в failed

Сбой публикации задачи в брокер после закоммиченного прогона SHALL переводить прогон в терминальное `failed` с причиной сбоя, а вебхук SHALL получать 5xx; GitHub такую доставку сам не повторяет — её переотправляет задача #149. Повторная доставка создаёт новый прогон — `failed` её не блокирует. Компенсация SHALL NOT маскировать исходную ошибку: прогон в терминальном состоянии не переписывается; если компенсация не удалась, ответ остаётся 5xx, а зависший прогон выметает sweep обработки.

#### Scenario: Сбой брокера переводит прогон в failed

- **WHEN** публикация задачи в очередь завершается исключением после закоммиченного прогона
- **THEN** прогон переводится в `failed` с причиной сбоя, и вебхук отвечает 5xx

#### Scenario: Повторная доставка после сбоя создаёт новый прогон

- **WHEN** после сбоя постановки приходит повторная доставка того же коммита
- **THEN** создаётся новый прогон в `queued` и задача ставится в очередь — `failed` повтор не блокирует

#### Scenario: Ответ остаётся 5xx, даже если компенсация не удалась

- **WHEN** публикация упала и компенсация не смогла записать `failed`
- **THEN** вебхук всё равно отвечает 5xx

### Requirement: Публикация переживает простой соединения

Адаптер очереди SHALL публиковать задачу, даже если брокер закрыл простаивавшее соединение, а клиент ещё считает его открытым (`is_closed` — `False`): при отказе публикации из-за соединения или закрытого канала адаптер переоткрывает обе стороны, объявляет топологию и повторяет публикацию один раз. Повторный отказ SHALL пробрасываться вызывающему, где его обрабатывает компенсация приёма. Отказы публикации (nack, unroutable) повторяться SHALL NOT.

#### Scenario: Проявившееся соединение переоткрывается, задача публикуется

- **WHEN** публикация падает из-за соединения, закрытого брокером после простоя, а `is_closed` ещё `False`
- **THEN** адаптер открывает новое соединение, публикует задачу, и вызывающий исключения не получает

#### Scenario: Повторный отказ уходит вызывающему

- **WHEN** публикация падает и после переоткрытия
- **THEN** исключение пробрасывается вызывающему

### Requirement: Действия opened и synchronize запускают ревью

Система SHALL запускать прогон ревью по событиям `pull_request` с действиями `opened` и `synchronize` своего PR (требование «Ревьюится только свой PR»). Для них SHALL создаваться или обновляться запись запроса на изменение — при `synchronize` head-коммит существующей записи сдвигается на новый — и создаваться прогон ревью в состоянии `queued` с источником прогона `webhook`, после чего задача ревью SHALL ставиться в очередь. Успешный ответ — HTTP 202.

#### Scenario: Открытие PR запускает ревью

- **WHEN** приходит `pull_request` с действием `opened` и валидной подписью для зарегистрированного репозитория, ветка PR в самом репозитории
- **THEN** ответ — HTTP 202, существует запись запроса на изменение и прогон ревью в состоянии `queued` с источником `webhook`, и в очереди появляется задача ревью

#### Scenario: Новый коммит в PR запускает новый прогон

- **WHEN** приходит `pull_request` с действием `synchronize` с валидной подписью для зарегистрированного репозитория, ветка PR в самом репозитории
- **THEN** ответ — HTTP 202, head-коммит существующего запроса на изменение сдвигается на новый, создаётся новый прогон ревью в состоянии `queued`, и задача ставится в очередь

### Requirement: Прочие действия pull request игнорируются

Действия `pull_request` `reopened`, `closed`, `edited` без `changes.base` и любые иные, кроме `opened`, `synchronize` и `edited` со сменой целевой ветки, SHALL получать HTTP 202 (ignored): записей не создаётся, очередь не трогается, ответ — не 5xx. При `reopened` система SHALL NOT переназначать бота ревьюером автоматически: пользователь переназначает его вручную, и следующее событие обрабатывается как обычный запуск.

#### Scenario: Reopened игнорируется

- **WHEN** приходит `pull_request` с действием `reopened`
- **THEN** ответ — HTTP 202 (ignored), записей не создаётся и в очередь ничего не уходит, а бот не переназначается ревьюером автоматически

#### Scenario: Неизвестное действие игнорируется без сбоя

- **WHEN** приходит `pull_request` с действием, отличным от `opened`, `synchronize`, `edited` и `reopened` (например, `closed`)
- **THEN** ответ — HTTP 202 (ignored), а не 5xx, записей нет и очередь не трогается

#### Scenario: Правка заголовка или описания игнорируется

- **WHEN** приходит `pull_request` `edited`, в `changes` которого нет `base`
- **THEN** ответ — HTTP 202 (ignored), записей нет и очередь не трогается

### Requirement: Гонка параллельных доставок разрешается по естественному ключу

Гонку доставок страхуют частичные уникальные индексы. Доставка, чью вставку отклонил индекс, после отката SHALL искать записи победителя по естественному ключу (репозиторий, номер): есть активный прогон на тот же коммит — проигравший отвечает его проекцией; у победителя другой коммит и только merge_request — проигравший создаёт новый прогон на доставленный коммит поверх его записей. Второй отказ индекса SHALL пробрасываться наверх: ответ 5xx.

#### Scenario: Проигравший гонку на тот же коммит отвечает прогоном победителя

- **WHEN** две параллельные доставки создают прогон на один и тот же коммит, и уникальный индекс отклоняет вторую вставку
- **THEN** проигравший после отката отвечает HTTP 202 с проекцией активного прогона победителя

#### Scenario: Победитель гонки с другим коммитом получает новый прогон

- **WHEN** в гонке первых доставок победитель нёс другой head-коммит, и активного прогона на доставленный коммит у него нет
- **THEN** проигравший после отката обновляет merge_request победителя и создаёт новый прогон на доставленный коммит, а второй отказ индекса даёт 5xx

### Requirement: Приём не разбирает и не хранит дифф

Вебхук SHALL NOT запрашивать и разбирать дифф: приёмная часть получает только метаданные PR (ошибка VCS на них даёт 502 до создания записей). Дифф SHALL NOT сохраняться в базе ни вебхуком, ни воркером: он транзиентен в обработке задачи, а сообщение очереди несёт идентификаторы (`head_sha`, `base_sha`, номер PR), по которым воркер достаёт дифф с лимитом размера и разбирает его.

#### Scenario: Дифф не персистится

- **WHEN** приём вебхука завершился созданием прогона и постановкой задачи
- **THEN** в базе появляются только записи запроса на изменение и прогона ревью, сообщение очереди содержит идентификаторы, а не содержимое диффа, а дифф достаёт и разбирает воркер при обработке задачи

### Requirement: Воркер разбирает дифф на файлы и hunk'и

Разбор unified diff на файлы и hunk'и SHALL выполнять воркер конвейера ревью при обработке задачи, достав дифф по идентификаторам из сообщения очереди, — чистой функцией `parse_diff`: для каждого файла — путь, старый путь при переименовании, признак бинарности и hunk'и с точными номерами строк из заголовков `@@ -a,b +c,d @@`.

#### Scenario: Multi-file дифф разбирается на файлы и hunk'и

- **WHEN** воркер разбирает дифф, затрагивающий несколько файлов
- **THEN** каждый файл разобран на hunk'и, и изменённые строки несут точные номера строк новой и старой версии

#### Scenario: Бинарный файл распознаётся

- **WHEN** дифф содержит бинарный файл
- **THEN** файл помечается бинарным, его hunk'и пусты, и разбор остальных файлов продолжается

#### Scenario: Переименование даёт оба пути

- **WHEN** дифф содержит переименованный файл
- **THEN** разобранный файл несёт и старый, и новый путь

### Requirement: Крайние случаи разбора диффа

При разборе диффа функцией `parse_diff` строки контекста (пробел в начале) SHALL NOT попадать в множества изменённых строк, но SHALL сдвигать счётчики строк; маркер `\ No newline at end of file` SHALL NOT ломать разбор; пустой дифф SHALL давать пустой список файлов.

#### Scenario: Строки контекста сдвигают счётчики, но не считаются изменёнными

- **WHEN** hunk содержит строки контекста, начинающиеся с пробела
- **THEN** они не попадают в множества изменённых строк, а номера следующих за ними строк учитывают их

#### Scenario: Маркер отсутствия перевода строки не ломает разбор

- **WHEN** дифф содержит строку `\ No newline at end of file`
- **THEN** разбор завершается успешно, и маркер не попадает в изменённые строки

#### Scenario: Пустой дифф даёт пустой список файлов

- **WHEN** разбирается пустой дифф
- **THEN** результат — пустой список файлов

### Requirement: Задача ревью ставится в очередь с доменными данными

Задача ревью SHALL ставиться через порт `JobQueue` единственным методом `enqueue`. Тело — JSON только с доменными данными по `docs/SYSTEM_DESIGN.md` §4.2: `job_id` (новый на постановку), `review_run_id`, `event_type`, `action`, `repository`, `pull_request` (номер, `head_sha`, `base_sha`) и `installation_id` для повторного получения воркером диффа и метаданных PR. Для игнорируемых событий и отклонённых вебхуков SHALL NOT публиковаться сообщений.

#### Scenario: Сообщение несёт только доменные данные

- **WHEN** прогон ревью успешно создан и задача поставлена в очередь
- **THEN** тело сообщения соответствует формату `docs/SYSTEM_DESIGN.md` §4.2 и не содержит ни диффа, ни метаданных доставки

#### Scenario: Две постановки одного прогона различимы

- **WHEN** один и тот же прогон ставится в очередь дважды
- **THEN** у двух сообщений разные `job_id` и одинаковый `review_run_id`

#### Scenario: Сообщение несёт installation_id из события

- **WHEN** вебхук обработан и задача поставлена в очередь
- **THEN** `installation_id` в сообщении совпадает с идентификатором инсталляции из payload'а доставленного вебхука, так что воркер авторизуется той же инсталляцией, что и приём

#### Scenario: Игнорируемое событие ничего не публикует

- **WHEN** вебхук завершается как ignored или отклонён по подписи
- **THEN** в очереди не появляется нового сообщения

### Requirement: Вебхук закрытия треда ревью

Эндпоинт приёма вебхуков SHALL обрабатывать событие GitHub
`pull_request_review_thread` с действиями `resolved` и `unresolved`: при валидной
подписи и зарегистрированном репозитории система SHALL обновить `thread_resolved`
у соответствующей записи `published_comments` по `comment.id` из payload и
ответить HTTP 202.

#### Scenario: Тред закрыт вручную на GitHub

- **WHEN** приходит `pull_request_review_thread` с `action=resolved` для комментария,
  опубликованного сервисом
- **THEN** у корневой inline-записи выставляется `thread_resolved=true`

### Requirement: Тело 202 приёма вебхука — модель схемы

Ответ `202` приёма вебхука SHALL быть одной из моделей схемы: `ReviewJob` со всеми полями — поле без значения приходит как `null`, время — в UTC с `Z`, — `{"status": "ignored"}` или `{"status": "acknowledged"}` для `pull_request_review_thread`.

#### Scenario: Новый прогон

- **WHEN** подписанный `pull_request` `opened` создал прогон
- **THEN** тело `202` проходит модель `ReviewJob`, `model`, `tokens_used`, `duration_seconds`, `failed_stage` и `error` — `null`, `created_at` оканчивается на `Z`

### Requirement: Дифф делится на строки только по переводу строки

Функция `parse_diff` SHALL делить дифф на строки только по `\n`, как его делят git и GitHub; один `\r` перед `\n` SHALL NOT попадать в строку. Прочие разделители строк Unicode (`\x0b`, `\x0c`, `\x1c`–`\x1e`, `\x85`, ` `, ` `) и `\r` внутри строки SHALL оставаться её содержимым: они не сдвигают номера строк и не начинают заголовок файла или hunk'а.

#### Scenario: Посторонний разделитель строк внутри строки кода

- **WHEN** добавленная строка содержит `\x0c`, `\x85`, ` ` или другой разделитель, кроме `\n`, а за ним — `diff --git a/evil.py b/evil.py` или `@@ -100 +100 @@`
- **THEN** строка остаётся одной: номера следующих строк не сдвигаются, фальшивого файла и фальшивого hunk'а нет

#### Scenario: Дифф с CRLF

- **WHEN** строки диффа заканчиваются на `\r\n`
- **THEN** разбор даёт те же файлы, номера и текст hunk'ов без `\r`, что и для того же диффа с `\n`

### Requirement: Лимит размера диффа в воркере

Воркер SHALL получать дифф с лимитом размера `DIFF_MAX_BYTES` (по умолчанию 5 МиБ): тело ответа читается потоком и SHALL NOT дочитываться дальше лимита. Дифф прогона больше лимита SHALL переводить прогон в `failed` с причиной «дифф больше лимита», а шаг `fetching_diff` — в `failed` с кодом `DIFF_TOO_LARGE`; модель SHALL NOT вызываться, частичное ревью SHALL NOT публиковаться, повторная доставка задачи SHALL NOT перезапускать прогон.

#### Scenario: Дифф больше лимита — прогон failed без ревью

- **WHEN** воркер получает дифф прогона больше `DIFF_MAX_BYTES`
- **THEN** прогон — `failed` с причиной «дифф больше лимита», шаг `fetching_diff` — `failed` с кодом `DIFF_TOO_LARGE`, модель не вызывается и на PR ничего не публикуется

#### Scenario: Тело диффа не дочитывается дальше лимита

- **WHEN** VCS отдаёт дифф больше лимита — с объявленной длиной или потоком без неё
- **THEN** загрузка обрывается не позже лимита, остаток тела не читается

#### Scenario: GitHub отказался строить дифф

- **WHEN** GitHub отвечает `422` на сравнение коммитов прогона (дифф слишком велик для GitHub)
- **THEN** прогон — `failed` с причиной «дифф больше лимита», шаг `fetching_diff` — `failed` с кодом `DIFF_TOO_LARGE`, модель не вызывается и на PR ничего не публикуется

### Requirement: Упавшие доставки повторяются

GitHub неудачные доставки сам не повторяет, поэтому воркер SHALL периодически запрашивать доставки вебхука приложения GitHub App за последние трое суток с аутентификацией JWT приложения и SHALL переотправлять доставку, у которой ни одна попытка с тем же `guid` не была успешной. Переотправляются только события приёма: `pull_request` `opened`/`synchronize`/`edited` своего PR, если её коммит — всё ещё голова PR, и `pull_request_review_thread` `resolved`/`unresolved`.

#### Scenario: Упавшая доставка переотправляется

- **WHEN** в списке доставок есть `pull_request` `synchronize` с ответом 5xx и без успешной попытки с тем же `guid`
- **THEN** воркер вызывает переотправку этой доставки

#### Scenario: Успешно переотправленная доставка больше не трогается

- **WHEN** у доставки с ответом 5xx есть более поздняя успешная попытка с тем же `guid`
- **THEN** переотправка не вызывается

#### Scenario: Устаревшая доставка не повторяется

- **WHEN** упала доставка `pull_request`, а голова PR по свежим метаданным уже другой коммит, чем `pull_request.head.sha` в её payload
- **THEN** переотправка не вызывается, и в лог пишется, что доставка устарела

#### Scenario: Чужие события не переотправляются

- **WHEN** упала доставка события, которое приём не обрабатывает (например, `push` или `pull_request` `closed`)
- **THEN** переотправка не вызывается

#### Scenario: Доставка PR постороннего не повторяется

- **WHEN** упала доставка `pull_request` `opened` из форка с `author_association = NONE`
- **THEN** переотправка не вызывается и к GitHub за метаданными PR воркер не обращается: приём всё равно ответил бы `ignored`

#### Scenario: Без реквизитов GitHub App повтор выключен

- **WHEN** у сервиса не задан идентификатор или приватный ключ GitHub App, или повтор выключен настройкой
- **THEN** воркер не обращается к API доставок и один раз пишет об этом в лог при старте

### Requirement: Повтор доставок ограничен

Повтор SHALL NOT нагружать API GitHub: за проход воркер SHALL делать запросы последовательно, читать не больше ограниченного числа страниц списка и переотправлять не больше настроенного числа доставок за бюджет времени прохода; одна доставка (`guid`) SHALL переотправляться не больше настроенного числа раз и не раньше, чем истекла пауза, растущая вдвое с каждой попыткой. Отказ лимита GitHub SHALL завершать проход. Двойная переотправка безвредна: повтор отвечает существующим прогоном.

#### Scenario: Попытки исчерпаны

- **WHEN** у упавшей доставки уже столько переотправок, сколько разрешено настройкой
- **THEN** переотправка больше не вызывается

#### Scenario: Пауза ещё не истекла

- **WHEN** последняя попытка доставки была позже, чем пауза для её числа попыток
- **THEN** в этом проходе доставка не переотправляется

#### Scenario: Бюджет времени прохода исчерпан

- **WHEN** проход повтора работает дольше настроенного бюджета
- **THEN** оставшиеся доставки в этом проходе не трогаются и ждут следующего

#### Scenario: Предел запросов за проход

- **WHEN** упавших доставок больше, чем разрешено переотправить за проход
- **THEN** переотправляются самые старые в пределах лимита, остальные — в следующих проходах

#### Scenario: Постоянный отказ не повторяется

- **WHEN** проверка или переотправка доставки получила постоянный отказ GitHub (например, 404 у удалённого PR или 422 у доставки вне окна)
- **THEN** доставка пропускается, и в следующих проходах того же воркера к ней не уходит ни одного запроса

#### Scenario: Устаревшие доставки не вытесняют нужные

- **WHEN** среди старых упавших доставок устаревших больше, чем лимит переотправок за проход, а новее них есть доставка текущей головы PR
- **THEN** доставка текущей головы переотправляется в том же проходе, лимит считает только переотправки, а устаревшие в следующих проходах того же воркера не запрашиваются

### Requirement: Смена целевой ветки запускает ревью

Событие `pull_request` с действием `edited`, в котором есть `changes.base`, а целевая ветка в свежих метаданных PR отличается от записанной у запроса на изменение, SHALL запускать прогон ревью так же, как `synchronize`: тот же head-коммит с другой базой — другой дифф, а check run merge gate висит на head-коммите и о базе не знает. Базовый коммит SHALL браться из свежих метаданных PR. Активный прогон на этот head-коммит SHALL переводиться в `cancelled` своим коммитом до создания нового прогона.

#### Scenario: Смена целевой ветки после завершённого ревью

- **WHEN** прогон на head-коммит завершился `completed` с check run `success`, а затем приходит `edited` с `changes.base` и другой целевой веткой в свежих метаданных
- **THEN** создаётся новый прогон в `queued` с новой базой, задача ставится в очередь, и check run на head-коммите выставляет уже он

#### Scenario: Смена целевой ветки во время ревью

- **WHEN** прогон на head-коммит со старой веткой ещё не завершён, и приходит `edited` с `changes.base`
- **THEN** этот прогон переводится в `cancelled`, создаётся новый прогон в `queued` с новой базой

#### Scenario: Повтор доставки смены ветки

- **WHEN** смена ветки уже принята, и приходит повтор той же доставки `edited`
- **THEN** ответ — дубль: ветка у PR уже записана новой

### Requirement: Смена целевой ветки блокирует merge gate до нового ревью

При смене целевой ветки приём SHALL выставить на head-коммит check run merge gate с `conclusion=failure` после коммита отмены и нового прогона и до постановки задачи: прежний `success` описывает чужой дифф. Сбой GitHub на блокировке SHALL давать HTTP 502 без задачи; новый прогон SHALL переводиться в `failed`, а запросу на изменение SHALL возвращаться прежняя целевая ветка.

#### Scenario: Окно между сменой ветки и новым ревью закрыто

- **WHEN** на head-коммите check run `success` по старой ветке, и приходит `edited` со сменой целевой ветки
- **THEN** до постановки нового прогона на head-коммит выставлен check run `failure`; если новое ревью упадёт, он остаётся

#### Scenario: Воркер старого прогона выставил gate после блокировки

- **WHEN** прогон на старой ветке прочитал свой статус до отмены и выставил `success` уже после блокировки приёма
- **THEN** перечитав последний прогон на head, он выставляет `failure` снова (требование «Отменённый прогон не выставляет merge gate», `review-pipeline`)

#### Scenario: GitHub недоступен на блокировке

- **WHEN** выставить блокирующий check run не удалось
- **THEN** ответ — HTTP 502, задача не ставится, новый прогон — `failed`, у PR прежняя ветка; повтор доставки снова блокирует head и создаёт прогон

### Requirement: Повторная доставка на проверенный коммит отвечает существующим прогоном

Вебхук на head-коммит, у которого есть активный прогон или завершённый не-`failed` прогон по вебхуку, SHALL NOT создавать новый прогон и ставить задачу, если последний прогон на этот коммит не `failed` и не `cancelled`. Ответ SHALL быть HTTP 202 с проекцией найденного прогона. Дубль SHALL проверяться до обновления merge_request и SHALL NOT переписывать записи.

#### Scenario: Повторная доставка безвредна

- **WHEN** приходит вебхук для head-коммита, у которого уже есть прогон в нетерминальном состоянии
- **THEN** второй активный прогон не создаётся, и ответ — не 5xx

#### Scenario: Повторная доставка отвечает 202 с проекцией существующего прогона

- **WHEN** приходит вебхук для head-коммита, у которого уже есть активный прогон
- **THEN** ответ — HTTP 202 с проекцией `ReviewJob` существующего прогона, новых записей нет и очередь не трогается

#### Scenario: Повтор после завершения прогона — один прогон и одно ревью

- **WHEN** приходит вебхук для head-коммита, прогон по вебхуку для которого уже завершился в `completed`, в том числе с тем же `X-GitHub-Delivery`
- **THEN** ответ — HTTP 202 с проекцией завершённого прогона, новый прогон не создаётся, задача не ставится, и второе ревью не публикуется

#### Scenario: Вершина целевой ветки сдвинулась

- **WHEN** прогон на head-коммит завершён, в целевую ветку влили другой PR, и приходит повтор доставки того же head-коммита с новой `base_sha` в метаданных
- **THEN** ответ — дубль: check run не трогается, новый прогон не создаётся

#### Scenario: Последний прогон на коммит упал после завершённого

- **WHEN** у head-коммита есть завершённый прогон, а более поздний прогон на него же (ревью после смены ветки) упал, и приходит повтор доставки
- **THEN** создаётся новый прогон в `queued` и задача ставится в очередь

#### Scenario: Повтор после failed создаёт новый прогон

- **WHEN** приходит вебхук для head-коммита, единственный прогон которого завершился в `failed`
- **THEN** создаётся новый прогон в `queued` и задача ставится в очередь

#### Scenario: Новый коммит после активного прогона запускает новый прогон

- **WHEN** приходит вебхук с новым head-коммитом для запроса на изменение, у которого есть активный прогон на предыдущем коммите
- **THEN** создаётся новый прогон ревью для нового коммита, а предыдущий прогон по-прежнему указывает свой коммит

### Requirement: Тело вебхука читается с лимитом до подписи

Тело доставки SHALL читаться с лимитом `WEBHOOK_BODY_MAX_BYTES` (по умолчанию 2 МиБ — с запасом над доставками `pull_request` и `pull_request_review_thread`) до проверки подписи. Тело больше лимита SHALL отклоняться `413` `REQUEST_BODY_TOO_LARGE` без проверки подписи, записей в базе и сообщений в очередь; как ограничивается чтение — требование «Тело запроса ограничено по размеру» в `review-rest-api`.

#### Scenario: Объявленная длина больше лимита

- **WHEN** приходит доставка с `Content-Length` больше лимита
- **THEN** ответ — `413` `REQUEST_BODY_TOO_LARGE`, тело у сервера не запрашивается, подпись не проверяется

#### Scenario: Поток без длины больше лимита

- **WHEN** приходит доставка chunked без `Content-Length` больше лимита с верной подписью
- **THEN** ответ — `413` `REQUEST_BODY_TOO_LARGE`, чтение оборвано на куске, где сумма перешла лимит, подпись не проверяется

#### Scenario: Тело в пределах лимита

- **WHEN** приходит подписанная доставка размером ровно в лимит — с `Content-Length` или chunked
- **THEN** она обрабатывается как раньше: подпись проверяется, исход определяется событием и телом

### Requirement: Приоритет задачи — свойство AMQP-сообщения

Приоритет задачи ревью SHALL передаваться свойством AMQP-сообщения, а не полем тела; очередь SHALL быть quorum-очередью, у которой приоритеты включены всегда.

#### Scenario: Приоритет живёт в свойствах AMQP

- **WHEN** задача публикуется в очередь
- **THEN** приоритет передан свойством AMQP-сообщения, а в теле сообщения поля приоритета нет

#### Scenario: Очередь учитывает приоритет без отдельного аргумента

- **WHEN** адаптер очереди публикует первое сообщение
- **THEN** очередь объявлена quorum-очередью без `x-max-priority`, и приоритеты сообщений учитываются при выдаче

### Requirement: Ревьюится только свой PR

PR свой, если его ветка лежит в самом репозитории (`pull_request.head.repo` — тот же репозиторий, что `repository`) или `author_association` автора — `OWNER`, `MEMBER` или `COLLABORATOR`. Чужой PR (из форка, в том числе с пустым `head.repo`, от остальных авторов) SHALL получать `202 ignored` без записей, задачи и check run, а отказ SHALL писаться в лог с репозиторием, номером PR и `author_association` полями записи.

#### Scenario: Скрытый участник организации

- **WHEN** приходит `pull_request` `opened` с `author_association = CONTRIBUTOR`, а ветка PR в самом репозитории
- **THEN** прогон создаётся и задача ставится в очередь, как обычно

#### Scenario: PR коллаборатора из форка

- **WHEN** приходит `pull_request` `opened` из форка с `author_association = COLLABORATOR`
- **THEN** прогон создаётся и задача ставится в очередь, как обычно

#### Scenario: PR из форка от постороннего

- **WHEN** приходит `pull_request` `opened` из форка с `author_association = FIRST_TIME_CONTRIBUTOR`
- **THEN** ответ `202 ignored`, записей нет, очередь не трогается, в логе запись с репозиторием, номером PR и `author_association`

#### Scenario: Форк удалён

- **WHEN** приходит `pull_request` `synchronize` с пустым `head.repo` и `author_association = CONTRIBUTOR`
- **THEN** ответ `202 ignored`, прогона нет

#### Scenario: PR постороннего — проверки нет

- **WHEN** приходит `pull_request` `opened` или `synchronize` из форка с `author_association = NONE` для подключённого или выключенного репозитория
- **THEN** ответ `202 ignored`, прогона нет, check run `dmc-268-ai-review` на `head_sha` не ставится
